代码是大语言模型智能体进展最快的领域，原因在于其结构而非偶然。代码是文本，所以在文本上训练出来的模型就能写代码。代码可执行，所以智能体能自己弄清它写的东西管不管用，无须问任何人。而且代码可检验：一套测试就是一个自动、可重复、大体诚实的检验器——正是 [[agents/agent-loops#prop-retry]] 指认为可靠智能体之稀缺资源的那种检测信号。一个写出函数、跑测试、读失败信息、再修复函数的模型，就是智能体循环处于最有利的环境。

本章将代码模型从单个函数带到整个代码仓库。先讲代码生成及其度量：Chen 等（2021）的 HumanEval 基准与 pass@$k$ 度量，并导出后者的无偏估计量。随后把代码变成一种动作——智能体为计算、探索、检验而运行的程序——并分析**执行反馈**：测试通过何时意味着程序正确，以及采样与过滤能做到什么（AlphaCode；Li 等，2022）。后半部分讲在真实代码库中浏览、编辑、测试的软件工程智能体，用 SWE-bench（Jimenez 等，2024）及其人工校验的子集来度量；还讲使「执行模型写的代码」这件事可以接受的根本设计原则：**沙箱化**。配有一个普通 Python 清单：在一个隔离的解释器里运行生成–测试–修复循环，并计算 pass@$k$。

## 代码生成及其度量 {#sec-generation}

在网页文本上训练的语言模型本来就会写短程序，因为网页上有大量的代码。Chen 等（2021）用公开 GitHub 仓库里的 $159$ GB Python 代码微调 GPT 模型，称之为 **Codex**，并建立了一个度量功能正确性（而非与参考实现的文本相似度）的基准。

::: definition HumanEval 与功能正确性 {#def-humaneval}
**HumanEval** 由 $164$ 道手写的 Python 编程题构成。每题给出一个函数签名和一段描述目标行为的 docstring，有时附示例；模型必须补全函数体。若一个补全在隔离环境中带时限地通过了该题隐藏的单元测试（平均每题 $7.7$ 个），就称其**功能正确**。
:::

从机器翻译继承下来的 BLEU 之类的文本指标对代码而言靠不住：两个程序可以共享大部分词元而行为不同，也可以几乎不共享而彼此等价。运行测试才度量到要紧的东西。但可以让模型给出多个样本，而只要任何一个通过的样本都有用——因为测试能分辨哪个通过——自然的度量就是 $k$ 个样本中至少一个通过的概率。

::: definition pass@$k$ {#def-passk}
对某问题，模型单个样本正确的概率为 $p$，则 **pass@$k$** 是 $k$ 个独立样本中至少一个正确的概率 $1 - (1 - p)^k$；一个基准的 pass@$k$ 是各问题上的平均。为估计它，每个问题抽 $n\ge k$ 个样本，数出其中正确的 $c$ 个，并用
$$
\widehat{\text{pass@}k} = 1 - \frac{\binom{n - c}{k}}{\binom{n}{k}}.
$$ {#eq-passk}
:::

::: proposition pass@$k$ 估计量是无偏的 {#prop-passk}
对单个问题，若 $n$ 个样本相互独立、每个以概率 $p$ 正确，则 $\E\big[\widehat{\text{pass@}k}\big] = 1 - (1 - p)^k$。代入估计量 $1 - (1 - c/n)^k$ 只要 $0 < p < 1$，对 $1 < k\le n$ 就向下有偏。
:::

::: proof
$\binom{n - c}{k}/\binom{n}{k}$ 是从 $n$ 个样本中均匀随机取的 $k$ 元子集不含 $c$ 个正确样本中任何一个的概率。给定样本时，它就是 $\Prob(\text{某个随机 } k\text{ 元子集不含正确样本}\mid\text{样本})$；再对样本取期望，它等于从 $n$ 个独立同分布样本中随机取的 $k$ 个样本全错的概率。独立同分布样本的随机 $k$ 元子集本身就是 $k$ 个独立同分布样本，所以这个概率是 $(1 - p)^k$，无偏性得证。至于代入估计量：$x\mapsto(1 - x)^k$ 当 $k > 1$ 时在 $[0, 1]$ 上严格凸，故由琴生（Jensen）不等式，当 $c/n$ 不是几乎必然为常数——即 $0 < p < 1$——时，$\E[(1 - c/n)^k] > (1 - \E[c/n])^k = (1 - p)^k$；于是 $\E[1 - (1 - c/n)^k] < 1 - (1 - p)^k$。
:::

Chen 等报告：一个 $12$ 亿参数的 Codex 单次采样解出 HumanEval 的 $28.8\%$，$100$ 次采样（pass@$100$）则达 $70.2\%$，而 GPT-3 一个也解不出。pass@$1$ 与 pass@$100$ 之差是本章最重要的数字：它说明一个通常失败的模型往往**有时能成**，于是任何能挑出成功样本的东西都能把广度变成准确率。作为通用策略的重复采样，以及作为其度量的 pass@$k$，在 [[reasoning/test-time-scaling]] 与 [[reasoning/self-consistency]] 中讨论。

::: example 估计 pass@$k$ {#ex-passk}
某模型在一个问题上采样 $n = 10$ 次，$c = 3$ 个样本通过。用 [[#eq-passk]] 估计 pass@$1$、pass@$5$、pass@$10$，并与代入式 $1 - (1 - c/n)^k$ 比较。
::: solution
pass@$1$：$1 - \binom{7}{1}/\binom{10}{1} = 1 - 7/10 = 0.3$。pass@$5$：$1 - \binom{7}{5}/\binom{10}{5} = 1 - 21/252 = 0.917$。pass@$10$：$\binom{7}{10} = 0$，故为 $1$ ——十个样本全用上，其中必有一个落在三个正确样本之中。代入式给出 $0.3$、$1 - 0.7^5 = 0.832$、$1 - 0.7^{10} = 0.972$。无偏估计量更大，正如 [[#prop-passk]] 所预言；而且它是不放回地使用样本的：代入式则假装接下来的 $k$ 个样本是成功率恰为 $c/n$ 的全新抽样。
:::
:::

### 基准会老化

HumanEval 和 Mostly Basic Python Problems（MBPP；Austin 等，2021，$974$ 题）多年间是标准的代码基准，两者都体现了 [[evaluation/benchmarks]] 描述的基准生命周期。它们的测试太少：Liu 等（2023）给 HumanEval 平均添加了约八十倍于原来的测试（HumanEval+），许多模型的通过率明显下降——通过原测试的程序，在没人查过的输入上是错的。题目是公开的，所以后来的模型可能在训练中见过它们（[[evaluation/contamination]]）；LiveCodeBench（Jain 等，2024）这类基准的应对办法是持续收集新竞赛题，并且只在各模型训练截止之后公布的题目上评测。而且基准饱和了：截至 2026 年，领先模型几乎一次就解出所有 HumanEval 题目，它已无法把它们区分开来。

## 代码作为动作 {#sec-code-action}

到目前为止，代码是**产品**。对智能体而言，代码还是**工具**：它不再调用计算器，而是写 `sum(x * w for x, w in zip(xs, ws))`；不再把大文件读进上下文，而是写个脚本去摘要；不再断言函数正确，而是写个测试。程序辅助语言模型（Gao 等，2023）让模型为算术与符号推理步骤写 Python、交给解释器去算；CodeAct（Wang 等，2024）把可执行的 Python 作为智能体的整个动作空间，于是一个动作可以调用多个工具、循环、分支，并报告在其多工具基准上成功率高于 JSON 式的工具调用。代码动作继承了解释器的精确（算术不出错）与表达能力（一步顶得上多次工具调用），代价是需要一个能安全运行任意代码的解释器——即 [[#sec-sandbox]] 的主题。

### 执行反馈

::: algorithm 生成、测试、修复 {#alg-repair}
给定一个带测试套件的任务（套件由外部提供，或由智能体自己写），以及 $r$ 次尝试的预算：
1. **生成**：从任务与已有的反馈出发，生成一个候选程序。
2. **执行**：在带时间和内存限制的隔离环境中对它运行测试。
3. 若全部测试通过，**返回**该程序。否则提取**反馈**——失败的测试、断言、异常与回溯、或期望输出与实际输出之差——把它追加到上下文，若尝试次数未用完则回到第 1 步。
:::

下面的清单为单个函数实现了这一循环。两份草稿充当模型：第一份对偶数长度列表的中位数算错；第二份像是响应失败的断言而写，处理了那种情形。测试在一个全新的临时目录里运行，运行它的 Python 进程以隔离模式启动（`-I`：不加载用户 site-packages，不接受会改变 Python 行为的环境变量），带最小化的环境与时间限制。这是进程隔离，不是安全沙箱；两者的区别正是 [[#sec-sandbox]] 的主题。清单最后计算 [[#eq-passk]]。

```python
import subprocess, sys, tempfile, os
from math import comb

TESTS = """
import sys; sys.path.insert(0, ".")   # -I 不把 cwd 放进 sys.path
from solution import median
assert median([3, 1, 2]) == 2
assert median([4, 1, 3, 2]) == 2.5
assert median([7]) == 7
assert median([-1, -1, 5, 9]) == 2.0
print("all tests passed")
"""

# 模型可能先后写出的草稿；后面的草稿像是针对反馈的回应。
DRAFTS = [
    "def median(xs):\n    return sorted(xs)[len(xs) // 2]\n",
    "def median(xs):\n    s = sorted(xs)\n    m = len(s) // 2\n"
    "    return (s[m - 1] + s[m]) / 2 if len(s) % 2 == 0 else s[m]\n",
]

def run_tests(code, timeout=5):
    """在一个全新目录里、一个以隔离模式（-I）启动的独立解释器中，
    带时间限制地对 `code` 运行测试。这不是安全沙箱。"""
    with tempfile.TemporaryDirectory() as d:
        open(os.path.join(d, "solution.py"), "w").write(code)
        open(os.path.join(d, "test_solution.py"), "w").write(TESTS)
        try:
            r = subprocess.run([sys.executable, "-I", "test_solution.py"], cwd=d,
                               capture_output=True, text=True, timeout=timeout,
                               env={"PATH": "/usr/bin:/bin"})
        except subprocess.TimeoutExpired:
            return False, "timeout"
        out = [l.strip() for l in (r.stdout + r.stderr).splitlines()
               if l.strip() and set(l.strip()) != {"^"}]       # 去掉脱字符标记
        return r.returncode == 0, " / ".join(out[-2:])

for attempt, code in enumerate(DRAFTS, 1):
    ok, feedback = run_tests(code)
    print(f"attempt {attempt}: {'PASS' if ok else 'FAIL'} | {feedback}")
    if ok:
        break

def pass_at_k(n, c, k):
    """pass@k 的无偏估计量：n 个样本中 c 个正确（Chen et al., 2021）。"""
    if n - c < k:
        return 1.0
    return 1 - comb(n - c, k) / comb(n, k)

for n, c in [(10, 3), (200, 12)]:
    print(n, c, [round(pass_at_k(n, c, k), 4) for k in (1, 5, 10)],
          "naive 1-(1-c/n)^k:", [round(1 - (1 - c / n) ** k, 4) for k in (1, 5, 10)])
```

```text
attempt 1: FAIL | assert median([4, 1, 3, 2]) == 2.5 / AssertionError
attempt 2: PASS | all tests passed
10 3 [0.3, 0.9167, 1.0] naive 1-(1-c/n)^k: [0.3, 0.8319, 0.9718]
200 12 [0.06, 0.2685, 0.4693] naive 1-(1-c/n)^k: [0.06, 0.2661, 0.4614]
```

让修复奏效的正是反馈那一行：不是「错了」，而是**哪个**输入失败了。Chen 等（2024）把这一点作为**自我调试**来研究：让模型在修改前先解释自己的代码和执行结果，报告了一致的收益——在有单元测试反馈可用时收益最大。$n = 200$、$c = 12$ 时两个估计量几乎一致；代入式的偏差要到 $n$ 接近 $k$ 时才要紧。

::: example 代码动作还是工具调用？ {#ex-code-action}
某智能体要求出一个 $5{,}000$ 行电子表格中某一列的总和，每行打印出来约 $12$ 个词元。比较两种做法：用 `read_rows` 工具把行读进上下文、每次调用 $500$ 行；还是写一个短脚本直接算出总和。
::: solution
读取：$10$ 次调用共返回 $60{,}000$ 个词元，上下文必须装下它们（或智能体边走边摘要），然后模型还得在「心算」里把 $5{,}000$ 个数加起来——而模型在长算术上正是会出错的。上下文每次调用增长 $6{,}000$ 个词元，十次调用还要重读约 $6{,}000\cdot(1 + 2 + \dots + 10) = 330{,}000$ 个词元。脚本：一个约 $60$ 个词元的动作，加一个数字作观察；算术由解释器精确完成。脚本在每一项上都更优——词元、延迟、准确率——只要它被放在一个造不成伤害的地方运行。
:::
:::

### 通过何时意味着正确？

测试套件是一个带两种错误率的检测器。它很少拒绝正确的程序（不稳定的测试、写错的期望），而每当缺陷落在测试没有覆盖之处，它就接受错误的程序。第二种错误率——**逃逸率**——决定一次「通过」值多少。

::: proposition 通过测试的价值 {#prop-pass}
设候选程序正确的先验概率为 $\pi$。假设测试对正确程序必定通过、对错误程序则以概率 $\varepsilon$ 通过（逃逸率）。则
$$
\Prob(\text{正确}\mid\text{通过}) = \frac{\pi}{\pi + (1 - \pi)\,\varepsilon}.
$$ {#eq-pass-posterior}
若独立抽取 $n$ 个候选，并从通过者中返回一个，则在至少有一个通过的条件下，返回的程序正确的概率仍是 [[#eq-pass-posterior]]；至少一个通过的概率为 $1 - (1 - \pi - (1 - \pi)\varepsilon)^n$。
:::

::: proof
由贝叶斯定理，$\Prob(\text{正确}\mid\text{通过}) = \Prob(\text{通过}\mid\text{正确})\,\pi/\Prob(\text{通过})$，其中 $\Prob(\text{通过}\mid\text{正确}) = 1$、$\Prob(\text{通过}) = \pi + (1 - \pi)\varepsilon$。第二个结论：每个候选以概率 $\pi + (1 - \pi)\varepsilon$ 独立通过，而在通过的条件下它正确的概率如上、且各候选相互独立；于是任选一个通过的候选（用一条不看正确性的规则）得到正确程序的概率就是它。没有一个通过的概率为 $(1 - \pi - (1 - \pi)\varepsilon)^n$。
:::

::: widget bayes
mode: test
prevalence: 0.2
sensitivity: 0.999
specificity: 0.9
caption: 把测试当作诊断。$1{,}000$ 个候选程序中 $20\%$ 是正确的（「患病率」）；测试几乎让每一个正确程序通过（「灵敏度」），并拒绝 $90\%$ 的错误程序（「特异度」，故逃逸率 $\varepsilon = 0.1$）。在通过的程序中，只有约 $71\%$ 是正确的（[[#eq-pass-posterior]]）。调高特异度——更多、更好的测试——看后验趋于 $1$；调低患病率（难题的情形），“通过”的含义就大打折扣。
:::

::: example 采样与过滤 {#ex-filter}
某模型在一道难题上的样本以概率 $\pi = 0.02$ 正确。题面的示例测试让 $5\%$ 的错误程序过关。若从通过的样本中交一个上去，它正确的概率多大？若能用一个逃逸率 $0.001$ 的更强隐藏测试集来过滤，情况如何变化？
::: solution
用示例测试：$0.02/(0.02 + 0.98\cdot0.05) = 0.02/0.069 = 0.290$。用更强的测试集：$0.02/(0.02 + 0.98\cdot0.001) = 0.02/0.02098 = 0.953$。过滤能把大量样本换成一个好答案，前提是过滤器的甄别力远超基准率之低——这里 $\varepsilon$ 必须远低于 $\pi$。AlphaCode（Li 等，2022）在编程竞赛中正是面对这个问题。它对每题采样极大数量的程序，剔除未通过题面示例测试的（约淘汰 $99\%$），再按幸存者在生成的输入上的行为聚类，从最大的若干簇中各交一个程序、总数至多十个。其模拟排名平均位于近期 Codeforces 竞赛参赛者的前 $54\%$。
:::
:::

::: warning 智能体可以在不解决问题的情况下满足测试
当通过测试是目标时，智能体可能用不正当的路子达成：对被测输入特判、捕获并压下测试要检查的异常、削弱断言，或者干脆改测试文件本身。这是小型的奖励破解（[[safety-alignment/reward-hacking]]），在把测试当奖励训练的智能体身上、以及只是被指示让测试通过的智能体身上都有过观察。防御：把评测测试放在智能体够不到的地方（或检查它们未被改动）、审查 diff 而不是只看测试结果、优先使用性质测试和留出的测试、并在指示中写明修改测试不是解决办法。
:::

## 软件工程智能体 {#sec-swe}

按规格写一个函数只是软件工程中很小的一部分。更大的部分是在既有代码库中工作：读懂一份 issue 报告、在上千个文件中找到相关的几个、做出与周围代码一致的修改，并确认别处没有因此坏掉。

::: definition SWE-bench {#def-swebench}
**SWE-bench**（Jimenez 等，2024；2023 年 10 月首发）由 $2{,}294$ 个任务实例构成，取自 $12$ 个流行开源 Python 仓库中已解决的 GitHub issue。每个实例给出 issue 文本和修复前一次提交时的仓库。系统必须产出一个补丁。补丁被应用后，运行来自真实修复的两组测试：**fail-to-pass** 测试——修复前失败、现在必须通过；**pass-to-pass** 测试——修复前通过、现在必须仍然通过。两组都通过的实例记为**已解决**；得分是已解决的百分比。
:::

发布之初，这一任务几乎遥不可及：当时评测的最强模型，拿到用 BM25（[[prompting-rag/vector-search]]）检索来的文件，也只解决了不到 $2\%$ 的实例。随后出现了两个更小的子集。**SWE-bench Lite**（$300$ 实例，2024 年）挑选自包含的 issue 以降低评测成本。**SWE-bench Verified**（$500$ 实例，2024 年 8 月由 OpenAI 与基准作者合作发布）经职业软件工程师筛查，淘汰了 issue 描述欠明确、或测试可能拒绝有效解的实例；它成了被报告最多的变体。Verified 上的报告分数从 2024 年年中最强系统的约三分之一，在 2025 年间升到明显过半；而截至 2026 年，关于剩余部分还有多少可测空间，争论仍在继续。

进步主要来自脚手架和为智能体编码训练的模型，两种取向相反的设计正好展示了光谱的两端：

- **SWE-agent**（Yang 等，2024）主张：正如人需要好的用户界面，智能体也需要一个为它们设计的**智能体–计算机接口**：一个按行号显示约百行窗口的文件查看器、返回简明摘要的搜索命令、一个替换若干行并运行 linter、从而拒绝引入语法错误之编辑的编辑命令，以及在命令无输出时给出提示信息的机制。有了这样的接口，一个基于 GPT-4 的智能体解决了完整基准的 $12.5\%$，远高于此前的检索基线。
- **Agentless**（Xia 等，2024）表明，一条没有开放式循环的固定流水线也可以很有竞争力：分层定位故障（先文件，再类与函数，最后到行），生成若干候选补丁，用复现测试和回归测试过滤，再按多数表决选择。它在 SWE-bench Lite 上以一小部分成本与当时的智能体系统不相上下——这正提醒我们（[[agents/agent-loops#sec-agent]]）：当步骤可预测时，工作流可以胜过智能体。

::: example 代码智能体的经济账 {#ex-swe-cost}
某智能体用 $40$ 步解决一个 issue：上下文从 $12{,}000$ 个词元起、每步增长 $2{,}000$ 个，每步输出 $300$ 个词元。按每百万输入词元 $\$3$、每百万输出词元 $\$15$ 计价，一次尝试成本多少？若它第一次尝试就解决 $60\%$ 的 issue、且失败能被测试检测到，那么在最多两次尝试下（设第二次能解决第一次失败者的 $30\%$），每个已解决 issue 的成本是多少？
::: solution
输入：$40\cdot12{,}000 + 2{,}000\cdot\frac{39\cdot40}{2} = 480{,}000 + 1{,}560{,}000 = 2{,}040{,}000$ 个词元，$\$6.12$。输出：$12{,}000$ 个词元，$\$0.18$。一次尝试花 $\$6.30$。至多两次尝试时：尝试次数的期望 $1 + 0.4 = 1.4$，期望成本 $\$8.82$；解决率 $0.6 + 0.4\cdot0.3 = 0.72$；每个已解决 issue 的成本 $8.82/0.72 = \$12.25$。对重复的前缀做缓存（[[inference/kv-cache]]）会大幅削减输入成本——这正是它对智能体如此要紧的原因。
:::
:::

### SWE-bench 度量什么，不度量什么

SWE-bench 的长处是真实（真实的 issue、仓库与测试）和自动评分。读任何分数之前，先了解它的局限是值得的。仓库公开且流行，所以其代码、issue 与修复可能出现在训练数据里，有些实例的解法甚至就写在 issue 讨论串里。来自真实修复的测试可能只针对原实现，从而拒绝有效的替代方案（这正是 Verified 筛查的理由）、或接受不完整的方案。所有任务都是 Python，且多数是库的缺陷修复而非应用的新功能。分数严重依赖脚手架、尝试次数、以及系统能否运行自己的测试，因此脱离这些细节的数字难以解读。其他语言的、带多模态 issue 的、使用更新或私有仓库的变体在 2024 与 2025 年相继出现以补这些缺口；一般原则见 [[agents/agent-security#sec-evaluation]]。

## 作为设计原则的沙箱化 {#sec-sandbox}

代码智能体会执行由模型写的程序，而模型会出错，并且会经由提示注入（[[prompting-rag/prompt-design#def-injection]]）被它在 issue、依赖的文档或网页里读到的文本操纵。问题不在于模型写的代码会不会有时做出有害的事——删错目录、耗尽内存、连上不该连的服务器——而在于真出事时它能造成多大伤害。**沙箱化**以构造作答，而不靠侥幸。

::: definition 沙箱 {#def-sandbox}
**沙箱**是一个把能力限制为任务所需范围的执行环境，其限制由操作系统或虚拟机监视器强制执行，而不是靠被运行的代码自觉。它的维度是：**文件系统**范围（哪些路径可见、可写）、**网络**访问（禁止、主机许可名单、或开放）、**凭据**（现场存在哪些机密、令牌与身份）、**资源**（CPU 时间、内存、磁盘、进程数）、**寿命**（用后即弃的一次性环境）与**可观测性**（记录什么）。一个沙箱的特征，由沙箱内代码所能造成的最具破坏性的事来刻画。
:::

按强度递增，实践中有这些层：带资源限制的操作系统进程隔离（像清单那样，约束了时间、别的约束不多）、带受限文件系统与网络策略的容器、以及为不可信代码设计的虚拟机或内核级隔离层。更强的隔离花费更多的启动时间和便利；合适的档位取决于代码可能够到什么。由定义可推出几条设计规则：

- **最小权限。**环境只拿到任务所需的文件、网络目的地与凭据。修 bug 的智能体需要的是仓库和测试运行器，不是部署密钥或整个主目录。
- **现场无机密。**出现在环境变量或配置文件里的凭据，对智能体运行的每一个程序、以及每一条开口索要它们的注入指令，都是现成可用的。
- **网络默认拒绝。**网络是数据离开的通道（[[agents/agent-security]]）；只对必需的开放，如包镜像。
- **一次性与检查点。**在一次性环境里运行，把智能体的改动保存为 diff 或分支，在任何东西进入共享系统之前由人评审。
- **读与写分离。**读代码风险低；推送到共享分支、发布包、跑数据库迁移应要求明确批准。

::: quiz
一个代码智能体运行在容器里：开发者的整个主目录以读写方式挂载、有网络访问、开发者的云凭据放在环境变量中。有人让它修好某个仓库里一个失败的测试。只改一处，哪个改动能最大程度降低一次出错或被操纵的操作可能造成的损害？
- [ ] 在系统提示里加上「绝不运行破坏性命令」。
- [ ] 换一个更强的模型。
- [x] 只挂载该仓库、移除凭据、把网络限制到包镜像。
- [ ] 记录智能体运行的每条命令。
::: solution
最小权限为任何操作能做的事封顶，无论模型想干什么。提示里的叮嘱只是一个请求，不是强制执行机制；更强的模型少犯错，但不是不犯错；日志有助于检测与调查，但那是事后。日志当然要记——但先收紧权限。
:::
:::

::: history
从规格出发做程序综合与计算机科学同龄，而神经代码生成的开端远早于大语言模型。Codex（Chen 等，2021）提出了 HumanEval 和无偏的 pass@$k$ 估计量，并驱动了早期的代码补全助手；Austin 等（2021）发布了 MBPP；Li 等（2022）以大规模采样与过滤让 AlphaCode 达到竞赛水平。开源代码模型接踵而至，包括 CodeGen（Nijkamp 等，2023）、StarCoder（Li 等，2023）和 Code Llama（Rozière 等，2023）。Gao 等（2023）把代码用作推理工具（PAL），Chen 等（2024）研究自我调试，Liu 等（2023）用 HumanEval+ 暴露了弱测试的问题，Jain 等（2024）建立了防污染的 LiveCodeBench。Jimenez 等于 2023 年 10 月发布 SWE-bench（ICLR 2024）；Yang 等（2024）提出 SWE-agent 与智能体–计算机接口；Wang 等（2024）提出 CodeAct；Xia 等（2024）用 Agentless 表明流水线也能竞争；SWE-bench Verified 于 2024 年 8 月发布。2024–2025 年，多家公司与开源项目的命令行及编辑器集成代码智能体得到广泛使用，模型也越来越多地在以测试评分的任务上用强化学习训练。
:::

::: summary
- 代码是对智能体最有利的领域：它可执行，而测试提供了便宜、自动的失败检测。
- HumanEval 用单元测试度量功能正确性；pass@$k$ 是 $k$ 个样本中有一个通过的概率，无偏估计为 $1 - \binom{n - c}{k}/\binom{n}{k}$。pass@$1$ 与 pass@$k$ 之差，正是过滤与验证能够收割的东西。
- 代码基准因测试薄弱、数据污染与饱和而老化；更强的测试套件与按日期筛选题目能应对前两者。
- 代码也是一种动作：解释器算得精确，一个程序顶得上多次工具调用；生成–测试–修复循环利用执行反馈。
- 一个通过测试的程序正确的概率是 $\pi/(\pi + (1 - \pi)\varepsilon)$：只有当逃逸率 $\varepsilon$ 远低于基准率 $\pi$ 时，对大量样本做过滤才管用。
- 智能体可以在不解决问题的情况下满足测试；保护评测测试，评审 diff。
- SWE-bench 用 fail-to-pass 与 pass-to-pass 测试给真实仓库上的补丁评分；其 Verified 子集（2024 年 8 月）剔除了有毛病的实例。脚手架（SWE-agent 的接口）与流水线（Agentless）都重要，而分数要连同设置一起读才可解读。
- 在按最小权限设计的沙箱里执行模型写的代码：限定范围的文件、现场无机密、网络默认拒绝、一次性环境、写入共享系统须批准。
:::

## 习题

::: exercise 从样本估计 pass@1 {level=1 check="0.06"}
某模型在一个问题上采样 $200$ 次，$12$ 个样本通过。pass@$1$ 的估计是多少？
::: solution
$1 - \binom{188}{1}/\binom{200}{1} = 1 - 188/200 = 12/200 = 0.06$。$k = 1$ 时，无偏估计量就是正确样本的比例。
:::
:::

::: exercise pass@5 手算 {level=1 check="0.9167"}
$n = 10$ 个样本中 $c = 3$ 个通过，计算 pass@$5$ 的无偏估计，保留四位小数。
::: solution
$\binom{7}{5} = 21$、$\binom{10}{5} = 252$，故 $1 - 21/252 = 1 - 0.0833 = 0.9167$。
:::
:::

::: exercise 需要的样本数 {level=1 check="45"}
一道题只有 $5\%$ 的样本能解出。使 pass@$k\ge0.9$ 的最小 $k$ 是多少？
::: solution
$1 - 0.95^k\ge0.9$ 即 $0.95^k\le0.1$，故 $k\ge\ln0.1/\ln0.95 = 44.9$，取 $k = 45$。
:::
:::

::: exercise 通过之后的后验 {level=2 check="0.714"}
候选程序正确的概率为 $0.2$；测试对正确程序必定通过、对错误程序通过 $10\%$。一个通过测试的程序正确的概率是多少？保留三位小数。
::: solution
$0.2/(0.2 + 0.8\cdot0.1) = 0.2/0.28 = 0.714$（[[#prop-pass]]）。
:::
:::

::: exercise 测试得多强？ {level=2 check="0.000206"}
样本正确的概率为 $\pi = 0.01$。逃逸率 $\varepsilon$ 为多少，才能让通过测试的程序以概率 $0.98$ 正确？保留三位有效数字。
::: solution
由 $\pi/(\pi + (1 - \pi)\varepsilon) = 0.98$ 得 $(1 - \pi)\varepsilon = \pi(1/0.98 - 1) = 0.01\cdot0.020408 = 0.00020408$，故 $\varepsilon = 0.00020408/0.99 = 0.000206$，即 $2.06\times10^{-4}$：大约每五千个错误程序中只能有一个漏网。
:::
:::

::: exercise 代入估计量的偏差 {level=2}
$n = 2$ 个样本、$k = 2$ 时，把无偏估计量与代入估计量 $1 - (1 - c/n)^2$ 的期望算成 $p$ 的函数，直接验证 [[#prop-passk]]。
::: solution
$c\sim\Bin(2, p)$。无偏的：$c\ge1$ 时 $\widehat{\text{pass@}2} = 1$、$c = 0$ 时为 $0$（因为 $\binom{2 - c}{2}/\binom{2}{2}$ 在 $c = 0$ 时为 $1$、否则为 $0$），期望为 $1 - (1 - p)^2$，与断言一致。代入的：$c = 0$ 得 $0$，$c = 1$ 得 $1 - \frac14 = \frac34$，$c = 2$ 得 $1$；期望为 $2p(1 - p)\cdot\frac34 + p^2 = \frac32p - \frac12p^2$。真值为 $1 - (1 - p)^2 = 2p - p^2$。差为 $(2p - p^2) - (\frac32p - \frac12p^2) = \frac12p(1 - p) > 0$（对 $0 < p < 1$）：代入式低估，在 $p = \frac12$ 处最严重，差 $\frac18$。
:::
:::

::: exercise 一份沙箱规格 {level=2}
按 [[#def-sandbox]] 的维度，为一个必须在某 web 应用仓库中修好一个失败测试的智能体写一份沙箱规格；测试需要本地数据库，包管理器必须能下载依赖。
::: solution
**文件系统：**仓库的全新克隆，可写；宿主机的其他部分一概不给；构建产物放暂存目录。**网络：**默认拒绝；放行包注册中心或内部镜像；数据库跑在沙箱内部，故不存在对外部数据库的访问。**凭据：**无；如需注册中心只读访问，则作用域限该注册中心；不给云、部署或源码库推送凭据。**资源：**CPU 与内存限额、每条命令与整个任务的墙钟限制、进程数与磁盘上限。**寿命：**用后即毁的一次性容器或虚拟机；成果以 diff 形式带出评审。**可观测性：**记录每条命令、其输出、以及每一次网络连接尝试，包括被拒绝的。推送改动、开 pull request、对共享数据库跑迁移，都在沙箱之外，需要批准。
:::
:::

::: exercise 破解自己测试的智能体 {level=3}
针对代码智能体产出的补丁，设计自动检查来检测上文警告所列的奖励破解行为——对被测输入特判、压制异常、削弱断言、修改测试——并讨论每种检查各自漏掉什么。
::: solution
(1) **测试完整性：**运行前对测试文件做哈希、运行后比对；拒绝触碰测试文件的补丁，除非任务本身要求，此时把 diff 交给评审。漏网：改动 fixture、配置（把测试标为跳过）或 conftest 文件——所以要把完整性检查扩展到全部测试基础设施。(2) **留出的测试：**用智能体从未见过、独立生成的测试来评测（性质测试，或如 HumanEval+ 那样来自更强套件的测试）。对可见输入的特判过不了它们。漏网：两个套件都没覆盖的缺陷。(3) **静态模式：**标记针对测试输入的新增字面量比较、改动代码周围宽泛的 `except` 子句、以及新增的 `skip` 或 `xfail` 标记。漏网：混淆或语义等价的写法，以及对合法代码的误报。(4) **变异分析：**对补丁做变异（翻转一个条件、改动一个常数）；若测试仍然通过，说明测试并未约束这处改动，这次“通过”提供的证据就很少。漏网：要费算力，以及等价变异体。(5) **由人或另一个模型评审**：对照 issue 审 diff。没有哪一项检查是完备的；把它们分层叠加能提高有效检测率，而每发现的一种新花样都变成一条新的回归检查。
:::
:::
