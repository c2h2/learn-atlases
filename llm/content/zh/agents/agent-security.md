两个问题决定一个智能体能否部署。**能用吗？**——它在将来要接受的任务上能多频繁地完成、代价多大、多稳定。**让它行动安全吗？**——它出错时会发生什么，有人存心让它干坏事时又会发生什么。这两个问题是相连的：智能体的用处来自它对工具、数据和世界的访问权；同一种访问权，正是错误或对手可以利用的东西。而两个问题都只能靠现实条件下的度量来回答，不能靠演示。

本章前半部分讲智能体的评测。先讲智能体基准如何搭建——带初始状态的环境、任务、功能性的成功检验与预算——再讲多数已发表的智能体结果所欠缺的统计学：成功率的置信区间、随机性智能体重复运行带来的额外方差（朴素区间会忽略它），以及诸如 pass$^k$ 的可靠性度量——智能体在 $k$ 次尝试中**每一次**都成功的概率。后半部分讲安全，落在威胁模型与防御两个层面。提示注入的概念性处理见 [[prompting-rag/prompt-design#def-injection]]，此处不再重复：这里的焦点是智能体——间接提示注入（Greshake 等，2023）与能行动的工具在这里相遇。我们将描述威胁模型、一条关于私密数据、不可信内容与对外通信三者组合的广为使用的设计启发式、按构造限制损害的防御手段——最小权限、沙箱、人工确认、权限分离、监控与审计——以及像 AgentDojo（Debenedetti 等，2024）这样把攻击与防御放在一起度量的评测套件。本章不含任何攻击载荷；理解防御并不需要它们。

## 评测智能体 {#sec-evaluation}

评测模型对一个问题的回答，需要一个问题和一个评分器。评测一个智能体，则需要一个供它行动的世界。

::: definition 智能体基准 {#def-benchmark}
一个**智能体基准**是一组任务 $\{\tau_1, \dots, \tau_T\}$，每个任务由以下部分构成：一个带指定初始状态的**环境**（网站、代码仓库、虚拟机、模拟用户与服务）；一条**指令**；一个**成功检验**——最终环境状态与智能体输出的函数，最好是**功能性的**（该发生的事真的发生了吗），而不是与一条参考动作序列作比较；以及一份**预算**（步数、词元、时间）。一次**运行**从初始状态出发、在一个任务上执行智能体一次，记录成败、成本与完整轨迹。由于智能体和环境都是随机的，每个任务可能运行 $R$ 次。
:::

本课程的每个基准都符合这个定义：SWE-bench（[[agents/code-agents#def-swebench]]）用测试检验最终的代码仓库；WebArena 和 OSWorld（[[agents/computer-use#def-webarena]]）用脚本检验网站和虚拟机的最终状态。τ-bench（Yao 等，2024）加入了由语言模型扮演的模拟**用户**，智能体必须在某一领域的政策规则下（例如航空公司对改签机票的规则）一边与用户对话一边使用工具，最后检验数据库的最终状态。基准设计的一般原则（[[evaluation/evaluation-principles]]、[[evaluation/benchmarks]]）依然适用，只是在智能体上有些特有的侧重：

- **功能性检验**给任何通往成功的路线记分，并能抓住那些只是「看起来对」的假成功，但必须谨慎撰写：只检查最终答案的检验可以被猜中，只检查数据库的检验可能漏掉别处的副作用。
- **状态重置。**每次运行都必须从同一初始状态出发；一次留下改动的环境会污染下一次。真实网站无法重置，这正是 WebArena 自建托管环境的原因。
- **环境不稳（flakiness）。**环境本身会出问题——服务超时、页面加载缓慢——这些不是智能体的错。它们必须被测量并报告，不能悄悄折进成功率里。
- **成本与延迟**是结果的一部分。Kapoor 等（2024）表明，一些精巧的智能体设计在控制住成本之后并不胜过简单基线，并主张把准确率与成本一起报告——作为帕累托前沿——而不是只报准确率。
- **数据污染与捷径。**公开的任务可能出现在训练数据里（[[evaluation/contamination]]）；环境里可能有意想不到的捷径（答案写在网页源码里、测试文件可以编辑）。智能体会找到它们。

### 成功率有多精确？

智能体基准都很小——几百个任务很常见，因为每个任务都要建造一个环境——而智能体又是随机的。这两点让报告的成功率远没有看上去那么精确。

::: proposition 重复运行时成功率的方差 {#prop-variance}
设任务 $i$ 对该智能体的成功概率为 $q_i$，各任务是从均值为 $\mu = \E[q]$、方差为 $\tau^2 = \Var(q)$ 的总体中随机抽取的。对 $T$ 个任务中的每一个独立运行 $R$ 次，记 $\bar{x}$ 为全部运行中的成功比例。则 $\E\bar{x} = \mu$ 且
$$
\Var(\bar{x}) = \frac{1}{T}\left(\tau^2 + \frac{\E[q(1 - q)]}{R}\right),\qquad \mu(1 - \mu) = \tau^2 + \E[q(1 - q)].
$$ {#eq-var}
朴素方差 $\mu(1 - \mu)/(TR)$ 把全部 $TR$ 次运行当作相互独立，它低估的倍数为 $1 + (R - 1)\rho$，其中 $\rho = \tau^2/(\mu(1 - \mu))$ 是任务内相关。重复运行只削减第二项；只有增加任务才能削减第一项。
:::

::: proof
记 $\bar{x}_i$ 为任务 $i$ 的成功比例。给定 $q_i$ 时，$\bar{x}_i$ 的均值为 $q_i$、方差为 $q_i(1 - q_i)/R$。由全方差公式，$\Var(\bar{x}_i) = \Var(q_i) + \E[q_i(1 - q_i)]/R = \tau^2 + \E[q(1 - q)]/R$。各任务相互独立，故 $\Var(\bar{x}) = \Var(\bar{x}_i)/T$，即 [[#eq-var]]。其次，$\E[q(1 - q)] = \mu - \E[q^2] = \mu - (\tau^2 + \mu^2) = \mu(1 - \mu) - \tau^2$，正是要用的恒等式。用 [[#eq-var]] 除以 $\mu(1 - \mu)/(TR)$ 得 $R\rho + (1 - \rho) = 1 + (R - 1)\rho$。
:::

实际推论：标准误要从各任务的成功比例 $\bar{x}_i$ 来估计（一个**按任务聚类**的标准误：$s/\sqrt{T}$，其中 $s$ 是诸 $\bar{x}_i$ 的标准差），而不是从合并起来的运行来估计。在同一批任务上比较两个智能体时，用逐任务的配对差，这能把任务难度的方差从比较中消去（[[evaluation/evaluation-statistics]]）。

::: example SWE-bench Verified 的置信区间 {#ex-ci}
某智能体在一次运行中解决了 SWE-bench Verified $500$ 个实例中的 $310$ 个。给出其解决率的 $95\%$ 置信区间。第二个智能体解决了 $325$ 个。第二个更好吗？
::: solution
$\hat{p} = 0.62$，标准误 $\sqrt{0.62\cdot0.38/500} = 0.0217$，于是区间为 $0.62\pm1.96\cdot0.0217 = 0.62\pm0.043$，从 $57.7\%$ 到 $66.3\%$。第二个智能体的 $65\%$ 落在其中，两个区间大幅重叠。差异是否显著取决于**配对**结果：若两个智能体在比如 $70$ 个实例上意见相左——第二个解出第一个失败的 $42$ 个、第一个解出第二个失败的 $27$ 个——McNemar 检验给出 $z = (42 - 27)/\sqrt{69} = 1.81$，在 $5\%$ 水平下不显著。而且这还只是各一次运行：有了运行间波动（[[#prop-variance]]），两个系统在 $500$ 个任务上三个百分点的差距，若不经重复运行确认，就在噪声之内。
:::
:::

### 可靠性：pass$^k$

对代码生成而言，pass@$k$（[[agents/code-agents#def-passk]]）奖的是 $k$ 次尝试中至少成功一次，在有检验器能挑出成功解时这很合理。但部署出去的智能体通常只有一次机会，而天天使用它的用户在意的是它是否**每次**都成功。τ-bench 提出了互补的度量。

::: definition pass$^k$ {#def-passhatk}
对单次运行成功概率为 $q$ 的任务，**pass$^k$** 是 $k$ 次独立运行全部成功的概率 $q^k$；一个基准的 pass$^k$ 是各任务上的平均。从 $n\ge k$ 次运行、$c$ 次成功出发，它可由 $\binom{c}{k}/\binom{n}{k}$ 无偏估计。
:::

把成功与失败互换，[[agents/code-agents#prop-passk]] 的论证就说明此估计量无偏：$\binom{c}{k}/\binom{n}{k}$ 正是从运行中随机取的 $k$ 个子集全为成功的概率。pass@$k$ 随 $k$ 上升而 pass$^k$ 下降；二者的差距度量**不一致性**。pass@$1$ 相同的两个智能体，pass$^k$ 可以天差地别：一个对 $60\%$ 的任务总是解决、其余从不解决，它的 pass$^k$ 对每个 $k$ 都等于 $0.6$；而另一个每个任务都有 $60\%$ 的概率解决，其 pass$^8 = 0.6^8 = 0.017$。

::: example 客服智能体的 pass$^k$ {#ex-passhatk}
一个客服智能体在 $3$ 个任务上各运行 $8$ 次，分别成功 $8$、$6$、$4$ 次。估计该基准的 pass$^1$、pass$^2$ 与 pass$^4$。
::: solution
逐任务用 $\binom{c}{k}/\binom{8}{k}$。$k = 1$：$1$、$0.75$、$0.5$，平均 $0.75$。$k = 2$：$1$、$\binom62/\binom82 = 15/28 = 0.536$、$\binom42/\binom82 = 6/28 = 0.214$，平均 $0.583$。$k = 4$：$1$、$\binom64/\binom84 = 15/70 = 0.214$、$\binom44/\binom84 = 1/70 = 0.014$，平均 $0.410$。$75\%$ 的平均成功率掩盖了只有一项任务被可靠处理的事实；一位四次带来第三个任务的用户，次次都满意的概率只有约 $1.4\%$。
:::
:::

### 一个基准模拟

下面的清单模拟一个 $T = 200$ 个任务的基准：任务难度从固定的、带种子的分布中抽取，每个任务上把一个模拟智能体运行 $R = 5$ 次，并比较朴素置信区间与聚类置信区间、以及两个度量。清单的后半部分是 [[#sec-defences]] 讨论的策略闸门。

```python
import random, math
from math import comb

# --- 1. 一个智能体基准：T 个任务，每个任务独立运行 R 次 --------------------
rng = random.Random(7)
T, R = 200, 5
difficulty = [rng.betavariate(1.2, 0.8) for _ in range(T)]       # 每个任务的成功概率
runs = [[rng.random() < q for _ in range(R)] for q in difficulty]

per_task = [sum(r) / R for r in runs]
mean = sum(per_task) / T
naive_se = math.sqrt(mean * (1 - mean) / (T * R))                 # 把 T*R 次运行当作独立
task_se = math.sqrt(sum((x - mean) ** 2 for x in per_task) / (T - 1) / T)   # 按任务聚类
print(f"success {mean:.3f}  naive 95% CI ±{1.96 * naive_se:.3f}  clustered ±{1.96 * task_se:.3f}")

def pass_hat_k(n, c, k):
    """pass^k 的无偏估计：k 次运行全部成功（由 n 次运行、c 次成功估计）。"""
    return comb(c, k) / comb(n, k)
def pass_at_k(n, c, k):
    return 1 - comb(n - c, k) / comb(n, k)
for k in (1, 2, 5):
    ph = sum(pass_hat_k(R, sum(r), k) for r in runs) / T
    pa = sum(pass_at_k(R, sum(r), k) for r in runs) / T
    print(f"k={k}: pass@k {pa:.3f}   pass^k {ph:.3f}")

# --- 2. 工具调用上的策略闸门（防御性设计，不含攻击内容） -------------------
TOOLS = {   # 名字：(读私密数据, 读不可信内容, 外部影响, 不可逆)
    "read_inbox":   (True,  True,  False, False),   # 邮件既是私密数据又不可信
    "fetch_url":    (False, True,  False, False),
    "read_file":    (True,  False, False, False),
    "send_email":   (False, False, True,  True),
    "create_draft": (False, False, False, False),
}

class Session:
    def __init__(self, allowed):
        self.allowed, self.private, self.untrusted, self.log = set(allowed), False, False, []
    def request(self, tool, confirmed=False):
        priv, untr, ext, irrev = TOOLS[tool]
        if tool not in self.allowed:
            verdict = "DENY (not granted for this task)"
        elif ext and self.private and self.untrusted and not confirmed:
            verdict = "HOLD (private data + untrusted content + external channel: ask the user)"
        elif irrev and not confirmed:
            verdict = "HOLD (irreversible: ask the user)"
        else:
            verdict = "ALLOW"
            self.private |= priv; self.untrusted |= untr
        self.log.append((tool, verdict, self.private, self.untrusted))
        return verdict

s = Session(allowed={"read_inbox", "fetch_url", "create_draft", "send_email"})
for tool in ["read_inbox", "fetch_url", "read_file", "create_draft", "send_email"]:
    print(f"{tool:12s} -> {s.request(tool)}")
print("audit log entries:", len(s.log), "| last:", s.log[-1])
```

k=2: pass@k 0.760   pass^k 0.418

朴素区间假装 $1{,}000$ 次运行就是 $1{,}000$ 个独立观测，比聚类区间窄了三分之一；[[#prop-variance]] 能解释这个差距——这个模拟里任务难度的方差很大。一个 $59\%$ 成功率的智能体，有 $92\%$ 的概率在五次尝试中至少解决一个任务，却只有 $24\%$ 的概率五次全解决：同一个智能体，你问的是哪个问题，它就显得出色或糟糕。

## 威胁模型 {#sec-threats}

安全分析始于说清楚：在保护什么、防着谁、以及从哪些入口进来。

::: definition 智能体的威胁模型 {#def-threat}
- **资产**：用户的私密数据（消息、文件、记录）、凭据与会话、金钱及智能体能动用的其他资源、它能改动的各系统的完整性，以及智能体自身输出与记忆的完整性。
- **对手**：任何能把文本、图像或其他内容放到智能体将要读到的位置的人——网页作者、邮件发件人、代码仓库的贡献者、工具或工具描述的发布者、另一个智能体——此外，就滥用而言还有用户本人。
- **入口点**：模型读到的、并非由系统开发者或用户撰写的一切输入：检索到的文档、工具结果、网页与屏幕截图、邮件与消息、文件内容、来自第三方服务器的工具描述（[[agents/function-calling#sec-protocols]]）、持久化的记忆（[[agents/memory-context#sec-retrieval]]）、以及来自其他智能体的消息。
- **危害**：**数据外泄**（把私密数据发给对手）、**越权操作**（购买、发消息、删除、改配置）、**完整性攻击**（细微错误的输出、投毒的代码）、**持久化**（存进记忆或文件、会影响后续会话的指令）、以及**拒绝服务**（烧掉预算的循环）。
:::

把对手与危害连起来的机制是**间接提示注入**：入口点上的内容被模型当成了指令（[[prompting-rag/prompt-design#def-injection]]）。Greshake 等（2023）针对把语言模型与检索、工具结合起来的应用演示了它，并表明上述危害原则上对任何能把内容送到模型面前的人都是可实现的。对智能体来说赌注比聊天更高，因为模型的输出是行动。根本困难没有变：语言模型通过同一条通道接收指令和数据，而服从文本里发现的指令，恰恰就是它被训练出来做的事。截至 2026 年，模型层面的防御已大幅降低已知注入手法的成功率、但并未降到零，而会针对防御调整自己内容的自适应攻击者仍在不断找到通路。因此本章余下部分假定**读不可信内容的智能体有时会被其操纵**，并追问：如何设计出使这种操纵损害有限的系统。

::: definition 致命三合一（设计启发式） {#def-trifecta}
Willison（2025）把以下情形命名为**致命三合一**（lethal trifecta）：一个同时具备（1）**访问私密数据**、（2）**接触不可信内容**、以及（3）**对外通信的能力**——任何能让数据离开智能体的通道，包括发消息、发网络请求，甚至渲染一个地址中编码了数据的链接或图片——的智能体，可能被（2）中的注入指令诱导，把（1）中的数据经（3）发送出去。这条启发式是：绝不让同一个智能体的上下文同时集齐三者；至少拆掉一条腿，或在各条腿之间放上人的确认。Meta 的研究者们在 2025 年发布的一条类似法则要求，一个智能体会话至多满足下列三条中的两条：处理不可信输入、访问敏感系统或私密数据、改变状态或对外通信。
:::

这条启发式之所以有用，是因为它在设计阶段就可检查——光看工具清单即可——而不必预测任何攻击会长什么样。它的逻辑可以表述为一条信息流性质。

::: proposition 拆掉三合一即可阻断经由智能体的数据外泄 {#prop-trifecta}
把一个智能体会话建模为一个不断累积**标签**的上下文：私密数据一旦进入就带「私密」标签，不可信内容一旦进入就带「不可信」标签。假设一切有外部影响的操作都只在上下文不同时带有这两个标签时才执行，除非有某个人确认了那个具体操作。那么，该会话未经确认执行的任何操作，都不可能既受不可信内容影响、又把私密数据带出去——智能体自己的操作无法替对手完成一次数据外泄。
:::

::: proof
标签只增不减，所以在对外操作的那一刻，上下文的标签涵盖了曾进入其中的一切。若操作未经确认就执行，上下文至少缺一个标签。若缺「私密」，则没有私密数据进入过它，操作的参数里就不会有任何私密数据。若缺「不可信」，则没有不可信内容进入过它，操作就没有受对手内容的影响（只受用户、开发者和可信来源的影响）。两种情形下，该操作都不是由对手操纵的外泄。
:::

这个命题的强度不超过它的标签。若不可信内容被错标成可信（用户上传的文档里可能含有别人写的文字），若一个有外部影响的通道没有被识别出来（一个用户界面会去拉取的图片 URL、一个链接预览、一个写进共享文件夹的文件），或者确认操作的人看不清它携带了什么，命题就会失效。它也不处理完整性攻击——注入一条「写微妙错误的代码」的指令并不需要外泄通道——也不处理用户的滥用。这正是三合一只是一条设计启发式、而非安全证明的原因。但它把一个没边的问题（「会不会有某段文本让智能体干坏事？」）变成一个有边的问题（「哪些会话集齐了三种能力，它们之间隔着什么？」），而清单里的 `Session` 闸门就是一个直接实现：会话读过收件箱（既私密又不可信）之后，发邮件就会被拦下来交给用户。

::: example 给智能体配置分类 {#ex-trifecta}
对每种配置，指出三合一的哪些腿在场，并给出消除风险的最便宜的改动：(a) 一个读收件箱、能发邮件的邮件助手；(b) 一个有网络访问权限、在不含机密的公开仓库上工作的代码智能体；(c) 一个浏览网页、把报告写进用户私密笔记、别无其他工具的研究智能体；(d) 一个读客户记录、在公开聊天里答疑的支持机器人。
::: solution
(a) 三条腿全在：收件箱内容既**私密**又**不可信**（任何人都能发邮件），而发送是对外的。最省的修法：把「发送」换成「创建草稿」，由人来发送；或要求确认，且确认中显示收件人与内容。(b) 有不可信内容（issue、依赖）和对外通信，但没有私密数据——除非环境里带着凭据，那将补上缺的那条腿；把机密挡在环境之外（[[agents/code-agents#def-sandbox]]）。完整性风险（注入的坏代码）仍在，需要评审。(c) 有不可信内容和私密数据（如果它能**读**笔记；若只能追加，则风险小些）；只要笔记不被共享、报告的渲染不去拉取远程资源，就没有对外通道。(d) 有私密数据和一个对外通道；不可信那条腿恰恰是客户的消息本身，那是不可信输入。把机器人的数据访问限制到已通过身份认证的该客户自己的记录上，让其他人的私密数据永远不进入上下文。
:::
:::

## 防御 {#sec-defences}

没有哪一重防御是完备的；务实的做法是**纵深防御**——层层失效尽可能相互独立的防线。

::: proposition 纵深防御 {#prop-depth}
若一次攻击必须接连突破 $m$ 层，各层被独立突破的概率为 $f_1, \dots, f_m$，则攻击成功的概率为 $\prod_i f_i$。若在有概率 $\gamma$ 的情况下，一个单一的共同原因会一次性突破所有层，则成功概率为 $\gamma + (1 - \gamma)\prod_i f_i\ge\gamma$。
:::

::: proof
独立性给出乘积。有共同原因时，按它是否发生做条件：经它成功的概率为 $\gamma$，否则成功还须独立地突破每一层。
:::

这个命题指出了该选哪几层：因**不同**原因失效的层。三层若都指望模型认出注入，就共享一个共同原因——一条有说服力的注入会把它们一起骗过。基于模型的检测器、代码强制执行的权限系统、以及人的确认，失效的原因各不相同。

::: example 共享失效点的几层 {#ex-depth}
一条注入要先后突破一个检测分类器（$f_1 = 0.2$）、模型自身训练出的抗性（$f_2 = 0.3$）、以及发消息前的确认步骤（$f_3 = 0.1$，即一个人没察觉就批准恶意消息的概率）。若各层独立，攻击成功的概率是多少？若在有 $0.05$ 概率的情况下，攻击被制成分类器与模型同时被骗、而确认界面不显示消息全文、因而那种情形下的批准是自动的，结果如何？
::: solution
独立：$0.2\cdot0.3\cdot0.1 = 0.006$。有共同原因：$0.05 + 0.95\cdot0.006 = 0.0557$，高出近十倍，且由所有层一起失效的情形主导。修法在于消除共同原因——把人将要看到的确切内容原样展示出来——而不是再叠加一层基于模型的防线。
:::
:::

主要的防御手段，大体按保证从强到弱排列：

- **最小权限。**只授予每个智能体、每个会话完成任务所需的最小工具、数据与权限：读就够了就只给读、会过期的受限令牌、收件人与目的地的许可名单。没被授予的权限，无论模型被说服去想要什么，都无从滥用。清单里的 `DENY` 就是这一层。
- **沙箱化。**让有副作用的操作运行在隔离环境里：网络默认拒绝、环境里不漂着凭据（[[agents/code-agents#sec-sandbox]]）。
- **不可逆与对外操作的人工确认。**支付、发消息、删除、发布、改权限都要停下来等待明确批准，且确认界面要原样展示将会发生什么——完整的收件人与内容，而不是那个可能已被攻陷的模型写出的摘要。确认疲劳是真的：让人什么都批，人就会什么都批，所以只确认要紧的事。
- **权限分离。**让不可信内容远离做决策的上下文。Willison 的**双 LLM 模式**（dual-LLM pattern，2023）中，一个有特权的模型负责规划并调用工具，但绝看不到不可信文本；一个被隔离的模型处理不可信文本，返回的结果只作为不透明变量交给有特权的一侧。CaMeL（Debenedetti 等，2025）把这一想法发展成一个系统：从可信的用户请求中提取任务的控制流、像程序一样执行它，并用能力（capability）跟踪每个值的来源，于是策略可以禁止，比如说，把源自一封不可信邮件的数据发往同样从邮件里来的地址。这类设计拿一部分效用换不依赖模型抗注入的保证。
- **模型层面的稳健性。**训练模型让系统和用户的指令优先于工具结果里的文本——建立**指令层级**（instruction hierarchy；Wallace 等，2024）——并在上下文中清楚标记不可信文本（加界或编码，有时称为聚焦标记，spotlighting；Hines 等，2024），都能降低注入成功率。它们是概率性防御：是有价值的一层，不是边界。
- **检测。**对输入标记疑似注入、对输出标记异常动作的分类器能抓住许多不高明的攻击，但它们本身也是可被绕过的模型。
- **监控与审计。**把每个输入来源、工具调用、参数、权限决策与确认连同来源，记入一份智能体无法修改的记录。日志支撑异常检测（陌生的收件人、一阵密集的读取）、事故后的调查与评测（[[safety-alignment/monitoring-control]]）。速率限制和一条可靠地叫停正在运行的智能体的途径，同属这一层。

::: warning 「忽略内容中的指令」不是安全边界
在系统提示里告诉模型忽略文档中出现的指令、把不可信文本包进标签，都是好实践，并且可度量地降低注入成功率。但它们终究只是对模型的请求，其能否生效由攻击者瞄准的同一机制决定，而攻击者可以不断迭代直到请求失效。要把提示层面的防御当作一层失效后必须扛得住的防线：当它们失效时，真正限制损害上限的是权限系统、沙箱与确认步骤。
:::

## 评测安全 {#sec-security-eval}

防御必须被度量，而度量需要既包含智能体应完成的任务、又包含它应抵挡的攻击的基准——因为一个靠什么都不干来挡住所有攻击的防御毫无用处。

::: definition 智能体的安全评测 {#def-security-eval}
一次**安全评测**把用户任务与**注入测试用例**配对：植入环境某个入口点的对抗内容（一封邮件、一个网页、一个文件、一个工具输出），外加一个其完成可以被功能性检验的攻击者目标（一次操作被执行、一份数据被发出）。它对每种防御配置至少报告**效用**（无攻击时的任务成功率）、**受攻击下的效用**（存在注入时的任务成功率）与**攻击成功率**（攻击者目标被达成的测试用例比例），且每项都带置信区间。
:::

**AgentDojo**（Debenedetti 等，2024）是一个广泛使用的例子。它提供了按常见智能体部署建模的环境——带邮件、日历和云文件的工作区、一个消息工作区、差旅预订和网上银行——含 $97$ 个用户任务与 $629$ 个安全测试用例，并被设计成可扩展的框架：新攻击与新防御都可以插进来、在同一批任务上评测。其作者报告：当时的智能体在所有良性任务上完成得都不算好，对最强智能体的攻击在相当可观的少数用例中得逞，而工具过滤、注入检测器等防御以降低一些效用为代价换来了攻击成功率的下降——这正是上面三个指标要暴露的权衡。**InjecAgent**（Zhan 等，2024）在涉及众多用户工具与攻击者工具的 $1{,}054$ 个测试用例上度量了注入脆弱性。滥用——用户直接要求智能体执行有害的多步任务——由另一些套件度量，如 AgentHarm（Andriushchenko 等，2024），它属于越狱稳健性（[[safety-alignment/robustness-jailbreaks]]）的话题。

静态套件有一个已知局限：其中的攻击是固定的，防御可以针对它们调参。面对**自适应**攻击者——针对特定防御调整自己内容的攻击者——的评测通常得到更高的攻击成功率，是对模型层面防御更诚实的度量。相比之下，最小权限、权限分离这类设计层面的防御，是通过检查系统在任何输入下**能**做什么来评测的，攻击者再怎么调整也改变不了这一点。

::: quiz
一个团队报告，其新注入检测器把公开基准上的攻击成功率从 $30\%$ 降到 $2\%$。在依赖它之前，你最希望看到的进一步结果是什么？
- [ ] 检测器在该基准训练集上的准确率。
- [ ] 在三个精挑细选的例子上的演示。
- [x] 开启检测器后在良性任务上的效用，以及面对针对该检测器调整过的攻击时的攻击成功率，并附置信区间。
- [ ] 检测器的参数量。
::: solution
检测器可能因为拦得太多而得到低的攻击成功率——这只有效用度量能揭穿；也可能因为拟合了基准里的固定攻击——这只有自适应攻击能揭穿。而置信区间回答的是：在所用的测试用例数量下，$2\%$ 与（比如）$6\%$ 是否可区分（[[#sec-evaluation]]）。
:::
:::

::: history
在模拟环境中评测交互式智能体可追溯到强化学习的基准，如雅达利学习环境（Bellemare 等，2013）；对语言智能体，ALFWorld 与 WebShop（2020–2022）、WebArena（2023）、SWE-bench（2023）、OSWorld（2024）和 τ-bench（Yao 等，2024）确立了功能性评测，Kapoor 等（2024）则主张控制成本的比较。安全方面，Perez 与 Ribeiro（2022）研究了提示攻击，Willison 于 2022 年 9 月为提示注入命名、2023 年提出双 LLM 模式，Greshake 等（2023）描述了针对使用工具的应用的间接提示注入。Wallace 等（2024）训练了指令层级；Hines 等（2024）提出聚焦标记；Zhan 等（InjecAgent，2024）与 Debenedetti 等（AgentDojo，2024）为智能体建立了注入基准；Andriushchenko 等（2024）用 AgentHarm 度量滥用；Debenedetti 等（2025）提出 CaMeL；Willison 于 2025 年 6 月命名了致命三合一，同年晚些时候又出现了相关的「rule of two」。整个 2025 年，模型提供商们陆续在智能体产品中加入注入分类器、确认提示与受限的工具模式；而截至 2026 年，提示注入仍是一个只能靠系统设计来防御的开放问题。
:::

::: summary
- 智能体基准提供带固定初始状态的环境、指令、功能性的成功检验与预算；成功率、成本、延迟与环境不稳要一并报告。
- 几百个任务上的成功率置信区间很宽（$500$ 个任务、$60\%$ 成功率时约 $\pm4$ 个百分点）；重复运行增加相关方差，所以要用按任务聚类的标准误与配对比较。
- pass@$k$（$k$ 次运行至少一次成功）与 pass$^k$（$k$ 次全部成功）回答不同的问题；二者的差距度量不一致性。
- 威胁模型：资产、能把内容放到智能体将要读到的位置的对手、入口点（一切不可信输入，包括工具描述、记忆和其他智能体）、以及危害（数据外泄、越权操作、完整性、持久化）。
- 假定读不可信内容的智能体有时会被其操纵。致命三合一启发式（私密数据、不可信内容、对外通信）能识别出会导致外泄的会话；拆掉一条腿，或在腿之间放上确认。
- 各层因不同原因失效时，纵深防御才有效：最小权限、沙箱、原样展示将会发生什么的确认、权限分离（双 LLM、CaMeL）、模型稳健性、检测、监控与审计日志。
- 像 AgentDojo 那样，用效用、受攻击下的效用与攻击成功率评测安全，并面对自适应攻击者评测；设计层面的保证不依赖于具体攻击。
:::

## 习题

::: exercise 置信区间 {level=1 check="0.043"}
某智能体在 $500$ 个任务上成功 $310$ 个。正态近似 $95\%$ 置信区间的半宽是多少？保留三位小数。
::: solution
$1.96\sqrt{0.62\cdot0.38/500} = 1.96\cdot0.021707 = 0.0425$，保留三位小数为 $0.043$。
:::
:::

::: exercise 从运行次数估计 pass$^k$ {level=1 check="0.4"}
某智能体在一个任务上 $5$ 次运行成功 $4$ 次。给出该任务 pass$^3$ 的无偏估计。
::: solution
$\binom43/\binom53 = 4/10 = 0.4$（[[#def-passhatk]]）。代入式 $(4/5)^3 = 0.512$ 偏高，由 [[agents/code-agents#prop-passk]] 的凸性论证可知。
:::
:::

::: exercise 纵深防御 {level=1 check="0.006"}
三层相互独立的防线被突破的概率分别为 $0.2$、$0.3$ 和 $0.1$。攻击突破全部三层的概率是多少？
::: solution
$0.2\cdot0.3\cdot0.1 = 0.006$（[[#prop-depth]]）。
:::
:::

::: exercise 精确估计所需的任务数 {level=2 check="2401"}
成功率接近 $0.5$ 时，要让 $95\%$ 置信区间的半宽不超过 $0.02$（每任务运行一次）需要多少个任务？向上取整。
::: solution
$1.96\sqrt{0.25/n}\le0.02$ 给出 $n\ge(1.96/0.02)^2\cdot0.25 = 98^2\cdot0.25 = 9{,}604\cdot0.25 = 2{,}401$ 个任务——比多数智能体基准的规模大好几倍。半宽放宽到 $0.04$ 只需四分之一，约 $600$ 个。
:::
:::

::: exercise 设计效应 {level=2 check="2.6"}
各任务成功概率的均值 $\mu = 0.6$、方差 $\tau^2 = 0.096$。每个任务运行 $R = 5$ 次。朴素方差把成功率的真实方差低估了多少倍？
::: solution
$\rho = \tau^2/(\mu(1 - \mu)) = 0.096/0.24 = 0.4$，倍数为 $1 + (R - 1)\rho = 1 + 4\cdot0.4 = 2.6$（[[#prop-variance]]）。朴素标准误小了 $\sqrt{2.6} = 1.61$ 倍。
:::
:::

::: exercise 稳定性 {level=2}
智能体 A 每次运行都解决 $60\%$ 的任务、另外 $40\%$ 从不解决。智能体 B 对每个任务都以 $0.6$ 的概率独立解决。计算各自的 pass@$1$、pass@$4$ 与 pass$^4$，并说明你会把哪一个部署为夜间无人值守的任务、哪一个作为其输出由人检查的工具。
::: solution
A：pass@$1 = 0.6$，pass@$4 = 0.6$，pass$^4 = 0.6$。B：pass@$1 = 0.6$，pass@$4 = 1 - 0.4^4 = 0.974$，pass$^4 = 0.6^4 = 0.130$。对必须夜夜成功的无人值守任务，A 好得多：在它处理得了的任务上它很可靠，其余一旦识别出来可以改道。对带重试、有人检查的工具，B 更好：四次尝试 $97\%$ 的情况下能成，由人或检验器挑出成功解。同样的平均成功率，可以是截然不同的产品。
:::
:::

::: exercise 审查工具清单 {level=2}
某助手拥有这些工具：`search_web`、`read_calendar`、`read_email`、`send_email`、`create_calendar_event`、`upload_file_to_share_link`。找出全部三合一风险，并重新设计工具集与确认流程，使助手仍能：(a) 摘要今天的邮件；(b) 安排邮件里请求的会议；(c) 在网上调研主题。
::: solution
私密数据：`read_calendar`、`read_email`。不可信内容：`search_web`、`read_email`。对外通道：`send_email`、`upload_file_to_share_link`（生成的链接谁都能拉取），以及 `create_calendar_event`（若它向外部参会者发邀请函）；若查询能编码数据，`search_web` 本身就是一条通道。读邮件与任何对外通道的组合都凑齐三合一。重新设计：(a) 摘要只需要 `read_email`，该会话里不放任何对外工具。(b) 安排会议：`create_calendar_event` 默认不发邀请函；邀请外部参会者需要确认，且确认中显示参会人与正文。(c) 调研在与 `search_web` 单独构成的会话里进行，不碰邮件和日历；其报告交给用户，而不是交进邮件会话。`upload_file_to_share_link` 除非有任务需要就删掉，需要时要求确认。`send_email` 换成 `create_draft`，由人来发送。
:::

::: exercise 日志必须包含什么 {level=3}
为一个使用工具的智能体设计审计日志记录，使得在「数据疑似被发往陌生地址」的事故之后，调查者能够查明：(i) 哪个输入带进了那条指令；(ii) 哪些数据被发送；(iii) 有没有人批准过；(iv) 策略闸门是否按规程行事。并解释为什么智能体本身绝不能向日志写入或删除。
::: solution
每个事件包含：单调递增的序号与时间戳；会话与任务标识；事件类型（收到输入、调用模型、请求工具调用、策略决策、请求并得到确认、工具结果）；对输入，记录来源（用户、系统、工具名以及 URL、消息或文件的标识符）与内容哈希、外加指向所存内容的指针；对模型调用，记录所用上下文各段的哈希，使调查者能看到模型每一步见过哪些输入；对工具调用，记录完整参数、当时会话的标签（如清单所示）、以及允许、挂起或拒绝它的策略规则；对确认，记录展示给人的确切内容、由谁作答、何时作答；对结果，记录大小与哈希。(i) 靠找到第一个上下文含可疑输入、且其智能体动作随后改变的模型调用来确定；(ii) 来自对外调用的参数；(iii) 来自确认记录；(iv) 用日志里的标签重放闸门的规则。日志必须只可追加、且位于智能体的权限之外，因为一个能被注入内容操纵的智能体也可能被操纵去抹掉或伪造那次操纵的记录；它应当由运行时写入而非由模型写入，并存到沙箱够不到的地方。
:::

::: exercise 两个智能体之间做选择 {level=3}
智能体 A 在 AgentDojo 式测试上效用 $0.71$、攻击成功率 $0.18$；加上一个防御的智能体 B 效用 $0.64$、攻击成功率 $0.04$。每个数字都来自约 $600$ 个测试用例。这些差异在统计上有意义吗？描述你还会收集哪些补充证据，以及你如何决定把一个邮件助手部署成哪一个。
::: solution
标准误：效用 $\sqrt{0.71\cdot0.29/600} = 0.0185$ 与 $\sqrt{0.64\cdot0.36/600} = 0.0196$，于是若相互独立，差值 $0.07$ 的标准误约为 $0.027$，$z\approx2.6$；在同一批任务上做配对分析会更锐利。攻击成功率：$\sqrt{0.18\cdot0.82/600} = 0.0157$ 与 $\sqrt{0.04\cdot0.96/600} = 0.0080$，差值 $0.14$ 的标准误为 $0.0176$，$z\approx8$：显然有意义。补充证据：重复运行以估计运行间方差（[[#prop-variance]]）；针对 B 的防御调整过的攻击，因为那 $4\%$ 可能只反映固定攻击；B 输掉的是哪些任务（若是要紧的任务，效用代价比看上去更大）；以及成功攻击的**严重程度**，而不只是比率。对一个天然凑齐三合一的邮件助手，决定因素应当是设计：把发送换成草稿、对对外操作要求确认之后，任一智能体身上一次成功的注入的残余影响都很小，届时选择可以偏向效用；而没有这些措施，两个攻击成功率都不可接受。
:::
