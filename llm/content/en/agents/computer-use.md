Most software was built for people, not programs. Booking a train, filing an expense claim, changing a setting in an administration console, exporting a report from an old desktop application: many such tasks have no interface an agent could call as a tool, only buttons, forms and menus. An agent that can operate a **browser** or a whole **computer** the way a person does — look at the screen, move the pointer, click, type — can in principle do any of them, without anyone building an integration first. That generality is why browsing and computer-use agents attract so much effort, and why they are hard: the agent must perceive a screen designed for human eyes, act through an interface designed for human hands, and do so for dozens of steps on websites that change, load slowly and interrupt with pop-ups.

This chapter treats web and computer control as an agent problem with an unusual observation and action space. It defines the environment formally, compares the three ways an agent can see a page — raw markup, the accessibility tree, and screenshots — with the token arithmetic that often decides between them, and analyses **grounding**, the step from "click the Checkout button" to a pair of pixel coordinates, with a small model of pointing error. A plain-Python listing drives a toy shop through its accessibility tree and checks the pointing model by simulation. The second half follows the history from WebGPT (Nakano et al., 2021) through the benchmarks that defined the field — WebArena (Zhou et al., 2024) for websites and OSWorld (Xie et al., 2024) for full operating systems — to screenshot-based computer-use models from 2024 on, and ends with the reasons these agents need stricter safeguards than any other kind.

## The environment {#sec-environment}

A browser or desktop is an environment in the sense of [[agents/agent-loops#def-agent]], with two features that matter. The agent never sees the full state — the server's database, the page's scripts, what lies below the fold — only a rendering of part of it. And the actions are low-level: a single meaningful operation ("buy the cheaper kettle") takes many clicks and keystrokes.

::: definition Computer-use environment {#def-gui-env}
A **computer-use environment** is a partially observable decision process with hidden state $s_t$ (the machine, the applications and any remote servers), an **observation function** producing $o_t$ from $s_t$, and an **action space** $\mathcal{A}$ of interface operations. Common observation types are the page **markup** (HTML), the **accessibility tree** (the structure exposed to assistive technologies: each element's role, name, state and position), and a **screenshot** (a pixel image of the screen), alone or in combination. Common action spaces are:
- **coordinate actions**: move or click at $(x, y)$, drag, scroll by an amount, type a string, press a key or key combination;
- **element actions**: click, type into or select the element with identifier $i$ in the current observation;
- **navigation actions** (browsers): open a URL, go back, switch tab;
- **control actions**: wait, take a new screenshot, finish, or ask the user.
:::

Element actions require the observation to name elements, which markup and accessibility trees do and screenshots do not; coordinate actions work with anything that can be seen, including canvases, remote desktops and applications with no accessibility information. Many agents combine them: a screenshot for understanding, an accessibility tree or labelled overlay for targeting, coordinates as the fallback.

### What the agent sees

The three observation types differ enormously in size and in what they make easy.

::: example Three views of one page {#ex-views}
A product page's HTML is $420$ kB, about $110{,}000$ tokens at roughly $3.8$ characters per token, most of it scripts, styles and tracking markup. Its accessibility tree lists $180$ elements at about $25$ tokens each. A screenshot is $1280\times800$ pixels, and the model's image encoder produces one token per $28\times28$-pixel block. Compare the token costs, and the number of steps that fit in a $128{,}000$-token window if each step keeps its observation.
::: solution
HTML: $110{,}000$ tokens — one page nearly fills the window. Accessibility tree: $180\cdot25 = 4{,}500$ tokens. Screenshot: $(1280/28)(800/28) = 45.7\cdot28.6\approx1{,}306$ tokens. With $8{,}000$ tokens of instructions and output reserve, the window holds one HTML observation, about $26$ accessibility trees, or about $92$ screenshots. In practice agents keep only the latest one or two observations in full and clear older ones ([[agents/memory-context#ex-clearing]]), which makes even accessibility trees affordable over long tasks; raw HTML is almost always cleaned or replaced.
:::
:::

The **accessibility tree** is generated by the browser or operating system from the page's structure and the annotations that web developers add for screen readers. Where it is complete it is the best observation available: compact, structured, with explicit roles ("button", "textbox", "link") and names, and with stable identifiers the agent can act on. Its weaknesses are that it is only as good as the page's accessibility markup — unlabelled icons, custom widgets drawn on a canvas and badly built forms appear as anonymous or missing elements — and that it omits visual information (layout, colour, images) that a person uses constantly.

A **screenshot** is the universal observation: anything a person can see, the agent can see, in any application. It requires a vision–language model ([[multimodal/vision-language-models]]), and it moves the difficulty to **grounding**: knowing *where* to click. A popular intermediate is **set-of-mark prompting** (Yang et al., 2023), in which a program draws numbered boxes over the interactive elements of a screenshot, so that a model can say "click 14" instead of producing coordinates. Zheng et al. (2024) found, for a vision–language model acting on real websites, that choosing the right action was easier than grounding it to the right element, which remained the main source of errors.

### A toy shop in plain Python

The listing implements a five-page shop whose observation is an accessibility tree with element identifiers, and a scripted policy, standing in for a model, that reads the tree as text and acts by identifier. It searches, compares the two prices *as they appear in the tree*, adds the cheaper kettle to the basket and stops at checkout, which requires confirmation. The second half models coordinate clicking, derived in [[#prop-pointing]].

```python
import math, random

# --- a toy web shop, rendered as an accessibility tree ---------------------
PAGES = {
    "home":    [("link", "Search"), ("link", "Account")],
    "search":  [("textbox", "Query"), ("button", "Go")],
    "results": [("link", "Kettle 1.7 L - 34.00"), ("link", "Kettle 1.0 L - 29.50"),
                ("button", "Next page")],
    "product": [("text", "Kettle 1.0 L, 29.50"), ("button", "Add to basket"),
                ("link", "Basket")],
    "basket":  [("text", "1 item, total 29.50"), ("button", "Checkout")],
}
LINKS = {("home", "Search"): "search", ("search", "Go"): "results",
         ("results", "Kettle 1.0 L - 29.50"): "product", ("product", "Basket"): "basket"}

class Shop:
    def __init__(self):
        self.page, self.query, self.basket = "home", "", 0
    def observe(self):
        """Accessibility tree: [id] role "name" -- ids are what the agent acts on."""
        return "\n".join(f'[{i}] {role} "{name}"' for i, (role, name) in enumerate(PAGES[self.page]))
    def act(self, action, eid=None, text=None):
        role, name = PAGES[self.page][eid]
        if action == "type" and role == "textbox":
            self.query = text
        elif action == "click" and name == "Add to basket":
            self.basket += 1
        elif action == "click" and (self.page, name) in LINKS:
            self.page = LINKS[(self.page, name)]
        elif action == "click" and name == "Checkout":
            return "STOP: checkout needs the user's confirmation"
        return "ok"

def policy(obs, mem):
    """Scripted stand-in for a model: choose an element id by reading the tree text."""
    rows = [line.split(" ", 2) for line in obs.splitlines()]
    def find(word):
        return next(int(r[0][1:-1]) for r in rows if word in r[2])
    if '"Search"' in obs:
        return "click", find("Search"), None
    if '"Query"' in obs:
        if not mem.get("typed"):
            mem["typed"] = True
            return "type", find("Query"), "kettle"
        return "click", find("Go"), None
    if "Kettle 1.7" in obs:                                   # compare prices in the tree
        prices = {int(r[0][1:-1]): float(r[2].rsplit(" ", 1)[1].strip('"'))
                  for r in rows if "Kettle" in r[2]}
        return "click", min(prices, key=prices.get), None
    if "Add to basket" in obs and not mem.get("added"):
        mem["added"] = True
        return "click", find("Add to basket"), None
    if '"Basket"' in obs:
        return "click", find("Basket"), None
    return "click", find("Checkout"), None

env, mem = Shop(), {}
for step in range(1, 10):
    page, obs = env.page, env.observe()
    action, eid, text = policy(obs, mem)
    result = env.act(action, eid, text)
    print(f"{step} {page:8s} {action:5s} [{eid}] {PAGES[page][eid][1]!r} {text or ''} -> {result}")
    if result.startswith("STOP"):
        break
print(env.observe().splitlines()[0])

# --- clicking by coordinates: Gaussian pointing error ----------------------
def p_hit(w, h, sigma):
    """P(click lands in a w x h box) if x and y errors are independent N(0, sigma^2)."""
    return math.erf(w / (2 * math.sqrt(2) * sigma)) * math.erf(h / (2 * math.sqrt(2) * sigma))
rng = random.Random(0)
for w, h, sigma in [(80, 30, 10), (80, 30, 20), (24, 24, 10)]:
    hits = sum(abs(rng.gauss(0, sigma)) <= w / 2 and abs(rng.gauss(0, sigma)) <= h / 2
               for _ in range(50000))
    print(f"box {w}x{h}, sigma {sigma}px: formula {p_hit(w, h, sigma):.4f}, simulated {hits/50000:.4f}")
```

```text
1 home     click [0] 'Search'  -> ok
2 search   type  [0] 'Query' kettle -> ok
3 search   click [1] 'Go'  -> ok
4 results  click [1] 'Kettle 1.0 L - 29.50'  -> ok
5 product  click [1] 'Add to basket'  -> ok
6 product  click [2] 'Basket'  -> ok
7 basket   click [1] 'Checkout'  -> STOP: checkout needs the user's confirmation
[0] text "1 item, total 29.50"
box 80x30, sigma 10px: formula 0.8663, simulated 0.8655
box 80x30, sigma 20px: formula 0.5219, simulated 0.5200
box 24x24, sigma 10px: formula 0.5927, simulated 0.5912
```

Even this toy shows the shape of real web tasks: seven low-level actions for one intention, information (the prices) that must be read from the observation and compared, and a consequential final step that the environment refuses to take without a person. Real pages add what the toy omits — a cookie banner covering the button, a "Next page" link hiding the cheapest item, a price that changes when an option is selected.

## Grounding: from intention to pixels {#sec-grounding}

With coordinate actions, an agent that has decided to press a button must output where it is. Errors in that output are a distinct failure mode from errors in deciding *what* to do, and a simple model makes their dependence on target size and screen resolution precise.

::: proposition Hitting a target {#prop-pointing}
Suppose an agent aims at the centre of a rectangular target of width $w$ and height $h$ pixels, and its click lands at the centre plus an error $(\epsilon_x, \epsilon_y)$ with $\epsilon_x, \epsilon_y$ independent and $\Normal(0, \sigma^2)$. Then the click lands inside the target with probability
$$
P(w, h, \sigma) = \operatorname{erf}\!\left(\frac{w}{2\sqrt2\,\sigma}\right)\operatorname{erf}\!\left(\frac{h}{2\sqrt2\,\sigma}\right).
$$ {#eq-pointing}
If a screenshot is downscaled by a factor $\kappa > 1$ before the model sees it, and the model's error is $\sigma$ in screenshot pixels, the probability is $P(w/\kappa, h/\kappa, \sigma)$, where $w$ and $h$ are the target's size on the screen.
:::

::: proof
The click is inside if $\lvert\epsilon_x\rvert\le w/2$ and $\lvert\epsilon_y\rvert\le h/2$, independent events. For $\epsilon\sim\Normal(0, \sigma^2)$, $\Prob(\lvert\epsilon\rvert\le a) = \Prob(\lvert Z\rvert\le a/\sigma)$ with $Z$ standard normal, which equals $\operatorname{erf}(a/(\sigma\sqrt2))$ by the definition $\operatorname{erf}(u) = \frac{2}{\sqrt\pi}\int_0^u e^{-t^2}dt$ and the substitution $t = z/\sqrt2$. With $a = w/2$ and $a = h/2$ this gives [[#eq-pointing]]. Downscaling by $\kappa$ shrinks the target to $w/\kappa\times h/\kappa$ screenshot pixels while the model's error, measured in the pixels it sees, is $\sigma$; the click is mapped back by multiplying by $\kappa$, which scales both the error and the target equally, so the probability is the same as for the shrunken target.
:::

The default is an $80\times30$ button; the marked points are the listing's $\sigma = 10$ and $20$. The lower curve shows the same button after the screenshot is downscaled by a factor of $2$: halving the target is equivalent to doubling the error. The narrow dimension dominates: a $30$-pixel-high button is hit far less reliably than its $80$-pixel width suggests.
:::

::: example Downscaled screenshots {#ex-downscale}
A $2560\times1600$ screen is downscaled to $1280\times800$ for the model. A "Save" icon is $24\times24$ screen pixels, and the model's pointing error is $\sigma = 5$ pixels in the image it sees. The model outputs $(600, 412)$. Where should the click go on the screen, and how likely is it to hit?
::: solution
The scale factor is $\kappa = 2$ in both directions, so the click goes to $(1200, 824)$ on the screen. The icon is $12\times12$ pixels in the screenshot, so $P = \operatorname{erf}(12/(2\sqrt2\cdot5))^2 = \operatorname{erf}(0.849)^2 = 0.770^2 = 0.593$ — the same as a $24\times24$ target with $\sigma = 10$ in the listing's last line. Forgetting the factor $\kappa$ when mapping back, a common bug in scaffolds, sends every click to the top-left quarter of the screen. Agents mitigate small-target errors by zooming (requesting a crop at higher resolution), by preferring element actions where an accessibility tree exists, and by checking a fresh screenshot after each click.
:::
:::

Real pointing errors are not Gaussian — models confuse similar elements, click the label instead of the checkbox, or aim at where a button was before the page shifted — but the model captures two robust facts: small targets are disproportionately hard, and the information lost in downscaling is not recovered by a better policy. Grounding improved substantially in 2024–2025 as vision–language models were trained on large collections of screenshots paired with element locations, and dedicated grounding benchmarks (for example ScreenSpot; Cheng et al., 2024) measured it separately from task success.

## From WebGPT to computer use {#sec-history}

Browsing agents preceded large language models: MiniWoB (Shi et al., 2017) offered small synthetic web tasks — click a button, fill a form — on which reinforcement-learning agents were trained from pixels and markup. Language models changed what was attempted.

**WebGPT** (Nakano et al., 2021) fine-tuned GPT-3 to answer long-form questions by operating a text-based browser through commands such as search, click a link, find in page, scroll, quote a passage and go back. It learnt first from human demonstrations of browsing (behaviour cloning), and was then improved by best-of-$n$ sampling against a reward model trained on human comparisons ([[post-training/reward-models]]). Its answers cited the passages it had quoted; human raters preferred them to the answers of the human demonstrators $56\%$ of the time, and to the highest-voted answers on a popular question-answering forum $69\%$ of the time. WebGPT established browsing with citations as a technique, and the fact that the browser was *text* — pages converted to a simplified textual form — made it a language task.

**Benchmarks on real sites** followed. Mind2Web (Deng et al., 2023) collected over two thousand tasks with recorded human action sequences across more than a hundred real websites, evaluating whether an agent chose the same next action. Offline action matching cannot credit alternative routes and cannot test recovery, so the next benchmarks ran agents live.

::: definition WebArena and OSWorld {#def-webarena}
**WebArena** (Zhou et al., 2024) is a self-hosted environment of functional websites — an online shop, a discussion forum, a software-collaboration platform, a content-management system for the shop and a map service, with supporting tools — populated with realistic data, and $812$ tasks given in natural language ("find the cheapest product in the category … and add it to my wish list"). Success is checked **functionally**, by inspecting the final state of the sites' databases or the answer, not by comparing action sequences. **OSWorld** (Xie et al., 2024) extends the idea to full desktop operating systems in virtual machines: $369$ tasks on Ubuntu (with a further set on Windows) involving real applications — office suites, browsers, image editors, file managers, terminals — each with an initial-state configuration and an execution-based evaluation script.
:::

Both benchmarks opened with very large gaps between people and agents. WebArena's authors reported a success rate of about $14\%$ for their best GPT-4-based agent against about $78\%$ for people; OSWorld's reported about $12\%$ for the best model against about $72\%$ for people. The human figures matter as much as the model figures: they show that most tasks are well specified, and that roughly a quarter of them defeat people too, through ambiguity or genuine difficulty that any agent will also face. Variants added visual tasks (VisualWebArena; Koh et al., 2024) and other operating systems, and agents' scores rose quickly through 2024 and 2025 with better grounding, models trained on interface interaction, and longer reliable horizons.

**Computer use** as a general model capability arrived in October 2024, when Anthropic released a model and interface for operating a desktop from screenshots with mouse and keyboard actions; similar browser- and computer-operating agents from other providers followed in 2025, along with open-weight models trained for interface control. As of 2026 they are used for routine tasks in browsers and desktop applications, typically in isolated virtual machines, and remain notably slower and less reliable than API-based tool use for tasks where an API exists. The general lesson of [[agents/function-calling]] still applies: when a structured interface is available, use it; operate the screen when it is not.

::: example Screen or API? {#ex-latency}
A task — export last month's invoices as a spreadsheet — takes a computer-use agent $30$ actions. Each action needs a screenshot ($0.3$ s), a model call reading about $1{,}300$ image tokens plus the history and producing a short action ($4$ s), and execution with waiting for the page to settle ($1.5$ s). The same task through the accounting system's API takes $3$ tool calls of $2.5$ s each, including model time. Compare the wall-clock times and the number of model calls.
::: solution
Screen: $30\cdot(0.3 + 4 + 1.5) = 30\cdot5.8 = 174$ s, almost three minutes, and $30$ model calls, each a chance of error. API: $3\cdot2.5 = 7.5$ s and $3$ model calls. The ratio — more than twenty in time, ten in calls — is typical, and it is why computer use is the fallback for interfaces without APIs rather than the default. Where it is used, the latency is often acceptable because the agent works unattended, but the error exposure is not reduced by patience.
:::
:::

### Why web tasks are hard

Several difficulties compound ([[agents/agent-loops#sec-compound]]). Tasks are long: tens of actions, each a chance to misclick or misread. Pages are **non-stationary**: content loads asynchronously, layouts shift, dialogs appear, so an action computed from a screenshot taken half a second ago can land on something else. Observations are **partial**: the relevant item may be below the fold, on the next page of results or behind a menu, and an agent that does not scroll or paginate concludes that it does not exist. Many actions are **irreversible** or costly — submitting a form, sending a message, buying — and the agent cannot always tell which. And every page is **untrusted content**: text on a page is read by the model and can be designed to look like instructions ([[agents/agent-security]]).

::: widget graph

algorithm: bfs

caption: The navigation graph of a small shop. Step through breadth-first search from Home: the product page is three clicks away by search, or through Account and Orders for a reorder. Agents explore such graphs implicitly; an agent that has not seen "Page2" cannot know that the cheapest item is there, which is why partial observability, not only misclicks, causes failures. Checkout is the one node whose entry should require a person's confirmation.
:::

::: example Steps and reliability on the web {#ex-web-reliability}
A web task takes $25$ actions. Each action is decided correctly with probability $0.97$ and, given a correct decision, grounded correctly with probability $0.98$. A fresh screenshot after each action detects $70\%$ of failures, which are then retried, up to $2$ attempts per action. What is the probability of finishing the task? What if the agent used element actions with grounding accuracy $0.999$?
::: solution
Per-attempt success $p = 0.97\cdot0.98 = 0.9506$. By [[agents/agent-loops#prop-retry]] with $d = 0.7$ and $r = 2$: $S = 0.9506\,(1 + 0.0494\cdot0.7) = 0.9506\cdot1.03458 = 0.98347$, and $S^{25} = 0.659$. With element actions, $p = 0.97\cdot0.999 = 0.96903$, $S = 0.96903\,(1 + 0.03097\cdot0.7) = 0.99004$, and $S^{25} = 0.779$. Better grounding is worth twelve points of task success here; better verification would be worth more (with $d = 0.95$, the first case gives $0.887$).
:::
:::

::: warning The screen is not the truth
A screenshot shows what a page *displays*, and a page displays what its author wants. A green "Payment successful" banner may appear before the server has confirmed anything, a price may exclude fees shown later, and an element labelled "Cancel" may do something else. Agents that take displayed text at face value inherit every error and deception on the page. Where the outcome matters, verify it through a channel the page does not control — the order in the account history, a confirmation email, the file on disk — and report to the user what was verified.
:::

## Designing computer-use agents responsibly {#sec-design}

Computer-use agents combine the widest action space with the least trustworthy input, so the safeguards of [[agents/agent-security]] apply in their strongest form:

- **Isolation.** Run the agent in a dedicated virtual machine or browser profile, not on a person's everyday desktop with all their sessions logged in. Give it only the accounts the task needs, ideally separate ones with limited rights.
- **Confirmation before consequential actions.** Purchases, messages, form submissions, deletions, changes to account settings and anything involving payment or credentials should pause for a person's explicit approval, showing exactly what will happen. The toy shop's checkout rule is the pattern.
- **Allow-lists.** Restrict the sites and applications the agent may visit for a given task; a travel-booking task does not need the user's email.
- **Treat on-screen text as data.** Instructions to the agent come from the user and the system prompt; text on pages is information about the task, never a new instruction, and the scaffold should make that distinction as explicit as it can.
- **Watchability.** Let the person see the agent's screen live, pause or take over at any point, and review a recording afterwards.

::: quiz
A browsing agent is asked to "find a hotel in Lisbon under €150 a night for 3–5 May and book it". Which design best balances usefulness and safety?
- [ ] Let the agent complete the booking with the user's saved card, since the user asked for a booking.
- [x] Let the agent search, compare and fill in the booking form, then pause and show the user the hotel, dates, total price and cancellation terms for approval before submitting.
- [ ] Refuse the task, because browsing agents cannot be trusted with bookings.
- [ ] Let the agent book, then email the user a summary afterwards.
::: solution
The agent does the laborious part — search, comparison, form filling — and the person makes the irreversible decision with full information, which also catches misreadings such as a per-person price or the wrong dates. Booking without confirmation, or reporting afterwards, puts payment behind an unverified chain of perceptions and clicks; refusing gives up a task the agent can do well with a checkpoint.
:::
:::

::: history
MiniWoB (Shi et al., 2017) and its extension MiniWoB++ (Liu et al., 2018) were early benchmarks of web interaction for reinforcement-learning agents. Nakano et al. (2021) trained WebGPT to browse a text-based web with citations, and Yao et al. (2022) built WebShop, a simulated shop used to evaluate ReAct. Deng et al. (2023) released Mind2Web on real websites; Zhou et al. (WebArena, 2023; ICLR 2024) and Koh et al. (VisualWebArena, 2024) made live, functionally graded web environments standard; Xie et al. (OSWorld, 2024) did the same for desktop operating systems. Yang et al. (2023) proposed set-of-mark prompting for visual grounding, Zheng et al. (2024) identified grounding as the bottleneck for vision-language web agents, and Shaw et al. (2023) and Hong et al. (CogAgent, 2024) trained models to act from pixels. Anthropic released computer use for its models in October 2024; other providers released browser- and computer-operating agents in 2025, and open-weight interface-control models followed.
:::

::: summary
- Computer-use agents act through interfaces built for people: observations are markup, accessibility trees or screenshots; actions are coordinate, element, navigation and control operations.
- Accessibility trees are compact and actionable but depend on the page's markup; screenshots are universal but need visual grounding; raw HTML is usually too long. Observation size decides how much history fits.
- Grounding is a separate failure mode: with Gaussian pointing error $\sigma$, a $w\times h$ target is hit with probability $\operatorname{erf}(w/2\sqrt2\sigma)\operatorname{erf}(h/2\sqrt2\sigma)$; small targets and downscaled screenshots are disproportionately hard.
- WebGPT (2021) browsed a text web with citations; WebArena (812 tasks on self-hosted sites) and OSWorld (369 desktop tasks in virtual machines) grade live agents functionally and opened with large human–agent gaps.
- Web tasks are long, non-stationary, partially observed, often irreversible and full of untrusted text, so errors compound and verification through independent channels matters.
- Run computer-use agents isolated, with allow-lists, live visibility and confirmation before every consequential action; treat on-screen text as data, never as instructions.
:::

$(1792/28)\cdot(896/28) = 64\cdot32 = 2{,}048$ tokens.

::: exercise Mapping a click back {level=1}
A $3840\times2160$ screen is shown to the model as a $1280\times720$ screenshot. The model clicks at $(512, 300)$. Where on the screen should the click be sent?
::: solution
The scale factor is $3$ in both directions, so $(1536, 900)$.
:::

::: exercise Hitting a button {level=1 check="0.866"}
Using [[#eq-pointing]], what is the probability of hitting an $80\times30$-pixel button with pointing error $\sigma = 10$ pixels? Give three decimal places.
::: solution
$\operatorname{erf}(80/28.28)\operatorname{erf}(30/28.28) = \operatorname{erf}(2.828)\operatorname{erf}(1.061) = 0.99994\cdot0.8664 = 0.866$.
:::
:::

::: exercise Required precision {level=2 check="6.12"}
What pointing error $\sigma$ (in pixels) gives a $95\%$ chance of hitting a $24$-pixel-wide target in the horizontal direction alone? Use $\Prob(\lvert Z\rvert\le1.96) = 0.95$ and give two decimal places.
::: solution
The click is within $12$ pixels of the centre with probability $0.95$ when $12/\sigma = 1.96$, so $\sigma = 12/1.96 = 6.12$ pixels. Hitting the target in both directions with probability $0.95$ needs each direction at $\sqrt{0.95} = 0.9747$, that is $z = 2.236$ and $\sigma = 5.36$ pixels.
:::
:::

Reproduce the first result of [[#ex-web-reliability]]: $25$ actions, decision accuracy $0.97$, grounding accuracy $0.98$, detection $d = 0.7$, $r = 2$. Give three decimal places.
::: solution
$p = 0.9506$, $S = 0.9506\,(1 + 0.0494\cdot0.7) = 0.98347$, $S^{25} = e^{25\ln0.98347} = e^{25\cdot(-0.016668)} = e^{-0.41671} = 0.659$.

::: exercise Choosing an observation {level=2}
For each task, choose an observation type (accessibility tree, screenshot, or both) and justify it: (a) filling a long form on a well-built government website; (b) editing a diagram in a canvas-based drawing application; (c) checking that a web page's layout looks correct on a phone-sized screen; (d) operating a legacy desktop application over a remote-desktop connection.
::: solution
(a) Accessibility tree: forms are well labelled on accessible sites, element actions avoid grounding errors, and the tree is compact over many fields. (b) Screenshot: the canvas content is not in the tree. (c) Screenshot, with the tree for locating elements: layout correctness is visual by definition. (d) Screenshot: a remote desktop transmits only pixels, so no tree is available, and coordinate actions are the only option — favour zooming and post-action verification.
:::
:::

::: exercise Detecting failures by screenshot {level=3}
In [[#ex-web-reliability]], find the detection rate $d$ needed for the coordinate-action agent to finish the $25$-step task with probability $0.9$, with $r = 2$. Then discuss what makes failure detection from screenshots hard, and one technique that raises $d$.
::: solution
We need $S^{25} = 0.9$, $S = 0.9^{1/25} = 0.995794$. With $p = 0.9506$: $0.9506\,(1 + 0.0494d) = 0.995794$, so $1 + 0.0494d = 1.047543$ and $d = 0.962$. Detection is hard because many failures look like success on screen: a click that landed on whitespace changes nothing visible, a form field that rejected input may show no error until submission, a slow page has not changed *yet*. Techniques that raise $d$: compare the screenshot before and after each action and treat "no change" as a likely failure; check for the expected effect explicitly (the field now contains the typed text, the basket count increased) by reading the accessibility tree or the page's state; and wait for the page to settle (network idle) before observing.
:::
:::

::: exercise Information hidden by pagination {level=3}
An agent looks for the cheapest of $N$ items listed $10$ per page, in random order. If it inspects only the first page, what is the probability that it finds the true cheapest item? If each additional page costs one action that fails independently with probability $0.02$, and a failed action ends the search with the best item seen so far, how many pages should it plan to read when $N = 50$, and what is its success probability?
::: solution
Only the first page: the cheapest item is on it with probability $10/N$, $0.2$ for $N = 50$. Reading all $5$ pages needs $4$ page-turning actions, all successful with probability $0.98^4 = 0.922$, and then the agent certainly finds the cheapest. Reading $m$ pages in all succeeds if the item is on one of the pages actually reached. The success probability is $\sum_{j=1}^{m}\frac{10}{50}\cdot0.98^{j-1}$: for $m = 5$, $0.2\,(1 + 0.98 + 0.9604 + 0.9412 + 0.9224) = 0.2\cdot4.804 = 0.961$. (Even when a page turn fails, the item may already have been seen.) Since every additional page increases the probability, it should read all five; the gain from page $j$ is $0.2\cdot0.98^{j-1}$, always positive. The lesson is that stopping early is a much larger risk than the cost of the extra actions, and agents must be told — or must learn — to exhaust pagination when a task asks for an extremum.
:::
