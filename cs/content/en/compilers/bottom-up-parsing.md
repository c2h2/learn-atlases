A top-down parser must decide which production to use for a construct *before* it has seen the construct: facing `id` at the start of a statement, it must already know whether it is an assignment or a call. The previous chapter showed how grammars can be rewritten to make such early decisions possible, and what that costs — left recursion removed, left factoring, parse trees that lean the wrong way. **Bottom-up** parsing takes the opposite approach. It reads tokens, keeps them on a stack, and only when the complete right-hand side of a production is on top of the stack does it decide to replace it by the left-hand side. Delaying the decision until all the evidence is in makes bottom-up parsers strictly more powerful than top-down ones: they handle left recursion directly, accept every LL(1) grammar and many more, and yet still run in linear time.

The price is that the parser's decisions — when to keep reading and when to reduce, and by which production — are no longer obvious to a human, so the parsers are almost always generated by a program, from the grammar, as tables. This chapter explains how. The central idea, due to Donald Knuth (1965), is that the stacks a correct parser can ever have form a *regular language*, recognised by a finite automaton built from "items" — productions with a marked position. We build that automaton (LR(0)), use it with look-ahead in three increasingly precise ways (SLR, LR(1), LALR(1)), compute everything with a short Python program, and compare with GNU Bison.

## Shift–reduce parsing

A bottom-up parser builds a parse tree from the leaves. In terms of derivations it runs a **rightmost** derivation backwards: each step replaces an occurrence of a right-hand side by its left-hand side (a **reduction**), until only the start symbol remains. Take the left-recursive expression grammar of [[compilers/top-down-parsing#eq-lr-grammar]], which bottom-up parsers handle as it is:

$$
E \to E + T \mid T \qquad T \to T * F \mid F \qquad F \to (\,E\,) \mid \mathrm{id}
$$

The rightmost derivation of `id * id + id` is

$$
\begin{aligned}
E &\Rightarrow E + T \Rightarrow E + F \Rightarrow E + \mathrm{id} \Rightarrow T + \mathrm{id} \Rightarrow T * F + \mathrm{id} \\
&\Rightarrow T * \mathrm{id} + \mathrm{id} \Rightarrow F * \mathrm{id} + \mathrm{id} \Rightarrow \mathrm{id} * \mathrm{id} + \mathrm{id},
\end{aligned}
$$

and a bottom-up parser discovers it from right to left: first reduce the first `id` to $F$, then $F$ to $T$, and so on.

::: definition Handle {#def-handle}
Let $S \Rightarrow^*_{\mathrm{rm}} \alpha A w \Rightarrow_{\mathrm{rm}} \alpha\beta w$ be a step of a rightmost derivation, with $w$ a string of terminals. The production $A \to \beta$ at the position just after $\alpha$ is a **handle** of the right-sentential form $\alpha\beta w$. A prefix of a right-sentential form that does not extend past the right end of its handle is a **viable prefix**.
:::

Since the derivation is rightmost, everything to the right of the handle is terminals. That is what makes a stack sufficient: a **shift–reduce parser** keeps the part $\alpha\beta$ to the left of the unread input on a stack and has four actions:

- **shift**: move the next input token onto the stack;
- **reduce** by $A \to \beta$: the top of the stack is $\beta$; pop it and push $A$;
- **accept**: the stack holds the start symbol and the input is exhausted;
- **error**.

The stack always holds a viable prefix, and the parser reduces exactly when the handle is on top. The whole problem of bottom-up parsing is deciding *when the top of the stack is a handle* — and if so, which one. Two things can go wrong. In a **shift/reduce conflict** the parser cannot decide whether to reduce or to shift more; in a **reduce/reduce conflict** it cannot decide between two productions.

::: example Handle pruning by hand {#ex-handles}
Parse `id * id + id` by shift–reduce steps, stating the handle at each reduction.
::: solution
| stack | input | action |
|---|---|---|
| | `id * id + id $` | shift |
| `id` | `* id + id $` | reduce $F \to \mathrm{id}$ |
| $F$ | `* id + id $` | reduce $T \to F$ |
| $T$ | `* id + id $` | shift — not reduce $E \to T$! |
| $T\ *$ | `id + id $` | shift |
| $T * \mathrm{id}$ | `+ id $` | reduce $F \to \mathrm{id}$ |
| $T * F$ | `+ id $` | reduce $T \to T * F$ |
| $T$ | `+ id $` | reduce $E \to T$ |
| $E$ | `+ id $` | shift |
| $E\ +$ | `id $` | shift |
| $E + \mathrm{id}$ | `$` | reduce $F \to \mathrm{id}$ |
| $E + F$ | `$` | reduce $T \to F$ |
| $E + T$ | `$` | reduce $E \to E + T$ |
| $E$ | `$` | accept |

The fourth row shows the difficulty. $T$ is a right-hand side ($E \to T$), but it is not the handle: reducing would give $E\ *\ \mathrm{id} + \mathrm{id}$, which is not a right-sentential form, because no sentential form has $E$ followed by $*$. The right decision depends on the next token: before `*` shift, before `+` reduce. The reductions, read from bottom to top, are the rightmost derivation above.
:::
:::

## LR(0) items and the characteristic automaton

How can a parser know whether the top of its stack is a handle without rescanning the stack at every step? Knuth's insight was to track, as the stack grows, *where in which productions* the parser might be.

::: definition LR(0) item {#def-item}
An **LR(0) item** of a grammar is a production with a dot somewhere in its right-hand side: $A \to \alpha \cdot \beta$ for a production $A \to \alpha\beta$. The item says: "we may be in the middle of recognising $A \to \alpha\beta$, having seen $\alpha$ and expecting $\beta$." An item $A \to \alpha\cdot$ with the dot at the end is **complete**. A production $A \to X_1 \cdots X_k$ has $k + 1$ items; $A \to \varepsilon$ has the single item $A \to \cdot$.
:::

We **augment** the grammar with a new start symbol $S'$ and production $S' \to S$, so that acceptance is the reduction by $S' \to S$ when the input is exhausted. Two operations on sets of items build the automaton.

- **Closure.** If $A \to \alpha \cdot B\beta$ is in a set $I$ and $B$ is a nonterminal, then the parser, expecting a $B$, might be at the beginning of any production for $B$; so add $B \to \cdot\gamma$ for every production $B \to \gamma$, and repeat.
- **Goto.** $\mathrm{goto}(I, X)$ is the closure of $\set{A \to \alpha X \cdot \beta : A \to \alpha \cdot X\beta \in I}$: move the dot over $X$ in every item that expects $X$.

::: algorithm Canonical collection of LR(0) item sets {#alg-lr0}
1. $I_0 \gets \mathrm{closure}(\set{S' \to \cdot S})$; $C \gets [I_0]$.
2. For each set $I$ in $C$ (including sets added along the way) and each grammar symbol $X$: let $J = \mathrm{goto}(I, X)$; if $J \ne \emptyset$, add $J$ to $C$ if it is new, and record the transition $I \xrightarrow{X} J$.
3. The sets in $C$ are the states, and the transitions the edges, of the **LR(0) automaton**, a DFA over grammar symbols whose start state is $I_0$.
:::

In Python, with an item represented as a pair (production number, dot position), and with `grammar` and `first_follow` from [[compilers/top-down-parsing]]:

```python
from ll1 import grammar, first_follow

def augment(prods):
    return [("S'", [prods[0][0]])] + prods          # production 0: S' -> S

def closure0(prods, items):                         # item = (production, dot position)
    items, work = set(items), list(items)
    while work:
        p, d = work.pop(); rhs = prods[p][1]
        if d < len(rhs):
            for q, (lhs, _) in enumerate(prods):
                if lhs == rhs[d] and (q, 0) not in items:
                    items.add((q, 0)); work.append((q, 0))
    return frozenset(items)

def goto(prods, I, X, close):
    return close(prods, {(it[0], it[1] + 1) + it[2:] for it in I
                         if it[1] < len(prods[it[0]][1]) and prods[it[0]][1][it[1]] == X})

def collection(prods, start, close):
    states, edges, work = [start], {}, [start]
    symbols = {x for _, rhs in prods for x in rhs}
    while work:
        I = work.pop(0)
        for X in sorted(symbols):
            J = goto(prods, I, X, close)
            if not J: continue
            if J not in states: states.append(J); work.append(J)
            edges[states.index(I), X] = states.index(J)
    return states, edges
```

(`goto` and `collection` are written to work unchanged for the LR(1) items of the next section, which carry an extra component; `it[2:]` passes it along.)

States $I_3, I_5, I_9, I_{11}$ have no outgoing edges: each contains a single complete item, and reaching one means "reduce now".

The automaton is a DFA whose input alphabet is the set of *grammar symbols*. Its meaning is the theorem behind LR parsing.

::: definition Valid item {#def-valid}
An item $A \to \beta_1 \cdot \beta_2$ is **valid** for a viable prefix $\gamma$ if there is a rightmost derivation $S' \Rightarrow^*_{\mathrm{rm}} \alpha A w \Rightarrow_{\mathrm{rm}} \alpha\beta_1\beta_2 w$ with $\gamma = \alpha\beta_1$.
:::

::: theorem Knuth's theorem on viable prefixes {#thm-viable}
For every string $\gamma$ of grammar symbols, the LR(0) automaton has a run on $\gamma$ from $I_0$ if and only if $\gamma$ is a viable prefix, and in that case the state reached is exactly the set of items valid for $\gamma$. In particular, the set of viable prefixes of a context-free grammar is a regular language.
:::

::: proof
We prove: the state reached on $\gamma$ (if any) equals $V(\gamma)$, the set of items valid for $\gamma$; and the run exists iff $V(\gamma) \ne \emptyset$. Since every viable prefix has at least one valid item (from the step of the derivation in which it occurs) and a prefix with a valid item is viable by definition, this gives the theorem. Induction on $\lvert \gamma \rvert$.

*Base*, $\gamma = \varepsilon$. The items valid for $\varepsilon$ are those $A \to \cdot\beta$ arising from derivations $S' \Rightarrow^*_{\mathrm{rm}} A w$; these are $S' \to \cdot S$ and, recursively, $B \to \cdot\delta$ whenever $A \to \cdot B\eta$ is valid (extend the derivation by rewriting $B$, then derive $\eta$ to terminals — possible since we assume every symbol derives some terminal string). That is exactly $\mathrm{closure}(\set{S' \to \cdot S}) = I_0$.

*Step.* Let $\gamma = \gamma' X$, and suppose the claim for $\gamma'$. First, an item with the dot not at the start, $A \to \beta_1 X \cdot \beta_2$, is valid for $\gamma' X$ iff $A \to \beta_1 \cdot X\beta_2$ is valid for $\gamma'$ — the same derivation witnesses both. Second, an item $B \to \cdot\delta$ is valid for $\gamma$ iff it is obtained by the closure rule from an item valid for $\gamma$ with the dot before $B$: if $S' \Rightarrow^*_{\mathrm{rm}} \gamma B w \Rightarrow \gamma\delta w$, look at the step that introduced this occurrence of $B$; it came from some item $C \to \mu \cdot B\nu$ valid for $\gamma$ (with $\nu$ derived to terminals in between, which is allowed in a rightmost derivation since $\nu$ is to the right), and conversely the closure rule only adds items that are valid by this construction. Hence $V(\gamma' X) = \mathrm{closure}(\set{A \to \beta_1 X\cdot\beta_2 : A \to \beta_1\cdot X\beta_2 \in V(\gamma')}) = \mathrm{goto}(V(\gamma'), X)$, which by the induction hypothesis is $\mathrm{goto}$ applied to the state reached on $\gamma'$. And the automaton has no transition exactly when this set is empty.
:::

So the parser need not examine its stack at all: it runs the automaton over the stack symbols, and the state tells it which items are valid. A complete item $A \to \beta\cdot$ in the state says "$\beta$ on top of the stack may be a handle for $A \to \beta$"; an item $A \to \alpha \cdot a\beta$ says "shifting $a$ keeps the stack a viable prefix". Better still, the parser does not even rerun the automaton after each reduction: it keeps the *state* reached after each stack symbol on the stack itself, so after popping $\lvert\beta\rvert$ entries the state underneath is the one reached on $\alpha$, and one goto transition on $A$ gives the new state.

## LR parsing tables: LR(0) and SLR(1)

::: definition LR parsing table {#def-lr-table}
An **LR table** has two parts. $\mathrm{ACTION}[s, a]$, for a state $s$ and a terminal or $\$$, is shift $t$, reduce $p$, accept or error. $\mathrm{GOTO}[s, A]$, for a nonterminal $A$, is the state reached from $s$ on $A$. From the automaton: if $A \to \alpha \cdot a\beta \in I_s$ with $a$ a terminal, $\mathrm{ACTION}[s, a] = $ shift $\mathrm{goto}(s, a)$; if $S' \to S \cdot \in I_s$, $\mathrm{ACTION}[s, \$] = $ accept; and if a complete item $A \to \beta \cdot$ (with $A \ne S'$) is in $I_s$, $\mathrm{ACTION}[s, a] = $ reduce $A \to \beta$ for all $a$ in a **look-ahead set** $\mathrm{LA}(s, A \to \beta)$. A grammar is in the class corresponding to a choice of look-ahead sets if no ACTION entry receives two different actions.
:::

- **LR(0)**: $\mathrm{LA}$ is the set of all terminals — reduce whenever a complete item is present, without looking at the input. Very few grammars are LR(0); the expression grammar is not, because of states 4 and 10.
- **SLR(1)** ("simple LR", DeRemer 1971): $\mathrm{LA}(s, A \to \beta) = \mathrm{FOLLOW}(A)$. Reduce to $A$ only if the next token can follow $A$ in *some* sentential form.

```python
def lr_table(prods, states, edges, lookahead):
    """lookahead(state, item) -> set of terminals on which to reduce."""
    nts = {a for a, _ in prods}
    action, conflicts = {}, []
    def put(s, t, act):
        old = action.setdefault((s, t), act)
        if old != act: conflicts.append((s, t, old, act))
    for s, I in enumerate(states):
        for it in sorted({it[:2] for it in I}):     # each core item once
            p, d = it; rhs = prods[p][1]
            if d < len(rhs) and rhs[d] not in nts:
                put(s, rhs[d], ("shift", edges[s, rhs[d]]))
            elif p == 0:                            # S' -> S . : accept at the end
                put(s, "$", ("accept",))
            elif d == len(rhs):
                for t in sorted(lookahead(s, it)):
                    put(s, t, ("reduce", p))
    return action, conflicts

def lr0_slr(prods, slr=True):
    prods = augment(prods)
    terms = {x for _, rhs in prods for x in rhs} - {a for a, _ in prods} | {"$"}
    follow = first_follow(prods)[2]
    states, edges = collection(prods, closure0(prods, {(0, 0)}), closure0)
    la = (lambda s, it: follow[prods[it[0]][0]]) if slr else (lambda s, it: terms)
    action, conflicts = lr_table(prods, states, edges, la)
    return prods, states, edges, action, conflicts
```

For the expression grammar, the LR(0) table has two conflicts, `(4, '*', ('reduce', 2), ('shift', 8))` and `(10, '*', ('reduce', 1), ('shift', 8))`, and the SLR table has none: $\mathrm{FOLLOW}(E) = \set{+, ), \$}$ does not contain `*`, so in state 4 the parser reduces by $E \to T$ only on `+`, `)` and `$`, and shifts on `*`. That is exactly the rule we found by hand.

The driver is the same for every kind of LR table. Its stack holds states; the grammar symbols are kept only for the trace.

```python
def lr_parse(prods, edges, action, tokens, trace=False):
    stack, toks, pos = [0], tokens + ["$"], 0      # stack of states (symbols implicit)
    syms = []                                       # grammar symbols, for the trace only
    while True:
        s, a = stack[-1], toks[pos]
        act = action.get((s, a))
        if trace: print(f"{' '.join(map(str, stack)):<14}{' '.join(syms):<14}{' '.join(toks[pos:]):<20}", end="")
        if act is None: raise SyntaxError(f"unexpected {a} in state {s}")
        if act[0] == "shift":
            stack.append(act[1]); syms.append(a); pos += 1
            if trace: print("shift", act[1])
        elif act[0] == "reduce":
            lhs, rhs = prods[act[1]]
            if rhs: del stack[-len(rhs):]; del syms[-len(rhs):]
            stack.append(edges[stack[-1], lhs]); syms.append(lhs)
            if trace: print(f"reduce {lhs} -> {' '.join(rhs)}")
        else:
            if trace: print("accept")
            return True
```

Look at the reduction by $T \to T * F$: the parser pops three states (`4 8 11`), uncovering state 0, and $\mathrm{GOTO}[0, T] = 4$. On `id + * id` the parser stops with `SyntaxError: unexpected * in state 7`: state 7 expects the start of a term after `+`.

::: theorem LR parsing is correct and linear {#thm-lr-correct}
If the ACTION table of a grammar has no conflicts (for any of the look-ahead choices above, or LR(1) below), then on every input $w$ the driver accepts if and only if $w \in L(G)$, its reductions in order are the reverse of the rightmost derivation of $w$, and it performs $O(\lvert w \rvert)$ actions.
:::

::: proof
*Soundness.* By [[#thm-viable]], the stack of states always corresponds to a viable prefix $\gamma$ of grammar symbols, and an invariant is that $\gamma$ followed by the unread input derives — in reverse — from the reductions made so far: a reduction replaces a right-hand side on top of the stack by its left-hand side, so if $\gamma' A x$ is a right-sentential form reached by a rightmost derivation then so is the form before the reduction. Acceptance means the stack is $S$ and the input empty, so the reductions read backwards form a rightmost derivation of $w$.

*Completeness.* Suppose $w \in L(G)$. Its rightmost derivation determines, at each point, the correct action: if the handle is on top of the stack, reduce by it; otherwise shift. In the first case the complete item for the handle is valid for the stack, so it is in the state, and the next token is in the look-ahead set (FOLLOW, or the LR(1) look-ahead, contains every token that can actually follow); in the second case some item with the dot before the next token is valid. Since the table has no conflicts, the correct action is the *only* action, and by induction the parser follows the derivation.

*Linear time.* Each shift consumes a token, so there are $\lvert w \rvert$ shifts. A conflict-free grammar is unambiguous (the parser's choices are forced), hence it has no cycle $A \Rightarrow^+ A$, and for a grammar without such cycles the number of interior nodes of a parse tree is at most a constant $c_G$ times the number of leaves plus one, so there are $O(\lvert w \rvert)$ reductions. (A grammar with $\varepsilon$-productions can have empty subtrees, but in a parse tree without cycles each run of nested empty subtrees has bounded size.) On an erroneous input the parser stops at the first error entry; it never makes more moves than on the longest correct prefix plus a bounded number of reductions.
:::

## LR(1) and LALR(1)

SLR uses FOLLOW sets, which merge the contexts in which a nonterminal appears: if $A$ can be followed by `=` *somewhere*, SLR considers reducing to $A$ before `=` *everywhere*. The classic grammar where this is not good enough models assignments in C, where the left side of `=` is an *l-value* (here $L$: a variable or a dereferenced pointer) and the right side an *r-value* $R$:

$$
S \to L = R \mid R \qquad L \to * R \mid \mathrm{id} \qquad R \to L
$$ {#eq-lvalue}

::: example An SLR conflict {#ex-slr-conflict}
Find the SLR conflict of [[#eq-lvalue]] and explain why it is spurious.
::: solution
The LR(0) automaton has ten states; state 2 is reached from the start on $L$ and contains

```text
2 S -> L . = R; R -> L .
```

The first item says shift on `=`. The second is complete, and SLR reduces by $R \to L$ on $\mathrm{FOLLOW}(R)$. Our program computes $\mathrm{FOLLOW}(R) = \set{=, \$}$: $R$ can be followed by `=` because $S \Rightarrow L = R \Rightarrow {*}R = R$, where the first $R$ is followed by `=`. So the table has the conflict `(2, '=', ('shift', 8), ('reduce', 5))` (production 5 is $R \to L$).

But in state 2 we have just read an $L$ at the very *start* of a statement. Reducing it to $R$ would make the statement begin with $R$, and an $R$ at the start can only be the whole statement ($S \to R$), followed by `$`, never by `=`. The FOLLOW set mixes in the `=` that follows an $R$ in a different place (after `*`). The reduction before `=` is never correct here; the grammar is unambiguous, and the conflict is an artefact of SLR's coarse look-ahead.
:::
:::

The cure is to carry the look-ahead inside the items.

::: definition LR(1) item {#def-lr1-item}
An **LR(1) item** is a pair $[A \to \alpha \cdot \beta,\ a]$ of an LR(0) item (its **core**) and a terminal or $\$$ $a$, the **look-ahead**. It is valid for a viable prefix $\gamma$ if there is a rightmost derivation $S' \Rightarrow^*_{\mathrm{rm}} \delta A w \Rightarrow_{\mathrm{rm}} \delta\alpha\beta w$ with $\gamma = \delta\alpha$ and $a$ the first symbol of $w\$$. The closure rule becomes: if $[A \to \alpha \cdot B\beta,\ a]$ is in the set, add $[B \to \cdot\gamma,\ b]$ for every production $B \to \gamma$ and every $b \in \mathrm{FIRST}(\beta a)$. In the canonical **LR(1)** table, a complete item $[A \to \alpha\cdot,\ a]$ means reduce on $a$ only.
:::

The look-ahead of a closure item is what can follow the $B$ *in this particular context*: the first symbol of $\beta$, or, if $\beta$ can vanish, the look-ahead $a$ of the item that asked for $B$. Only the closure changes; `goto`, the collection and the table builder are reused:

```python
def closure1(prods, items):                         # item = (production, dot, lookahead)
    nullable, first, _, first_seq = first_follow(prods)
    items, work = set(items), list(items)
    while work:
        p, d, a = work.pop(); rhs = prods[p][1]
        if d < len(rhs) and rhs[d] in first:        # dot before a nonterminal B
            f, nul = first_seq(rhs[d + 1:])
            for b in f | ({a} if nul else set()):   # lookaheads: FIRST(beta a)
                for q, (lhs, _) in enumerate(prods):
                    if lhs == rhs[d] and (q, 0, b) not in items:
                        items.add((q, 0, b)); work.append((q, 0, b))
    return frozenset(items)

def lr1(prods, lalr=False):
    prods = augment(prods)
    states, edges = collection(prods, closure1(prods, {(0, 0, "$")}), closure1)
    if lalr:                                        # merge states with the same core
        core = lambda I: frozenset((p, d) for p, d, _ in I)
        cores = []
        for I in states:
            if core(I) not in cores: cores.append(core(I))
        merged = [frozenset().union(*(I for I in states if core(I) == c)) for c in cores]
        edges = {(cores.index(core(states[s])), X): cores.index(core(states[t]))
                 for (s, X), t in edges.items()}
        states = merged
    la = lambda s, it: {a for p, d, a in states[s] if (p, d) == it[:2]}
    action, conflicts = lr_table(prods, states, edges, la)
    return prods, states, edges, action, conflicts
```

Canonical LR(1) is the most powerful of the methods — a grammar is LR(1) exactly when it can be parsed deterministically bottom-up with one token of look-ahead — but it can have many more states than LR(0), because states with the same items and different look-aheads are kept apart. **LALR(1)** ("look-ahead LR", DeRemer 1969) is the compromise used by Yacc and Bison: merge the LR(1) states that have the same core, taking the union of their look-aheads. The merged automaton has exactly the states of the LR(0) automaton — the cores of the LR(1) states are precisely the LR(0) states — but with look-ahead sets that are usually far more precise than FOLLOW.

::: example LALR(1) resolves the l-value conflict {#ex-lalr}
Compute the LALR(1) states of [[#eq-lvalue]] with their look-aheads and check state 2.
::: solution
The program prints (look-aheads after the comma, `$/=` meaning $\set{\$, =}$):

```text
0 S' -> . S, $; S -> . L = R, $; S -> . R, $; L -> . * R, $/=; L -> . id, $/=; R -> . L, $
1 L -> . * R, $/=; L -> * . R, $/=; L -> . id, $/=; R -> . L, $/=
2 S -> L . = R, $; R -> L ., $
3 S -> R ., $
4 S' -> S ., $
5 L -> id ., $/=
6 R -> L ., $/=
7 L -> * R ., $/=
8 S -> L = . R, $; L -> . * R, $; L -> . id, $; R -> . L, $
9 S -> L = R ., $
```

In state 0, $S \to \cdot R$ has look-ahead $\$$, and closure gives $R \to \cdot L$ the look-ahead $\mathrm{FIRST}(\varepsilon\,\$) = \set{\$}$. Moving over $L$, state 2 contains $[R \to L\cdot,\ \$]$: reduce only before $\$$. The shift on `=` no longer conflicts, and `lr1(LR, lalr=True)` reports no conflicts. The canonical LR(1) automaton has 14 states (it keeps separate copies of $L \to \mathrm{id}\cdot$ and friends for the contexts "before `=`" and "at the end"); LALR merges them back into the 10 LR(0) states.
:::
:::

Merging never loses as much as SLR does, but it can lose something.

::: theorem Merging cores introduces no shift/reduce conflicts {#thm-lalr-merge}
If a grammar is LR(1), its LALR(1) table may have reduce/reduce conflicts, but it has no shift/reduce conflicts.
:::

::: proof
Suppose a merged state $M$ has a shift/reduce conflict on $a$: it contains a complete item $[A \to \alpha\cdot,\ a]$ and an item $[B \to \beta \cdot a\gamma,\ b]$ for some $b$. The complete item came from some LR(1) state $I$ with the core of $M$. Since all the LR(1) states merged into $M$ have the same core, $I$ also contains an item with core $B \to \beta \cdot a \gamma$ (with some look-ahead). Shift actions depend only on the core, so $I$ shifts on $a$ and reduces by $A \to \alpha$ on $a$: $I$ already had the conflict, and the grammar is not LR(1). Reduce/reduce conflicts can arise because look-aheads of *different* complete items, from different LR(1) states, are united.
:::

::: example LR(1) but not LALR(1) {#ex-not-lalr}
Show that $S \to a\,A\,d \mid b\,B\,d \mid a\,B\,e \mid b\,A\,e$, $A \to c$, $B \to c$ is LR(1) but not LALR(1).
::: solution
After `a c` the LR(1) parser is in the state $\set{[A \to c\cdot,\ d],\ [B \to c\cdot,\ e]}$ — after $a$, an $A$ must be followed by $d$ and a $B$ by $e$ — and after `b c` in $\set{[A \to c\cdot,\ e],\ [B \to c\cdot,\ d]}$. Each state is conflict-free, and the program finds 14 LR(1) states and no conflicts:

```text
6 A -> c ., d; B -> c ., e
9 A -> c ., e; B -> c ., d
```

The two states have the same core $\set{A \to c\cdot, B \to c\cdot}$, so LALR merges them into one state in which both reductions have look-aheads $\set{d, e}$: two reduce/reduce conflicts, on $d$ and on $e$ — and the LALR automaton has 13 states. SLR fails in the same way. GNU Bison 3.8.2, whose default is LALR(1), agrees: `warning: 2 reduce/reduce conflicts`; with `-Dlr.type=canonical-lr` (or `ielr`, an algorithm that splits only the states that need it), the warning disappears.
:::
:::

The four methods form a hierarchy. Our program's results on the four grammars of this chapter:

| grammar | LR(0) | SLR(1) | LALR(1) | LR(1) |
|---|---|---|---|---|
| expressions | 12 states, 2 conflicts | 12 states, none | 12 states, none | 22 states, none |
| l-values [[#eq-lvalue]] | 10, 1 | 10, 1 | 10, none | 14, none |
| [[#ex-not-lalr]] | 13, 6 | 13, 2 | 13, 2 | 14, none |
| $E \to E+E \mid E*E \mid \mathrm{id}$ | 7, 4 | 7, 4 | 7, 4 | 7, 4 |

Every LR(0) grammar is SLR(1), every SLR(1) grammar is LALR(1) and every LALR(1) grammar is LR(1), and the examples show that each inclusion is strict. Every LL(1) grammar is also LR(1) — a bottom-up parser knows everything a top-down parser knows, and more — but not necessarily LALR(1). The last row is an ambiguous grammar, which no method can parse without help.

::: quiz
A state of an LALR(1) parser contains the items $[A \to x\,\cdot,\ \set{a, b}]$ and $[B \to x \cdot y,\ \set{a}]$, where $y$ is a terminal. Which statement is correct?
- [ ] There is a shift/reduce conflict on $a$.
- [ ] There is a reduce/reduce conflict on $a$.
- [x] There is no conflict: reduce on $a$ or $b$, shift on $y$.
- [ ] The parser cannot reduce, because the look-ahead of the second item contains $a$.
::: solution
A shift/reduce conflict needs a complete item whose look-ahead contains a terminal that some item has *after its dot*. Here the dot in $B \to x \cdot y$ is before $y$, so the state shifts on $y$; the look-ahead $\set{a}$ of that item matters only later, when $B \to xy\cdot$ is complete. The complete item reduces on $a$ and $b$. Distinct terminals, no conflict.
:::
:::

## Ambiguity, precedence and parser generators

Grammar writers often prefer the ambiguous but readable $E \to E + E \mid E * E \mid \mathrm{id}$ to the layered grammar, and declare the precedence and associativity of the operators separately. Bison reports the conflicts and resolves them using the declarations:

```console
$ cat amb.y
%token ID
%%
e : e '+' e | e '*' e | ID ;
$ bison amb.y
amb.y: warning: 4 shift/reduce conflicts [-Wconflicts-sr]
$ cat prec.y
%token ID
%left '+'
%left '*'
%%
e : e '+' e | e '*' e | ID ;
$ bison prec.y && echo no conflicts
no conflicts
```

The rule: each production gets the precedence of its last terminal, each token its declared precedence (later `%left` lines bind tighter). In a shift/reduce conflict between reducing by a production $p$ and shifting a token $t$, reduce if $p$ has higher precedence than $t$, shift if lower, and if equal, reduce for `%left` and shift for `%right`. Unresolved shift/reduce conflicts default to shift (which implements the nearest-`if` rule for the dangling `else`: Bison reports `1 shift/reduce conflict` for the `if`-`then`-`else` grammar, and the default resolution is the right one), and reduce/reduce conflicts to the production listed first.

::: example Resolving conflicts by precedence {#ex-prec}
Implement the precedence rule on top of `lr_table` and parse `id + id * id + id` with the ambiguous grammar.
::: solution
```python
PREC = {"+": (1, "left"), "*": (2, "left")}       # like %left '+'  %left '*'
def resolve(prods, action, conflicts):
    for s, t, a1, a2 in conflicts:
        shift, red = (a1, a2) if a1[0] == "shift" else (a2, a1)
        if shift[0] != "shift" or red[0] != "reduce": continue   # leave r/r conflicts
        ops = [x for x in prods[red[1]][1] if x in PREC]
        if not ops or t not in PREC: continue
        p_rule, (p_tok, assoc) = PREC[ops[-1]][0], PREC[t]       # rule takes its last operator's precedence
        action[s, t] = red if p_rule > p_tok or (p_rule == p_tok and assoc == "left") else shift
    return action
AMB = grammar("E -> E + E | E * E | id")
prods, states, edges, action, conflicts = lr0_slr(AMB)
action = resolve(prods, action, conflicts)
lr_parse(prods, edges, action, "id + id * id + id".split(), trace=True)
```

```text
0                           id + id * id + id $ shift 2
0 2           id            + id * id + id $    reduce E -> id
0 1           E             + id * id + id $    shift 4
0 1 4         E +           id * id + id $      shift 2
0 1 4 2       E + id        * id + id $         reduce E -> id
0 1 4 6       E + E         * id + id $         shift 3
0 1 4 6 3     E + E *       id + id $           shift 2
0 1 4 6 3 2   E + E * id    + id $              reduce E -> id
0 1 4 6 3 5   E + E * E     + id $              reduce E -> E * E
0 1 4 6       E + E         + id $              reduce E -> E + E
0 1           E             + id $              shift 4
0 1 4         E +           id $                shift 2
0 1 4 2       E + id        $                   reduce E -> id
0 1 4 6       E + E         $                   reduce E -> E + E
0 1           E             $                   accept
```

In state 6 ($E + E$ on the stack) facing `*`, the rule $E \to E + E$ has precedence 1 and `*` has 2, so the parser shifts: multiplication binds tighter. Facing `+` in the same state, equal precedence and `%left` give a reduction: `(a + b*c) + d`. The table has only 7 states, against 12 for the layered grammar, and the parser makes no unit reductions such as $T \to F$ — one reason why parser generators encourage this style.
:::
:::

::: warning "No conflicts" does not mean "the grammar I meant"
Precedence declarations silence conflicts; they do not check that the resolution is what you intended. A misplaced `%left` or an unintended default shift produces a parser that accepts the right language but builds the wrong trees, and the generator says nothing. Conversely, a conflict report is not proof of ambiguity: the grammar may be unambiguous but not LALR(1) ([[#ex-not-lalr]]). Read the conflict report (Bison's `-Wcounterexamples` prints an input showing the two ways of parsing it), resolve each conflict deliberately, and test the trees, not only acceptance.
:::

### Generated or hand-written?

LR parser generators are used for many language implementations — PostgreSQL's SQL parser and PHP's are Bison grammars, OCaml programmers use Menhir — and for small domain-specific languages where the grammar changes often. A generated LR parser makes it easy to check that a grammar is unambiguous and to change it safely. Its weaknesses are error messages (a table entry says only "error in state 7") and the difficulty of handling the context-sensitive corners of real languages. That is why the big C, C++, Go, Rust and JavaScript compilers use hand-written recursive descent ([[compilers/top-down-parsing]]), and why CPython replaced its LL(1) parser generator by a PEG parser (with memoised backtracking) in Python 3.9 (2020). For grammars that are ambiguous or need unbounded look-ahead, **GLR** parsing (Tomita, 1985; Bison's `%glr-parser`) runs several LR stacks in parallel whenever a conflict is met, and **Earley** parsing handles every context-free grammar in cubic time (linear for most LR grammars).

::: history
Donald Knuth introduced LR($k$) parsing in "On the translation of languages from left to right" (*Information and Control*, 1965), proving that LR($k$) grammars are exactly those parsable deterministically bottom-up with $k$ symbols of look-ahead, and that the viable prefixes form a regular language. His canonical tables were too large for the machines of the time. Frank DeRemer's MIT thesis "Practical translators for LR($k$) languages" (1969) introduced LALR, and his paper "Simple LR($k$) grammars" (*Communications of the ACM*, 1971) introduced SLR; DeRemer and Thomas Pennello published the efficient algorithm for computing LALR look-aheads in 1982. Stephen C. Johnson's Yacc ("Yet Another Compiler-Compiler", Bell Labs, 1975) made LALR parser generation part of every Unix system, with precedence declarations for ambiguous grammars; GNU Bison (from 1985, Robert Corbett, later Richard Stallman and others) is its free successor. Masaru Tomita's GLR (1985) and Joel Denny and Brian Malloy's IELR(1) (2010) extended the range of LR methods.
:::

## Where this leads

The parser's real job is not to accept or reject but to build a tree for the rest of the compiler. In an LR parser, each reduction is the natural moment to build the tree node for the production just recognised — Yacc and Bison attach an action to each production for exactly this purpose. [[compilers/semantic-analysis]] defines the abstract syntax tree for Mini, builds it with a recursive-descent parser, and checks it for scope and type errors.

::: summary
- A bottom-up parser runs a rightmost derivation backwards by **shifting** tokens and **reducing** handles ([[#def-handle]]); its stack always holds a viable prefix.
- **LR(0) items** ([[#def-item]]) and the closure/goto construction ([[#alg-lr0]]) give a DFA over grammar symbols that recognises viable prefixes and tells, for each, which items are valid ([[#thm-viable]], Knuth).
- An LR table decides reductions by look-ahead sets: all terminals (LR(0)), **FOLLOW** sets (SLR), per-item look-aheads (canonical **LR(1)**), or LR(1) look-aheads merged over equal cores (**LALR(1)**). Conflict-free tables give linear-time parsers that output the reversed rightmost derivation ([[#thm-lr-correct]]).
- LR(0) ⊂ SLR(1) ⊂ LALR(1) ⊂ LR(1), all strict: the l-value grammar is LALR(1) but not SLR, and [[#ex-not-lalr]] is LR(1) but not LALR(1). LALR merging adds only reduce/reduce conflicts ([[#thm-lalr-merge]]).
- LALR has the LR(0) automaton's states (12 for expressions, against 22 for LR(1)) and is the default of Yacc and Bison.
- Ambiguous expression grammars are made deterministic by **precedence and associativity** declarations; default resolutions (shift, first production) handle the dangling `else`. Always check what a resolution does.
:::

## Exercises

::: exercise Counting items {level=1 check="20"}
How many LR(0) items does the augmented expression grammar ($S' \to E$, $E \to E+T \mid T$, $T \to T*F \mid F$, $F \to (E) \mid \mathrm{id}$) have? (Enter the number.)
::: solution
A production with $k$ symbols on the right has $k + 1$ items: $S' \to E$: 2; $E \to E + T$: 4; $E \to T$: 2; $T \to T * F$: 4; $T \to F$: 2; $F \to (E)$: 4; $F \to \mathrm{id}$: 2. Total $20$. The 12 states of the LR(0) automaton are subsets of these 20 items.
:::
:::

::: exercise Counting reductions {level=1 check="6"}
How many reductions does the SLR parser for the expression grammar make on the input `( id )`? (Enter the number; do not count the final accept.)
::: solution
`id` is reduced to $F$, $T$ and $E$ (three reductions: $F \to \mathrm{id}$, $T \to F$, $E \to T$); after shifting `)`, the parser reduces $F \to (E)$, then $T \to F$ and $E \to T$. That is $6$ reductions, one for each interior node of the parse tree other than $S'$.
:::
:::

::: exercise Finding handles {level=1}
For the right-sentential forms (a) $E + T * \mathrm{id}$ and (b) $T * (E)$ of the expression grammar, give the handle, and the form that results from reducing it.
::: solution
(a) The handle is $F \to \mathrm{id}$ at the last position; reducing gives $E + T * F$. (Not $E \to E + T$: reducing $E + T$ to $E$ would give $E * \mathrm{id}$, which is not a right-sentential form, since `*` never follows $E$.) Next the handle would be $T \to T * F$, giving $E + T$. (b) The handle is $F \to (E)$; reducing gives $T * F$, whose handle is $T \to T * F$.
:::
:::

::: exercise SLR table entries {level=2}
For the grammar $S \to A\,a \mid b\,A\,c \mid d\,c \mid b\,d\,a$, $A \to d$ (a standard example), build the LR(0) automaton far enough to find the state reached on $b\,d$, and decide whether the grammar is SLR(1) and whether it is LALR(1).
::: solution
On $b$ from the start we reach $\set{S \to b \cdot A c,\ S \to b \cdot d a,\ A \to \cdot d}$; on $d$ from there, $\set{S \to b d \cdot a,\ A \to d \cdot}$. SLR reduces $A \to d$ on $\mathrm{FOLLOW}(A) = \set{a, c}$ (from $S \to A a$ and $S \to b A c$), and the other item shifts on $a$: a shift/reduce conflict, so the grammar is not SLR(1). The state reached on $d$ from the start, $\set{S \to d \cdot c,\ A \to d\cdot}$, has a second SLR conflict, on $c$. With LR(1) look-aheads, after $b$ the item $A \to \cdot d$ has look-ahead $c$ (from $S \to b \cdot A c$), so in the state on $b\,d$ the reduction is only on $c$, and in the state on $d$ it is only on $a$ (from $S \to \cdot A a$): no conflicts. The two states have different cores, so LALR merging changes nothing, and the grammar is LALR(1). `lr0_slr` reports the two conflicts `(4, 'c', …)` and `(7, 'a', …)`; `lr1(…, lalr=True)` reports none.
:::
:::

::: exercise The dangling else, bottom-up {level=2}
Bison reports one shift/reduce conflict for `s : IF B THEN s | IF B THEN s ELSE s | OTHER ;`. Identify the state and the items involved, say which resolution Bison's default chooses, and show that it attaches each `else` to the nearest `if`.
::: solution
The conflict is in the state reached after `IF B THEN s`, which contains $s \to \mathrm{IF}\ B\ \mathrm{THEN}\ s\,\cdot$ (complete: reduce, with $\mathrm{ELSE}$ in its look-ahead, because an `if` without `else` may be nested inside an outer `if` that has one) and $s \to \mathrm{IF}\ B\ \mathrm{THEN}\ s \cdot \mathrm{ELSE}\ s$ (shift `ELSE`). Bison's default for an unresolved shift/reduce conflict is to shift. On `if b then if b then other else other`, when the parser has `IF B THEN IF B THEN s` on the stack and sees `ELSE`, shifting continues the *inner* statement, so the `else` becomes part of the inner `if`; the inner `if-then-else` is then reduced to $s$, and only after that the outer `if-then` is reduced. That is the nearest-`if` rule. The conflict can be silenced, without changing the behaviour, by `%precedence THEN` and `%precedence ELSE` (ELSE binding tighter) or Bison's `%expect 1`.
:::
:::

::: exercise Precedence by hand {level=2}
The ambiguous grammar $E \to E + E \mid E * E \mid \mathrm{id}$ has four shift/reduce conflicts, in states 5 (stack $E * E$) and 6 (stack $E + E$), each on `+` and `*`. For each of the four, say what `%left '+'` followed by `%left '*'` chooses and why; then say what changes if the declarations are `%right '+'` and `%left '*'`, and what tree results for `a + b + c`.
::: solution
State 5, rule $E \to E * E$ (precedence of `*`, 2). On `*`: equal precedence, left-associative: reduce, so `a * b * c` is `(a*b)*c`. On `+`: rule 2 > token 1: reduce, so `a * b + c` is `(a*b) + c`. State 6, rule $E \to E + E$ (precedence 1). On `*`: rule 1 < token 2: shift, so `a + b * c` is `a + (b*c)`. On `+`: equal, left: reduce, `(a+b)+c`. With `%right '+'`, the only change is state 6 on `+`: equal precedence and right associativity give shift, so `a + b + c` parses as `a + (b + c)`. The language accepted is unchanged; only the trees differ.
:::
:::

::: exercise LR but not LL {level=3}
(a) Show that the grammar $S \to A \mid B$, $A \to a\,A \mid c$, $B \to a\,B \mid d$ is LR(0) but not LL($k$) for any $k$. (b) Explain in one paragraph why the bottom-up parser can wait while the top-down parser cannot.
::: solution
(a) The language is $a^*c \cup a^*d$. *Not LL($k$):* to expand $S$ the top-down parser must choose between $S \to A$ and $S \to B$ at the very first token, but for any $k$ the inputs $a^k c$ and $a^k d$ have the same first $k$ tokens and need different choices (`ll1_table` reports the conflict at $M[S, a]$ for $k = 1$). *LR(0):* the LR(0) automaton never has to decide early. From the start state, on $a$ it moves to a state containing both $A \to a \cdot A$ and $B \to a \cdot B$ (with their closures $A \to \cdot aA \mid \cdot c$, $B \to \cdot aB \mid \cdot d$), and stays there on further $a$'s; on $c$ it reaches $A \to c\cdot$, on $d$ it reaches $B \to d\cdot$. Every state with a complete item contains nothing else, so there are no conflicts: `lr0_slr(…, slr=False)` finds 9 states and no conflicts. After the $c$ or $d$, the parser reduces $A \to aA$ (or $B \to aB$) repeatedly, and finally $S \to A$ (or $S \to B$).

(b) A top-down parser commits to a production when it *starts* the corresponding subtree, so it must predict the whole shape from a bounded look-ahead. A bottom-up parser commits to a production when the subtree is *finished*; until then it keeps all compatible items alive in one state of the LR automaton (here, $A \to a\cdot A$ and $B \to a\cdot B$ together), which is a finite summary of unboundedly much left context. This is why LR($k$) is strictly more powerful than LL($k$).
:::
:::

::: exercise The viable-prefix property {level=3}
Prove that a canonical LR(1) parser never shifts a token that cannot continue the input read so far: if it shifts the $i$-th token, then the first $i$ tokens are a prefix of some sentence of $L(G)$. Show that an SLR or LALR parser has the same property for shifts, but may make some extra *reductions* before detecting an error; give an example with the expression grammar.
::: solution
*Canonical LR(1).* Suppose the stack holds viable prefix $\gamma$ (with states valid for it) and the parser shifts $a$. The shift entry exists because some item $[A \to \alpha \cdot a\beta,\ b]$ is in the state, hence valid for $\gamma$: there is a rightmost derivation $S' \Rightarrow^* \delta A w \Rightarrow \delta\alpha a\beta w$ with $\gamma = \delta\alpha$. Every symbol derives a terminal string, so $\gamma a \beta w$ derives some sentence $x a y$ where $\gamma \Rightarrow^* x$; and by the soundness invariant of [[#thm-lr-correct]], $\gamma$ derives exactly the tokens read so far. So the tokens read, followed by $a$, are a prefix of a sentence. For reductions, LR(1) reduces on $a$ only if a complete item with look-ahead $a$ is valid, which again implies that $a$ can follow; so a canonical LR(1) parser detects an error at the first token where the input stops being a prefix of a sentence, before any reduction.

*SLR/LALR.* Shift entries depend only on cores, which are the LR(0) valid items, so the same argument applies to shifts. But their reduce look-aheads are supersets of the LR(1) look-aheads, so they may reduce on a token that cannot follow in this context, and discover the error only in the state reached after the reductions. Example: the SLR parser on `( id $` (a missing `)`): after shifting `(` and `id`, it reduces $F \to \mathrm{id}$, $T \to F$ and $E \to T$ on $\$$ (which is in the FOLLOW sets), reaching state 6, where $\mathrm{ACTION}[6, \$]$ is an error (`unexpected $ in state 6`). No erroneous token has been shifted, but three useless reductions were made — harmless, but it affects error messages, since the parser reports the error in state 6 rather than right after `id`. The canonical LR(1) parser built by `lr1` stops immediately after shifting `id`, with `unexpected $ in state 10`: its state for `id` inside parentheses has look-aheads `)`, `+`, `*` only.
:::
:::
