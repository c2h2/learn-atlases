一个五人团队被问到一套新的订票系统要开发多久。负责人把七个主要任务的最佳猜测加在一起，回答「十七个工作日」。六周之后系统交付了。没有人偷懒，也没有哪一项估计错得离谱：数据库比预期多花了一点时间，测试发现了需要再做一轮的问题，而两个本可以并行的任务都在等同一个人。每一种效应都朝同一个方向推。我们将在后面证明，由最可能值制定的计划几乎总是会被延误的计划。

程序设计课程教的是如何写出正确的程序。**软件工程**关心的是：当一个程序要由许多人、历时数月乃至数年来完成，要服务于依赖它并且还会不断要求修改它的用户时，情况会发生哪些变化——必须有人决定造什么、如何分工、预测何时完成、察觉它何时出了毛病，并在交付之后让它持续运转。这个术语是带着故意的挑衅意味选定的：它取自 1968 年一次北约会议的名称，当时 IBM 的 OS/360 等大型项目纷纷延误、超支且不可靠，与会者谈到了「软件危机」。本章研究这门学科的**过程**一侧：组织工作的生命周期模型、计划驱动与敏捷开发，以及让计划少靠猜测的定量工具——关键路径、三点估计、模拟、排队论与风险暴露。贯穿全章，我们会区分关于模型能*证明*什么、关于真实项目已经*观察到*什么，以及哪些只是坊间传言。

## 软件过程

每个软件项目，无论多么非正式，都在做同样几种工作。有人弄清想要什么，有人设计并编写代码，有人检查它做了想要它做的事，而随着需要的变化，成果还要被修改。萨默维尔（Sommerville）的教材列出了这四项活动，本课程的其余部分将逐一讨论它们。

::: definition 软件过程 {#def-process}
**软件过程**是通向软件系统的生产与演化的一组结构化的活动。基本活动是**规格说明**（确定系统应当做什么以及对其的限制）、**设计与实现**（确定怎么做，并把系统造出来）、**确认**（检查系统是否做了客户想要的事，validation）与**演化**（随需求和环境的变化而修改系统）。**过程模型**（**生命周期模型**）则是对这些活动如何排序、重叠与重复、以及各自产出什么的抽象描述。
:::

这些活动不是必须按次序各发生一次的阶段；它们是工作的种类。下面的模型恰恰在于它们如何在时间上被安排。值得从一开始就区分两大流派。

::: definition 计划驱动与增量开发 {#def-plan-driven}
在**计划驱动**（plan-driven）开发中，所有过程活动都预先规划，进度以计划为基准来衡量；每个活动产出文档，作为下一个活动的输入。在**增量**（incremental，又称**迭代** iterative）开发中，系统被构造成一系列版本（**增量**），每个增量在上一个的基础上增加功能，且每个增量都在一个短周期内完成规格说明、构造与确认，因而后面增量的计划可以根据前面增量的情况调整。
:::

两个流派没有谁「对」。一个为飞机做飞行控制软件的团队——它必须在首飞之前依据一份固定的规格说明通过认证——需要计划、文档与可追踪性，而一个为初创公司做网上商店的团队则不需要。选择过程是一个关于风险的工程决策，就像选择数据结构是一个关于代价的决策一样。

### 顺序模型及其误读

最广为人知的计划驱动模型把这些活动排成一串阶段——需求、设计、实现、测试、运行——每个阶段在前一个结束之后才开始，像水流下阶梯。它被普遍称为**瀑布模型**（waterfall model），通常归功于温斯顿·罗伊斯（Winston Royce）1970 年的论文《大型软件系统的管理》。这一归功只对了一半。罗伊斯确实画了那张顺序图，但论文紧接着的下一句话就把那种实现方式称为「有风险的」，说它「招致失败」，因为测试——第一次看到系统真实行为的时刻——被放在了最后。论文的其余部分加上了反馈回路、一个先行设计阶段、一个先造出来再扔掉的中试版本（「要做两遍」），以及贯穿始终的客户参与。文中并没有出现「瀑布」这个词。

那么，顺序模型为何成了标准（它正是美国国防部标准 DOD-STD-2167（1985 年）的基础）？因为它便于管理：每个阶段以一份可以签字认可的文档告终，进度就表现为已完成阶段的多少。它的弱点正是罗伊斯指出的那个：需求中的一个误解要直到用户看到运行中的系统时才会被发现，而到那时，一切都已建立在它之上了。

**V 模型**在许多安全攸关的行业中使用，它保持这一顺序，但把每个规格说明阶段与检验它的测试阶段配成对：需求对验收测试，体系结构对系统测试，详细设计对集成测试，代码对单元测试。它的价值在于测试是在写规格说明时就被*规划*好的；这些测试级别我们将在 [[software-engineering/testing]] 中遇到。

### 迭代式、风险驱动的开发

巴里·博姆（Barry Boehm）的**螺旋模型**（1988 年）把风险作为组织原则。螺旋的每一圈确定目标，识别并化解最大的风险（通常是构造一个原型），开发并验证下一层次的产品，然后规划下一圈。一个主要风险是用户界面未知的团队，第一圈花在界面原型上；一个主要风险是性能的团队，则花在基准测试上。螺旋与其说是一个固定的过程，不如说是一条选择过程的规则：先做那个最能降低失败风险的事。

::: example 选择过程 {#ex-choose-process}
对每个项目，说明你会倾向于计划驱动还是增量过程，并说明理由。(a) 一套铁路信号联锁软件，要由国家安全管理机构认证。(b) 一家业务模式仍在试错的新食品配送公司的手机应用。(c) 用一套必须给出完全相同结果的新系统，替换某银行使用了 30 年的批处理账务系统。
::: solution
(a) **计划驱动**，或至少偏重计划。认证要求一份完整、经批准的规格说明、成文的设计，以及每条需求都被测试过的证据（我们也会在 [[software-engineering/verification]] 中遇到这类标准）。需求是稳定的——列车的物理规律不会变——所以计划的主要代价（失去灵活性）很小。

(b) **增量式。** 最大的风险是造出没有人想要的东西。短增量能把可工作的软件迅速放到用户面前，下一增量的计划可以根据他们的反应调整。过重的先行规格说明只会把错误的产品详细地规定下来。

(c) **混合。** 所要求的*行为*是固定且可测试的（旧系统就是一个预言机：同一批输入分别跑两套系统再比较结果，见 [[programming-1/testing-debugging#ex-random-test]]），这适合周密的计划；但*风险*藏在旧代码中许多没有成文的规则里，最好用一次迁移一部分、逐部分比较的增量方式把它们找出来。大多数真实项目都以这种方式混合两大流派。
:::
:::

## 敏捷开发

到 20 世纪 90 年代末，许多实践者得出结论：重量级的计划驱动过程恰恰在最常见的商业项目上失败了——那些在系统构建期间需求不断变化的项目。若干「轻量」方法相继出现——Scrum（肯·施瓦伯（Ken Schwaber）与杰夫·萨瑟兰（Jeff Sutherland）于 1995 年提出）、极限编程（Kent Beck，《解析极限编程》（*Extreme Programming Explained*），1999）、DSDM、Crystal、特征驱动开发——2001 年 2 月，其中十七位作者汇聚在犹他州的雪鸟（Snowbird），写下了**《敏捷软件开发宣言》**。它陈述了四项价值：

> 个体与互动高于过程与工具；可工作的软件高于面面俱到的文档；客户协作高于合同谈判；响应变化高于遵循计划。

并补充说「右栏各项也有价值，但我们更看重左栏各项」。其后跟着十二条原则，其中包括频繁地交付可工作的软件——「从几周到几个月」——欢迎变化的需求，以及主要用可工作的软件来衡量进度。宣言是一份价值观的声明，而不是一个过程；团队实际遵循的是那些方法。

**Scrum** 是使用最广的方法，其定义见《Scrum 指南》（*Scrum Guide*，施瓦伯与萨瑟兰；现行版本出自 2020 年）。工作按固定长度的**冲刺**（sprint）完成，不超过一个月。**产品负责人**（Product Owner）对期望特性组成的**产品待办列表**（Product Backlog）排序；**开发人员**（Developers）在**冲刺计划会**上选出本冲刺能够完成的工作，形成一个带冲刺目标的**冲刺待办列表**（Sprint Backlog）；他们在 15 分钟的**每日 Scrum** 中协调；冲刺结束时，在**冲刺评审会**上展示一个符合团队**完成的定义**（Definition of Done）的可用**增量**，并在**冲刺回顾会**上反思自己的工作方式。**Scrum 主管**（Scrum Master）帮助团队运用这一方法。Scrum 对如何写代码只字未提。**极限编程**（XP）则不然：它规定了若干工程实践，如测试先行开发（[[software-engineering/testing]]）、结对编程、持续集成（[[software-engineering/version-control]]）、重构（[[software-engineering/refactoring-maintenance]]）、小规模发布以及代码的共同所有权。**看板**（Kanban）由戴维·安德森（David Anderson）等人在 21 世纪头十年的末尾从精益制造引入软件领域，它不使用固定迭代：工作项在一块分栏的看板（待办、进行中、评审、完成）上流动，每一栏都有**在制品（WIP）限制**。

为什么限制进行中的工作会让一个团队更快？排队论的一个结果回答了这个问题。

::: proposition 利特尔法则 {#prop-little}
考察一个工作项进出其中的系统，在一个平稳的长时段内观察（系统内的工作项数量不会无界增长）。令 $\lambda$ 为平均**吞吐量**（单位时间完成的工作项数），$L$ 为系统内平均工作项数（**在制品**），$W$ 为每个工作项在系统中停留的平均时间（**周期时间**或**前置时间**）。则
$$
L = \lambda W .
$$ {#eq-little}
:::

::: proof
我们给出在一个以空系统开始和结束的有限观察窗口 $[0, T]$ 上的论证，它抓住了基本思想；约翰·利特尔（John Little）1961 年的证明一般地处理了 $T \to \infty$ 的极限。设 $N$ 个工作项通过系统，第 $i$ 项在系统内停留 $w_i$ 时间。设 $n(t)$ 为时刻 $t$ 系统内的工作项数。用两种方式计算面积 $A = \int_0^T n(t)\,dt$。每个工作项在恰好 $w_i$ 个时间单位内对 $n(t)$ 贡献 $1$，所以 $A = \sum_{i=1}^{N} w_i$。于是
$$
L = \frac{A}{T} = \frac{N}{T}\cdot\frac{1}{N}\sum_{i=1}^{N} w_i = \lambda W .
$$
这一恒等式既不需要关于到达或服务时间分布的任何假设，也不需要关于服务项目次序的任何假设。
:::

利特尔法则把一句管理口号变成了算术。若一个团队平均每周完成 $\lambda = 3$ 个工作项，进行中的有 $L = 12$ 项，则一个工作项从开始到完成平均要 $W = 12/3 = 4$ 周。不加快完成而只是多开工并不会提高 $\lambda$；它增加的是 $L$，从而由 [[#eq-little]]，增加每个工作项所需的时间。同样的吞吐量下把在制品限制为 $6$，平均周期时间就减半为 $2$ 周——每个工作项的反馈来得快一倍，优先级改变时被搁置的工作也更少。（它并没有让团队每周完成*更多*的工作；它让每一件工作*更早*完成。）

::: warning 敏捷不是「不做计划」也不是「不写文档」
宣言认为可工作的软件*比*面面俱到的文档更有价值；它并没有说文档没有价值。敏捷团队在三个层次上不断计划——发布、迭代与当天——并在学到新东西时重新计划。他们避免的是对尚不可知之事做详细计划。同样，满口 Scrum 的词汇（冲刺、每日站会、故事点）却保持固定范围、固定日期、不接收用户反馈，这不是敏捷开发；那只是一个多了些会议的顺序过程。判断一个过程要看它做了什么——可工作的软件多久到达用户手中、团队从中学习得多快——而不是看它的仪式叫什么名字。
:::

::: quiz
一个看板团队平均每周完成 5 个工作项。看板上显示有 20 项进行中，而且这个数字几个月来大致不变。一个工作项在看板上平均停留多久？
- [ ] 1 周
- [x] 4 周
- [ ] 5 周
- [ ] 100 周
::: solution
系统平稳（WIP 大致不变），利特尔法则适用：$W = L/\lambda = 20/5 = 4$ 周。注意，不需要知道工作项的大小与种类的任何情况——只需要长期平均值。
:::
:::

## 估计工作量与进度

每个过程都必须在开工之前回答「要多久，要花多少钱？」。需要估计来决定一个项目是否值得启动、为其配备人手、以及向客户作出承诺。出了名的差，其部分原因我们可以解释。

### 任务网络的调度

假设工作已划分成带有估计工期的任务，并带有**先后约束**：在 API 设计好之前不能构造它所服务的用户界面。任务与约束构成一个有向无环图。

::: definition 任务网络与关键路径 {#def-critical-path}
**任务网络**是一个有向无环图，其顶点是工期 $d(t) \ge 0$ 的任务 $t$，其边 $u \to t$ 表示 $t$ 要等 $u$ 完成之后才能开始。一个**调度**给每个任务指派开始时间 $s(t) \ge 0$，对每条边 $u \to t$ 满足 $s(t) \ge s(u) + d(u)$；调度的**长度**是 $\max_t \bigl(s(t) + d(t)\bigr)$。**路径** $t_1 \to \dots \to t_k$ 的**长度**是 $\sum_i d(t_i)$，**关键路径**是长度最大的路径。
:::

::: theorem 关键路径决定最短调度 {#thm-critical-path}
假设人手无限，凡前置任务已完成的任务都能并行。则任务网络的最短调度，其长度等于关键路径的长度。**最早开工调度**
$$
s(t) = \max_{u \to t} \bigl(s(u) + d(u)\bigr), \qquad s(t) = 0 \text{ 若 } t \text{ 没有前置任务},
$$ {#eq-earliest-start}
按拓扑序计算，即可达到这一长度。
:::

::: proof
**每个调度的长度都不小于任一路径。** 设 $t_1 \to \dots \to t_k$ 是一条路径。约束给出 $s(t_{i+1}) \ge s(t_i) + d(t_i)$，且 $s(t_1) \ge 0$，故由归纳法 $s(t_k) \ge \sum_{i<k} d(t_i)$，而调度的长度不小于 $s(t_k) + d(t_k) \ge \sum_{i \le k} d(t_i)$。

**最早开工调度达到该下界。** 因为图无环，它有拓扑序（[[algorithms/graph-search]]），按该顺序处理任务，计算 $s(t)$ 时 [[#eq-earliest-start]] 中的每个 $s(u)$ 都已已知；该调度按构造满足每条约束。沿拓扑序归纳，$s(t)$ 等于*恰好在 $t$ 之前*结束的最长路径的长度：对没有前置任务的任务成立（$0$），且若对每个前置任务 $u$ 成立，则 $s(t) = \max_u (s(u) + d(u))$ 就是进入 $t$ 的最长路径。于是 $s(t) + d(t)$ 是以 $t$ 结尾的最长路径，整个调度的长度就是全局最长路径。
:::

一个任务的**松弛时间**（slack）是它在不延长工期的前提下可以推迟开工的时间：其*最晚*开始时间（从末尾反向计算一遍得到）减去最早开始时间。关键路径上的任务松弛为零。这就是**关键路径法**（CPM），1957–59 年与 PERT（见下文）一道在杜邦（DuPont）与雷明顿·兰德（Remington Rand）公司为大型工程项目发展起来。它就是 [[algorithms/shortest-paths]] 中的 DAG 最长路径计算，只是工期标在顶点上。

::: example 订票系统 {#ex-cpm}
导言中的订票系统有七个任务（工期以天计）：`spec` 3；`db` 5 和 `api` 4，都在 `spec` 之后；`ui` 6 在 `api` 之后；`reports` 2 在 `db` 之后；`test` 3 在 `db`、`ui`、`reports` 之后；`deploy` 1 在 `test` 之后。求最短调度、每个任务的松弛时间与关键路径。
::: solution
按拓扑序正向一遍得到最早开始时间：`spec` 0、`db` 3、`api` 3、`ui` $3 + 4 = 7$、`reports` $3 + 5 = 8$、`test` $\max(3 + 5, 7 + 6, 8 + 2) = 13$、`deploy` 16，于是工期为 $16 + 1 = 17$ 天。下面的程序把正向、反向两遍都做了：

```python
from graphlib import TopologicalSorter

def critical_path(tasks):
    """tasks: 任务名 -> (工期, 前置任务名集合)。
    返回（项目长度、最早开始时间、松弛、零松弛任务）。"""
    order = list(TopologicalSorter({t: deps for t, (_, deps) in tasks.items()}).static_order())
    es = {}                                   # 每个任务的最早开始时间
    for t in order:                           # 正向一遍，前置任务在前
        dur, deps = tasks[t]
        es[t] = max((es[d] + tasks[d][0] for d in deps), default=0)
    length = max(es[t] + tasks[t][0] for t in tasks)
    succ = {t: [u for u in tasks if t in tasks[u][1]] for t in tasks}
    ls = {}                                   # 仍保持 `length` 的最晚开始时间
    for t in reversed(order):                 # 反向一遍，后继任务在前
        ls[t] = min((ls[u] for u in succ[t]), default=length) - tasks[t][0]
    slack = {t: ls[t] - es[t] for t in tasks}
    path = [t for t in order if slack[t] == 0]
    return length, es, slack, path

tasks = {
    "spec":    (3, set()),
    "db":      (5, {"spec"}),
    "api":     (4, {"spec"}),
    "ui":      (6, {"api"}),
    "reports": (2, {"db"}),
    "test":    (3, {"db", "ui", "reports"}),
    "deploy":  (1, {"test"}),
}
if __name__ == "__main__":
    length, es, slack, path = critical_path(tasks)
    print("length:", length)
    for t in tasks:
        print(f"{t:8} start {es[t]:2}  slack {slack[t]}")
    print("critical:", " -> ".join(path))
```

```console
$ python3 cpm.py

spec     start  0  slack 0
db       start  3  slack 3
api      start  3  slack 0
ui       start  7  slack 0
reports  start  8  slack 3
test     start 13  slack 0
deploy   start 16  slack 0
critical: spec -> api -> ui -> test -> deploy
```

关键路径是 `spec → api → ui → test → deploy`（$3 + 4 + 6 + 3 + 1 = 17$）。数据库和报表可以拖延三天而不延误任何事；`ui` 拖一天，交付就晚一天。想让项目更早完成的经理必须缩短关键路径——比如把 `ui` 拆开——因为在 `db` 上增加投入毫无作用。（这里零松弛的任务构成一条路径；一般情况下它们可以构成多条关键路径，而最后一行按拓扑序列出了所有关键路径。）
:::
:::

### 三点估计与计划为何总是乐观

单个数字掩盖了估计中的不确定性。**计划评审技术**（PERT）1958 年为美国海军的北极星导弹计划而开发，它要求给出三个估计：乐观工期 $a$、最可能工期 $m$ 与悲观工期 $b$，并用
$$
\mu \approx \frac{a + 4m + b}{6}, \qquad \sigma \approx \frac{b - a}{6}.
$$ {#eq-pert}
来近似工期的均值与标准差。这些公式是一种约定（它们来自特定参数的贝塔分布），不是自然规律。它们的重要特征为一切合理的模型所共有：软件任务是**右偏的**。一个任务可能比预期稍早完成，却可能拖得久得多——悲观一侧的尾部很长——所以均值落在最可能值之上。对用户界面任务，若 $(a, m, b) = (4, 6, 12)$，则 $\mu \approx (4 + 24 + 12)/6 \approx 6.7$ 天，而不是 6。

还有第二个更微妙的乐观来源，而且它可以被证明。

::: proposition 由最可能值制定的计划是乐观的 {#prop-merge-bias}
设任务工期 $D(t)$ 是随机变量，项目长度为 $\Lambda = \max_P \Lambda_P$，其中 $\Lambda_P = \sum_{t \in P} D(t)$ 是路径 $P$ 的长度，最大值取遍所有路径。则
$$
\E[\Lambda] \;\ge\; \max_P \E[\Lambda_P] \;=\; \max_P \sum_{t \in P} \E[D(t)] .
$$
此外，若每个 $\E[D(t)] \ge m(t)$，其中 $m(t)$ 为最可能值（右偏），则 $\E[\Lambda]$ 不小于按最可能值算出的关键路径长度。
:::

::: proof
对每个结果与每条路径 $P$，$\Lambda \ge \Lambda_P$。两边取期望，对每个 $P$ 有 $\E[\Lambda] \ge \E[\Lambda_P]$，于是 $\E[\Lambda] \ge \max_P \E[\Lambda_P]$；又由期望的线性性 $\E[\Lambda_P] = \sum_{t\in P}\E[D(t)]$（不需要独立性）。在 $\E[D(t)] \ge m(t)$ 之下，每个 $\E[\Lambda_P]$ 都不小于按最可能工期计算的路径长度，对路径取最大之后亦然。
:::

不等式 $\E[\max] \ge \max \E$ 称为**合并偏差**（merge bias）：凡是路径汇合之处（我们的网络里的 `test`），任一条进入路径上的延误都会拖慢汇合，因此可能赶上关键路径的准关键路径会加大期望长度。它与右偏一起解释了为什么 17 天的最可能计划是一个很差的赌注。模拟能显示它有多差。

::: example 模拟进度 {#ex-monte-carlo}
给 [[#ex-cpm]] 的每个任务配上以下三点估计构成的三角分布，模拟 20,000 个项目，估计在 17 天计划内完成的概率。
::: solution
```python
import random
from cpm import critical_path            # 上面定义的函数，存为 cpm.py

# （乐观、最可能、悲观）工期（天），以及前置任务
est = {
    "spec":    ((2, 3, 6),  set()),
    "db":      ((3, 5, 10), {"spec"}),
    "api":     ((3, 4, 8),  {"spec"}),
    "ui":      ((4, 6, 12), {"api"}),
    "reports": ((1, 2, 4),  {"db"}),
    "test":    ((2, 3, 8),  {"db", "ui", "reports"}),
    "deploy":  ((1, 1, 2),  {"test"}),
}
rng = random.Random(1968)
runs = []
for _ in range(20_000):
    sample = {t: (rng.triangular(lo, hi, mode), deps)   # 注意参数顺序
              for t, ((lo, mode, hi), deps) in est.items()}
    runs.append(critical_path(sample)[0])
runs.sort()
n = len(runs)
print(f"P(length <= 17) = {sum(r <= 17 for r in runs) / n:.3f}")
print(f"mean = {sum(runs) / n:.1f}, median = {runs[n // 2]:.1f}, "
      f"85th percentile = {runs[int(0.85 * n)]:.1f}")
```

```console
$ python3 montecarlo.py
P(length <= 17) = 0.019
mean = 21.7, median = 21.6, 85th percentile = 24.3
```

在此模型下，17 天的计划约有 **2%** 的概率被满足。三角分布的均值为 $(a + m + b)/3$；沿关键路径把这些均值加起来得到 $21.7$，与模拟的均值一致，所以这里几乎全是右偏在起作用，合并偏差贡献很小（`db` 路径很少成为关键路径）。按第 85 百分位数（约 24 天）作承诺，大约六个项目里能兑现五个。数字的可靠性取决于三点估计的可靠性，但结论的*方向*不依赖它们：由 [[#prop-merge-bias]]，任何右偏模型的期望长度都高于最可能计划。
:::
:::

模拟还暴露了一个 PERT 和上面命题的用法共同隐含的假设：任务工期相互独立。现实中它们是正相关的——如果团队低估了数据库，多半也出于同样的原因低估了 API。误差独立时，$k$ 个同类任务之和的标准差按 $\sqrt{k}$ 增长，因此项目变大时相对不确定性缩小；误差相关时它并不缩小，一个大计划按比例的不确定性与一个小计划的相当。

### 工作量估计

工期来自对**工作量**（人·日）的估计。主要方法有**专家判断**（常常是结构化的，如宽带德尔菲法或**计划扑克**：估计者同时亮出自己的估计，并讨论离群值）、与已完成项目的**类比**，以及拟合历史数据的**参数化模型**。最著名的参数化模型是博姆的 **COCOMO**（《软件工程经济学》（*Software Engineering Economics*），1981），用 TRW 公司的 63 个项目标定。对「有机型」项目（小团队、熟悉的问题），其基本形式是
$$
E = 2.4\,S^{1.05} \text{ 人月}, \qquad T = 2.5\,E^{0.38} \text{ 月},
$$
其中 $S$ 为以千行交付源代码（KLOC）计的规模。对 $S = 32$，$E \approx 91$ 人月，$T \approx 13.9$ 月，意味着平均约 $6.6$ 人的团队。指数 $1.05 > 1$ 编码了一种**规模不经济**：规模加倍，工作量乘以 $2^{1.05} \approx 2.07$，因为更大的系统需要更多的沟通与集成。更精细的版本（中级 COCOMO、2000 年的 COCOMO II）再乘上可靠性要求、团队经验等成本驱动因子。

参数化模型有两个严重局限。它们需要在代码存在之前先知道规模，而规模本身又是一个估计；它们的常数描述的是用来拟合它们的项目——以 COCOMO 为例，是 20 世纪 70 年代某一家公司的项目——所以在其输出有意义之前必须用本地数据重新标定。它们持久的价值在于揭示出的*形状*：工作量比规模增长得更快，进度又比工作量增长得慢得多，于是给定工作量就存在一个合理的最短工期。

## 人员与风险管理

### 布鲁克斯法则

弗雷德里克·布鲁克斯（Frederick Brooks）在 20 世纪 60 年代主持了 IBM System/360 操作系统 OS/360 的开发，并把这段经验凝练成《人月神话》（*The Mythical Man-Month*，1975；20 周年版 1995）。同名文章论证：人与月只有在可以不加沟通而划分的工作中才可以互换——他举的例子是摘棉花——而软件不是这样的，并总结出**布鲁克斯法则**：「向一个已经延误的软件项目增加人手，只会让它更晚完成。」他给出了两个机制。新人必须由现有成员培训，而培训者因此少做工作；而且协调的工作量随着必须彼此沟通的人数增长。

::: proposition 沟通渠道 {#prop-channels}
在一个 $n$ 人团队中，若每一对人都可能需要协调，则沟通渠道有 $\binom{n}{2} = n(n-1)/2$ 条。
:::

::: proof
每条渠道是一个无序的两人对，这样的对有 $\binom{n}{2}$ 个：第一个人有 $n$ 种选择，第二个人有 $n - 1$ 种，再除以 $2$，因为每一对被数了两次。
:::

从 5 人增加到 10 人，人手翻倍，渠道却从 10 条增加到 45 条。一个玩具模型把这一权衡说清楚。设一个项目需要 $W$ 人月可划分的工作，且每一对人会在整个项目上增加 $c$ 人月的协调开销。$n$ 人时总工作量是 $W + c\,n(n-1)/2$，由 $n$ 人分担，于是工期是
$$
T(n) = \frac{W}{n} + \frac{c\,(n - 1)}{2}.
$$ {#eq-brooks-model}
把 $n$ 当作连续变量，$T'(n) = -W/n^2 + c/2$ 在 $n^* = \sqrt{2W/c}$ 处为零，且 $T$ 是凸的，所以这就是最小值：超过 $n^*$，每一个多余的人都会让项目*更慢*。$W = 60$、$c = 0.5$ 时，$n^* = \sqrt{240} \approx 15.5$，且 $T(15) = T(16) = 7.5$ 个月；$30$ 人时 $T = 2 + 7.25 = 9.25$ 个月。

::: widget plot
f: w/x + c*(x - 1)/2; w/x
x: 1, 40
y: 0, 30
sliders: w=10:5:200:60; c=0.1:0.05:2:0.5
labels: T(n) = W/n + c(n-1)/2; W/n \text{（无协调开销）}
caption: 项目工期 $T$（月）对团队规模 $n$ 的玩具模型 [[#eq-brooks-model]]，其中工作量为 $W$ 人月，每一对人有 $c$ 的协调开销。没有协调开销时（下方曲线），人越多总是越有利。有了它，就在 $\sqrt{2W/c}$ 附近出现一个最优值，更大的团队反而更慢。把 $c$ 调大以模拟需要更多协调的工作：最优值左移。这是对布鲁克斯论证的示意，不是经过验证的真实团队模型。
:::

布鲁克斯法则在多大程度上为真？它是一个论证，不是经过测量的定律，而且专门针对*延误了*的项目：新人在临近截止期时加入，必须学习一个已经复杂的系统。布鲁克斯本人在 1995 年版中称之为过于简单化，同时为其核心辩护。对项目动力学的模拟研究——以阿卜杜勒-哈米德与马德尼克（Abdel-Hamid and Madnick）的《软件项目动力学》（*Software Project Dynamics*，1991）为开端——发现：后期增员会增加成本，但并不总是拉长进度；这取决于何时、增员多少、剩余工作在多大程度上可以划分。有用的教训更窄也更可靠：人不能与月互换，沟通是真实的成本；组织通过让小团队在彼此的部分之间拥有定义清晰的接口来降低它——这个思想我们在 [[software-engineering/software-architecture]] 中讨论康威定律时还会再回到。

### 风险管理

博姆的螺旋模型把风险放在计划的中心，他 1991 年的文章《软件风险管理：原则与实践》（"Software risk management: principles and practices"）给出了标准的定量工具。

::: definition 风险暴露 {#def-risk-exposure}
**风险**是可能引起损失的未来事件。其**风险暴露**是
$$
\mathrm{RE} = P(\text{事件发生}) \times L, 
$$
其中 $L$ 是发生时损失的大小（以钱、天数或其他共同单位计）。**风险管理**识别风险、估计其暴露、对其排序，并规划**缓解措施**；一项缓解措施只要把暴露降低的幅度超过其成本 $C$ 就值得做（其**风险削减杠杆** $(\mathrm{RE}_{\text{前}} - \mathrm{RE}_{\text{后}})/C$ 超过 1）。
:::

::: example 风险排序 {#ex-risk}
一个项目列出三个风险。(1) 一名关键开发人员离职：概率 $0.2$，损失 30 天。(2) 第三方支付 API 更改接口：概率 $0.5$，损失 6 天。(3) 上线时性能不达标：概率 $0.3$，损失 40 天。给出排序。一个两天的负载测试原型可把 (3) 的概率降到 $0.1$；值得做吗？
::: solution
暴露：(1) $0.2 \times 30 = 6$ 天；(2) $0.5 \times 6 = 3$ 天；(3) $0.3 \times 40 = 12$ 天。排序：性能、关键人员、API。原型把风险 (3) 的暴露降到 $0.1 \times 40 = 4$ 天，花 $2$ 天成本换来 $8$ 天的削减：杠杆 $8/2 = 4 > 1$，值得——这正是螺旋模型推荐的那种早期的、降低风险的工作。（对风险 (1)，典型的缓解措施是结对编程与文档，使知识不掌握在一个人手里。）
:::
:::

概率与损失本身的估计也是判断，所以这些数字是用来给风险排序的，而不是预测结果的。它们的价值在于迫使人们在还有时间采取行动的时候，就哪些地方可能出问题展开一次明确的讨论。

### 度量交付

一个团队应当度量什么，才能知道自己的过程是否有效？近年最有影响的回答来自妮科尔·福斯格伦（Nicole Forsgren）主持的《DevOps 现状》（*State of DevOps*）系列调查，总结在《加速》（*Accelerate*，福斯格伦、汉布尔（Humble）与金（Kim），2018）一书中。他们提出了软件交付绩效的四项度量：**部署频率**（变更多久到达生产环境一次）、**变更前置时间**（从提交到在生产中运行）、**变更失败率**（引起需要补救之故障的部署所占的比例）与故障后的**服务恢复时间**（后期报告中改称「失败部署恢复时间」）。他们的头号发现是这些度量彼此相关：部署最频繁的受访者同时也有最低的失败率与最快的恢复，于是在他们的数据里，速度与稳定不是一对权衡。

这些结果是这个领域拥有的最好证据之一，而它们有明显的限度，作者们也有讨论。数据来自**调查**：自我选择的受访者对自己情况的报告，其中许多人本来就对 DevOps 感兴趣。这些构念经过了统计验证，但分析确立的是*相关性*；书中用结构模型论证预测关系——比原始相关更强，但比受控实验更弱。而且，任何被当作*目标*的度量都会招来钻空子——部署琐碎的变更会抬高部署频率，却没有交付任何东西（古德哈特定律（Goodhart's law）：一个度量一旦成为目标，就不再是好度量）。要用这类度量去看过程慢在哪里，而不是给团队排名。

::: warning 你会常听到的那些数字
软件工程里充斥着被远远超出其证据地反复引用的统计。Standish 集团的 *CHAOS* 报告（始于 1994 年）声称只有 16% 的项目取得了成功；这个数字被广泛引用，但方法与数据从未发表，且有批评（约根森（Jørgensen）与莫洛肯-厄斯特沃尔德（Moløkken-Østvold），2006；伊夫林斯（Eveleens）与费尔霍夫（Verhoef），*IEEE Software*，2010）指出，它对成功的定义——达到*初始*估计——所衡量的估计偏差不亚于它所衡量的项目失败。所谓「有些程序员的生产率高十倍」的说法，可追溯到萨克曼（Sackman）、埃里克森（Erikson）与格兰特（Grant）1968 年的一次小实验：它比较了两个任务、两种编程语言上的调试时间；它发现的差异是真实的，但「10 倍」这个数字是坊间之谈。著名的「不确定性之锥」（博姆 1981，麦康奈尔（McConnell）2006 年推广）——估计随项目推进从 $0.25\times$–$4\times$ 的范围收敛到实际值——是一个关于估计*最好能做到什么*的模型，而不是估计确实会收敛这一观察；洛朗·博萨维（Laurent Bossavit）的《软件工程的小妖精》（*The Leprechauns of Software Engineering*，2012–2015）把这些说法和类似的说法一直追溯到单薄的证据。当你遇到一个数字时，要问它在何处测量、在什么项目上、用了什么定义。
:::

关于估计，*确实*有什么是证据充分的？马格纳·约根森（Magne Jørgensen）等人对实证文献的综述（如《关于软件开发工作量专家估计研究之综述》（"A review of studies on expert estimation of software development effort"），*Journal of Systems and Software*，2004）发现：多数项目超出其工作量估计；专家估计平均不比基于模型的估计差；估计会被无关信息（如客户期望的数字）带偏（「锚定」）。实际结论是：用你自己过去项目的数据来估计，把估计表达为区间或概率，把估计与目标、承诺分开，并随着了解的加深重新估计。

::: history
北约科学委员会的软件工程会议于 1968 年 10 月 7–11 日在德国加尔米施举行，由彼得·瑙尔（Peter Naur）与布赖恩·兰德尔（Brian Randell）报告，给这个领域起了名字、带来了危机感；1969 年在罗马召开了第二次会议。温斯顿·罗伊斯（Winston Royce）1970 年的论文描述——并批评——了后来被称为瀑布的顺序生命周期。弗雷德里克·布鲁克斯（Frederick Brooks）1975 年出版了《人月神话》，来自他管理 OS/360 的经验；1995 年的 20 周年版加入了他的 1986 年文章《没有银弹》，文章论证任何单一技术都不会带来数量级的生产率提升，因为软件的根本困难在于其概念复杂性，而非表达上的偶然因素。巴里·博姆（Barry Boehm）的《软件工程经济学》（1981）引入了 COCOMO，他的螺旋模型于 1988 年发表于 *IEEE Computer*。《敏捷宣言》写于 2001 年 2 月；福斯格伦、汉布尔与金的《加速》（2018）则把基于调查的交付绩效度量带给了广大读者。

其余各章将逐一处理过程活动：规格说明在 [[software-engineering/requirements]]，设计在 [[software-engineering/software-architecture]] 与 [[software-engineering/design-principles]]，协作构建的机制在 [[software-engineering/version-control]]，确认在 [[software-engineering/testing]] 与 [[software-engineering/verification]]，演化在 [[software-engineering/refactoring-maintenance]]，以及伴随这一切而来的责任在 [[software-engineering/professional-ethics]]。估计所用的概率在[数学图谱：期望](/learn/maths/lesson.php?c=probability&l=expectation)中展开；像利特尔法则这样的排队思想将在 [[operating-systems]] 与 [[networks]] 中重现，在那里它们支配着调度与缓冲；关键路径背后的最长路径计算在 [[algorithms/shortest-paths]]。

::: summary
- **软件过程**组织四项活动——规格说明、设计与实现、确认、演化（[[#def-process]]）。计划驱动的过程预先固定计划；增量式的以短周期交付并重新计划（[[#def-plan-driven]]）。按风险选择。
- 罗伊斯 1970 年的论文提出了顺序的「瀑布」并称其有危险；**螺旋模型**先做最能降低风险的事；**敏捷**方法（Scrum、XP、看板）频繁交付可工作的软件并随之调整。
- **利特尔法则** $L = \lambda W$（[[#prop-little]]）：吞吐量固定时，在制品越少，周期时间越短。
- 最短调度等于任务网络中**关键路径**的长度（[[#thm-critical-path]]）；只有关键路径上的任务会延误交付。
- 任务工期右偏且路径会汇合，所以 $\E[\text{长度}] \ge$ 最可能计划（[[#prop-merge-bias]]）；要模拟，并按百分位数作承诺，而不是按最可能值。
- 沟通渠道按 $n(n-1)/2$ 增长（[[#prop-channels]]），这是**布鲁克斯法则**的基础——一个关于延误项目的论证，不是测出来的常数。用**暴露** $P \times L$ 给风险排序（[[#def-risk-exposure]]）。
- 实证结果（DORA 度量、估计研究）带有局限：调查、相关性、本地标定。要把大名鼎鼎的数字——CHAOS、「10 倍」、不确定性之锥——当作待核查的说法。
:::

## 习题

::: exercise 沟通渠道 {level=1 check="45"}
一个团队从 5 人增长到 10 人，其中任意一对人都可能需要协调。大团队有多少条沟通渠道？（填入数字。）
::: solution
由 [[#prop-channels]]，$10 \cdot 9/2 = 45$，而原来的团队是 $5 \cdot 4/2 = 10$：人加倍，渠道是原来的四倍半。
:::
:::

::: exercise 周期时间 {level=1 check="2.5"}
一个支持团队平均每天解决 8 张工单，而处于打开状态的工单数几个月来一直在 20 张上下。一张工单从到达至解决平均多少天？（填入天数。）
::: solution
系统平稳，利特尔法则给出 $W = L/\lambda = 20/8 = 2.5$ 天。
:::
:::

::: exercise 一次 PERT 估计 {level=1 check="7"}
一个任务的乐观、最可能、悲观工期为 3、6、15 天。它的 PERT 平均工期是多少天？（填入天数。）
::: solution
由 [[#eq-pert]]，$\mu = (3 + 4 \cdot 6 + 15)/6 = 42/6 = 7$ 天，比最可能值多一天，因为悲观一侧的尾部很长。PERT 标准差是 $(15 - 3)/6 = 2$ 天。
:::
:::

::: exercise 两个风险的排序 {level=1 check="8"}
风险 A 的概率为 $0.4$，将造成 20 天损失；风险 B 的概率为 $0.1$，将造成 60 天损失。两个风险暴露中较大的是多少天？（填入数字。）
::: solution
由 [[#def-risk-exposure]]，$\mathrm{RE}_A = 0.4 \times 20 = 8$ 天且 $\mathrm{RE}_B = 0.1 \times 60 = 6$ 天，于是 A 以暴露 $8$ 排第一。注意 B 这个更不可能发生的风险反而有更大的潜在损失；暴露是一个排序工具，一个根本经不起 60 天损失的项目仍然可能把 B 当作优先。
:::
:::

::: exercise 缩短项目 {level=2 check="14"}
在 [[#ex-cpm]] 中，团队把 `ui` 拆成两半，由不同的人并行完成，每半在 `api` 之后需要 3 天，`test` 要等两半都完成。新的最短工期是多少天？现在哪些任务是关键任务？（填入长度。）
::: solution
正向一遍：`spec` 0、`db` 3、`api` 3、两半 `ui` 都是 7、`reports` 8、`test` $\max(3 + 5,\ 7 + 3,\ 8 + 2) = 10$、`deploy` 13，项目在 $13 + 1 = \mathbf{14}$ 天结束。现在有两条路径长度为 14：`spec → api → ui-half → test → deploy`（$3 + 4 + 3 + 3 + 1$）与 `spec → db → reports → test → deploy`（$3 + 5 + 2 + 3 + 1$）。原本有三天松弛的数据库和报表现在成了关键任务。缩短一条关键路径常常把另一条提升为关键路径：此后再想缩短必须*同时*缩短两条路径，而且由 [[#prop-merge-bias]]，两条关键路径在 `test` 汇合，会使期望长度比任何单条所显示的和更糟。
:::
:::

::: exercise 中途增员 {level=2 check="4.5"}
一个延误的项目还剩 24 人月可划分的工作和 4 名开发人员。又来了两个人。第一个月里新人没有产出，每人占用一位老手一半的时间培训；此后六人全力工作。忽略其他协调开销。剩余工作还要多少个月？与不加人比较，并对剩余 4 人月重复这两个计算。（填入 24 人月情形下六人所需的月数。）
::: solution
新人不来：$24/4 = 6$ 个月。新人来：第 1 个月老手完成 $4 - 2 \times 0.5 = 3$ 人月，剩 $21$，六人再花 $21/6 = 3.5$ 个月完成；总共 $\mathbf{4.5}$ 个月，节省 1.5 个月。剩 4 人月时：不增员为 $1$ 个月；增员则第 1 个月完成 3，剩 1，需要 $1/6$ 个月，约 $1.17$ 个月——*更晚*。盈亏平衡点在 6 人月（两种做法都是 1.5 个月）。布鲁克斯法则描述的是剩余工作相对于上手成本很少的情形；趁早、且留下大量可划分工作时，增员是有帮助的。现实中的上手期常常比一个月长，协调开销（[[#eq-brooks-model]]）会把盈亏平衡点推得更远。
:::
:::

::: exercise 最优团队规模 {level=2 check="20"}
在 $W = 200$ 人月、$c = 1$ 人月/对的玩具模型 [[#eq-brooks-model]] 中，什么团队规模使工期最短，最短工期是多少？（填入团队规模。）
::: solution
$n^* = \sqrt{2W/c} = \sqrt{400} = 20$。于是 $T(20) = 200/20 + 19/2 = 10 + 9.5 = 19.5$ 个月。核对邻居：$T(19) = 10.53 + 9 = 19.53$，$T(21) = 9.52 + 10 = 19.52$，都略长。注意最小值多平：大约 15 到 27 人之间都在 20.5 个月以内，所以模型真正的信息是 $T$ 对极大团队而言的陡增，而不是最优位置的精确。
:::
:::

::: exercise 度量什么？{level=2}
一位经理提议按每周部署数奖励团队。用《加速》的四项交付度量说明可能会出什么问题，并提出对这些度量更好的用法。
::: solution
部署频率只衡量吞吐量。单独奖励它会诱使人为拆分变更、或不充分测试就部署；后者会表现为更高的变更失败率与更多的恢复服务时间——即那两个稳定性度量。这就是古德哈特定律：度量一旦成为目标，就不再反映它本要衡量的东西。更好的用法是诊断：把四项放在一起、随时间、在团队内部跟踪，以找出瓶颈（很长的前置时间可能指向缓慢的代码评审或手工测试），并记住这些度量背后的证据来自调查，显示的是诸度量与组织绩效之间的相关性，而不是提高某个数字就能带来改进。
:::
:::

::: exercise 松弛时间与关键路径 {level=3}
在一个项目长度为 $L$（关键路径长度）的任务网络中，定义 $\ell^-(t)$ 为恰好在 $t$ 之前结束的最长路径的长度（不含 $d(t)$），$\ell^+(t)$ 为从 $t$ 开始的最长路径的长度（含 $d(t)$）。反向一遍在 $t$ 没有后继时计算 $ls(t) = L - d(t)$，否则 $ls(t) = \min_{t \to u} ls(u) - d(t)$。证明 $\mathrm{slack}(t) = ls(t) - s(t) = L - \bigl(\ell^-(t) + \ell^+(t)\bigr)$，并推出松弛非负，且恰好对位于某条关键路径上的任务为零。
::: solution
**断言 1：** $ls(t) = L - \ell^+(t)$。按逆拓扑序归纳。若 $t$ 没有后继，从 $t$ 开始的最长路径就是 $t$ 自身，$\ell^+(t) = d(t)$，且 $ls(t) = L - d(t)$。否则，设断言对所有后继 $u$ 成立，
$$
ls(t) = \min_u \bigl(L - \ell^+(u)\bigr) - d(t) = L - \Bigl(d(t) + \max_u \ell^+(u)\Bigr) = L - \ell^+(t),
$$
因为从 $t$ 开始的最长路径由 $t$ 加上从它的某个后继开始的最长路径组成。

**断言 2：** 对最早开工调度，$s(t) = \ell^-(t)$；这已在 [[#thm-critical-path]] 的证明中给出。

于是 $\mathrm{slack}(t) = L - \ell^+(t) - \ell^-(t)$。而 $\ell^-(t) + \ell^+(t)$ 是*经过* $t$ 的最长路径的长度（把进入 $t$ 的最长路径与离开 $t$ 的最长路径接起来）。任何路径的长度都不超过 $L$，所以松弛 $\ge 0$；且当且仅当某条经过 $t$ 的路径长度为 $L$、即 $t$ 位于某条关键路径上时，它才为 $0$。这就证明了在 [[#ex-cpm]] 中把关键任务读作零松弛任务的做法。
:::
:::

::: exercise 相关的估计误差 {level=3}
修改 [[#ex-monte-carlo]] 的模拟，使得在每个模拟项目中，每个工期都乘上一个共享因子 $f$，$f$ 从 $[0.8, 1.6]$ 上众数为 $1$ 的三角分布抽取——模拟一个把所有任务都朝同一方向估错的团队。比较有与无共享因子时项目长度的均值、标准差与相对离散度（标准差除以均值），并解释结果。
::: solution
```python
import random, statistics
from cpm import critical_path

# （乐观、最可能、悲观）工期（天），以及前置任务
est = {
    "spec":    ((2, 3, 6),  set()),
    "db":      ((3, 5, 10), {"spec"}),
    "api":     ((3, 4, 8),  {"spec"}),
    "ui":      ((4, 6, 12), {"api"}),
    "reports": ((1, 2, 4),  {"db"}),
    "test":    ((2, 3, 8),  {"db", "ui", "reports"}),
    "deploy":  ((1, 1, 2),  {"test"}),
}

def simulate(correlated, runs=20_000, seed=2001):
    rng = random.Random(seed)
    lengths = []
    for _ in range(runs):
        # 一个共享因子：整个团队按同一比例误判了工作
        f = rng.triangular(0.8, 1.6, 1.0) if correlated else 1.0
        sample = {t: (f * rng.triangular(lo, hi, mode), deps)
                  for t, ((lo, mode, hi), deps) in est.items()}
        lengths.append(critical_path(sample)[0])
    return statistics.mean(lengths), statistics.stdev(lengths)

for c in (False, True):
    m, s = simulate(c)
    print(f"correlated={c!s:5}  mean {m:5.1f}  sd {s:4.1f}  sd/mean {s / m:.2f}")
```

```console
$ python3 correlated.py
correlated=False  mean  21.7  sd  2.5  sd/mean 0.12
correlated=True   mean  24.6  sd  4.7  sd/mean 0.19
```

共享因子的均值为 $(0.8 + 1 + 1.6)/3 \approx 1.13$，把平均长度抬高约 13%（从 21.7 天到 24.6 天）。更重要的是标准差几乎翻倍。误差独立时，一些任务上的超估会被其他任务上的低估部分抵消，于是和的离散度只按任务数的平方根增长。共享因子让每个任务同向变化、不会抵消：整体的不确定性按同样的比例与其各部分一样大。由于真实的估计误差是正相关的——同一批人、同样的乐观、同样不熟悉的技术——任务独立的模拟和 PERT 的方差公式都低估了真实风险。
:::
