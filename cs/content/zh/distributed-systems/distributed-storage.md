一个社交网络存储十亿份用户资料，每份几千字节——共计数 TB，以每秒一百万次请求对外服务。没有哪台单一机器能在内存里装下那么多数据，也没哪台能答那么多次请求，所以数据必须切分——比如说——到一百台机器上。于是每个请求都始于一个问题：*用户 42 的资料存在哪台机器上？*这个问题的答案必须能让每个客户端和服务器不必每次都去问一个中心目录就能算出来，必须把数据和负载均匀铺开，必须能在机器被加入、移除和更换时照常工作——而且每份数据都必须存放在几台机器上，使得丢失一台什么也不丢。

本章讲的是**分布式存储**：数据如何在机器之间**分区**，每个分区如何被**复制**，以及这些部件如何拼装成键值存储和文件系统。我们证明为什么朴素的哈希在一台机器加入时会重新洗牌几乎所有数据，而**一致性哈希**只搬动最少的量；我们分析它的负载不均衡，以及**虚拟节点**如何修复它，并用模拟来检验。然后我们研究两大设计流派：无主、最终一致的 **Dynamo** 风格——带宽松法定数量、版本向量和 Merkle 树反熵——以及 **Bigtable** 与 **Spanner** 的有主风格——按范围分区、每个分区由共识复制。最后我们看分布式文件系统——Google 文件系统及其后代——以及**擦除码**，它用复制成本的一小部分提供同样量级的持久性。本章建立在复制与法定数量（[[distributed-systems/replication-consistency]]）、共识（[[distributed-systems/consensus]]）和可靠性算术（[[distributed-systems/fault-tolerance]]）之上；B树与日志结构合并树这类单机存储结构见 [[databases/storage-indexing]]。

## 分区

::: definition 分区 {#def-partitioning}
**分区**（partitioning，又称**分片**）把一个视作带值键集合的数据集切分成互不相交的**分区**（partition，又称**分片** shard），并把每个分区分配给一台或多台机器。**分区方案**是一个从键到分区的函数，外加分区到机器的放置。得到不成比例的数据或请求份额的分区（或机器）是**热点**；普遍的不均匀是**倾斜**。
:::

有两种基本方案。

- **范围分区**把连续的键区间分配给分区：`a`–`f`、`g`–`m`，依此类推。范围查询（"客户 42 在三月的所有订单"）只触及少数分区，分区在长得太大时可以**分裂**。但倾斜的键会造成热点：若键是时间戳，今天的全部写入都落在最后一个分区上。
- **哈希分区**对键施加哈希函数 $h$，再对哈希值分区。好的哈希无论键的分布如何都把键均匀铺开，消灭由键的模式造成的热点——但范围查询现在必须询问每一个分区。（单个极热门的键——名人的资料——在任何方案下都仍是热点；它需要缓存，或者把键本身拆开。）

最简单的哈希方案 $\mathit{machine}(k) = h(k) \bmod n$ 有一个致命缺陷。

::: proposition 重新哈希几乎搬走一切 {#prop-mod-n}
若键被分配到机器 $h(k) \bmod n$，且哈希值均匀分布，那么把机器数从 $n$ 改为 $n + 1$ 会改变比例为 $n/(n+1)$ 的键所在的机器。
:::

::: proof
二元组 $(h \bmod n, h \bmod (n+1))$ 只取决于 $h \bmod n(n+1)$，因为 $n$ 与 $n + 1$ 互素，且对均匀哈希值而言 $h \bmod n(n+1)$ 在 $\set{0, \dots, n(n+1) - 1}$ 上均匀。把这样的值写成 $x = q(n + 1) + r$，其中 $0 \le q < n$、$0 \le r \le n$；于是 $x \bmod (n+1) = r$ 且 $x \bmod n = (q + r) \bmod n$（因为 $n + 1 \equiv 1 \pmod n$）。键留在原机器上当且仅当 $(q + r) \bmod n = r$，这要求 $r < n$（因为 $(q+r) \bmod n < n$），此时又要求 $q \equiv 0 \pmod n$，即 $q = 0$。所以恰有 $n$ 个值 $x = 0, 1, \dots, n - 1$ 保住自己的机器，比例为 $n / (n(n+1)) = 1/(n+1)$。其余的 $n/(n+1)$ 都要搬家。
:::

给十台机器加上第十一台会搬走 $91\%$ 的数据，尽管理想情况只需搬新机器应占的 $1/11 \approx 9\%$。搬家期间几乎每个请求都落空——对缓存而言，几乎每个请求都打到它背后的数据库上。补救办法是让分配方案依赖于机器本身，而不是机器的数目。

## 一致性哈希

David Karger 及合作者在 1997 年为分发 web 缓存引入了**一致性哈希**，它成为对等网络系统与键值存储分区的标准做法。

::: definition 一致性哈希 {#def-consistent-hashing}
把机器和键都哈希到一个圆——**环**——上——实践中是带循环回绕的整数 $0, \dots, 2^{64} - 1$，我们把它归一化到 $[0, 1)$。每台机器 $s$ 放在点 $h(s)$ 处。键 $k$ 被分配给 $h(k)$ 顺时针方向的第一个机器，即它的**后继**。于是每台机器拥有从其前驱之点（不含）到它自己之点（含）的**弧段**。
:::

::: theorem 一致性哈希搬动的量是最小的 {#thm-consistent}
把哈希函数建模为把机器和键放在环上独立的均匀随机点处。当一台机器加入 $n$ 台机器的环时，只有被它接管的那段弧内的键会搬家，且全部搬到新机器上，搬家键的期望比例为 $1/(n+1)$。当一台机器离开时，只有它自己的键搬家，全部交给它的后继。
:::

::: proof
新机器 $s$ 落在某台机器 $t$ 的弧段内，把该弧段一分为二：$t$ 的前驱与 $h(s)$ 之间的键现在以 $s$ 为后继；$h(s)$ 与 $h(t)$ 之间的键仍以 $t$ 为后继；而其他每个键的后继都不变，因为没有添加别的点。所以只有现在归 $s$ 所有的弧段内的键搬家，且是从 $t$ 搬到 $s$。加入之后有 $n + 1$ 台机器位于独立的均匀点上，由对称性每台拥有的弧段期望长度相同；这些长度之和为 $1$，所以每段弧的期望长度为 $1/(n+1)$，$s$ 的弧段亦然。其中（均匀放置的）键的期望比例就是 $1/(n+1)$。移除是加入的逆过程。
:::

平均而言，搬动的数据*量*恰是合适的——可它一开始分布得均匀吗？$n$ 个随机点的弧段变化很大。

::: proposition 最大的弧段 {#prop-max-arc}
$n$ 台机器位于独立的均匀点上时，某台机器拥有长度超过 $c/n$（即平均值的 $c$ 倍）的弧段的概率至多为 $n(1 - c/n)^{n-1} \le n e^{-c(n-1)/n}$。特别地，以高概率最大的弧段长度为 $O(\log n / n)$，约为平均值的 $\ln n$ 倍。
:::

::: proof
机器 $s$ 的弧段长于 $x$，恰当其他 $n - 1$ 个点没有一个落在 $h(s)$ 正前方（逆时针方向）长度为 $x$ 的区间内。对每个其他点，这以 $1 - x$ 的概率发生且相互独立，所以概率为 $(1 - x)^{n-1}$。对 $n$ 台机器用联合界，某段弧超过 $x = c/n$ 的概率至多为 $n(1 - c/n)^{n-1}$，由 $1 - y \le e^{-y}$ 得第二个形式。取 $c = 2\ln n \cdot n/(n-1)$ 可使界至多为 $1/n$。
:::

所以每台机器只有一个点时，最忙的机器通常持有其应得份额数倍的数据，最闲的几乎什么都没有。标准的补救是给每台机器许多个点。

::: definition 虚拟节点 {#def-vnodes}
采用**虚拟节点**时，每台物理机器 $s$ 被放在环上的 $v$ 个点 $h(s\#1), \dots, h(s\#v)$ 处，并拥有以其各点为端点的那些弧段的并集。
:::

一台机器的份额现在是 $v$ 段弧长之和，会集中在其均值 $1/n$ 附近：每台机器取 $v = \Theta(\log n)$ 个点时，以高概率每台机器的份额都在 $1/n$ 的常数因子以内；$v$ 更大时，散布大致按 $1/\sqrt{v}$ 收缩。虚拟节点还有两个好处：容量翻倍的机器可以简单拿两倍的点；一台机器失效时，它的负载分散到许多台机器上（它的众多点的后继们的主人），而不是整个压在一个邻居身上。

::: example 模拟一个环 {#ex-ring}
在环上放置 $10$ 台机器，分别带 $v = 1$、$10$ 和 $100$ 个虚拟节点，分配 $100{,}000$ 个键，测量负载最重与最轻的机器相对均值的比例。然后加入第十一台机器并统计搬家的键数。与 $h(k) \bmod n$ 作比较。
::: solution
```python
import bisect, hashlib

def h(s):
    """A 64-bit position on the ring from a cryptographic hash (stable across runs)."""
    return int.from_bytes(hashlib.sha256(s.encode()).digest()[:8], "big")

class Ring:
    def __init__(self, nodes, vnodes):
        self.points = sorted((h(f"{n}#{v}"), n) for n in nodes for v in range(vnodes))
        self.keys = [p for p, _ in self.points]
    def owner(self, key):
        i = bisect.bisect(self.keys, h(key)) % len(self.points)   # 顺时针方向的第一个点
        return self.points[i][1]

keys = [f"user:{i}" for i in range(100_000)]
for vnodes in (1, 10, 100):
    before = Ring([f"node{i}" for i in range(10)], vnodes)
    after = Ring([f"node{i}" for i in range(11)], vnodes)          # 加入第十一个节点
    load = {}
    for k in keys:
        o = before.owner(k); load[o] = load.get(o, 0) + 1
    moved = sum(before.owner(k) != after.owner(k) for k in keys)
    print(f"vnodes={vnodes:3}  max/mean load={max(load.values()) / (len(keys) / 10):.2f}"
          f"  min/mean={min(load.values()) / (len(keys) / 10):.2f}  moved={moved / len(keys):.3f}")
moved_mod = sum(h(k) % 10 != h(k) % 11 for k in keys)
print(f"hash mod n: moved={moved_mod / len(keys):.3f}")
```

```console
$ python3 ring.py

vnodes= 10  max/mean load=1.77  min/mean=0.46  moved=0.108
vnodes=100  max/mean load=1.17  min/mean=0.77  moved=0.090
hash mod n: moved=0.909
```

每台机器一个点时，最忙的机器持有其份额的 $2.46$ 倍，最闲的只有 $4\%$——正是 [[#prop-max-arc]] 所预测的不均衡。$100$ 个虚拟节点时，各负载都在均值的约 $25\%$ 以内。每种情形下，第十一台机器加入时都有约 $1/11 \approx 0.091$ 的键搬家（单点情形不那么精确，因为一段随机弧离它的期望值很远），而 $h(k) \bmod n$ 搬了 $0.909$，恰是 [[#prop-mod-n]] 的 $n/(n+1)$。二分查找使每次查找为 $O(\log(nv))$；$1000$ 个点时环表只有几 KB，可以在每个客户端上复制一份。
:::
:::

:::

环的两种替代方案值得了解。**会合哈希**（rendezvous hashing，最高随机权重；Thaler 与 Ravishankar，1998）把键 $k$ 分配给使 $h(k, s)$ 最大的机器 $s$；它不需要环、均衡得好，且一台机器离开时只搬走它自己的键（习题 9），代价是每次查找 $O(n)$。**跳跃一致性哈希**（jump consistent hashing；Lamping 与 Veach，2014）用几次算术运算算出 $[0, n)$ 中的桶号，$n$ 增大时只搬走 $1/(n+1)$ 的键——但只支持增删*最后*一个桶，所以适合编号的分片而非单台机器。许多系统通过创建远多于机器数的分区（比如固定 $1000$ 个分区）、在机器之间整片整片地搬运、并把分配记录在一张小型、复制的**元数据**表里，从根本上回避了这个问题。

## 无主复制：Dynamo 设计

Amazon 的 Dynamo（DeCandia 及合作者，2007）把一致性哈希与 [[distributed-systems/replication-consistency]] 的法定数量结合，构建了一个总是接受写入的键值存储——购物车绝不该拒绝一次"加购"——代价是最终一致性。它的设计被 Riak、Cassandra（把它与 Bigtable 的数据模型结合）和 Voldemort 采用。

::: algorithm Dynamo 风格的复制 {#alg-dynamo}
1. **放置。** 每个键存储于 $h(k)$ 顺时针方向的最先 $N$ 台互异物理机器上（跳过已被选中机器的其余虚拟节点），即它的**偏好列表**。
2. **写。** 一个**协调者**（任意节点，通常是列表中的第一个）把带更新后版本向量的写入发给这 $N$ 个副本，收到 $W$ 个确认后报告成功。
3. **读。** 协调者询问这 $N$ 个副本，收到 $R$ 个应答后返回。若应答中包含因果无关的版本（版本向量互不支配），就把它们全部——**兄弟版本**——返回，由客户端合并后写回结果。
4. **宽松法定数量与提示移交。** 若偏好列表中的某些机器不可达，写入就改发到环上下一个健康的机器，并附上指明预期所有者的**提示**；所有者恢复后，带提示的数据交还给它。
5. **修复。** **读修复**把最新版本发给返回了陈旧版本的副本；**反熵**在后台用 Merkle 树比较副本，拷贝缺失的更新。
:::

各部件咬合在一起。版本向量（[[distributed-systems/time-clocks#alg-vector]]），每个协调过一次写的副本一个分量，能分辨更新的版本与并发的版本：若一个向量支配另一个，较旧的版本被丢弃；否则两者都留给应用——它知道怎么合并购物车——或者存储自动合并为 CRDT（[[distributed-systems/replication-consistency#def-crdt]]）。宽松法定数量在故障期间保持写入的可用性，但它们破坏了 [[distributed-systems/replication-consistency#thm-quorum]] 的相交论证：被替补机器接受的写并不在那 $N$ 个指定副本中的任何一个上，所以对这些副本的读在提示移交完成之前看不到它。典型的设置是 $N = 3$ 且 $R = W = 2$；对时延敏感的应用用 $R = 1$ 或 $W = 1$。

::: example 购物车里的兄弟版本 {#ex-siblings}
一个购物车键的偏好列表为 $A, B, C$，$N = 3$、$R = W = 2$，版本向量带 $[A, B, C]$ 各分量。追踪：(1) 一个客户端加购 "book"，由 $A$ 协调；(2) 网络分区把 $A$ 与 $B$、$C$ 隔开；一个客户端经 $A$ 加购 "pen"，另一个客户端经 $B$ 加购 "lamp"；(3) 分区愈合，一个客户端来读。
::: solution
(1) $A$ 存储 $\set{\text{book}}$、向量 $[1, 0, 0]$ 并复制它；$B$ 和 $C$ 确认。

(2) $A$ 无法到达 $B$ 或 $C$。用宽松法定数量，它在本地和替补节点 $D$——环上下一个健康的机器——写入 $\set{\text{book}, \text{pen}}$、$[2, 0, 0]$，并附注这份拷贝属于 $B$ 或 $C$；$W = 2$ 满足。在分区另一侧，$B$ 读到 $\set{\text{book}}$、$[1,0,0]$，把 $\set{\text{book}, \text{lamp}}$、$[1, 1, 0]$ 写给自己和 $C$。

(3) 提示移交之后，一次读收集到 $[2, 0, 0]$ 和 $[1, 1, 0]$。谁也不支配谁（$A$ 的分量 $2 > 1$，$B$ 的分量 $0 < 1$），所以它们并发，读返回两个兄弟版本。客户端把它们合并——对购物车就是取并集，$\set{\text{book}, \text{pen}, \text{lamp}}$——并把结果以合并后的向量 $[2, 1, 0]$（在其协调者处推进，支配两个兄弟）写回，于是两个兄弟都被丢弃。两次写在分区期间都被接受，谁也没有丢；代价是应用必须自己合并。倘若客户端在一侧删除过 "book"，并集合并会把它复活——这正是 OR-Set（[[distributed-systems/replication-consistency]]）所修复的异常。
:::
:::

### 用 Merkle 树做反熵

读修复只修复被读到的数据。要找出两个副本之间的所有差异——每个副本或许持有几十亿个键——而不用发送所有键，Dynamo 风格的系统会比较 **Merkle 树**（哈希树，Ralph Merkle，1979）。

::: definition Merkle 树 {#def-merkle}
把键范围分成 $2^d$ 个桶。副本的 **Merkle 树**是一棵深度为 $d$ 的完全二叉树：每个叶存放一个桶内容的密码学哈希，每个内部节点存放其两个孩子哈希的哈希。两个副本自根向下比较树，只进入哈希不同的子树。
:::

::: proposition Merkle 比较的代价 {#prop-merkle}
若两个副本深度为 $d$ 的树恰在 $k$ 个叶上不同，自顶向下的比较至多交换 $1 + 2kd$ 个节点哈希，并找出那 $k$ 个不同的桶。若 $k = 0$，它只交换一个哈希。
:::

::: proof
节点的哈希在两个副本之间不同，只有当它下面某个叶不同（假定没有哈希碰撞，密码学哈希使碰撞可忽略）。比较先发送根，并对每个不同的内部节点发送它的两个孩子。不同的内部节点是那 $k$ 个不同叶的祖先：在叶之上的 $d$ 层（第 $0$ 到 $d-1$ 层）中，每层至多 $k$ 个。所以至多展开 $kd$ 个内部节点，每个发送 $2$ 个哈希，再加上根：$1 + 2kd$。到达的叶恰是那些不同的叶。若 $k = 0$，根相同，比较即止。
:::

::: example 比较两个副本 {#ex-merkle}
一个分区的两个副本持有 $10^8$ 个键，分成 $2^{20}$ 个各约 $100$ 键的桶，哈希为 $32$ 字节。一次短暂失联之后，$3$ 个桶不同。与发送每个键的哈希相比，这次比较交换多少数据？
::: solution
由 $d = 20$、$k = 3$ 的 [[#prop-merkle]]：至多 $1 + 2 \cdot 3 \cdot 20 = 121$ 个哈希，不到 $4$ KB，用 $21$ 轮消息（每层一轮），此后只需对那 $3$ 个不同的桶（约 $300$ 个键）逐键比较。若每键发送一个 $32$ 字节的哈希要花 $3.2$ GB。代价在维护：每次写入都必须更新其叶到根路径上的哈希，或者定期重算树；分区在机器之间迁移时树必须重建——这是这种设计一个众所周知的运维成本。
:::
:::

::: warning 最后写入获胜会悄无声息地丢数据
许多无主存储用**最后写入获胜**（last writer wins，LWW）来化解并发写：每次写入带一个墙钟时间戳，时间戳最大的存活。这是靠让其中一个写入消失来让冲突消失。并发写入——两个用户在同一时刻更新同一个键——只留一个，不报任何错；而且因为时钟有偏移（[[distributed-systems/time-clocks]]），即使在现实时间中*更晚*发生的写，也可能输给一台钟走得快的机器上更早的写。LWW 只适合丢失并发更新无伤大雅的数据（缓存、只写一次的不可变键），或者每个键只由一个写入者写的键设计。
:::

## 有主的分区存储

另一设计流派保留分区，但给每个分区配一个领导者并用共识来复制，从而对每个键提供线性一致的读写。

Google 的 **Bigtable**（Chang 及合作者，2006）存储一个从 (row, column, timestamp) 到值的稀疏有序映射。表被**范围分区**为大约 $100$–$200$ MB 的 **tablet**，每个 tablet 由一台 tablet 服务器服务；tablet 的位置构成一个三层的元数据 tablet 层次，其根位于 Chubby 锁服务中的一个文件里，于是客户端缓存位置、很少去询问。tablet 以日志结构合并树存储，其文件住在分布式文件系统里，复制由文件系统提供；主服务器把 tablet 指派给服务器，并用 Chubby 租约确保每个 tablet 恰有一台服务器。Apache HBase 遵循这一设计。

**Spanner**（Corbett 及合作者，2012）以及受它启发的系统，如 CockroachDB 和 TiDB，用各自的 Paxos 或 Raft 组复制每个范围分区（"split"、"range" 或 "region"），通常是三个或五个位于不同故障域的副本。组的领导者为其范围提供线性一致的读写；范围在变大时分裂，并经由共识组的成员变更在机器之间迁移。跨越多个范围的事务需要 [[distributed-systems/distributed-transactions]] 的原子提交协议，而 Spanner 的 TrueTime 让它们达到外部一致。

::: quiz
某存储用一致性哈希把键分区到 $50$ 台机器上，每台 $200$ 个虚拟节点，并把每个键复制到顺时针方向接下来的 $3$ 台互异机器上，$R = W = 2$。哪句话正确？
- [ ] 加入第 $51$ 台机器会搬走约 $1/51$ 的*键*，以及相同比例的副本拷贝，全部搬到新机器上
- [x] 对键 `user:1000` 到 `user:2000` 的范围查询一般必须联系每台机器
- [ ] 因为 $R + W > N$，读是线性一致的
- [ ] 每台机器 $200$ 个虚拟节点时，单个热键的请求会散布到 $200$ 个点上
::: solution
哈希分区把相邻的键撒在整个环上，所以范围查询是向所有机器的分散–汇集。加入一台机器会把约 $1/51$ 的每个副本位置的数据挪到它上面——但它同时改变某些偏好列表中第二、第三个是谁，所以一些拷贝也会在既有机器之间移动。法定数量相交并不给出线性一致性（见 [[distributed-systems/replication-consistency]]）。而单个键只映射到一个点，从而只对应一个偏好列表，无论虚拟节点有多少：热键依旧热。
:::
:::

## 分布式文件系统

分布式文件系统呈现文件与目录，其数据住在许多机器上。Sun 的 **NFS**（1984）让客户端挂载远程服务器的目录：它的服务器原本是**无状态**的，其操作被设计成幂等的（在显式偏移处读写，而不是相对服务器端的文件位置），于是服务器崩溃后客户端可以直接重试（[[distributed-systems/remote-communication#def-idempotent]]）。客户端缓存数据并在打开时与服务器核对；NFS 的**关闭–打开一致性**（close-to-open consistency）保证：打开文件的客户端能看到更早关闭过该文件的所有客户端的写入，但并发写不在保证之列。单机上的文件系统结构见 [[operating-systems/file-systems]]。

Google 规模的数据中心存储需要的则是别的东西：许多 GB 大的文件，主要以追加方式写、主要顺序读，跑在每天有机器故障的数千台廉价机器上。

::: definition Google 文件系统的体系结构 {#def-gfs}
在 **Google 文件系统**（Ghemawat、Gobioff 与 Leung，2003）中，文件被分成 $64$ MB 的定长**块（chunk）**，每块由唯一句柄标识，作为普通文件存放在若干**块服务器**上（默认三台，位于不同机架）。单个**主服务器**把所有元数据放在内存里——名字空间、文件到块的映射以及块的位置——并把元数据变更记入一份复制的操作日志。客户端只向主服务器请求元数据；数据直接在客户端和块服务器之间流动。对每块，主服务器把**租约**授给一个副本，即**主本（primary）**，由它为块的所有变更选定顺序并转发给**从本（secondary）**。
:::

这个设计做了几处大胆简化，被后来的系统继承。单个主服务器简单，能以全局视野做放置决策，但限制了文件数（它的内存大约每块 $64$ 字节）且是单点故障，靠快速重启和影子主服务器缓解。大块减少元数据和主服务器流量。故障是家常便饭：块服务器发送心跳；某台消失时，主服务器从幸存的副本重新复制它的块——从许多台机器并行地复制，从而把修复时间、进而由 [[distributed-systems/fault-tolerance#thm-mttdl]] 把丢失数据的风险都保持得很小。GFS 的有意弱一致性：它的**记录追加**操作*至少一次*地把数据追加到系统选定的偏移处，所以应用必须容忍重复和填充，用唯一标识符和校验和来辨认记录——把 [[distributed-systems/remote-communication]] 的去重原则推行到应用层。Hadoop 分布式文件系统（HDFS）遵循同样的体系结构，有 NameNode 和 DataNode，默认块大小为 $128$ MB（截至 2026 年）。Google 的后继者 Colossus 把元数据本身分散到一个类 Bigtable 的存储上。

::: example 主服务器的内存 {#ex-gfs-master}
一个 GFS 集群以 $64$ MiB 的块、每块三副本存储 $4$ PiB 数据。主服务器要跟踪多少块？按每块约 $64$ 字节的块元数据计算，需要多少内存？
::: solution
$4 \cdot 2^{50} / 2^{26} = 2^{26} \approx 6700$ 万块（副本不增加块，只增加位置）。每块 $64$ 字节即 $2^{32}$ 字节 $= 4$ GiB——在一台大机器上宽裕地放进内存。换成 $1$ MiB 的块，同样的数据要 $256$ GiB 元数据，这正是块取得大的原因之一。另一面是大量小文件会浪费这个设计：一个 $1$ KB 的文件照样要花一块的元数据。
:::
:::

### 擦除码

三副本复制把每个字节存三遍。**擦除码**以低得多的代价达到可比的持久性。

::: definition Reed–Solomon $(k, m)$ 编码 {#def-erasure}
**$(k, m)$ 擦除码**把一块数据分成 $k$ 个数据分片（fragment）并算出 $m$ 个校验分片，使得原始数据可以从 $k + m$ 个分片中的**任意** $k$ 个重构。Reed–Solomon 码（里德-所罗门码，1960）把数据视作有限域上一个次数小于 $k$ 的多项式的取值、并存储在 $k + m$ 个点处的值，从而对任意 $k$ 和 $m$ 做到这一点。存储开销为 $(k + m)/k$，码能容忍任意 $m$ 个分片的丢失。
:::

$(6, 3)$ 码每字节数据存储 $1.5$ 个字节，并能容忍任意 $3$ 个分片丢失；三副本复制每字节数据要 $3$ 个字节，却只能容忍 $2$ 份拷贝丢失。代价在别处。读取完好的数据要触及 $k$ 台机器而不是一台（若布局让数据分片可直读，则读一个数据分片），而**修复**一个丢失的分片需要读 $k$ 个分片——是重新拷贝一份副本的网络流量的六倍。因此存储系统让热的、最近写入的数据保持复制，把冷数据转换成擦除码形式；Facebook 存照片的 f4 系统（2014）和 HDFS 的擦除码支持（自 $3$ 版起）是例子，Microsoft 的 Azure 存储使用**局部重构码**（local reconstruction codes），让常见的单分片故障修复更便宜。其中的多项式机制属于有限域的内容，在数学图谱中讲解。

::: history
分布式文件系统始于 1980 年代初：Sun 的 NFS（1984）和 Carnegie Mellon 的 Andrew 文件系统（1980 年代；Howard 及合作者，1988），后者的整文件缓存与回调影响了后来的设计。David Karger、Eric Lehman、Tom Leighton、Rina Panigrahy、Matthew Levine 与 Daniel Lewin 的《一致性哈希与随机树》（"Consistent hashing and random trees"）发表于 STOC 1997，催生了 Akamai 的内容分发网络；2001 年，Chord（Stoica 及合作者）和其他分布式哈希表把它用于对等查找。Sanjay Ghemawat、Howard Gobioff 与 Shun-Tak Leung 在 SOSP 2003 上描述了 Google 文件系统，Fay Chang 及合作者在 OSDI 2006 上描述了 Bigtable。Giuseppe DeCandia 及合作者的《Dynamo：Amazon 的高可用键值存储》（"Dynamo: Amazon's highly available key-value store"，SOSP 2007）奠定了无主设计；Avinash Lakshman 与 Prashant Malik 的 Cassandra（2009–10）把它与 Bigtable 的数据模型结合。Merkle 树源自 Ralph Merkle 关于数字签名的工作（专利申请于 1979 年）；Irving Reed 与 Gustave Solomon 的码发表于 1960 年。James Corbett 及合作者的 Spanner 出现在 OSDI 2012。
:::

## 后续内容

分区且复制的存储给每个键一个稳定的归属；触及多个分区上多个键的操作——不同分片两个账户之间的银行转账——需要**分布式事务**，见下一章（[[distributed-systems/distributed-transactions]]）。大规模批处理与流处理正是从这些文件系统和存储读输入、写输出，并把计算搬到数据身边（[[distributed-systems/data-processing]]）。web 搜索的倒排索引以同样的方式分区到数千台机器上（[[information-retrieval/web-search]]）。

::: summary
- **分区**按键范围（利于范围查询，易出热点）或按哈希（均匀，但范围查询要触及所有分区）把数据铺到机器上。
- 加入一台机器时 $h(k) \bmod n$ 会搬走比例为 $n/(n+1)$ 的键（[[#prop-mod-n]]）；**一致性哈希**期望只搬 $1/(n+1)$（[[#thm-consistent]]）。
- 每台机器一个点会留下长约平均值 $\ln n$ 倍的弧段（[[#prop-max-arc]]）；**虚拟节点**均衡负载、分散恢复。
- **Dynamo 风格**存储使用偏好列表、法定数量、带提示移交的**宽松法定数量**、带兄弟版本的**版本向量**、读修复和 **Merkle 树**反熵（[[#prop-merkle]]）——保持可用但最终一致；LWW 会丢并发写。
- **有主**存储（Bigtable、Spanner）按范围分区数据，并用共识组复制每个分区，提供每键线性一致的访问。
- **GFS/HDFS** 把元数据主服务器与块服务器分开，使用大块、用租约决定变更顺序、并快速并行地重新复制；记录追加是至少一次。
- **擦除码** $(k, m)$ 以开销 $(k+m)/k$ 容忍 $m$ 次丢失，用更便宜的存储换取更贵的读和修复。
:::

::: exercise 擦除码开销 {level=2 check="1.4"}
使用 $(10, 4)$ Reed–Solomon 码。存储开销因子是多少？它能容忍多少个分片同时丢失？修复一个丢失的分片必须读多少个分片？（填入开销因子。）
::: solution
开销 $(10 + 4)/10 = 1.4$。它能容忍任意 $4$ 个分片丢失。修复一个丢失的分片需要读任意 $10$ 个幸存分片——是丢失分片数据的十倍，这正是擦除码主要的运维成本。
:::

::: exercise 十倍的超载 {level=2 check="1000*(1 - 10/1000)^999"}
用 [[#prop-max-arc]] 的联合界，给出 $1000$ 台机器每台一个点时，某台机器拥有超过其应得份额 $10$ 倍的环的概率上界。（填入上界。）
::: solution
$n(1 - c/n)^{n-1} = 1000 \times 0.99^{999} \approx 0.044$。$c = 14$ 时界降到约 $0.00076$；最大的弧段通常约为平均值 $\ln 1000 \approx 7$ 倍。
:::
:::

::: exercise 偏好列表与虚拟节点 {level=2}
在 [[#alg-dynamo]] 中，偏好列表为什么必须跳过已被选中机器的虚拟节点？还要加上什么约束，才能让一个键的副本扛住整个机架的丢失？
::: solution
有了虚拟节点，顺时针方向最先的 $N$ 个*点*可能属于不足 $N$ 台机器——一台机器的 $v$ 个点中的两个可能相邻。若列表不跳过它们，一个键的三个"副本"中的两个就可能落在同一台机器上，那台机器一丢就丢两份。跳过重复的机器保证 $N$ 台互异机器。对付机架故障，还要跳过同一机架中已用过的机器，沿环继续走，直到覆盖 $N$ 个互异的机架（Cassandra 的机架感知放置就这么做）。代价是负载略欠均匀，因为某些键要走更长的路。
:::
:::

::: exercise 一次 Merkle 比较 {level=2 check="1 + 2*5*16"}
两个副本使用深度为 $16$ 的 Merkle 树，在 $5$ 个桶上不同。[[#prop-merkle]] 的自顶向下比较最多交换多少个哈希？（填入数量。）
::: solution
$1 + 2kd = 1 + 2 \cdot 5 \cdot 16 = 161$。若 $5$ 个不同的桶共享祖先（例如全在同一棵子树里），不同的内部节点更少，发送的哈希也更少。
:::
:::

::: exercise 直接证明重新哈希的比例 {level=3}
列出 $\set{0, \dots, 89}$ 中满足 $x \bmod 9 = x \bmod 10$ 的余数 $x$，给出 $n = 9$ 时 [[#prop-mod-n]] 的一个计数证明；并推广：对任意 $n < n'$，把 $h \bmod n$ 换成 $h \bmod n'$ 时，多大比例的键留在原机器？
::: solution
$x \bmod 9 = x \bmod 10$ 恰对 $x = 0, 1, \dots, 8$ 成立：对 $x = 10q + r$（$0 \le q \le 8$、$0 \le r \le 9$），有 $x \bmod 9 = (q + r) \bmod 9$，它等于 $r$ 仅当 $r \le 8$ 且 $q = 0$。即 $90$ 个余数中的 $9$ 个，比例为 $1/10$；所以 $9/10$ 的键搬家。

一般地，对任意 $n < n'$，$x \in [0, \mathrm{lcm}(n,n'))$ 内 $x \bmod n = x \bmod n'$ 成立，恰当 $x \bmod n' < n$ 且 $x - (x \bmod n')$ 是 $n$ 和 $n'$ 的公倍数，即 $x = \ell \cdot \mathrm{lcm}(n, n') + r$ 且 $0 \le r < n$——在一个周期内，就是 $x = 0, \dots, n - 1$ 这 $n$ 个值。所以留在原机器的键比例恒为 $n/\mathrm{lcm}(n, n')$，对任何一对都成立。$n' = n + 1$ 时是 $1/(n+1)$；$n' = 2n$ 时是 $1/2$——集群扩容一倍会搬走一半的键，这就是一些系统只按倍增扩容的原因。
:::
:::

::: exercise 会合哈希 {level=3}
用 Python 实现会合哈希（把键 $k$ 分配给使 $h(k \,\|\, s)$ 最大的机器 $s$），并证明：一台机器离开时只有它自己的键搬家；一台机器 $s'$ 加入时只有 $s'$ 现在赢得的键搬家，且全部搬到 $s'$。加入时搬家的期望比例是多少？
::: solution
```python
import hashlib

def score(key, node):
    return int.from_bytes(hashlib.sha256(f"{key}|{node}".encode()).digest()[:8], "big")

def owner(key, nodes):
    return max(nodes, key=lambda s: score(key, s))

nodes = [f"node{i}" for i in range(10)]
keys = [f"user:{i}" for i in range(100_000)]
moved = sum(owner(k, nodes) != owner(k, nodes + ["node10"]) for k in keys)
print(f"moved on join: {moved / len(keys):.3f}")
```

```console
$ python3 hrw.py
moved on join: 0.091
```

*离开。* 若 $s$ 离开，被另一台机器 $t$ 拥有的键 $k$ 原本在所有机器中以 $t$ 使 $h(k \| \cdot)$ 最大；移除 $s \ne t$ 移除的是一个更小的分数，所以 $t$ 仍是最大。只有 $s$ 拥有的键搬家，各自搬到其分数第二高的机器——它们分散到其余所有机器上，而不是整个砸在一个邻居身上。

*加入。* 加入 $s'$ 为每个键增加一个分数。若 $h(k \| s')$ 不是新的最大值，原来的最大者仍然获胜，$k$ 留下；若是，$k$ 搬到 $s'$。所以搬走的键全部搬到 $s'$。把分数建模为独立且连续，则对给定的键，$n + 1$ 台机器各有相同的概率拿最高分，所以一个键以概率 $1/(n+1)$ 搬家，与 $n = 10$ 时模拟出的 $0.091$ 相符。
:::
:::
