某存储服务通过锁服务发放的锁，允许一次只有一个客户端写一个文件。客户端 1 获得了一把锁——一份有效期十秒的**租约**（lease）——并开始写入。随后它的进程停止了十五秒——一次漫长的垃圾回收停顿，或者它的虚拟机被暂停以进行迁移。租约到期；锁服务把锁授予客户端 2，客户端 2 写了这个文件。客户端 1 醒来，仍然相信自己持有锁（在它看来什么都没有发生），并在客户端 2 的写入之上完成了自己的写。文件被破坏了，尽管每个组件都“正确”地行事。

让系统在自己的部分部件出故障时继续工作，这就是**容错**的目标。前面几章给出了主要工具：复制（[[distributed-systems/replication-consistency]]）与共识（[[distributed-systems/consensus]]）。本章补齐其余内容。我们从可靠性的词汇与算术开始——可用性、平均无故障时间、丢失数据的概率——然后用 Chandra 与 Toueg 的不可靠故障检测器把**故障检测**精确化，其中包括为开头那个故事解围的租约与**栅栏令牌**（fencing token）。我们考察**状态机复制**对被复制的服务有什么要求。然后我们告别崩溃故障，直面**拜占庭**故障：有缺陷的进程可能说谎。我们证明那条著名的下界——达成一致所需进程数必须超过叛徒数的三倍，$n \ge 3f + 1$；研究兰波特（Lamport）、Shostak 与 Pease 的递归算法；对它进行模拟；并看 PBFT 如何使用大小为 $2f + 1$ 的法定数量。最后我们以恢复收尾：检查点与回滚。

## 故障、错误与失效

可信性（dependability）文献（Avižienis、Laprie、Randell 与 Landwehr，2004）区分了日常语言统称为“故障”的三件事。

::: definition 故障、错误、失效 {#def-fault}
**失效**（failure）是系统交付的服务偏离其规格的事件。**错误**（error）是系统状态中可能导致失效的那部分。**故障**（fault）是错误的原因——硬件或软件中的缺陷、操作员的失误、宇宙射线。当故障正在产生错误时称它是**活动的**，否则是**休眠的**。
:::

内存单元里的位翻转是一个故障；变量里的错误值是一个错误；返回给用户的错误答案是失效。一个组件的失效，是包含它的系统的一个故障——这正是我们能用不可靠的部件构建可靠系统的原因。**容错**意味着阻止故障变成系统失效：可以**掩蔽**它们（复制：其余副本照常运行），可以检测错误并**恢复**（从检查点重启），或者**安全失效**（停机而不造成危害）。

### 可用性与可靠性

::: definition 可靠性与可用性 {#def-availability}
系统的**可靠性** $R(t)$ 是它在时间 $t$ 内无失效运行的概率。它的**平均无故障时间**（MTTF）是从（重新）启动到下一次失效的期望时间，**平均修复时间**（MTTR）是从失效到恢复服务的期望时间。它的（稳态）**可用性**是长期运行中处于可用状态的时间比例：
$$
A = \frac{\mathrm{MTTF}}{\mathrm{MTTF} + \mathrm{MTTR}}.
$$ {#eq-availability}
:::

这个公式来自更新–报酬定理：系统在可用时段（均值 MTTF）与停机时段（均值 MTTR）之间交替，长期来看可用时间的比例就是两个均值之比。可用性常用“**几个九**”来引述：$99.9\%$（“三个九”）允许每年停机 $8.8$ 小时，$99.99\%$ 允许 $53$ 分钟，$99.999\%$ 约 $5$ 分钟。公式显示出两个杠杆：让故障更稀少，或者让修复更快。自动故障转移主要是把 MTTR 从小时级（要呼叫值班人员）压缩到秒级的手段。

*丢失数据*的概率则与可用性表现不同：只有当每个副本都在修复完成之前失效时，数据才会丢失。

::: theorem 两个副本的平均数据丢失时间 {#thm-mttdl}
两个副本独立失效，失效率各为 $\lambda$（寿命服从指数分布，故 $\mathrm{MTTF} = 1/\lambda$）。一个副本失效后，以比率 $\mu$ 进行修复——其数据从幸存副本重新拷贝——（$\mathrm{MTTR} = 1/\mu$）。若第二个副本在修复期间失效，数据即告丢失。从两个副本都可用开始，平均数据丢失时间为
$$
\mathrm{MTTDL} = \frac{3\lambda + \mu}{2\lambda^2} \;\approx\; \frac{\mathrm{MTTF}^2}{2\,\mathrm{MTTR}} \quad\text{当 } \mu \gg \lambda.
$$ {#eq-mttdl}
:::

::: proof
令 $T_2$、$T_1$ 分别表示从两个副本可用、一个副本可用出发到数据丢失的期望时间。两个副本可用时，第一次失效在速率为 $2\lambda$ 的指数时间后到来（均值 $1/(2\lambda)$），进入状态 $1$：$T_2 = \frac{1}{2\lambda} + T_1$。一个副本可用时，下一个事件在均值 $1/(\lambda + \mu)$ 之后到来；它以概率 $\mu/(\lambda + \mu)$ 是一次修复（回到状态 $2$），以概率 $\lambda/(\lambda+\mu)$ 是一次失效（数据丢失）。于是
$$
T_1 = \frac{1}{\lambda + \mu} + \frac{\mu}{\lambda + \mu}\, T_2 = \frac{1}{\lambda + \mu} + \frac{\mu}{\lambda + \mu}\left(\frac{1}{2\lambda} + T_1\right).
$$
两边乘以 $\lambda + \mu$ 并整理 $T_1$：$\lambda T_1 = 1 + \frac{\mu}{2\lambda}$，故 $T_1 = \frac{2\lambda + \mu}{2\lambda^2}$，而 $T_2 = \frac{1}{2\lambda} + \frac{2\lambda+\mu}{2\lambda^2} = \frac{3\lambda + \mu}{2\lambda^2}$。当 $\mu \gg \lambda$ 时分子约为 $\mu$，得到 $\mu/(2\lambda^2) = \mathrm{MTTF}^2 / (2\,\mathrm{MTTR})$。
:::

::: example 两块磁盘多久丢一次数据？ {#ex-mttdl}
一块磁盘的 MTTF 为 $100{,}000$ 小时（约 $11$ 年），重新复制其内容需要 $24$ 小时。一对镜像磁盘的 MTTDL 是多少？若重新复制只要 $1$ 小时呢？
::: solution
$\lambda = 10^{-5}$（每小时），$\mu = 1/24$。由 [[#eq-mttdl]]，$\mathrm{MTTDL} = (3 \times 10^{-5} + 0.04167)/(2 \times 10^{-10}) \approx 2.08 \times 10^8$ 小时，约 $23{,}800$ 年。修复时间取 $1$ 小时则长 $24$ 倍。对 MTTF 的二次依赖和对 MTTR 的反比依赖，正是分布式存储系统要快速、并行地从多个来源重新复制丢失数据的原因（[[distributed-systems/distributed-storage]]）。

但这些数字乐观得离谱。它们假定故障相互独立，而同一批次的磁盘会一起失效，一次电源故障会带走整个机柜，一个软件缺陷或一条操作员命令可以一次删掉所有副本。实践中，相关故障才是数据丢失的主因：这正是副本要被安置在不同故障域（机柜、楼宇、地域）的原因，也正是备份——线上系统中的缺陷无法触及的拷贝——仍然必要的原因。
:::
:::

## 故障检测

由 [[distributed-systems/system-models#thm-indistinguishable]]，异步系统中的任何算法都不可能既完备又准确地检测崩溃。Tushar Chandra 与 Sam Toueg（1996）把这个否定结果变成了一种正面理论：不再要求完美的检测，而是规定检测器*可以错到什么程度*，并问它对哪些问题已经够用。

::: definition 不可靠故障检测器 {#def-fd}
**故障检测器**是每个进程上的一个模块，它输出一个它当前**怀疑**已经崩溃的进程集合。其性质：
- **强完备性**：最终每个崩溃的进程都被每个正确进程永久怀疑；
- **强准确性**：没有进程会在崩溃之前被怀疑；
- **弱准确性**：存在某个正确进程从不被怀疑；
- **最终强准确性**：存在一个时刻，此后没有正确进程被任何正确进程怀疑；
- **最终弱准确性**：存在一个时刻，此后存在某个正确进程从不被任何正确进程怀疑。

**完美**检测器 $\mathcal{P}$ 具有强完备性和强准确性；**最终完美**检测器 $\Diamond\mathcal{P}$ 具有强完备性和最终强准确性；**最终强**检测器 $\Diamond\mathcal{S}$ 具有强完备性和最终弱准确性。
:::

Chandra 与 Toueg 证明，只要多数进程正确，共识就可用 $\Diamond\mathcal{S}$ 求解；Chandra、Hadzilacos 与 Toueg（1996）证明 $\Diamond\mathcal{S}$——等价地，**最终领导者**检测器 $\Omega$，它最终在每个正确进程输出同一个正确进程——是共识的*最弱*故障检测器。这精确地说明了为什么 Paxos 和 Raft 恰好需要一个最终正确的领导者选举机制：它们的选举实现 $\Omega$，而 FLP 说明更弱的东西都无济于事。在部分同步下，一个简单的心跳协议就能实现 $\Diamond\mathcal{P}$。

::: algorithm 带自适应超时的心跳 {#alg-heartbeat}
每个进程每隔 $\eta$ 个时间单位向其他每个进程发送一次心跳。进程 $p$ 为每个 $q$ 保存一个超时 $T_q$（初始为 $T_0$）以及收到 $q$ 上一次心跳的时刻。
1. 若在距上一条 $q$ 的心跳 $T_q$ 之内没有新的心跳到达，就把 $q$ 加入怀疑集合。
2. 收到来自某个被怀疑的 $q$ 的心跳时：把 $q$ 移出怀疑集合，并置 $T_q \gets 2T_q$（这次怀疑是误判）。
:::

::: proposition 心跳实现最终完美检测器 {#prop-heartbeat}
在一个部分同步系统中，若某个未知时刻 GST 之后每条消息都在 $\Delta$ 内投递、每个正确进程都按时发送心跳，则 [[#alg-heartbeat]] 满足强完备性和最终强准确性。
:::

::: proof
*完备性。* 崩溃的进程 $q$ 只发送了有限多条心跳。在最后一条被投递（或丢失）之后，每个正确进程 $p$ 等过 $T_q$ 便怀疑 $q$；由于不再有心跳到来，$q$ 再也不会被移出。

*最终准确性。* 固定正确进程 $p$ 与 $q$。GST 之后，来自 $q$ 相邻两次心跳到达 $p$ 的间隔至多 $\eta + \Delta$，所以对 $q$ 的每次怀疑都会因一条心跳的到达而解除，并把 $T_q$ 翻倍；超时从不缩小。GST 之后的怀疑只可能发生在 $T_q < \eta + \Delta$ 期间，而每一次都使 $T_q$ 翻倍，所以 GST 之后 $p$ 对 $q$ 的怀疑至多 $\lceil \log_2((\eta + \Delta)/T_0) \rceil$ 次，其中最后一次也终将解除；从那以后 $p$ 永不怀疑 $q$。进程对是有限多个，所以经过某个时刻后，没有正确进程会怀疑任何正确进程。
:::

生产系统更愿意输出一个怀疑的程度，而不是简单的“是”或“否”。**φ 累积故障检测器**（φ accrual，Hayashibara 及合作者，2004）被 Cassandra 和 Akka 使用，它从近期历史估计心跳间隔的分布，并输出
$$
\varphi(t) = -\log_{10} \Prob(\text{下一条心跳晚于距上一条 } t \text{ 的时刻到达}),
$$
于是 $\varphi = 1$ 表示活着的进程有 $10\%$ 的可能迟到这么久，$\varphi = 3$ 表示 $0.1\%$ 的可能。每个应用选择自己的阈值，在检测速度与误怀疑之间权衡。

::: example 一个 φ 值 {#ex-phi}
心跳间隔建模为均值 $1$ s 的指数分布。距上一条心跳已过去 $5$ s。$\varphi$ 是多少？要等多久才有 $\varphi = 8$？
::: solution
对以秒计的 $t$ 有 $\Prob(\text{间隔} > t) = e^{-t}$，所以 $\varphi(t) = -\log_{10} e^{-t} = t \log_{10} e = t / \ln 10$。$t = 5$ 时 $\varphi \approx 2.17$：活着的进程迟到这么久的概率为 $e^{-5} \approx 0.7\%$。要 $\varphi = 8$ 需要 $t = 8 \ln 10 \approx 18.4$ s。真实实现通常改用正态分布拟合最近的间隔，其更薄的尾部使 $\varphi$ 在延迟超过几个标准差后增长得快得多。
:::
:::

### 租约与栅栏

故障检测器的错误对共识是无害的——无论检测器说什么，Paxos 和 Raft 都是安全的——但对任何授予**排他**权利的东西都是危险的。**租约**（lease）是一把带到期时间的锁：持有者可以在租约到期前行动，而锁服务在此之前（外加时钟漂移的裕量）不会把它授予任何别人。租约能容忍持有者崩溃，因为锁会自行释放；但开头那个故事显示了它的弱点：持有者可能并不*知道*自己的租约已过期，因为它被暂停了，或者它的时钟不准，或者那条告诉存储服务该怎么做的消息在网络里被拖延到了过期之后。

::: definition 栅栏令牌 {#def-fencing}
锁服务在每次授予锁时发一个**栅栏令牌**（fencing token）：一个随每次授予递增的数（例如授予被提交时的 Raft 日志索引或任期号）。客户端在向受保护资源发出的每个请求中都带上该令牌。资源记住它见过的最大令牌，并**拒绝**任何携带较小令牌的请求。
:::

::: proposition 栅栏使过期持有者人畜无害 {#prop-fencing}
若资源一次处理一个请求并执行 [[#def-fencing]] 的规则，那么它一旦接受了令牌为 $t$ 的请求，就永不接受来自更早授予（其令牌小于 $t$）的持有者的请求。因此，被接受的请求按授予次序来自各个持有者；租约被取代的持有者，在其继任者发出请求之后就再也无法修改资源了。
:::

::: proof
资源记住的最大值 $\mathit{max}$ 从不减小，接受 $t$ 之后它至少为 $t$。携带令牌 $t' < t$ 的请求在其后到达，有 $t' < t \le \mathit{max}$，于是被拒绝。令牌随授予递增，所以更早的授予有更小的令牌。
:::

在开头的故事里，客户端 1 的令牌是 $33$，客户端 2 的是 $34$；一旦客户端 2 的写入被接受，客户端 1 携带令牌 $33$ 的迟到写入就被拒绝。栅栏把最后一道检查移到了唯一按序看到所有请求的地方——资源本身——而不是相信每个客户端对时间的判断。同样的思想体现为 Raft 的任期号，它让跟随者能够拒绝被废黜领导者的消息。

::: warning 超时告诉你的是过去，不是现在
“我确认过我的租约有效，所以我可以写”是一个检查–行动竞争：在检查与写入之间，进程可能暂停任意长的时间（垃圾回收、缺页、调度、虚拟机暂停），网络也可能把写入拖延。先读时钟、与租约到期时间比较、然后执行一次远程动作的代码，对该动作生效时租约是否仍然有效毫无保证。只有在*资源处*进行的检查——栅栏令牌、带版本号的条件写入——才能关掉这扇窗口。
:::

## 状态机复制的实践

共识给出一个复制日志；[[distributed-systems/consensus#def-smr]] 把日志变成复制的服务。要让副本保持完全一致，服务必须满足 Fred Schneider 在 1990 年那篇综述中列出的若干要求。

- **确定性。** 每个副本都必须从相同的命令计算出相同的新状态和输出。读时钟、生成随机数、遍历次序随机化的哈希表、或在多个线程上运行命令都会破坏它。领导者可以在记录*之前*消除非确定性——记录“把 $x$ 置为 $1717171717$”而不是“把 $x$ 置为当前时间”——或者各副本严格顺序地执行命令。
- **命令恰好执行一次。** 超时重试的客户端可能把它的命令送进日志两次。[[distributed-systems/remote-communication#alg-dedup]] 的去重表必须成为复制状态的一部分，这样每个副本——包括未来的领导者——都能认出重复。
- **有界日志。** 除非副本定期对状态机做**快照**并丢弃快照已覆盖的日志前缀，日志将永远增长；落后或新加入的副本随后通过接收快照被更新到最新。
- **再配置。** 更换机器会改变副本集合，从而改变多数派的含义。一步到位的更换可能造出两个不相交的多数派（一个属于旧配置，一个属于新配置）；Raft 的联合共识与单服务器变更、以及 Vertical Paxos，是为安全地完成这件事设计的协议。
- **线性一致的读。** 正如 [[distributed-systems/consensus]] 中的警告所解释的，读必须经由日志，或者由多数派确认，除非假定了带时钟漂移界限的租约。

复制只掩蔽独立的故障。若某条命令触发了一个使服务崩溃的缺陷，每个副本都会应用这条命令并且每个副本都会崩溃——“致命查询”。防御手段包括：在命令进入日志之前验证它、在不同副本上运行不同的软件版本、以及对自动重启进行限速。

## 拜占庭故障

到目前为止，有缺陷的进程只是停下来或丢失消息。**拜占庭**进程（出自兰波特（Lamport）、Shostak 与 Pease 1982 年的论文）则什么都干得出来：发送错误的值、给不同的进程发送不同的值（**两面三刀**，equivocate）、或与其他有缺陷的进程串通。当进程由互不信任的各方运营（区块链、跨组织系统）、攻击者可能控制某些机器、以及未被检测出的硬件故障可能造成任意行为（飞行控制、航天器）时，拜占庭模型就很重要。

::: definition 拜占庭协议 {#def-byzantine}
$n$ 个进程各有一个输入值；其中至多 $f$ 个是拜占庭的。其余的称为**正确的**。进程通过可靠、认证的点对点链路通信（接收方知道链路上每条消息是哪个进程发来的，但消息不携带第三方能够核验的签名——**口头消息**）。若一个算法满足以下条件，则称它解决了**拜占庭协议**问题：
- **一致性**：所有正确进程决定相同的值；
- **有效性**：若所有正确进程的输入都是 $v$，它们就决定 $v$；
- **终止性**：每个正确进程都作出决定。

在**拜占庭将军**（拜占庭广播）变体中，有一个进程是**指挥官**，它发送一个值；一致性同上，有效性则表述为：若指挥官是正确的，每个正确进程都决定指挥官的值。
:::

有效性必须用正确进程的输入来表述：拜占庭进程的“输入”没有意义。两个变体关系密切：有了广播，每个进程广播自己的输入，每个正确进程对它得到的各个值取多数作决定。

### 三个进程无法容忍一个叛徒

::: theorem $n \le 3f$ 时不存在拜占庭协议 {#thm-3f}
在口头消息的同步模型中，若 $3 \le n \le 3f$，则没有确定性算法能在 $n$ 个进程中解决拜占庭协议问题。（当 $n \le 2$ 且 $f \ge 1$ 时问题是平凡的，因为可能只剩一个正确进程，它可以决定自己的输入。）
:::

::: proof
*三个进程、一个故障。* 设某算法为进程 $A$、$B$、$C$ 在 $f = 1$（输入取自 $\set{0,1}$）时解决了问题。每个进程运行一个程序，并通过链路分别连到另外两个。构造一个六个进程 $A_0, B_0, C_0, A_1, B_1, C_1$ 的环，按圈

$$
A_0 - B_0 - C_0 - A_1 - B_1 - C_1 - A_0,
$$

连接，其中 $X_i$ 运行 $X$ 的程序、输入为 $i$，它的“通往 $Y$”的链路接到它那个是 $Y$ 的拷贝的邻居上。（检验：$A_0$ 的邻居是 $B_0$ 和 $C_1$，$B_0$ 的是 $A_0$ 和 $C_0$，依此类推——每个拷贝都恰有一个其余每种类型的邻居。）这个环不是该算法的合法系统，但它是一个由确定性程序组成的良定义同步系统，因而有唯一的执行 $S$。我们把 $S$ 与原系统的三次合法执行作比较。

- $\alpha_1$：$A$ 与 $B$ 正确、输入 $0$；$C$ 是拜占庭的。$C$ 在它通往 $A$ 的链路上恰好发送 $S$ 中 $C_1$ 发给 $A_0$ 的东西，在它通往 $B$ 的链路上恰好发送 $C_0$ 发给 $B_0$ 的东西。$C$ 可以这样做：模拟除 $A_0$ 和 $B_0$ 以外的整个环，把它从 $A$ 和 $B$ 收到的消息喂给这场模拟。对轮归纳可知，$A$ 与 $B$ 在 $\alpha_1$ 中收到的与 $A_0$、$B_0$ 在 $S$ 中收到的完全相同，于是它们有相同的视图。在 $\alpha_1$ 中两个正确进程输入都是 $0$，由有效性与终止性它们决定 $0$。所以在 $S$ 中 $A_0$ 与 $B_0$ 决定 $0$。
- $\alpha_2$：$B$ 与 $C$ 正确、输入 $1$；$A$ 是拜占庭的，对 $B$ 扮演 $A_1$，对 $C$ 扮演 $A_0$。同理，$B$ 与 $C$ 分别有 $B_1$、$C_1$ 的视图，由有效性决定 $1$。所以在 $S$ 中 $B_1$ 与 $C_1$ 决定 $1$。
- $\alpha_3$：$C$ 正确、输入 $1$，$A$ 正确、输入 $0$，$B$ 是拜占庭的，对 $C$ 扮演 $B_1$、对 $A$ 扮演 $B_0$。于是 $C$ 与 $A$ 分别有 $S$ 中 $C_1$ 与 $A_0$ 的视图，而它们在环上相邻。于是 $C$ 决定 $1$、$A$ 决定 $0$——两个正确进程不一致，违反一致性。

*一般的 $n \le 3f$。* 设算法 $\mathcal{A}$ 在 $3 \le n \le 3f$ 时解决 $n$ 个进程、$f$ 个故障的问题。把 $n$ 个进程分成三个非空组 $G_A, G_B, G_C$，每组至多 $f$ 个。让三个进程 $A, B, C$ 各模拟一组：$A$ 运行 $G_A$ 的全部程序，组内消息在内部投递，组间消息经它的链路发送，依此类推；组内所有成员都取模拟者的输入。一个拜占庭的模拟者对应于它整组都是拜占庭的——至多 $f$ 个进程，这是 $\mathcal{A}$ 所能容忍的。若模拟者 $A$ 决定（比如说）它组里第一个成员所作的决定，那么 $\mathcal{A}$ 的一致性、有效性与终止性就给出一个三个进程、容忍一个拜占庭进程的算法，而我们刚刚证明它不存在。
:::

这个环论证出自 Michael Fischer、Nancy Lynch 与 Michael Merritt（1986），他们称之为一个“容易的不可能性证明”；兰波特（Lamport）、Shostak 与 Pease 原始的论证（1982）用不同的证明得到了同样的界。直觉是：三个进程时，收到另外两个发来的相互矛盾报告的正确的进程无法分辨是谁在说谎。注意口头消息的角色：拜占庭进程可以把“$C_1$ 说过的话”原样演给 $A$ 看，因为消息中没有任何东西能证明是谁原创的。使用不可伪造的**签名消息**后，无论有多少叛徒，拜占庭广播都可解（Dolev 与 Strong，1983，$f + 1$ 轮），不过即使在部分同步系统中，即使有签名，共识的 $3f + 1$ 界仍然存在（Dwork、Lynch 与 Stockmeyer，1988）。

### 口头消息算法

兰波特（Lamport）、Shostak 与 Pease 还给出了匹配 $n \ge 3m + 1$（$m$ 个叛徒）的算法。其思想是递归：每个中尉转发自己听到的消息，所有人取多数。

::: algorithm 口头消息算法 OM($m$) {#alg-om}
设 $\mathrm{majority}(v_1, \dots, v_k)$ 为超过一半的 $v_i$ 持有的值，若不存在这样的值则为默认值 "retreat"。
- **OM(0)**：指挥官把自己的值发给每个中尉；每个中尉使用它收到的值（什么都没收到则用 "retreat"）。
- **OM($m$)**，$m > 0$：(1) 指挥官把自己的值发给每个中尉。(2) 对每个中尉 $j$，令 $v_j$ 为 $j$ 收到的值（或 "retreat"）；$j$ 在 OM($m - 1$) 中充当指挥官，把 $v_j$ 发给其余 $n - 2$ 个中尉。(3) 每个中尉 $i$：对每个 $j \ne i$，令 $v_j$ 为它在第 2 步中通过 OM($m-1$) 就 $j$ 得到的值，取 $v_i$ 为它在第 1 步中直接收到的值，并使用 $\mathrm{majority}(v_1, \dots, v_{n-1})$。
:::

::: lemma 忠诚的指挥官必被服从 {#lem-om-ic2}
对任意 $m$ 和 $k$，只要将军人数超过 $2k + m$ 而叛徒至多 $k$ 个，OM($m$) 就满足有效性（指挥官忠诚时，每个忠诚的中尉都采用指挥官的值）。
:::

::: proof
对 $m$ 归纳。$m = 0$ 时，忠诚的指挥官向所有人发送 $v$，忠诚的中尉采用它。$m > 0$ 时，忠诚的指挥官把 $v$ 发给全部 $n - 1$ 个中尉。每个忠诚的中尉 $j$ 随后在 $n - 1$ 个将军中充当指挥官运行 OM($m - 1$)，而 $n - 1 > 2k + (m - 1)$，所以由归纳假设，每个忠诚的中尉 $i$ 对每个忠诚的 $j$ 都得到 $v_j = v$。$n - 1$ 个中尉中至多 $k$ 个是叛徒，而 $n - 1 > 2k$，所以忠诚者是多数；于是中尉 $i$ 处的值 $v_1, \dots, v_{n-1}$ 中多数等于 $v$，$i$ 采用 $v$。
:::

::: theorem $n > 3m$ 时 OM($m$) 解决拜占庭将军问题 {#thm-om}
若将军人数超过 $3m$ 而叛徒至多 $m$ 个，OM($m$) 满足一致性和有效性。
:::

::: proof
对 $m$ 归纳。$m = 0$ 时没有叛徒，两个性质都显然成立。设 $m > 0$。若指挥官忠诚，由 [[#lem-om-ic2]] 取 $k = m$（因为 $n > 3m = 2m + m$）得有效性，而有效性蕴含一致性。若指挥官是叛徒，则至多 $m - 1$ 个中尉是叛徒，而中尉有 $n - 1 > 3m - 1 \ge 3(m - 1)$ 个；于是由归纳假设，第 2 步中的每次 OM($m-1$) 运行都满足一致性和有效性。由一致性，所有忠诚的中尉对每个不是自己的中尉 $j \neq$ 都得到相同的值 $v_j$；而对忠诚的 $j$，OM($m-1$) 的有效性告诉我们其他忠诚的中尉得到的恰好是 $j$ 直接收到的值，也就是 $j$ 为自己采用的那个 $v_j$。所以每个忠诚的中尉持有相同的向量 $(v_1, \dots, v_{n-1})$，算出相同的多数。
:::

OM($m$) 运行 $m + 1$ 轮——这是最优的，理由与崩溃情形的 $f + 1$ 下界相同——但发送 $O(n^{m+1})$ 条消息，因为每条消息都要沿一棵深度为 $m$ 的树转发。它是一个可能性证明，而不是实用协议。一次模拟显示了这条界在起作用；叛徒采用一个简单的策略：对偶数编号的将军说实话，对奇数编号的说谎：

```python
from collections import Counter

def majority(values):
    """多数值；若不存在严格多数则返回默认值 "retreat"。"""
    v, c = Counter(values).most_common(1)[0]
    return v if c > len(values) / 2 else "retreat"

def om(m, commander, lieutenants, value, traitors):
    """口头消息算法 OM(m)。返回 {中尉: 它对该指挥官采用的值}。"""
    def sent(to):                                    # 指挥官对中尉 `to` 说的话
        if commander in traitors and to % 2 == 1:    # 叛徒对奇数编号的将军说谎
            return "retreat" if value == "attack" else "attack"
        return value
    received = {l: sent(l) for l in lieutenants}
    if m == 0:
        return received
    result = {}
    sub = {j: om(m - 1, j, [l for l in lieutenants if l != j], received[j], traitors)
           for j in lieutenants}                     # 每个中尉 j 转发自己收到的值
    for i in lieutenants:
        votes = [received[i]] + [sub[j][i] for j in lieutenants if j != i]
        result[i] = majority(votes)
    return result

def run(n, m, traitors, value="attack"):
    out = om(m, 0, list(range(1, n)), value, set(traitors))
    loyal = {i: v for i, v in out.items() if i not in traitors}
    print(f"n={n} m={m} traitors={sorted(traitors)}  loyal decisions={loyal}")

run(4, 1, {3})          # 忠诚的指挥官，一个叛徒中尉
run(4, 1, {0})          # 叛徒指挥官
run(7, 2, {0, 6})       # m = 2 且 n = 7 > 3m
run(3, 1, {2})          # n = 3 = 3m：IC2 可能失效
```

```console
$ python3 om.py
n=4 m=1 traitors=[3]  loyal decisions={1: 'attack', 2: 'attack'}
n=4 m=1 traitors=[0]  loyal decisions={1: 'retreat', 2: 'retreat', 3: 'retreat'}
n=7 m=2 traitors=[0, 6]  loyal decisions={1: 'retreat', 2: 'retreat', 3: 'retreat', 4: 'retreat', 5: 'retreat'}
n=3 m=1 traitors=[2]  loyal decisions={1: 'retreat'}
```

::: example 手推四个将军的 OM(1) {#ex-om}
解释输出的第一、第二和第四行。
::: solution
*忠诚的指挥官，叛徒 $3$。* 指挥官向 $1, 2, 3$ 发送 "attack"。第 2 步中，忠诚的 $2$ 转发 "attack"；叛徒 $3$ 向 $2$（偶数）转发 "attack"、向 $1$（奇数）转发 "retreat"。中尉 $1$ 持有（来自指挥官的 attack、经 $2$ 的 attack、经 $3$ 的 retreat）：多数是 attack。中尉 $2$ 持有（attack、经 $1$ 的 attack、经 $3$ 的 attack）：attack。有效性成立。

*叛徒指挥官。* 它向 $2$ 发 "attack"，向 $1$ 和 $3$ 发 "retreat"。所有中尉都忠诚并如实转发，于是每个中尉持有相同的多重集合 $\set{\text{retreat}, \text{attack}, \text{retreat}}$——中尉 $i$ 自己的值加上另外两人的转发值，而这两者合起来正是指挥官发出的三个值。所有人都采用 "retreat"：一致性成立，尽管他们没有进攻。有效性不适用，因为指挥官是叛徒。

*三个将军。* $n = 3$、叛徒是 $2$ 时，中尉 $1$ 持有（来自指挥官的 attack、经 $2$ 的 retreat）：没有多数，于是取默认值 "retreat"——尽管指挥官忠诚且说了 "attack"。有效性失效，正如 [[#thm-3f]] 断言对某种策略它必然失效。

第三行中，指挥官和中尉 $6$ 都是叛徒，而五个忠诚的中尉仍然达成了一致，这就是 $m = 2$ 时的 [[#thm-om]]。他们一致于 "retreat"，因为叛徒指挥官对六个中尉中的三个（$1$、$3$ 和 $5$）发了 "retreat"，对其余三个发了 "attack"；两边都没有多数，于是递归转发让每个忠诚的中尉得到同样的图景，默认值获胜。
:::

### 实用拜占庭容错

Miguel Castro 与 Barbara Liskov 的 **PBFT**（1999）使拜占庭容错在部分同步网络的状态机复制中变得实用：它永远安全，并且像 Paxos 一样，一旦网络守时就活跃。它使用 $n = 3f + 1$ 个副本、带签名或 MAC 认证的消息、以及大小 $2f + 1$ 的法定数量。正常运行时，由领导者（primary）在 **pre-prepare** 消息中为每个请求指定一个序号；副本广播 **prepare** 消息，集齐 $2f + 1$ 条相符 prepare（含 pre-prepare）的副本便知道没有正确副本能在该序号上准备过另一个请求；随后副本广播 **commit** 消息，并在收到 $2f + 1$ 条 commit 后执行该请求。**视图更换**（view change）替换失效的领导者。整个设计建立在一条计数事实之上。

::: proposition 拜占庭法定数量相交 {#prop-bft-quorum}
在 $n = 3f + 1$ 个副本中，任意两个大小 $2f + 1$ 的法定数量至少有 $f + 1$ 个副本相同，因而至少有一个*正确*副本相同。
:::

::: proof
$\lvert Q_1 \cap Q_2 \rvert \ge \lvert Q_1\rvert + \lvert Q_2\rvert - n = 2(2f + 1) - (3f + 1) = f + 1$。至多 $f$ 个副本有故障，所以交集中至少有一个是正确的。正确副本不会发送相互矛盾的消息（比如对两个不同的请求在同一序号和视图上做 prepare），所以两个法定数量不可能同时为相互矛盾的决定作证。
:::

大小 $2f + 1$ 也从另一侧被强制：一个副本最多只能等待 $n - f$ 条消息，因为 $f$ 个副本可能永远不作答复，于是法定数量的大小为 $n - f$；而其中两个必须共享一个正确副本：$2(n - f) - n \ge f + 1$，即 $n \ge 3f + 1$（习题 8）。PBFT 每个请求需要 $O(n^2)$ 条消息，因为每个副本都要向其他所有副本广播；HotStuff（2019）等后续协议用门限签名把通信量降到线性。**中本聪共识**——比特币（2008）的协议——在开放的、无需许可的成员资格下走了另一条路：工作量证明使投票权与算力成正比，在一个区块之上堆叠的区块越多，就以压倒性的概率达成一致，而非最终确定。

::: quiz
某系统使用 PBFT，必须容忍 $2$ 个拜占庭副本。最少需要多少个副本？客户端在相信一个结果之前必须等到多少条相符的答复？
- [ ] $5$ 个副本；$3$ 条答复
- [x] $7$ 个副本；$3$ 条答复
- [ ] $7$ 个副本；$5$ 条答复
- [ ] $6$ 个副本；$4$ 条答复
::: solution
$n = 3f + 1 = 7$。客户端在 $f + 1 = 3$ 个副本给出相同答复时接受该结果：其中至少有一个是正确的，而正确副本只返回达成一致的那个执行的输出。（在协议内部，副本使用大小 $2f + 1 = 5$ 的法定数量；客户端的阈值较小就够了，因为它只需要一个正确的见证者，而不需要交集。）
:::
:::

## 恢复

用复制掩蔽失效是一种策略；另一种是**恢复**：失效之后恢复到一个正确状态再继续。进程定期把状态**检查点**（checkpoint）到稳定存储，崩溃后从最近的检查点重启。在分布式计算中这很微妙，因为各进程的检查点必须彼此吻合：若进程 $q$ 的检查点记录了收到某个消息、而进程 $p$ 的检查点没有记录发送它，那么把两者都回滚到这些检查点会得到一个不可能的状态——不一致的割（[[distributed-systems/time-clocks#def-cut]]）。

**非协调检查点**下每个进程独立打检查点，恢复时寻找构成一致割的最新一组检查点。这会引起连锁——**多米诺效应**——把进程越滚越远，可能一路回到起点，因为每次回滚都会撤销其他进程检查点所依赖的那些发送。**协调检查点**通过取一致快照避免这一点，例如用 Chandy–Lamport 算法（[[distributed-systems/time-clocks#alg-chandy-lamport]]）；流处理器就是这样打检查点的（[[distributed-systems/data-processing]]）。**消息日志**记录每个进程收到的消息（或它们的次序），使崩溃的进程能从最后一个检查点确定性地重放到崩溃前的精确状态而不回滚任何别人——与重放数据库的预写式日志是同一思想（[[databases/recovery]]）。

::: example 多米诺效应 {#ex-domino}
进程 $P$ 与 $Q$ 独立打检查点。依次发生：$P$ 打检查点 $p_1$；$P$ 向 $Q$ 发送 $m_1$；$Q$ 收到 $m_1$ 并打检查点 $q_1$；$Q$ 向 $P$ 发送 $m_2$；$P$ 收到 $m_2$ 并打检查点 $p_2$；$P$ 向 $Q$ 发送 $m_3$；$Q$ 收到 $m_3$ 并打检查点 $q_2$；$Q$ 向 $P$ 发送 $m_4$；随后 $P$ 在下一个检查点之前崩溃。各进程必须回滚到哪些检查点？
::: solution
$P$ 从 $p_2$——它最近的检查点——重启。对 $(p_2, q_2)$ 不一致：$q_2$ 记录了收到 $P$ 在 $p_2$ 之后发送的 $m_3$。所以 $Q$ 必须回滚到 $q_1$。于是 $(p_2, q_1)$ 不一致：$p_2$ 记录了收到 $Q$ 在 $q_1$ 之后发送的 $m_2$。所以 $P$ 必须回滚到 $p_1$。再看 $(p_1, q_1)$：$q_1$ 记录了收到在 $p_1$ 之后发送的 $m_1$——又不一致，于是 $Q$ 必须回滚到初始状态。最后（$Q$ 的初始状态，$p_1$）是一致的，因为 $p_1$ 没有记录任何消息。一次崩溃几乎撤销了两个进程的全部工作：每个检查点都被一条恰好跨越它的消息“污染”了。若用协调检查点，就会把 $p_2$ 与 $q_2$ 作为一个一致快照记录下来，并把 $m_3$ 记为正在途中。
:::
:::

兰波特（Lamport）、Robert Shostak 与 Marshall Pease 在《拜占庭将军问题》（"The Byzantine generals problem"，《ACM TOPLAS》，1982）中提出了拜占庭将军问题，此前 1980 年的论文《在有故障的情况下达成一致》（"Reaching agreement in the presence of faults"，Pease、Shostak 与兰波特）已证明了 $3f+1$ 界；这项工作源自 SRI 为 NASA 研制的 SIFT 容错飞行控制计算机。Danny Dolev 与 Ray Strong 在 1983 年给出了认证算法，Michael Fischer、Nancy Lynch 与 Michael Merritt 在《分布式共识问题的容易不可能性证明》（"Easy impossibility proofs for distributed consensus problems"，1986）中给出了环证明。Fred Schneider 的《用状态机方法实现容错服务：综述》（"Implementing fault-tolerant services using the state machine approach: a tutorial"，《ACM Computing Surveys》，1990）把状态机复制系统化。Tushar Chandra 与 Sam Toueg 的不可靠故障检测器，以及加上 Vassos Hadzilacos 的共识最弱检测器，发表于 1996 年的《Journal of the ACM》。Miguel Castro 与 Barbara Liskov 在 OSDI 1999 上报告了 PBFT。Algirdas Avižienis、Jean-Claude Laprie、Brian Randell 与 Carl Landwehr 的可信性分类学发表于 2004 年，与 Naohiro Hayashibara 及合作者的 φ 累积故障检测器同年。中本聪（Nakamoto）的比特币论文发表于 2008 年。
:::

## 后续内容

分布式存储系统（[[distributed-systems/distributed-storage]]）把本章的算术付诸实践：跨故障域安置副本、快速重新复制与反熵。[[distributed-systems/distributed-transactions]] 会遇到复制无法单独解决的一种故障——协调者在提交中途崩溃。拜占庭故障与对手连接着 [[security/security-principles]]，以及使认证拜占庭模型成为可能的 [[cryptography/signatures]] 中的密码签名。

::: summary
- **故障**产生**错误**，错误可能导致**失效**；容错要么掩蔽故障、要么从错误中恢复、要么安全失效。
- 可用性是 $\mathrm{MTTF}/(\mathrm{MTTF} + \mathrm{MTTR})$；在独立性假设下，两个副本大约每 $\mathrm{MTTF}^2/(2\,\mathrm{MTTR})$ 丢失一次数据（[[#thm-mttdl]]）——但相关故障才是主导。
- 故障检测器按**完备性**与**准确性**分类；带递增超时的心跳在部分同步下给出 $\Diamond\mathcal{P}$（[[#prop-heartbeat]]），而 $\Omega$（最终领导者）是共识的最弱检测器。
- 租约需要**栅栏令牌**，并在资源处检查（[[#prop-fencing]]）；超时对现在一无所知。
- 状态机复制需要**确定性**、复制的去重、快照与安全的再配置。
- 口头消息的**拜占庭协议**需要 $n \ge 3f + 1$（[[#thm-3f]]）；**OM($m$)** 以指数消息代价达到它（[[#thm-om]]）；签名对广播有帮助，对部分同步共识则不然。
- **PBFT** 使用 $3f + 1$ 个副本和大小 $2f + 1$ 的法定数量，它们共享一个正确副本（[[#prop-bft-quorum]]）。
- **恢复**使用一致（协调）检查点或消息日志，以避免多米诺效应。
:::

## 习题

::: exercise 几个九 {level=1 check="0.0005*525600"}
$99.95\%$ 的可用性允许每年（按 365 天计）多少分钟停机？（填入分钟数。）
::: solution
一年有 $365 \times 24 \times 60 = 525{,}600$ 分钟；其 $0.05\%$ 是 $262.8$ 分钟，约 $4.4$ 小时。
:::
:::

::: exercise 由 MTTF 与 MTTR 计算可用性 {level=1 check="1000/1002"}
某服务器平均每 $1000$ 小时失效一次，修复需要 $2$ 小时。它的可用性是多少？（填入分数。）
::: solution
由 [[#eq-availability]]，$A = 1000/(1000 + 2) \approx 0.998$。若把修复自动化到 $2$ 分钟，无需改进任何硬件就能得到 $1000/(1000 + 1/30) \approx 0.99997$。
:::
:::

::: exercise PBFT 规模 {level=1 check="7"}
PBFT 容忍 $2$ 个拜占庭故障需要多少副本？（填入数量。）
::: solution
$3f + 1 = 7$。法定数量大小 $2f + 1 = 5$；容忍 $2$ 个故障的崩溃容错协议只需 $5$ 个副本。
:::
:::

::: exercise 手算 OM(1) {level=2}
四个将军；指挥官忠诚，下令 "retreat"，中尉 $1$ 是叛徒，向所有人转发 "attack"。OM(1) 中每个忠诚的中尉决定什么？再假设中尉 $1$ 和 $2$ 都是叛徒并转发 "attack"。可能出什么问题？[[#thm-om]] 的哪个假设被违反了？
::: solution
*一个叛徒。* 中尉 $2$ 和 $3$ 各持有：retreat（直接）、attack（经 $1$）、retreat（经另一个忠诚中尉）。多数是 retreat：有效性成立。

*两个叛徒。* 中尉 $3$ 持有：retreat（直接）、attack（经 $1$）、attack（经 $2$）。多数是 attack——它违抗了一位忠诚的指挥官。$m = 1$ 时算法假定至多一个叛徒；四个将军中的两个叛徒需要 $n > 3 \times 2 = 6$，以及 OM(2)。
:::
:::

::: exercise MTTDL {level=2 check="(3/10000 + 1/10)/(2/10000^2)"}
两个副本的 MTTF 各为 $10{,}000$ 小时，重新复制需要 $10$ 小时。用精确公式 [[#eq-mttdl]]，MTTDL 是多少小时？（填入小时数。）
::: solution
$\lambda = 10^{-4}$，$\mu = 0.1$：$(3 \times 10^{-4} + 0.1)/(2 \times 10^{-8}) = 0.1003 / (2 \times 10^{-8}) = 5.015 \times 10^6$ 小时，约 $572$ 年。近似式 $\mathrm{MTTF}^2/(2\,\mathrm{MTTR}) = 10^8/20 = 5 \times 10^6$ 与精确值相差不超过 $0.3\%$。
:::
:::

::: exercise φ 累积 {level=2 check="6/ln(10)"}
心跳间隔建模为均值 $0.5$ s 的指数分布。距上一条心跳已过去 $3$ s 时 $\varphi$ 是多少？（填入该值。）
::: solution
速率为每秒 $2$ 次，所以 $\Prob(\text{间隔} > 3) = e^{-6}$，$\varphi = -\log_{10} e^{-6} = 6/\ln 10 \approx 2.61$。
:::
:::

::: exercise 心跳并非完美 {level=3}
(a) 证明在 [[#prop-heartbeat]] 的部分同步模型中没有算法能实现完美故障检测器 $\mathcal{P}$。(b) 证明在 $\Delta$ 已知、心跳周期为 $\eta$ 的同步系统中，一个固定超时就能实现 $\mathcal{P}$，并给出最小的安全超时。
::: solution
(a) GST 之前系统的行为如同异步，所以 [[distributed-systems/system-models#thm-indistinguishable]] 的论证适用：取一次 $q$ 崩溃、$p$ 最终在时刻 $T$ 怀疑它（完备性）的执行；构造另一次 $q$ 正确、但它的所有消息都被延迟到 $T$ 之后、而 GST 晚于 $T$ 的执行。$p$ 有相同的视图，在 $T$ 怀疑 $q$，强准确性便告失效。

(b) 正确的 $q$ 相邻两次心跳相隔 $\eta$ 发出，每条到达耗时介于 $0$ 与 $\Delta$ 之间，所以到达之间的间隔至多 $\eta + \Delta$（前一条立刻到达，后一条等了 $\Delta$）。超时 $T = \eta + \Delta$（测量它时再加时钟漂移的裕量）永不怀疑正确进程——强准确性——并在崩溃进程最后一条心跳之后 $T$ 之内怀疑它——完备性。任何更小的超时都可能被恰好 $\eta + \Delta$ 的间隔愚弄。
:::
:::

::: exercise 为什么 $n - f$ 法定数量强制 $3f + 1$ {level=3}
在 $n$ 个副本、至多 $f$ 个有故障的拜占庭系统中，一个副本至多只能等待 $n - f$ 条消息（有故障的可能保持沉默）。证明：任意两个 $n - f$ 个副本的集合至少共享一个正确副本，当且仅当 $n \ge 3f + 1$。把它与 [[#thm-3f]] 联系起来。
::: solution
两个大小为 $n - f$ 的集合至少共享 $2(n - f) - n = n - 2f$ 个副本，最坏情况下恰好这么多（让它们尽可能少地重叠即可，当 $n - 2f \ge 0$ 时这是可行的）。最坏情况下全部 $f$ 个故障副本都在交集中，所以交集中有正确副本有保证，当且仅当 $n - 2f \ge f + 1$，即 $n \ge 3f + 1$。若 $n = 3f$，两个大小为 $2f$ 的法定数量可以恰好重叠在 $f$ 个副本上，而且全都故障：故障副本对一个法定数量说“$v$”，对另一个说“$w$”，两个法定数量看起来都完整而一致——这正是 [[#thm-3f]] 环论证所利用的两面三刀：拜占庭进程对它的两个邻居分别用不同的声音说话。
:::
:::

::: exercise 与存储服务配合的栅栏 {level=3}
用 Python 实现一个执行栅栏令牌的玩具存储服务器和一个发递增令牌的锁服务，重演本章开头那个故事：客户端 1 获得锁（令牌 $33$），暂停，租约到期，客户端 2 获得锁（令牌 $34$）并写入，然后客户端 1 写。证明客户端 1 的写入被拒绝。然后解释：若存储服务器本身用一个无领导者、最终一致的协议复制，为什么栅栏*不会*起作用。
::: solution
```python
class LockService:
    def __init__(self): self.token = 32
    def acquire(self, client):
        self.token += 1                      # 每次授予都发一个更大的新令牌
        return self.token

class Storage:
    def __init__(self): self.max_token, self.data = 0, None
    def write(self, token, value):
        if token < self.max_token:
            return f"rejected write {value!r} with stale token {token}"
        self.max_token, self.data = token, value
        return f"accepted write {value!r} with token {token}"

locks, disk = LockService(), Storage()
t1 = locks.acquire("client 1")               # 33；随后客户端 1 暂停，租约到期
t2 = locks.acquire("client 2")               # 34
print(disk.write(t2, "client 2's data"))
print(disk.write(t1, "client 1's data"))     # 客户端 1 醒来并写入
print("final:", disk.data)
```

```console
$ python3 fencing.py
accepted write "client 2's data" with token 34
rejected write "client 1's data" with stale token 33
final: client 2's data
```

[[#prop-fencing]] 的证明需要一个能按序看到所有请求并记住最大令牌的单点。在无领导者的存储中，客户端 2 的写可能到达副本 $A$ 和 $B$，而客户端 1 的迟到写到达副本 $C$——$C$ 没有见过令牌 $34$，于是接受 $33$。不同的副本现在持有不同的“最新”值，后来的合并（比如按墙钟时间戳最后写者胜）可能挑中客户端 1 的。栅栏需要资源执行一次线性一致的检查——对令牌的 compare-and-set——而在复制存储中这需要共识，或至少需要一个线性一致的寄存器（[[distributed-systems/replication-consistency#alg-abd]]）。
:::
