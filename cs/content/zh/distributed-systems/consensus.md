[[distributed-systems/replication-consistency]] 的主–备协议留下了一个漏洞。主副本停止响应时，必须有一个备份副本接管——但只能有一个，而且只有在所有副本都同意由它接管时才行。若两个备份副本各自认定自己是新主副本，系统就有了两个主副本，都接受写入：脑裂。若副本们不能就应用的更新次序达成一致，它们的状态就会分道扬镳。这两个问题的底层是同一个问题：一组进程——其中一些可能崩溃、消息也可能被延迟——如何能**就一个值取得一致**？

这就是**共识**问题，也是容错分布式计算的心脏。有了共识，集群才能就领导者、复制日志的下一条目、事务是否提交、谁持有锁取得一致。有了共识，我们可以复制任何确定性服务——键值存储、锁服务、数据库——使它在少数机器崩溃时仍能运行，并且表现得像单一线性一致的拷贝。

本章精确定义共识，并在同步系统中轻易地解决它。然后我们证明这个领域最著名的结果——**FLP 不可能性定理**：在纯异步系统中，只要有一个进程可能崩溃，就没有确定性算法能保证共识。实用协议对此的对策是永远**安全**、只在网络表现良好时**活跃**。我们研究两个最重要的协议：兰波特（Lamport）的 **Paxos**（附安全性证明），以及 Ongaro 与 Ousterhout 的 **Raft**（附安全性论证和一个小型模拟，在丢失消息与领导者崩溃的条件下运行）。我们在 [[distributed-systems/system-models]] 的模型中工作：崩溃停止或崩溃恢复进程、经重传变可靠的公平丢失链路、以及异步或部分同步。

## 共识问题

::: definition 共识 {#def-consensus}
$n$ 个进程 $p_1, \dots, p_n$ 各从一个集合 $V$ 中**提议**一个值，并可**决定**一个值。若在下述条件于至多 $f$ 个进程崩溃的每次执行中都成立，则称算法解决了**共识**问题：
- **终止性**：每个正确进程最终都作出决定；
- **一致性**：没有两个进程作出不同的决定；
- **有效性**：被决定的值由某个进程提议过；
- **完整性**：一个进程至多决定一次。
:::

如上表述的一致性**对全体进程一致**（uniform）：它既约束正确的进程，也约束作出决定后崩溃的进程。这正是复制所需要的——一个应用了某条命令随后崩溃的副本，不能应用了与别人不同的命令。有效性排除了“总是决定 $0$”这种平凡算法。一致性、有效性和完整性是**安全**性质：一旦违反，就在某个有限时刻被违反。终止性是**活性**性质：只有无穷执行才能违反它。

共识是**全序广播**（也称原子广播）的构件：全序广播要求所有正确进程以相同次序投递相同的消息。给定共识，为序列的每个位置运行一个实例：第 $k$ 个实例决定哪个消息被第 $k$ 个投递。反过来，给定全序广播，广播你的提议、把第一个投递的值决定下来，就解决了共识。两个问题是等价的（习题 9），而全序广播正是复制所需的东西。

::: definition 状态机复制 {#def-smr}
**状态机**是一个确定性服务：一组状态、一个初始状态、以及把状态映射到新状态和输出的命令。**状态机复制**在 $n$ 个副本的每一个上运行状态机的一份拷贝，并用全序广播（或一串共识实例，即**复制日志**）使每个副本按相同次序应用相同的命令。由于机器是确定性的，所有副本经历相同的状态并产生相同的输出。
:::

状态机复制由兰波特（Lamport）在 1978 年提出，并由 Fred Schneider 在 1990 年综述；[[distributed-systems/fault-tolerance]] 会回到它对确定性等各方面的要求。有了它，复制就归结为就日志达成一致——这正是本章各协议的工作。

### 同步系统中的共识

若消息延迟与处理速度都有界，进程就能按**轮**运行：每轮中每个进程先发送消息，然后接收该轮中所有未崩溃进程发给它的消息。一轮中途崩溃的进程可能已经把它的消息发给了某些进程而没来得及发给另一些。

::: algorithm FloodSet {#alg-floodset}
每个进程 $p_i$ 维护一个集合 $W_i$，初始为 $\set{v_i}$，即它自己的提议。
1. 对轮 $1, 2, \dots, f + 1$：把 $W_i$ 发送给其他每个进程；把 $W_i$ 更新为 $W_i \cup \bigcup_j W_j$，并对本轮收到的所有集合取并。
2. 第 $f + 1$ 轮之后，决定 $\min W_i$。
:::

::: theorem FloodSet 容忍 $f$ 次崩溃 {#thm-floodset}
在至多 $f$ 次崩溃故障的同步轮模型中，[[#alg-floodset]] 满足终止性、一致性、有效性和完整性。
:::

::: proof
终止性与完整性是显然的：每个正确进程恰好在第 $f + 1$ 轮之后决定一次。有效性：每个集合 $W_i$ 只含提议，因为它以一个提议起步、只靠与其他同类集合取并而增长。

对于一致性，注意至多 $f$ 个进程崩溃，所以在 $f + 1$ 轮中至少有一轮——设为第 $r$ 轮——没有任何进程崩溃。第 $r$ 轮中，每个在该轮开始时存活的进程都把自己的集合发给其他所有进程，而它们全都收到所有这些集合。于是第 $r$ 轮结束时，每个存活的进程都有相同的集合 $W = \bigcup_i W_i$（对该轮开始时存活进程取并）。此后每一轮，发出的每个集合都等于 $W$（只有第 $r$ 轮结束时存活的进程会发送，而它们都持有 $W$），取并不改变任何集合。因此每个坚持到第 $f + 1$ 轮结束的进程都持有 $W$，决定 $\min W$。
:::

这个界是紧的：当 $n \ge f + 2$ 时，该模型的每个共识算法在某些执行中都至少要 $f + 1$ 轮，这是 Fischer 与 Lynch（1982）、Dolev 与 Strong（1983，针对拜占庭故障）首先证明的经典结果，后来对崩溃故障也成立（见 Lynch 的《分布式算法》（*Distributed Algorithms*），1996）。[[#thm-floodset]] 的证明说明了原因：一个正在崩溃的进程每轮都能把自己的值藏起来、只告诉至多一个进程，而这个值可以在一系列正在崩溃的进程之间像涓流一样传递，最多流 $f$ 轮。

::: example 藏着值的 FloodSet {#ex-floodset}
三个进程的提议为 $p_1 = 0$、$p_2 = 5$、$p_3 = 7$，按 $f = 1$（两轮）运行 FloodSet。第 1 轮中，$p_1$ 把自己的集合发给 $p_2$，随后在发给 $p_3$ 之前崩溃。每个进程决定什么？若只跑一轮会出什么问题？
::: solution
第 1 轮之后：$W_2 = \set{0, 5, 7}$（它收到了 $p_1$ 和 $p_3$ 的），$W_3 = \set{5, 7}$（它漏掉了 $p_1$ 的）。第 2 轮没有崩溃（只允许一次崩溃）：$p_2$ 把 $\set{0,5,7}$ 发给 $p_3$，$p_3$ 现在也有 $\set{0, 5, 7}$。两者都决定 $\min = 0$。只跑一轮的话，$p_2$ 会决定 $0$ 而 $p_3$ 决定 $5$——不一致。第二轮的存在就是为了传播一个正在崩溃的进程只透露给部分进程的值。注意 $p_1$ 的值 $0$ 被决定了，尽管 $p_1$ 已经崩溃；有效性允许这一点。
:::
:::

现实系统中的困难在于，轮依赖已知的界限：一轮之内没等到某个进程消息的进程，就断定它崩溃了。若一条慢消息在轮结束之后才到达，算法就可能破坏一致性。倘若我们完全不作时间性假设呢？

## FLP 不可能性定理

1985 年，Michael Fischer、Nancy Lynch 与 Michael Paterson 证明：在异步模型中，只要一个进程可能崩溃，共识对确定性算法就是不可能的——即使链路可靠，即使崩溃是干净的停机，即使只允许提议 $0$ 和 $1$。这个证明是 [[distributed-systems/system-models]] 中不可区分性技术的杰作，我们给出它并证明其主要步骤。

::: definition 配置、事件与价 {#def-valence}
一个**配置**由每个进程的局部状态和正在传输的消息集合（**消息缓冲区**）构成。一个**事件** $e = (p, m)$ 是进程 $p$ 的一步：它从缓冲区接收消息 $m$（或 $m = \varnothing$，什么也不接收），确定性地改变状态，并把新消息放入缓冲区。若 $m$ 在 $C$ 的缓冲区中（或 $m = \varnothing$），则事件 $e$ 对配置 $C$ **适用**；$e(C)$ 是结果配置。**调度**是事件的有限或无穷序列；若某个调度能从 $C$ 走到某配置，则称该配置从 $C$ **可达**。

每个进程有一个只能写一次的输出，初始为空。配置 $C$ 是 **$v$-价的**，若从 $C$ 可达的、有进程作出决定的每个配置都决定 $v$，且这样的配置存在；$C$ 是**单价的**，若它是 $0$-价的或 $1$-价的；$C$ 是**双值的**，若从它可达的配置中 $0$ 和 $1$ 都仍是可能的决定。
:::

在异步模型中，适用事件的每个有限调度都是可能的，消息可以被任意延迟但每条消息最终都被正确进程接收，而空接收 $\varnothing$ 总是适用的，所以进程总能迈出一步。若至多一个进程只执行有限多步（它已崩溃），且发给执行无穷多步的进程的每条消息最终都被接收，则称一次执行是**可容许的**。

反设某个确定性算法在此模型中解决了二元共识，容忍一次崩溃。那么在每次可容许执行中每个正确进程都会作出决定。

::: lemma 不相交的调度可交换 {#lem-commute}
若调度 $\sigma_1$ 与 $\sigma_2$ 都对 $C$ 适用，且它们中执行步骤的进程集合不相交，则 $\sigma_2$ 对 $\sigma_1(C)$ 适用，$\sigma_1$ 对 $\sigma_2(C)$ 适用，且 $\sigma_1(\sigma_2(C)) = \sigma_2(\sigma_1(C))$。
:::

::: proof
进程 $p$ 的一步只取决于 $p$ 的状态和它接收的消息，也只影响 $p$ 的状态和缓冲区（移除收到的消息、加入新消息）。$\sigma_1$ 中的步骤既不改变 $\sigma_2$ 中进程的状态，也不移除发给它们的消息，所以 $\sigma_1$ 之后 $\sigma_2$ 仍然适用且效果相同；对称地亦然。两种次序下所有进程的最终状态与最终缓冲区都相同。
:::

::: lemma 存在双值的初始配置 {#lem-initial}
某个初始配置是双值的。
:::

::: proof
初始配置由提议向量决定。考虑 $n + 1$ 个初始配置 $C_0, C_1, \dots, C_n$，其中 $C_k$ 的 $p_1, \dots, p_k$ 提议 $1$、其余提议 $0$；相邻配置只差一个进程的提议。由有效性，$C_0$（全 $0$）只能决定 $0$，$C_n$（全 $1$）只能决定 $1$，而由终止性，两者的某个决定都可达，所以 $C_0$ 是 $0$-价的，$C_n$ 是 $1$-价的。若没有 $C_k$ 是双值的，就存在一对相邻配置 $C_{k-1}$（$0$-价）与 $C_k$（$1$-价），只差 $p_k$ 的提议。考虑从 $C_{k-1}$ 出发的一次可容许执行：$p_k$ 一开始就崩溃、一步不走；其余进程经过一个不含 $p_k$ 的有限调度 $\sigma$ 后作出决定，设为 $v$。同样的 $\sigma$ 对 $C_k$ 也适用——其余进程状态相同，而 $p_k$ 从不行动——并导致同样的决定 $v$。于是 $v = 0$（因 $C_{k-1}$ 是 $0$-价的）且 $v = 1$（因 $C_k$ 是 $1$-价的），矛盾。
:::

::: lemma 双值配置可以一直保持双值 {#lem-bivalent}
设 $C$ 是双值的，$e = (p, m)$ 是对 $C$ 适用的事件。设 $\mathcal{C}$ 为从 $C$ 出发、不施加 $e$ 可达的配置集合，$\mathcal{D} = \set{e(E) : E \in \mathcal{C}}$。则 $\mathcal{D}$ 含有一个双值配置。
:::

::: proof
首先注意，$e$ 对每个 $E \in \mathcal{C}$ 都适用，因为 $m$ 在 $e$ 被施加之前一直留在缓冲区里（或 $m = \varnothing$）。反设 $\mathcal{D}$ 不含双值配置。

*$\mathcal{D}$ 同时含有 $0$-价配置和 $1$-价配置。* 由于 $C$ 是双值的，对每个 $i \in \set{0,1}$，存在从 $C$ 可达的 $i$-价配置 $E_i$。若 $E_i \in \mathcal{C}$，则 $e(E_i) \in \mathcal{D}$ 从 $E_i$ 可达，于是它不是 $(1-i)$-价的，又因它是单价的，所以它是 $i$-价的。若 $E_i \notin \mathcal{C}$，则从 $C$ 到 $E_i$ 的路上施加过 $e$，于是某个 $F \in \mathcal{D}$ 在这条路上；$E_i$ 从 $F$ 可达，所以 $F$ 作为单值配置是 $i$-价的。

*邻居。* 若 $\mathcal{C}$ 中两个配置之一可由另一个施加单个事件得到，就称它们为**邻居**。因为 $e(C)$ 是单值的——不妨设为 $0$-价——而某个 $E \in \mathcal{C}$ 使 $e(E)$ 是 $1$-价的，沿从 $C$ 到 $E$ 的调度走一遍（其所有配置都在 $\mathcal{C}$ 中），就能找到邻居 $C_0, C_1 \in \mathcal{C}$，满足对某个事件 $e' = (p', m')$ 有 $C_1 = e'(C_0)$，且 $e(C_0)$ 是 $0$-价的、$e(C_1)$ 是 $1$-价的。

*情形 $p' \neq p$。* 由 [[#lem-commute]]，$e(C_1) = e(e'(C_0)) = e'(e(C_0))$。于是 $1$-价配置 $e(C_1)$ 从 $0$-价的 $e(C_0)$ 可达——不可能。

*情形 $p' = p$。* 考虑从 $C_0$ 出发、$p$ 立即崩溃的一次可容许执行，设 $\sigma$ 是一个不含 $p$ 的任何步骤的有限调度，走完它之后有进程作出了决定；令 $A = \sigma(C_0)$。则 $A$ 是单值的。由 [[#lem-commute]]（$\sigma$ 不含 $p$ 的步骤，而 $e$ 与 $e'$ 是 $p$ 的步骤），$e(A) = \sigma(e(C_0))$，它从 $0$-价的 $e(C_0)$ 可达，所以是 $0$-价的；而 $e(e'(A)) = \sigma(e(e'(C_0))) = \sigma(e(C_1))$，从 $1$-价的 $e(C_1)$ 可达，所以是 $1$-价的。两者都从 $A$ 可达，于是 $A$ 是双值的——与“$A$ 中已作出决定”矛盾。

两种情形都不可能，所以 $\mathcal{D}$ 含有双值配置。
:::

::: theorem FLP 不可能性（Fischer、Lynch 与 Paterson，1985） {#thm-flp}
在链路可靠的异步模型中，只要一个进程可能崩溃，就没有确定性算法能在 $n \ge 2$ 个进程中解决共识。
:::

::: proof
利用上面的引理，我们构造一次没有进程 ever 作出决定的可容许执行，违反终止性。从双值初始配置出发（[[#lem-initial]]）。把进程排进一个队列，分阶段重复：取队列头的进程 $p$；令 $m$ 为缓冲区中发往 $p$ 的最旧消息，若没有则取 $\varnothing$；对 $e = (p, m)$ 应用 [[#lem-bivalent]]，经一个以 $e$ 结尾的有限调度到达一个双值配置；把 $p$ 移到队尾。

每个阶段有限且以双值配置结束，所以决定永远不会作出（有进程作出决定的配置不是双值的）。每个进程每 $n$ 个阶段执行一步，于是所有进程都执行无穷多步——一个进程都没有崩溃——而每条消息最终都会成为其接收方的最旧消息并被接收。这次执行是可容许的，却没有进程作出决定。
:::

有三点值得强调。第一，坏执行中**没有崩溃**：正是崩溃的单纯*可能性*迫使算法在每一步都准备好在缺少某个进程的情况下前进，而 [[#lem-bivalent]] 利用的正是这一点。第二，定理说的是**终止性**：安全在异步模型中很容易保证（永远不决定！），而无论网络如何表现，Paxos 和 Raft 都从不违反一致性。第三，坏执行很脆弱：它需要一个对手调度器，恰好把“正确”的消息永远拖延下去。真实网络并不如此恶意，这正是实用协议能工作的原因。

绕过 FLP 的标准途径有三条，每条削弱一个假设。
- **部分同步。** Dwork、Lynch 与 Stockmeyer（1988）证明：若系统最终同步，共识在崩溃故障下当 $n \ge 2f + 1$ 时可解：算法永远安全，延迟一旦有界就终止。Paxos 和 Raft 走的就是这条路，用超时做领导者选举。
- **故障检测器。** Chandra 与 Toueg（1996）证明：配备一个最终不再怀疑某个正确进程的不可靠故障检测器，共识就可解（[[distributed-systems/fault-tolerance]]）。
- **随机化。** Ben-Or（1983）给出了一个以概率 $1$ 终止的随机化算法；FLP 只适用于确定性算法。

::: theorem 必须多数正确 {#thm-majority}
在部分同步模型中（或在异步模型中配上任何可能在有限时间内犯错的故障检测器），若 $n \le 2f$，没有算法能容忍 $f$ 次崩溃故障而解决共识。
:::

::: proof
设 $n \le 2f$，把进程分成大小各不超过 $f$ 的两组 $G_1$ 与 $G_2$。在执行 $\alpha$ 中，$G_2$ 的所有进程一开始就崩溃，$G_1$ 的全部进程提议 $0$；崩溃的至多 $f$ 个，所以由终止性，$G_1$ 的进程作出决定，由有效性它们决定 $0$，设不晚于时刻 $t_1$。在执行 $\beta$ 中，对称地，$G_1$ 一开始就崩溃，$G_2$ 提议 $1$，$G_2$ 在不晚于 $t_2$ 决定 $1$。在执行 $\gamma$ 中，谁也不崩溃，$G_1$ 提议 $0$，$G_2$ 提议 $1$，两组之间的每条消息都被延迟到 $\max(t_1, t_2)$ 之后——部分同步允许这样，因为全局稳定时刻可以更晚。到 $t_1$ 为止，$G_1$ 的进程无法把 $\gamma$ 与 $\alpha$ 区分开，于是它们决定 $0$；到 $t_2$ 为止，$G_2$ 无法把 $\gamma$ 与 $\beta$ 区分开，于是它决定 $1$。一致性被违反。
:::

所以崩溃容错的共识需要 $n \ge 2f + 1$：三个副本容忍一次崩溃，五个容忍两次。下面每个协议里都出现多数派，原因恰如 [[distributed-systems/replication-consistency#thm-quorum]]：任意两个多数派相交，于是一个多数派作出的决定，每个后来的多数派都看得见。

- [ ] Raft 不受影响，因为它是随机化的。
::: solution
Raft 永远安全；FLP 表明存在它不终止的执行——例如由不走运的时序造成的反复 split vote。可靠的链路帮不上忙：FLP 本来就假定链路可靠。Raft 的随机化超时让坏执行变得不太可能，但它的安全性不依赖随机性，而且对手调度器仍能阻止进展；终止性只在部分同步下才有保证。
:::
:::

## Paxos

Leslie Lamport 的 Paxos（写于 1989 年，1998 年以《兼职议会》（"The part-time parliament"）为题发表，2001 年又以《Paxos 简述》（"Paxos made simple"）平实重述）是异步模型崩溃故障下第一个实用的共识协议，支撑着许多生产系统。进程扮演三种角色，一个进程可以身兼数职：**提议者**（proposer）提议值，**接受者**（acceptor）投票，**学习者**（learner）学习决定。接受者共 $n = 2f + 1$ 个。

提议用**投票号**（ballot number）标记，全局全序且每个提议者各不相同（例如二元组（计数，提议者 id））。协议每个投票号包含两个阶段。

::: algorithm 一元 Paxos {#alg-paxos}
每个接受者持久存储：$\mathit{promised}$，它已承诺过的最高投票号（初始为 $0$）；以及 $\mathit{accepted}$，它接受过值的最高投票号（投票号，值）二元组及那个值（初始为空）。

*阶段 1。* (a) 提议者选取一个新投票号 $b$，向所有接受者发送 $\textsf{prepare}(b)$。(b) 接受者收到 $b > \mathit{promised}$ 的 $\textsf{prepare}(b)$ 时，置 $\mathit{promised} \gets b$，回复 $\textsf{promise}(b, \mathit{accepted})$；否则忽略该请求（或回复拒绝）。

*阶段 2。* (a) 提议者从多数接受者收到 $b$ 的承诺后，选取一个值：这些承诺报告的 $\mathit{accepted}$ 二元组中投票号最高的那个的值；若没有一个报告接受过的值，则任取一个值（它自己的提议）。它向所有接受者发送 $\textsf{accept}(b, v)$。(b) 接受者收到 $b \ge \mathit{promised}$ 的 $\textsf{accept}(b, v)$ 时，置 $\mathit{promised} \gets b$、$\mathit{accepted} \gets (b, v)$ 并通知学习者；否则忽略。

*决定。* 当多数接受者对同一投票号 $b$ 接受了 $(b, v)$ 时，值 $v$ 被**选定**（chosen）。学习者得知此事后决定 $v$。
:::

关键规则是阶段 2(a)：提议者只有当它的多数中没有接受者接受过任何东西时，才可以自由提议自己的值；否则它必须采纳它听到的最新的已接受值。这条规则正是 Paxos 安全的原因。

::: theorem Paxos 的安全性 {#thm-paxos}
若值 $v$ 在投票号 $b$ 中被选定，则每个 $b' \ge b$ 的 $\textsf{accept}(b', v')$ 消息都有 $v' = v$。因此，被选定的值至多一个，并且无论消息如何延迟或丢失、无论多少进程崩溃，一致性、有效性和完整性在每次执行中都成立。
:::

::: proof
设 $v$ 在投票号 $b$ 中被选定，由接受 $(b, v)$ 的多数接受者集合 $Q$ 选定。我们对 $b' \ge b$ 强归纳证明任何 $\textsf{accept}(b', v')$ 都有 $v' = v$。$b' = b$ 时：一个投票号属于一个提议者，它每个投票号只发送一个值，所以 $v' = v$。

设 $b' > b$，并设结论对 $[b, b')$ 之间的所有投票号成立。$b'$ 的提议者在收到 $b'$ 的来自某多数 $Q'$ 的承诺之后才发送 $\textsf{accept}(b', v')$。$Q$ 与 $Q'$ 都是多数，故某个接受者 $a$ 同属两者。$a$ 接受过 $(b, v)$，并承诺了 $b'$。它必然是在承诺 $b'$ *之前*接受 $(b, v)$ 的：承诺了 $b' > b$ 之后它就会忽略 $\textsf{accept}(b, v)$。所以 $a$ 的承诺报告了一个投票号至少为 $b$ 的已接受二元组。于是 $Q'$ 的承诺所报告的二元组中最高的投票号 $c$ 满足 $b \le c < b'$（它小于 $b'$，因为接受者只报告在承诺 $b'$ 之前接受过的投票号，而那些都低于 $b'$）。$b'$ 的提议者把 $v'$ 选作那个二元组的值，而该值曾以 $\textsf{accept}(c, v')$ 发送，$b \le c < b'$。由归纳假设，$v' = v$。

关于推论：若 $v$ 在投票号 $b$ 中选定而 $w$ 在投票号 $c \ge b$ 中选定，那么 $w$ 曾以某个针对投票号 $c$ 的 accept 消息发送，所以 $w = v$。有效性：accept 消息中的每个值要么是某个提议者的提议，要么来自更早的 accept 消息，于是归纳可知它被提议过。完整性成立，因为学习者只决定一次。
:::

这个证明只用法定数量相交和接受者们的承诺，根本不用时间。所以 Paxos 在完全异步模型中是安全的，FLP 只在活性上咬人：两个提议者可以**对决**——每个都在对方的 accept 阶段完成之前 prepare 出更高的投票号，没完没了。解药是用超时选出一位**选定提议者**（distinguished proposer，即领导者），只在其似乎失效时让其他人提议；在部分同步下，单一领导者终会稳定下来，它的提议就会成功。

::: example Paxos 找回已被选定的值 {#ex-paxos}
接受者 $A_1, A_2, A_3$。提议者 $P$ 以值 $x$ 运行投票号 $1$：它的 prepare 到达全部三个接受者，得到承诺；它的 $\textsf{accept}(1, x)$ 到达 $A_1$ 和 $A_2$ 并被接受，随后 $P$ 崩溃。提议者 $Q$ 以值 $y$ 开始投票号 $2$，收到 $A_2$ 和 $A_3$ 的承诺。$Q$ 提议什么？若 $\textsf{accept}(1, x)$ 只到达过 $A_1$ 呢？
::: solution
$x$ 已在投票号 $1$ 中被选定：多数（$A_1, A_2$）接受了它。$Q$ 收到的承诺是：$A_2$ 报告接受过 $(1, x)$，$A_3$ 报告没有。最高的已接受二元组是 $(1, x)$，所以 $Q$ 必须发送 $\textsf{accept}(2, x)$ 而不是 $y$——正是 [[#thm-paxos]] 的相交论证，$A_2$ 就是那个公共接受者。决定熬过了做成它的那个提议者的崩溃。

若只有 $A_1$ 接受过，$x$ 就不算被选定。$Q$ 的多数 $\set{A_2, A_3}$ 什么都没报告，所以 $Q$ 可以提议 $y$；若 $A_2$ 和 $A_3$ 接受，$y$ 就被选定。$A_1$ 仍持有 $(1, x)$，但少数派的陈旧接受无害：任何听到 $A_1$ 的后来提议者也会听到 $A_2$ 或 $A_3$，它们报告带有 $y$ 的更高投票号 $2$。注意 $Q$ 从外部无法区分这两种情形——两种情况下它都看到多数——而在两种情况下它的行为都是安全的。
:::
:::

### Multi-Paxos

复制日志需要每个日志位置一个共识实例。每个条目都跑两个阶段要花两次往返。**Multi-Paxos** 观察到阶段 1 不依赖于值：领导者可以用投票号 $b$ *一次性*为所有未来的日志位置跑阶段 1（接受者对每个位置回复它们的已接受二元组），此后只要它还是领导者，就只需阶段 2 的一轮提交每个新条目——到多数派一次往返，外加每个接受者一次持久写。新领导者以更高的投票号跑阶段 1，把它不知道的位置上所有可能被选定的值全部学到、重新提议，并用空操作填补空缺。兰波特（Lamport）的论文对这些细节多有留白，正确实现 Multi-Paxos 是出了名的难；Google 的 Chubby 团队在《Paxos 实战》（"Paxos made live"，Chandra、Griesemer 与 Redstone，2007）中描述了他们的经验。Raft 正是为填补这个空白而设计的。

## Raft

Diego Ongaro 与 John Ousterhout 的 Raft（《寻找易于理解的共识算法》（"In search of an understandable consensus algorithm"），2014）解决与 Multi-Paxos 相同的问题，容错性与性能也相同，但围绕一个**强领导者**和少数几条可以逐条核查的规则组织起来。它被用于 etcd、Consul、CockroachDB、TiKV 和许多其他系统（截至 2026 年）。

### 任期、角色与选举

时间被分成连续编号的**任期**（term）；每个任期以一次选举开始，每个任期至多选出一个领导者。每台服务器是**跟随者**（follower）、**候选人**（candidate）或**领导者**（leader）。每台服务器持久存储它的**当前任期**、它在该任期**投过票的**候选人（若有）、以及它的**日志**——一串条目，每个条目含一条命令和一个任期号（创建它的领导者当时所处的任期）。

::: algorithm Raft 领导者选举 {#alg-raft-election}
1. 每条消息都携带发送方的任期。看到比自己当前任期更高的任期的服务器采纳它、清空自己的投票、成为跟随者。较低任期的消息被拒绝。
2. 一个跟随者若在一个**选举超时**——随机选取，例如取自 $[150, 300]$ ms——之内没有听到领导者的声音，就成为候选人：它把自己的任期加一、投自己一票，并向所有服务器发送 $\textsf{RequestVote}(\mathit{term}, \mathit{lastLogTerm}, \mathit{lastLogIndex})$。
3. 一台服务器若在本任期还没有把票投给别人，且候选人的日志**至少和自己一样新**——候选人的最后日志任期更大，或相等且最后索引不小于自己的（**选举限制**）——就把票投给它。回复之前先把票写入稳定存储。
4. 收到多数选票的候选人成为领导者，并立即发送心跳（空的 $\textsf{AppendEntries}$）。收到来自其任期某领导者的 $\textsf{AppendEntries}$ 的候选人成为跟随者。若选举超时（split vote），它开始一个新任期。
:::

随机化超时是选举通常一次就成功的原因：定时器最先到期的服务器，通常能在别的服务器定时器到期之前请求并收到选票。

::: proposition 选举安全性 {#prop-election-safety}
每个任期至多选出一个领导者。
:::

::: proof
任期 $T$ 的领导者收到过任期 $T$ 中多数服务器的选票。每台服务器每个至多投票一次——它的票在稳定存储上，所以跨崩溃也成立。两个多数派共享一台服务器，而它将不得不在任期 $T$ 中把票投给两个候选人。所以同一任期出两个领导者是不可能的。
:::

### 日志复制

::: algorithm Raft 日志复制 {#alg-raft-log}
1. 客户端把命令发给领导者，领导者把它作为新条目追加到自己的日志末尾，带上当前任期。
2. 领导者向每个跟随者发送 $\textsf{AppendEntries}(\mathit{term}, \mathit{prevLogIndex}, \mathit{prevLogTerm}, \mathit{entries}, \mathit{leaderCommit})$，其中条目是它日志中位置 $\mathit{prevLogIndex}$ 之后的那些。
3. **一致性检查。** 跟随者只有当它的日志在 $\mathit{prevLogIndex}$ 处有一个任期为 $\mathit{prevLogTerm}$ 的条目时才接受。若通过，它删除与新条目冲突的现有条目（同索引、不同任期）及其后的一切，追加自己没有的新条目，并答复成功。否则答复失败，领导者以更小的 $\mathit{prevLogIndex}$ 重试，直到日志吻合。
4. **提交规则。** 领导者当一个条目存储到多数服务器上*并且*它是在领导者当前任期中创建的，才视之为**已提交**；提交一个条目就提交它之前的每个条目。跟随者从 $\mathit{leaderCommit}$ 得知提交索引。
5. 每台服务器按日志次序把已提交条目应用到它的状态机。
:::

::: example 修复跟随者的日志 {#ex-log-repair}
任期 $4$ 的新领导者日志任期为 $[1, 1, 2, 4]$（索引 $1$–$4$）。一个曾从任期 $2$ 的旧领导者额外收到过条目的跟随者持有 $[1, 1, 2, 2, 2]$。领导者对该跟随者从 $\mathit{nextIndex} = 5$ 开始（自己最后一条之后一位）。追踪 $\textsf{AppendEntries}$ 交换的过程直到日志吻合。
::: solution
1. $\mathit{prevLogIndex} = 4$、$\mathit{prevLogTerm} = 4$，无条目。跟随者索引 $4$ 处的条目任期是 $2 \ne 4$：失败。领导者置 $\mathit{nextIndex} = 4$。
2. $\mathit{prevLogIndex} = 3$、$\mathit{prevLogTerm} = 2$，条目 $[(4, \cdot)]$ 供索引 $4$ 使用。跟随者索引 $3$ 处的条目任期为 $2$：检查通过。它索引 $4$ 处的条目（任期 $2$）与新条目（任期 $4$）冲突，于是它删除索引 $4$ 和 $5$，追加领导者的条目。它的日志现在是 $[1, 1, 2, 4]$，与领导者完全相同，答复成功且匹配索引 $4$。

跟随者索引 $4$ 和 $5$ 上的两个任期 $2$ 的条目被丢弃了。只有因为它们*未被提交*，这样做才是安全的：一个存储得太少、以至于新领导者都没有的条目不可能已被提交，理由见下文 [[#thm-leader-completeness]]。真实实现会加速第 1 步：让跟随者报告冲突条目的任期以及该任期的第一个索引，领导者就能每轮跳过整个任期而不是一个条目。
:::
:::

一致性检查给了 Raft 一个不变式，使它的日志易于推理。

::: lemma 日志匹配 {#lem-log-matching}
若两个日志在相同索引处有相同任期的条目，则这两个条目相同（命令相同），并且两个日志在该索引之前的所有条目完全相同。
:::

::: proof
*第一部分。* 由选举安全性，一个任期至多一个领导者，而领导者在其任期的给定索引处至多创建一个条目，且从不改动它。条目在服务器之间只会以拷贝的方式移动，所以任何地方索引 $i$ 上任期 $T$ 的条目都是那个唯一条目的拷贝。

*第二部分，* 对成功 $\textsf{AppendEntries}$ 步数归纳。初始时所有日志为空。设结论成立，且一个跟随者接受了领导者索引 $k = \mathit{prevLogIndex}$ 之后的条目。检查保证跟随者索引 $k$ 处的条目具有领导者在 $k$ 处的任期，于是由归纳假设，跟随者的日志与领导者的在 $k$ 之前一致；这一步之后，跟随者日志到最后一个新条目为止是领导者日志的拷贝。任何其他日志，若与新部分中某个索引、某个任期处的跟随者日志匹配，则在该处也与领导者的日志匹配（由第一部分，条目是同一个），于是对该日志与领导者日志用归纳假设，它在这两个索引之前与领导者的一致，从而与跟随者的一致。删除冲突的后缀只会缩短日志，不会造出新的相同（索引，任期）对。
:::

::: theorem 领导者完备性 {#thm-leader-completeness}
若一个条目在任期 $T$ 中被提交，则它出现在所有大于 $T$ 的任期的领导者日志中。
:::

::: proof
反设不然。设 $e$ 被任期 $T$ 的领导者 $L_T$ 提交，并设 $U > T$ 是缺失 $e$ 的最小任期，其领导者为 $L_U$。由提交规则，$L_T$ 把一个任期 $T$、索引不小于 $e$ 的条目存储到了多数服务器上，而由 [[#lem-log-matching]]，持有那个条目的每台服务器也持有 $e$；所以 $e$ 在某个多数派上。

$L_T$ 把 $e$ 复制到了多数服务器，$L_U$ 从多数服务器得到选票，于是某台服务器 $V$ 两者都做过。$V$ 投票给 $L_U$ 之前接受过 $e$：否则它会先看到任期 $U > T$ 并拒绝 $L_T$ 的 $\textsf{AppendEntries}$。$V$ 投票时仍有 $e$，因为条目只在它们与领导者的日志冲突时才被删除，而 $T$ 与 $U$ 之间的每个领导者都含有 $e$（由 $U$ 的极小性），它们谁也不会导致 $e$ 被删。

$V$ 把票投给了 $L_U$，所以 $L_U$ 的日志至少和 $V$ 的一样新。分两种情形。
- *最后任期同为 $S$。* 那么 $L_U$ 的日志至少和 $V$ 的一样长。两者的最后条目都由任期 $S$ 的唯一领导者创建，所以由 [[#lem-log-matching]]，两个日志各自到自己最后索引为止都与那个领导者的日志相同。$L_U$ 的日志是两条前缀中较长的那条，所以它含有 $V$ 的全部日志，包括 $e$——矛盾。
- *$L_U$ 的最后任期比 $V$ 的大。* $V$ 的最后任期至少是 $T$，因为 $V$ 持有任期 $T$ 的 $e$，所以 $L_U$ 的最后条目有某个满足 $T < S < U$ 的任期 $S$。创建该条目的任期 $S$ 的领导者含 $e$（由 $U$ 的极小性）；由日志匹配，$L_U$ 的日志在任期 $S$ 的条目之前与那个领导者的一致，所以它也含有 $e$——矛盾。
:::

::: corollary 状态机安全性 {#cor-smr-safety}
若一台服务器已把索引 $i$ 处的条目应用到它的状态机，别的服务器就永远不会在索引 $i$ 处应用不同的条目。
:::

::: proof
服务器只应用已提交的条目。若两台服务器在索引 $i$ 处应用了不同的条目，则两者都已提交，设先提交者在任期 $T$、另一个在任期 $T' \ge T$。由 [[#thm-leader-completeness]]，任期 $T'$ 的领导者的日志在索引 $i$ 处持有第一个条目；它只提交自己日志中的条目，而由 [[#lem-log-matching]]，它在索引 $i$ 处只有一个条目。所以两个条目相同。
:::

提交规则对*当前*任期条目的限制微妙而 essential（不可或缺）。没有它，Raft 论文中下面这个场景就会丢一个已提交的条目。

::: example 为什么按计数只能提交当前任期的条目 {#ex-figure8}
五台服务器 $S_1, \dots, S_5$。(a) $S_1$ 在任期 $2$ 是领导者，把一个索引 $2$（任期 $2$）的条目只复制给了 $S_2$，随后崩溃。(b) $S_5$ 以 $S_3, S_4, S_5$ 的选票在任期 $3$ 当选，在索引 $2$ 追加一个任期为 $3$ 的不同条目，随后在复制它之前崩溃。(c) $S_1$ 重启，在任期 $4$ 当选，并把它的任期 $2$ 条目复制给 $S_3$：它现在在 $S_1, S_2, S_3$ 上，是多数派。假设 $S_1$ 把它当作已提交，随后崩溃。可能发生什么？
::: solution
(d) $S_5$ 能在任期 $5$ 当选：它的最后日志任期是 $3$，大于 $S_2$、$S_3$、$S_4$（空）日志的最后任期 $2$，所以它们都认为自己日志至少和对方一样新，$S_5$ 得到 $S_2, S_3, S_4$ 的选票。成为领导者后，它用自己的任期 $3$ 条目在每个跟随者上覆写索引 $2$。一个存储到多数派上——并且在天真规则下已被 $S_1$ 应用过——的条目被替换了：状态机安全性失效。

Raft 的规则禁止了出错的那一步：任期 $4$ 中，$S_1$ 不能靠数副本提交任期 $2$ 的条目。它只能间接提交：等到它之后某个任期 $4$ 的条目到达多数派。那时多数派的最后任期是 $4$，$S_5$（最后任期 $3$）再也赢不了选举，[[#thm-leader-completeness]] 的证明便成立。上面定理的证明在第一段就用到了该规则：已提交条目都是存储到多数派上的某个当前任期条目的前缀。
:::
:::

### 一个模拟

下面的程序在一个进程里模拟五台 Raft 服务器，以毫秒为步长推进。每条消息被延迟 $5$–$20$ ms，并以 $0.2$ 的概率丢失。领导者每 $40$ ms 收到一条新命令，每 $25$ ms 发送一次 $\textsf{AppendEntries}$。$t = 1000$ ms 时领导者崩溃；$t = 1800$ ms 时它带着仅存的持久状态（任期、投票、日志）重启。每一步之后，驱动程序检查状态机安全性：每台服务器上每个索引处已提交的条目，都必须等于该索引处有史以来第一个被提交的条目。消息处理函数遵照 [[#alg-raft-election]] 与 [[#alg-raft-log]]（做了简化：没有日志压缩，没有成员变更，领导者一次回退一个条目重试）：

```python
import random
N, MAJ = 5, 3
rng = random.Random(1)
leaders, elections = [], [0]                                   # 供最后报告用

class Server:
    def __init__(self, i):
        self.id, self.term, self.voted, self.log = i, 0, None, []   # 持久状态
        self.reset(0)
    def reset(self, now):                                           # 易失状态
        self.role, self.commit, self.votes, self.up = "follower", 0, set(), True
        self.deadline = now + rng.randint(150, 300)                 # 随机化选举超时
    def last(self): return (self.log[-1][0] if self.log else 0, len(self.log))

def handle(s, m, now, send):
    if m["term"] > s.term:                                          # 更高的任期：下台
        s.term, s.voted, s.role = m["term"], None, "follower"
    t = m["type"]
    if t == "vote_req":
        ok = (m["term"] == s.term and s.voted in (None, m["src"])
              and (m["last_term"], m["last_idx"]) >= s.last())      # 选举限制
        if ok: s.voted, s.deadline = m["src"], now + rng.randint(150, 300)
        send(s.id, m["src"], type="vote", term=s.term, granted=ok)
    elif t == "vote" and s.role == "candidate" and m["term"] == s.term and m["granted"]:
        s.votes.add(m["src"])
        if len(s.votes) >= MAJ:
            s.role, s.next, s.match = "leader", [len(s.log)] * N, [0] * N
            s.match[s.id] = len(s.log); leaders.append((s.term, s.id, now))
    elif t == "append":
        if m["term"] < s.term:
            return send(s.id, m["src"], type="ack", term=s.term, ok=False, idx=0)
        s.role, s.deadline = "follower", now + rng.randint(150, 300)
        p = m["prev_idx"]
        if p > len(s.log) or (p > 0 and s.log[p - 1][0] != m["prev_term"]):
            return send(s.id, m["src"], type="ack", term=s.term, ok=False, idx=p)   # 一致性检查失败
        for j, e in enumerate(m["entries"]):
            if p + j < len(s.log) and s.log[p + j][0] != e[0]:
                del s.log[p + j:]                                   # 删除冲突的后缀
            if p + j >= len(s.log): s.log.append(e)
        done = p + len(m["entries"])                                # 至此日志已与领导者一致
        s.commit = max(s.commit, min(m["commit"], done))
        send(s.id, m["src"], type="ack", term=s.term, ok=True, idx=done)
    elif t == "ack" and s.role == "leader" and m["term"] == s.term:
        if m["ok"]:
            s.match[m["src"]] = max(s.match[m["src"]], m["idx"])
            s.next[m["src"]] = max(s.next[m["src"]], m["idx"])
            for k in range(len(s.log), s.commit, -1):               # 提交规则：多数派 且 当前任期
                if sum(x >= k for x in s.match) >= MAJ and s.log[k - 1][0] == s.term:
                    s.commit = k; break
        else:
            s.next[m["src"]] = max(0, s.next[m["src"]] - 1)         # 退一格重试
```

驱动程序投递消息、触发超时，并让领导者接受命令、发送心跳：

```python
servers, net, applied, violations = [Server(i) for i in range(N)], [], {}, 0
def send(src, dst, **m):
    if rng.random() >= 0.2:                                         # 丢失 20% 的消息
        net.append((now + rng.randint(5, 20), dst, dict(m, src=src)))
for now in range(3000):
    if now == 1000: crashed = next(s for s in servers if s.role == "leader"); crashed.up = False
    if now == 1800: crashed.reset(now)                              # 仅凭持久状态重启
    for item in [x for x in net if x[0] == now]:
        net.remove(item)
        if servers[item[1]].up: handle(servers[item[1]], item[2], now, send)
    for s in (s for s in servers if s.up):
        if s.role != "leader" and now >= s.deadline:                # 超时：开始一次选举
            s.term, s.voted, s.role, s.votes = s.term + 1, s.id, "candidate", {s.id}
            elections[0] += 1
            s.deadline = now + rng.randint(150, 300)
            lt, li = s.last()
            for d in range(N):
                if d != s.id: send(s.id, d, type="vote_req", term=s.term, last_term=lt, last_idx=li)
        if s.role == "leader":
            if now % 40 == 0: s.log.append((s.term, f"cmd{now}")); s.match[s.id] = len(s.log)
            if now % 25 == 0:                                       # 心跳 / 复制
                for d in range(N):
                    if d == s.id: continue
                    p = s.next[d]
                    send(s.id, d, type="append", term=s.term, prev_idx=p,
                         prev_term=s.log[p - 1][0] if p else 0, entries=s.log[p:], commit=s.commit)
    for s in servers:                                               # 状态机安全性，每一步检查一次
        for k in range(s.commit):
            violations += applied.setdefault(k, s.log[k]) != s.log[k]
for term, sid, t in leaders: print(f"t={t:4} ms  server {sid} becomes leader of term {term}")
terms = [t for t, _, _ in leaders]
print("elections started:", elections[0], " terms with two leaders:", [t for t in set(terms) if terms.count(t) > 1])
print("commit index per server:", [s.commit for s in servers])
print("entries committed:", len(applied), " safety violations:", violations,
      " last:", applied[len(applied) - 1])
```

```console
$ python3 raft.py
t= 378 ms  server 3 becomes leader of term 2
t=1411 ms  server 4 becomes leader of term 5
elections started: 8  terms with two leaders: []
commit index per server: [53, 53, 53, 53, 54]
entries committed: 54  safety violations: 0  last: (5, 'cmd2960')
```

把输出与理论对照着读。第一个领导者当选于任期 $2$——任期 $1$ 的选举因丢失选票而失败——在 $378$ ms 之后。它在 $1000$ ms 崩溃后，集群**不可用**了 $411$ ms：跟随者必须等超时，而由于 $20\%$ 的消息丢失，又有两次选举（任期 $3$ 和 $4$）失败，服务器 $4$ 才在任期 $5$ 胜出。任何任期都未出现两个领导者（[[#prop-election-safety]]）。重启的服务器 $3$ 以跟随者身份重新加入，通过一致性检查收到了它错过的条目并追平；而在全部 $3000$ 步中没有任何已提交条目被改动过（[[#cor-smr-safety]]）。领导者的提交索引比跟随者领先一，后者在下一次心跳时得知。换别的随机种子运行会改变时序和选举次数，却从不改变安全性的结果——这正是证明所承诺的，因为安全性不依赖时序。（这个模拟只是教学模型；真实实现还必须在回复之前持久化状态、限制消息大小、把日志压缩成快照、并安全地变更成员资格。）

::: warning 自以为是领导者的，未必是领导者
一台自认为是领导者的服务器可能早已被废黜而不自知：它可能与多数派失去了联系，而多数派已经在更高的任期里选出了新领导者。若它用自己的本地状态回答读请求，就可能返回陈旧数据，违反线性一致性。Raft 的写路径是安全的，因为旧领导者没有多数派就什么都提交不了。至于读，领导者或者必须在回答之前通过与多数派交换心跳确认自己仍是领导者（**ReadIndex** 技术），或者依赖基于时间的**租约**——只有当时钟漂移有界时它才安全，而这正是异步模型之外的假设（[[distributed-systems/time-clocks]]）。
:::

::: quiz
某 Raft 跟随者的日志条目任期为 $[1, 1, 2, 2, 2]$；某候选人的日志条目任期为 $[1, 1, 3]$。跟随者在候选人的任期里还没有投过票。它投不投票？
- [x] 投，因为候选人的最后任期（$3$）更高
- [ ] 不投，因为候选人的日志更短
- [ ] 不投，因为两个日志在索引 $3$ 处不同
- [ ] 仅当候选人的任期至少为 $4$ 时才投
::: solution
“至少一样新”先比较最后任期，只有最后任期相等时才比较长度。候选人的最后条目来自任期 $3$，比跟随者的任期 $2$ 新；任期 $3$ 的条目只可能存在于任期 $3$ 的领导者当选时已知此前每个已提交条目的情况下。跟随者索引 $3$–$5$ 的任期 $2$ 条目，不可能在任期 $3$ 开始之后、而候选人蒙在鼓里的情况下被提交——所以投赞成票是安全的，候选人若胜出，跟随者冲突的条目会被覆写。
:::
:::

## 实践

与不加复制的写相比，共识很贵：每个提交条目都需要领导者到多数派一次往返，外加每台多数派服务器上一次持久写（一次 `fsync`，在现代固态硬盘上从几十微秒到几毫秒）。因此系统把许多命令**成批**装进一个条目，并把条目**流水线化**，不等前面的提交完就发后面的。在数据中心内，这类系统每秒几千到几十万次提交是典型数字；跨大洲时，每次提交都要付一次广域网往返——[[distributed-systems/replication-consistency]] 中 PACELC 的代价。

所以共识组通常保持在三五台的规模——通常三台或五台服务器——并且用于*元数据*与*协调*而非数据本身：集群的配置、每个分区由谁领导、谁持有锁。Google 的 Chubby 锁服务（Burrows，2006）与 Apache ZooKeeper（Hunt 及合作者，2010；其协议是 Zab）把这作为服务提供，etcd 则为 Kubernetes 提供同样的东西。大型数据库为每个数据分区运行一个共识组，于是吞吐量随分区数增长（[[distributed-systems/distributed-storage]]）。

::: history
兰波特（Lamport）、Shostak 与 Pease 的《在有故障的情况下达成一致》（"Reaching agreement in the presence of faults"，1980）与《拜占庭将军问题》（"The Byzantine generals problem"，1982）提出了带任意故障的协议问题。Michael Fischer、Nancy Lynch 与 Michael Paterson 的《一个 faulty 进程下分布式共识的不可能性》（"Impossibility of distributed consensus with one faulty process"，《Journal of the ACM》，1985）获得 2001 年的 Dijkstra 奖。Michael Ben-Or 的随机化协议发表于 1983 年，Cynthia Dwork、Nancy Lynch 与 Larry Stockmeyer 的部分同步结果发表于 1988 年，Tushar Chandra 与 Sam Toueg 的故障检测器发表于 1996 年。Brian Oki 与 Barbara Liskov 的 Viewstamped Replication（1988）是与 Paxos 关系密切的早期基于领导者的复制协议。兰波特（Lamport）于 1989 年投递了以希腊小岛议会故事讲述 Paxos 的《兼职议会》（"The part-time parliament"）；它发表于 1998 年的《ACM Transactions on Computer Systems》，《Paxos 简述》（"Paxos made simple"）随后于 2001 年问世。Diego Ongaro 与 John Ousterhout 在 2014 年的 USENIX Annual Technical Conference 上报告了 Raft，并获最佳论文奖。
:::

## 后续内容

[[distributed-systems/fault-tolerance]] 在共识之上构建状态机复制，把故障检测精确化，并追问进程不只是崩溃、而是**拜占庭**时会怎样——答案需要 $n \ge 3f + 1$。[[distributed-systems/distributed-storage]] 为每个分区使用共识组。[[distributed-systems/distributed-transactions]] 表明原子提交是与共识不同的问题、两阶段提交为何会阻塞，以及把它的协调者跑在 Paxos 上如何消除阻塞。用于 Paxos 与 Raft 的形式规格和模型检测的形式方法（如 TLA+）在 [[software-engineering/verification]] 中介绍。

::: summary
- **共识**：每个正确进程都决定（终止性）同一个（一致性）被提议过的（有效性）值；它与**全序广播**等价，是**状态机复制**的基础。
- 有了同步轮，**FloodSet** 在 $f + 1$ 轮内解决共识（[[#thm-floodset]]）。
- **FLP**：异步模型中，只要一个进程可能崩溃，就没有确定性算法能解决共识（[[#thm-flp]]）——双值配置可以被永远维持下去。
- 部分同步下，共识可解当且仅当**多数正确**，$n \ge 2f + 1$（[[#thm-majority]]）。
- **Paxos** 在每次执行中都安全：提议者必须采纳多数报告的投票号最高的已接受值（[[#thm-paxos]]）；Multi-Paxos 在稳定领导者下每个条目一次往返提交。
- **Raft** 用任期、随机化选举、**选举限制**、**一致性检查**和**当前任期提交规则**保证选举安全性、日志匹配、领导者完备性和状态机安全性。
- 实用协议**永远安全**、只在时序良好时活跃；FLP 说的是活性。
:::

## 习题

::: exercise 能容忍多少故障？ {level=1 check="3"}
$7$ 台服务器组成的共识组使用多数派。还能有多台服务器崩溃而它仍有进展？（填入数量。）
::: solution
$7$ 的多数派是 $4$，所以至多 $3$ 台可以崩溃。由 [[#thm-majority]]，容忍 $f$ 次崩溃需要 $n \ge 2f + 1$；$7 = 2 \cdot 3 + 1$。注意 $6$ 台服务器也只能容忍 $2$ 次崩溃（$6$ 的多数派是 $4$），这就是共识组取奇数成员的原因。
:::
:::

::: exercise FloodSet 的消息数 {level=1 check="60"}
$n = 5$ 个进程、$f = 2$、没有进程崩溃时，FloodSet 一共发送多少条消息？（填入数量。）
::: solution
共 $f + 1 = 3$ 轮，每轮每个进程发给其他 $n - 1 = 4$ 个进程：$3 \times 5 \times 4 = 60$ 条消息。
:::
:::

::: exercise 谁能当选？ {level=1}
三台 Raft 服务器的日志任期为 $A = [1, 2, 2]$、$B = [1, 2]$、$C = [1, 3]$。对每台服务器，说明另外两台中的哪些会给它投票（假设它们在该候选人的任期里都还没投过票）。
::: solution
比较（最后任期，长度）：$A = (2, 3)$，$B = (2, 2)$，$C = (3, 2)$。$A$ 作候选人：$B$ 投赞成（$A$ 的最后任期相等且更长）；$C$ 投反对（$3 > 2$）。$B$ 作候选人：$A$ 投反对（最后任期相同而更短）；$C$ 投反对。$C$ 作候选人：两家都投赞成，因为它的最后任期 $3$ 最高。所以 $A$ 和 $C$ 能胜出（各需再得一票）；$B$ 不能。
:::
:::

::: exercise 提议者必须提议什么？ {level=2}
五个接受者。某提议者运行投票号 $9$，收到其中三个的承诺，报告的已接受二元组是：$(5, x)$、无、$(7, y)$。它必须提议什么值？它能确定 $y$ 已被选定吗？
::: solution
它必须提议 $y$，即投票号最高的已接受二元组（$7$）的值。它不能确定 $y$ 已被选定：也许只有这一个接受者在投票号 $7$ 中接受过它。但 $y$ *有可能*已被选定（被某个包含不在此法定数量内的接受者的多数），而除非 $y = x$，$x$ 不可能已在投票号 $5$ 中被选定：若 $x$ 曾在投票号 $5$ 中被选定，那么由 [[#thm-paxos]]，投票号 $7$ 的每次接受都将携带 $x$。所以提议 $y$ 是唯一安全的选择。
:::
:::

::: exercise 提交索引 {level=2 check="4"}
任期 $5$ 的某 Raft 领导者日志任期为 $[1, 3, 3, 5, 5, 5]$（索引 $1$–$6$）。它对四个跟随者的匹配索引是 $6, 4, 3, 1$（自己的日志长 $6$）。它可以视为已提交的最高索引是多少？（填入索引。）
::: solution
五台服务器中多数派是 $3$。存储在至少 $3$ 台服务器上的索引（领导者 $6$，跟随者 $6, 4, 3, 1$）：索引 $4$ 在领导者和匹配 $6$、$4$ 的两个跟随者上——三台；索引 $5$ 只在两台上。所以索引 $4$ 复制到了多数派，而它的任期是 $5$、是任期，由提交规则索引 $4$（及其前的一切）已提交。若索引 $4$ 处的条目来自更早的任期，领导者就得继续等待。
:::
:::

::: exercise 首次超时的期望时间 {level=2 check="180"}
Raft 领导者崩溃后，其余 $4$ 台服务器中的每台在它收到最后一次心跳后的 $[150, 300]$ ms 内均匀随机地超时（假设它们同时收到最后一次心跳）。第一台服务器成为候选人的期望时间是多少？（填入毫秒数。）
::: solution
$[0, w]$ 上 $k$ 个独立均匀变量最小值的均值是 $w/(k+1)$。取 $w = 150$、$k = 4$，首次超时平均发生在心跳后 $150 + 150/5 = 180$ ms。再加上一次往返的选举成功，故障转移在该模型中约需 $200$ ms——不计 split vote 时能指望的最短不可用时间。
:::
:::

::: exercise 不相交的法定数量 {level=3}
某设计者用 $4$ 个接受者、大小 $2$ 的法定数量跑 Paxos，并声称这能容忍 $2$ 次崩溃。给出一个选出两个不同值的执行。然后证明：$4$ 个接受者时，若所有法定数量大小都是 $3$，Paxos 是安全的，并说明那能容忍几次崩溃。
::: solution
接受者 $A_1, \dots, A_4$。提议者 $P$ 运行投票号 $1$：得到 $A_1, A_2$ 的承诺，随后 $\textsf{accept}(1, x)$ 被 $A_1, A_2$ 接受——$x$ 被选定（一个 $2$ 的“法定数量”）。提议者 $Q$ 运行投票号 $2$：得到 $A_3, A_4$ 的承诺，它们什么都没接受过，于是 $Q$ 可以提议 $y$；$A_3, A_4$ 接受——$y$ 被选定。两个值都被选定：一致性失效，因为法定数量 $\set{A_1, A_2}$ 与 $\set{A_3, A_4}$ 不相交，而 [[#thm-paxos]] 的证明需要一个公共接受者。

法定数量为 $3$ 时，$4$ 个接受者的任意两个法定数量至少共享 $3 + 3 - 4 = 2$ 个接受者，证明照旧成立：安全性保持。进展需要 $3$ 个存活的接受者，所以只容忍 $1$ 次崩溃——与只有 $3$ 个接受者时相同，这就是不取偶数的原因。
:::
:::

::: exercise 接受者必须记住 {level=3}
证明：若 Paxos 中的接受者可以崩溃并恢复，却*没有*稳定存储（忘掉 $\mathit{promised}$ 和 $\mathit{accepted}$），就可能选定两个不同的值。Raft 中哪些状态扮演同样的角色？它们若不持久化会出什么问题？
::: solution
三个接受者。投票号 $1$：$A_1, A_2$ 接受 $x$——被选定。$A_2$ 崩溃并以空状态恢复。投票号 $2$：承诺来自 $A_2$（报告什么都没有）和 $A_3$（什么都没有），于是提议者可以提议 $y$；$A_2$ 和 $A_3$ 接受——$y$ 被选定。相交的那个接受者 $A_2$ 忘了自己的接受，[[#thm-paxos]] 的归纳步骤便告失效。（只忘 $\mathit{promised}$ 也一样：接受者可以承诺投票号 $3$，忘掉，然后在依赖过它承诺的投票号 $3$ 提议者之后，接受一个旧的投票号 $2$ 的值。）

在 Raft 中，$\mathit{currentTerm}$、$\mathit{votedFor}$ 和日志是持久的。若 $\mathit{votedFor}$ 丢失，一台服务器就可能在同一任期给两个候选人投票——崩溃前一次、崩溃后一次——破坏 [[#prop-election-safety]]：同一任期可能选出两个领导者，它们可能创建索引与任期都相同而内容不同的条目，破坏日志匹配。若跟随者已确认过的日志条目丢失，计入多数派的条目就可能消失，破坏领导者完备性。
:::

::: exercise 共识与全序广播 {level=3}
(a) 给定共识算法（可供多个独立实例使用），实现全序广播。(b) 给定全序广播，解决共识。针对崩溃故障论证每个构造的正确性。
::: solution
(a) 每个进程可靠广播它想要全序广播的每条消息，并保存它已收到但尚未投递的消息集合，连同从 $1$ 开始的计数器 $k$。反复执行：把当前的待决集合提议给共识实例 $k$（必要时提议空集）；当实例 $k$ 决定集合 $S$ 时，把 $S$ 中尚未投递的消息按某个固定的确定性次序（比如按发送方和序号排序）投递，然后进入实例 $k + 1$。

*同一次序*：每个进程依次投递实例 $1, 2, \dots$ 决定的集合、都按同一方式排序，而由一致性所有进程看到的决定集合相同，所以它们的投递序列完全相同。*不凭空创造*：由有效性，被决定的集合是被提议过的，所以其中只含广播过的消息。*正确进程的每条消息都被投递*：由可靠广播，它最终进入每个正确进程的待决集合并留在其中直到投递。每个有故障的进程在崩溃前只在有限多个实例中提议过；在此之后的每个实例中，被决定的集合都由某个正确进程提议（有效性），而当所有正确进程都把该消息挂在待决集合中后，每次这样的提议都包含它。所以它会被投递。

(b) 每个进程全序广播自己的提议，并把第一个投递的消息的值决定下来。*一致性*：所有进程投递同一条第一个消息。*有效性*：它是某个进程的提议。*终止性*：每个正确进程都广播过，所以每个正确进程至少投递一条消息。*完整性*：只决定一次。于是两个问题等价，FLP 同样适用于全序广播。
:::
