一家搜索公司想统计一次全网抓取——$10$ TB 文本——中每个词出现的次数。一台以 $200$ MB/s 从磁盘读取的机器，光是读完数据就要 $14$ 小时。一千台机器一分钟内就能干完——前提是有人写出这样一个程序：切分输入、在每台机器上启动工作、把每个词的部分计数搬到负责该词的机器、把它们合并、应付崩溃的机器（一千台机器，每隔几小时总有一台会出故障）和快得莫名其妙的机器，再把结果写到某个持久的地方。对每个分析任务——数词频、建索引、把日志和用户表做连接、训练模型——都重写一遍这样的程序，成本高得离谱。

**大规模数据处理**系统只写它一次。程序员提供几个纯函数；系统把它们并行化、把数据搬来搬去、靠重跑工作来容忍故障。本章研究这样的三代系统。**MapReduce**（Dean 与 Ghemawat，2004）提出了映射、洗牌、归约的模型，用确定性重执行实现容错——我们证明它正确并加以模拟。**数据流**（Dataflow）系统如 Spark，把 MapReduce 推广到分区数据集上的算子图，把数据留在内存里、靠**血统**从丢失的分区恢复。**流处理器**处理不断到来的无界数据，这迫使人们仔细区分**事件时间**与**处理时间**，并引入**窗口**与**水位线**；它们的恰好一次保证来自 [[distributed-systems/time-clocks]] 的一致快照。自始至终，要紧的代价是跨网络搬运的字节数和最慢的任务。这些作业读写的存储系统就是 [[distributed-systems/distributed-storage]] 的那些；加速比的一般规律，如阿姆达尔定律，见 [[parallel-computing/performance-laws]]。

## MapReduce 模型

::: definition MapReduce {#def-mapreduce}
一个 **MapReduce** 作业由两个函数指定：
- $\mathit{map}\colon (k_1, v_1) \to \text{list}(k_2, v_2)$，独立地应用于每条输入记录；
- $\mathit{reduce}\colon (k_2, \text{list}(v_2)) \to \text{list}(v_3)$，对每个互异的中间键 $k_2$ 连同具有该键的**全部**中间值应用一次。

作业的输出是所有 reduce 调用输出的并集。系统负责把中间键值对按键分组——即**洗牌**（shuffle）。
:::

词频统计中，$\mathit{map}(\text{docId}, \text{text})$ 对文本里的每个词 $w$ 发出 $(w, 1)$，$\mathit{reduce}(w, [1, 1, \dots])$ 发出 $(w, \text{sum})$。倒排索引（[[information-retrieval/inverted-indexes]]）把每个文档映射成若干 $(w, \text{docId})$ 对，并把每个词的列表归约成一条排好序的倒排列表。分布式排序把每条记录映射成 $(\text{key}, \text{record})$，依靠洗牌按键有序地把键送达 reducer，并配一个把键区间按序送往各 reducer 的分区函数。连接、直方图、每次一步的图算法——出人意料地多的一族计算都能装进这个模型。

模型的威力来自它的禁忌：map 与 reduce 一次只见一条记录或一个键，不共享状态，没有副作用。于是每次调用都彼此独立，系统可以在任何地方、以任何次序、运行任意多次。

::: algorithm MapReduce 的执行 {#alg-mr-exec}
1. 把输入（在分布式文件系统中）切成 $M$ 个**切片（split）**，通常每个 $64$–$128$ MB。选定 $R$（reduce 任务的个数）和一个**分区函数**，默认为 $\mathit{hash}(k_2) \bmod R$。
2. 一个**主节点**把 map 任务指派给空闲的**工作节点**，优先选持有该任务切片某副本的机器上的工作节点（**数据本地性**），使输入从本地磁盘读出。
3. 一个 map 工作节点读取自己的切片，对每条记录应用 $\mathit{map}$，把中间键值对写进自己**本地磁盘**上的 $R$ 个分区——每个 reduce 任务一个——必要时先施加一个**合并器**（combiner）。它把分区位置报告给主节点。
4. 一个 reduce 工作节点从每个 map 工作节点取回自己的分区（**洗牌**），按键**排序**并合并，然后按键的次序对每个键及其值列表调用 $\mathit{reduce}$，把输出写进分布式文件系统里的一个临时文件。
5. 一个 reduce 任务完成时，把它**原子地重命名**临时文件为最终输出名。所有 $R$ 个 reduce 任务完成，作业结束。
:::

### 再执行带来的容错

主节点对工作节点发心跳。某个工作节点故障时，它进行中的任务被重置为空闲、改派他处。它*已完成的 map* 任务也会被重新执行，因为其输出在故障机器的本地磁盘上；已完成的 reduce 任务不会，因为其输出在复制过的文件系统里。尚未取回被重执行的 map 任务输出的 reducer，改从新工作节点取。为什么最终结果仍然正确？

::: theorem 确定性重执行等价于一次无故障运行 {#thm-reexec}
设 $\mathit{map}$ 与 $\mathit{reduce}$ 是其输入的确定性函数，每个 map 任务的输出只在该任务完成之后才被使用，且每个 reduce 任务的输出由至多成功一次的原子重命名提交。那么任何带有任意工作节点故障与重执行模式的执行，其输出都等于一次无故障执行的输出。
:::

::: proof
固定输入切片和分区函数。在一次无故障执行中，reduce 任务 $r$ 的输入是全体键落在分区 $r$ 中的中间键值对构成的多重集 $I_r$，它们从 $M$ 个 map 任务的输出 $O_1, \dots, O_M$ 收集而来，其输出是函数 $F(I_r)$（对每个键按排序次序施加 reduce），因为 $\mathit{reduce}$ 是确定性的。

在任意一次执行中，map 任务 $j$ 可能运行多次，但每次运行都对同一切片施加确定性的 $\mathit{map}$，所以产生同一个输出 $O_j$；reducer 只使用*已完成*的某次运行的输出，无论它从哪次取的。于是每个完成的 reduce 任务都恰好收到多重集 $I_r$，并恰好产生 $F(I_r)$，无论它是第几次尝试。原子重命名使恰有一个完成尝试的输出成为任务 $r$ 的最终输出，失败尝试的部分输出留在永不被重命名的临时文件里。因此每个 reduce 任务的最终输出——从而整个作业的输出——都等于无故障的输出。
:::

证明恰好指出了正确性可能在哪里丢失。若 $\mathit{map}$ 不确定——它随机采样、读时钟、或依赖哈希表的遍历次序——同一任务的两次尝试会产生不同的输出，而若不同的 reducer 从不同尝试取数，作业的输出就不对应*任何*一次执行（习题 8）。而 map 或 reduce 里的副作用，比如写外部数据库，是每次尝试发生一次，不是每个任务一次。这又是 [[distributed-systems/remote-communication]] 的至少一次执行：重执行之所以安全，恰在操作是确定性的、其唯一效果都被原子地提交之时。

同样的推理把主节点的故障也用重启作业的方式容忍了（最初的系统就这么干；后来的系统复制主节点的状态）。它容忍不了确定性的缺陷：一条能让 $\mathit{map}$ 崩溃的记录，每次尝试都会崩。因此 MapReduce 提供一种模式：在同一记录上反复失败若干次后，跳过该记录。

### 掉队者

作业在最后一个任务完成时结束，所以一台慢机器——一块出故障的磁盘、一个吵闹的邻居、一颗配置错误的 CPU——会拖住一切。这样的**掉队者**（straggler）在大规模下并不罕见。

::: proposition 等待 $m$ 个任务中最慢的那个 {#prop-straggler}
若 $m$ 个任务并行运行、持续时间相互独立且服从均值为 $1$ 的指数分布，则全部完成之前的期望时间是调和数
$$
H_m = 1 + \tfrac12 + \tfrac13 + \dots + \tfrac1m \approx \ln m + 0.5772.
$$
:::

::: proof
当仍有 $i$ 个任务在运行时，下一个完成之前的时间是 $i$ 个速率为 $1$ 的独立指数变量之最小值（由无记忆性，剩余时间仍是速率为 $1$ 的指数分布），即服从速率为 $i$ 的指数分布、均值 $1/i$。总时间是 $i = m, m - 1, \dots, 1$ 这些间隔之和，期望为 $\sum_{i=1}^m 1/i = H_m$。其中的近似是标准渐近式 $H_m = \ln m + \gamma + O(1/m)$，欧拉（Euler）常数 $\gamma \approx 0.5772$。
:::

一千个任务时，作业的期望时间约为平均任务时间的 $7.5$ 倍，几乎全都耗在等最后几个上。MapReduce 的补救是**备份任务**（推测执行）：临近某个阶段末尾时，主节点为仍在运行的任务启动复制副本，取先完成的那个——正因为有 [[#thm-reexec]]，这才安全。Dean 与 Ghemawat 报告，他们的排序基准测试在禁用备份任务后慢了 $44\%$。

caption: $m$ 个并行任务中最慢者完成所需的期望时间（以平均任务时间为单位），任务时间取指数分布（[[#prop-straggler]]）：阶梯函数是 $H_m$，光滑曲线是其近似 $\ln m + \gamma$。两个点是 $m = 100$（$5.2$）与 $m = 1000$（$7.5$）。注意曲线永不平坦：并行度每提高十倍，就要多等约 $2.3$ 个平均任务时间。真实任务时间的尾部常比指数更重，这让掉队者更糟、备份任务更值钱。
:::

### 合并器与洗牌的代价

洗牌把每个中间键值对都搬过网络，它通常是作业中最贵的部分。对词频统计，每篇文档里每出现一次 "the" 都变成一个发往某个 reducer 的对 $(\text{the}, 1)$。**合并器**是在洗牌之前对每个 map 任务的输出运行一次的 reduce 函数，于是每个 map 任务只需发一个 $(\text{the}, 7972)$，而不必发 $7972$ 个对。当归约可以分段进行时，它就是合法的。

::: proposition 合并器何时正确 {#prop-combiner}
设 $\mathit{reduce}(k, [v_1, \dots, v_n])$ 输出 $(k, v_1 \oplus v_2 \oplus \dots \oplus v_n)$，其中 $\oplus$ 满足结合律与交换律。那么对某个键的值任取若干不交的子集施加 $\oplus$（以任何次序），再对部分结果施加 $\mathit{reduce}$，与对全部值施加 $\mathit{reduce}$ 输出相同。
:::

::: proof
设键 $k$ 的值被划分为组 $G_1, \dots, G_t$（每个 map 任务一组），令 $c_j = \bigoplus_{v \in G_j} v$ 为合并器对第 $j$ 组以某种次序算出的输出。reduce 接着计算 $c_1 \oplus \dots \oplus c_t$，按部分结果到达的次序。由结合律，这个表达式等于去掉括号后全部值的 $\oplus$；由交换律，值的次序无关紧要。所以它等于 $v_1 \oplus \dots \oplus v_n$。
:::

求和、计数、最大、最小与集合并都合格。均值不直接合格——各组大小不同时，均值的均值是错的——但改成携带 (sum, count) 对就可合并，其分量和满足结合律与交换律（习题 9）。中位数则根本不存在小的可合并摘要。

::: example 词频统计，模拟 {#ex-wordcount}
在一个 Python 进程里模拟 MapReduce，输入 $100$ 篇合成文档、每篇 $200$ 词，$R = 4$ 个 reduce 分区。统计带与不带合并器时洗牌的中间对数，并检验重执行失败的 map 任务（每次尝试以 $0.3$ 的概率失败）不改变结果。
::: solution
```python
import random, re
from collections import defaultdict

def map_fn(doc_id, text):
    for word in re.findall(r"[a-z]+", text.lower()):
        yield word, 1

def reduce_fn(word, counts):
    yield word, sum(counts)

def mapreduce(inputs, R, combine=False, fail_prob=0.0, seed=0):
    rng = random.Random(seed)
    buckets = [defaultdict(list) for _ in range(R)]   # 洗牌：中间数据的 R 个分区
    shuffled = attempts = 0
    for doc_id, text in inputs:                      # 每个输入切片一个 map 任务
        while True:                                  # 重执行该任务直到成功
            attempts += 1
            out = defaultdict(list)
            for k, v in map_fn(doc_id, text):
                out[k].append(v)
            if rng.random() >= fail_prob:            # 工作节点存活：提交该任务的输出
                break
        if combine:                                  # 合并器：洗牌前在本地做 reduce
            out = {k: [v for _, v in reduce_fn(k, vs)] for k, vs in out.items()}
        for k, vs in out.items():
            buckets[hash(k) % R][k].extend(vs)
            shuffled += len(vs)
    result = {}
    for b in buckets:                                # 每个分区一个 reduce 任务，按键有序
        for k in sorted(b):
            result.update(reduce_fn(k, b[k]))
    return result, shuffled, attempts

rng = random.Random(1)
vocab = ["the", "of", "and", "data", "node", "map", "reduce", "fault", "log", "zipf"]
docs = [(i, " ".join(rng.choices(vocab, weights=[50, 30, 25, 5, 4, 3, 3, 2, 2, 1], k=200)))
        for i in range(100)]
plain, s1, a1 = mapreduce(docs, R=4)
comb, s2, _ = mapreduce(docs, R=4, combine=True)
fail, _, a3 = mapreduce(docs, R=4, fail_prob=0.3, seed=5)
print("top words:", sorted(plain.items(), key=lambda kv: -kv[1])[:3])
print("pairs shuffled without combiner:", s1, " with combiner:", s2)
print("same result with combiner:", plain == comb,
      " with 30% task failures:", plain == fail, f"({a3} attempts for {len(docs)} tasks)")
```

```console
$ python3 mapreduce.py
top words: [('the', 7972), ('of', 4883), ('and', 3920)]
pairs shuffled without combiner: 20000  with combiner: 977
same result with combiner: True  with 30% task failures: True (145 attempts for 100 tasks)
```

没有合并器时，全部 $20{,}000$ 次词的出现都穿过洗牌；有它时，每个 map 任务对见过的每个不同的词只发一个对——每篇至多 $10$ 个、共 $977$ 个——省了 $20$ 倍，且由 [[#prop-combiner]] 结果相同。有故障时，$100$ 个任务用了 $145$ 次尝试（期望次数是 $100/0.7 \approx 143$），而结果完全一致，正如 [[#thm-reexec]] 所保证的，因为 `map_fn` 是确定性的，且只有成功尝试的输出被提交。词频是倾斜的，真实文本正是如此：收到 "the" 的那个 reducer 拿到的数据远多于别的 reducer，这是一个只有合并器才压得住的热点。
:::
:::

### 连接

按键连接两个数据集是数据分析中最常见的操作，算法的选择就是在选择跨网络搬运什么。

- **重分区（洗牌）连接**把两个输入都映射成（连接键，带标记的记录）对；洗牌把两个输入中键相同的记录带到同一个 reducer，由它配对。两个输入都过一次网络。
- **广播（map 端）连接**适用于一个输入很小的情形：把它整个复制给每个 map 任务、装进哈希表，让大输入流过各 map 任务、探查哈希表。只有小输入搬运，每台机器一次。

::: example 选择连接算法 {#ex-join}
在 $100$ 台机器的集群上，按用户 id 把一个 $1$ TB 的页面浏览日志与一张 $2$ GB 的用户表连接。估算每种算法的网络流量。
::: solution
重分区连接洗牌两个输入：约 $1$ TB $+ 2$ GB $\approx 1.002$ TB，其中（在 $100$ 台机器间哈希分区）约 $99\%$ 会跨过网络——大约 $1$ TB。广播连接把 $2$ GB 表发给 $100$ 台机器：$200$ GB，而 $1$ TB 日志就地读取。这里广播连接省了五倍，且大的一侧越大，差距越大。若机器有 $1000$ 台，广播要花 $2$ TB，反而输了。一般地，当（机器数）$\times$（小表大小）$<$（大表大小）$+$（小表大小），且小表装得进每台机器的内存时，广播胜过重分区。分布式 SQL 引擎的查询优化器做的正是这个选择，用的是大小估计（[[databases/query-optimisation]]）。第三个选项：当两个输入已经按连接键同样地分区且有序时，可做完全不洗牌的归并连接。
:::
:::

## 数据流系统

MapReduce 僵硬的二段式形状对需要许多阶段的计算很别扭，而把每个阶段的输出写进复制文件系统的做法对**迭代**算法太慢。PageRank（[[information-retrieval/web-search]]）在同一张图上把同样的"连接再聚合"一步重复几十遍；作为一串 MapReduce 作业，它每轮迭代都要从磁盘重读图、把排名重写到三副本存储里。

数据流系统——Microsoft 的 Dryad（2007）、Apache Spark（2010–12）、Apache Flink 和 Google 的 Dataflow——把模型推广到分区集合上由算子（map、filter、join、group、aggregate……）构成的有向无环图（DAG），整体规划、整体优化。Spark 的核心抽象让容错不必复制也变得便宜。

::: definition 弹性分布式数据集与血统 {#def-rdd}
**弹性分布式数据集**（resilient distributed dataset，RDD；Zaharia 及合作者，2012）是一个不可变的记录集合，被切成**分区**；它要么由稳定存储中的数据定义，要么由对其他 RDD 的确定性**变换**（map、filter、join、groupByKey……）定义。定义一个 RDD 的那张变换图就是它的**血统**（lineage）。若子 RDD 的一个分区只依赖有限多个父分区，它对其父有**窄依赖**（map、filter、union、已共同分区的输入做 join），若它可能依赖所有父分区则是**宽依赖**（groupByKey、需要洗牌的 join）。
:::

RDD 可以留在内存里。一台机器故障、一些分区丢失时，Spark 从血统**重算**它们——重读输入、重新施加确定性变换——而不是事先复制过它们。这就是 [[#thm-reexec]] 提升到整张图的版本，也同样要求确定性。窄依赖重算便宜（只需相应的父分区），且能在一个任务内**流水线化**；宽依赖就是一次洗牌，标志一个**阶段边界**，它之后重算一个丢失分区可能需要每个父分区的数据——这就是 Spark 把洗牌输出写到本地磁盘、并让程序把长血统**检查点**到稳定存储的原因。结果是迭代作业跨轮把数据集留在内存里；RDD 论文报告，在迭代式机器学习负载上相对 Hadoop 最高加速 $20$ 倍。

::: example 恢复 PageRank 的丢失分区 {#ex-lineage}
一个 Spark PageRank 作业保存着 `links`（每个页面的出链，按页面哈希分区成 $100$ 个分区并缓存于内存），并在第 $i$ 轮从 `links.join(ranks_{i-1})` 算出 `ranks_i`，其后接一个把每个页面的份额发给其邻居的 `flatMap`，和一个按页对份额求和的 `reduceByKey`（分区器不变）。第 $10$ 轮之后，持有 `links` 和 `ranks_10` 的第 $37$ 号分区的机器发生故障。哪些东西必须重算？
::: solution
因为 `links` 和每个 `ranks_i` 共享同一哈希分区，这个 `join` 是窄依赖：连接数据的分区 $p$ 只依赖 `links` 和 `ranks_{i-1}` 的分区 $p$。`flatMap` 之后的 `reduceByKey` 是宽依赖——份额要跑到目标页面所在的分区——所以每轮迭代是一个洗牌阶段。

`links` 的分区 $37$ 由它的血统重算：重读输入文件中对应的块，重新施加解析与分区。`ranks_10` 的分区 $37$ 通过宽的 `reduceByKey` 依赖第 $10$ 轮 map 侧*全部* $100$ 个分区的洗牌输出。若那些洗牌文件还活在别的机器的本地磁盘上，Spark 只需重跑分区 $37$ 的 reduce 任务。若不在，它必须重跑第 $10$ 轮的 map 侧，而这需要完整的 `ranks_9`——如此沿血统一路回溯，最坏回到第 $0$ 轮。正是为了防止这种连环重算，长的迭代作业每隔几轮就把一个 RDD **检查点**到复制存储，截断一次故障可能迫使系统回放的血统。
:::
:::

::: warning 数据流不是数据库
数据流引擎常经由 SQL 使用，这让它看起来像数据库，但两者的故障语义不同。它们是为整份数据集的*确定性*重算设计的，不为并发事务性更新设计：在变换内部写外部存储的作业，会在每次重试和推测副本时重复那些写。要把变换当纯函数看待，把输出经引擎的已提交输出汇（sink）写出（它们用原子重命名或事务实现），让任何外部效果幂等（[[distributed-systems/remote-communication#def-idempotent]]）。
:::

## 流处理

批处理作业处理一个有界数据集，它在作业开始前已经齐备。许多数据源永无终止：点击、支付、传感器读数、日志行。**流处理器**持续运行一张数据流图，随记录到达更新结果——支付发生后几毫秒内给出欺诈分、比现实晚几秒而不是晚一天的仪表盘。

难点在时间。每条记录有一个**事件时间**——它何时发生（由源头打的时间戳）——和一个**处理时间**——系统何时看到它。两者相差网络时延、重试、离线手机上积压的缓冲、以及故障——有时差几秒，有时差几天。依赖于*事情何时发生*的结果——"每分钟点击数"、"每个用户的会话数"——必须按事件时间计算，可系统永远无法确信自己已经看到了截至某事件时间的全部事件。

::: definition 窗口与水位线 {#def-watermark}
**窗口**按事件时间把每条记录指派给一个或多个有限分组：**滚动**（tumbling）窗口是固定的不重叠区间（$[12{:}00, 12{:}01)$、$[12{:}01, 12{:}02)$……）；**滑动**（sliding）窗口长度固定而周期更短，因而彼此重叠；**会话**（session）窗口把一个键中间隔短于超时的记录归成一组。**水位线**是一个随记录在数据流中流动的时间戳 $W$，它断言不再期待事件时间早于 $W$ 的记录。当水位线越过 $t$，在 $t$ 结束的窗口就完整了，其结果可以被发出。以早于当前水位线的事件时间到达的记录与断言矛盾，是**迟到**记录：窗口尚未发出的迟到记录照常并入；窗口已经发出的则需要一个处理策略。
:::

水位线通常是启发式的——"见过的最大事件时间减去五秒"——因为数据源很少能知道再没有更旧的了。太激进的水位线会产出过早、不完整的结果和大量迟到记录；太保守的则让正确的结果来迟。Akidau 及合作者（2015）的 Dataflow 模型把这一折中挑明：**触发器**（trigger）决定何时发出窗口的结果（在水位线处、提早发推测结果、迟到数据到了再发一次），**允许迟到**（allowed lateness）决定窗口的状态为修正保留多久。

::: example 带迟到记录的滚动窗口计数 {#ex-window}
按事件时间对一分钟的滚动窗口统计点击数。水位线是见过的最大事件时间减 $10$ s。记录按以下顺序到达，事件时间为：$12{:}00{:}05$、$12{:}00{:}40$、$12{:}01{:}02$、$12{:}00{:}55$、$12{:}01{:}15$、$12{:}00{:}30$。各在何时发出什么计数？
::: solution
逐条追踪到达后的水位线 $W$：
1. $12{:}00{:}05$ → 窗口 $[12{:}00, 12{:}01)$ 有 $1$；$W = 11{:}59{:}55$。
2. $12{:}00{:}40$ → $2$；$W = 12{:}00{:}30$。
3. $12{:}01{:}02$ → 窗口 $[12{:}01, 12{:}02)$ 有 $1$；$W = 12{:}00{:}52$。
4. $12{:}00{:}55$ → 它晚于 $W$，不算迟到：窗口 $12{:}00$ 有 $3$；$W$ 停在 $12{:}00{:}52$（最大事件时间仍是 $12{:}01{:}02$）。
5. $12{:}01{:}15$ → 窗口 $12{:}01$ 有 $2$；$W = 12{:}01{:}05 > 12{:}01{:}00$，于是窗口 $[12{:}00, 12{:}01)$ 完整：**发出 $3$**。
6. $12{:}00{:}30$ → 它的事件时间早于 $W$：**迟到**。它的窗口已经发出。设有允许迟到时，系统把计数更新为 $4$ 并发出修正；没有允许迟到时，记录被丢弃（或送入侧输出）。

第 4 条记录晚于下一条已属下一分钟，却仍按时被计入，因为水位线的 $10$ s 余量罩住了它；第 6 条迟了 $35$ s，罩不住。换成处理时间窗口，就只会按到达次序计数，把各分钟混作一团。
:::
:::

### 恰好一次的状态

流处理器的算子保持状态——计数、开着的窗口、连接缓冲区——而且要连跑几个月，所以必须能从故障中恢复，既不漏算也不重复计算输入。Apache Flink（Carbone 及合作者，2015）的办法是把 Chandy–Lamport 快照（[[distributed-systems/time-clocks#alg-chandy-lamport]]）改造到数据流图上。

::: algorithm 异步屏障快照 {#alg-barrier}
源从可回放的日志（如 Kafka 分区）读取，其读位置（**偏移量**，offset）可被记录、可回卷。通道是 FIFO 的。
1. 要启动快照 $n$，每个源记录自己当前的偏移量，并向它的每条输出通道发出一个**屏障** $n$。
2. 有多个输入的算子在某个输入上收到屏障 $n$ 时，停止处理该输入（缓存其记录），直到它在**所有**输入上都收到屏障 $n$（**对齐**）。
3. 然后它把自己状态的一份副本写入持久存储（异步、写时复制），在全部输出上发出屏障 $n$，恢复处理，先处理缓存的记录。
4. 当每个算子都确认过屏障 $n$，快照 $n$ 即完成。发生故障时，每个算子从最近一个完整快照恢复状态，每个源回卷到记录的偏移量。
:::

::: theorem 屏障快照给出恰好一次的状态 {#thm-barrier}
在 FIFO 通道、对齐、确定性算子和可回放源的条件下，快照 $n$ 记录的状态恰是数据流处理完记录偏移量之前的那批源记录后到达的状态。于是恢复之后，每条源记录对算子状态恰好产生一次影响。
:::

::: proof
对每条通道，把屏障 $n$ 之前发出的记录称为*前屏障*记录。沿（无环的）图从源向下游归纳：每个算子的快照恰反映它的前屏障输入记录，而它在自己的屏障 $n$ 之前发出的记录恰是它由这些记录产生的输出。对源这按构造成立：它在偏移量之前的记录之后立即发出屏障。对算子，其输入的前屏障记录由归纳假设恰是上游算子前屏障处理的输出。由 FIFO，它们全都在各自通道的屏障 $n$ 之前到达；由对齐，算子在拍快照之前不处理任何输入的屏障后记录（缓存起来），而它已处理了每个前屏障记录，因为它等齐了每个输入上的屏障。所以它的快照恰反映其前屏障输入；又因它在快照之后、处理任何缓存记录之前发出屏障 $n$，它在屏障前发出的记录恰是由前屏障输入产生的那些。

因此快照是一个一致割（[[distributed-systems/time-clocks#def-cut]]），其中每条通道都是空的：对齐把 Chandy–Lamport 的信道状态收进了算子内部。恢复时，算子恰好恢复这个状态，源从记录的偏移量重放*未*反映在快照里的那些记录；算子是确定性的，重处理得出与第一次相同的结果。于是每条源记录在状态中恰好被反映一次——要么在快照里，要么被重放——绝不重复。
:::

"恰好一次"说的是对处理器*状态*的影响，不是记录被处理几次：故障之后，快照之后的记录会被再次处理。对外部系统的输出是另一回事。要让输出也恰好一次，汇必须幂等（按键写，重复覆盖自身）或是**事务性**的：Flink 的两阶段提交汇为每个快照区间在外部系统开一个事务，屏障到达时预提交，快照完成时提交——就是 [[distributed-systems/distributed-transactions]] 的原子提交协议，以快照完成为提交点。Kafka 的事务同样把消费者的输入偏移量与其输出原子地一起提交。对齐有代价：一条慢输入通道会拖住其他通道，背压下快照可能耗时很久，这催生了后来的**非对齐**检查点——把途中的记录随快照一并存储，正像 Chandy–Lamport 记录信道状态那样。

::: history
Teradata（1980 年代）、Gamma（DeWitt 及合作者，1986–90）、Bubba 等并行数据库早已把数据分区、用哈希分区连接并行运行关系算子。Jeffrey Dean 与 Sanjay Ghemawat 的《MapReduce：面向大型集群的简化数据处理》（"MapReduce: simplified data processing on large clusters"，OSDI 2004）让这一模型和靠重执行的容错声名远播；Doug Cutting 与 Mike Cafarella 的开源实现 Hadoop 于 2006 年跟进；David DeWitt 与 Michael Stonebraker 的批评《MapReduce：一大倒退》（"MapReduce: a major step backwards"，2008）认为它把并行数据库拙劣地重新发明了一遍。Michael Isard 及合作者于 2007 年描述了 Dryad，Grzegorz Malewicz 及合作者于 2010 年为图处理描述了 Pregel，Matei Zaharia 及合作者发表了 Spark（2010）与弹性分布式数据集（NSDI 2012）。流方面，Jay Kreps、Neha Narkhede 与 Jun Rao 于 2011 年描述了 Kafka；Twitter 的 Storm 同年开源；Google 的 MillWheel 出现于 2013 年；Tyler Akidau 及合作者的《Dataflow 模型》（"The dataflow model"，VLDB 2015）围绕事件时间、窗口、水位线与触发器统一了批与流。Paris Carbone 及合作者于 2015 年描述了 Flink 的异步屏障快照。
:::

## 后续内容

本章的思想与几门别的课程相接。并行加速及其极限——阿姆达尔定律与古斯塔夫森定律、通信的代价——在 [[parallel-computing/performance-laws]] 与 [[parallel-computing/message-passing]] 中展开。在 web 规模上构建倒排索引、计算 PageRank——MapReduce 的经典应用——见 [[information-retrieval/inverted-indexes]] 与 [[information-retrieval/web-search]]。分布式 SQL 引擎的查询优化承接 [[databases/query-optimisation]]。而训练大型机器学习模型本身就是一种分布式数据流，有自己的数据与参数分区，将在 LLM 图谱中讨论。

::: summary
- **MapReduce**：把每条记录映射成键值对、按键**洗牌**、对每个键的值做归约；分区、调度、本地性与故障都交给系统。
- **重执行**确定性任务、输出原子提交，得到与无故障运行相同的输出（[[#thm-reexec]]）；不确定性和副作用会破坏这一点。
- 作业要等最慢的任务——$m$ 个指数任务约 $\ln m$ 个平均任务时间（[[#prop-straggler]]）——所以**备份任务**很重要。
- 当 reduce 是满足结合律、交换律的折叠时，**合并器**削减洗牌流量（[[#prop-combiner]]）；按必须搬运什么来选择**广播**连接还是**重分区**连接。
- **数据流**系统运行算子 DAG；Spark 的 **RDD** 靠**血统**恢复丢失的分区，窄依赖可流水线化，宽依赖标记洗牌。
- 流处理区分**事件时间**与处理时间；**窗口**按事件时间分组，**水位线**决定窗口何时完整；迟到数据需要一个策略。
- 带对齐的**屏障快照**给出恰好一次的*状态*（[[#thm-barrier]]）；恰好一次的*输出*需要幂等或事务性的汇。
:::

::: exercise 数 map 任务 {level=1 check="8192"}
$1$ TiB 输入被切成 $128$ MiB 的切片，一片一个 map 任务。一共有多少个 map 任务？（填入数量。）
::: solution
$2^{40}/2^{27} = 2^{13} = 8192$ 个 map 任务。
:::

::: exercise 中间键值对 {level=1 check="8"}
词频统计的 map 对每个词发出 $(w, 1)$。对单个文档 "to be or not to be that is the question"（无标点），map 发出多少个中间对？合并器把它们归并成多少个？（填入合并后的数量。）
::: solution
文档有 $10$ 个词——to、be、or、not、to、be、that、is、the、question——所以 map 发出 $10$ 个对。不同的词是 to、be、or、not、that、is、the 和 question：$8$ 个。合并器发送 $8$ 个对，其中 $(\text{to}, 2)$ 和 $(\text{be}, 2)$ 各代替两个对。
:::
:::

::: exercise 掉队者 {level=1 check="25/12"}
用 [[#prop-straggler]]，$4$ 个并行、持续时间为均值 $1$ 的指数分布的任务，期望完成时间是多少？（填入数量。）
::: solution
$H_4 = 1 + 1/2 + 1/3 + 1/4 = 25/12 \approx 2.08$。
:::
:::

::: exercise 广播还是洗牌？ {level=2 check="400"}
在 $100$ 台机器的集群上，把一张 $500$ GB 的表与一张 $4$ GB 的表连接。广播连接通过网络发送多少 GB？哪种算法更便宜？（填入广播连接发送的 GB 数。）
::: solution
广播把 $4$ GB 发给 $100$ 台机器每台一份：$400$ GB。重分区连接约发送 $504$ GB（其中约 $99/100$ 跨过网络，约 $499$ GB）。这里广播略便宜，前提是 $4$ GB 能从容地装进每台机器做哈希表的内存；若机器有 $200$ 台，广播要花 $800$ GB，就输了。
:::
:::

::: exercise 迟到还是准时？ {level=2}
在 [[#ex-window]] 中，把水位线启发式改为"见过的最大事件时间减 $40$ s"。现在哪些记录迟到了？窗口 $[12{:}00, 12{:}01)$ 何时发出？
::: solution
每条记录到达后的水位线依次是 $11{:}59{:}25$、$12{:}00{:}00$、$12{:}00{:}22$、$12{:}00{:}22$、$12{:}00{:}35$、$12{:}00{:}35$。第 6 条记录（$12{:}00{:}30$）到达时事件时间低于水位线 $12{:}00{:}35$，按定义算迟到——但它的窗口还没发出，因为水位线仍在 $12{:}01{:}00$ 之前，所以照常计入。窗口 $[12{:}00, 12{:}01)$ 在水位线越过 $12{:}01{:}00$ 时发出，计数为 $4$，也就是当一条事件时间晚于 $12{:}01{:}40$ 的记录到达时。余量更大意味着发结果里漏掉的记录更少，但结果来得更晚。
:::
:::

::: exercise 窄还是宽？ {level=2}
把下列 Spark 变换的依赖判为窄或宽：(a) `map`；(b) `filter`；(c) `groupByKey`；(d) `union`；(e) 两个按连接键同样哈希分区的 RDD 做 `join`；(f) 分区互不相干的两个 RDD 做 `join`。`textFile → flatMap → map → reduceByKey → filter` 的阶段边界在哪里？
::: solution
(a)、(b)、(d) 窄：每个输出分区只依赖一个父分区（对 union 是某一父的一个分区）。(c) 宽：一个输出分区要从每个父分区收集一个键的值。(e) 窄：结果的分区 $i$ 只依赖每个输入的分区 $i$。(f) 宽：两个输入都得洗牌。在这条流水线里，`textFile`、`flatMap` 和 `map` 流水线化在一个阶段内；`reduceByKey` 需要洗牌，新阶段从此开始，包含 reduce 侧和 `filter`。
:::
:::

::: exercise 合并即折叠 {level=3}
证明：若 $\oplus$ 满足结合律、有单位元 $e$ 但*不*满足交换律，只要系统保持值的次序，合并器仍可正确使用：每个 map 任务对某键持有的值构成固定全局次序中的一段连续块，reduce 按该次序接收部分结果。举一个这样的操作的例子，并说明真实的 MapReduce 系统为什么不提供这个保证。
::: solution
设固定的全局次序下的值为 $v_1, \dots, v_n$，map 任务 $j$ 持有连续块 $v_{a_j}, \dots, v_{b_j}$，各块依序排列。合并器算出 $c_j = v_{a_j} \oplus \dots \oplus v_{b_j}$（由结合律，加括号方式随意），reduce 按序算出 $c_1 \oplus \dots \oplus c_t$。由结合律，整个表达式等于 $v_1 \oplus \dots \oplus v_n$ 的任意加括号形式；全程没有用到重排，所以不需要交换律。（空块贡献 $e$。）例子：字符串拼接，或函数的复合，或"取最后一个值"（当值按时间排序、用于保留最新事件时）。真实系统不提供这个保证，因为洗牌按 map 任务完成的次序交付部分结果——而完成次序随调度、重执行和备份任务而变——且一个键的值来自处理任意切片的各个任务；要施加次序就得按显式序号排序，这正是"二次排序"技巧做的事。
:::
:::

::: exercise 不确定的 map {level=3}
一个 map 函数用未播种的随机数生成器从其输入记录中采样 $1\%$。说明：在故障后重执行的情况下，作业的输出可能不对应任何一次无故障执行。你会怎么修复这个作业？
::: solution
设 map 任务 $j$ 已完成、reducer $1$ 已取回它给 $r = 1$ 的输出分区，随后工作节点在 reducer $2$ 取分区 $2$ 之前故障。主节点在另一台工作节点上重执行任务 $j$；新的随机种子会采样到*不同*的 $1\%$ 记录，reducer $2$ 取到新尝试的分区 $2$。于是 reducer $1$ 的输入反映样本 $S$，reducer $2$ 的反映样本 $S' \ne S$。最终输出混合了两个不同样本的片段——例如，所有键的采样记录总数未必等于任何一个样本的大小——所以它不是任何单次运行的输出。这正是 [[#thm-reexec]] 证明第一步的失效：同一任务的不同尝试产生了不同的输出 $O_j$。修复办法是让 map 确定化：用切片的标识给生成器播种；更好的做法是按哈希采样——当 $\mathit{hash}(\text{record id}) \bmod 100 = 0$ 时保留记录——每次尝试选出的都是同一批记录。
:::
:::

::: exercise 可合并的均值 {level=3}
为计算每个键取值的均值，写出可与 [[#ex-wordcount]] 模拟器配合使用的 `map_fn`、`reduce_fn` 和一个合并器，并依据 [[#prop-combiner]] 说明你的合并器为什么正确。
::: solution
携带 (sum, count) 对；按分量相加来合并；只在最后除一次。

```python
def map_fn(_, record):                 # record = (key, value)
    key, value = record
    yield key, (value, 1)

def combine_fn(key, pairs):            # 部分聚合：把和与计数分别相加
    yield key, (sum(s for s, _ in pairs), sum(c for _, c in pairs))

def reduce_fn(key, pairs):
    s = sum(s for s, _ in pairs)
    c = sum(c for _, c in pairs)
    yield key, s / c

parts = [list(combine_fn("a", [(1.0, 1), (3.0, 1)])), list(combine_fn("a", [(5.0, 1)]))]
print(list(reduce_fn("a", [p[0][1] for p in parts])))
```

```console
$ python3 mean.py
[('a', 3.0)]
```

运算 $(s_1, c_1) \oplus (s_2, c_2) = (s_1 + s_2, c_1 + c_2)$ 满足结合律与交换律，而 reduce 是"用 $\oplus$ 折叠，再相除"，所以由 [[#prop-combiner]]，无论值如何分组，折叠出的对都一样——总是 (总和, 计数)——最后的除法给出精确均值，这里是 $(1 + 3 + 5)/3 = 3$。模拟器的 `combine` 标志调用 `reduce_fn` 当合并器，所以这个作业需要像上面那样另配一个 `combine_fn`：reduce 函数本身（它做除法）*不是*合法的合并器。
:::
