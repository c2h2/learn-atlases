一家银行把账户存在分区到许多台机器的数据库里。一位客户要把 £100 从第 1 分片上的账户 $A$ 转到第 7 分片上的账户 $B$。第 1 分片必须借记 $A$，第 7 分片必须贷记 $B$，两者要么都发生，要么都不发生。若第 1 分片借记之后、第 7 分片还没来得及贷记就崩溃，钱就凭空消失了；若第 7 分片贷记了、第 1 分片却发现 $A$ 余额不足，钱又被凭空创造出来。在一台机器上，[[databases/transactions]] 的事务和 [[databases/recovery]] 的恢复日志保证原子性。跨机器——它们各自独立出故障、通过不可靠的网络通信——我们需要一个协议，让事务涉及的所有机器一致同意**提交**它，或者一致同意**中止**它。

本章研究这样的**原子提交**协议以及与之配套的并发控制。我们定义原子提交问题，并看清它与共识有何不同。我们研究**两阶段提交**，证明它安全，并证明它可能**阻塞**：一个参与者可能陷在那里、持有锁，直到崩溃的协调者恢复——这一点用一个小程序枚举每个崩溃点来验证。**三阶段提交**在崩溃故障下消除阻塞，在分区下则不能；让共识来决定提交（**Paxos Commit**）才能真正解决问题。然后我们把锁定和多版本并发控制扩展到跨机器，并证明 Google Spanner 基于 TrueTime 的**提交等待**给出**外部一致性**。最后我们讲 **Saga**——当事务横跨无法为彼此持锁的服务时的替代方案。

## 原子提交

一个分布式事务有一个**协调者**（通常是收到客户端请求的那台机器）和几个**参与者**（持有事务所触及数据的分片，也叫*资源管理器*）。每个参与者本地执行事务的自己的那部分，持有锁，然后就能判断自己能否提交：它可能因为约束违例、死锁或本地故障而不得不拒绝。

::: definition 原子提交 {#def-atomic-commitment}
每个参与者**投票** Yes 或 No，每个进程可**决定** Commit 或 Abort。一个**原子提交协议**保证：
- **一致性**：没有两个进程作出不同的决定；
- **有效性**：若有参与者投 No，决定是 Abort；且进程只有在所有参与者都投了 Yes 时才决定 Commit；
- **非平凡性**：若所有参与者都投 Yes 且不发生故障，决定是 Commit；
- **终止性**：在任何所有故障最终都被修复的执行中（每个进程最终恢复并一直运行，消息最终被投递），每个进程最终作出决定。

若终止性以更强的形式成立——即使某些其他进程仍处于崩溃、失联状态，每个正确（未崩溃、连通）的进程也作出决定——则称协议是**非阻塞**的。
:::

原子提交形似共识（[[distributed-systems/consensus#def-consensus]])——人人必须对两个值中的一个达成一致——但有两点不同。第一，*每个*参与者都有一票否决权：一个 No 就强制 Abort，所以决定取决于每个参与者的输入，而共识无需听到崩溃的少数派就能决定一个值。第二，投了 Yes 的参与者已经放弃了自行中止的权利；它必须等待决定。这些差别正是提交会在共识不必阻塞的地方阻塞的原因。

## 两阶段提交

两阶段提交（two-phase commit，2PC）由 Jim Gray 在 1978 年描述，Butler Lampson 与 Howard Sturgis 也在大约同时给出了一个版本；它至今仍是标准协议，用于分布式数据库和用于跨系统事务的 XA 标准。

::: algorithm 两阶段提交 {#alg-2pc}
*阶段 1（投票）。*
1. 协调者向每个参与者发送 $\textsf{prepare}$。
2. 能提交的参与者把一条 $\textsf{prepared}$ 记录**强制写入**自己的日志——包括日后提交或中止所需的一切，比如它的 redo 与 undo 信息以及它的锁——然后回复 $\textsf{yes}$。不能提交的参与者写一条中止记录、回滚并回复 $\textsf{no}$。

*阶段 2（决定）。*
3. 若所有票都是 $\textsf{yes}$，协调者把一条 $\textsf{commit}$ 记录强制写入自己的日志——即**提交点**——并向所有参与者发送 $\textsf{commit}$。若有任何一票是 $\textsf{no}$，或某张票在超时前没有到达，它写 $\textsf{abort}$ 并发送 $\textsf{abort}$。
4. 收到决定的参与者把它写入日志、提交或回滚、释放锁并发送确认。所有参与者都确认后，协调者可以忘掉这个事务。

*恢复。* 恢复的协调者重发其日志中的任何决定。发现自己有一条 $\textsf{prepared}$ 记录却没有决定的恢复参与者去询问协调者。还没有投票的参与者可以单方面中止。
:::

::: theorem 两阶段提交的安全性 {#thm-2pc}
在带稳定日志的崩溃恢复模型中，2PC 在每次执行中都满足一致性、有效性和非平凡性，无论消息如何延迟或丢失。若所有进程最终都恢复、所有消息最终都被投递（靠重传），它也满足终止性。
:::

::: proof
*有效性。* 协调者只有在收到每个参与者的 $\textsf{yes}$ 之后才决定 Commit（步骤 3），而投 No 的参与者会中止、永不提交；超时导致 Abort，绝不导致 Commit。

*一致性。* 只有协调者选择决定，且只选一次，并在发送之前把它持久记录下来。参与者作决定只有两种方式：(i) 收到协调者的决定；(ii) 在投 Yes *之前*单方面中止。情形 (ii) 中，协调者永远收不到该参与者的 Yes，所以它不可能决定 Commit，而会决定 Abort。已投 Yes 的参与者从不自行作决定，恢复的协调者重发记录在案的决定而不是重新选择。所以所有决定都等于协调者的决定。

*非平凡性。* 所有票为 Yes 且无故障时，每票都到达，协调者决定 Commit。

*终止性。* 若协调者在记录决定之前崩溃，恢复后它发现没有决定，就中止（若它从未记录过决定，就绝不可能发送过 Commit）。否则它重发决定。已投 Yes 的参与者不断询问协调者直到收到答复；只要最终能恢复、消息最终能投递，它们终会收到。
:::

对 $n$ 个参与者，2PC 的代价是 $4n$ 条消息（每个参与者的 $\textsf{prepare}$、投票、决定和确认）和两次往返，之后才能把结果告知客户端（在阶段 2 的决定记录之后——实际上提交记录一持久就可以告知了）。它需要在每个参与者（$\textsf{prepared}$ 记录）和协调者（提交记录）各一次强制日志写，通常还要在每个参与者为决定多一次非强制写。**假定中止**（presumed abort）之类的优化——对没有某事务记录的协调者，答"中止"，于是它不必记录中止也不必确认中止——以及投票后退出阶段 2 的只读参与者能削减开销。但根本问题不在开销。

::: example 跨地域提交的时延 {#ex-2pc-latency}
伦敦的一个协调者提交一个有两个参与者的事务：一个在伦敦（往返 $1$ ms），一个在纽约（往返 $70$ ms）。强制日志写处处耗时 $1$ ms。多久之后可以告诉客户端"已提交"？纽约的参与者收到 $\textsf{prepare}$ 之后要持有多久的锁？
::: solution
阶段 1：$\textsf{prepare}$ 在 $35$ ms 后到达纽约；纽约强制写入自己的 $\textsf{prepared}$ 记录（$1$ ms），它的票再过 $35$ ms 返回：最后一票在 $71$ ms 到达（伦敦的那票早就到了）。协调者强制写提交记录：$72$ ms。$72$ ms 时就可以告诉客户端了——这就是提交点。决定在 $72 + 35 = 107$ ms 到达纽约，参与者在那里写入决定、约 $108$ ms 释放锁。所以纽约在被要求准备*之后*持锁 $108 - 35 = 73$ ms，还要加上事务此前运行的时间；任何想要那些行的事务都得等这么久。倘若每个"站点"本身就像 Spanner 那样是散布在多个地区的复制共识组，每次强制日志写都变成一次法定数量往返，同样的计算被广域时延支配好几倍——这正是这类系统把一个共识组的副本、把常见事务的各参与者放在一起的原因。
:::
:::

### 阻塞

设想一个投了 Yes 之后便杳无音信的参与者。它处于**存疑**（in doubt，也称**不确定**）状态：它不能中止，因为协调者可能已决定 Commit 并告知了别人；它也不能提交，因为协调者可能已决定 Abort，或者某一票可能是 No。它必须等待，而等待期间它持有锁，于是每个触及同一数据的其他事务也只好等待。

::: proposition 两阶段提交会阻塞 {#prop-2pc-blocks}
设所有参与者都已投 Yes，随后协调者崩溃。在协调者恢复之前，一个没有收到决定、也联系不上任何收到决定的参与者的参与者，若不冒违反一致性的风险就无法作出决定。
:::

::: proof
考虑两次执行，在协调者收到最后一张 Yes 票之前它们完全相同。在 $E_1$ 中协调者随即崩溃，还没有记录任何决定；恢复后它将中止。在 $E_2$ 中它记录 Commit，向一个参与者 $q$ 发送 $\textsf{commit}$，$q$ 提交，然后它崩溃；恢复后它将重发 Commit。一个从协调者一无所获、也无法与 $q$ 通信的参与者 $p \ne q$ 在两次执行中的视角相同。若它决定 Commit，$E_1$ 中的一致性被违反；若它决定 Abort，$E_2$ 中的一致性被违反。所以它必须等待协调者（或 $q$）重新可达。
:::

**协作式终止协议**在某些情形下有帮助：存疑的参与者询问其他参与者，若其中有人有决定，或有人还没投票（因而可以中止并保证 Abort），存疑者就能作决定。但若所有可达的参与者都存疑——如证明之中——阻塞依旧。阻塞是本质性的：Skeen 与 Stonebraker（1983）证明，若网络可能分区，没有提交协议能是非阻塞的；而在异步系统中，非阻塞原子提交受制于 FLP 不可能性（[[distributed-systems/consensus#thm-flp]]），因为它将解决共识。

::: example 协调者的每个崩溃点 {#ex-2pc-crashes}
用三个参与者模拟 2PC，全部投 Yes，在其运行的每一步之后让协调者崩溃，并施加恢复（采用假定中止）。哪些崩溃点会让参与者被阻塞？原子性在所有情形下都保持吗？
::: solution
```python
def run(votes, crash_at):
    """2PC with one coordinator and len(votes) participants. The coordinator crashes after
    `crash_at` of its steps (None: no crash). Returns participant states before and after recovery."""
    n = len(votes)
    coord_log, part = [], ["init"] * n          # 参与者状态：init、prepared、committed、aborted
    steps = [("prepare", i) for i in range(n)] + [("log", None)] + [("decide", i) for i in range(n)]
    decision = "commit" if all(votes) else "abort"
    for k, (kind, i) in enumerate(steps):
        if k == crash_at:
            break                                # 协调者在这里崩溃
        if kind == "prepare":                    # 参与者投票；投 yes 先强制写入其日志
            part[i] = "prepared" if votes[i] else "aborted"
        elif kind == "log":
            coord_log.append(decision)           # 提交点：决定在协调者处持久化
        else:
            part[i] = decision + "ted" if decision == "commit" else "aborted"
    before = list(part)
    # 恢复（假定中止）：重发已记录的决定；没有任何记录则中止。
    final = coord_log[0] if coord_log else "abort"
    part = [s if s in ("committed", "aborted") else final + ("ted" if final == "commit" else "ed")
            for s in part]
    return before, part

n = 3
print("crash after step | states before recovery              | after recovery")
for crash_at in [0, 1, 3, 4, 5, None]:
    before, after = run([True] * n, crash_at)
    assert len(set(after)) == 1                  # 原子性：所有人最终结局相同
    blocked = sum(s == "prepared" for s in before)
    print(f"{str(crash_at):>16} | {', '.join(before):35} | {after[0]} (blocked: {blocked})")
before, after = run([True, False, True], None)
print("one 'no' vote, no crash ->", after)
```

```console
               0 | init, init, init                    | aborted (blocked: 0)
               1 | prepared, init, init                | aborted (blocked: 1)
               3 | prepared, prepared, prepared        | aborted (blocked: 3)
               4 | prepared, prepared, prepared        | committed (blocked: 3)
               5 | committed, prepared, prepared       | committed (blocked: 2)
            None | committed, committed, committed     | committed (blocked: 0)
one 'no' vote, no crash -> ['aborted', 'aborted', 'aborted']
```

原子性在每个崩溃点都成立（`assert` 从未触发）。崩溃点 $3$ 和 $4$ 两行是 [[#prop-2pc-blocks]] 证明的缩影：参与者的状态*完全相同*——全都 prepared——结局却不同，因为唯一的差别，提交记录有没有到达协调者的日志，对它们不可见。三个参与者全部被阻塞、持着锁，直到协调者回来。崩溃点 $5$ 时，一个参与者已经提交；另外两个可以用协作式终止协议从它那里得知结果。仍处于 `init` 状态的参与者没有被阻塞：它们没有投票，可以自行中止。
:::

## 三阶段提交

Dale Skeen 的**三阶段提交**（three-phase commit，3PC，1981–83）在只有崩溃故障的同步系统假设下消除阻塞。它的思路来自 [[#prop-2pc-blocks]] 的证明：在 2PC 中，已准备（prepared）参与者的状态既与已提交状态"相邻"（别的参与者可能已提交），也与已中止状态相邻（协调者可能中止）。3PC 插入一个**预提交**（pre-commit）阶段，使得只要还有任何运行中的进程存疑，就没有进程能提交。

::: algorithm 三阶段提交 {#alg-3pc}
1. **CanCommit。** 同 2PC 的阶段 1：协调者询问；参与者投票，投 Yes 者变为**存疑**。
2. **PreCommit。** 若全投 Yes，协调者向所有参与者发送 $\textsf{precommit}$；每个参与者变为**预提交**并确认。否则协调者发送 $\textsf{abort}$。
3. **DoCommit。** 收到对 $\textsf{precommit}$ 的每一个确认之后，协调者发送 $\textsf{commit}$；参与者提交。

*终止协议*，在协调者被检测到已崩溃时由幸存者运行（在同步系统中这是精确的）：在运行中的参与者里选出一个新协调者，收集它们的状态。若任何参与者已提交或已预提交，就向尚未预提交者发送 $\textsf{precommit}$，然后向所有人发送 $\textsf{commit}$。若无人如此（全都存疑或已中止），发送 $\textsf{abort}$。
:::

::: proposition 在同步系统的崩溃故障下 3PC 是非阻塞的 {#prop-3pc}
在可靠链路、精确故障检测（同步模型）和崩溃故障下，3PC 满足一致性和有效性，且每个运行中的参与者最终都作出决定，即使协调者和其他参与者已经崩溃。
:::

::: proof
*关键不变式。* (a) 参与者只有在每个参与者都投了 Yes 时才会预提交，因为协调者只在那时才发送 $\textsf{precommit}$。(b) 若任何进程已提交，则每个参与者在那之前都已预提交（或已提交），因为 $\textsf{commit}$ 只在每个参与者都确认了 $\textsf{precommit}$ 之后才发送——由最初的协调者发送，或由一个先把每个运行中的参与者都带到预提交状态的终止协调者发送。(c) 若任何进程已中止，则没有进程预提交或提交：中止只发生在任何 $\textsf{precommit}$ 发送之前（投 No 或 CanCommit 超时），或由一个发现无人预提交的终止协调者作出——而有精确的故障检测和同步链路，崩溃协调者的 $\textsf{precommit}$ 不可能在此之后仍滞留途中。

*一致性。* 若某进程提交，由 (b) 每个运行中的参与者都已预提交或已提交，所以此后运行的终止协议会看到这样的状态并提交。若某进程中止，由 (c) 没有参与者预提交，所以此后运行的终止协议会中止。于是没有两个进程作出不同决定。*有效性*：提交需要一个预提交的参与者，而由 (a) 所有参与者都投了 Yes。

*非阻塞。* 终止协议只使用运行中参与者的状态，且得益于精确的故障检测，能在有界时间内完成；若新协调者崩溃，幸存者重新运行它，由同样的不变式保证安全。
:::

致命的假设是精确的故障检测。若网络**分区**，一组全部预提交的参与者和一组全部存疑的参与者可能各自断定对方已经崩溃，各自运行终止协议，分别决定 Commit 和 Abort——一致性被违反（习题 8）。由于真实网络会分区，3PC 很少被使用。

### 通过共识决定提交

稳健的补救是复制协调者的决定，让它容错。Jim Gray 与兰波特（Lamport）的 **Paxos Commit**（2006）让每个参与者的票由一组 $2f + 1$ 个接受者经由一个 Paxos 实例记录；当每个实例都决定 Yes 时事务提交。只要有法定数量的接受者可用它就是非阻塞的，且在常见情形下消息延迟与 2PC 相同。实践中这个想法最简单的形式，是把协调者以及每个参与者都当作复制状态机来运行：在 Spanner 中每个分片是一个 Paxos 组（[[distributed-systems/distributed-storage]]），协调者的提交记录是一条 Paxos 日志条目，"崩溃的协调者"几秒之内就被协调者所在组的新领导者取代，新领导者从复制日志中读出决定。2PC 的阻塞并未消失，但现在它需要的是某个组的*多数派*失效，而不是单台机器失效。FLP 仍适用于底层的共识，所以足够不走运的网络仍能拖住进展——但绝不可能破坏原子性。

- [ ] 所有参与者都确认了提交时
::: solution
提交记录持久之前，崩溃会在恢复时导致 Abort，即使所有票都是 Yes。一旦持久，恢复时便会重发 Commit，结局就此确定。这就是协调者要强制写那条记录的原因：它是**提交点**，与 [[databases/recovery]] 中单机数据库的提交记录完全一样。
:::
:::

## 分布式并发控制

原子提交让分布式事务要么全做要么全不做。隔离性——并发事务表现得像逐个执行——则需要跨机器的并发控制。

**分布式两阶段锁定。** 每个参与者对自己的数据运行严格两阶段锁定（[[databases/transactions]]），持有全部锁直到事务的提交或中止为人所知，即直到 2PC 的阶段 2。各站点的严格 2PL 加上 2PC 给出全局的（冲突）可串行化：每个事务的锁在其提交点处仍在所有站点持有，按提交点给事务排序就得到与每个站点的冲突相容的串行次序。代价是事务的锁要横跨网络往返持有——而协调者出故障时，要持有多久就取决于 2PC 阻塞多久。

**分布式死锁。** 锁散布在许多台机器上时，等待图也散布在各站点：$T_1$ 在第 1 分片上等待 $T_2$，而 $T_2$ 在第 7 分片上等待 $T_1$，哪个站点都看不见环。检测需要拼出全局图（集中式，或像 1983 年的 Chandy–Misra–Haas 算法那样沿等待边发送探针）——而拼出来的图若不是一个一致快照，就可能报告**幻影死锁**。许多系统改用**超时**（让等了太久的事务中止）或用时间戳预防死锁——**等待–死亡**（wait-die）与**伤害–等待**（wound-wait）——它们不需要全局信息，因为每个站点比较的都是同样的全局唯一时间戳。

**多版本并发控制。** 快照隔离与可串行化的 MVCC 同样可以分布式化（[[databases/transactions]]），前提是时间戳跨机器一致：事务在每个分片上读取"始于"其开始时间戳的快照，而只有当带较旧时间戳的提交对带较新时间戳的读者在*每个*分片上都可见时，这个快照才有意义。Google 的 **Percolator**（Peng 与 Dabek，2010）在 Bigtable 上为增量 web 索引提供快照隔离，从中心**时间戳预言机**（timestamp oracle）取得时间戳；TiDB 也是如此。中心预言机简单而正确，但每个事务都要一次往返，跨地区时还很长。Spanner 则从时钟取得一致的时间戳。

### Spanner 与外部一致性

::: definition 外部一致性 {#def-external}
一个事务系统是**外部一致**的（严格可串行化的），若它可串行化，且串行次序尊重现实时间：若事务 $T_1$ 在 $T_2$ 开始之前提交（按绝对时间），则 $T_1$ 在串行次序中先于 $T_2$。对基于时间戳的系统：若 $T_1$ 在 $T_2$ 开始前提交，则 $s_1 < s_2$，其中 $s_i$ 是 $T_i$ 的提交时间戳。
:::

外部一致性是把线性一致性（[[distributed-systems/replication-consistency#def-linearisable]]）提升到事务层面。它正是用户所期待的：你若看到自己的转账得到确认，再告诉同事，同事去查就能看到。Spanner 用 [[distributed-systems/time-clocks]] 的 TrueTime 接口做到这一点：$\mathrm{TT.now}()$ 返回一个区间 $[\mathit{earliest}, \mathit{latest}]$，保证包含调用它那一刻的绝对时间。

::: algorithm 带提交等待的 Spanner 提交 {#alg-commit-wait}
对读写事务 $T$，在其协调者领导者取得全部锁之后（对多分片事务，所有参与者都已准备之后）：
1. 选取提交时间戳 $s \ge \mathrm{TT.now}().\mathit{latest}$，在全部锁都已持有时求值（并且大于本领导者先前指定的任何时间戳以及各参与者的任何准备时间戳）。
2. **提交等待**：在 $\mathrm{TT.now}().\mathit{earliest} > s$ 之前，不使 $T$ 的写入可见、不释放其锁、不向客户端报告提交。
3. 然后以时间戳 $s$ 应用写入，释放锁并回复。
:::

::: theorem 提交等待给出外部一致性 {#thm-external}
若 TrueTime 的区间始终包含绝对时间，则对任何满足"$T_1$ 的提交在 $T_2$ 开始之前可见（其提交等待已结束）"的事务 $T_1$ 与 $T_2$，提交时间戳满足 $s_1 < s_2$。
:::

::: proof
用 $t_{\mathrm{abs}}(e)$ 表示事件 $e$ 的绝对时间。设 $e_1$ 为 $T_1$ 提交等待的结束。在 $e_1$，$\mathrm{TT.now}().\mathit{earliest} > s_1$，而区间包含绝对时间，所以 $t_{\mathrm{abs}}(e_1) \ge \mathit{earliest} > s_1$。$T_2$ 在事件 $e_2$ 开始，$t_{\mathrm{abs}}(e_2) > t_{\mathrm{abs}}(e_1)$，并在之后的事件 $e_3$（取得其锁之后）选取时间戳 $s_2 \ge \mathrm{TT.now}().\mathit{latest} \ge t_{\mathrm{abs}}(e_3)$。串联起来：$s_2 \ge t_{\mathrm{abs}}(e_3) > t_{\mathrm{abs}}(e_2) > t_{\mathrm{abs}}(e_1) > s_1$。
:::

提交等待约长 $2\varepsilon$，其中 $\varepsilon$ 是 TrueTime 区间的半宽：$s$ 约在 $\mathit{true} + \varepsilon$ 处选取，等待在 $\mathit{earliest} = \mathit{true}' - \varepsilon$ 超过它时结束，即 $\mathit{true}' \approx \mathit{true} + 2\varepsilon$。按 2012 年论文报告的 $1$–$7$ ms 不确定度，等待是几毫秒到十四毫秒，并与提交记录的 Paxos 复制重叠，上文图例所示。定理完全依赖 TrueTime 的保证：若某台机器的时钟误差超过 $\varepsilon$，外部一致性会悄无声息地失效，这就是 Spanner 的时间主服务器要交叉核对 GPS 与原子钟、并淘汰时钟失常机器的原因。同样的时间戳还提供**无锁快照读**：时间戳为 $t$ 的只读事务在每个分片上按 $t$ 读取，只需等到每个分片确信没有更小时间戳的提交仍在悬而未决。

::: example 外部一致性现场演示 {#ex-commit-wait}
TrueTime 的 $\varepsilon = 4$ ms。事务 $T_1$ 在绝对时间 $100.000$ s 取得其锁。它何时变得可见？带什么时间戳？此后开始的事务 $T_2$ 能拿到的最小时间戳是多少？
::: solution
设 TrueTime 的区间以真实时间为中心。绝对时间 $100.000$ s 时，$\mathrm{TT.now}()$ 返回 $[99.996, 100.004]$，于是 $s_1 = 100.004$。提交等待持续到 $\mathit{earliest} > 100.004$，即绝对时间超过 $100.008$：$T_1$ 约在 $100.008$ s 变得可见，比它取得锁晚 $2\varepsilon = 8$ ms。那之后开始的事务 $T_2$ 选取 $s_2 \ge \mathit{latest} \ge$ 绝对时间 $> 100.008 > s_1$，正如 [[#thm-external]] 所说。

若没有等待，$T_1$ 会在 $100.000$ 就可见。一个 $100.001$ 在这样一台机器上开始的 $T_2$——它（正确的）区间为 $[99.993, 100.001]$、真实时间恰在区间右端——可能选到 $s_2 = 100.001 < s_1$；它的快照就会漏掉 $T_1$，尽管 $T_1$ 已对用户可见。
:::
:::

**确定性数据库**另辟蹊径。Calvin（Thomson 及合作者，2012）先通过共识就事务请求的全局*次序*达成一致，然后每个分片按该次序确定性地执行它们。既然每个副本和分片都事先知道次序，就根本不需要任何提交协议——事务不可能在一个分片失败而在另一个成功，除非出于每个分片都看得见的确定性原因——代价是要预先声明每个事务的读集与写集。

## Saga：没有锁的事务

跨组织或跨独立部署的服务——一个支付提供商、一家航空公司、一家酒店——2PC 通常不可接受：没有服务肯让别家持有自己的锁，协调者的故障也绝不能把它们冻住。Hector Garcia-Molina 与 Kenneth Salem 的 **Saga**（1987）索性放弃隔离性。

::: definition Saga {#def-saga}
**Saga** 是一串本地事务 $T_1, T_2, \dots, T_k$——每个由一个服务独立提交——外加**补偿事务** $C_1, \dots, C_{k-1}$，其中 $C_i$ 在语义上撤销 $T_i$。Saga 保证：要么 $T_1, \dots, T_k$ 全部提交，要么若某个 $T_j$ 失败，则 $T_1, \dots, T_{j-1}, C_{j-1}, \dots, C_1$ 提交。
:::

用 Saga 订票：订机票、订酒店、刷卡扣款；若扣款失败，取消酒店订单再取消机票。每一步和每个补偿都必须重试到成功为止，所以每一步都必须**幂等**（[[distributed-systems/remote-communication#thm-dedup]]），而 Saga 的进度由一个编排器持久记录，或以日志中的事件记录（**发件箱**（outbox）模式把事件与状态变更写在同一个本地事务里，使两者不可能只发生一个）。

::: example 一个失败的 Saga {#ex-saga}
编排器运行 Saga：$T_1$ = 订座，$T_2$ = 订房，$T_3$ = 扣款，补偿为 $C_1$ = 释放座位、$C_2$ = 释放房间。银行卡被拒付，而编排器在刚发出 $C_2$ 之后崩溃一次。追踪会发生什么。
::: solution
编排器在每一步执行前后都先记入自己的持久日志。(1) 它记下"开始 $T_1$"，以幂等键 $(s, 1)$ 调用航空公司；座位订上；它记下"$T_1$ 完成"。(2) 对 $T_2$ 与酒店做同样的事。(3) 它以键 $(s, 3)$ 调用支付服务；卡被拒，于是 $T_3$ 失败（它的本地事务中止，没有可补偿的）；它记下"$T_3$ 失败，开始补偿"。(4) 它记下"开始 $C_2$"，以键 $(s, \bar 2)$ 调用酒店取消；酒店释放房间；编排器在记录结果之前崩溃。(5) 重启后它读日志，看到 $C_2$ 已开始而未完成，就用同一个键再次调用取消；酒店认出这个键，直接返回存好的结果而不再做任何事。它记下"$C_2$ 完成"。(6) 它照同样的方式运行 $C_1$，记下"Saga 已中止"。最终状态就像什么都没订过——但有一阵子，其他顾客看到座位和房间是被占着的。
:::
:::

::: warning Saga 没有隔离性
在 $T_1$ 与其后可能的补偿 $C_1$ 之间，其他事务能看到 $T_1$ 的效果：航班座位显示被订出、又变回空位；确认酒店的邮件已发出去、随后又是取消。补偿是语义上的，不是回滚——发出去的邮件收不回，退款也不等于从未被扣款。Saga 给出的原子性是"终究要么全有要么全无"意义上的，ACID 的隔离性一点也没有，所以应用必须为这些中间状态做设计，比如把记录标记为待处理，或者安排步骤顺序，把最可能失败、最难补偿的步骤放到最后。
:::

::: history
Jim Gray 在《Notes on data base operating systems》（1978）中描述了两阶段提交；Butler Lampson 与 Howard Sturgis 在 1976 年 Xerox PARC 一篇关于分布式存储系统崩溃恢复的未发表论文中给出了一个版本。Dale Skeen 的《非阻塞提交协议》（"Nonblocking commit protocols"，SIGMOD 1981）引入了三阶段提交和阻塞理论；他与 Michael Stonebraker 合著的《分布式系统中崩溃恢复的形式模型》（"A formal model of crash recovery in a distributed system"）发表于 1983 年。C. Mohan、Bruce Lindsay 与 Ron Obermarck 的假定中止与假定提交优化（1986）在 IBM 的 R* 项目中实现。Philip Bernstein、Vassos Hadzilacos 与 Nathan Goodman 的《数据库系统的并发控制与恢复》（*Concurrency Control and Recovery in Database Systems*，1987）把原子提交形式化。Hector Garcia-Molina 与 Kenneth Salem 的《Saga》发表于 SIGMOD 1987。分布式事务的 X/Open XA 标准始于 1991 年。Jim Gray 与兰波特（Lamport）的《事务提交的共识》（"Consensus on transaction commit"，*ACM TODS*，2006）定义了 Paxos Commit。Daniel Peng 与 Frank Dabek 在 OSDI 2010 描述了 Percolator；Alexander Thomson 及合作者的 Calvin 和 James Corbett 及合作者的 Spanner 都发表于 2012 年。
:::

## 后续内容

分布式事务融汇了它前面的一切：数据库的日志与恢复、法定数量与复制、用于复制协调者的共识、用于时间戳的时钟。[[distributed-systems/data-processing]] 对规模化的正确性采取不同的思路：批处理器和流处理器彻底避开细粒度事务，靠确定性重执行、并把*输出*与输入位置一起原子提交来保证结果正确——这是本章所研究的原子提交的一个狭窄而高效的形态。

::: summary
- **原子提交**：所有参与者要么都提交要么都中止；任何一个 No 票都强制 Abort。与共识不同，每个参与者都有一票否决。
- **两阶段提交**——先准备/投票，再决定——在每次执行中都安全（[[#thm-2pc]]）；**提交点**是协调者持久的提交记录。
- 2PC 会**阻塞**：协调者宕机时，已准备的参与者无法作决定（[[#prop-2pc-blocks]]），且持着锁；网络可能分区时，阻塞是本质性的。
- **三阶段提交**在精确故障检测下的崩溃故障中非阻塞（[[#prop-3pc]]），分区下却不安全；**Paxos Commit** 与复制协调者使提变成容错的。
- 各站点严格 2PL 加 2PC 给出全局可串行化；分布式死锁需要全局检测、超时或基于时间戳的预防。
- **Spanner 的提交等待**约 $2\varepsilon$，基于 TrueTime 给出**外部一致性**（[[#thm-external]]）；时间戳预言机（Percolator）或全局次序（Calvin）是替代方案。
- **Saga** 用补偿替代隔离，用于跨自治服务的事务；步骤与补偿必须幂等。
:::

## 习题

::: exercise 数 2PC 的消息 {level=1 check="20"}
一个有 $5$ 个参与者（外加独立协调者）的事务，所有票为 Yes、无故障，2PC 一共发送多少条消息（算上确认）？（填入数量。）
::: solution
每个参与者的 $\textsf{prepare}$、投票、决定和确认：$4 \times 5 = 20$。
:::
:::

::: exercise 谁可以中止？ {level=1}
在 2PC 中，下列谁可以在不问任何人的情况下自行中止事务：(a) 一个还没有收到 $\textsf{prepare}$ 的参与者；(b) 一个已投 Yes 的参与者；(c) 还没有记录决定的协调者；(d) 已记录 Commit 之后的协调者？
::: solution
(a) 可以——它会投 No（或不投票，协调者会超时）。(b) 不行——它存疑，必须等待。(c) 可以——不可能有人被告知过 Commit。(d) 不行——决定已不可挽回。(a) 与 (b) 之间的不对称就是这个协议的全部难点。
:::
:::

::: exercise 提交等待 {level=1 check="14"}
TrueTime 的不确定度为 $\varepsilon = 7$ ms。Spanner 的提交等待大约多长（毫秒）？（填入毫秒数。）
::: solution
约 $2\varepsilon = 14$ ms，理由见 [[#thm-external]] 之后的论证。
:::
:::

::: exercise 提交的概率 {level=2 check="0.999^8"}
一个事务触及 $8$ 个分片；每个分片独立地以 $0.999$ 的概率能够投 Yes（否则它投 No 或联系不上、协调者超时）。事务提交的概率是多少？（填入概率。）
::: solution
2PC 只有在每个参与者都投 Yes 时才提交：$0.999^8 \approx 0.992$。每多一个分片就把中止率乘上一个倍数——即 [[distributed-systems/system-models#ex-availability]] 的"需要全部"曲线——这就是系统要靠选好分区键把事务尽量约束在单个分片内的原因。
:::
:::

::: exercise 假定中止 {level=2}
在假定中止之下，在记录决定之前崩溃的协调者不保留该事务的任何记录，对任何询问它不认识的事务的参与者回答"中止"。解释为什么这是安全的，以及它为什么在中止时省下日志写和消息。为什么它*不能*对不认识的事务回答"提交"（除非再做别的改动）？
::: solution
协调者没有记录，就从未记录过 Commit，于是从未发送过 Commit，于是没有参与者可能已提交：Abort 是唯一自洽的答复。中止时协调者不必强制写中止记录（没有记录就意味着中止），参与者也不必确认中止，因为协调者无需知道自己何时可以忘掉一个它毫无记录的事务。对不认识的事务答"提交"，对一个已被中止（或从未到达决定）而后被忘掉的事务就是错的；所以*假定提交*要求协调者在发送 $\textsf{prepare}$ *之前*强制写一条列出参与者的记录，以便崩溃之后知道自己该中止哪些事务。
:::
:::

::: exercise 一个分布式死锁 {level=2}
$T_1$ 持有第 1 分片上 $x$ 的锁，并请求第 2 分片上的 $y$；$T_2$ 持有第 2 分片上的 $y$，并请求第 1 分片上的 $x$。时间戳为：$T_1$ 是 $10$，$T_2$ 是 $20$（小者为旧）。说明为什么两个分片各自的本地等待图都没有环。在伤害–等待（wound-wait）下会发生什么？
::: solution
第 1 分片的图有边 $T_2 \to T_1$（$T_2$ 等待 $T_1$ 持有的 $x$）；第 2 分片的图有 $T_1 \to T_2$。各自无环；只有并集有环 $T_1 \to T_2 \to T_1$。在伤害–等待（wound-wait）下，较旧的事务请求较新事务持有的锁就**伤害**（中止）对方，较新的请求较旧的则等待。在第 2 分片，$T_1$（较旧）向 $T_2$（较新）请求 $y$：$T_2$ 被中止、释放 $y$，$T_1$ 得以前进。在第 1 分片，$T_2$ 等待较旧的 $T_1$，这是允许的——何况它反正也被中止了。不需要任何全局信息，因为两个分片比较的是同样的时间戳；$T_2$ 稍后以*原有*时间戳重启，所以它终将成为最旧的，不会饿死。
:::
:::

::: exercise 没有提交等待的外部一致性 {level=3}
证明：若 Spanner 仍取 $s \ge \mathrm{TT.now}().\mathit{latest}$ 但跳过提交等待，外部一致性就会失效——构造两个在不同机器上的事务，它们的 TrueTime 区间都正确。然后解释为什么用单一时钟的单机数据库不需要提交等待。
::: solution
设 $\varepsilon = 4$ ms。$T_1$ 在绝对时间 $t = 100.000$ 于机器 $M_1$ 上取得其锁，$M_1$ 的区间为 $[100.000, 100.008]$——正确，因为它包含 $t$——于是 $s_1 = 100.008$。没有提交等待，$T_1$ 在 $100.000$ 就可见。$T_2$ 在 $100.001$ 于 $M_2$ 上开始，$M_2$ 在选时间戳时的区间为 $[99.993, 100.001]$，正确，得到 $s_2 = 100.001 < s_1 = 100.008$。$T_2$ 在 $T_1$ 可见之后开始，却有 $s_2 < s_1$，于是按时间戳次序 $T_2$ 先于 $T_1$：在 $s_2$ 处的快照读会漏掉 $T_1$。外部一致性失效。

在一台机器上，只有一个单调时钟（或计数器）时，在 $T_1$ 提交之后开始的事务读钟更晚、拿到更大的时间戳，因为时钟从不倒退。提交等待补偿的是*多个*时钟之间仅以 $2\varepsilon$ 为界的不一致。
:::
:::

::: exercise 分区下的 3PC {level=3}
给出一个四个参与者、发生网络分区的 3PC 执行，其中两个参与者提交、两个中止。[[#prop-3pc]] 的哪条假设被违反了？
::: solution
四人全投 Yes。协调者发送 $\textsf{precommit}$；它到达参与者 $P_1$ 和 $P_2$，随后网络在 $P_3$、$P_4$ 收到之前分裂为 $\set{\text{协调者}, P_1, P_2}$ 和 $\set{P_3, P_4}$。协调者收不到 $P_3$、$P_4$ 的确认，随后崩溃（或干脆被切断）。第一侧，$P_1$ 和 $P_2$ 检测到协调者失效（或它还活着、只是把 $P_3, P_4$ 当作已崩溃），运行终止协议，发现预提交的参与者，于是**提交**。另一侧，$P_3$ 和 $P_4$ 怀疑所有其他人，运行终止协议，只发现存疑的参与者，于是**中止**。一致性失效。被违反的假设是精确的故障检测：分区使存活的进程与崩溃的进程不可区分（[[distributed-systems/system-models#thm-indistinguishable]]），而证明中的不变式 (c)——决定中止时不存在任何 $\textsf{precommit}$——不成立，因为作决定的一侧看不见另一侧。
:::
:::

::: exercise 一次旅行的 Saga {level=3}
为"订机票、订酒店、扣卡"设计一个带补偿的 Saga。说明步骤应如何排序、为什么，每一步必须存储什么才幂等，以及扣款失败时用户可能看到什么。
::: solution
步骤：$T_1$ 暂订酒店、$T_2$ 暂订机票、$T_3$ 扣卡；补偿 $C_1$ 取消酒店、$C_2$ 取消机票。次序：把补偿代价低的步骤放前面，难撤销的放最后——扣款的补偿是账单上可见的退款，所以放最后，只在其他一切都已经成功时才发生。预订应做成会过期的*暂定*保留，这样崩溃的编排器不会留下永久订单。

幂等性：每个请求都带上 Saga 标识符和步骤编号作为幂等键；每个服务在自己的效果所在的同一本地事务里存下"Saga $s$ 第 $i$ 步已完成，结果 $r$"，重发时返回 $r$。补偿用同样的键，且即使正向步骤从未发生也必须能成功（取消一个不存在的预订是无操作），因为编排器可能不知道一个超时的步骤究竟生效没有。

扣款失败时：用户可能短暂看到机票和酒店处于已订状态（在应用里，若确认邮件发得太早也会收到），随后被取消。期间可能已有其他顾客被告知某个座位或房间不可订。这些都是缺失隔离性的可见后果，设计上应把它们藏起来——例如在 Saga 完成前显示"处理中"，只在最后才发送确认。
:::
