一位用户修改了自己的头像，网站显示“已保存”，她重新加载页面——看到的却还是旧头像。什么也没有丢：写入到达了数据库的一个副本，而这次重新加载由另一个尚未收到该写入的副本提供服务。几秒钟后，新头像在所有地方都出现了。这是缺陷（bug）吗？对一张头像，大多数人会耸耸肩。但对一个银行余额，或对一个告诉两个客户端各自持有同一把锁的锁服务，这将是一场灾难。

把同一份数据保存若干份拷贝——**副本（replica）**——是分布式系统幸存于故障并快速为用户服务的方式，它也引出了本章的核心问题：当存在多份拷贝、而更新需要时间传播时，一次读可以返回什么？答案是**一致性模型**，即存储系统与它的用户之间的约定。我们先看复制如何实现——由一个主副本，或由副本的**法定数量（quorum）**——并证明法定数量的相交性质。然后我们精确定义主要的一致性模型：**线性一致性**、**顺序一致性**、**因果一致性**与**最终一致性**，以及其间的会话保证。我们按 Gilbert 与 Lynch 的精确形式证明 **CAP 定理**，它指出在网络分区期间没有任何系统能同时做到什么；还有它的日常孪生兄弟 PACELC。最后我们介绍 **CRDT**：一种经过设计、使副本可以独立接受更新且可证明收敛的数据类型。我们依赖 [[distributed-systems/time-clocks]] 中的先行发生关系与向量时钟，以及 [[distributed-systems/system-models]] 中的模型。

## 复制

::: definition 复制对象 {#def-replicated}
一个**复制对象**是一个数据对象（寄存器、键值映射、计数器、数据库），由 $N$ 个进程——**副本**——各保存一份拷贝。**客户端**通过向一个或多个副本发送请求来对该对象调用操作。**复制协议**规定客户端联系哪些副本、更新如何在副本之间传播、以及每个副本返回什么。
:::

复制服务于三个目标：**容错**（丢失部分副本后数据仍在）、**可用性**（即使其他副本不可达，某些副本仍能应答）以及**性能**（读分散到多台机器上，较近的副本应答更快）。这些目标与**一致性**——副本在多大程度上表现得像单一拷贝——相互牵制。

### 主–备复制

最简单的协议指定一个副本为**主副本**（primary，又称领导者、主节点），其余副本是**备份副本**（backup，又称跟随者、从节点）。

::: algorithm 主–备复制 {#alg-primary-backup}
1. 客户端把所有更新发送给主副本。
2. 主副本把每个更新应用到自己的拷贝上，在它的**日志**中为它指定下一个位置，并把更新发送给每个备份副本。
3. 每个备份副本按日志次序应用更新并对其确认。
4. 在**同步**复制中，主副本只有在所有备份副本（或其中一组固定副本）确认之后才答复客户端；在**异步**复制中它立即答复。
5. 读由主副本服务；若可接受陈旧数据，也可由任何备份副本服务。
6. 若主副本失效，某个备份副本被**提升**为主副本（**故障转移**），其余副本跟随它。
:::

由于由单个进程为所有更新定序，每个副本都按相同次序应用相同的更新并到达相同的状态——这正是 [[distributed-systems/consensus]] 发展的状态机复制的思想。困难在于第 4 步和第 6 步。在异步复制下，向客户端确认过的写入可能只存在于主副本上；若主副本在转发它之前失效，故障转移就会把它丢掉。而对每个备份副本都同步复制，一个缓慢或失效的备份副本就会阻塞所有写入。许多系统用**半同步**复制折中：等待一个备份副本（或多数派）确认，其余的异步转发。

故障转移比看上去更难。判定主副本已经失效需要一个超时，而由 [[distributed-systems/system-models#thm-indistinguishable]]，这个判断可能是错的：旧主副本也许只是慢，或者只是被隔绝了。若在一个备份副本被提升时旧主副本仍在运行，就有了两个主副本——**脑裂**——两者都接受写入，这些写入随后发生冲突。安全的故障转移要求副本们*就哪一个是主副本达成*一致，并且被废黜的主副本不能继续以主副本的身份行事；这就是共识，我们把它推迟到 [[distributed-systems/consensus]]。

::: example 从滞后的备份副本读 {#ex-lag}
主副本向两个备份副本异步复制，**复制滞后**——主副本应用更新与备份副本应用更新之间的延迟——在备份副本 1 上是 $50$ ms，在备份副本 2 上是 $2$ s（它刚重启，正在追赶）。用户在时刻 $0$ 更新自己的头像，并在 $t = 0.5$ s 重新加载页面；她的读被发往随机一个副本。她可能看到什么？随后她又在 $t = 0.6$ 和 $t = 0.7$ s 各重新加载一次。
::: solution
在 $t = 0.5$ s，主副本和备份副本 1 有新头像；备份副本 2 没有。她有 $1/3$ 的概率看到旧头像：她读不到自己写的内容。若她的三次重新加载分别落在备份副本 1、备份副本 2 和主副本上，她会看到新、旧、新——她的读**在时间上倒退**。这两种异常都会在 $2$ s 之后消失，那时所有副本达成一致。这就是**最终一致性**的实际表现，而这两种异常正是下文会话保证中的*读己之写*和*单调读*所要禁止的。常见的补救办法是在用户写入之后的一小段时间内把她的读路由到主副本，或路由到至少已应用她上次写入所在日志位置的副本。
:::
:::

## 法定数量

客户端可以不经过单一主副本，而直接联系若干副本并等待其中足够的数量。Thomas（1979）和 Gifford（1979）引入了这一**法定数量（quorum）**思想。

::: definition 读法定数量与写法定数量 {#def-quorum}
设有 $N$ 个副本。若每次写都发送给所有副本、并在 $W$ 个副本确认后即视为完成，每次读都询问所有副本、并在 $R$ 个副本答复后即返回，则称该协议使用大小为 $W$ 的**写法定数量**和大小为 $R$ 的**读法定数量**。每个存储的值都带有一个**版本**（时间戳）；读返回所有答复中版本最高的值。
:::

::: theorem 法定数量相交 {#thm-quorum}
若 $R + W > N$，则每个读法定数量与每个写法定数量都相交。因此，若版本 $v$ 的一次写在某次读开始之前已经完成，且更晚的写的版本更大，则该读返回的版本至少为 $v$。
:::

::: proof
设 $Q_R$ 为读法定数量、$Q_W$ 为写法定数量，是 $N$ 个副本的子集且 $\lvert Q_R\rvert = R$、$\lvert Q_W\rvert = W$。则 $\lvert Q_R \cap Q_W\rvert = \lvert Q_R\rvert + \lvert Q_W\rvert - \lvert Q_R \cup Q_W\rvert \ge R + W - N > 0$，因为并集至多有 $N$ 个元素。关于推论：写完成时，其法定数量 $Q_W$ 中的每个副本都存储着版本 $v$（或更高的版本，因为副本只保留它见过的最高版本）。读的法定数量 $Q_R$ 含有 $Q_W$ 中的某个副本，它答复的版本 $\ge v$，而读返回其答复中的最大值。
:::

常见的选择是 $N = 3$、$R = W = 2$，或 $N = 5$、$R = W = 3$：即多数派，读写都能容忍少数副本失效。其他选择则改变代价的分布：$R = 1, W = N$ 使读快而写脆弱（任何一个副本失效都会阻塞写），$R = N, W = 1$ 反之。条件 $W > N/2$ 在另一类协议中另有作用：写者从自己的写法定数量处得知当前版本，如 Gifford 的加权投票；它使任意两个*写*法定数量相交（$2W > N$），于是写总能看见更早完成的写的版本（习题 5）。

::: example 故障下的法定数量系统 {#ex-quorum}
副本 $r_1, r_2, r_3$ 采用 $R = W = 2$，都持有 $(\text{版本 } 4, \text{值 } a)$。某客户端以版本 $5$ 写 $b$；这次写到达 $r_1$ 和 $r_2$ 并完成，而 $r_3$ 此刻宕机。随后 $r_1$ 崩溃，$r_3$ 带着它的旧拷贝恢复。某客户端进行读。它返回什么？若改为 $W = 1$ 呢？
::: solution
这次读需要从两个存活副本得到答复，而现在存活的是 $r_2$（版本 $5$，值 $b$）和 $r_3$（版本 $4$，值 $a$）。它返回版本更高的 $b$——正确，因为 $r_2$ 同时属于两个法定数量，正如 [[#thm-quorum]] 所保证的。读请求方还可以把 $(5, b)$ 发给 $r_3$ 来**修复**它，使后来的读不必只依赖 $r_2$（Dynamo 风格的存储把这称为**读修复**）。

若 $W = 1$，则 $R + W = 3 = N$，相交性失效：那次写可能只在 $r_1$ 上完成；$r_1$ 崩溃后，读法定数量 $\set{r_2, r_3}$ 中不含版本 $5$ 的任何拷贝，返回 $a$。已确认的写不复可见——而若 $r_1$ 的磁盘丢失，它就永远消失了。
:::
:::

::: warning $R + W > N$ 不是线性一致性
法定数量相交保证读能看见在它开始之前*已完成*的写。对于仍在进行中的写，它什么也没说。若一次写已经到达某个读法定数量的一个副本但尚未完成，第一次读可能返回新值，而较晚的、所用法定数量不含该副本的读返回旧值——即 [[#ex-histories]] 中的新–旧倒置。故障使情况更糟：到达不足 $W$ 个副本的写从客户端角度看是失败的，却可能已存储在某些副本上，并被后来的读返回。而使用**宽松法定数量**（sloppy quorum——在任意 $W$ 个可达节点上接受写，不一定是指定的副本，Dynamo 便如此，见 [[distributed-systems/distributed-storage]]）的系统，在故障期间干脆放弃了相交性。法定数量只是构件；一个线性一致的协议还需要更多东西，比如 [[#alg-abd]] 的写回阶段。
:::

## 一致性模型

要比较协议，我们需要一门精确的语言来描述客户端观察到什么。客户端只能看见它调用的操作和它收到的响应，而每个操作都要花时间。

::: definition 历史 {#def-history}
一个**历史**是操作的集合，每个操作带有发出它的客户端、它的种类与参数（对寄存器而言：`write(v)` 或 `read`）、它的响应（`ok` 或读到的值）、一个**调用**时刻和一个**响应**时刻。若 $a$ 的响应时刻早于 $b$ 的调用时刻，则称操作 $a$ 在真实时间中**先于** $b$，记作 $a <_H b$。互不先于的两个操作**重叠**。每个客户端一次只调用一个操作，所以一个客户端的操作被 $<_H$ 全序排列（它的**程序次序**）。
:::

一个**顺序规格**说明操作一次一个地执行时对象的行为：对寄存器而言，读返回最近一次写的值（或初始值）。下面的模型通过参照顺序执行，说明哪些并发历史是可接受的。

::: definition 线性一致性 {#def-linearisable}
历史 $H$ 是**线性一致的**，若存在其操作的一个全序 $S$，使得 (i) $S$ 满足对象的顺序规格，且 (ii) $S$ 尊重真实时间：若 $a <_H b$，则 $a$ 在 $S$ 中先于 $b$。等价地，每个操作都仿佛在它的调用与响应之间的某个时刻（它的**线性化点**）瞬时生效。
:::

线性一致性（Herlihy 与 Wing，1990）是最强的常用模型：复制对象的行为完全像一份被原子访问的单拷贝。一次写一旦完成，其后所有的读都返回它或更新的值；而一旦*任何*读返回了新值，后来的读就不会再返回更旧的值。Gilbert 与 Lynch 称之为**原子一致性**，它就是 CAP 中的“C”。锁、领导者选举、唯一性约束（“该用户名已被占用”），以及一切需要两个客户端就单一的、最新的值取得一致的场景，都离不开它。

::: definition 顺序一致性 {#def-sequential}
历史 $H$ 是**顺序一致的**，若存在其操作的一个全序 $S$，满足顺序规格并尊重每个客户端的程序次序（但不必尊重不同客户端之间的真实时间次序）。
:::

顺序一致性（兰波特（Lamport），1979）是为多处理器内存提出的模型（[[programming-languages/concurrency-models]]）：所有客户端看到相同的操作次序，并且该次序与每个客户端各自的执行相容，但它可能把一个客户端的操作在真实时间中“挪动”到与它不重叠的另一客户端操作的前后。只要所有人的看法都与某个顺序执行相容，客户端就可能读到陈旧的值。

下一个模型放弃了单一次序。

::: definition 因果一致性 {#def-causal}
若两次写在 [[distributed-systems/time-clocks#def-hb]] 的意义下一个先行发生于另一个，则称它们**因果相关**，其中客户端读取由 $w$ 写入的值算作从 $w$ 收到一条消息。历史是**因果一致的**，若每个客户端看见所有写入的次序都尊重因果性：若 $w_1 \to w_2$，则没有客户端会先从同一对象读到 $w_2$ 的值、随后又读到 $w_1$ 的值（或 $w_2$ 覆盖掉的值）。并发的写可以被不同客户端以不同次序看见。
:::

因果一致性（Ahamad 及合作者，1995）排除了最令人困惑的异常——先看到某条评论的回复、后看到评论本身，或朋友已被移出好友列表之后还看到与他们共享的照片——同时允许副本以不同次序应用并发的更新，这使得实现它时无需等待远端副本。实现用向量时钟或显式依赖列表跟踪依赖关系，并把一个更新推迟到它所依赖的更新都可见之后才让它可见。

::: definition 最终一致性与会话保证 {#def-eventual}
复制对象是**最终一致的**，若一旦更新停止，所有副本最终都收敛到相同状态，且每次读最终都返回该状态。Terry 及合作者的**会话保证**约束单个客户端（一个会话）所看到的东西：
- **读己之写**：一次读反映同一会话更早的每一次写；
- **单调读**：一次读不会返回比同一会话更早的读更旧的状态；
- **单调写**：一个会话的各次写按发出的次序被应用；
- **写随读**：一次写排在会话发出它之前曾读过其效果的那些写之后。
:::

最终一致性只是一个活性性质：它说副本*最终*会一致，但对在此期间读返回什么、以及相互冲突的并发写如何合并都一无所议。它是最弱的有用模型，也最容易被做成高度可用的。四条会话保证合起来，等价于每个会话内部的因果一致性。

::: example 为历史分类 {#ex-histories}
一个寄存器初始持有 $0$。时刻以毫秒计。
- $H_1$：客户端 $A$ 在 $[0, 4]$ 期间写 $1$；客户端 $B$ 在 $[1, 2]$ 期间读到 $0$；客户端 $C$ 在 $[2.5, 3]$ 期间读到 $1$。
- $H_2$：与 $H_1$ 相同，只是 $B$ 在 $[1, 2]$ 期间读到 $1$，$C$ 在 $[2.5, 3]$ 期间读到 $0$。

哪些是线性一致的？哪些是顺序一致的？
::: solution
在 $H_1$ 中两次读都与写重叠。把写的线性化点放在 $2$ 与 $2.5$ 之间：于是 $B$ 的读（$0$）在它之前，$C$ 的读（$1$）在它之后。次序 $B{:}\,\mathrm{read} \to 0$、$A{:}\,\mathrm{write}(1)$、$C{:}\,\mathrm{read} \to 1$ 尊重真实时间，所以 $H_1$ 是线性一致的。

在 $H_2$ 中，$B$ 的读返回 $1$，所以在任何有效次序中写必须排在它之前；$C$ 的读返回 $0$，所以写必须排在它之后。于是 $C$ 的读在该次序中先于 $B$ 的读；但 $B$ 的读（在 $2$）在 $C$ 的读（在 $2.5$）开始之前就已结束，真实时间要求相反的次序。$H_2$ **不是线性一致的**：一个读者已经看见新值之后，更晚的读者却看见了旧值——这是**新–旧倒置**，正是没有写回阶段的法定数量系统可能造成的现象。但它**是顺序一致的**：次序 $C{:}\,\mathrm{read} \to 0$、$A{:}\,\mathrm{write}(1)$、$B{:}\,\mathrm{read} \to 1$ 尊重每个客户端（单操作）的程序次序和寄存器的规格。一个穷举检查程序证实了上述线性一致性判定：

```python
from itertools import permutations

def linearisable(history, initial=0):
    """history：针对单个读/写寄存器的操作列表，元素为 (name, kind, value, invoke, respond)。
    穷举：尝试每一个尊重真实时间与寄存器规格的全序。"""
    for order in permutations(history):
        pos = {op[0]: i for i, op in enumerate(order)}
        if any(a[4] < b[3] and pos[a[0]] > pos[b[0]] for a in history for b in history):
            continue                                   # 违反真实时间次序
        value, ok = initial, True
        for name, kind, v, _, _ in order:
            if kind == "w":
                value = v
            elif v != value:                           # 读必须返回最近一次写入的值
                ok = False
                break
        if ok:
            return [op[0] for op in order]
    return None

H2 = [("A:w1", "w", 1, 0, 4), ("B:r0", "r", 0, 1, 2), ("C:r1", "r", 1, 2.5, 3)]
H3 = [("A:w1", "w", 1, 0, 4), ("B:r1", "r", 1, 1, 2), ("C:r0", "r", 0, 2.5, 3)]
print("H2:", linearisable(H2))
print("H3:", linearisable(H3))
```

```console
H3: None
```

（程序中，`H2` 和 `H3` 是本例的历史 $H_1$ 和 $H_2$。）穷举法对 $n$ 个操作需要与 $n!$ 成正比的时间；判定线性一致性在一般情况下是 NP完全的（Gibbons 与 Korach，1997），不过实用的检查器凭借巧妙的搜索能处理包含成千上万个操作的历史。
:::
:::

这些模型构成一个层次：每个线性一致的历史都是顺序一致的（真实时间次序包含程序次序），每个顺序一致的历史都是因果一致的，每个传播更新的因果一致系统都是最终一致的。每个包含都是严格的，$H_2$ 对第一个包含给出了例证。线性一致性还有顺序一致性不具备的一个性质：它是**局部的**（可组合的）——多个对象上的一个历史是线性一致的，当且仅当它在每个对象上的限制是线性一致的（Herlihy 与 Wing，1990）——所以线性一致的对象可以自由组合，而两个顺序一致的对象合在一起却未必是顺序一致的（习题 8 给出经典的例子）。

::: quiz
某个键值存储保证：在你写入一个键之后，你自己后来的读返回你的值或更新的值，但其他客户端可能有一段时间仍看到旧值。它提供的是哪种保证？
- [ ] 线性一致性
- [ ] 顺序一致性
- [x] 读己之写（一条会话保证）
- [ ] 以上都不是：它甚至不是最终一致的
::: solution
读己之写只关乎会话自己的写。在你的写完成之后其他客户端仍看到陈旧的值，这违反线性一致性；顺序一致性在原则上可能成立，但没有被保证。该存储是否最终一致，取决于其他客户端的读最终能否赶上——描述中没有说。
:::
:::

## CAP 定理

2000 年，Eric Brewer 猜测一个分布式系统不能同时提供**一致性**、**可用性**与**分区容忍性**。Seth Gilbert 与 Nancy Lynch 在 2002 年把这一表述精确化并给出了证明。精确版本比“三选二”的口号窄得多，也有用得多。

::: definition Gilbert 与 Lynch 意义上的可用性与分区 {#def-cap}
考虑在异步模型中由一组节点对读/写寄存器的实现，节点之间的消息可能丢失。
- 若非失效节点收到的每个请求最终都有响应（在每次执行中都是如此，包括丢失消息的执行），则称它是**可用的**。
- 若它产生的每个历史都是线性一致的，则称它是**原子一致的**。
- **分区**是指从一个节点组发往其余节点的所有消息都丢失的一次执行；**分区容忍**意味着上面的保证在这样一些执行中也必须成立。
:::

::: theorem CAP（Gilbert 与 Lynch，2002） {#thm-cap}
在异步网络模型中，不存在既可用又原子一致的读/写寄存器实现，能在包括丢失消息的执行在内的所有执行中都成立。
:::

::: proof
设某实现 $\mathcal{A}$ 既可用又原子一致。把节点划分成两个非空不相交的集合 $G_1$ 与 $G_2$，设寄存器的初始值为 $v_0$。考虑一次执行 $\alpha$，其中 $G_1$ 与 $G_2$ 之间双向的所有消息都丢失，且没有节点失效。

在 $\alpha$ 中，某客户端在 $G_1$ 的一个节点写 $v_1 \ne v_0$。由可用性，这次写完成了，设在时刻 $t_1$ 完成——它必须完成，尽管没有任何消息到达 $G_2$。此后，某客户端在 $G_2$ 的一个节点读；由可用性，这次读在某个时刻 $t_2 > t_1$ 返回。

现在把 $\alpha$ 与执行 $\beta$ 比较：$\beta$ 中根本没有写，丢失同样的消息，并在同一时刻于 $G_2$ 的同一节点发出同样的读。两次执行中都从未有消息从 $G_1$ 到达 $G_2$，所以 $G_2$ 的各节点在 $\alpha$ 与 $\beta$ 中的视图完全相同，读在两者中返回相同的值。在 $\beta$ 中，唯一被写过的值是 $v_0$，所以由原子一致性，这次读返回 $v_0$；于是它在 $\alpha$ 中也返回 $v_0$。但在 $\alpha$ 中，$v_1$ 的写在读开始之前已经完成，于是每个线性化都把写排在读之前，读便必须返回 $v_1$。这与原子一致性矛盾。
:::

这个证明与 [[distributed-systems/system-models]] 的不可区分性论证几乎一模一样：收不到消息的节点无从知晓别处的写。Gilbert 与 Lynch 还证明，在带时钟的部分同步模型中这一不可能性依然存在：只要消息可能丢失，即使延迟有界的网络也无法两者兼得，因为丢失的那些消息携带着关于那次写的唯一信息。

CAP 对设计意味着什么？分区——交换机故障、防火墙配置错误、电缆被挖断、数据中心失去上联——不是可选项；它们总会发生。所以这一定理说的是在分区*期间*该怎么办：要么某些请求必须等待或失败（放弃严格意义上的可用性：这些节点不作响应），要么某些读可能返回陈旧的值（放弃线性一致性）。选择前者的系统，如使用共识的复制数据库，有时被称为 **CP**；选择后者的系统，如 Dynamo 风格的存储和 DNS，被称为 **AP**。

::: warning CAP 没有说什么
口号“一致性、可用性、分区容忍：三选二”在好几个地方误导人。*C 是线性一致性*，不是 ACID 意义上的“一致性”，也不是任何更弱的模型；许多有用的模型（因果一致性、会话保证）是能同可用性兼得的（Mahajan、Alvisi 与 Dahlin 在 2011 年证明，比因果一致性的一个真实时间变体更强的模型做不到这一点）。*A 是完全可用性*：每个未失效节点都必须答复每个请求。一个分区中多数派一侧照常工作、少数派一侧拒绝请求的系统，按这个定义“不可用”，尽管大多数用户会说它可用性很高。*P 不是一个选择项*：“放弃分区容忍”的系统，只是在分区发生时行为没有定义而已。而且 *CAP 对没有分区时只字未提*：那时系统可以同时拥有 C 和 A，但要付出时延的代价——这正是 PACELC 补充的内容。
:::

### PACELC

Daniel Abadi（2012）指出，正常运行中一致性与可用性的折中，实际上是一致性与**时延**的折中。他的 **PACELC** 表述：若出现**分区**（**P**artition），在**可用性**（**A**vailability）与**一致性**（**C**onsistency）之间选择；**否**则（**E**lse），在**时延**（**L**atency）与**一致性**（**C**onsistency）之间选择。一次线性一致的写在得到确认之前必须到达法定数量；若副本分布在不同大洲，那么每次写都要付出一次广域网往返——即使什么都没坏。这不是某些协议的毛病：Richard Lipton 与 Jonathan Sandberg（1988）以及 Hagit Attiya 与 Jennifer Welch（1994）证明，在消息延迟落于 $[d - u, d]$ 之间的系统中，即使是一个顺序一致的读/写寄存器，其读与写的时延之和也必须至少为 $d$，所以线性一致的寄存器更是如此。在本地确认写、再异步传播的系统（EL）快而弱；等待的系统（EC）一致而慢。许多系统让每个请求自行选择。

## 线性一致寄存器的算法

法定数量再加上一个想法，就能在异步模型中实现线性一致性，只要多数副本正确：读者必须帮忙完成它所观察到的那次写。这个算法出自 Attiya、Bar-Noy 与 Dolev（1995），通常称为 **ABD**；我们给出它的多写者形式。

::: algorithm ABD 寄存器 {#alg-abd}
每个副本存储一个二元组 $(\mathit{ts}, \mathit{val})$，其中时间戳 $\mathit{ts} = (k, \mathit{id})$ 按字典序比较；收到 $\langle \textsf{store}, \mathit{ts}', v'\rangle$ 的副本在 $\mathit{ts}' > \mathit{ts}$ 时替换自己的二元组，无论如何都作出确认。$N = 2f + 1$ 个副本，其中至多 $f$ 个崩溃。
- **客户端 $c$ 写 $v$**：(1) 向所有副本发送 $\textsf{query}$ 并等待 $f + 1$ 个答复 $(\mathit{ts}_j, \cdot)$；令 $k$ 为最大的第一分量；(2) 向所有副本发送 $\langle \textsf{store}, (k + 1, c), v\rangle$ 并等待 $f + 1$ 个确认；返回。
- **读**：(1) 向所有副本发送 $\textsf{query}$ 并等待 $f + 1$ 个答复；令 $(\mathit{ts}, v)$ 为其中时间戳最大的答复；(2) **写回**：向所有副本发送 $\langle \textsf{store}, \mathit{ts}, v\rangle$ 并等待 $f + 1$ 个确认；返回 $v$。
:::

::: theorem ABD 是线性一致且无等待的 {#thm-abd}
在异步系统中，$2f + 1$ 个副本至多 $f$ 个崩溃且链路可靠，则每个正确客户端的每个操作都会终止，且 [[#alg-abd]] 的每个历史都是线性一致的。
:::

::: proof
*终止性。* 每个阶段在 $2f + 1$ 个副本中等待 $f + 1$ 个答复，而其中至少有 $f + 1$ 个是正确的并且终将答复。

*线性一致性。* 为每个已完成的操作 $o$ 关联它在第二阶段存储的时间戳 $\mathit{ts}(o)$（写的新时间戳；读的写回时间戳）。任意两个由 $f + 1$ 个副本组成的集合都相交，因为 $2(f+1) > 2f + 1$。

关键断言：若 $o_1$ 在 $o_2$ 开始之前完成，则 $\mathit{ts}(o_2) \ge \mathit{ts}(o_1)$，且当 $o_2$ 是写时 $\mathit{ts}(o_2) > \mathit{ts}(o_1)$。$o_1$ 完成时，有 $f + 1$ 个副本持有不小于 $\mathit{ts}(o_1)$ 的时间戳（副本从不减小自己的时间戳）。$o_2$ 的查询阶段听到 $f + 1$ 个副本，其中必有一个在上述副本之中，所以它见到的时间戳不小于 $\mathit{ts}(o_1)$。读存储它见过的最大时间戳，故 $\mathit{ts}(o_2) \ge \mathit{ts}(o_1)$；写取比它见到的所有第一分量都大的第一分量，故 $\mathit{ts}(o_2) > \mathit{ts}(o_1)$。

不同的写有不同的时间戳（它们或者客户端 id 不同，或者同一客户端时 $k$ 不同，因为客户端较晚的写会见到它较早的那次）。现在按时间戳为所有操作排序，把每个写排在具有相同时间戳的读之前，把时间戳相同的读按真实时间排序（任何与真实时间相容的次序都行）。每个读返回与它的时间戳一起存储的值，即拥有该时间戳的那次写的值（或初始值），并且它被排在那次写之后、排在每个具有更大时间戳的写之前——所以该次序满足寄存器规格。由关键断言它尊重真实时间：若 $o_1 <_H o_2$，则 $o_2$ 的时间戳至少与 $o_1$ 的一样大，$o_2$ 是写时严格更大；而当两者是时间戳相同的读时，我们已按真实时间为它们定序；并且一个写不可能被排在具有相同时间戳的读之后。所以该历史是线性一致的。
:::

写回阶段正是阻止 [[#ex-histories]] 中新–旧倒置的机制：看到新值的读者在返回之前确保某个法定数量持有它，于是每个后来的读者也看得见它。代价是每次读两次往返，而且该算法需要多数副本正确——这是最优的，因为当 $N \le 2f$ 时，把系统划分成两个大小不超过 $f$ 的半边就得到 CAP 场景，而两侧都必须作出响应。

## 无冲突复制数据类型

在谱系的另一端，有些应用希望每个副本立即接受更新——即使在分区期间——并在之后收敛：协同编辑的文本编辑器、购物车、点赞计数器。仅靠最终一致性时，并发更新会冲突：一个副本把寄存器置为 $A$，另一个置为 $B$，谁赢？按时间戳**最后写者胜**（last-writer-wins）很简单，却会悄无声息地丢弃一个更新。**无冲突复制数据类型**（CRDT）由 Marc Shapiro、Nuno Preguiça、Carlos Baquero 与 Marek Zawirski 在 2011 年系统化，它们是经过设计使并发更新*可交换*的数据类型，收敛由代数保证。

::: definition 状态型 CRDT {#def-crdt}
**连接半格**（join-semilattice）是一个带有偏序 $\le$ 的集合 $S$，其中任意两个元素 $x, y$ 都有最小上界 $x \sqcup y$（**连接**）。连接满足结合律、交换律和幂等律。一个**状态型 CRDT**（收敛型复制数据类型）由以下部分构成：状态组成的连接半格 $S$、初始状态、**膨胀的**（即对每个 $x$ 有 $x \le u(x)$）**更新**操作 $u$、副本收到另一副本的状态 $y$ 时把自己的状态 $x$ 置为 $x \sqcup y$ 的**合并**操作，以及从状态读出某个值的**查询**。
:::

::: theorem 状态型 CRDT 收敛 {#thm-crdt}
在状态型 CRDT 中，(i) 副本的状态从不减小，因此任何更新都不会丢失；(ii) 合并一组状态的结果与合并的次序、分组和重复都无关；(iii) 若每个副本的当前状态都送达其他每个副本并被合并，所有副本最终处于同一状态，即所有状态的连接。因此，接收到相同更新（直接或间接经由合并）的副本处于相同状态（**强最终一致性**）。
:::

::: proof
(i) 更新是膨胀的，而合并把 $x$ 替换为 $x \sqcup y \ge x$。特别地，一旦某个更新的效果进入了某个状态 $z$，由 $z$ 经进一步更新与合并得到的每个状态都 $\ge z$。

(ii) 把状态 $y_1, \dots, y_k$ 以任意次序、可能带重复地合并进 $x$、且中间结果相互合并的一个合并序列，计算的是多重集合 $\set{x, y_1, \dots, y_k}$ 的某个加括号、某些元素重复出现时的连接。由结合律与交换律，加括号和次序都无关紧要；由幂等律（$y \sqcup y = y$），重复也无关紧要：结果是 $x \sqcup y_1 \sqcup \dots \sqcup y_k$。

(iii) 设各副本的状态为 $x_1, \dots, x_N$，让每个副本 $i$ 合并其他所有副本的状态（其间没有更新）。由 (ii)，副本 $i$ 最终处于 $x_i \sqcup \bigsqcup_{j \ne i} x_j = \bigsqcup_{j} x_j$，对每个 $i$ 都一样。

关于最后的论断，可以这样定义一组更新所决定的状态：把每个更新在发起它的副本上作用于初始状态，再取连接；接收到相同的更新意味着连接了同一组这样的贡献，而由 (ii)，结果不依赖于它们到达所经过的路径。
:::

因此，合并可以在最弱的网络上安全地进行：状态可以被多次发送、以任何次序、经由公平丢失链路传送，并在副本之间 gossip 传播——这正是一个分区后最终重新连通的系统所具有的性质。（**操作型** CRDT 则广播更新操作本身；它们需要可靠的因果投递，但发送的数据更少，而且两种类型可以互相模拟。）

难点在于设计出能表示有用数据类型的半格。

- **G-Counter**（只增计数器），$N$ 个副本：状态是向量 $c \in \N^N$；副本 $i$ 通过在 $c[i]$ 上加数来递增；合并是按分量取最大；值为 $\sum_i c[i]$。按分量取最大是按分量次序下的连接，而递增抬高一个分量，所以它是膨胀的。
- **PN-Counter**：两个 G-Counter $P$ 与 $N$，分别计增量与减量；值为 $\sum P - \sum N$。
- **G-Set**（只增集合）：并集运算下的集合。**2P-Set**：一个存放已添加元素的 G-Set 与一个存放已删除元素的 G-Set（“墓碑”）；元素被添加且未被删除时存在——但一旦被删除就永远不能再添加。
- **OR-Set**（观察删除集合）：每次添加 $x$ 都生成一个新的唯一标签 $(x, t)$；删除 $x$ 时，把副本已*观察到*的 $x$ 的各个标签记为已删除。元素拥有一个已添加而未删除的标签时它存在。并发的添加创建一个删除未曾见到的标签，所以**添加**在与删除并发时**获胜**。
- **LWW-Register**：二元组（时间戳，值），连接为“时间戳大者胜”。它能收敛，但会丢弃并发的写；**多值寄存器**则相反，用版本向量保留所有并发的值，让应用程序去解决冲突。

::: example 收敛的计数器与购物车 {#ex-crdt}
模拟 G-Counter 的三个副本，应用 $200$ 个随机步骤，每个步骤或者是某个随机副本上的一次递增，或是一个随机副本的状态合并进另一个副本。然后让每个副本以随机次序合并其他每个副本。另外，演示当一个副本从购物清单中删除 "milk"、而另一个副本并发地再次添加它时，OR-Set 会怎样。
::: solution
```python
import random

class GCounter:
    """只增计数器：每个副本一个分量；合并 = 按分量取最大（一个连接半格）。"""
    def __init__(self, n, me): self.v, self.me = [0] * n, me
    def increment(self, k=1): self.v[self.me] += k
    def merge(self, other): self.v = [max(a, b) for a, b in zip(self.v, other.v)]
    def value(self): return sum(self.v)

class ORSet:
    """观察删除集合：每次添加生成唯一标签；删除只删它见过的标签。"""
    def __init__(self): self.adds, self.removes = set(), set()   # (元素, 标签) 的集合
    def add(self, x, tag): self.adds.add((x, tag))
    def remove(self, x): self.removes |= {(e, t) for e, t in self.adds if e == x}
    def merge(self, o): self.adds |= o.adds; self.removes |= o.removes
    def value(self): return {e for e, t in self.adds - self.removes}

rng, n = random.Random(42), 3
counters = [GCounter(n, i) for i in range(n)]
total = 0
for step in range(200):                      # 随机递增与随机两两合并
    i, j = rng.randrange(n), rng.randrange(n)
    if rng.random() < 0.5:
        counters[i].increment(); total += 1
    else:
        counters[i].merge(counters[j])
print("before final exchange:", [c.value() for c in counters], "true total:", total)
for i in range(n):                            # 任意次序的一轮交换：每个副本合并所有副本
    for j in rng.sample(range(n), n):
        counters[i].merge(counters[j])
print("after final exchange: ", [c.value() for c in counters])

a, b = ORSet(), ORSet()
a.add("milk", "a1"); b.merge(a)              # 两个副本都看到 milk
b.remove("milk")                             # b 删除它见过的 milk……
a.add("milk", "a2")                          # ……而 a 并发地再次添加 milk
a.merge(b); b.merge(a)
print("OR-set after merge:", a.value(), b.value())
```

```console
after final exchange:  [111, 111, 111]
OR-set after merge: {'milk'} {'milk'}
```

在最后那次交换之前各副本并不一致——每个副本都漏掉了一些递增——但没有任何递增丢失，并且经过一轮合并后，三个副本都报告真实总数 $111$，正如 [[#thm-crdt]] 所承诺的。（细心的读者会注意到最后的循环并不是一次同时的交换：副本 $0$ 在副本 $1$ 和 $2$ 拿到其他副本的状态之前就进行了合并。它依然有效，因为副本 $0$ 的合并包罗万象，而后来的副本会合并副本 $0$ 的完整状态。）在 OR-Set 中，$b$ 的删除只删掉了它观察到的标签 `a1`；并发添加的标签 `a2` 存活下来，所以 milk 留在两份清单上。天真的“最后写者胜”集合可能把它丢掉；而 Dynamo 最初的购物车——只按并集合并、没有删除——正是因为会复活被删除的商品而出名。
:::
:::

CRDT 被用在协同编辑器（如 RGA 这样的序列 CRDT，以及 Automerge 和 Yjs 中的设计）、分布式数据库（Riak 的数据类型、Redis Enterprise 的双活复制）以及可离线工作的移动应用中。它们的局限也是真实的：它们无法表达需要协调的不变式，例如“余额绝不低于零”——两个副本可以各自批准一笔单独看没问题、合起来却使账户透支的取款。这类不变式需要达成一致，这正是下一章的主题。

::: history
Peter Alsberg 与 John Day 在 1976 年描述了主–备复制。Robert Thomas 的多数派共识方法（1979）与 David Gifford 的加权投票（1979）引入了法定数量。Leslie Lamport 在 1979 年为多处理器定义了顺序一致性，Maurice Herlihy 与 Jeannette Wing 在《线性一致性：并发对象的正确性条件》（"Linearizability: a correctness condition for concurrent objects"，*TOPLAS*，1990）中定义了线性一致性。Douglas Terry 及合作者随 Bayou 项目在 1994 年引入了会话保证，Mustaque Ahamad 及合作者在 1995 年把因果内存形式化；同年，Hagit Attiya、Amotz Bar-Noy 与 Danny Dolev 的寄存器算法发表在《Journal of the ACM》。Eric Brewer 的 CAP 猜测是 PODC 2000 的大会报告；Seth Gilbert 与 Nancy Lynch 的证明发表在 2002 年的《SIGACT News》。Werner Vogels 的《最终一致》（"Eventually consistent"，2008–09）与 Amazon 的 Dynamo 论文（DeCandia 及合作者，2007）在工业界普及了弱一致性；Daniel Abadi 在 2012 年的《IEEE Computer》上提出了 PACELC。Marc Shapiro、Nuno Preguiça、Carlos Baquero 与 Marek Zawirski 在 2011 年定义了 CRDT 与强最终一致性。
:::

## 后续内容

主–备复制需要就谁是主副本、以及更新的次序达成一致，这就是**共识**（[[distributed-systems/consensus]]）；有了共识，复制日志给出线性一致的状态机。法定数量、宽松法定数量、版本向量与反熵在 [[distributed-systems/distributed-storage]] 的分区键值存储设计中再次出现。一次跨多个对象保持一致——事务——是 [[distributed-systems/distributed-transactions]] 的主题，Spanner 在那里提供跨大洲的线性一致（外部一致）事务。多处理器内部的内存一致性——同一层次结构在更小尺度上的再现——见 [[parallel-computing/memory-consistency]]。

::: summary
- **主–备**复制在一个副本上为更新定序；异步复制在故障转移时可能丢失已确认的写，不安全的故障转移会造成**脑裂**。
- 满足 $R + W > N$ 的**法定数量**两两相交（[[#thm-quorum]]），所以读能看见在它之前完成的每一次写；$2W > N$ 使写者之间有序。
- **线性一致性**（真实时间次序）⊃ **顺序一致性**（程序次序）⊃ **因果一致性** ⊃ **最终一致性**；会话保证介于其间。
- **CAP**（Gilbert–Lynch）：在消息可能丢失的异步网络中，寄存器不可能既线性一致又在每个节点都可用（[[#thm-cap]]）。C 指线性一致性，A 指*每个*未失效节点都作出响应。
- **PACELC**：即使没有分区，一致性也要用时延来换。
- **ABD** 用多数派加上读的写回构造线性一致的寄存器（[[#thm-abd]]）。
- **CRDT** 使用连接半格使合并可交换、副本可证明地收敛（[[#thm-crdt]]）；它们无法强制需要协调的不变式。
:::

::: exercise 选择法定数量 {level=1 check="5"}
$N = 7$ 个副本，读法定数量大小 $R = 3$。要保证读一定能看到已完成的写，最小的写法定数量大小 $W$ 是多少？（填入 $W$。）
::: solution
需要 $R + W > N$，即 $W > 4$，所以 $W = 5$。于是写能容忍 $2$ 个副本失效，读能容忍 $4$ 个。

::: exercise 哪种模型？ {level=1}
对每条需求，给出本章能满足它的最弱模型：(a) 用户发表一条评论并重新加载后，她能看到自己的评论；(b) 试图注册同一用户名的两个客户端不能都成功；(c) 绝不能向看不到评论本身的人显示某条评论的回复；(d) 点赞计数器可以暂时不准，但活动停止后必须变准。
::: solution
(a) 读己之写。(b) 线性一致性（唯一性检查需要单一的、最新的视图——实际上需要一个线性一致的 compare-and-set，而在有故障发生时它又需要共识）。(c) 因果一致性：回复因果地依赖于评论。(d) 最终一致性，例如用 PN-Counter CRDT。
:::

::: exercise G-Counter 算术 {level=1 check="15"}
一个 G-Counter 的三个副本状态为 $(5, 0, 2)$、$(3, 4, 2)$ 和 $(3, 0, 6)$。三者互相合并状态后报告什么值？（填入该值。）
::: solution
连接是按分量取最大：第一分量 $5, 3, 3$ 给出 $5$；第二分量 $0, 4, 0$ 给出 $4$；第三分量 $2, 2, 6$ 给出 $6$。合并后的状态 $(5, 4, 6)$ 的值为 $5 + 4 + 6 = 15$。注意这不是三个副本的值之和（$7 + 9 + 9$）：在多个副本上计入过次的递增只计一次。
:::
:::

::: exercise 法定数量的可用性 {level=2 check="0.9^5 + 5*0.9^4*0.1 + 10*0.9^3*0.1^2"}
五个副本各以概率 $0.9$ 独立可用。多数派法定数量可用的概率是多少？（填入该概率。）
::: solution
$5$ 台中至少 $3$ 台可用：$0.9^5 + 5 \cdot 0.9^4 \cdot 0.1 + 10 \cdot 0.9^3 \cdot 0.1^2 = 0.59049 + 0.32805 + 0.0729 = 0.99144$。

::: exercise 写法定数量必须相交 {level=2}
证明：$N$ 个副本中大小为 $W$ 的任意两个写法定数量相交，当且仅当 $2W > N$。然后考虑这样一个协议：写者从它即将写入的那 $W$ 个副本读出当前版本，并在那里写入版本“当前 $+1$”。在 $N = 4$、$W = 2$、$R = 3$（于是 $R + W > N$）下，给出一次执行：两次写，第二次在第一次完成之后才开始，两者却带着相同的版本、不同的值。
::: solution
*充分性：* $\lvert Q_1 \cap Q_2\rvert \ge 2W - N > 0$。*必要性：* 若 $2W \le N$，取 $Q_1$ 为前 $W$ 个副本、$Q_2$ 为接下来的 $W$ 个，它们不相交。

*执行：* 副本 $r_1, \dots, r_4$ 都持有版本 $5$。写者 $A$ 使用法定数量 $\set{r_1, r_2}$：它在那里读到版本 $5$，写入 $(6, a)$ 并完成。随后写者 $B$ 使用 $\set{r_3, r_4}$，$A$ 的写从未到达过那里：它读到版本 $5$，写入 $(6, b)$。尽管 $B$ 在 $A$ 完成之后才开始，两个值现在带着相同的版本，而后来的读法定数量如 $\set{r_1, r_3, r_4}$ 会同时看到两者，无法分辨哪个更新。若 $2W > N$，两个写法定数量共享一个副本，$B$ 就会读到版本 $6$ 并写入 $7$。ABD 以另一种方式避开该问题：它的写者查询一个*读*法定数量，由于 $R + W > N$，它与每个写法定数量相交；并且它把写者的标识符放进时间戳，使时间戳独一无二。
:::
:::

::: exercise 一个 PN-Counter {level=2}
在 [[#ex-crdt]] 的 `GCounter` 类之上用 Python 实现一个 PN-Counter，并证明它的合并在某个合适的次序下是连接，从而 [[#thm-crdt]] 适用。
::: solution
```python
class PNCounter:
    def __init__(self, n, me): self.p, self.n = GCounter(n, me), GCounter(n, me)
    def increment(self, k=1): self.p.increment(k)
    def decrement(self, k=1): self.n.increment(k)
    def merge(self, other): self.p.merge(other.p); self.n.merge(other.n)
    def value(self): return self.p.value() - self.n.value()
```
状态是 $\N^N$ 中的向量构成的二元组 $(P, N)$，按分量排序：$(P, N) \le (P', N')$ 当且仅当按分量有 $P \le P'$ 且 $N \le N'$。两个二元组的最小上界是按分量取最大得到的二元组，正是 `merge` 所计算的东西，所以这是一个连接半格。两个更新都抬高某个向量的一个分量，所以它们是膨胀的。因此定理适用。*值* $\sum P - \sum N$ 并非单调——它可能变小——但状态是单调的，而收敛所需要的正是这一点。
:::
:::

::: exercise 线性一致蕴含顺序一致 {level=3}
证明每个线性一致的历史都是顺序一致的。然后给出单个寄存器上两个客户端的一个历史——与 [[#ex-histories]] 中的 $H_2$ 不同、且其中一个客户端执行两个操作——它顺序一致但不是线性一致的。
::: solution
*证明。* 设 $S$ 是 $H$ 的一个线性化。它满足顺序规格。若 $a$ 与 $b$ 是同一客户端的操作，且程序次序中 $a$ 在 $b$ 之前，那么由于客户端一次只调用一个操作，$a$ 的响应先于 $b$ 的调用，故 $a <_H b$，而 $S$ 把 $a$ 排在 $b$ 之前。所以 $S$ 尊重程序次序，$H$ 是顺序一致的。

*例子。* 客户端 $A$ 在 $[0, 1]$ 期间写 $1$，随后在 $[2, 3]$ 期间读到 $1$。客户端 $B$ 在 $[4, 5]$ 期间读到 $0$。线性一致性被违反：写在 $B$ 的读开始之前已经完成，所以 $B$ 必须读到 $1$。顺序一致性成立，取次序 $B{:}\,\mathrm{read} \to 0$、$A{:}\,\mathrm{write}(1)$、$A{:}\,\mathrm{read} \to 1$，它尊重两个客户端的程序次序。$B$ 只是从一个落后很多的副本读，而这正是顺序一致性允许无限期维持下去的情形。
:::
:::

::: exercise 顺序一致性不可组合，且不可用 {level=3}
两个寄存器 $x$ 与 $y$ 初始为 $0$。客户端 $A$ 写 $x \gets 1$ 然后读 $y$；客户端 $B$ 写 $y \gets 1$ 然后读 $x$。(a) 证明若两次读都返回 $0$，则该历史不是顺序一致的，尽管它在每个寄存器上的限制是顺序一致的。(b) 推出：在把 $A$ 的节点与 $B$ 的节点分开的分区期间仍保持可用的任何两寄存器实现，都不可能是顺序一致的。
::: solution
(a) 用 $w_x, r_y$ 表示 $A$ 的操作，$w_y, r_x$ 表示 $B$ 的操作。在满足规格的一个顺序中，$r_y$ 返回 $0$，所以它排在 $w_y$ 之前；$r_x$ 返回 $0$，所以它排在 $w_x$ 之前。程序次序给出 $w_x$ 在 $r_y$ 之前、$w_y$ 在 $r_x$ 之前。合起来：$w_x < r_y < w_y < r_x < w_x$，出现环——这样的次序不存在。限制到 $x$，历史由 $w_x$（$A$ 所作）与 $r_x \to 0$（$B$ 所作）组成，每个客户端只有一个操作：次序 $r_x, w_x$ 可行。$y$ 同理。所以每个对象单独看都是顺序一致的，合在一起却不是：顺序一致性不是局部性质，这与线性一致性不同。

(b) 分区期间，可用性迫使 $A$ 的写与读在没有来自 $B$ 一侧任何消息的情况下完成，对 $B$ 亦然。考虑两个客户端都在分区期间并发执行各自两个操作的执行。$A$ 的节点无从知晓 $w_y$，$B$ 的节点也无从知晓 $w_x$——如 [[#thm-cap]] 的证明，与另一边从未发生写的执行作比较，那里读必须返回 $0$。于是两次读都返回 $0$，由 (a) 这不是顺序一致的。
:::
:::

::: exercise ABD 的代价 {level=3 check="4"}
在 [[#alg-abd]] 中，无故障时一次读要消耗多少个单向消息延迟（从客户端发出第一条消息起算到它返回）？解释为什么一个在第一阶段看到所有副本持有相同时间戳的读可以安全地跳过写回。（填入消息延迟数。）
::: solution
两个阶段，每个阶段一次往返：查询与答复（$2$ 个延迟）、存储与确认（$2$ 个延迟）：共 $4$ 个消息延迟。若第一阶段的 $f + 1$ 个答复都带着相同的最大时间戳，该值就已经存储在 $f + 1$ 个副本组成的法定数量中，而这正是写回要确立的东西；任何后来操作的查询都会与这个法定数量相交，看到不小于它的时间戳。于是读可以在一次往返后返回——这就是常见的“快速读”优化。若答复不一致，读者便无从知道最新的值是否已经到达某个法定数量，必须把它写回。
:::
