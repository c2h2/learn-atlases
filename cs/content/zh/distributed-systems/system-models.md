一家在线商店把顾客的购物车保存在三台服务器上，使得即使失去其中任意一台机器，顾客的购物车也不会丢失。一天傍晚，一台前端服务器向服务器 B 发送“把商品 42 加入购物车 7”，之后毫无回音。它该怎么办？也许 B 已经崩溃，前端应当改把请求发给 C。也许 B 还活着，只是垃圾回收器运行时停顿了几秒，商品最终会被加上——这样再发给 C 就可能把它加上两次。也许 B 收到了请求、加上了商品并且作了答复，丢失的只是那条答复。也许前端与 B 之间的网络断了，而 B 与 C 之间仍然通信正常。站在前端的位置上，**所有这些情形看起来完全一样**：沉默。

这正是**分布式系统**的精髓：一批计算机通过网络交换消息彼此协作，并且各自独立地出故障。兰波特（Lamport）在 1987 年的一封电子邮件中有一个令人难忘的表述：“分布式系统是这样一个系统，其中一台你甚至不知道其存在的计算机出了故障，就能使你自己的计算机无法使用。”这个学科之所以困难——也同样引人入胜——一切都来自两个事实：**没有共享内存**也**没有全局时钟**，每台机器只知道消息告诉过它的事情；故障是**部分的**，所以系统的一部分在继续运行而另一部分已经停止，并且没有任何一部分能够确定究竟发生了什么。

在为这样的系统设计算法、或证明某些问题无解之前，我们必须先精确地说出我们假设了什么。本章建立标准的**系统模型**：进程及其故障、链路及其故障，以及关于时间性的假设。我们要证明两个塑造了本课程后续内容的基本事实——在异步系统中，崩溃的进程与缓慢的进程无法区分；以及通信双方无法在一条可能丢失所有消息的链路上就任何事情达成一致（**两将军**问题）——最后我们来看工程师忘记这些模型时会陷入的那些谬误。

## 为什么系统要分布式

没有人为了好玩而把计算分布式：一台机器要好编程得多。接受这种困难有四种理由。

- **规模。** 数据或负载大得超出单台机器的承受能力。整个网络的搜索索引、或社交网络的消息存储放不进一块磁盘，每秒数百万的请求也放不进一颗处理器。
- **容错与可用性。** 每台机器终将出故障。如果一个服务必须在磁盘损坏、电源烧毁或数据中心断电时继续运行，它就必须把状态保存在多个地点的多台机器上——这就是**复制**，即 [[distributed-systems/replication-consistency]] 的主题。
- **时延。** 光在光纤中约以 $200{,}000$ km/s 传播，是其在真空中速度的三分之二，所以无论计算机多快，一次从欧洲到澳大利亚的往返都要远超 $100$ ms。用离用户较近的副本为其服务，是唯一能在所有地方都快起来的办法。
- **天然的分布。** 有些系统生来就是分布式的：一家银行的各个分行、一座工厂的传感器、一笔支付的各个参与方、必须就一张订单达成一致的两家公司的系统。

代价是失去单机白白提供给我们的两样东西：对整体状态的一致视角（一块内存、由一颗处理器读取），以及“机器要么工作要么不工作”的假设。分布式系统可能*部分*在工作，这既是它的长处（其余部分照常运行），也是它的主要困难（其余部分必须弄清发生了什么）。

### 独立故障的量化

假设每台机器有比例为 $a$ 的时间可用，且各台机器相互独立。如果一个服务需要*全部* $n$ 台机器——比如一次请求依次访问 $n$ 台服务器——它可用的概率是 $a^n$；如果它只需要*其中任意一台*，它可用的概率是 $1 - (1 - a)^n$。随着 $n$ 增大，这两个表达式朝相反方向变化。

::: example 串联与并联的可用性 {#ex-availability}
每台服务器独立地有 $99\%$ 的时间可用。比较需要三台服务器全部可用的服务、需要三台中任意一台可用的服务，以及需要 $5$ 台中至少 $3$ 台可用的服务（多数派，正如 [[distributed-systems/consensus]] 中的共识协议所做的那样）。
::: solution
三台全部：$0.99^3 = 0.970299$，约 $97\%$——服务每年停机约 $11$ 天，是一台服务器的三倍。三台需其一：$1 - 0.01^3 = 0.999999$，每年停机约 $32$ 秒。五台中的多数派：至少 $3$ 台服务器可用时服务可用，

$$
\sum_{k=3}^{5} \binom{5}{k} 0.99^k\, 0.01^{5-k} = 0.99^5 + 5 \cdot 0.99^4 \cdot 0.01 + 10 \cdot 0.99^3 \cdot 0.01^2 \approx 0.99999015,
$$

因此它每年停机约 $5$ 分钟。分布式设计既能让故障成倍增加（第一种设计），也能把故障掩藏起来（另外两种）；你得到哪一种，完全取决于设计是需要每个部件还是只需要部分部件。独立性假设是乐观的：同一机柜里的机器共享交换机和电源，而软件缺陷会同时打击所有副本。
:::
:::

## 进程、消息与执行

我们把一个分布式系统建模为一个固定的**进程**集合 $\Pi = \set{p_1, \dots, p_n}$，每个进程是一台确定性的状态机，通过**链路**（信道）相连并在其上传输消息。一个进程无法读取另一个进程的状态；它只能通过收到的消息来了解系统的其余部分。算法写成**事件处理器**的形式：“收到来自 $q$ 的消息 $m$ 时，执行……”，“定时器超时时，执行……”。

::: definition 事件、执行与局部视图 {#def-execution}
进程执行**步骤**。一步之中，它至多接收一条消息（或一条也不接收），执行本地计算，改变自己的状态，并发送零条或多条消息。一个进程的**事件**就是它的各种步骤：**发送**、**接收**与**内部**事件。一次**执行**（或**运行**）是所有进程的步骤的序列，连同被发送与被投递的消息，并要求每条被投递的消息都在更早的时刻被发送过。进程 $p$ 在一次执行中的**局部视图**是它自己各步骤的序列：它的初始状态、它按到达顺序收到的消息，以及它的输出。
:::

局部视图是关键概念。因为进程是确定性的，它在任一时刻之前的行为*只*取决于它的初始状态和它迄今收到的消息序列。在某个步骤之前 $p$ 具有相同局部视图的两次执行对 $p$ 而言是**不可区分的**：$p$ 在两者中必须表现得完全一样。分布式计算中几乎每一个不可能性证明——本章的那些、[[distributed-systems/consensus]] 的 FLP 定理、[[distributed-systems/fault-tolerance]] 的 $3f+1$ 下界——都是这样做的：构造两个某个进程无法区分的执行，并论证它在两者中必须作出相同的决定，尽管这个决定只在其中一个执行里是正确的。

一个模型就是我们认为可能的那些执行的集合。它有三个部分：**链路**上可能出什么问题、**进程**上可能出什么问题，以及我们对**时间性**允许做哪些假设。

## 链路

真实的网络会丢失、重复、延迟和重排分组（[[networks/network-principles]]）。链路的最弱但仍有用的模型刻画了这些现象，同时禁止网络凭空编造消息或*系统性地*丢失消息。

::: definition 公平丢失、顽固与完美链路 {#def-links}
设 $p$ 和 $q$ 是不崩溃的进程。从 $p$ 到 $q$ 的**公平丢失链路**满足
- **公平丢失**：若 $p$ 向 $q$ 无限次地发送消息 $m$，则 $q$ 无限次地投递 $m$；
- **有限重复**：若 $p$ 发送 $m$ 有限次，则 $q$ 投递 $m$ 有限次；
- **不凭空产生**：若 $q$ 投递了来自 $p$ 的 $m$，则 $p$ 更早发送过 $m$。

一条**完美链路**（可靠链路）满足
- **可靠投递**：若 $p$ 向 $q$ 发送 $m$，则 $q$ 最终投递 $m$；
- **不重复**：任何消息至多被投递一次；
- **不凭空产生**，同上。

完美链路**并不**承诺按发送顺序投递消息；**FIFO 完美链路**额外作出这一承诺。
:::

这些是 Cachin、Guerraoui 和 Rodrigues 教科书中的抽象。“投递”意味着“交给上层的算法”，这与一个分组仅仅到达是不同的：重复的分组会到达，但不会被再次投递。这些定义对消息*何时*到达不置一词——那是时间性模型的事情。

公平丢失链路是网络给我们提供的东西；完美链路是我们希望在其上编程的东西。标准构造使用重传与重复抑制，与 [[networks/reliable-transport]] 中可靠传输协议的思想完全相同。

::: algorithm 由公平丢失链路构造完美链路 {#alg-perfect-link}
发送方 $p$：
1. 要发送 $m$：选取一个全新的序号 $s$，把 $(s, m)$ 加入未确认消息集合 $U$，并发送 $\langle \text{DATA}, s, m \rangle$。
2. 每隔 $T$ 个时间单位：对每个 $(s, m) \in U$，再次发送 $\langle \text{DATA}, s, m \rangle$。
3. 收到 $\langle \text{ACK}, s \rangle$ 时：把 $(s, \cdot)$ 从 $U$ 中移除。

接收方 $q$，维护已投递序号的集合 $D$：
1. 收到来自 $p$ 的 $\langle \text{DATA}, s, m \rangle$ 时：向 $p$ 发送 $\langle \text{ACK}, s \rangle$；若 $s \notin D$，把 $s$ 加入 $D$ 并投递 $m$。
:::

::: theorem 完美链路构造的正确性 {#thm-perfect-link}
若 $p$ 和 $q$ 不崩溃，且它们之间双向的链路都是公平丢失链路，则 [[#alg-perfect-link]] 实现了从 $p$ 到 $q$ 的完美链路。
:::

::: proof
*不凭空产生。* $q$ 只在收到 $\langle \text{DATA}, s, m\rangle$ 时才投递 $m$，而按公平丢失链路的不凭空产生性质，该包必由 $p$ 发出；而 $p$ 只对它被要求发送的消息发送这样的包。

*不重复。* 序号是全新的，所以每条消息都有自己的 $s$。$q$ 只在 $s \notin D$ 时才投递序号为 $s$ 的消息，并在同一步中把 $s$ 加入 $D$，因此它至多投递一次。

*可靠投递。* 设 $p$ 发送了序号为 $s$ 的 $m$。反设 $q$ 永不投递 $m$。那么 $q$ 从未收到 $\langle \text{DATA}, s, m\rangle$（它首次收到时就会投递 $m$），于是它从不发送 $\langle \text{ACK}, s \rangle$，于是 $p$ 从不把 $(s, m)$ 从 $U$ 中移除，于是 $p$ 无限次地发送 $\langle \text{DATA}, s, m\rangle$。由公平丢失，$q$ 无限次地收到它——矛盾。所以 $q$ 投递 $m$。
:::

这个证明说明了确认的用处：不是为了投递的正确性——单凭重传就能保证——而是为了让发送方*停止*重传。没有确认，$p$ 会永远重发每一条消息——正确，但没有实用价值。还请注意构造中隐藏的两项开销。接收方的集合 $D$ 会无界地增长；真实协议通过使用 FIFO 序号并只记住按序投递的最大序号来限制它，TCP 就是这么做的。而且这个构造依赖于 $q$ *记住* $D$：若 $q$ 可能崩溃并携带空内存重启，它就会投递重复消息（习题 8）。

::: example 要传输多少次？ {#ex-transmissions}
每个方向的每个分组都以概率 $\ell$ 独立丢失。若每轮重传都把每条未确认的消息重发一遍，平均而言 [[#alg-perfect-link]] 要把每个数据包发送多少次（计入重传）？
::: solution
在每一轮中，一条给定的未确认消息被从 $U$ 中移除，当且仅当它的数据包到达*并且*确认成功返回，这以概率 $(1 - \ell)^2$ 发生。直到此时所需的轮数服从成功概率为 $(1 - \ell)^2$ 的几何分布，因此其均值为 $1/(1 - \ell)^2$。当 $\ell = 0.1$ 时是每条消息 $1.235$ 次传输；当 $\ell = 0.5$ 时是 $4$ 次。用固定种子的模拟与此一致：

```python
import random

def perfect_link(messages, loss, seed):
    """在丢弃每个分组的概率为 `loss` 的信道上采用重传直至确认的机制。"""
    rng = random.Random(seed)
    unacked = dict(enumerate(messages))      # 发送方：序号 -> 尚未确认的消息
    delivered, seen = [], set()               # 接收方：已投递的消息、已见过的序号
    sends = rounds = 0
    while unacked:
        rounds += 1
        for seq, m in list(unacked.items()):  # 每次超时，重发所有未确认的消息
            sends += 1
            if rng.random() < loss:           # 数据包丢失
                continue
            if seq not in seen:               # 重复抑制
                seen.add(seq)
                delivered.append(m)
            if rng.random() >= loss:          # 确认成功送达
                del unacked[seq]
    return delivered, sends, rounds

for loss in (0.0, 0.1, 0.3, 0.5):
    d, s, r = perfect_link([f"m{i}" for i in range(1000)], loss, seed=1)
    print(f"loss={loss:.1f}  delivered={len(d)}  in order={d == sorted(d, key=lambda x: int(x[1:]))}"
          f"  sends/message={s/1000:.3f}  predicted={1/(1-loss)**2:.3f}  rounds={r}")
```

```console
$ python3 plink.py
loss=0.0  delivered=1000  in order=True  sends/message=1.000  predicted=1.000  rounds=1
loss=0.1  delivered=1000  in order=False  sends/message=1.228  predicted=1.235  rounds=5
loss=0.3  delivered=1000  in order=False  sends/message=2.038  predicted=2.041  rounds=12
loss=0.5  delivered=1000  in order=False  sends/message=3.953  predicted=4.000  rounds=24
```

在每一个丢失率下，全部 $1000$ 条消息都恰好投递了一次，正如 [[#thm-perfect-link]] 所承诺的。但只要存在任何丢失，它们就*不会*按序投递：首份拷贝丢失的消息会比它后面的消息晚一轮投递。完美链路的定义允许这一点，它提醒我们：定序是一项单独的保证，必须单独付出代价。
:::
:::

## 进程故障

一个进程在某次执行中**正确**，如果它永远遵照其算法行事；否则它是**有缺陷的**。故障模型说明有缺陷的进程*怎样*偏离算法。我们通常用一个参数 $f$ 来限定有缺陷进程的数量，并考察 $n$ 相对于 $f$ 必须多大。

::: definition 故障模型 {#def-failures}
- **崩溃停止**（崩溃）：有缺陷的进程在某一步之前正确遵照其算法，此后不再执行任何步骤。它永不恢复。
- **崩溃恢复**：进程可能崩溃并稍后重启，丢失其易失状态，但保留它写入**稳定存储**（磁盘）的任何内容。一个进程若最终永远运行下去（或只崩溃有限次），则称其为正确的。
- **遗漏**：有缺陷的进程还可能拒绝发送它应当发送的某些消息（**发送遗漏**），或拒绝接收发给它的消息（**接收遗漏**），而在其他方面遵照其算法。
- **拜占庭**（任意）：有缺陷的进程可能以任意方式行事——发送错误或自相矛盾的消息、假装收到过没有收到的消息、或与其他有缺陷的进程串通。不过它无法在认证链路上伪造消息：若 $q$ 在来自 $p$ 的链路上收到 $m$，则 $p$ 发送过它。在**认证拜占庭**模型中，进程还会给自己的消息签名，有缺陷的进程无法伪造正确进程的签名。
:::

这些模型是层层嵌套的：崩溃是一种特殊的遗漏故障（某一点之后一切都不发），遗漏又是一种特殊的拜占庭行为。所以能容忍 $f$ 个拜占庭进程的算法也能容忍 $f$ 次遗漏或崩溃故障；而对崩溃成立的不可能性结果对每个更弱的模型都成立。列表中每往下一级，算法都更难、更昂贵：我们将会看到，共识在部分同步下的崩溃故障中需要 $n \ge 2f + 1$ 个进程，而在拜占庭故障下需要 $n \ge 3f + 1$ 个（[[distributed-systems/fault-tolerance]]）。

现实中的故障不会自带标签。内核崩溃或停电是崩溃。悄悄丢弃写入的磁盘、丢弃来消息的满队列、或阻断单向流量的防火墙规则是遗漏。内存中损坏了答复的位翻转、使某个副本算出不同答案的软件缺陷、或被攻击者控制的失陷机器是拜占庭。在数据中心中通常假定崩溃恢复模型，靠校验和把大多数损坏变成可检测的（从而类似崩溃的）故障；拜占庭模型用于机器由互不信任的各方运营的场景，如区块链；或用于安全性要求容忍任意硬件故障的场景，如飞机控制。

::: warning 崩溃恢复不是能重启的崩溃停止
人们很容易把崩溃后重启的进程当作一个新的、正确的进程。它不是：它已经**忘记**了自己在崩溃前说过的话，而其他进程可能正依赖于它。如果一次选举中的投票者投了候选人 A，随后崩溃、重启，接着投了 B，那么他就投了两次票，而两位候选人可能都相信自己拥有多数支持。崩溃恢复模型的算法必须把其他进程可能依赖的一切写入稳定存储——例如，Raft 在回复投票请求*之前*把当前任期号和投票写入磁盘（[[distributed-systems/consensus]]）。而写稳定存储很慢（一次磁盘落盘要几十微秒到几毫秒），正因如此这些写入会被小心翼翼地削减。
:::

## 时间性

模型的第三部分涉及时间：消息最多可以花多久、进程彼此相对跑多快，以及本地时钟跟随真实时间的程度。

::: definition 同步、异步与部分同步系统 {#def-timing}
- 若消息延迟存在*已知*的界限 $\Delta$（在正确进程之间的链路上发送的每条消息都在 $\Delta$ 内投递）且相对进程速度存在界限 $\Phi$（当另一个进程只走一步时，没有正确进程会走超过 $\Phi$ 步），并且每个进程都有一个本地时钟，其相对真实时间的漂移以已知速率 $\rho$ 为界，则系统是**同步**的。
- 若完全不存在界限：正确进程之间的消息终将投递，正确进程终将走出下一步，但两者都可能耗时任意长，且进程没有时钟（或时钟不携带任何保证），则系统是**异步**的。
- 若界限 $\Delta$ 和 $\Phi$ 存在但进程并*不知道*它们；或在另一种常见版本中，界限已知但只在某个称为**全局稳定时刻**（GST）的未知时刻之后才成立，GST 之前系统的行为如同异步——则系统是**部分同步**的（Dwork、Lynch 和 Stockmeyer，1988）。
:::

同步模型让算法很容易——消息缺失就是故障的证据——但它的假设在真实网络上并不成立：拥塞的交换机、一次重传或一段垃圾回收停顿都可能把延迟拉长到平常值的许多倍。异步模型不作任何时间性假设，所以它的算法无论网络如何表现都是正确的；但正如我们将要证明的，一些最基本的问题在其中变得不可能。部分同步是多数实用协议赖以建立的折中：它们被设计成在任何时候都是**安全的**（绝不做错事），即使网络是异步的；并在网络足够长时间地表现同步之后是**活跃的**（最终取得进展）。

### 崩溃看起来像延迟

异步的第一个推论是沉默不提供信息。

::: theorem 崩溃的进程与缓慢的进程不可区分 {#thm-indistinguishable}
在带崩溃故障的异步模型中，设 $p$ 和 $q$ 为进程，并假设在某次执行 $E$ 中，$q$ 在时刻 $t$ 崩溃，此后 $p$ 在某个时刻 $T > t$ 断定（例如输出）“$q$ 已崩溃”。那么存在一次执行 $E'$，其中 $q$ 是正确的，而 $p$ 同样在时刻 $T$ 断定“$q$ 已崩溃”。因此，该模型中没有任何算法能够既**完备**（每个崩溃的进程最终都被怀疑）又**准确**（正确的进程从不被怀疑）地检测崩溃。
:::

::: proof
如下构造 $E'$。在时刻 $t$ 之前，每个进程执行与 $E$ 中完全相同的步骤，每条消息都在与 $E$ 中相同的时刻投递。$t$ 之后，$q$ 不崩溃而是继续执行步骤，但它此后发送的每条消息都被延迟到时刻 $T$ 之后，投递给其指定的进程。其他每个进程在 $T$ 之前与 $E$ 中行为一致；$T$ 之后所有消息终将被投递。异步模型允许任意有限延迟，所以这是一次合法执行；而 $q$ 执行了无穷多步并收到了它的所有消息，故 $q$ 在 $E'$ 中是正确的。

在 $T$ 之前，$p$ 在 $E'$ 中收到的每条消息也都在 $E$ 中被 $p$ 于相同时刻收到：来自 $q$ 以外进程的消息相同，$q$ 在 $t$ 之前发送的消息相同，而 $q$ 的后续消息没有一条在 $T$ 之前到达。对每个其他进程 $r \ne q$ 同样成立：在 $T$ 之前它收到的与在 $E$ 中完全一样，于是对时间归纳可知，除 $q$ 外的所有进程在两次执行中于 $T$ 之前执行相同的步骤并发送相同的消息。因此 $p$ 在 $E$ 和 $E'$ 中的局部视图在 $T$ 之前相同，而它是确定性的，所以执行相同的步骤，在 $E'$ 中的 $T$ 时刻断定“$q$ 已崩溃”——而那里 $q$ 是正确的。

至于最后的主张：完备性迫使 $p$ 在 $E$ 中某个有限时刻 $T$ 怀疑 $q$；上述构造随即给出一个 $q$ 正确而 $p$ 怀疑 $q$ 的运行，违反准确性。
:::

证明很短，结果却根本：异步系统中的故障检测必然是一种**怀疑**问题，每一次超时都是一次猜测。[[distributed-systems/fault-tolerance]] 把这发展为**不可靠故障检测器**理论，它刻画一个算法需要多好的一次猜测。

相反，在同步系统中，超时就是证明。

::: proposition 同步系统中的精确崩溃检测 {#prop-sync-detect}
在消息延迟界限为 $\Delta$ 的同步系统中，假设每个进程都立即响应“ping”消息（在本地处理时间 $\delta$ 之内）。若 $p$ 向 $q$ 发送 ping，并在 $2\Delta + \delta$ 内（以 $p$ 自己的时钟计量并校正漂移）未收到答复，则 $q$ 已经崩溃。
:::

::: proof
若 $q$ 是正确的，ping 会在 $\Delta$ 内到达，$q$ 会在随后 $\delta$ 内答复，答复会在再往后 $\Delta$ 内到达 $p$，于是 $p$ 会在 $2\Delta + \delta$ 的真实时间内收到答复。若 $p$ 的时钟以真实时间的 $[1 - \rho, 1 + \rho]$ 速率运行，则 $p$ 在自己的时钟上等待 $(2\Delta + \delta)(1 + \rho)$，以确保至少有 $2\Delta + \delta$ 的真实时间已经过去。届时仍无答复就意味着 $q$ 不是正确的。
:::

问题在于 $\Delta$ 必须是真正的界限，而不是典型值。网络延迟有很长的尾巴：数据中心内大多数分组在不到一毫秒的几分之一内到达，但偶尔有一个要花几百毫秒；而短到足以快速检测崩溃的超时，有时会在活着的进程上误触发。

::: widget distribution
dist: lognormal
params: mu=0, sigma=0.5
a: 3
b: 10
caption: 往返时间模型：对数正态分布，中位数为 $1$（可把单位想成 $10$ ms），形状参数 $\sigma = 0.5$。超过 $3$ 个单位超时的阴影面积，是一台完全健康的服务器在某一次请求上被怀疑的概率——这里约为 $1.4\%$。增大 $\sigma$（网络突发更剧烈）并观察尾部变厚：当 $\sigma = 1$ 时，同样的超时带来约 $14\%$ 的误怀疑。没有任何有限超时能把阴影面积化为零，这就是 [[#thm-indistinguishable]] 的数字版本。
:::

::: example 部分同步系统中的超时 {#ex-doubling}
某个协议不知道延迟界限 $\Delta$。它从 $T_0 = 10$ ms 的超时开始，每当怀疑一个后来证明还活着的进程时就把超时翻倍。若真实（未知）的界限是 $\Delta = 1$ s，在超时变得足够大之前最多能发生多少次误怀疑？
::: solution
经过 $k$ 次翻倍后超时为 $10 \cdot 2^k$ ms，一旦 $2^k \ge 100$ 它就不小于 $1000$ ms，即 $k \ge \log_2 100 \approx 6.64$，所以在 $k = 7$ 次翻倍之后（超时 $1.28$ s）。每次误怀疑至多引起一次翻倍，因此至多发生 $7$ 次误怀疑，此后（在部分同步的第一个版本中，界限始终成立）再也不会发生。这正是使协议在部分同步下保持活跃的标准技巧：让超时增长，直到超过未知的界限。在 GST 版本的模型中，同样的论证适用于 GST 之后发生的怀疑。实践中超时还被允许缓慢地重新缩小，以免一次不良事件让故障检测永远变慢。
:::
:::

::: quiz
某服务器的垃圾回收器偶尔使它停顿 $5$ 秒，期间它既不发送也不处理消息。在哪种模型中，这种行为是一种**故障**？
- [x] 界限小于 $5$ s 的同步模型
- [ ] 异步模型
- [ ] 部分同步模型（第一种版本），无论界限多大
- [ ] 崩溃停止模型，因为进程停止了
::: solution
在同步模型中，该进程违反了已知的速度界限，这是一种**定时（性能）故障**。在异步模型中，任何有限停顿都是允许的，所以该进程只是慢，仍然是正确的。在界限未知的部分同步中，界限可能大于 $5$ s，因此 $5$ s 的停顿与进程正确并不矛盾。它也不是崩溃：进程会恢复运行，可能基于陈旧信息行动——这是缺陷的一个经典来源，例如一位前任领导者醒来后继续以领导者的身份行事。[[distributed-systems/fault-tolerance]] 讨论了对此防护的栅栏令牌（fencing token）。
:::
:::

## 两将军问题

在一条不可靠的链路上，一致性能有多强？答案是一个经典的不可能性结果，通常以故事讲述。两位将军 $A$ 和 $B$ 驻扎在敌人占据的山谷两侧的两座山上。合力他们可以取胜，但单独进攻是灾难。他们只能依靠穿越山谷、可能被俘的信使通信。他们能约定进攻吗？

$A$ 发送“拂晓进攻”。若信使被俘，$B$ 从未听说、不会进攻，所以 $A$ 除非确信消息已经送达，就不能进攻。$B$ 发送确认；可现在 $B$ 不知道确认是否送达，而 $A$ 若没收到确认就不会进攻——所以 $B$ 除非确信，也不能进攻。$A$ 再对确认作确认，如此论证不断重复。每条消息都把发送方留在疑虑之中。定理使其精确化。

::: definition 协同进攻 {#def-coordinated-attack}
两个进程 $A$ 和 $B$ 各有一个取值于 $\set{0, 1}$ 的输入（$1$ 表示“我打算进攻”），并且各自必须输出一个取值于 $\set{0,1}$ 的决定。它们通过双向都可能丢失任意消息的链路通信。若在每次执行中，一个协议都满足以下条件，则称其解决了**协同进攻**问题：
- **一致性**：$A$ 和 $B$ 不会作出不同的决定；
- **有效性**：若两个输入都是 $0$，两者都决定 $0$；若两个输入都是 $1$ 且没有消息丢失，两者都决定 $1$；
- **终止性**：两个进程都在有限步内作出决定。
:::

有效性是刻意定得很弱的：它只排除两个无用的协议——“总是决定 $0$”（当双方都想进攻且网络完美时它失败）和“总是决定 $1$”（当双方都不进攻时它失败）。进程不会崩溃，协议也可以任凭我们设计得多么巧妙。

::: theorem 协同进攻的不可能性（两将军问题） {#thm-two-generals}
在可能丢失消息的链路上，没有确定性协议能解决协同进攻问题。
:::

::: proof
反设某协议解决了它。设 $R$ 是两个输入都为 $1$ 且没有消息丢失的执行；由有效性，两者都决定 $1$。由终止性，两者都在有限步后作出决定，所以在两次决定中较晚者之前，$R$ 中投递的消息只有有限多条，设为 $k$ 条。按投递次序将它们编号为 $m_1, \dots, m_k$。对 $j = k, k-1, \dots, 0$，设 $R_j$ 为两个输入都是 $1$、$m_1, \dots, m_j$ 按 $R$ 中的方式投递、其后每条消息都被丢失的执行。

*两者在 $R_k$ 中都决定 $1$。* 直到两者在 $R$ 中都作出决定为止，每个进程在 $R_k$ 中收到的消息与在 $R$ 中完全相同，所以两者有相同的视图，都决定 $1$。

*若两者在 $R_j$（$j \ge 1$）中都决定 $1$，则两者在 $R_{j-1}$ 中也决定 $1$。* $R_j$ 与 $R_{j-1}$ 的唯一区别是 $m_j$ 是否投递。设 $X$ 是发送 $m_j$ 的进程，$Y$ 是它的接收方。在两个执行中，$X$ 收到的都恰好是 $m_1, \dots, m_{j-1}$ 中发给它的那些而没有别的，因为更晚的消息在两个执行中都丢失。所以 $X$ 在 $R_j$ 和 $R_{j-1}$ 中视图相同，在两者中都决定 $1$。由一致性，$Y$ 在 $R_{j-1}$ 中决定 $1$。

由归纳法，两者在 $R_0$ 中都决定 $1$——那里两个输入都是 $1$ 而每条消息都丢失。现在设 $R_0'$ 是 $A$ 的输入为 $1$、$B$ 的输入为 $0$、每条消息都丢失的执行。$A$ 什么也没收到、输入为 $1$，在 $R_0$ 和 $R_0'$ 中都是如此，所以它的视图相同，在 $R_0'$ 中决定 $1$；由一致性，$B$ 在 $R_0'$ 中也决定 $1$。最后设 $R_0''$ 的两个输入都是 $0$ 且每条消息都丢失。$B$ 在 $R_0'$ 和 $R_0''$ 中输入都是 $0$ 且一无所收，所以它在 $R_0''$ 中决定 $1$——与有效性矛盾，后者要求两个输入都是 $0$ 时决定 $0$。
:::

这个证明表明：任何*有限*多次的确认都无济于事——每一轮消息都可以被剥离掉而发送方毫无察觉。它的结构——一串执行，相邻两个对某个进程而言不可区分——正是 [[distributed-systems/consensus]] 中 FLP 证明的模板。

真实的系统怎么办？它们放弃要求中的一项。TCP 的连接拆除（[[networks/reliable-transport]]）放弃了确定性：发送最后一个确认的一方等待一段时间（TIME-WAIT 状态），然后假定对方已经收到。支付系统放弃了同时性：它们满足于*最终*一致，不断重试直到双方都记录了结果——在公平丢失链路上、双方都活跃时，这最终总会成功。而随机化协议放弃了绝对性：它们让不一致只是不太可能，而非不可能。

::: example 让分歧不太可能 {#ex-messengers}
$A$ 决定进攻并派出 $k$ 名信使，每名信使以概率 $p$ 独立被俘。只要至少一名信使到达 $B$ 就进攻；$A$ 无论如何都进攻。分歧的可能性有多大？当 $p = 0.5$ 时，多少名信使能让分歧小于百万分之一？
::: solution
两位将军分歧，当且仅当每名信使都被俘，概率为 $p^k$。我们需要 $0.5^k < 10^{-6}$，即 $k > 6 \log_2 10 \approx 19.93$，所以 $k = 20$ 名信使给出 $2^{-20} \approx 9.5 \times 10^{-7}$。该协议只是以极小的概率违反定理的要求——但它确实会违反，例如当山谷被完全封锁（网络分区）时，$p = 1$，分歧必然发生。概率论证的可靠性，不超过其背后的独立性假设。
:::
:::

## 分布式计算的谬误

工程师很少明确陈述自己的系统模型，而其隐含模型通常是单机的那个同步、无故障的模型。1994 年，当时在 Sun Microsystems 的 Peter Deutsch 列出了初次接触分布式系统的程序员常犯的七个错误假设；James Gosling 后来添上了第八个。它们被称为**分布式计算的谬误**：

1. 网络是可靠的。
2. 时延为零。
3. 带宽是无限的。
4. 网络是安全的。
5. 拓扑不会改变。
6. 只有一个管理员。
7. 传输成本为零。
8. 网络是同构的。

每条谬误都对应上面模型或网络课程的某个部分。*可靠性*：链路是公平丢失的而非完美的，而一次分区就能把一个数据中心与世界的其余部分隔开。*时延*：消息需要时间，其下界由物理定律决定，这决定了一个请求能负担得起多少次串行往返。*安全性*：网络上可能潜藏着敌手，因此链路必须认证并加密（[[security/network-security]]）。*拓扑与管理*：机器由不与你协调的人增删移动，所以成员关系必须是动态的。*同构性*：每次升级期间不同的机器运行着你软件的不同版本，所以消息必须能被新旧代码同时读懂（[[distributed-systems/remote-communication]]）。

::: example 时延的下界 {#ex-light}
一个来自伦敦的请求必须依次由位于伦敦、纽约（约 $5{,}570$ km 之外）和法兰克福（约 $640$ km 之外）的服务器确认，每次确认都需要一次从伦敦出发的往返。用光纤中光速 $200{,}000$ km/s 为时延建立下界。
::: solution
跨越距离 $d$ 的一次往返至少需要 $2d / (200{,}000\ \text{km/s})$：到纽约 $55.7$ ms，到法兰克福 $6.4$ ms；伦敦的往返可忽略不计。所以该请求至少需要 $62$ ms；而真实的光纤路由比大圆航线更长，还要加上交换设备带来的延迟，所以仅纽约的往返取 $70$–$80$ ms 更现实。一个需要 $5$ 次串行跨大西洋往返的协议，无论硬件如何都无法在 $280$ ms 之内响应。这就是地理复制的系统极力设法在一次的广域网往返内完成提交的原因，也是 [[distributed-systems/replication-consistency]] 中那些无需等待远端副本的一致性模型颇具吸引力的原因。
:::
:::

::: history
两将军问题最早出现在 E. A. Akkoyunlu、K. Ekanadham 和 R. V. Huber 1975 年一篇关于网络协议的论文中；Jim Gray 在他 1978 年关于数据库操作系统的讲义中把它作为将军悖论讲述，此后它成为不可能性结果的标准例子。对模型的系统研究始于 1970 年代末：兰波特（Lamport）的《时间、时钟以及分布式系统中事件的次序》（"Time, clocks, and the ordering of events in a distributed system"，1978）给出了没有全局时钟的消息传递模型，而兰波特（Lamport）、Robert Shostak 和 Marshall Pease 的《拜占庭将军问题》（"The Byzantine generals problem"，1982）引入了任意故障。Richard Schlichting 和 Fred Schneider 在 1983 年定义了失效停止处理器。Fischer、Lynch 和 Paterson 的不可能性结果（1985）展示了异步的代价，而 Cynthia Dwork、Nancy Lynch 和 Larry Stockmeyer 的《部分同步下的共识》（"Consensus in the presence of partial synchrony"，1988）提出了实用协议赖以立足的中间地带。Flaviu Cristian 的综述《理解容错分布式系统》（"Understanding fault-tolerant distributed systems"，1991）把故障划分为崩溃、遗漏、定时和任意四类。Nancy Lynch 的《分布式算法》（*Distributed Algorithms*，1996）以及 Cachin、Guerraoui 和 Rodrigues 的《可靠与安全的分布式编程导论》（*Introduction to Reliable and Secure Distributed Programming*，第 2 版，2011）完整地给出了这些模型；本章的链路抽象沿用后者的体系。
:::

后续每一章都在这些模型之一中工作。[[distributed-systems/remote-communication]] 在不可靠链路之上构造请求–应答通信，并直面“丢失的答复意味着什么”这一问题。[[distributed-systems/time-clocks]] 考察没有全局时钟时我们能够知道事件的什么次序。[[distributed-systems/replication-consistency]] 和 [[distributed-systems/consensus]] 在崩溃与异步之下保持数据副本的一致——并证明在纯异步模型中共识是不可能的。[[distributed-systems/fault-tolerance]] 把超时变成故障检测器，并处理拜占庭进程。

::: summary
- 分布式系统是一组**没有共享内存、没有全局时钟**、通过消息通信并**独立出故障**的进程；故障是部分的。
- 一个**模型**定下链路故障（公平丢失、完美）、进程故障（崩溃停止、崩溃恢复、遗漏、拜占庭——后者逐一包含前者）与时间性（同步、异步、部分同步）。
- **重传加重复抑制**把公平丢失链路变成完美链路（[[#thm-perfect-link]]）；定序是一项单独的保证。
- 进程只依据其**局部视图**行动；不可区分的执行迫使相同的行为，这是不可能性证明的基础。
- 在异步系统中，崩溃的进程**无法与缓慢的进程区分**（[[#thm-indistinguishable]]）：超时只是猜测。在同步系统中，超时是证明。
- 在有损链路上的**协同进攻**是不可能的（[[#thm-two-generals]]）；实用系统满足于最终的一致或概率性的一致。
- 需要*全部*机器的设计让故障概率成倍增加；只需要*部分*机器的设计掩藏故障。
- **分布式计算的谬误**就是被无意间假定的那个同步、无故障模型。
:::

## 习题

::: exercise 多数派可用性 {level=1 check="1 - 0.95^3 - 3*0.95^2*0.05"}
三台服务器各自以概率 $0.95$ 独立可用。一个服务至少需要其中 $2$ 台。它*停机*的概率是多少？（填入该概率。）
::: solution
服务在 $2$ 台或 $3$ 台可用时运行：$0.95^3 + 3 \cdot 0.95^2 \cdot 0.05 = 0.857375 + 0.135375 = 0.99275$。所以它停机的概率是 $1 - 0.95^3 - 3 \cdot 0.95^2 \cdot 0.05 = 0.00725$，约 $0.7\%$——相比单台服务器的 $5\%$。
:::
:::

::: exercise 故障分类 {level=1}
把每一项归类为崩溃、遗漏、定时或拜占庭故障（在时间性有意义的同步模型中）：(a) 一台服务器断电；(b) 一台路由器的队列溢出，丢了一个答复；(c) 一个有内存错误的副本返回余额 $£1{,}000{,}000$ 而不是 $£100$；(d) 一台虚拟机被宿主机暂停 $2$ s；(e) 一个控制着某个副本的攻击者向不同客户端发送不同的答案。
::: solution
(a) 崩溃。(b) 遗漏（链路的发送遗漏或接收方的接收遗漏；在 [[#def-links]] 的链路模型中，这正是公平丢失链路分内之事）。(c) 拜占庭：是错误的值，而不是缺失。(d) 在同步模型中是定时（性能）故障；在异步模型中只是慢。(e) 拜占庭，而且是恶意的——最难的情形，这正是拜占庭容忍协议必须处理*两面三刀*（对不同进程说不同的话）的原因。
:::
:::

::: exercise 重传次数 {level=1 check="1.5625"}
在 [[#ex-transmissions]] 中，若每个分组以概率 $0.2$ 丢失，每条消息的平均传输次数是多少？（填入该数。）
::: solution
$1/(1 - 0.2)^2 = 1/0.64 = 1.5625$。
:::
:::

::: exercise 光速 {level=2 check="170"}
沿光纤路由，悉尼与伦敦相距约 $17{,}000$ km。在 $200{,}000$ km/s 下最小往返时间是多少毫秒？（填入毫秒数。）
::: solution
$2 \times 17{,}000 / 200{,}000$ s $= 0.17$ s $= 170$ ms。一个需要三次这样的往返的同步协议无法在半秒内完成。
:::
:::

::: exercise 超时翻倍 {level=2 check="7"}
在 [[#ex-doubling]] 中，假设初始超时为 $50$ ms，真实延迟界限为 $5$ s。至多能发生多少次误怀疑？（填入该数。）
::: solution
我们需要 $50 \cdot 2^k \ge 5000$，即 $2^k \ge 100$，所以 $k = 7$（$50 \cdot 128 = 6400$ ms）。至多 $7$ 次误怀疑，每次引起一次翻倍。
:::
:::

::: exercise 对确认作确认 {level=2}
一位学生为两将军问题提出如下协议：$A$ 发送“进攻”；$B$ 确认；$A$ 对确认作确认；每位将军一收到对方的任何一条消息就进攻。给出一个两位将军意见不一致的执行，并解释它体现了 [[#thm-two-generals]] 证明中的哪一步。
::: solution
两个输入都是 $1$。$A$ 的消息到达 $B$；$B$ 已收到一条消息，于是它将进攻，并发出确认；确认丢失了。$A$ 没有收到 $B$ 的任何消息，于是它不进攻。两位将军分歧。无论进攻规则是什么，决定作出前投递的最后一条消息都可能丢失而其发送方毫无察觉，于是发送方与先前作出相同的决定，而接收方的视图已经改变：这正是从 $R_j$ 到 $R_{j-1}$ 的归纳步骤。把规则改成“收到两条消息后进攻”只会把问题挪到下一条消息上。
:::
:::

::: exercise 拜占庭容忍蕴含崩溃容忍 {level=2}
证明：若一个算法在至多 $f$ 个拜占庭进程的模型中解决了问题 $P$（正确进程输出的一个性质），那么它在相同时间性模型中也能解决至多 $f$ 个崩溃停止进程的 $P$。
::: solution
设 $E$ 是集合 $F$（$\lvert F\rvert \le f$）发生崩溃故障的一次执行。$F$ 中崩溃的进程 $p$ 在崩溃前遵照算法行事，此后无所作为。“遵照算法直到第 $s$ 步，然后停下”是拜占庭进程可以选择的行为之一，因为拜占庭进程可以为所欲为。所以 $E$ 也是（同一个集合 $F$ 作为至多 $f$ 个拜占庭进程的）一次执行，且正确进程的步骤完全相同。算法在每一这样的执行中都解决 $P$，所以 $E$ 中正确进程的输出满足 $P$。反之不成立：诸如 Raft 之类的崩溃容忍算法很容易被一个说谎的进程愚弄。
:::
:::

::: exercise 失忆破坏完美链路 {level=3}
在崩溃恢复模型中，假设 [[#alg-perfect-link]] 的接收方 $q$ 只在内存中维护集合 $D$，因而重启会将其清空。证明“不重复”可能失效。然后解释如何修复该算法，以及为什么发送方只需按批（例如每次预留 $1000$ 个序号一块）在稳定存储上保存它的序号计数器就够了。
::: solution
*失效。* $p$ 发送序号为 $s$ 的 $m$；$q$ 收到它、投递 $m$、把 $s$ 加入 $D$ 并发送确认，而确认丢失。$q$ 崩溃并带着 $D = \emptyset$ 重启。$p$ 重发 $\langle \text{DATA}, s, m\rangle$；$q$ 发现 $s \notin D$，第二次投递 $m$。

*修复。* $q$ 必须把投递与把 $s$ 插入 $D$ 一起变得持久：在投递之前，把 $s$（若投递意味着把 $m$ 交给一个也要持久化它的应用，则连同消息）**原子地**写入稳定存储，例如追加到日志并落盘。重启时，$q$ 重新载入 $D$。若 $q$ 在写入之后、确认之前崩溃，$p$ 重传，$q$ 确认但不重新投递。

*发送方的计数器。* 序号必须保持全新，即便跨越发送方的重启——若 $p$ 重启后把计数器归 $0$，一条带着旧序号的新消息会被误当作重复而丢弃。每次递增都落盘意味着每条消息一次磁盘写入。替代做法：$p$ 在磁盘上记录“小于 $B + 1000$ 的序号可能正在使用”，并在内存中使用 $B, B+1, \dots$；崩溃后它从 $B + 1000$ 继续。一些序号被跳过，这没有害处，因为重要的只是全新性，而不是连续性。（此时接收方的集合 $D$ 若不留心就不能再压缩成“迄今投递的最大序号”，这也是真实协议把序号与携带全新标识符的连接或会话绑定的原因之一。）
:::
:::

::: exercise 众多信使 {level=3 check="1/1024"}
在 [[#ex-messengers]] 中，每名信使以概率 $0.5$ 被俘，$A$ 派出 $10$ 名。两位将军分歧的概率是多少？然后证明：若每条消息以 $0 < p < 1$ 的概率独立丢失，且终止性必须在每次执行中成立，那么没有*确定性*协议能把分歧概率降为 $0$。（第一问填入该概率。）
::: solution
$10$ 名全被俘：$0.5^{10} = 1/1024$。

第二问：当 $0 < p < 1$ 时，每种有限的丢失模式都有正概率。取一个在每次执行中都满足有效性和终止性的确定性协议。由 [[#thm-two-generals]]，它在某个执行 $E$ 中违反一致性。一致性是在有限步内判定完成的，其间发送了有限多条消息，设为 $r$ 条；这些消息各自投递还是丢失的模式决定了直到两次决定为止的整个执行（协议是确定性的，输入是固定的）。该模式的概率至少为 $\min(p, 1-p)^r > 0$。所以分歧的概率为正。随机化和概率性丢失能让分歧罕见，但绝不可能使之不可能。
:::
:::
