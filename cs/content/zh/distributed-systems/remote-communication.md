一家网店的订单服务调用支付服务：`charge(card, 20.00)`。在源代码里，这看起来与任何其他函数调用没有区别。但这次调用以字节的形式穿越网络到达另一台机器，而某一天它既不返回也不失败——两秒后超时了。顾客被扣款了吗？如果订单服务放弃，它可能损失一笔其实已经付了钱的生意。如果它重试，它可能对顾客扣两次款。如果它去问支付服务“你扣款了吗？”，那个问题也可能超时。

本章讨论不同机器上的进程如何交谈，以及远程通信*看起来*的样子——一次函数调用、一条发出的消息——与它*实际上*是什么之间的鸿沟：一个可能丢失、延迟、重复或在执行后答复却永远到不了方的请求。我们研究**远程过程调用**以及实参如何变成字节（**序列化**），包括当程序的新旧版本并排运行时格式如何演进。然后我们把故障问题精确化：证明客户端不可能总能知道自己的请求是否被执行，定义**至多一次**、**至少一次**与**恰好一次**语义，并展示**幂等性**和请求标识符如何带来恰好一次执行的效果。最后我们讨论超时与重试，以及它们可能让系统可靠性下降的种种意外方式。我们在 [[distributed-systems/system-models]] 的模型中工作：公平丢失链路、崩溃或崩溃恢复进程、部分同步；其下的字节流与数据报来自 [[networks/sockets]]。

## 消息与请求

在最底层，进程通过发送**消息**通信：发送方把一串字节交给网络，指明接收方。其上构建了好几种模式。

- **单向消息**（“发后即忘”）：发送方不期待答复。日志与指标常这样用，通常跑在 UDP 上。
- **请求–应答**：客户端发送请求并等待响应。几乎所有服务之间的通信——HTTP、数据库协议、RPC——都是这种形状。
- **发布–订阅**：发送方在命名的**主题**（topic）上发布消息；该主题的每个订阅者都会收到它们。双方都不知道对方是谁。
- **消息队列**：发送方把消息放进由**代理**（broker）保管的队列，消费者稍后从中取出。队列把消息持久地存储下来，所以发送方和接收方不必同时运行。

Van Steen 和 Tanenbaum 沿两条轴给通信分类，这些分类解释了上述差异。若通信系统在消息被投递之前一直保存它——即使发送方和接收方没有同时运行（邮件系统、消息队列）——则通信是**持久的**；若消息在无法立即投递时就被丢弃（TCP 连接、RPC），则是**瞬态的**。若发送方阻塞——直到消息被系统接受、被投递给接收方、或被处理并得到答复——则通信是**同步的**；若发送方立即继续，则是**异步的**。RPC 在最强意义上是瞬态且同步的：调用者等待结果。

::: definition 请求–应答协议 {#def-request-response}
在**请求–应答协议**中，客户端向服务器发送请求消息 $\langle \mathit{id}, \mathit{op}, \mathit{args}\rangle$，其中 $\mathit{id}$ 标识该请求。服务器在自己的状态上执行 $\mathit{op}(\mathit{args})$，并发送响应 $\langle \mathit{id}, \mathit{result}\rangle$。客户端用 $\mathit{id}$ 把响应与尚未完成的请求配对。若在**超时**之内没有响应到达，客户端可以重发请求，或向其调用者报告失败。
:::

请求标识符身兼两职。它让拥有多个未完成请求的客户端能把每个响应与它的请求配对（响应可能以不同的次序返回）。而且，正如我们将看到的，它让服务器能把重发的请求识别为重复。

## 远程过程调用

手写一个请求–应答协议，需要为每个请求编写构造、发送、等待、解析响应和处理错误的代码。Andrew Birrell 和 Bruce Nelson 的**远程过程调用**（remote procedure call，RPC，1984）生成这些代码，使调用远程过程看起来就像调用本地过程。

::: definition 远程过程调用 {#def-rpc}
一个**远程过程调用**（RPC）系统接受一份**接口定义**——服务器各过程的名称、参数类型和结果类型——并为每个过程生成两个**存根**（stub）。**客户端存根**与该过程签名相同；被调用时，它把实参**序列化**（marshal）成请求消息、发送之、等待响应、把结果反序列化并返回，或抛出一个错误。**服务器存根**（骨架）接收请求、反序列化实参、调用真正的过程，并把结果序列化后发送。**绑定**机制告诉客户端服务器在哪里（名字服务、DNS 或配置文件）。
:::

::: algorithm 一次远程调用，逐步进行 {#alg-rpc}
1. 调用者把客户端存根 `charge(card, 20.00)` 当作本地过程来调用。
2. 客户端存根把过程标识符与实参序列化成字节，附上一个全新的请求 id，并把消息交给 RPC 运行时。
3. 运行时把消息发往已绑定的服务器地址，并启动一个定时器。
4. 服务器端的运行时收到消息，把它交给服务器存根；存根反序列化实参并调用真正的 `charge`。
5. 服务器存根把结果（或异常）序列化进一个带同一请求 id 的响应；运行时把它发送出去。
6. 客户端运行时收到响应，取消定时器并唤醒客户端存根；存根反序列化结果并把结果返回给调用者。
7. 若定时器先到期，运行时按照该调用的故障语义，要么重发请求（步骤 3），要么向调用者返回超时错误。
:::

这个思想影响深远——Sun RPC（后来在 RFC 1057、1988 年被标准化）支撑着 NFS 文件系统，Java RMI、CORBA、Thrift 和 gRPC 都是它的后代——但“远程调用与本地调用*一样*”的承诺在四个方面是假的，Jim Waldo 及其合作者的《关于分布式计算的札记》（"A note on distributed computing"，1994）对此作了阐述。

- **时延。** 本地调用花费纳秒；数据中心内的一次远程调用花费几十到几百微秒，跨大洲则花费几十到几百毫秒——相差五到八个数量级。为本地使用而设计的、包含许多小调用的接口，一旦远程化就会慢得无法使用。
- **内存。** 远程过程无法循着指针进入调用者的内存。实参是拷贝过去的，所以调用按值进行；传一个大型数据结构意味着把它整个拷贝一遍，而且服务器对它的改动客户端是看不到的。
- **部分失败。** 本地调用要么返回，要么整个程序崩溃。远程调用可能在双方都继续运行的情况下失败，而调用者可能不知道调用是否生效。这是本章大部分内容的主题。
- **并发性。** 服务器同时服务许多客户端，所以它的过程是并发运行的，必须加以同步（[[operating-systems/threads-locks]]）。

::: example 啰嗦接口的代价 {#ex-chatty}
一个客户端要显示一张 $100$ 行的订单。接口提供 `getLine(order, i)`，一次返回一行。每次调用在数据中心内花费 $0.5$ ms（一次往返加处理），而当客户端在欧洲、服务器在美国时花费 $80$ ms。试与一次调用 `getLines(order)` 比较：它在 $100$ Mb/s 的链路上用一个 $20$ KB 的响应返回全部 $100$ 行。
::: solution
在数据中心内，啰嗦接口花费 $100 \times 0.5 = 50$ ms；跨大西洋则是 $100 \times 80 = 8$ s。批量调用的代价是一次往返加上传输时间 $20{,}000 \times 8 / 10^8 = 1.6$ ms：数据中心内约 $2$ ms，跨大西洋 $82$ ms。差别与数据量毫无关系，全在串行往返的次数上。这就是 [[distributed-systems/system-models]] 的第二条谬误（“时延为零”）在起作用，也是远程接口要围绕粗粒度操作、批量和分页来设计的原因。（每次调用的开销是实践中常见量级的代表性数字，并非任何特定系统的属性。）
:::
:::

## 序列化

要把一个值发送过网络，我们必须把它变成一列字节，而接收方必须把字节变回一个相等的值——那台机器可能使用不同的处理器、操作系统和程序设计语言，并且可能运行着程序的不同版本。

::: definition 序列化 {#def-serialisation}
一组值 $V$ 的一个**序列化**（编码，marshalling）是一对函数 $\mathit{enc}\colon V \to \set{0,1}^*$ 与 $\mathit{dec}\colon \set{0,1}^* \to V \cup \set{\bot}$，满足对每个 $v \in V$ 有 $\mathit{dec}(\mathit{enc}(v)) = v$。这里 $\bot$ 表示输入不合法。若没有任何编码是另一个编码的真前缀，从而接收方能判断一个值在哪里结束，则称该格式是**自定界的**。
:::

指针无法发送，因为地址在另一台机器上毫无意义；数据结构必须被摊平。字节序和整数宽度必须由格式而非机器来规定（[[networks/sockets]] 讨论了网络字节序）。而 **JSON** 这样的文本格式与 **Protocol Buffers** 这样的二进制格式的取舍非常不同：JSON 可读、不需要模式，但每条消息都重复字段名、把十进制数写成文本、且不加额外编码就无法表示二进制数据；Protocol Buffers 需要模式、没有模式便不可读，但紧凑且解析飞快。

### 变长整数

真实消息中的大多数整数都很小——计数、长度、枚举值、字段号。因此 Protocol Buffers 用变长的字节数来编码整数。

::: definition Base-128 varint {#def-varint}
非负整数 $n$ 的 **varint** 编码从最低有效位开始，把它的二进制表示分成 $7$ 位一组。每组变成一个字节：低 $7$ 位存放该组，最高位（**续接位**）在除最后一个之外的每个字节中都是 $1$。
:::

::: proposition varint 的长度 {#prop-varint-length}
对 $n \ge 1$，$n$ 的 varint 编码长 $\lceil b/7 \rceil$ 个字节，其中 $b = \lfloor \log_2 n \rfloor + 1$ 是 $n$ 的位数；$0$ 的编码是一个字节。该编码是自定界的、可解码的。
:::

::: proof
编码器每 $7$ 位一组输出一个字节，并在某个组之后其上方不再有非零位时停止。一个有 $b$ 个有效位的整数恰好需要 $\lceil b/7\rceil$ 个组来容纳它们，而最后一组非零（它含最高位的 $1$），所以编码器恰好输出那么多字节。解码逐字节读入直到遇到最高位为 $0$ 的字节，它标志着结束——因此没有编码会是另一个编码的真前缀，因为真前缀会以一个续接位置一的字节结尾。其值为按序的 $7$ 位组 $g_i$ 上的 $\sum_{i} g_i \, 128^i$，恰好逆转编码过程。
:::

一个 Protocol Buffers 消息是若干字段的序列，每个字段先编码为一个**标签**——$(\text{字段号} \ll 3) \mid \text{线路类型}$ 的 varint——后面跟值。线路类型 $0$ 是 varint；线路类型 $2$ 是“长度定界”：一个 varint 长度，随后是那么多字节（字符串、字节数组、嵌套消息）。字段*名*从不出现在线路上，出现的只有编号。

::: example 手工编码一条消息 {#ex-protobuf}
某模式声明 `int32 id = 1;` 与 `string name = 2;`。编码一条 `id = 150`、`name = "hi"` 的消息，并与 JSON 文本 `{"id":150,"name":"hi"}` 比较大小。
::: solution
*字段 1。* 标签：$(1 \ll 3) \mid 0 = 8$，一个字节 `08`。值：$150 = 10010110_2$，八位，所以两个组。低七位是 $0010110_2 = 22 = \texttt{0x16}$；加上续接位，得 $\texttt{0x96}$。剩下的一位给出组 $1$，字节 `01`。所以字段 1 是 `08 96 01`。

*字段 2。* 标签：$(2 \ll 3) \mid 2 = 18 = \texttt{0x12}$。长度 $2$，字节 `02`。随后是 `hi` 的 ASCII 字节 `68 69`。所以字段 2 是 `12 02 68 69`。

消息为 `08 96 01 12 02 68 69`，$7$ 个字节；JSON 文本是 $22$ 个字节。一段小程序验证了编码：

```python
def varint(n):
    """把非负整数编码为 base-128 varint，最低位组在前。"""
    out = bytearray()
    while True:
        low7 = n & 0x7F
        n >>= 7
        if n:
            out.append(low7 | 0x80)   # 后面还有字节：置续接位
        else:
            out.append(low7)
            return bytes(out)

def zigzag(n):
    """把有符号数映射为无符号数：0,-1,1,-2,2,... -> 0,1,2,3,4,...（64 位版本）。"""
    return (n << 1) ^ (n >> 63)

def field(number, wire_type, payload):
    return varint(number << 3 | wire_type) + payload

for n in (1, 127, 128, 150, 300, 2**21):
    print(n, varint(n).hex(' '))
msg = field(1, 0, varint(150)) + field(2, 2, varint(2) + b"hi")
print("message:", msg.hex(' '), len(msg), "bytes")
print("zigzag:", [zigzag(n) for n in (0, -1, 1, -2, 2, -3, 3)])
print('JSON:', len('{"id":150,"name":"hi"}'), "bytes")
```

```console
$ python3 varint.py
1 01
127 7f
128 80 01
150 96 01
300 ac 02
2097152 80 80 80 01
message: 08 96 01 12 02 68 69 7 bytes
zigzag: [0, 1, 2, 3, 4, 5, 6]
JSON: 22 bytes
```

输出也展示了 [[#prop-varint-length]] 的边界：$127$（七位）放进一个字节，$128$ 需要两个，$2^{21}$（二十二位）需要四个。负数对 varint 是个麻烦，因为在补码表示下 $-1$ 的全部 $64$ 位都是 $1$，会占十个字节；`sint32`/`sint64` 类型先施加 **zigzag** 映射：$n \ge 0$ 时 $n \mapsto 2n$，$n < 0$ 时 $n \mapsto -2n - 1$，于是小的负数变成小的正数。
:::
:::

### 模式演进

在运行的系统里，你无法在同一瞬间升级每台机器。在**滚动升级**期间，新服务器要同旧客户端对话、旧服务器要同新客户端对话，而一个版本写入的数据会被另一个版本读取——在数据库里，可能是多年之后。

::: definition 向后兼容与向前兼容 {#def-compat}
若新代码能读旧代码写的数据，则一次格式变更是**向后兼容**的；若旧代码能读新代码写的数据，则是**向前兼容**的。
:::

Protocol Buffers 依靠字段编号对常见变更同时做到这两点。遇到不认识的字段号时，解码器会把它跳过——线路类型告诉它该跳过多少字节——于是旧代码读新数据时会忽略新增字段（向前兼容）。旧数据中缺失的字段在新代码中取其默认值（向后兼容）。规则如下：你可以用新编号添加字段、可以删除可选字段，但你**绝不可把字段号复用**给不同的含义，否则旧数据会被悄无声息地误读；而改变字段的类型只有在编码到线路上相同的那些类型之间才是安全的。基于 JSON 的 API 依惯例遵循同样的纪律——读取方忽略未知的键、把缺失的键当作默认值——而 Avro 这类格式则显式地把写入方的模式与读取方的模式相互解析匹配。

::: warning 绝不用语言的原生对象格式反序列化不受信任的数据
许多语言能序列化任意对象：Python 的 `pickle`、Java 的内置序列化、PHP 的 `unserialize`。这些格式编码了*要实例化哪个类*，并可能在解码期间触发代码。因此，解码来自不可信来源的字节，可能使接收方构造发送方指定的对象并运行发送方选定的方法——这是一类众所周知的漏洞。防御办法是使用只存数据的格式（JSON、Protocol Buffers、CBOR），用模式规定哪些类型可以出现，校验每个解码出的值，并把反序列化器当作攻击面的一部分（[[security/secure-development]]）。对于程序自己写入、自己读取、存储在别人无法修改的地方的数据，原生格式没有问题。
:::

## 出问题时

回到那个超时的支付调用。我们现在可以精确地说出它的结局为什么不可知。

::: proposition 客户端无法知道超时的请求是否被执行 {#prop-unknowable}
考虑一个跑在可能丢失消息的链路之上、服务器不会崩溃的请求–应答协议。假设在某个时刻，客户端必须向其调用者报告某个请求是否被执行，而它尚未收到该请求的任何响应。那么存在两个对客户端直到该时刻都不可区分的执行，其中一个里请求被执行了，另一个里没有。
:::

::: proof
设 $E_1$ 为客户端发送的请求的每一份拷贝都丢失的执行；服务器从未收到它，也从未执行它。设 $E_2$ 与之完全相同，只是请求的第一份拷贝被投递了；服务器执行它并发送响应，而该响应以及其后服务器发给客户端的每条消息都丢失。（若客户端重发，$E_2$ 中的服务器也可能收到后续拷贝并作出响应；那些响应同样丢失。）在两个执行中，客户端发送同样的消息而一无所收，所以直到它必须报告的时刻为止其局部视图完全相同，而它是确定性的，于是报告同样的内容。在 $E_1$ 中请求没有被执行，在 $E_2$ 中被执行了；无论它报告什么，在两者之一中都是错的。
:::

既然客户端无法知晓，RPC 系统提供了一组**故障语义**供选择，每一种都是关于一次调用被执行多少次的一项承诺。

::: definition 调用语义 {#def-call-semantics}
对远程过程的一次调用，
- **可能**（maybe）语义：请求只发送一次，不重试；过程至多执行一次，超时时调用者不知道它是否被执行；
- **至少一次**语义：客户端不断重发直到收到响应；若调用正常返回，则过程被执行了一次或多次；
- **至多一次**语义：服务器识别重复，所以无论调用是否返回，过程绝不被执行多次；
- **恰好一次**语义：过程恰好被执行一次，且调用者得知结果。
:::

由 [[#prop-unknowable]]，当消息可能被无限期丢失时，在*有界*时间内带结果的恰好一次是不可能的。但在公平丢失链路、服务器最终可用的条件下，把至少一次的重试与至多一次的重复检测结合起来，便得到唯一可实现意义上的恰好一次：客户端不断重试直到得知结果，而过程生效一次。要严格表述这一点，我们需要两个概念：幂等性与去重。

::: definition 幂等操作 {#def-idempotent}
状态为 $s$ 的服务器上的操作 $\mathit{op}$ 是**幂等**的，如果连续执行它两次与执行它一次的效果相同：对每个状态 $s$，若从 $s$ 执行 $\mathit{op}$ 到达状态 $s'$ 并给出响应 $r$，那么从 $s'$ 执行 $\mathit{op}$ 到达状态 $s'$ 并给出响应 $r$。
:::

“把收货地址设为 X”“删除文件 F”“查询余额”都是幂等的。“给余额加 $£20$”“向日志追加一行”“创建一张新订单”都不是。在 HTTP 中，`GET`、`PUT` 和 `DELETE` 方法被定义为幂等的而 `POST` 不是（RFC 9110），这就是浏览器在重新提交表单前要警告用户的原因。注意幂等说的是*连续*重复：“把 $x$ 设为 $5$”是幂等的，但若另一客户端在中间把 $x$ 设为 $7$，一条延迟到达的“把 $x$ 设为 $5$”的重复就会把它覆盖。只有当重复不可能任意迟地到达时，重试幂等操作才是无害的——这又是必须附上请求标识符的理由。

依靠服务器端去重，任何操作都能变成可安全重试的。

::: algorithm 去重的服务器 {#alg-dedup}
客户端给每个请求附上唯一标识符 $\mathit{id}$——例如二元组（客户端标识符，客户端序号）——并在每次重试时重发*同一个*标识符。服务器维护一张把标识符映射到响应的表 $\mathit{Done}$。
1. 收到 $\langle \mathit{id}, \mathit{op}, \mathit{args}\rangle$ 时：若 $\mathit{id} \in \mathit{Done}$，发送 $\langle \mathit{id}, \mathit{Done}[\mathit{id}]\rangle$ 并结束。
2. 否则执行 $r \gets \mathit{op}(\mathit{args})$，置 $\mathit{Done}[\mathit{id}] \gets r$——要与 $\mathit{op}$ 的状态改变**原子地**完成，并且若服务器可能崩溃恢复则须是持久的——然后发送 $\langle \mathit{id}, r \rangle$。
:::

::: theorem 带去重的重试使每个请求恰好执行一次 {#thm-dedup}
假设链路是公平丢失的，服务器最终会一直保持运行，且服务器的状态连同 $\mathit{Done}$ 能挺过崩溃并由步骤 2 原子地更新。若客户端重发标识符为 $\mathit{id}$ 的请求直到收到响应，则 (a) 该操作恰好执行一次，且 (b) 客户端最终收到那次执行的响应。
:::

::: proof
*至多一次。* 对应 $\mathit{id}$ 的操作只在步骤 2 执行，而只有 $\mathit{id} \notin \mathit{Done}$ 时才会到达步骤 2，且它在同一次原子的、持久的更新中把 $\mathit{id}$ 加入 $\mathit{Done}$。所以第一次执行之后 $\mathit{id} \in \mathit{Done}$ 永远成立——崩溃或者发生在更新之前（此时执行的效果和表项都不能幸免，仿佛请求从未到达），或者发生在更新之后（此时两者都留存下来）。请求的每个后续拷贝走步骤 1。

*至少一次，且客户端得知结果。* 假设客户端从未收到响应。那么它无限次重发，于是由公平丢失，最终运行的服务器无限次收到该请求。服务器永久运行之后的第一次这样的接收会执行该操作（若它尚未执行）或发现表项，无论哪种情况，此后每次接收都发送 $\langle \mathit{id}, \mathit{Done}[\mathit{id}]\rangle$。响应被发送了无穷多次，所以由公平丢失有一条会被送达——矛盾。于是客户端收到了响应，而每条对应 $\mathit{id}$ 的响应携带的都是 $\mathit{Done}[\mathit{id}]$，即那次唯一执行的结果。
:::

定理的假设正是真实系统成败所在。这张表必须**与操作效果原子地**一起更新：如果服务器扣了卡、崩溃了，重启后没有那条表项，重试就会再扣一次。标识符必须**由客户端选定**并在每次重试时复用：由服务器生成的标识符认不出它从未见过的请求。而这张表不能永远增长。若每个客户端至多只有一个未完成请求并按序为请求编号，服务器对每个客户端只需保留最大序号及其响应（习题 7）；否则表项在超过任何客户端会重试的时长之后被清除。支付 API 正是把这一机制作为**幂等键**（idempotency key）暴露出来的：客户端随每个请求发送一个唯一的键，服务器对重复的键返回存好的结果。

::: example 有无去重的重试 {#ex-dedup}
一个客户端在一条以概率 $0.2$ 丢失每个请求和每个答复的链路上，一千次存入 $£10$，每笔存款都重试直到收到答复。分别在有和没有 [[#alg-dedup]] 的情况下模拟服务器，并解释误差的大小。
::: solution
```python
import random

class Server:
    def __init__(self, dedup):
        self.balance, self.dedup, self.done = 0, dedup, {}   # done：请求 id -> 存好的答复
    def handle(self, req_id, amount):
        if self.dedup and req_id in self.done:
            return self.done[req_id]            # 重复：重发存好的答复，不再执行
        self.balance += amount                  # 非幂等操作
        reply = ("ok", self.balance)
        self.done[req_id] = reply               # 在真实服务器中：与余额原子地一起持久化
        return reply

def call(server, rng, req_id, amount, loss, max_tries=20):
    """至少一次语义的客户端：重发同一个请求 id 直到有答复到达。"""
    for attempt in range(max_tries):
        if rng.random() < loss:                 # 请求丢失
            continue
        reply = server.handle(req_id, amount)
        if rng.random() < loss:                 # 答复丢失
            continue
        return reply
    raise TimeoutError(req_id)

for dedup in (False, True):
    rng, s = random.Random(7), Server(dedup)
    for i in range(1000):
        call(s, rng, req_id=("client-1", i), amount=10, loss=0.2)
    print(f"dedup={dedup!s:5}  expected balance=10000  actual balance={s.balance}")
```

```console
$ python3 rpc.py
dedup=False  expected balance=10000  actual balance=12540
dedup=True   expected balance=10000  actual balance=10000
```

没有去重时，顾客被多入账了 $£2540$。这个大小是可以预测的：服务器每执行一次请求，答复就以概率 $0.2$ 丢失，引发一次重试，而重试（一旦送达）会再次执行这笔存款。每笔存款的执行次数服从成功概率 $0.8$ 的几何分布，其均值为 $1/0.8 = 1.25$，预测余额为 $£12{,}500$。有了去重，第一次执行之后的每次重试收到的都是存好的答复，余额分毫不差。
:::
:::

::: quiz
假设没有其他客户端触碰同一份数据，哪些操作客户端可以在**不**带请求标识符的情况下安全重试？
- [x] 带请求体 `ada@example.org` 的 `PUT /users/7/email`
- [ ] 创建一张新订单的 `POST /orders`
- [x] `DELETE /files/report.pdf`
- [ ] “页面浏览量计数器加一”
::: solution
设置一个值和删除一个对象是幂等的：各做两次与做一次留下的状态相同。（第二次 `DELETE` 可能返回 "not found" 而不是 "deleted"，细心的客户端必须接受这一点；*状态*是一样的。）创建订单和给计数器加一则不是——每重复一次状态就再变一次——所以重试它们需要按请求标识符去重。
:::
:::

## 超时、重试与退避

每次远程调用都需要一个**超时**：没有它，对已崩溃服务器的调用会永远阻塞，而它占用的线程或连接永远不会释放。由 [[distributed-systems/system-models#thm-indistinguishable]]，每次超时都是一次猜测。太短，客户端会放弃本会成功的调用，而它的重试雪上加霜；太长，一台崩溃的服务器会占住调用者整整一个超时的时长。常见的取法是观测时延某个高分位数的一个小倍数，例如第 $99$ 百分位的两倍。

重试把瞬时故障变成成功，但它们也成倍放大负载。放大多少？

::: proposition 重试的负载放大 {#prop-amplification}
客户端在首次尝试之后至多重试 $r$ 次，每次尝试以概率 $q < 1$ 独立失败。则每次调用的期望尝试次数为
$$
1 + q + q^2 + \dots + q^r = \frac{1 - q^{r+1}}{1 - q}.
$$ {#eq-amplification}
:::

::: proof
第 $(i+1)$ 次尝试（$i = 0, \dots, r$）恰好发生在前 $i$ 次尝试全部失败之时，其概率为 $q^i$。由期望的线性性，尝试次数的期望为 $\sum_{i=0}^{r} q^i$，即所给和式的几何级数。
:::

故障罕见时，重试几乎不花钱：$q = 0.01$、$r = 3$ 时因子是 $1.0101$。但故障很少是独立的。当服务器过载时，*大多数*尝试都会超时，$q$ 逼近 $1$，因子逼近 $r + 1$：就在服务器最承受不起的时刻，每个客户端的负载翻成了四倍。额外的负载让服务器保持过载，从而让 $q$ 保持高位，于是即便触发事件早已过去，系统仍会滞留在这个**亚稳态**的过载状态里（习题 9）。多层各自重试还会相互连乘：三层各自重试三次，就能把一个用户请求变成底层服务上的 $4^3 = 64$ 次尝试。

有三种实践能限制损害。

- **指数退避**：相邻重试之间依次等待 $b, 2b, 4b, \dots$，给过载的服务器恢复的时间。
- **抖动**（jitter）：把每次等待随机化，例如在 $[0, b \cdot 2^i]$ 内均匀取一（“完全抖动”），使同时失败的客户端不会以同步的波浪一起重试。
- **重试预算与断路器**：把重试限制在全部请求的一个比例（比如 $10\%$）之内；对一段时间持续失败的服务干脆停止调用，立即返回错误。

### 尾部时延

一个扇出到许多服务器的请求要等最慢的那个。Jeffrey Dean 和 Luiz André Barroso 在《The tail at scale》（2013）中描述了这一后果。

::: example 扇出与尾部 {#ex-tail}
一个页面由 $100$ 台服务器的响应拼装而成，并行查询它们。每台服务器 $99\%$ 的时间在 $10$ ms 内答复，否则（比如说）慢到 $1$ s，彼此独立。多大的比例的页面会变慢？
::: solution
页面快，当且仅当 $100$ 个响应全都快，概率为 $0.99^{100} \approx 0.366$。所以约 $63\%$ 的页面要等至少一个慢响应：单台服务器的第 $99$ 百分位时延变成了整个页面的*中位*时延。让每台服务器的平均水平更快没有用；只有削减尾部才有用。一种技术是**对冲请求**：若响应未在比如说第 $95$ 百分位时延内到达，就向另一个副本发送请求的第二份拷贝，取先回来的答案。这要多花百分之几的负载，却能削去大部分尾部——而且它只对幂等的（通常是只读的）请求安全。
:::
:::

::: widget plot
f: 1 - (1 - p)^x
x: 1, 200
y: 0, 1
sliders: p=0.01:0.001:0.1:0.001
labels: \text{等待慢服务器的请求所占比例}
points: 100,0.634; 10,0.0956
caption: 一个扇出到 $n$ 台服务器的请求遇到至少一台慢服务器的概率，其中每台以概率 $p$ 独立地变慢。$p = 0.01$ 时，两个点分别是 $10$ 台（$9.6\%$ 的请求变慢）与 $100$ 台（$63\%$）。把 $p$ 减半并注意曲线只以一半的速度上升：扇出很大时，决定用户所见时延的是每个组件的尾部，而非它的平均值。
:::

超时还需要在一条调用链上协调。若一个用户请求有 $1$ s 的预算并依次经过三个服务，被调用方在调用方已经放弃之后仍然埋头苦干，就是在为一个没人会读的答案浪费资源。因此 gRPC 这类 RPC 框架会随每次调用传播一个**截止时间**（deadline）；每个被调用方都知道还剩多少时间，可以快速失败。

## 超越请求–应答

请求–应答在时间上把客户端与服务器绑在一起：通话发生的那一刻，双方都必须运行且可达。**消息代理**消除了这种耦合。生产者把一条消息写入由代理持久保管的队列或主题，然后继续前行；消费者准备好时才读取消息，而代理会重投一条消息，直到某个消费者确认它。投递语义就是上面定义的那些，只是上升了一层：代理通常提供至少一次投递，消费者必须幂等或按消息标识符去重，与 [[#thm-dedup]] 中完全一样。**基于日志的代理**（如 Apache Kafka）把每个主题维护成一个只追加、分区的日志；消费者记录自己读到了哪里（它的**偏移量**，offset），而“恰好一次处理”是靠把消费者的偏移量与它产出的结果原子地存储在一起来实现的——与 [[#alg-dedup]] 中同样的原子性要求。构建在这种日志之上的流处理器是 [[distributed-systems/data-processing]] 的主题。

截至 2026 年，服务之间的通信大多要么用 HTTP 之上的 JSON，即所谓的**REST**这种面向资源的风格（Roy Fielding，2000）；要么用带二进制格式的 RPC 框架，其中 gRPC（HTTP/2 之上的 Protocol Buffers）使用最广；GraphQL 在浏览器与后端之间很常见。它们在风格与工具上各有不同，但每一个都免不了本章的这些难题：时延、版本演进，以及一次超时调用那不可知的结局。

::: history
Bruce Jay Nelson 1981 年在卡内基梅隆大学的博士论文引入了*远程过程调用*一词；Andrew Birrell 和 Nelson 的《实现远程过程调用》（"Implementing remote procedure calls"，《ACM Transactions on Computer Systems》，1984）描述了 Xerox PARC 的 Cedar RPC 系统，给出了至今仍在使用形式的存根、绑定与至多一次语义。Sun 的 ONC RPC（RFC 1057，1988）及其外部数据表示（XDR，RFC 1014，1987）支撑了 NFS；对象管理组织（OMG）的 CORBA（1991）和 Java RMI（1997）把 RPC 扩展到分布式对象。Jim Waldo、Geoff Wyant、Ann Wollrath 和 Sam Kendall 的 Sun 技术报告《关于分布式计算的札记》（"A note on distributed computing"，1994）论证：隐藏本地对象与远程对象之间的差别是一个错误。Roy Fielding 的博士论文（2000）定义了 REST。Facebook 于 2007 年发布了 Thrift，Google 于 2008 年将 Protocol Buffers 开源；gRPC 于 2015 年跟进，2016 年达到 1.0 版。Dean 和 Barroso 的《The tail at scale》（《Communications of the ACM》，2013）使尾部时延成为核心设计关切。
:::

## 后续内容

请求标识符与去重表在整个课程中反复出现。在 [[distributed-systems/replication-consistency]] 和 [[distributed-systems/consensus]] 中，复制服务必须在其*所有*副本之间对客户请求去重，于是这张表成为复制状态的一部分。[[distributed-systems/distributed-transactions]] 让多个服务器上的若干操作成为原子的，正是“把表与效果原子地一起更新”的推广。[[distributed-systems/data-processing]] 会在流处理器中再次遇到恰好一次处理。超时则在 [[distributed-systems/fault-tolerance]] 中变成故障检测器。

::: summary
- 通信可以是**持久或瞬态**的、**同步或异步**的；RPC 是瞬态且同步的，消息队列是持久且异步的。
- **RPC** 生成序列化实参与结果的存根，但远程调用在**时延、内存、部分失败与并发**四个方面不同于本地调用；接口要设计得粗粒度。
- **序列化**必须与语言无关且可演进；Protocol Buffers 使用 **varint**（[[#prop-varint-length]]）和**字段编号**，只要编号绝不被复用，就能带来向前与向后兼容。
- 请求超时的客户端**无法知道**它是否被执行（[[#prop-unknowable]]）。
- **幂等**操作可以自由重试；任何操作只要配上**客户端选定的请求标识符**和与效果**原子地**更新的去重表，重试就变得安全（[[#thm-dedup]]）。
- 重试至多把负载**放大** $r + 1$ 倍（[[#prop-amplification]]）；要使用指数退避、抖动、预算与截止时间。
- 扇出到 $n$ 台服务器时，每台的**尾部**时延会变成整体的典型时延。
:::

::: exercise varint 的长度 {level=1 check="3"}
$100{,}000$ 的 varint 编码占多少个字节？（填入字节数。）
::: solution
$2^{16} = 65{,}536 \le 100{,}000 < 2^{17}$，所以 $100{,}000$ 有 $17$ 位，由 [[#prop-varint-length]] 需要 $\lceil 17/7\rceil = 3$ 个字节。（事实上 $128^2 = 16{,}384 \le 100{,}000 < 128^3$。）
:::
:::

::: exercise 哪些操作是幂等的？ {level=1}
按 [[#def-idempotent]] 的含义，哪些是幂等的？(a) `x = max(x, 10)`；(b) `x = x * 2`；(c) “把商品 42 加入购物车 7 的商品*集合*”；(d) “把商品 42 加入购物车 7 的商品*列表*”；(e) “给顾客发一封邮件”。
::: solution
(a) 是：第一次执行后 $x \ge 10$，第二次不再改变它。(b) 否。(c) 是：已经包含 42 的集合不变。(d) 否：列表会多出一个 42。(e) 否：会发出两封邮件——这是服务器状态*之外*的效应，去重也必须把它覆盖进来（在发送邮件之前或与发送原子地记录“订单 7 的邮件已发”，并接受在两者之间崩溃时零封或两封的小风险）。注意 (a) 和 (c) 还是**可交换的**，[[distributed-systems/replication-consistency]] 中的 CRDT 利用的正是这个性质。
:::
:::

$1 - 0.98^{50} \approx 0.636$。近三分之二的请求要等一台慢服务器。

::: exercise 期望尝试次数 {level=2 check="(1 - 0.2^5)/0.8"}
用 [[#eq-amplification]]，当每次尝试以概率 $0.2$ 失败、至多重试 $4$ 次时，每次调用的期望尝试次数是多少？（填入该数。）
::: solution
$r = 4$，$q = 0.2$：$(1 - 0.2^5)/(1 - 0.2) = 0.99968 / 0.8 = 1.2496$。

::: exercise zigzag {level=2 check="199"}
在 zigzag 映射下，$-100$ 由哪个无符号整数表示？它的 varint 占多少字节，与朴素补码 varint 的十个字节相比如何？（填入那个无符号整数。）

某银行服务提供 `transfer(from, to, amount)`。客户端在有损网络上调用它并在超时时重试。服务把账户存在数据库中。描述客户端发送什么、服务器存什么、在哪个事务中存，以及下列各事件下会发生什么：(a) 请求丢失；(b) 服务器在更新余额之后、答复之前崩溃；(c) 答复丢失；(d) 客户端崩溃并重启。
::: solution
客户端为每笔*逻辑上的*转账生成一个唯一标识符（一个随机的 $128$ 位值，或客户端 id 加序号），在第一次尝试之前把它存到本地，并在每次尝试中随请求发送它。服务器在**一个数据库事务**中检查表 `done(id, result)`；若 `id` 已存在就返回存好的结果；否则扣款、入账并插入 `(id, result)`，然后提交并答复。

(a) 请求丢失：服务器上什么都没发生；重试会执行这笔转账。(b) 提交后崩溃：事务已经提交，余额和 `done` 行都是持久的；重试会找到那一行并返回存好的结果。若崩溃发生在提交之前，事务回滚，重试会执行它——无论哪种情况都恰好一次。(c) 答复丢失：同 (b)。(d) 客户端重启后必须复用同一个标识符，这就是它要在第一次尝试前存下它的原因；换一个全新的标识符会让服务器把重试当成一笔新转账。
:::
:::

::: exercise 限制去重表的大小 {level=3}
假设每个客户端每次至多有一个未完成请求，并按 $1, 2, 3, \dots$ 为其请求编号，且链路是 FIFO 的。证明服务器对每个客户端只需存储它已执行的最大序号及该请求的响应，而序号更小的请求可以忽略。若链路可能重排消息、且客户端可能在开始新请求之后重发旧请求，又会出什么问题？
::: solution
*断言。* 当服务器收到客户端 $c$ 的请求 $k$ 时，$c$ 的每个 $j < k$ 都已被执行、或永远不再需要响应。因为 $c$ 只有在收到 $k - 1$ 的响应之后才发送请求 $k$，所以请求 $k-1$ 已被执行（按至多一次语义，恰好一次执行）且其响应已送达；归纳可知所有 $j < k$ 亦然。于是服务器看到 $k$ 时，可以丢弃存下的 $k - 1$ 的响应：客户端再也不会向它要了，因为它已经拿到了；而在 FIFO 链路下，更早发出的 $k-1$ 的任何拷贝都不可能晚于 $k$ 到达。收到的请求编号 $j$ 于是按下述规则处理：$j$ 等于存下的最大编号——返回存下的响应；$j$ 更大——执行它并替换表项；$j$ 更小——忽略它（它只可能是过期的重复）。

*重排。* 若链路会重排，请求 $k - 1$ 的迟到拷贝可能在 $k$ 执行之后到达。上面的规则会忽略它，这是正确的——客户端已不在等它。危险的是相反的情形：若服务器只存一个计数器而**不**存响应，那么在响应丢失之后对 $k$ 的重试就只能靠重新执行来答复。所以服务器必须为每个客户端保留最近一次响应。当每个客户端有多个未完成请求时，它必须保留一个最近响应的窗口，真实系统（以及 TCP 的序号）正是以这种方式推广该方案。
:::
:::

::: exercise 完全抖动 {level=3 check="1550"}
一个客户端使用完全抖动：第 $i$ 次重试（$i = 0, 1, 2, \dots$）之前等待一个从 $[0, b \cdot 2^i]$ 中均匀抽取的时间。取 $b = 100$ ms，到第五次重试发出为止（即对 $i = 0, \dots, 4$ 各次重试）等待总时长的期望是多少？与不带抖动的朴素指数退避比较。（以毫秒填入期望总时长。）
::: solution
第 $i$ 次重试前的等待期望为 $b \cdot 2^i / 2$。对 $i = 0, \dots, 4$ 求和：$\frac{b}{2}(1 + 2 + 4 + 8 + 16) = 50 \times 31 = 1550$ ms。朴素指数退避恰好等待 $b \cdot 2^i$，总计 $3100$ ms。完全抖动把平均等待减半，而更重要的是，它把同一时刻失败的客户端在各区间上均匀摊开，使它们的重试不会以同步的一波到达。
:::
:::

::: exercise 亚稳态故障 {level=3 check="3200"}
一台服务器能处理 $1000$ 次请求每秒。客户端每秒发出 $800$ 个新请求，超时时至多重试 $3$ 次。平时几乎没有尝试会失败。一次短暂的网络故障让所有尝试在几秒内全部超时。用 [[#prop-amplification]]，在所有尝试都失败期间，客户端给出的负载是多少每秒（尝试次数）？解释为什么故障结束后服务器可能仍然过载，以及重试预算如何打破这个循环。（填入每秒尝试次数。）
::: solution
$q = 1$、$r = 3$ 时，每个请求产生 $r + 1 = 4$ 次尝试，所以给出的负载是 $4 \times 800 = 3200$ 次每秒。故障之后网络已经正常，但服务器要面对每秒 $3200$ 次尝试，超过其容量的三倍；它的队列不断变长，响应超出客户端的超时，于是尝试继续失败（$q$ 保持在 $1$ 附近），使过载得以维持——触发因素已消失，这却是一个稳定状态。把重试限制在请求量的（比如说）$10\%$ 的重试预算，能把给出的负载封顶在每秒 $880$，低于容量，于是队列得以排空，$q$ 下降，系统回到健康状态。负载削减（迅速拒绝多余的请求而不在队列中积压）和退避的作用方式与此相同。
:::
:::
