互联网的网络层不作出任何保证。一个从某台主机发往另一台主机的分组，可能到达，可能带着差错到达，可能到达两次，可能在比它晚发送的分组之后才到达，也可能根本不达——而且最后这种情况下没有任何人通知发送方。可是当你下载一个文件时，每个字节都恰好到达一次，顺序不乱，内容完好。在有损的网络和你的程序之间，某个协议把一条有损信道变成了一条可靠的信道。

怎么办？显而易见的回答——“发送每个分组，若丢失就重发”——把一切难点都藏了起来。丢失的唯一证据是沉默，发送方怎么知道一个分组丢了？如果丢失的偏偏是接收方的确认，发送方就会重发一个接收方早已收到的分组：接收方怎样认出这个重复分组？而每发送一个分组都等一个确认，会把一条又长又快的路径的几乎全部容量浪费掉（[[networks/network-principles#ex-lfn]]）。本章从第一性原理出发回答这些问题。我们先讲传输层最简单的任务——把分组交付给正确的进程——以及只做这件事的最小传输协议 **UDP** 和它的**互联网校验和**。然后一步步构造可靠传输——确认、序号、定时器——得到**交替比特协议**，证明它的正确性，并弄清它为什么慢。最后我们把它**流水线化**，介绍**回退 N 帧**和**选择重传**，并证明两者各需要多少个序号。下一章的 TCP 正是这些设计的精化。

## 复用与 UDP

网络层把数据报交付给*主机*。主机上可能同时有许多进程在通信，所以传输层的第一个任务是**分用**：把每个到达的报文段交付给正确的套接字（[[networks/sockets#def-socket]]）。发送方一侧的**复用**则从许多套接字收集数据，加上分用所需的首部，再把报文段交给网络层。承担这一信息的是端口号。一个 UDP 套接字仅由目的 IP 地址和端口号标识，所以许多客户发往 53 号端口的数据报都到达同一个 DNS 服务器套接字；一条 TCP 已连接套接字由全部四个值（源和目的地址与端口）标识，所以每个客户的连接都有自己的套接字。

::: definition UDP {#def-udp}
**用户数据报协议**（RFC 768，1980）只在 IP 之上增加了分用和可选的差错检测。其首部为 8 字节：

| 比特 0–15 | 比特 16–31 |
|---|---|
| 源端口 | 目的端口 |
| 长度（首部加数据，以字节计） | 校验和 |

校验和覆盖一个**伪首部**——源和目的 IP 地址、一个零字节、协议号（UDP 为 17）和 UDP 长度——其后是 UDP 首部（校验和字段置零）和数据，若长度为奇数再补一个零字节凑成偶数。在 IPv4 上，校验和为零表示“未计算”；在 IPv6 上校验和是必需的（RFC 8200）。
:::

UDP 不提供连接建立、重传、定序或拥塞控制。这正是它的意义所在：一个用不上这些东西的应用——一次 DNS 查询、一路迟到即无用的语音抽样、一个在用户空间构造的新传输协议如 QUIC——以 8 字节开销得到网络的原始服务，且不添加任何时延。伪首部是一处出于实用而被迫违反分层的做法：把 IP 地址计入校验和，能让接收方发现交付给了错误主机的数据报。

### 互联网校验和

::: definition 互联网校验和 {#def-checksum}
一串字节的**互联网校验和**（RFC 1071）按下式计算：把它拆成 16 位大端字（长度为奇数时补一个零字节），按**一补数算术**把这些字相加——即普通加法，但任何从最高位溢出的进位都回加到最低位（**回环进位**）——再对和取一补数（按位取反）。发送方把结果存入校验和字段。接收方把*包括*校验和在内的所有字相加；若一补数和为 `0xFFFF`——即其反为 $0$——数据就通过检验。
:::

```python
# checksum.py：对一条 UDP 数据报（RFC 768）计算互联网校验和（RFC 1071）
import socket, struct

def internet_checksum(data: bytes) -> int:
    if len(data) % 2:
        data += b"\x00"                          # 长度为奇数时补一个零字节
    total = 0
    for (word,) in struct.iter_unpack("!H", data):   # 16 位大端字
        total += word
        total = (total & 0xFFFF) + (total >> 16)     # 回环进位
    return ~total & 0xFFFF                       # 对和取一补数

def udp_datagram(src, dst, sport, dport, payload):
    length = 8 + len(payload)
    pseudo = socket.inet_aton(src) + socket.inet_aton(dst) + struct.pack("!BBH", 0, 17, length)
    header = struct.pack("!HHHH", sport, dport, length, 0)      # 校验和暂置 0
    csum = internet_checksum(pseudo + header + payload)
    if csum == 0:
        csum = 0xFFFF                            # 在 UDP over IPv4 中 0 表示“无校验和”
    return struct.pack("!HHHH", sport, dport, length, csum) + payload, pseudo

dgram, pseudo = udp_datagram("192.0.2.1", "198.51.100.2", 5000, 7, b"Hi!")
print("datagram:", dgram.hex(" "))
print("checksum: %#06x" % struct.unpack("!H", dgram[6:8]))
print("receiver's check:", hex(internet_checksum(pseudo + dgram)))     # 数据完好时为 0
bad = bytearray(dgram); bad[9] ^= 0x01                                  # 翻转一个比特
print("after a bit flip:", hex(internet_checksum(pseudo + bytes(bad))))
```

```console
$ python3 checksum.py
datagram: 13 88 00 07 00 0b 96 a8 48 69 21
checksum: 0x96a8
receiver's check: 0x0
after a bit flip: 0x1
```

::: example 手工计算一次 UDP 校验和 {#ex-checksum}
验证上面 11 字节数据报的校验和 `0x96a8`：它从 192.0.2.1 的 5000 号端口发往 198.51.100.2 的 7 号端口（回声服务），携带三个字节 `Hi!`。
::: solution
相加的字如下：

| 部分 | 16 位字 |
|---|---|
| 伪首部：源地址 192.0.2.1 | `c000` `0201` |
| 目的地址 198.51.100.2 | `c633` `6402` |
| 零，协议 17；UDP 长度 11 | `0011` `000b` |
| UDP 首部：端口 5000 和 7 | `1388` `0007` |
| 长度 11；校验和 0 | `000b` `0000` |
| 数据 `H` `i` `!` 和补位字节 | `4869` `2100` |

它们的普通和为 `0x26955`。把进位折回——$\texttt{0x6955} + \texttt{0x2} = \texttt{0x6957}$——即得一补数和，它的反为 $\texttt{0xFFFF} - \texttt{0x6957} = \texttt{0x96A8}$。在接收方，同样的字把 `0000` 换成 `96a8` 后相加得 $\texttt{0x6957} + \texttt{0x96A8} = \texttt{0xFFFF}$，其反为 $0$：数据报通过检验。把字节 `i` 的最低位翻转会使一个字改变 $1$，和变成 `0xFFFE`，检验结果为 $1$。
:::
:::

为什么用这样古怪的求和？因为它具有使它在 1970 年代的计算机上就很便宜、今天仍然便宜的一些性质。

::: proposition 互联网校验和的性质 {#prop-checksum}
设 $S(w_1, \dots, w_n)$ 为若干 16 位字的一补数和。则：

1. $S$ 不依赖于字的次序，所以和可以按任意次序、并行地计算，或在一个字改变时增量地计算（路由器递减 IPv4 生存时间时就这样做）。
2. $S$ 作为整数与 $w_1 + \dots + w_n$ 对 $2^{16} - 1$ 同余。
3. 校验和检测出每一个改变单个比特的差错，更一般地，每一个只落在一个 16 位字内的差错——该字在 `0x0000` 与 `0xFFFF` 之间的互换除外。
4. 校验和检测不出两个 16 位字的互换。
:::

::: proof
对于 (2)：把一个进位回加，是把和 $x = 2^{16}c + y$ 替换为 $y + c$，而 $x - (y + c) = c(2^{16} - 1)$，所以每次折叠都保持对 $2^{16}-1$ 的余数不变。于是最终和与诸字的普通和同余。（一补数算术有两个零的表示，`0x0000` 与 `0xFFFF`；两者都 $\equiv 0$。）性质 (1) 随之成立，因为普通和不依赖于次序。性质 (4) 也成立：互换两个字，普通和不变。

对于 (3)：若一个字从 $w$ 变为 $w'$，接收方的和就改变 $w' - w$（对 $2^{16} - 1$ 取模）。只有当 $w' \equiv w \pmod{2^{16}-1}$ 时它才仍通过检验。由于 $0 \le w, w' \le 2^{16} - 1$，在 $w \ne w'$ 时这只在 $\{w, w'\} = \{\texttt{0x0000}, \texttt{0xFFFF}\}$ 时发生。单个比特翻转把一个字改变 $\pm 2^j$（$0 \le j \le 15$），它永不为 $\pm(2^{16}-1)$，所以总能被检出。
:::

以现代标准看互联网校验和很弱：它漏掉互换的字，随机多比特差错中大约每 $2^{16}$ 个漏掉一个。因此链路使用强得多的循环冗余校验（[[networks/link-layer]]），而互联网校验和是防御*在*路由器和主机内部引入之差错的最后一道防线——链路层的检查看不到那里，这正是 [[networks/network-principles#prop-e2e]] 端到端论据的体现。

::: warning 校验和不是签名
校验和检测的是*偶然*的破坏。它对蓄意对手不提供任何保护：对手可以修改一个分组再重算校验和（或利用性质 4 在不改变校验和的情况下改变数据）。防范攻击者的完整性需要以秘密密钥加钥的**消息认证码**，正如 TLS 和 QUIC 所提供的（[[networks/application-layer]]）；那是一个密码学原语（[[cryptography]]），不是差错检测码。
:::

## 构造可靠信道

我们现在设计一个提供**可靠数据传输**服务的协议：发送应用把报文交给协议，接收协议把每条报文恰好一次、无差错、按发送顺序交付给接收应用。协议运行在一条**不可靠信道**——网络的模型——之上，信道可能对每个分组做下面这些事：

- **破坏**它：我们假定破坏总能被校验和检出（被破坏的分组等同于丢失）；
- **丢失**它；
- 但*不*重排分组：信道是 **FIFO** 的。本章末尾放宽这一条。

一个协议是一对程序——**发送方**和**接收方**——各自是响应事件的状态机：来自应用的一条报文、来自信道的一个分组、一个定时器到期。我们分三步构造它们。

**第 1 步：确认。** 若信道只会破坏分组，接收方就可以对每个分组回以一个**确认**（ACK）——如果它通过了校验和——或一个**否定确认**（NAK）——如果没有；发送方在收到 NAK 后重传。基于这一思想的协议称为 **ARQ**（自动重传请求）协议。

**第 2 步：序号。** 但是 ACK 或 NAK 本身也可能被破坏。发送方吃不准而重传时，接收方可能收到一条它已经交付过的分组的第二份拷贝——而它无法把重复分组与内容相同的新分组区分开。补救办法是每个分组带一个**序号**。对于每发一个分组都要等它被确认后才发下一个的发送方，一个比特就够了：接收方期待的是它最后接受的分组的下一个，带另一个比特的分组就是重复。有了序号，NAK 就不再必要：接收方只需确认它最后接受的那个分组，*带上它的编号*，而对上一个分组的 ACK 就表示“不是这个”。

**第 3 步：定时器。** 若信道还能丢失分组，沉默就是丢失的唯一证据。发送方在发送一个分组时启动一个**定时器**，若定时器到期时确认还没有到达就重传。**超时时间**要选得恰当很难：太短，发送方会重发那些仅仅是被延迟的分组（有序号保证正确性无碍，但浪费）；太长，恢复就慢。它至少应为一个往返时间。TCP 如何估计它见 [[networks/tcp-congestion]]。

合起来，这些就给出经典的协议。

::: algorithm 交替比特协议 {#alg-abp}
**发送方**，带一个比特 $s$，初值 $0$：

1. 等待来自应用的一条报文 $m$。构成分组 $(s, m, \text{校验和})$，发送它，并启动定时器。
2. 等待下列事件之一：
   1. 一个未损坏、携带比特 $s$ 的 ACK：停止定时器，置 $s \gets 1 - s$，转到第 1 步；
   2. 一个损坏的 ACK，或一个携带 $1 - s$ 的 ACK：忽略它，继续等待；
   3. 定时器到期：重发分组 $(s, m, \text{校验和})$，重启定时器，继续等待。

**接收方**，带一个期待比特 $e$，初值 $0$，收到一个分组时：

1. 若它已损坏，忽略它（或确认比特 $1 - e$）。
2. 若它携带比特 $e$：把它的报文交付应用，发送携带比特 $e$ 的 ACK，并置 $e \gets 1 - e$。
3. 若它携带比特 $1 - e$（重复分组）：不交付，但再次发送携带比特 $1 - e$ 的 ACK——上一条 ACK 可能丢了。
:::

::: theorem 交替比特协议的正确性 {#thm-abp}
在可能丢失分组、且破坏可检出的（双向）FIFO 信道上，交替比特协议只把发送方收到过的报文交付给接收应用，每条至多一次、按序交付。进一步，若每个被无限次重传的分组终会被完好收到，则每条报文终会被交付。
:::

::: proof
给报文编号 $0, 1, 2, \dots$；报文 $i$ 以比特 $i \bmod 2$ 发送。设 $m$ 为发送方当前报文的编号（于是 $s = m \bmod 2$），$d$ 为接收方已交付的报文数（于是 $e = d \bmod 2$）。我们证明下面结论始终成立：

**不变式。** 或者 (A) $d = m$：接收方恰好交付了报文 $0, \dots, m-1$，前向信道中的每个数据分组都是报文 $m - 1$ 或 $m$ 的拷贝，所有 $m-1$ 的拷贝都在所有 $m$ 的拷贝之前，且反向信道中的每个 ACK 都携带比特 $1 - s$；或者 (B) $d = m + 1$：接收方恰好交付了 $0, \dots, m$，前向信道中的每个数据分组都是 $m$ 的拷贝，且反向信道中的 ACK 是若干个携带比特 $1 - s$ 的后面（按 FIFO）跟着若干个携带比特 $s$ 的。

初始 (A) 成立，$m = d = 0$，信道为空。考察每个事件。

- **在 (A) 态，接收方收到 $m - 1$ 的一份拷贝**：它携带比特 $(m-1) \bmod 2 = 1 - e$，所以接收方重新确认比特 $1 - e = 1 - s$。(A) 仍成立。
- **在 (A) 态，接收方收到 $m$ 的一份拷贝**：它携带比特 $e$，于是接收方交付报文 $m$——正确的下一条报文——发送 ACK $e = s$，且 $d$ 变为 $m + 1$。$m - 1$ 的所有拷贝在 FIFO 信道中都排在这个分组之前，所以都已离开，只剩下 $m$ 的拷贝。携带比特 $s$ 的 ACK 加入反向信道，排在一切携带比特 $1 - s$ 的之后。(B) 成立。
- **在 (B) 态，接收方收到 $m$ 的一份拷贝**：它携带比特 $m \bmod 2 = 1 - e$（因为 $e = (m+1) \bmod 2$），是重复分组；接收方重新确认比特 $1 - e = s$。(B) 成立。
- **发送方收到携带比特 $1 - s$ 的 ACK**：忽略，一切不变。（在 (A) 态只有这类 ACK。）
- **在 (B) 态，发送方收到携带比特 $s$ 的 ACK**：它前进到 $m + 1$。此时 $d = m + 1$ 成为新的 $m$；前向信道中保存着旧 $m$ 的拷贝，现在它们是“$m-1$”，发送方的新分组排在它们之后；反向信道中剩下的 ACK 携带旧比特 $s$，即新的 $1 - s$。(A) 成立。
- **超时、丢失与破坏**只是向当前报文的前向信道尾部追加拷贝，或删除分组；它们既不改变处于哪种情形，也不改变那些次序性质。

交付只发生在第二种情形，且总是在 $d = m$ 时交付报文 $d$：所以报文按序交付，每条一次。活性方面：在 (A) 态，发送方重传报文 $m$ 直到它被收到，这终将发生；于是 (B) 成立，而接收方对每份拷贝都作确认，所以发送方终会收到携带比特 $s$ 的 ACK 并前进。
:::

证明指明了 FIFO 假设用在哪里：它保证报文 $m-1$ 的陈旧拷贝不会超过报文 $m$、赶在接收方期待报文 $m + 1$（其比特相同）时到达。在可以任意重排分组的信道上，没有任何使用有限序号集合的协议能保持正确；真实协议转而假定一个*分组最长生存时间*，过了它，旧分组必然已经消失。

### 停止等待的代价

交替比特协议是一个**停止等待**协议：发送一个分组，等待一个往返收取它的确认。

::: proposition 停止等待的利用率 {#prop-stopwait}
在速率为 $R$、往返时间为 $\text{RTT}$、分组长 $L$ 比特、ACK 大小可忽略、无丢失的信道上，停止等待发送方处于发送状态的时间占比为

$$
U_\text{sender} = \frac{L/R}{\text{RTT} + L/R}
$$ {#eq-utilisation}

其吞吐量为 $L / (\text{RTT} + L/R)$。
:::

::: proof
一个周期从发送方开始发送一个分组的时刻起，到它可以开始下一个分组的时刻止：发送分组花 $L/R$，之后它的最后一个比特在 $\text{RTT}/2$ 后到达接收方，ACK 再经 $\text{RTT}/2$ 返回。周期长 $\text{RTT} + L/R$，其中发送方发送了 $L/R$，交付 $L$ 比特。
:::

::: example 跨越大陆的停止等待 {#ex-stopwait}
一条 1 Gb/s 路径的 RTT 为 30 ms。一个停止等待协议发送 1500 字节的分组。它的利用率和吞吐量是多少？
::: solution
$L/R = 12000 / 10^9 = 12$ µs。由 [[#eq-utilisation]]，$U = 0.012 / 30.012 \approx 0.0004$：发送方只有 0.04% 的时间在发送。吞吐量为 $12000\ \text{bits} / 30.012\ \text{ms} \approx 400$ kb/s——可这是一条千兆比特链路。协议正确而无用。带宽时延乘积为 $10^9 \times 0.03 = 3 \times 10^7$ 比特，约 2,500 个分组；要想用满链路，发送方必须有那么多未确认的分组在途。
:::
:::

## 流水线

**流水线**协议允许发送方在收到确认之前最多发送 $N$ 个分组。这就需要比一个比特更大的序号范围、发送方的缓冲（存放已发送而尚未确认、可能需要重传的分组），以及可能的接收方缓冲。有两种基本设计，区别在于如何从丢失中恢复。

两者都使用**滑动窗口**。发送方的序号落入四个区域：已确认；已发送但尚未确认；可用——尚未发送但在窗口允许之内；尚不可用。**窗口**是从**基**（最旧的未确认分组）开始的 $N$ 个序号的范围。随着确认到达，基上移，窗口向前滑动。

caption: 发送方利用率 $U = \min(1, N \cdot (L/R) / (\text{RTT} + L/R))$ 随窗口大小 $N = x$（以分组计）的变化（下面的 [[#eq-window-util]]），其中发送时间 $L/R = l$、$\text{RTT} = r$，均以毫秒计。初始值取自 [[#ex-stopwait]]：1 Gb/s 上的 1500 字节分组，RTT 30 ms。利用率线性增长，直到窗口覆盖整个往返，然后饱和；拐点位于以分组计的带宽时延乘积处。增大 $r$，看拐点如何右移：长路径需要大窗口。增大 $l$（更大的分组或更慢的链路），需要的分组数就少了。
:::

### 回退 N 帧

::: algorithm 回退 N 帧（Go-back-N） {#alg-gbn}
序号对 $2^k$ 取模；窗口大小为 $N$。

**发送方**，带变量 $\textit{base}$ 和 $\textit{next}$，初值均为 $0$：

1. *应用发来报文*：若 $\textit{next} < \textit{base} + N$，发送携带该报文的分组 $\textit{next}$，若 $\textit{base} = \textit{next}$ 则启动定时器，并置 $\textit{next} \gets \textit{next} + 1$；否则拒绝（或缓存）该报文。
2. *收到 ACK $a$*（累计式：“直到 $a$ 为止的所有分组都已到达”）：置 $\textit{base} \gets a + 1$；若 $\textit{base} = \textit{next}$ 则停止定时器，否则重启它。
3. *超时*：重启定时器，重发所有分组 $\textit{base}, \dots, \textit{next} - 1$。

**接收方**，$\textit{expected}$ 初值为 $0$：收到编号恰为 $\textit{expected}$ 且未损坏的分组时，交付它，发送 ACK $\textit{expected}$，并把 $\textit{expected}$ 加一；收到任何其他分组时，丢弃它并重发 ACK $\textit{expected} - 1$。
:::

回退 N 帧的接收方简单到不能再简单：它不保留缓冲区，只按序接受下一个分组。单个定时器属于最旧的未确认分组。代价是一次丢失就丢弃在它之后发送的所有分组，即使它们到达了，发送方也必须重发。

::: example 一次丢失下的回退 N 帧 {#ex-gbn}

::: solution

| | | 收到 0：交付，ACK 0 |
| | | 收到 1：交付，ACK 1 |

### 选择重传

::: algorithm 选择重传 {#alg-sr}
序号对 $2^k$ 取模；发送方和接收方的窗口大小均为 $N$。

**发送方**：与回退 N 帧相同，$\textit{base}, \dots, \textit{base} + N - 1$ 的分组可以处于未决状态，但为**每个**分组保留一个单独的定时器。分组 $n$ 超时的时候，只重发分组 $n$。收到分组 $n$ 的 ACK（个别确认，不是累计确认）时，把 $n$ 标记为已确认；若 $n = \textit{base}$，则把 $\textit{base}$ 推进到最小的未确认序号。

**接收方**，窗口 $[\textit{rbase}, \textit{rbase} + N - 1]$：

1. 窗口内的分组 $n$：发送 ACK $n$，若它是新的就缓存该分组。若 $n = \textit{rbase}$，交付它以及紧随其后的所有编号连续的已缓存分组，并把 $\textit{rbase}$ 推进到它们之后。
2. $[\textit{rbase} - N, \textit{rbase} - 1]$ 内的分组 $n$（已经交付过）：再次发送 ACK $n$——先前那条 ACK 可能丢了——但不交付它。
3. 其他情况忽略该分组。
:::

选择重传只重发丢失的分组，代价是接收方缓冲和每分组定时器。在 [[#ex-gbn]] 的设定下改用选择重传，分组 3、4、5 会被接收方缓存，只有分组 2 在它自己的定时器到期时重发，2–5 随它的到达一起交付：$8$ 次发送而不是 $11$ 次。

::: example 窗口内的序号太多时 {#ex-sr-ambiguity}
一个选择重传协议使用 2 位序号（$0$–$3$）和大小 $N = 3$ 的窗口。给出一个运行过程，其中接收方把一个重复分组当成新数据接受。
::: solution
发送方发送真实编号为 $0, 1, 2$ 的分组，携带序号 $0, 1, 2$。三个都到达；接收方交付它们，逐一确认，并把自己的窗口移到真实编号 $3, 4, 5$，对应序号 $3, 0, 1$。三条 ACK 全部丢失。发送方分组 $0$ 的定时器到期并重发它，序号为 $0$。接收方看到序号 $0$，它落在自己的窗口里——于是把它当成真实分组 $4$，把旧数据当作新数据缓存起来。数据就此被破坏，却不被察觉。

若 $N = 2$，同样的运行过程就无害：交付 $0$ 和 $1$ 之后，接收方的窗口是真实编号 $\{2, 3\}$、序号 $\{2, 3\}$，而发送方只能重发序号 $\{0, 1\}$，接收方认出那是上一个窗口，重新确认即可。
:::
:::

这个例子可以推广为一个精确的上界。

::: theorem 序号对 $2^k$ 取模时的窗口大小 {#thm-window}
假定可能丢失分组的 FIFO 信道和 $k$ 位序号。当且仅当 $N \le 2^k - 1$ 时，回退 N 帧对一切丢失模式都能正确工作。当且仅当 $N \le 2^{k-1}$ 时，选择重传对一切丢失模式都能正确工作。
:::

::: proof
记 $n$ 为分组的真实（无界）编号；它以 $n \bmod 2^k$ 发送。设 $r$ 为接收方下一个期待的真实编号（选择重传情形下 $r = \textit{rbase}$），$b$ 为某时刻发送方的基。两个事实始终成立。第一，$b \le r$：发送方只在 ACK 时前进，而 ACK 只承认接收方收到的分组，接收方又只收到过小于 $r$ 的分组。（选择重传中，$[b, r)$ 内的分组可能被个别确认，但 $b$ 只越过已确认的分组，这些分组或者小于 $r$，或者缓存在接收方的窗口内；两种情形下对基都有 $b \le r$，且所有未决分组都小于 $b + N$。）第二，$b \ge r - N$：接收方收到过分组 $r - 1$，它是发送方在窗口包含它时发出的，所以对于当时的基 $b'$ 有 $r - 1 \le b' + N - 1$，且 $b \ge b'$。于是发送方能发送或重发的每个分组——包括仍滞留信道中的那些，由 FIFO 和同样的论证，它们是从基至少为 $r - N$ 的窗口发出的——其真实编号都落在 $[r - N, r + N - 1]$ 内。

*回退 N 帧，充分性。* 接收方必须恰好接受真实编号为 $r$ 的那个分组。$[r - N, r + N - 1]$ 内的另一个分组与它序号相同，只有当它的真实编号是 $r \pm 2^k$。但发送方分组的真实编号至多为 $b + N - 1 \le r + N - 1$；所以 $r + 2^k$ 只可能在 $2^k \le N - 1$ 时出现，而 $r - 2^k \ge r - N$ 只有当 $2^k \le N$。当 $N \le 2^k - 1$ 时，两者都不会发生。

*选择重传，充分性。* 接收方必须把落在自己窗口 $[r, r + N - 1]$ 内的分组（应缓存）与 $[r - N, r - 1]$ 内的分组（应重新确认）区分开。这两个区间合起来是 $2N$ 个连续的真实编号。若 $2N \le 2^k$，它们的序号两两不同，于是接收方对每个分组的归类都正确。

*必要性。* 对于 $N = 2^k$（或更大）的回退 N 帧：发送方发出真实分组 $0, \dots, 2^k - 1$，全部被接收并交付，所有 ACK 丢失。接收方现在期待真实编号 $2^k$，序号 $0$；发送方超时重发真实分组 $0$，序号 $0$，接收方把它当作新数据交付。对于 $N > 2^{k-1}$ 的选择重传：发送方发出真实 $0, \dots, N-1$；全部到达且所有 ACK 丢失；接收方的窗口是 $[N, 2N - 1]$，因为 $N \le 2^k \le 2N - 1$，其中包含真实编号 $2^k$；发送方重发真实 $0$，它的序号与 $2^k$ 的相同，接收方把它当作新数据接受（[[#ex-sr-ambiguity]] 就是 $k = 2$、$N = 3$ 的情形）。
:::

### 吞吐量与丢失

窗口为 $N$ 个分组时，发送方每个 $\text{RTT} + L/R$ 的周期发送 $N$ 个分组，只要这不超过链路速率：

$$
U = \min\left(1,\ \frac{N \cdot L/R}{\text{RTT} + L/R}\right).
$$ {#eq-window-util}

填满管道所需的窗口为 $N \ge 1 + \text{RTT}/(L/R)$：以分组计的带宽时延乘积，再加一。在 [[#ex-stopwait]] 中那是 $2501$ 个分组。

丢失对两个协议的影响各不相同。考察一个窗口恰好填满管道的发送方，在每个长 $L/R$ 的时隙发送一个分组，信道以概率 $p$ 独立地丢失每个数据分组，并设丢失恰好在窗口用完时被察觉，即丢失分组发出后 $N$ 个时隙。选择重传只重发丢失的分组，所以每个分组平均需要 $1/(1-p)$ 次发送，效率为 $1 - p$。回退 N 帧中，一次失败的发送还浪费了它之后的 $N - 1$ 个时隙。一个分组失败的次数服从几何分布、均值为 $p/(1-p)$，所以它平均花费 $1 + N p/(1 - p)$ 个时隙，效率为

$$
E_\text{GBN} = \frac{1 - p}{1 + (N - 1)p}.
$$ {#eq-gbn-eff}

```python
# gbn.py：回退 N 帧在有损信道上运行，每个时隙发送一个分组
import random

def go_back_n(n, N, D, p, seed=1):
    """Send packets 0..n-1 with window N over a channel with one-way delay D slots
    that loses each data packet with probability p (ACKs are not lost)."""
    rng = random.Random(seed)
    base = nxt = expected = 0                    # 发送方窗口 [base, nxt)；接收方
    timer, sent, t = None, 0, 0
    data, acks, delivered = [], [], []           # 信道内容：（到达时刻，序号）
    while expected < n:
        for a in [s for (at, s) in acks if at == t]:      # 到达的累计 ACK
            if a >= base:
                base = a + 1
                timer = t + 2 * D + 1 if base < nxt else None
        if timer is not None and t >= timer:     # 超时：回退到 base
            nxt, timer = base, None
        if nxt < min(base + N, n):               # 窗口允许就发送一个分组
            if rng.random() >= p:
                data.append((t + D, nxt))
            if timer is None:
                timer = t + 2 * D + 1
            nxt, sent = nxt + 1, sent + 1
        for s in [s for (at, s) in data if at == t]:      # 接收方：只按序接收
            if s == expected:
                delivered.append(s)
                expected += 1
            acks.append((t + D, expected - 1))
        t += 1
    assert delivered == list(range(n))           # 每个分组恰好一次、按序
    return sent, t

for p in (0.0, 0.01, 0.05, 0.1):
    sent, slots = go_back_n(20000, N=9, D=4, p=p)
    print(f"p={p:<4} transmissions per packet {sent / 20000:.3f}"
          f"  predicted {(1 + 8 * p) / (1 - p):.3f}")
```

```console
p=0.01 transmissions per packet 1.101  predicted 1.091
p=0.05 transmissions per packet 1.477  predicted 1.474
p=0.1  transmissions per packet 2.016  predicted 2.000
```

该模拟在单向时延 $4$ 个时隙（于是窗口 $2 \times 4 + 1$ 个时隙恰好填满管道）的信道上，用窗口 $N = 9$ 发送 20,000 个分组，并检查接收方恰好一次、按序交付了每个分组。每分组发送次数与模型的 $1/E_\text{GBN} = (1 + (N-1)p)/(1-p)$ 在本次运行的随机涨落范围内吻合。

::: quiz
一个回退 N 帧接收方已经交付了分组 0–9，现在收到分组 11。它怎么做？
- [ ] 缓存分组 11 并发送 ACK 11。
- [x] 丢弃分组 11 并发送 ACK 9。
- [ ] 丢弃分组 11 并为分组 10 发送 NAK。
- [ ] 交付分组 11 并等待分组 10。
::: solution
回退 N 帧接收方只按序接受下一个分组，这里是 10（[[#alg-gbn]]）。它丢弃 11，重复它对最后一个有序分组的累计确认 ACK 9；发送方最终会超时并重发从 10 起的一切。（这种重复 ACK 正是 TCP 的*快速重传*用作丢失早期信号的东西：[[networks/tcp-congestion]]。）缓存分组 11 并逐个确认它是选择重传的做法。
:::

## 实践中

真实的传输协议把这些思想结合起来。TCP 给*字节*编号而不是给分组编号，序号有 32 位；它的确认像回退 N 帧那样是累计式的，携带下一个期待字节的编号；但几乎所有实现都像选择重传那样缓存乱序数据，而**选择性确认**选项（SACK，RFC 2018）让接收方报告它在累计点之后还持有哪些数据块，使发送方只重发空缺。即使在快路径上，$2^{32}$ 个字节序号也会在几秒之内绕回——在 10 Gb/s 下约 $3.4$ s——比旧分组可能在网络中滞留的时间还短，于是 TCP 加上时间戳来分辨新旧分组（PAWS，RFC 7323）。QUIC 用另一种方式回避了这个问题：它的分组编号高达 $2^{62}$ 且从不复用，即使重传也是把丢失的数据装进新分组发送；这同时也消除了“一个确认对应分组的哪一份拷贝”的歧义。

[[#thm-abp]] 的 FIFO 假设在互联网中并不成立：走不同路由的分组可能被重排。协议转而依赖对分组能存活多久的界定——IP 的生存时间字段和一个*最长报文段寿命*（MSL，TCP 假定它为两分钟）——并把序号空间取得足够大，使得带有某个旧序号的分组还可能存在的期间内，该序号不会被复用。剩下的设计问题——网络由其他发送方共享，窗口究竟应该多大——就是下一章的主题。

::: history
交替比特协议由英国国家物理实验室（National Physical Laboratory，唐纳德·戴维斯（Donald Davies）分组交换研究的大本营）的 K. A. Bartlett、R. A. Scantlebury 与 P. T. Wilkinson 在"A note on reliable full-duplex transmission over half-duplex links"（*Communications of the ACM*，1969）中发表。带回退 N 恢复的滑动窗口协议被内置进 1970 年代的数据链路层协议，著名的是 IBM 的 SDLC 及其 ISO 后继 HDLC；滑动窗口还是瑟夫（Cerf）与卡恩（Kahn）1974 年传输控制程序的核心。N. V. Stenning 的"A data transfer protocol"（1976）给出了滑动窗口协议最早的形式化正确性证明之一，开创了协议验证研究的漫长脉络。互联网校验和的设计与快速实现由 R. Braden、D. Borman 与 C. Partridge 在 RFC 1071（1988）中给出。
:::

## 后续内容

[[networks/tcp-congestion]] 把本章的协议变成 TCP：连接的建立与释放、字节序号、超时估计、流量控制，以及决定窗口大小的拥塞控制。比校验和更强的差错检测码以及链路层重传出现在 [[networks/link-layer]] 与 [[networks/wireless-mobile]]。为 [[#thm-abp]] 所用的正确性证明风格——对若干台机器的状态与它们之间信道的一个不变式——在 [[distributed-systems]] 中针对分布式算法进一步发展，在有损信道上无法达成可靠一致（“两将军”问题）也在那里出现。

::: summary
- 传输层按端口号把报文段**分用**给套接字。**UDP** 只在 IP 之上加上端口、长度和校验和（8 字节）（[[#def-udp]]）。
- **互联网校验和**是 16 位字一补数和的反码（[[#def-checksum]]）；它能检出所有单比特差错，但检不出互换的字，而且防不了攻击者（[[#prop-checksum]]）。
- 在有损信道上可靠传输需要**确认**、**序号**（识别重复分组）和**定时器**（检测丢失）。**交替比特协议**在 FIFO 信道上正确（[[#thm-abp]]）。
- 停止等待的利用率为 $(L/R)/(\text{RTT} + L/R)$（[[#prop-stopwait]]）；填满一条路径需要一个约等于一个带宽时延乘积的窗口。
- **回退 N 帧**使用累计 ACK 和单个定时器，丢失后重发整个窗口；**选择重传**缓存乱序分组，只重发丢失的。
- 使用 $k$ 位序号时，回退 N 帧要求 $N \le 2^k - 1$，选择重传要求 $N \le 2^{k-1}$（[[#thm-window]]）。
- 有丢失时，回退 N 帧的效率 $(1-p)/(1 + (N-1)p)$ 在大窗口下崩溃，而选择重传的效率是 $1 - p$（[[#eq-gbn-eff]]）。
:::

$L = 10^4$ 比特，所以 $L/R = 10^4/10^8 = 0.1$ ms，由 [[#eq-utilisation]] 得 $U = 0.1/(10 + 0.1) = 1/101 \approx 0.0099$：约 1%，即约 990 kb/s 的吞吐量。
:::

::: exercise 填满管道 {level=2 check="2251"}
对 [[#ex-stopwait]] 的路径（1 Gb/s，RTT 30 ms，1500 字节分组），使利用率至少达到 90% 的最小窗口是多少（以分组计）？选择重传为这个窗口需要多少位序号？（输入窗口。）
::: solution
由 [[#eq-window-util]] 需要 $N \cdot 0.012 / 30.012 \ge 0.9$，即 $N \ge 0.9 \times 30.012/0.012 = 2250.9$，所以 $N = 2251$。选择重传需要 $2^{k-1} \ge 2251$，故 $k - 1 \ge 12$（$2^{11} = 2048$ 不够，$2^{12} = 4096$ 够用）：$k = 13$ 位。
:::

::: exercise 数一数回退 N 帧的发送次数 {level=2 check="9"}
一个窗口 $N = 3$ 的回退 N 帧发送方发送分组 $0$ 到 $5$。分组 1 第一次发送时丢失；其他什么都不丢，且超时足够长，不会有任何分组白白超时。总共进行了多少次发送？（输入数目。）
::: solution
发送方发送 0, 1, 2。分组 0 到达（ACK 0），于是窗口变为 $[1, 3]$，发送方发送 3。分组 1 丢失；2 和 3 被丢弃，每次都重新产生 ACK 0。窗口一直保持 $[1, 3]$，直到超时后重发 1, 2, 3 并被逐一确认，使发送方得以发送 4 和 5。发送次数：$0, 1, 2, 3$（$4$ 次），$1, 2, 3$（$3$ 次），$4, 5$（$2$ 次）：共 $9$ 次。
:::

::: exercise 有损信道上的停止等待 {level=2}
在交替比特协议中，每个数据分组以概率 $p$ 独立丢失，ACK 从不丢失，且超时恰设在一次发送结束后一个 RTT 处（于是一个 ACK 本该到达的时刻，超时恰好触发）。证明每条报文的期望发送次数为 $1/(1-p)$，吞吐量为 $(1 - p) L / (\text{RTT} + L/R)$。若 ACK 也以概率 $q$ 独立丢失，结论还成立吗？
::: solution
每次尝试以概率 $1 - p$ 成功，且相互独立，所以尝试次数服从均值 $1/(1-p)$ 的几何分布。每次尝试——无论成败——都恰好花费 $\text{RTT} + L/R$（失败的那次在 ACK 本该到达的时刻以超时告终）。于是每条报文的期望时间为 $(\text{RTT} + L/R)/(1-p)$，由更新报酬定理（长期速率 = 每个周期的报酬 / 平均周期长度），吞吐量为 $(1-p) L/(\text{RTT} + L/R)$。若 ACK 也丢失，一次尝试只有当分组和它的 ACK 都到达才成功，概率为 $(1 - p)(1 - q)$，于是平均尝试次数为 $1/((1-p)(1-q))$，吞吐量乘以 $(1-p)(1-q)$。丢失的 ACK 造成的额外发送送来的是重复分组，接收方把它们丢弃并重新确认。
:::
:::

::: exercise 校验和查不出的差错 {level=3}
(a) 用 [[#prop-checksum]] 的性质 2 证明：互联网校验和恰好当字的普通和改变 $2^{16} - 1$ 的倍数时查不出差错。(b) 找出两个不同、仅两个比特位置不同的 4 字节消息，使它们校验和相同。(c) 解释为什么校验和与字节序无关：对字节互换后的字计算它，得到的是字节互换后的校验和（RFC 1071 据此让小端机器免去转换）。
::: solution
(a) 接收方的检验在一包括校验和在内的所有字的一补数和 $\equiv 0 \pmod{2^{16}-1}$ 时通过。数据完好时正是如此。一个差错使普通和改变某个 $\Delta$，由性质 2，一补数和改变 $\Delta \bmod (2^{16}-1)$；所以差错查不出当且仅当 $\Delta \equiv 0 \pmod{2^{16} - 1}$。

(b) 把第一个字的比特 $0$ 从 $0$ 翻成 $1$（加上 $1$），把第二个字的比特 $0$ 从 $1$ 翻成 $0$（减去 $1$）：$\Delta = 0$。例如字 `0x0000 0x0001` 与 `0x0001 0x0000`（字节 `00 00 00 01` 与 `00 01 00 00`）的一补数和都是 `0x0001`，校验和都是 `0xFFFE`。任意两个字的同一比特位置上一对相反的翻转都会被漏掉。

(c) 交换一个 16 位字的两个字节就是旋转 8 位。在一补数算术里，把每个加数都旋转 8 位会把和也旋转 8 位，因为回环进位使求和的行为就像在一个 16 位的环上做算术，其中比特 15 的进位进入比特 0，恰如比特 7 的进位进入比特 8：无论把哪个字节称为高位，做的都是同一个“环形”运算。而取反与旋转可交换。所以对着字节互换后的字算出的校验和，就是校验和的字节互换，小端机器可以直接对本机字节序读入的 16 位字求和并原样存下结果。
:::
:::

::: exercise 一个选择重传模拟器 {level=3}
把 `gbn.py` 改造成选择重传：每分组定时器（各 $2D + 1$ 个时隙）、个别 ACK，以及缓存窗口 $[\textit{rbase}, \textit{rbase} + N - 1]$ 内分组的接收方。内部使用真实（无界）编号，但在接收方接受每个分组时检查它的真实编号落在窗口内——也就是说，一个只见 $2^k$ 取模序号、且 $2N \le 2^k$ 的接收方本会把它正确归类。对 $N = 9$、$D = 4$、$p \in \set{0.01, 0.05, 0.1}$ 测量每分组发送次数，并与预测值 $1/(1-p)$ 比较。
::: solution
```python
import random

def selective_repeat(n, N, D, p, seed=1):
    rng = random.Random(seed)
    base = nxt = rbase = 0
    timers, acked, buffered, delivered = {}, set(), set(), []
    data, acks, sent, t = [], [], 0, 0
    while rbase < n:
        for a in [s for (at, s) in acks if at == t]:    # 个别 ACK
            acked.add(a)
            timers.pop(a, None)
            while base in acked:
                base += 1
        resend = [s for s, due in timers.items() if due <= t]
        if resend:                                       # 重传最早超时的分组
            s = min(resend)
        elif nxt < min(base + N, n):
            s, nxt = nxt, nxt + 1
        else:
            s = None
        if s is not None:                                # 每个时隙至多一次发送
            if rng.random() >= p:
                data.append((t + D, s))
            timers[s] = t + 2 * D + 1
            sent += 1
        for s in [s for (at, s) in data if at == t]:
            assert rbase - N <= s < rbase + N            # 若 2N <= 2^k 则可模 2^k 归类
            if s >= rbase:
                buffered.add(s)
                while rbase in buffered:
                    buffered.remove(rbase)
                    delivered.append(rbase)
                    rbase += 1
            acks.append((t + D, s))                      # 新分组和重复分组一律 ACK
        t += 1
    assert delivered == list(range(n))
    return sent

for p in (0.01, 0.05, 0.1):
    print(f"p={p:<4} transmissions per packet {selective_repeat(20000, 9, 4, p) / 20000:.3f}"
          f"  predicted {1 / (1 - p):.3f}")
```

```console
p=0.01 transmissions per packet 1.011  predicted 1.010
p=0.05 transmissions per packet 1.054  predicted 1.053
p=0.1  transmissions per packet 1.114  predicted 1.111
```

对 $s$ 的断言从不失败，正如 [[#thm-window]] 所预测：接收方看到的每个分组都在其窗口基的 $N$ 之内。与同一信道上回退 N 帧的 $1.101$、$1.477$ 和 $2.016$ 相比，选择重传只发送丢失的东西。注意其中 ACK 从不丢失这个简化；加上 ACK 丢失无需改动任何逻辑，因为丢失的 ACK 只会造成超时和重复分组，而接收方会对重复分组重新确认。
:::
