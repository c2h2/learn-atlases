像"某个课程拿了 A 的学生的姓名"这样的查询，对数据库来说不过是一个关系代数表达式：Student 与 Enrolled 的一次连接、对成绩的一次选择、一次投影。这个表达式里的每个算子，都必须由读取真实页的真实算法来完成。选择只有几种做法；连接却有很多族，同一份输入上它们的代价能相差一万倍。一千页的表与五百页的表做连接，朴素的嵌套循环要五千万次页读，哈希连接只要四千五百次——按每次随机读几毫秒计，约八小时对三秒。

本章是查询求值的**物理**层。先说明计划如何被执行（迭代器模型），然后给出选择、排序、连接与聚集的主要算法，每个都在 [[databases/storage-indexing#def-io-model]] 的 I/O 代价模型中分析——附带正确性与代价公式的证明，以及一个贯穿的数值例子。下一章（[[databases/query-optimisation]]）用这些公式在计划之间做选择。

**记号。** 关系 $R$：$B(R)$ 页，$T(R)$ 个元组；$M$ 是该算子可用的缓冲帧数。代价计页的读与写，但按惯例*不*计写出最终结果的代价——它对每个算法都一样。贯穿示例把 Enrolled（$E$：$B(E) = 1000$ 页，$T(E) = 100\,000$ 个元组）与 Student（$S$：$B(S) = 500$ 页，$T(S) = 40\,000$ 个元组）按 sid 连接，取 $M = 52$ 帧。

## 从查询到计划

一条查询要经过若干阶段。**解析器**检查 SQL 并构造语法树；**重写器**展开视图并把查询规范化；**优化器**产出一个**物理计划**——一棵树，其结点是"哈希连接"、"索引扫描"这类算法而不是代数算子；**执行器**负责运行它。

::: definition 迭代器（Volcano）模型 {#def-iterator}
在**迭代器模型**中，每个物理算子实现三个方法：`open()` 做准备（并打开其孩子），`next()` 返回下一个输出元组或结束标记，`close()` 释放资源。算子通过调用孩子的 `next()` 获得输入。若算子边读输入边产生输出，称它是**流水线的**；若必须先消费完整个输入才能产出任何输出，称它是**阻塞的**。
:::

选择与投影是流水线的：每次 `next()` 都从孩子往下拉，直到拉出一个合格的元组。排序是阻塞的：最小的元组可能是最后一个才读到的。执行由根结点按需驱动：客户只要十行（`LIMIT 10`），计划产出十行就停，下面的扫描也随之停止读取。Python 生成器能直接表达这个模型：

```python
from collections import defaultdict
calls = defaultdict(int)                         # 每个算子产出了多少行

def scan(table, name):
    for row in table:
        calls[name] += 1
        yield row

def select(child, pred, name):
    for row in child:
        if pred(row):
            calls[name] += 1
            yield row

def hash_join(build, probe, bkey, pkey, name):
    table = defaultdict(list)
    for b in build:                              # 阻塞：先消费完 build 侧
        table[b[bkey]].append(b)
    for p in probe:                              # 流水线：流式处理 probe 侧
        for b in table.get(p[pkey], []):
            calls[name] += 1
            yield p + b

def limit(child, n):
    for i, row in enumerate(child, start=1):
        yield row
        if i == n:
            return                               # 停止拉取：上游的工作也随之停止
```

在 [[databases/relational-model]] 的十行 Enrolled 与五行 Student 上，运行计划"前两条得 A 的选课记录连同姓名"：

```python
plan = limit(hash_join(scan(Student, "scan S"),
                       select(scan(Enrolled, "scan E"), lambda e: e[2] == "A", "select"),
                       0, 0, "join"), 2)
for row in plan:
    print(row[4], row[1])
print(dict(calls))
```

```console
$ python3 volcano.py

Ada MA101
{'scan S': 5, 'scan E': 3, 'select': 2, 'join': 2}
```

构建侧（Student）被整个读完——哈希连接的构建阶段是阻塞的——但十行 Enrolled 只读了三行，因为 limit 在得到两个结果后就停止了拉取。当一个算子的输出必须存放起来再重读（例如嵌套循环连接的内侧输入本身是一个连接时），它被**物化**到一个临时文件中，代价是写它和读它。现代引擎常常每次调用处理一批元组（**向量化执行**），或把计划编译成机器码，但逻辑结构不变。

## 选择

对选择 $\sigma_\theta(R)$，可选项取决于 $\theta$ 与可用的访问路径（[[databases/storage-indexing]]）。

- **文件扫描**：读全部 $B(R)$ 页，测试每个元组。永远可行。
- **二分查找**用于按 $A$ 排序的文件，适用 $A = c$ 或 $A$ 上的范围：$\lceil\log_2 B(R)\rceil$ 加上存放匹配项的页。
- **索引扫描**，用 $A$ 上的 B+树：约 $h + 1$ 次 I/O 到达第一个匹配叶子，加上匹配的叶子，再加上数据页——聚簇约 $s \cdot B(R)$，非聚簇至多 $s \cdot T(R)$，其中 $s$ 是被选元组的比例（[[databases/storage-indexing#ex-unclustered]]）。
- **哈希索引**在 $A$ 上，仅限等值：到桶约 $1$–$2$ 次 I/O，加上匹配的记录。

合取 $\theta_1 \wedge \theta_2$ 可以为选择性最强的那个合取项用索引，其余条件在取回的元组上测试；或者用两个索引，在内存里求两者 rid 集的交，只取交中的元组。析取 $\theta_1 \vee \theta_2$ 只有当*每个*析取项都有索引时才能用索引（对 rid 集求并）；否则终究要扫描，因为满足无索引析取项的元组可能位于任何地方。

::: example 合取与析取的访问路径 {#ex-access-path}
Enrolled 有 $T = 100\,000$ 个元组、$B = 1000$ 页，code 上有聚簇 B+树、grade 上有非聚簇 B+树，高度都是 $2$。条件 `code = 'CS202'` 匹配 $200$ 个元组（分布在 $2$ 页上），`grade = 'A'` 匹配 $25\%$ 的元组。为 (a) `code = 'CS202' AND grade = 'A'` 与 (b) `code = 'CS202' OR grade = 'A'` 各选一个计划。
::: solution
(a) 候选：文件扫描，$1000$ 次 I/O；code 索引，$h + 1 = 3$ 次 I/O 到第一个叶子，加 $2$ 个数据页，再在取回的 $200$ 个元组上测试 grade，约 $5$ 次 I/O；grade 索引，$3$ 次加上至多 $25\,000$ 次随机数据页读，再测试 code。聚簇的 code 索引把扫描比下去了，相差 $200$ 倍。把两个索引的 rid 集求交帮不上忙：仅读 grade 索引的 $25\,000$ 个条目所花的叶子页，就比 code 索引计划的全部代价还多。

(b) 元组满足任一条件即合格，所以计划必须找出所有 `grade = 'A'` 的元组，占全表的 $25\%$。走非聚簇的 grade 索引至多要 $25\,000$ 次 I/O（rid 按页排序后约 $1000$ 次），于是计划是一次文件扫描，$1000$ 次 I/O，两个条件一起测试。析取的代价由它*最不*选择性的析取项决定。
:::
:::

## 外部排序

`ORDER BY` 要排序，批量装载建 B+树要排序，去重与分组要排序，排序归并连接也要排序。当 $B(R)$ 超过 $M$，数据无法在内存中排完，就要用**外部归并排序**。

::: algorithm 外部归并排序 {#alg-external-sort}
输入：$B$ 页的文件，$M \ge 3$ 个缓冲帧。
1. **第 0 趟（生成归并段）。** 反复读入 $M$ 页，在内存中给这些元组排序，写 out 为一个有序**归并段**。这产生 $\lceil B/M \rceil$ 个各占 $M$ 页的归并段（最后一个可能短些）。
2. **归并趟。** 只要归并段多于一根：把归并段每 $M - 1$ 个分成一组，每组合并成一个归并段，每个归并段用一个输入帧，另用一个输出帧。每轮归并反复把 $M - 1$ 个当前段首中最小的元组移入输出帧，输出帧写满就落盘，某个归并段的输入帧空了就读它的下一页。
:::

::: theorem 外部归并排序的代价 {#thm-sort-cost}
[[#alg-external-sort]] 把文件排好序需要

$$
P(B, M) = 1 + \Bigl\lceil \log_{M-1} \lceil B/M \rceil \Bigr\rceil
$$ {#eq-sort-passes}

趟，每趟把每个页读一遍、写一遍，总代价 $2B \cdot P(B, M)$ 次 I/O。
:::

::: proof
*正确性*。第 0 趟产出的每个归并段是有序的。对有序归并段做归并时，每一步输出的都是其所有输入中剩余的元组里最小的那个，因为每个归并段剩余的元组中最小者就在其段首；所以输出的归并段有序，且恰好包含其输入的全部元组。当只剩一个归并段时，它包含每个元组，且按序排列。

*趟数*。第 0 趟留下 $r_0 = \lceil B/M\rceil$ 个归并段。一趟归并把 $r$ 个归并段变成 $\lceil r/(M-1)\rceil$ 个，于是归纳可得 $k$ 趟归并后有 $\lceil r_0/(M-1)^k\rceil$ 个（对整数 $n$ 用到 $\lceil\lceil x\rceil/n\rceil = \lceil x/n\rceil$）。它恰为 $1$ 当且仅当 $(M-1)^k \ge r_0$，即 $k \ge \log_{M-1} r_0$；所以需要 $\lceil \log_{M-1} r_0 \rceil$ 趟归并，再加上第 0 趟。

*代价*。每一趟把 $B$ 个页各读一次、各写一次，所以每趟代价 $2B$。
:::

::: example 用 5 帧排 108 页 {#ex-sort}
用 $M = 5$ 帧排一个 $B = 108$ 页的文件。然后估算用 $M = 101$ 与 $M = 1001$ 排一个 $10^6$ 页文件的代价。
::: solution
第 0 趟每次读 $5$ 页：$\lceil 108/5\rceil = 22$ 个归并段（$21$ 个 $5$ 页段和一个 $3$ 页段）。每趟归并一次合并 $M - 1 = 4$ 个归并段：$22 \to 6 \to 2 \to 1$。共 $1 + 3 = 4$ 趟，与 $1 + \lceil \log_4 22 \rceil = 1 + 3$ 吻合，代价 $2 \cdot 108 \cdot 4 = 864$ 次 I/O。一个把 $108$ 页、每页 $4$ 个随机键排序并统计页传送次数的模拟与之一致：

```python
import heapq, random

def external_sort(pages, M):
    """Sort a list of pages (lists of keys) with M buffer frames; count page I/Os."""
    io = 0
    runs = []                                         # 第 0 趟：每个 M 页的有序归并段
    for i in range(0, len(pages), M):
        chunk = sorted(k for p in pages[i:i + M] for k in p)
        io += 2 * len(pages[i:i + M])                  # 每页一读一写
        runs.append(chunk)
    passes = 1
    while len(runs) > 1:                              # 一次归并 M - 1 个归并段
        runs = [list(heapq.merge(*runs[i:i + M - 1])) for i in range(0, len(runs), M - 1)]
        io += 2 * len(pages)
        passes += 1
    return runs[0], passes, io

random.seed(3)
keys = random.sample(range(10**6), 108 * 4)            # 108 页，每页 4 个键
pages = [keys[i:i + 4] for i in range(0, len(keys), 4)]
out, passes, io = external_sort(pages, M=5)
print(out == sorted(keys), passes, io)
```

```console
$ python3 extsort.py
True 4 864
```

对 $B = 10^6$：$M = 101$ 时，第 0 趟产生 $9901$ 个归并段，$100$ 路归并还需 $\lceil\log_{100} 9901\rceil = 2$ 趟，共 $3$ 趟，代价 $6 \times 10^6$ 次 I/O。$M = 1001$ 时，第 0 趟产生 $1000$ 个归并段，一趟 $1000$ 路归并直接合并：$2$ 趟，$4 \times 10^6$ 次 I/O。代价随内存只按对数下降。
:::
:::

两趟的情形值得一個名字：文件恰能用两趟（第 0 趟加一次归并）排好，当且仅当 $\lceil B/M \rceil \le M - 1$，这大约在 $B \le M^2$ 时成立。所以相当于文件*平方根*大小的内存就够了：$M = 1000$ 个 8 KiB 帧（8 MiB）能在两趟内排约 $10^6$ 页（8 GB）。有两个标准改进。**替换选择**在随机输入上产生平均 $2M$ 页的归并段（高德纳（Knuth）的分析），使归并段数减半。**双缓冲**为每个归并段备两个帧，处理当前页的同时预读下一页，用较小的归并路数换取 I/O 与计算的重叠。

## 连接算法

连接既是最昂贵也是最常使用的算子，算法有四族。我们只考虑等值连接 $R \bowtie_{R.a = S.b} S$；任意条件只有嵌套循环能处理。

### 嵌套循环

最简单的算法把**外层**关系 $R$ 的每个元组与**内层**关系 $S$ 的每个元组比较。按元组逐个做，$R$ 的每个元组都要把 $S$ 读一遍：$B(R) + T(R)\,B(S)$ 次 I/O。按页做，$R$ 的每页要把 $S$ 读一遍：$B(R) + B(R)\,B(S)$。真正的改进是利用内存。

::: algorithm 块嵌套循环连接 {#alg-bnl}
1. 反复直到 $R$ 读完：把 $R$ 的接下来 $M - 2$ 页读入内存（一个**块**），以块内元组的连接属性在内存中建哈希表。
2. 对每个这样的块，用一个帧逐页扫描 $S$；对每个元组 $s$ 探测哈希表，把每个连接结果经剩下的输出帧输出。
:::

::: proposition 块嵌套循环连接的代价 {#prop-bnl}
[[#alg-bnl]] 的代价是 $B(R) + \lceil B(R)/(M-2) \rceil \cdot B(S)$ 次 I/O。取较小的关系作外层最省；若 $B(R) \le M - 2$，代价为 $B(R) + B(S)$，即每个输入只读一遍。
:::

::: proof
$R$ 被读一遍，分成 $\lceil B(R)/(M-2)\rceil$ 个块；$S$ 每个块读一遍。输出正确，因为每对 $(r, s)$ 恰好被检查一次：含 $r$ 的块在内存中、$s$ 正被扫描的那一次。记 $b_R = B(R)$、$b_S = B(S)$、$m = M - 2$，以 $R$ 为外层的代价是 $b_R + \lceil b_R/m\rceil b_S \approx b_R + b_R b_S/m$，以 $S$ 为外层约 $b_S + b_S b_R/m$；乘积项相同，所以应取较小的关系作外层，能省下 $b_R - b_S$（向上取整的影响除外）。
:::

### 索引嵌套循环

若 $S$ 在连接属性 $b$ 上有索引，那么对 $R$ 的每个元组 $r$，可以直接查找 $S$ 中的匹配元组而不必扫描 $S$：代价是 $B(R) + T(R) \cdot c$，其中 $c$ 是一次索引查找加取回匹配项的代价——B+树约 $2$–$4$ 次 I/O，哈希索引 $1$–$2$ 次，非聚簇索引再加每个匹配元组一次 I/O。当 $R$ 很小时（例如经过一次高选择性选择之后）索引嵌套循环非常出色，$R$ 大时很差，因为它要做 $T(R)$ 次随机查找。

### 排序归并连接

::: algorithm 排序归并连接 {#alg-smj}
1. 把 $R$ 按 $a$ 排序、$S$ 按 $b$ 排序（[[#alg-external-sort]]）。
2. 同步扫描两个有序输入。当前 $R$ 键较小就在 $R$ 中前进；当前 $S$ 键较小就在 $S$ 中前进。若都等于 $v$，就把键为 $v$ 的 $R$ 元组与键为 $v$ 的 $S$ 元组的所有对输出（键 $v$ 的两个**组**），并越过这两个组继续前进。
:::

归并阶段的正确性在于：两个输入都有序时，连接值为 $v$ 的元组在每个输入中都连续；当归并在两边都到达 $v$ 时，它们全在这两个组里，而每个匹配对都有相同的值 $v$。若 $S$ 的每个组都能装进内存（在 $S$ 的码上连接时每组只有一个元组，这是通常情形），代价是 $B(R) + B(S)$；最坏情形——所有元组同键——归并退化为嵌套循环。若输入已经有序（例如经聚簇 B+树读出），排序阶段是免费的，而且输出按连接键有序，对后面的 `ORDER BY` 或 `GROUP BY` 是一份馈赠。当 $B(R)$ 与 $B(S)$ 都不超过约 $M^2$ 时，两次排序的最后一趟可以与连接直接合并，总共 $3\bigl(B(R) + B(S)\bigr)$：第 0 趟把两个输入都读一遍写一遍，一趟归并读两边的所有归并段，条件是归并段总数至多 $M - 1$。

### 哈希连接

::: algorithm Grace 哈希连接 {#alg-hash-join}
1. **分区。** 选一个取值 $M - 1$ 个的哈希函数 $h$。扫描 $S$，把每个元组写进分区 $S_i$，$i = h(s.b)$，每个分区一个输出帧。同样按 $h(r.a)$ 把 $R$ 分成 $R_1, \dots, R_{M-1}$。
2. **探测。** 对每个 $i$：把 $S_i$ 读入内存，用一个*不同的*哈希函数 $h'$ 在 $b$ 上建内存哈希表；然后扫描 $R_i$，以每个 $r.a$ 探测该表，输出匹配。
:::

::: theorem 哈希连接的正确性与代价 {#thm-hash-join}
[[#alg-hash-join]] 计算 $R \bowtie_{a = b} S$。若每个分区 $S_i$ 都能装进 $M - 2$ 帧（另留一帧读 $R_i$、一帧做输出），代价为 $3\bigl(B(R) + B(S)\bigr)$ 次 I/O。分区均匀时，只要 $B(S) \le (M - 1)(M - 2)$，约 $B(S) \le M^2$，这一条件就满足。
:::

::: proof
*正确性*。若 $r.a = s.b$，则 $h(r.a) = h(s.b)$，于是 $r \in R_i$、$s \in S_i$ 对同一个 $i$ 成立，探测第 $i$ 个分区时这一对就被找到。反过来，每个输出对都经过 $r.a = s.b$ 的检验。$R$ 的每个元组恰好在一个分区中、只被探测一次，所以没有哪一对会被输出两次。

*代价*。分区阶段把两个关系都读一遍并重写为分区：$2(B(R) + B(S))$。探测阶段把每个分区各读一遍：$B(R) + B(S)$。合计 $3(B(R) + B(S))$。每个 $S_i$ 约含 $B(S)/(M-1)$ 页；要装进 $M - 2$ 帧，需要 $B(S) \le (M-1)(M-2)$。

探测阶段需要第二个哈希函数 $h'$，因为 $S_i$ 的所有元组有相同的 $h$ 值，按 $h$ 哈希的表会把它们全塞进同一个桶。
:::

某个分区太大时——因为 $S$ 远大于 $M^2$，或因为哈希值分布倾斜——对它再递归地分区。**混合哈希连接**在分区阶段把 $S$ 的第一个分区留在内存里，于是 $R$ 中相应的元组立刻完成连接、不必写出；当 $S$ 整个装进内存时，哈希连接把每个输入恰好读一遍。只需要*较小的*那个输入（**构建**输入）能按分区装下；较大的（**探测**输入）可以任意大。

::: example 给贯穿示例算账 {#ex-join-costs}
对 $E \bowtie S$ 按 sid 连接，取 $B(E) = 1000$、$T(E) = 100\,000$、$B(S) = 500$、$T(S) = 40\,000$、$M = 52$，计算每个连接算法的代价。索引嵌套循环假定 Student.sid 上有聚簇 B+树，每次查找 $3$ 次 I/O。
::: solution
| 算法 | 公式 | I/O |
|---|---|---|
| 元组嵌套循环，$E$ 在外 | $1000 + 100\,000 \cdot 500$ | $50\,001\,000$ |
| 页嵌套循环，$S$ 在外 | $500 + 500 \cdot 1000$ | $500\,500$ |
| 块嵌套循环，$E$ 在外 | $1000 + \lceil 1000/50 \rceil \cdot 500$ | $11\,000$ |
| 块嵌套循环，$S$ 在外 | $500 + \lceil 500/50 \rceil \cdot 1000$ | $10\,500$ |
| 索引嵌套循环，$E$ 在外 | $1000 + 100\,000 \cdot 3$ | $301\,000$ |
| 排序归并，各自排序 | $2\cdot 1000\cdot 2 + 2\cdot 500 \cdot 2 + 1500$ | $7\,500$ |

| Grace 哈希连接 | $3 \cdot (1000 + 500)$ | $4\,500$ |

四个算法在内存列表上用 Python 都很容易写出来；在贯穿示例上比较它们、验证结果一致，是很好的检验：

```python
from collections import defaultdict

def nested_loop_join(R, S, r_key, s_key):
    return [r + s for r in R for s in S if r[r_key] == s[s_key]]

def hash_join(R, S, r_key, s_key):
    table = defaultdict(list)
    for s in S:                                  # 在较小的输入上构建
        table[s[s_key]].append(s)
    return [r + s for r in R for s in table.get(r[r_key], [])]   # 探测

def sort_merge_join(R, S, r_key, s_key):
    R = sorted(R, key=lambda t: t[r_key]); S = sorted(S, key=lambda t: t[s_key])
    out, i, j = [], 0, 0
    while i < len(R) and j < len(S):
        a, b = R[i][r_key], S[j][s_key]
        if a < b: i += 1
        elif a > b: j += 1
        else:                                    # 键相等：连接两个组
            j2 = j
            while j2 < len(S) and S[j2][s_key] == a: j2 += 1
            while i < len(R) and R[i][r_key] == a:
                out += [R[i] + s for s in S[j:j2]]
                i += 1
            j = j2
    return out
```

在十条选课记录与五名学生上，三个实现返回同样 $10$ 个元组（[[databases/relational-model#prop-join-size]]：sid 是外码，每条选课记录恰对应一个）。

::: quiz
哪些连接算法能求 $R \bowtie_{R.a < S.b} S$，即按不等式连接？
- [x] 块嵌套循环连接
- [ ] Grace 哈希连接
- [x] 适配区间的排序归并式算法（带状连接），或在 $S.b$ 上建 B+树的索引嵌套循环
- [ ] 都不行：不等式连接无法计算
::: solution
嵌套循环能求值任何条件。哈希要求相等：满足 $a < b$ 的元组落在互不相关的桶里。若 $S$ 按 $b$ 有序（或 $b$ 上有 B+树），对每个 $r$，匹配的 $s$ 构成连续区间 $b > r.a$，于是一次索引范围扫描或归并式的扫动就能找到它们。当然，不等式连接的输出可能接近 $T(R)\,T(S)$ 个元组，所以没有哪个算法在大输入上是便宜的。
:::
:::

::: warning "哈希连接总是最快"——并不尽然
每个算法都有自己的得胜领地。外层输入小而内层有索引时，索引嵌套循环最好：几次查找，不必读整个内层关系。输入已经有序、或输出反正必须有序时，排序归并取胜，且在倾斜下退化得更从容。较小的关系装得进内存时块嵌套循环最好，而任意条件下它是唯一选择。大型无序等值连接用哈希连接极妙，但它要为构建侧准备内存，而且某个连接值出现得极频繁时会难受（它的所有元组落进同一个分区，再怎么重新分区也分不开）。优化器依据对大小与选择率的估计做选择；估计错了，选择也就错了（[[databases/query-optimisation]]）。
:::

## 其他算子

**带去重的投影**（`SELECT DISTINCT`）与**分组**（`GROUP BY`）都需要把相同的值聚到一起处理，两者都可以排序或哈希——与连接相同的两招。

- *排序*：按投影属性或分组属性排序，重复元组与同组成员便相邻，一遍扫描即可去重或计算每组聚集值。重复在生成归并段与归并期间就已可消除，所以代价至多是排序的代价。
- *哈希*：像哈希连接那样按属性分区，然后每个分区用内存哈希表处理，每个不同取值或每个组维护一个条目。聚集时内存表只需存每组的累计值——一个计数、一个和、一个最小值——所以只要*组*数装得进内存，一遍扫描就够，无论输入多大。

`COUNT`、`SUM`、`MIN`、`MAX` 这类聚集可增量维护；`AVG` 以"一个和加一个计数"维护。集合运算化归到同样的模式：$R \cap S$ 与 $R - S$ 是在全部属性上的连接再加以测试，可由对两个输入排序或哈希实现。外连接通过记住哪些元组找到过伴侣来改造连接算法——对以保留侧为构建输入的哈希连接，就是每个哈希表条目加一个标志。

::: example 选择之后的索引嵌套循环 {#ex-inl}
把 [[#ex-join-costs]] 的查询改成 $\sigma_{\text{code} = \text{'CS202'}}(E) \bowtie S$，设 $200$ 条选课记录满足，经 Enrolled.code 上的聚簇索引找到，代价 $3 + 2$ 次 I/O（匹配元组占 $2$ 页）。比较索引嵌套循环与哈希连接。
::: solution
索引嵌套循环：$5$ 次 I/O 找出 $200$ 条选课记录，然后在 Student 的索引里做 $200$ 次查找、每次 $3$ 次 I/O：$5 + 600 = 605$ 次 I/O。选择以流水线方式接入连接，$200$ 个元组从不落盘。

哈希连接：构建侧应取选出的选课记录，它们装得进内存（$2$ 页），于是哈希连接把它们读一遍，然后扫描整个 Student，$500$ 页：$5 + 500 = 505$ 次 I/O。

两者都比不加选择的连接的 $4500$ 低一个数量级——先做选择是最重要的优化，没有之一。这里两者接近；若匹配的记录只有 $20$ 条，索引嵌套循环（$5 + 60$）明显取胜；若 $2000$ 条（$5 + 6000$ 对约 $520$），哈希连接取胜。转折点取决于匹配数，而这正是优化器必须估计的量。
:::
:::

::: history
迭代器模型由格茨·格拉费（Goetz Graefe）为 Volcano 系统提出（"Volcano — an extensible and parallel query evaluation system"，1994，此前有 1990 年论文），他的综述《大型数据库的查询求值技术》（"Query evaluation techniques for large databases"，*ACM Computing Surveys*，1993）至今是标准参考。System R（20 世纪 70 年代）使用嵌套循环与排序归并连接，见 Blasgen 与 Eswaran（1977）的记述。哈希连接出自日本的 Grace 数据库机项目（Kitsuregawa、Tanaka 与 Moto-oka，1983）以及 DeWitt 等人的《主存数据库系统的实现技术》（"Implementation techniques for main memory database systems"，1984）——后者引入了混合哈希连接；夏皮罗（Shapiro）1986 年的分析对两者作了比较。外部归并排序比数据库更古老：高德纳（Knuth）的《计算机程序设计艺术》第 3 卷（*The Art of Computer Programming*, volume 3，1973）分析的就是 20 世纪 50 年代为磁带驱动器发明的替换选择与多阶段归并。向量化执行模型由 MonetDB/X100 提出（Boncz、Zukowski 与 Nes，2005）。
:::

## 后续内容

本章的代价公式是优化器（[[databases/query-optimisation]]）的原料，而优化器还必须估计中间结果的大小 $T$ 与 $B$——那些公式的输入——并选择连接次序。并行与分布式数据库把数据按机器分区，用的恰恰是 [[#alg-hash-join]] 的哈希分区；MapReduce 风格的系统则是放大规模的排序归并和哈希算法（[[parallel-computing]]、[[distributed-systems]]）。归并排序的分治结构与归并的分析来自 [[algorithms/divide-and-conquer]]，哈希来自 [[data-structures/hash-tables]]。

::: summary
- 计划是物理算子构成的树，按**迭代器模型**执行：`open`、`next`、`close`；流水线算子流式传递，阻塞算子（排序、哈希构建）先消费完输入。
- **选择**用文件扫描、二分查找或索引；合取可以求 rid 集的交，析取要求每个析取项都有索引。
- **外部归并排序**产生 $\lceil B/M\rceil$ 个归并段、一次归并 $M - 1$ 个：$2B\,(1 + \lceil\log_{M-1}\lceil B/M\rceil\rceil)$ 次 I/O；$B \lesssim M^2$ 时两趟就够。
- **块嵌套循环**代价 $B(R) + \lceil B(R)/(M-2)\rceil B(S)$，较小的关系在外；**索引嵌套循环**代价 $B(R) + T(R)\cdot c$，外层小时最快。
- **排序归并**与**Grace 哈希连接**在输入至多约 $M^2$ 页时代价约 $3(B(R)+B(S))$（哈希连接只要求构建侧如此）；哈希要求等值条件，排序归并吃得下有序输入、吐得出有序输出。
- 去重、分组与集合运算使用同样的排序或哈希技术；哈希聚集只为组需要内存。
:::

## 习题

::: exercise 排序代价 {level=1 check="80000"}
用 $M = 11$ 帧对外部归并排序一个 $10\,000$ 页的文件需要几趟、多少次 I/O？（输入 I/O 数。）
::: solution
第 0 趟：$\lceil 10\,000/11\rceil = 910$ 个归并段。一次归并 $10$ 个：$910 \to 91 \to 10 \to 1$，三趟归并。共 $4$ 趟，$2 \cdot 10\,000 \cdot 4 = 80\,000$ 次 I/O；[[#eq-sort-passes]] 也给出 $1 + \lceil \log_{10} 910 \rceil = 1 + 3 = 4$。
:::
:::

::: exercise 块嵌套循环 {level=1 check="6300"}
$R$ 有 $2000$ 页、$S$ 有 $300$ 页，$M = 102$。取较好的外层关系时块嵌套循环连接的代价是多少？（输入 I/O 数。）
::: solution
$S$ 在外：$300 + \lceil 300/100\rceil \cdot 2000 = 300 + 6000 = 6300$。$R$ 在外：$2000 + \lceil 2000/100 \rceil \cdot 300 = 2000 + 6000 = 8000$。较小的关系在外更省，省 $B(R) - B(S) = 1700$ 次 I/O，与 [[#prop-bnl]] 的预言一致。
:::
:::

::: exercise 流水线 {level=1}
在计划 $\pi_{\text{name}}(\sigma_{\text{grade} = \text{'A'}}(E) \bowtie_{\text{hash}} S)$ 中，$S$ 是构建输入。哪些算子是流水线的，哪些是阻塞的？若换成 $E$ 作构建输入，情况有何变化？
::: solution
扫描、选择与投影是流水线的。哈希连接对构建输入 $S$ 是阻塞的（必须读完整个 $S$ 才能产出输出），对探测输入是流水线的：每条入选的选课记录一到手就被连接、投影。若让 $E$（选择之后）作构建输入，连接就会先消费完全部入选的选课记录，再流式扫 $S$；选择留下的元组很少时这样更好，因为哈希表就小了——如 [[#ex-inl]]。
:::
:::

::: exercise 两趟排序所需内存 {level=2 check="11586"}
把 1 TiB 的文件（$2^{27}$ 页）在两趟内排好，最小的 8 KiB 帧数 $M$ 是多少？（输入 $M$。）
::: solution
两趟需要 $\lceil B/M\rceil \le M - 1$。$B = 2^{27} = 134\,217\,728$：$M = 11\,585$ 时 $\lceil B/M\rceil = 11\,586 > 11\,584$；$M = 11\,586$ 时 $\lceil B/M \rceil = 11\,585 \le 11\,585$。所以 $M = 11\,586$ 帧，约 $90.5$ MiB——不到文件的十分之一的一个百分点，平方根法则的生动体现。
:::
:::

::: exercise 哈希连接的内存 {level=2 check="102"}
Grace 哈希连接的构建输入有 $10\,000$ 页。假设分区完全均匀，使每个分区都能装进 $M - 2$ 帧的最小 $M$ 是多少？（输入 $M$。）
::: solution
需要 $\lceil 10\,000/(M-1)\rceil \le M - 2$。$M = 101$：$\lceil 10\,000/100\rceil = 100 > 99$。$M = 102$：$\lceil 10\,000/101 \rceil = 100 \le 100$。故 $M = 102$。实践中会留出安全余量（为哈希表开销与倾斜留 $1.2$ 左右的"宽松因子"）。
:::

::: exercise 哈希去重 {level=2}
描述如何在 $B$ 页的关系上用哈希计算 `SELECT DISTINCT dept FROM Course`，并给出不同取值装得进内存与装不进内存时的代价。
::: solution
若不同院系的集合装得进内存（多半如此——院系很少），扫描关系一遍，把每个 dept 插入内存哈希集合，输出该集合：$B$ 次 I/O。一般地，按 $h(\text{dept})$ 把关系分成 $M - 1$ 个分区（$2B$ 次 I/O），然后读入每个分区，用第二个哈希函数的内存哈希表去重（$B$ 次 I/O），共 $3B$，条件是每分区内的不同取值装得进内存。同一值的重复拷贝必落进同一分区，所以各分区可独立处理。
:::
:::

::: exercise 选择连接算法 {level=2}
对贯穿示例（$B(E) = 1000$、$B(S) = 500$），$S$ 在外的块嵌套循环在帧数 $M$ 达到多少时赶上哈希连接的 $4500$ 次 I/O？在 $M = 502$ 时优化器为什么仍可能偏爱块嵌套循环？
::: solution
$S$ 在外的块嵌套循环代价 $500 + \lceil 500/(M-2)\rceil \cdot 1000$。当 $\lceil 500/(M-2)\rceil \le 4$、即 $M - 2 \ge 125$、$M \ge 127$ 时它不超过 $4500$：此时代价 $500 + 4000 = 4500$。$M = 502$ 时整个 $S$ 装得下（$\lceil 500/500 \rceil = 1$）：$1500$ 次 I/O，是 Grace 哈希连接的三分之一，与把整个 $S$ 留在内存的混合哈希连接持平。内存多到这份上，两者都是每个输入读一遍，决胜负的只剩 CPU 代价。
:::
:::

::: exercise 带重复元的排序归并 {level=3}
证明 [[#alg-smj]] 的归并阶段输出的恰好是连接，并证明：若对每个值 $v$，$b = v$ 的 $S$ 元组能装进 $M - 2$ 帧，则其 I/O 代价是 $B(R) + B(S)$。没有这一假设时最坏代价是什么？
::: solution
*正确性*。不变式：当归并处于 $R$ 的位置 $i$ 与 $S$ 的位置 $j$ 时，凡涉及 $i$ 之前或 $j$ 之前元组的连接对都已输出，此外没有输出别的对。初始为真。若 $R[i].a < S[j].b$，$j$ 及其后的任何元组都匹配不了 $R[i]$（它们 $\ge S[j].b$），而 $j$ 之前的已经处理完毕，所以让 $i$ 前进保持不变式；$>$ 的情形对称。若两边都等于 $v$，$v$ 在 $R$ 与 $S$ 中的组是连续的（有索性），两组之间的所有对都被输出，而这两个组中元组的任何别的伴侣都必须具有键 $v$、因而就在组里；越过两组继续前进保持不变式。当一个输入耗尽时，另一输入剩下的元组都不再有伴侣。

*代价*。若每个 $S$ 组都能装进 $M - 2$ 帧，就把它读入内存一次，让 $R$ 组经一个帧流过去，再留一帧做输出：$R$ 与 $S$ 的每页各读一次，$B(R) + B(S)$。

*最坏情形*。若两个关系的所有元组同键，输出就是 $R \times S$；组装不下时，$S$ 的组必须为 $R$ 组的每个块重读一遍，这就是块嵌套循环：$B(R) + \lceil B(R)/(M-2)\rceil B(S)$。
:::
:::

::: exercise 带 I/O 计数的块嵌套循环实现 {level=3}
在以页列表给出的关系上实现块嵌套循环连接，统计页读次数，并在 $B(R) = 7$、$B(S) = 5$、$M = 4$ 下用两种外层关系的选择验证 [[#prop-bnl]]。
::: solution
```python
from collections import defaultdict
from math import ceil

def bnl(Rpages, Spages, rk, sk, M):
    reads, out = 0, []
    block_size = M - 2                         # 一帧给 S，一帧给输出
    for i in range(0, len(Rpages), block_size):
        block = Rpages[i:i + block_size]
        reads += len(block)
        table = defaultdict(list)
        for page in block:
            for r in page:
                table[r[rk]].append(r)
        for page in Spages:                    # 每个块对 S 扫一遍
            reads += 1
            for s in page:
                out += [r + s for r in table.get(s[sk], [])]
    return out, reads

R = [[(p * 3 + k, "r") for k in range(3)] for p in range(7)]           # 键 0..20
S = [[((p * 3 + k) * 2, "s") for k in range(3)] for p in range(5)]     # 偶数键 0..28
out1, n1 = bnl(R, S, 0, 0, 4)
out2, n2 = bnl(S, R, 0, 0, 4)
print(len(out1), n1, 7 + ceil(7 / 2) * 5, len(out2), n2, 5 + ceil(5 / 2) * 7)
```

两种顺序都找到 $11$ 个匹配（偶数键 $0$–$20$），页数与公式一致：$R$ 在外 $7 + 4 \cdot 5 = 27$，$S$ 在外 $5 + 3 \cdot 7 = 26$。块很小时取整效应不能忽略：较小的关系在外这里只省一次页读，而不是 $B(R) - B(S) = 2$。
