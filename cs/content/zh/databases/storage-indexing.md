一张有一亿条传感器读数的表要占好几个吉字节。靠读整张表来找某个传感器的读数，意味着把这些吉字节全部从外存搬进内存；靠索引来找则只需读寥寥几页。两者之差——几秒或几分钟对上不到一毫秒——正是本章的主题。SQL（[[databases/sql]]）对行存在何处、如何找到它们不作任何约定，关系模型也坚持如此（[[databases/relational-model]]）。然而在底层，每个 DBMS 都有一个**存储管理器**，把记录编排在页里、页编排在文件里，并把最有用的页留在内存中；还有**索引**，把查找变成沿一棵树的几步下行，或一次哈希探测。

我们先建立每一本数据库教材都在使用的代价模型——数页的传送，而不是数指令——然后从记录与页出发搭建文件与缓冲池，接着研究索引的两大家族：几乎每个关系系统的默认索引 B+树，以及哈希索引。树结构本身在 [[data-structures/balanced-trees]] 中已经建立，哈希则在 [[data-structures/hash-tables]]；这里的问题是当每个结点都是一个磁盘页时，它们表现出怎样的行为。实验使用 **SQLite 3.46.1**。

## 存储层次与代价模型

数据存放在一个设备层次结构上。按大致的量级（以 2026 年为准，不同产品之间差别很大）：

| 设备 | 典型访问时延 | 顺序带宽 | 掉电后是否保留 |
|---|---|---|---|
| CPU 高速缓存 | 1–10 ns | — | 否 |
| 主存（DRAM） | 约 100 ns | 数十 GB/s | 否 |
| NVMe 闪存 SSD | 每次 4 KiB 随机读约 10–100 µs | 数 GB/s | 是 |
| 磁盘（HDD） | 每次随机读约 5–10 ms（寻道 + 旋转） | 约 100–250 MB/s | 是 |

两个事实决定一切。第一，持久存储比内存慢几个数量级，所以回答一个未被缓存数据的查询，时间花在**I/O** 上。第二，存储按固定大小的**块**读写，读一个字节与读整个块代价相同；而在磁盘上，读相邻的块远比读零散的块便宜。因此 DBMS 以**页**为单位管理数据——通常是 4–16 KiB 的块（SQLite 默认为 4096 字节，PostgreSQL 为 8 KiB）——标准代价模型数的就是页。

::: definition I/O 代价模型 {#def-io-model}
一个操作的**代价**是从持久存储读或写的页数。内存中的计算不计费，每次页访问代价相同，把最终输出送给用户的代价不计。参数：一个关系有 $N$ 条记录，存放在 $B$ 页中，于是每页 $N/B$ 条记录。
:::

这个模型忽略 CPU 代价，也不区分随机 I/O 与顺序 I/O——两者都是简化，[[databases/query-processing]] 将在要紧处加以细化。尽管如此，它的预测能力出奇地好，因为算法所能控制的正是触及的页数。

## 记录、页与文件

**记录**是元组的存储形态。若每个字段都是定长的，记录就是各字段首尾相接，第 $i$ 个字段按固定偏移找到。变长字段（字符串，以及以"缺席"方式存储的空值）需要一个小小的头部：记录开头放一个字段偏移数组，于是任何字段都能以常数量时间找到，空值只在空值位图里花一个比特。

::: definition 槽页 {#def-slotted}
**槽页**按如下方式在一个页中存放变长记录。页首的头部记录槽位个数，以及每个**槽位**对应一条记录的偏移与长度；记录从页尾向前存放，空闲空间位于槽数组与记录之间。一条记录由它的**记录标识**（rid）标识，即（页号，槽位号）二元组。
:::

经槽数组的这层间接正是设计的关键。记录可以在页内搬动——删除之后压缩空闲空间——而 rid 不变，变的只是槽位里的偏移。被删除记录的槽位标记为空并可复用；长到过不了本页的记录可以搬到别的页，在原槽位留下一个转发地址。索引存放 rid，所以 rid 的稳定性要紧。

一个**文件**是存放一个关系的记录的一页页集合。最简单的组织方式是**堆文件**：记录放进任何有空位的地方，不讲次序，DBMS 另外维护一个有空闲空间的页的目录。**顺序文件**则按某个属性的次序存放记录。每种组织各有偏爱：

| 操作 | 堆文件 | 顺序文件（按检索键有序） |
|---|---|---|
| 扫描全部记录 | $B$ | $B$ |
| 按键值作等值查找 | 平均 $B/2$ | $\lceil\log_2 B\rceil$（对页作二分查找） |
| 范围查找 | $B$ | $\lceil\log_2 B\rceil$ + 匹配项所在的页 |
| 插入 | $2$（读并写一个有空位的页） | $\approx \log_2 B + B$（找到位置，后移其后的记录） |
| 删除（已给定记录） | $2$ | $\approx \log_2 B + B$（后移以填补空档） |

对一个既大、又不断变化、还必须回答高选择性查询的表，两者都不可接受：堆文件为一次查找读遍全部，顺序文件为一次插入重写半个文件。索引兼取两者之长。

## 缓冲管理器

页在内存中处理，内存中划出一个称为**缓冲池**的区域，分成一次装一页的**帧**。**缓冲管理器**给系统的其余部分制造一种幻觉：每个页都在内存里。

::: algorithm 缓冲管理器：申请一个页 {#alg-buffer}
为响应页 $p$ 的请求：
1. 若 $p$ 已在某个帧中，给该帧的**钉住计数**加一并返回它。
2. 否则按**替换策略**选一个钉住计数为 $0$ 的帧；若它的页是**脏页**（读入后被修改过），先把它写回存储。
3. 把 $p$ 读入该帧，钉住计数置 $1$、清脏位；返回它。

申请者在不再需要该页时**解除钉住**（钉住计数减一），并说明是否修改过它（置脏位）。
:::

被钉住的页不能被换出——有某个算子正在读它。替换策略决定换出哪个未钉住的页。**LRU**（least recently used，最近最少使用）换出最久以前解除钉住的页；**时钟**（clock）算法用每帧一个引用位、一只旋转的指针廉价地近似 LRU：指针扫过之处清除引用位，换出第一个引用位本来就是 $0$ 的帧（同样的算法在 [[operating-systems]] 的虚拟内存部分还会出现）。对随机访问，LRU 是不错的默认选择，但它有一个出了名的失效情形。

::: proposition 顺序泛滥 {#prop-flooding}
若一个 $P$ 页的文件在一个 $M < P$ 帧的缓冲池中被从头到尾反复扫描，且别无其他活动，则在 LRU 之下*每次*页请求都未命中。
:::

::: proof
我们证明当页 $i$ 被请求时它不在池中。扫描期间，最近使用过的 $M$ 个页恰好就是紧接着请求的那 $M$ 个页。页 $i$ 上次被请求恰在 $P$ 次请求之前（上一轮扫描），而 $P > M$，所以此后至少又有 $M$ 个互不相同的页被请求——正是两次请求 $i$ 之间的 $P - 1 \ge M$ 个页。LRU 恰好保留最近使用的 $M$ 个页，故 $i$ 早已被换出。第一轮扫描本来每个页都未命中。
:::

时钟算法也会遭遇同样的事。用 $M = 4$ 帧、对页 $1$ 到 $5$ 扫描三遍做一个简单模拟：

```python
from collections import OrderedDict

def lru(refs, frames):
    pool, misses = OrderedDict(), 0
    for p in refs:
        if p in pool:
            pool.move_to_end(p)               # 最近使用的放在末尾
        else:
            misses += 1
            if len(pool) == frames:
                pool.popitem(last=False)      # 淘汰最近最少使用的
            pool[p] = True
    return misses

def mru(refs, frames):
    pool, misses, last = set(), 0, None
    for p in refs:
        if p not in pool:
            misses += 1
            if len(pool) == frames:
                pool.remove(last)             # 淘汰最近最多使用的
            pool.add(p)
        last = p
    return misses

scan = list(range(1, 6)) * 3                  # 读页 1..5，共三遍
print(lru(scan, 4), mru(scan, 4))
```

```console
$ python3 buf.py
15 7
```

LRU 对全部 $15$ 次请求都未命中；**MRU**（淘汰最近最多使用的页）只错过第一轮扫描的 $5$ 次，此后每轮各错过一页。真正的缓冲管理器会识别大规模顺序扫描，划出一小圈帧专供其使用（PostgreSQL 对大表的扫描就这么做），以免一个大查询把人人都在用的页冲掉。因为 DBMS 了解自身的访问模式——嵌套循环连接会重扫内关系，索引根页会被不停地读——它能比操作系统的文件缓存更好地管理自己的缓冲区，这是数据库系统常常绕过文件缓存的原因之一。缓冲管理器还强制执行崩溃恢复关于脏页*何时*可以写回存储的规则（[[databases/recovery]]）。

## 索引

::: definition 索引 {#def-index}
在一个**检索键**（一个或多个属性，不一定是关系的码）上的**索引**，是一种数据结构：给定检索键的一个值或一段取值范围，它能迅速找到匹配的记录。它的**数据条目**有三种形态之一：(1) 记录本身；(2) （键值，rid）二元组；(3) （键值，rid 列表）二元组。若数据记录在文件中的次序与数据条目的次序相同或接近，称该索引是**聚簇的**；否则称为**非聚簇的**。
:::

一个关系至多只有一个聚簇索引——记录只能按一种次序存放——但可以有任意多个非聚簇索引。类型 (1) 的索引按构造就是聚簇的：索引*就是*文件本身。SQLite 的每张普通表都按这种方式存放：一棵按其整型 `rowid` 键控的 B+树（`INTEGER PRIMARY KEY` 就是 `rowid` 的别名），而每个二级索引都是另一棵由 (键值, rowid) 条目构成的 B树——类型 (2)。PostgreSQL 把表存放在堆文件中，它的所有索引都是类型 (2)，指向元组标识；它的 `CLUSTER` 命令沿某个索引把表一次性排序，却不维持这一次序。对范围查询而言，这一区别极为要紧，[[#ex-unclustered]] 可见一斑。

### B+树

::: definition B+树 {#def-bplus}
具有**扇出** $F$ 与**叶容量** $L$ 的 **B+树**是一棵有根树，其中每个结点占一个页，并且：
1. 所有叶子在同一深度 $h$，称为**高度**；叶子按序存放 $\lceil L/2 \rceil$ 到 $L$ 个数据条目（根若本身就是叶子，可以少一些），并与相邻叶子相连，构成一个有序表；
2. 每个内部结点存放 $k$ 个键 $k_1 < \dots < k_k$ 和 $k + 1$ 个孩子指针 $c_0, \dots, c_k$，$c_i$ 的子树中的每个键都至少为 $k_i$ 且小于 $k_{i+1}$；除根以外的内部结点有 $\lceil F/2\rceil$ 到 $F$ 个孩子，根若不是叶子则至少有 $2$ 个孩子。
:::

内部结点只负责为查找指路；全部数据条目都在叶子里。与 [[data-structures/balanced-trees#def-btree]] 那种内部结点也存条目的 B树相比，这有两点好处：内部结点只放键与指针，所以 $F$ 很大；范围扫描沿着叶链向前走，不必折回树上。

查找键 $k$ 时从根开始；在每个内部结点，跟随满足 $k_i \le k < k_{i+1}$ 的指针 $c_i$（页内二分查找，在我们的代价模型中免费）；到叶子里找 $k$。**范围查找** $a \le k \le b$ 先找到 $a$ 所在的叶子，再沿叶链前进，直到某个键超过 $b$。

::: theorem B+树的高度与查找代价 {#thm-bplus-height}
一棵高度 $h \ge 1$、存放 $N$ 个数据条目的 B+树满足

$$
L\,F^{h} \;\ge\; N \;\ge\; 2\,\lceil F/2 \rceil^{h-1} \lceil L/2 \rceil,
\qquad\text{于是}\qquad
\log_F \frac{N}{L} \;\le\; h \;\le\; 1 + \log_{\lceil F/2\rceil} \frac{N}{2\lceil L/2\rceil}.
$$ {#eq-bplus-height}

一次等值查找读 $h + 1$ 页；一次返回 $\ell$ 个叶子中条目的范围查找读 $h + \ell$ 页。
:::

::: proof
*$N$ 的上界*。每个内部结点至多有 $F$ 个孩子，所以深度 $h$ 上至多有 $F^h$ 个结点，每个都是至多含 $L$ 个条目的叶子。

*$N$ 的下界*。根至少有 $2$ 个孩子，其余每个内部结点至少 $\lceil F/2 \rceil$ 个；于是深度 $d \ge 1$ 上至少有 $2\lceil F/2\rceil^{d-1}$ 个结点，特别地叶子至少有 $2\lceil F/2 \rceil^{h-1}$ 个，每个叶子至少 $\lceil L/2\rceil$ 个条目（$h \ge 1$ 时没有叶子是根）。

对两个界取对数即得 $h$ 的界。一次查找每层读一个结点，共 $h + 1$ 页；范围查找先读 $h$ 个内部结点，再读连续的 $\ell$ 个叶子。
:::

对数的底数正是 B+树实用性的来源：$F$ 达到几百时，$h$ 小得惊人。

::: example B+树的算术 {#ex-bplus-arith}
一张 $N = 10^8$ 行的表在 64 位整型键上建类型 (2) 的索引，页大小 8 KiB。一个数据条目或内部条目是一个键（8 字节）加一个指针（8 字节），稳态下各页约三分之二满。估算高度、页数与一次查找的代价。
::: solution
一页至多放 $\lfloor 8192/16 \rfloor = 512$ 个条目（忽略小小的页头），故 $F \approx L \approx 512$；按三分之二占用率，每个结点约 $341$ 个条目。

- 叶子：$10^8 / 341 \approx 293\,256$ 页，约 $2.2$ GiB。
- 上一层：$293\,256 / 341 \approx 860$ 页。
- 再上一层：$860/341 \approx 3$ 页；然后是根一页。

所以树有 $4$ 层，高度 $h = 3$，一次查找读 $4$ 个索引页加记录所在 $1$ 页：至多 $5$ 次 I/O。若结点全满，树只有 $3$ 层（$512^3 \approx 1.3\times10^8 \ge 10^8$），与 [[#eq-bplus-height]] 的下界吻合：$\log_{512}(10^8/512) \approx 1.95$，故 $h \ge 2$。

实际上顶层各级总是被缓存的：根加叶子上方的 $860$ 页只占约 $7$ MiB，所以一次查找实际约 $2$ 次 I/O——一个叶子页，一个数据页。对比：在约 $10^8/100 = 10^6$ 个数据页的顺序文件（每页 $100$ 行）上作二分查找：$\lceil\log_2 10^6\rceil = 20$ 次 I/O。
:::
:::

sliders: F=4:4:512; L=4:4:512

caption: B+树高度随条目数 $N$ 的变化，上下界来自 [[#eq-bplus-height]]，并与 $\log_2 N$（平衡二叉树的高度）比较。把 $F$ 与 $L$ 拖到几百——4–16 KiB 页的典型值：一亿个条目时高度仍停留在 $2$–$4$，而二叉树需要 $27$ 层——每次查找 $27$ 次随机 I/O。结点很小时（$F = L = 4$），B+树并不比二叉树好。
:::

同样的算术在 SQLite 中也成立。表 `Reading(id INTEGER PRIMARY KEY, sensor INTEGER, t INTEGER, value REAL)` 填入 $10^6$ 条随机读数，并在 `sensor` 上建了索引；SQLite 的 `dbstat` 虚拟表会报告每棵树每层的页数：

```sql
SELECT name, length(path) - length(replace(path, '/', '')) AS level,
       COUNT(*) AS pages, SUM(ncell) AS cells
FROM dbstat WHERE name LIKE 'reading%' GROUP BY name, level ORDER BY name, level;
```

4 KiB 页、上百万行，两棵树都是三层。表树把全部 $10^6$ 行放在它的 $5769$ 个叶子里（每叶约 $173$ 行），内部结点的扇出约 $384$——所以按 `id` 查找读 $3$ 页。这棵索引是 B树而不是 B+树：$10^6 - 997\,353 = 2647$ 个条目住在内部层，每个分界键一个。

### 插入与删除

插入通过分裂满结点来保持树平衡，与 B树相同，只在叶子上有一处不同。

::: algorithm B+树的插入 {#alg-bplus-insert}
插入条目 $(k, v)$：
1. 查找 $k$ 应在的叶子 $\lambda$，记下从根下来的路径。
2. 若 $\lambda$ 的条目不足 $L$ 个，把 $(k, v)$ 按序插入；完毕。
3. 否则**分裂** $\lambda$：新建叶子 $\lambda'$，把 $L + 1$ 个条目前面 $\lceil (L+1)/2 \rceil$ 个留在 $\lambda$，其余移到 $\lambda'$，把 $\lambda'$ 接到 $\lambda$ 之后，并把 $\lambda'$ 中最小键的**副本**连同指向 $\lambda'$ 的指针插进父结点。
4. 若父结点此时有 $F + 1$ 个孩子，分裂它：保留前面 $\lceil (F+1)/2 \rceil$ 个孩子，其余移入新结点，并把分隔两者的中间键**移动**（不是复制）上去交给祖父。沿路径向上重复。
5. 若根被分裂，新建一个有两个孩子的根；高度加一。
:::

在叶子一层，分界键被*复制*上去，因为每个键都必须留在叶子里；在内部结点中它被*移动*上去，与 B树一样。代价是 $h + 1$ 次读，最坏情形下约 $2(h+1) + 1$ 次写；分裂很少发生——对某个叶子每 $\lceil L/2\rceil$ 次插入至多引发一次叶子分裂——所以摊还代价接近 $h + 2$ 次 I/O。

::: example 分裂一个叶子 {#ex-split}
一棵 $L = F = 3$ 的 B+树，根含键 $20$，有两个叶子 $[5, 10, 15]$ 与 $[20, 25]$。依次插入 $12$、$30$、$35$。
::: solution
- 插入 $12$：它应进左叶子，而左叶子已满。四个条目 $5, 10, 12, 15$ 分裂为 $[5, 10]$ 与 $[12, 15]$，键 $12$ 被*复制*进根，根变为 $[12 \mid 20]$，有三个孩子 $[5, 10]$、$[12, 15]$、$[20, 25]$。
- 插入 $30$：右叶子变为 $[20, 25, 30]$。
- 插入 $35$：右叶子溢出；$20, 25, 30, 35$ 分裂为 $[20, 25]$ 与 $[30, 35]$，$30$ 被复制上去。根将含键 $12, 20, 30$ 并有四个孩子，超过 $F = 3$，于是它也分裂：孩子分成 $2 + 2$，中间键 $20$ *移动*上去成为新的根，旧根变成两个结点 $[12]$ 与 $[30]$。

最终的树根为 $[20]$，内部结点 $[12]$ 与 $[30]$，叶子链 $[5,10] \to [12,15] \to [20,25] \to [30,35]$。高度从 $1$ 长到 $2$，长的是根，所有叶子仍在同一深度。注意 $20$ 同时出现在根和叶子里，而 $12$ 与 $30$ 同时出现在内部结点和叶子里：B+树内部的键只是用于指路的副本。
:::
:::

删除把条目从所在叶子中取走；若叶子的条目数跌破 $\lceil L/2 \rceil$，就向兄弟借一个条目（随之更新父结点中的分界键），或与兄弟合并（从父结点删去一个分界键，父结点可能继而欠丰满）。许多系统放宽这一要求，允许不满的页存在，直到页变空才回收，因为删除比插入少见，而表往往还会再长回去。

**批量装载**为已有数据建索引，比反复插入快得多：先把条目排序，从左到右填满叶子（达到所需的占用率），再由下一层的头键逐层建立每个内部层。代价就是排序的代价（[[databases/query-processing]]）加上每页一次写，完全不发生分裂。多数系统对满表执行 `CREATE INDEX` 用的就是这种方法。

### 用好索引

::: example 索引何时不如扫描 {#ex-unclustered}
一个关系有 $N = 10^6$ 条记录，存于 $B = 10^4$ 页（每页 $100$ 条）。一个范围查询选取比例为 $s$ 的记录。比较全表扫描、聚簇 B+树和非聚簇的类型 (2) B+树，三者高度都取 $h = 2$，索引的叶子页忽略不计。
::: solution
- **全表扫描**：$B = 10\,000$ 次 I/O，与 $s$ 无关。
- **聚簇索引**：匹配的记录连续，约占 $sB$ 页：代价 $\approx h + 1 + 10\,000\,s$。
- **非聚簇索引**：每个匹配的 rid 可能指向不同的页，最坏情形下每个要花一次 I/O：$\approx h + 1 + 10^6 s$。

非聚簇索引只有在 $10^6 s < 10^4$、即 $s < 1\%$ 时才胜过扫描。$s = 10\%$ 时它要花约 $100\,000$ 次 I/O——是扫描的十倍——而聚簇索引约 $1\,000$ 次。一个常用的改进是先收集 rid，按页排序后每页只取一次，把代价压到 $\min(sN, B)$ 页以内（PostgreSQL 称之为位图堆扫描）；优化器依据对 $s$ 的估计在这些计划之间做选择（[[databases/query-optimisation]]）。
:::
:::

::: widget plot
f: 10000 + 0*x; 3 + 100*x; 3 + 10000*x
x: 0, 5
y: 0, 30000
labels: \text{全表扫描}; \text{聚簇索引}; \text{非聚簇索引}
points: 1,10003
caption: [[#ex-unclustered]] 的关系（$10^6$ 条记录、$10^4$ 页）上，范围选择的 I/O 代价随选择率（百分比）的变化。非聚簇索引在 $1\%$ 处与全表扫描相交（那个点），此后远差于扫描，因为它为每条匹配记录付一次随机读页；聚簇索引则始终远低于两者。这就是优化器有时无视你刚建的索引的原因。
:::

只用到索引中已存列的查询可以只靠索引回答，完全不碰表：称索引对该查询是**覆盖的**。SQLite 的 `EXPLAIN QUERY PLAN` 在 Reading 表上展示了这些决策：

```console
$ sqlite3 big.db "EXPLAIN QUERY PLAN SELECT * FROM Reading WHERE sensor = 42;"
QUERY PLAN
`--SCAN Reading
$ sqlite3 big.db "CREATE INDEX reading_sensor ON Reading(sensor);"
$ sqlite3 big.db "EXPLAIN QUERY PLAN SELECT * FROM Reading WHERE sensor = 42;"
QUERY PLAN
`--SEARCH Reading USING INDEX reading_sensor (sensor=?)
$ sqlite3 big.db "EXPLAIN QUERY PLAN SELECT COUNT(*) FROM Reading WHERE sensor BETWEEN 10 AND 19;"
QUERY PLAN
`--SEARCH Reading USING COVERING INDEX reading_sensor (sensor>? AND sensor<?)
$ sqlite3 big.db "EXPLAIN QUERY PLAN SELECT * FROM Reading WHERE id = 500000;"
QUERY PLAN
`--SEARCH Reading USING INTEGER PRIMARY KEY (rowid=?)
```

没有索引时，唯一的计划就是扫描。有了索引，等值查询先查索引，再按 rowid 逐条取出匹配的行；计数只需要 sensor 的值，而它在索引里，于是表根本不被读取；按 `id` 的查找则下降表自己的 B+树。$(a, b)$ 上的**复合索引**先按 $a$、再按 $b$ 排序条目：它服务只涉及 $a$、或同时涉及 $a$ 与 $b$ 的条件，却不服务只涉及 $b$ 的条件，正如按姓、名排序的电话簿帮不了你找出所有叫玛丽亚的人。

::: quiz
一张表在 (dept, salary) 上有 B+树索引。下面哪些条件能利用索引避免全表扫描？
- [x] `dept = 'CS'`
- [x] `dept = 'CS' AND salary > 50000`
- [ ] `salary > 50000`
- [x] `dept BETWEEN 'CS' AND 'MA'`
::: solution
条目先按 dept 排序，同一 dept 内再按 salary 排序。关于 dept 的条件（等值或范围）截出的是连续一段条目；dept 固定后，salary 范围在这一段内也是连续的。只涉及 salary 的条件匹配的条目散落在每个 dept 的区段里，索引无法缩小搜索范围（不过若索引是覆盖的，系统仍可能改为扫描整个索引而不是表）。
:::
:::

::: warning 索引不是免费的
每个索引都会加快某些查询，同时拖慢其键列上的每次插入、删除与更新，因为索引也得跟着改——有 $k$ 个索引时，插入一行大约多花 $k$ 次树下降和页写。索引还占空间（上面 sensor 索引有 $2659$ 页，接近表的一半大），并争夺缓冲池。在一个取值种类很少的列上建索引，或只为选取表中大比例记录的查询建索引，可能永远不会被选中（[[#ex-unclustered]]）。应为高选择性的常用条件和连接所用的列建索引，用系统的计划解释来度量效果，并删掉从不使用的索引。
:::

## 哈希索引

哈希索引按检索键的哈希值把数据条目放进**桶**：等值查找计算 $h(k)$、读一个桶——通常 $1$ 到 $2$ 次 I/O，与 $N$ 无关。哈希帮不上范围查找，因为它故意把相邻的键打散（[[data-structures/hash-tables]]）。数据库的难题是增长：桶数固定的静态哈希文件随表变大长出越来越长的溢出链，而一次性给整个文件重新哈希是一个漫长的阻塞操作。

::: definition 可扩展哈希 {#def-extendible}
**可扩展哈希索引**有一个含 $2^g$ 个指向桶的指针的**目录**，$g$ 称为**全局深度**；键 $k$ 的条目经目录槽位 $h(k) \bmod 2^g$（哈希值的低 $g$ 位）找到。每个桶有一个**局部深度** $d \le g$，低 $d$ 位相同的 $2^{g-d}$ 个目录槽位都指向它。局部深度为 $d$ 的桶溢出时，按第 $d$ 位分裂为两个局部深度 $d + 1$ 的桶；若 $d = g$，先把目录加倍（每个槽位复制一份）并把 $g$ 加一。
:::

目录很小——只放指针——通常常驻内存，所以一次等值查找花一次桶读。分裂只重写一个桶，必要时使目录加倍；文件的其余部分原封不动。

::: example 可扩展哈希的踪迹 {#ex-extendible}
在桶容量为 $2$、$h(k) = k$ 的可扩展哈希索引中，从一个空桶和 $g = 0$ 出发，插入键 $8, 5, 6, 3, 10, 13$。
::: solution
二进制表示：$8 = 1000$，$5 = 0101$，$6 = 0110$，$3 = 0011$，$10 = 1010$，$13 = 1101$。

- $8$、$5$：都进唯一的桶（局部深度 $0$）。
- $6$：桶已满且 $d = g = 0$，于是目录加倍为 $2$ 个槽位（$g = 1$），桶按第 $0$ 位分裂：槽位 `0` 收 $\set{8, 6}$，槽位 `1` 收 $\set{5}$，局部深度都是 $1$。
- $3$（最低位为 $1$）：槽位 `1` 变为 $\set{5, 3}$。
- $10$（最低位为 $0$）：槽位 `0` 已满且 $d = g = 1$，于是目录加倍为 $4$ 个槽位（$g = 2$），桶按第 $1$ 位分裂：$8 = \ldots00$ 进槽位 `00`，$6 = \ldots10$ 与 $10 = \ldots10$ 进槽位 `10`。桶 $\set{5, 3}$ 的局部深度为 $1$，所以槽位 `01` 与 `11` 都指向它。
- $13 = \ldots01$：槽位 `01` 已满，但其桶的 $d = 1 < g = 2$，于是*不*加倍目录就分裂：$5 = \ldots01$ 与 $13 = \ldots01$ 留在槽位 `01`，$3 = \ldots11$ 移入槽位 `11`。

最终状态（$g = 2$）：`00` $\to \set{8}$，`01` $\to \set{5, 13}$，`10` $\to \set{6, 10}$，`11` $\to \set{3}$，局部深度全为 $2$。对 [[#def-extendible]] 做一个 Python 模拟得到同样的状态。
:::
:::

若许多键的低几位相同——或者干脆是同一个键、某个重复次数超过一个桶容量的值——分裂无法把它们分开，目录可能一再加倍；这时终究还是需要溢出页。**线性哈希**（Litwin，1980）干脆不要目录，随装载增长按固定的轮流顺序一次分裂一个桶。哈希索引用于等值查找，更主要的是用于查询处理内部的哈希连接与分组（[[databases/query-processing]]）；作为持久索引，B+树占统治地位，因为它以几乎相同的查找代价支持范围与排序。

## 实践

半个世纪以来，B+树一直是标准的持久索引，但写密集的系统日益改用**日志结构合并树**（LSM 树，O'Neil 等人，1996）：更新先攒在一个内存中的有序表里，再顺序写出为不可变的有序文件，由后台任务合并，用更慢的读（可能要查好几个文件，布隆过滤器能帮上忙）换来得快得多的写。LevelDB、RocksDB 与 Cassandra 等系统（截至 2026 年）都在用它；Kleppmann 的著作对两种设计做了细致的比较。用于分析的列式存储把每一列分开存放并压缩，于是读一百列中三列的查询只读那三列。闪存已把随机读与顺序读的差距缩小，这改变的是优化器的代价常数，而不是本章的逻辑：索引赢在少碰页。

::: history
鲁道夫·拜耳（Rudolf Bayer）与爱德华·麦凯特（Edward McCreight）在波音科学研究实验室发明了 B树（"Organization and maintenance of large ordered indexes"，*Acta Informatica*，1972；1970 年首次报告）；全部数据放在相连叶子中的 B+树变体在 20 世纪 70 年代成为标准，道格拉斯·科默（Douglas Comer）的综述《无所不在的 B树》（"The ubiquitous B-tree"，*ACM Computing Surveys*，1979）已经称其无所不在。IBM 的 VSAM（1973）使用了类似 B+树的索引，System R 与 Ingres 都有 B树索引。罗纳德·费金（Ronald Fagin）、尤尔格·尼弗格尔特（Jürg Nievergelt）、尼古拉斯·皮彭格（Nicholas Pippenger）与 H. 雷蒙德·斯特龙（H. Raymond Strong）于 1979 年发表可扩展哈希，维托尔德·利特温（Witold Litwin）于 1980 年发表线性哈希。槽页布局与缓冲管理器的钉住—解除钉住协议出自 System R 的同一时期；洪泰·周（Hong-Tai Chou）与戴维·德威特（David DeWitt）在 1985 年研究了面向数据库负载的缓冲替换策略，伊丽莎白·奥尼尔（Elizabeth O'Neil）、帕特里克·奥尼尔（Patrick O'Neil）与格哈德·韦库姆（Gerhard Weikum）的 LRU-K（1993）针对这类负载改进了 LRU。
:::

## 后续内容

查询处理（[[databases/query-processing]]）在堆文件、B+树与哈希之上构建选择、排序与连接算法，按 [[#def-io-model]] 的模型计代价；优化器（[[databases/query-optimisation]]）依据选择率的估计在扫描与索引之间做选择。缓冲管理器在崩溃恢复（[[databases/recovery]]）中再次出现：脏页何时必须写回存储的规则决定了什么东西必须记日志。并发控制还必须在许多事务同时使用索引结构时保护它们（[[databases/transactions]]）。存储器层次与缓存的一般理论见 [[computer-systems/memory-hierarchy]]。

::: summary
- **I/O 代价模型**数的是页的传送；持久存储比内存慢几个数量级，且按几 KiB 的页访问。
- **槽页**用稳定的**记录标识**（页号，槽位号）存放变长记录；**堆文件**插入便宜而查找很慢，**顺序文件**恰好相反。
- **缓冲管理器**用带钉住计数与脏位的帧缓存页；扫描超过池的容量时 LRU 会遭遇**顺序泛滥**（[[#prop-flooding]]）。
- **B+树**把全部条目放在相连的叶子里，用扇出为 $F$ 的内部结点指路；高度约为 $\log_F N$（[[#thm-bplus-height]]）——$10^8$ 个条目只需 $3$ 或 $4$ 层——等值、范围查找与插入都是 $O(\log_F N)$ 次 I/O。
- **聚簇**索引使记录按键有序；**非聚簇**索引每条匹配记录至多付一次 I/O，选择率略大就输给别人扫描。
- **覆盖**索引与**复合**索引能单靠索引回答查询、或按键前缀回答；每个索引都要花费空间和更新代价。
- **可扩展哈希**靠分裂一个桶并把一个小目录加倍来增长；哈希索引大约一次 I/O 回答等值查找，但做不了范围。
:::

## 习题

::: exercise 每页记录数 {level=1 check="107"}
$72$ 字节的记录存放在 $8192$ 字节的槽页中，页头占 $24$ 字节，每条记录另有 $4$ 字节的槽位项。一页能装多少条记录？没有槽数组又能装多少？（输入前一个数。）
::: solution
每条记录花 $72 + 4 = 76$ 字节，可用空间 $8192 - 24 = 8168$ 字节，故 $\lfloor 8168/76 \rfloor = 107$ 条记录（$76 \cdot 107 = 8132 \le 8168 < 8208 = 76 \cdot 108$）。按位置寻址的定长记录不需要槽位：$\lfloor 8168/72 \rfloor = 113$。槽数组每页花掉六条记录——这就是稳定记录标识与变长记录的代价。
:::
:::

::: exercise 索引的高度 {level=1 check="3"}
一个 B+树索引有 $F = L = 200$，所有结点全满。要装下 $10^7$ 个条目，最小高度 $h$ 是多少？（输入 $h$。）
::: solution
由 [[#thm-bplus-height]] 需要 $200 \cdot 200^h \ge 10^7$，即 $200^{h+1} \ge 10^7$。$200^2 = 40\,000$，$200^3 = 8\times10^6 < 10^7$，$200^4 = 1.6 \times 10^9$。故 $h + 1 = 4$，$h = 3$：共四层，根、两个内部层和叶子。
:::
:::

::: exercise MRU 下的顺序泛滥 {level=1 check="7"}
手工验证对页 $1$ 到 $5$ 经 $4$ 个帧扫描三遍时 MRU 的未命中次数。（输入未命中次数。）
::: solution
第一轮：$1, 2, 3, 4$ 未命中并填满缓冲池；$5$ 未命中并淘汰最近最多使用的 $4$：池为 $\set{1, 2, 3, 5}$。第二轮：$1, 2, 3$ 命中；$4$ 未命中并淘汰 $3$（最近使用过的）：$\set{1, 2, 4, 5}$；$5$ 命中。第三轮：$1, 2$ 命中；$3$ 未命中并淘汰 $2$：$\set{1, 3, 4, 5}$；$4, 5$ 命中。未命中共 $5 + 1 + 1 = 7$ 次，与模拟打印的一致。
:::
:::

::: exercise 选择索引 {level=2}
表 Orders(id, customer, date, total) 有 $5\times10^7$ 行。负载是：按 id 查一张订单（非常频繁）；列出某个客户的全部订单，新的在前（频繁）；统计一段日期内每天的销售额（每晚一次）。请设计索引，并说明每个查询会采用什么计划。
::: solution
- id：主码，以聚簇 B+树（或主码索引）存放：每次查找约 $3$–$4$ 次 I/O，大多命中缓存。
- (customer, date) 上的复合索引：一个客户的条目连续存放且已按日期排好，"某客户的订单、新的在前"倒序读一遍即可，无需排序；再把 total 也放进索引（或在支持的地方用 `INCLUDE` 列），对按客户汇总而言就是覆盖的。
- 对每晚的报表，date 上的索引只在范围很窄时有用；范围覆盖表的大半时，全表扫描更便宜（[[#ex-unclustered]]）。若报表要紧，干脆按 date 聚簇这张表（例如按日期次序插入，对订单来说这是自然发生的）。

每个额外的索引都会拖慢新订单的插入，这里查找占绝对优势，这是可以接受的。
:::
:::

::: exercise 叶子分裂 {level=2}
用 [[#alg-bplus-insert]] 把键 $1, 2, \ldots, 10$ 按递增次序插入一棵 $L = F = 3$ 的空 B+树。画出最终的树并计算叶子占用率。为什么递增插入会浪费空间？实际系统如何避免？
::: solution
按算法执行（旧叶子留 $\lceil 4/2 \rceil = 2$ 个条目，移走 $2$ 个）：插入 $1, 2, 3$ 后根即叶子 $[1,2,3]$；$4$ 把它分裂为 $[1,2]$ 与 $[3,4]$，根为 $[3]$；$5$ 得 $[3,4,5]$；$6$ 分裂为 $[3,4]$、$[5,6]$，根为 $[3 \mid 5]$；$7$ 填满 $[5,6,7]$；$8$ 分裂为 $[5,6]$、$[7,8]$，而根将得 $3, 5, 7$ 三个键、四个孩子，于是根分裂：在新根 $[5]$ 之下分为 $[3]$ 与 $[7]$；$9$ 填满 $[7,8,9]$；$10$ 把它分裂为 $[7,8]$、$[9,10]$，并把 $9$ 加进结点 $[7]$，得 $[7 \mid 9]$。

最终的树：根 $[5]$；内部结点 $[3]$（孩子 $[1,2]$、$[3,4]$）与 $[7 \mid 9]$（孩子 $[5,6]$、$[7,8]$、$[9,10]$）。五个容量为 $3$ 的叶子共装 $10$ 个条目：占用率 $10/15 = 67\%$，而且除最末一个外每个叶子都永远停留在半满，因为后来的键不会再进入它。系统会识别右端的追加并按不均等的方式分裂——旧叶子留满，另起一个新叶子——顺序键的占用率因此接近 $100\%$；批量装载也是同样做法。
:::
:::

::: exercise 盈亏平衡选择率 {level=2 check="1/200"}
一个关系有 $N = 2\times 10^6$ 条记录，存于 $B = 10^4$ 页。忽略索引页，选择率 $s$ 为多大时，非聚簇索引（每条匹配记录一次 I/O）与全表扫描代价相同？（把 $s$ 以分数输入。）
::: solution
非聚簇索引花 $sN = 2\times10^6\,s$ 次 I/O，扫描花 $10^4$ 次。两者相等时 $s = 10^4 / (2\times10^6) = 1/200 = 0.5\%$。一般地，盈亏平衡选择率是 $B/N$，即每页记录数的倒数：每页记录越多，扫描越早占优。
:::
:::

::: exercise 可扩展哈希续 {level=2}
接着 [[#ex-extendible]] 继续插入 $1$，再插入 $21$。给出最终的目录与各桶的局部深度。
::: solution
$1 = 0001$ 进槽位 `01`，其桶 $\set{5, 13}$ 已满且局部深度 $2 = g$。目录加倍到 $g = 3$（槽位 `000`–`111`，每个复制低两位相同的槽位），桶按第 $2$ 位分裂：$5 = 0101$ 与 $13 = 1101$ 的第 $2$ 位为 $1$，进槽位 `101`；$1 = 0001$（第 $2$ 位为 $0$）进槽位 `001`。现在 `001` $\to \set{1}$，`101` $\to \set{5, 13}$，局部深度都是 $3$；其余的桶保持局部深度 $2$，各由两个槽位指向。

$21 = 10101$，低三位 `101`：那个桶 $\set{5, 13}$ 已满且局部深度 $3 = g$。再次加倍到 $g = 4$，按第 $3$ 位分裂：$5 = 0101$ 与 $21 = 1\,0101$ 的第 $3$ 位为 $0$，进槽位 `0101`；$13 = 1101$ 进槽位 `1101`。最终：$g = 4$，十六个槽位；桶 $\set{8}$、$\set{6, 10}$ 与 $\set{3}$ 局部深度 $2$（各四个槽位指向），$\set{1}$ 局部深度 $3$（两个槽位），$\set{5, 21}$ 与 $\set{13}$ 局部深度 $4$（各一个槽位）。对 [[#def-extendible]] 的模拟与此一致。两次插入使目录加倍两次，因为 $5$、$13$ 与 $21$ 的低位相同——这正是只取哈希值少数几位的软肋。
:::
:::

::: exercise 基于比较的索引的下界 {level=3}
设某个索引是一棵树，其结点是页，每页至多放 $F$ 个键与指针，查找时只能把待查键与所读页中的键比较。证明：当索引区分 $N$ 个不同的键时，必有某个查找至少读 $\log_{F+1} N$ 页，并由此说明 B+树在不超过对数底数之差的常数因子意义下是最优的。
::: solution
把一次查找看成从根出发的一次行走：读过一页（其中至多 $F$ 个键）后，把待查键与它们比较，结果落在至多 $F + 1$ 个区间之一，从而决定下一个要读的页（或给出答案）。于是读完 $t$ 页后，查找至多走过 $(F + 1)^t$ 条不同的路径，而查找结果必须不同的键需要不同的路径。要区分 $N$ 个键就需要 $(F + 1)^t \ge N$，即最坏情形的查找有 $t \ge \log_{F+1} N$。B+树读 $h + 1 \le 2 + \log_{\lceil F/2 \rceil} (N/2\lceil L/2\rceil)$ 页（[[#thm-bplus-height]]）；由于 $\log_{\lceil F/2\rceil} N = \log_{F+1} N \cdot \frac{\ln(F+1)}{\ln \lceil F/2\rceil}$，当 $F$ 增大时该比值趋于 $1$，所以 B+树与下界只差一个常数因子（$F$ 大时接近 $1$）。哈希逃出了这个界，因为它不比较键。
:::
:::

::: exercise 模拟时钟算法 {level=3}
实现时钟替换策略，并与 LRU 比较：(a) $4$ 个帧、对页 $1$–$5$ 扫描三遍；(b) 引用串 $1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5$、$3$ 个帧。解释结果。
::: solution
```python
def clock(refs, frames):
    slots, ref, hand, misses = [None] * frames, [0] * frames, 0, 0
    for p in refs:
        if p in slots:
            ref[slots.index(p)] = 1          # 又被引用：给它第二次机会
            continue
        misses += 1
        while ref[hand]:                     # 跳过被引用的帧并清除其引用位
            ref[hand] = 0
            hand = (hand + 1) % frames
        slots[hand], ref[hand] = p, 1        # 替换被淘汰的页
        hand = (hand + 1) % frames
    return misses

scan = list(range(1, 6)) * 3
belady = [1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5]
print(lru(scan, 4), clock(scan, 4), lru(belady, 3), clock(belady, 3))
```

```console
$ python3 clock.py
15 15 10 9
```

(a) 时钟与 LRU 一样泛滥：一个页转回来时，它的引用位早已被指针清除，也已被替换。(b) 第二个串上 LRU 未命中 $10$ 次，时钟 $9$ 次：时钟只是近似 LRU，这里它较粗的信息恰好把页 $5$ 的邻居保得稍好一些。两者都不最优；贝拉迪（Bélády）最优策略（换出将来最晚才再次使用的页）在 (b) 上只需 $7$ 次未命中。页替换策略在 [[operating-systems]] 中继续讨论。
:::
