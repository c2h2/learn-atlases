一笔 £100 的 A 到 B 转账已经办理，应用已被告知"已提交"。一秒之后断电。服务器重启时，这笔转账必须在——这就是**持久性**——哪怕装着 A 和 B 的那些页还留在缓冲池里、从未写到盘上。另一个事务在断电时只做了一半；为了在缓冲池里腾地方，它改过的某些页其实已经写到了盘上。它的改动必须消失——这就是**原子性**——哪怕其中一部分已经在盘上。恢复（recovery）就是 DBMS 中让这两个承诺无论崩溃何时发生都能兑现的部分。

这件工具是一份**日志**：一份只许追加、记录每一次修改的记录序列，并且*先于*它所描述的修改写入稳定存储器。本章从第一原理出发建立日志机制——缓冲策略、撤销与重做信息、**预写式日志**规则与检查点——然后介绍 **ARIES**，即 IBM 的 C. Mohan 等人（1992）提出的、作为多数商用系统基础的恢复算法。我们将在一整个示例上追踪 ARIES 的执行（以一段小型模拟验证），并证明即使系统在恢复期间再次崩溃它依然正确。本章假定并发控制已经存在，那在 [[databases/transactions]]；缓冲管理器在 [[databases/storage-indexing]]。

## 故障与存储

我们区分三类故障。

- **事务故障**：事务中止——或因自身 `ROLLBACK`，或因违反约束，或因并发控制器选中它作死锁牺牲者。它的效果必须在系统继续运行的同时被撤销。
- **系统崩溃**：断电、操作系统或 DBMS 失效。主存内容（缓冲池在内）丢失；持久存储的内容幸存。
- **介质故障**：磁盘或 SSD 丢失数据。这靠冗余来处理——复制的日志、RAID、备份加日志归档——不在狭义崩溃恢复的范围内。

恢复假定存在**稳定存储**：一旦写入就绝不丢失。没有哪种真实设备是稳定的，但把数据写到多个独立设备（镜像磁盘、其他机器上的副本）并对每次写加以确认，就能很好地逼近稳定存储。写入按页进行，崩溃可能把一次页写打断到一半（**撕裂页**）；系统用校验和察觉这种事，并从日志中该页的完整副本（PostgreSQL 的"全页写入"）或别处的第二份拷贝来修复。

### 缓冲策略

缓冲管理器的两个决定，决定了恢复必须做什么。

::: definition steal 与 force {#def-steal-force}
若缓冲管理器可以（为腾出一个帧）把被*未提交*事务修改过的页写到持久存储上，则称它使用 **steal**（可窃取）策略，否则称 **no-steal**。若事务提交确认之前，它修改过的全部页都被写到持久存储上，则称使用 **force**（强制）策略，否则称 **no-force**。
:::

::: proposition 恢复必须能做到什么 {#prop-policies}
有了 steal，恢复必须能够**撤销**已到达持久存储的未提交事务的修改。有了 no-force，恢复必须能够**重做**尚未到达持久存储的已提交事务的修改。no-steal 且 force 时，对崩溃既不需要撤销也不需要重做。
:::

::: proof
崩溃之后，持久数据库恰含崩溃前写入的那些页。steal 之下，这样的页可能含有一个从未提交的事务的修改；原子性要求把它去掉，于是它的旧值必须可以找回——撤销。no-force 之下，已提交事务的修改可能只存在于丢失的缓冲帧里；持久性要求重新落实它，于是它的新值必须可以找回——重做。no-steal 之下，未提交的修改从不在盘上；force 之下，已提交的修改全在盘上；两者兼备时，崩溃后的盘上恰是已提交的修改，只要提交事务自身的写是原子的（而这一点在实践中又非得靠日志或影子页不可）。
:::

no-steal 把事务大小限制在缓冲池以内，force 让每次提交都等待其全部页的随机写。因此高性能系统采用 **steal 与 no-force**——最灵活的缓冲策略，也是对恢复要求最苛的：撤销与重做都需要。

::: example 一次崩溃留下了什么 {#ex-crash-state}
在 steal 与 no-force 之下，$T_1$ 把 $X$ 从 $1$ 改为 $2$ 并提交；$T_2$ 把 $Y$ 从 $5$ 改为 $6$，仍在运行。缓冲管理器把 $Y$ 的页写到了盘上（为腾地方），却没有写 $X$ 的页。系统崩溃。盘上是什么？恢复必须做什么？
::: solution
盘上：$X = 1$（已提交的修改从未写出）而 $Y = 6$（未提交的修改被窃取到盘上）。正确的状态是 $X = 2$、$Y = 5$。恢复必须**重做** $T_1$ 的修改，用它的后像 $2$；**撤销** $T_2$ 的修改，用它的前像 $5$。若用 force，$X$ 的页会在 $T_1$ 提交时写出，无须重做；若用 no-steal，$Y$ 的页根本写不出去，无须撤销。于是两种像都必须记在日志里，[[#def-log]] 正是把它们放进去的地方。
:::
:::

## 日志

::: definition 日志与日志记录 {#def-log}
**日志**是一个记录序列，每条记录由**日志序列号**（LSN）标识，LSN 随记录在日志中的位置递增。事务 $T$ 修改数据项 $X$（位于页 $P$）的一条**更新记录**包含 $T$、$P$、**前像**（旧值，供撤销）、**后像**（新值，供重做），以及 $T$ 上一条日志记录的 LSN（**prevLSN**）。其他记录标记事务的**提交**、**中止**与**结束**，以及**检查点**。每个数据页在页头存有 **pageLSN**：包含在其中的最新一条日志记录的 LSN。
:::

日志顺序写入内存中的**日志缓冲区**，并在若干时刻**刷写**（强制写出）到稳定存储器；顺序追加十分便宜，这就是记日志优于强制写数据页的原因。**flushedLSN** 是已知已落在稳定存储上的最大 LSN。两条规则把日志与数据联系起来。

::: definition 预写式日志（WAL） {#def-wal}
1. **撤销规则**：一个数据页写到持久存储之前，描述对它所做的全部修改的日志记录——尤其是 LSN 等于其 pageLSN 的那一条——必须已经写到稳定存储：$\text{pageLSN} \le \text{flushedLSN}$。
2. **重做规则**：事务被报告为已提交之前，它的全部日志记录（含提交记录）必须已在稳定存储上。
:::

::: theorem 预写式日志使恢复成为可能 {#thm-wal}
在 steal 与 no-force 之下，若遵守 WAL 规则，则任何崩溃之后，稳定存储上的日志包含：(a) 未提交事务的、已出现在持久数据库中的每个修改的前像；(b) 已提交事务的每个修改的后像。
:::

::: proof
(a) 设未提交事务 $T$ 的一个修改（日志记录 LSN 为 $\ell$）出现在盘上的某个页里。该页写入时含有这个修改，所以它当时的 pageLSN 至少是 $\ell$；由撤销规则，日志在该页写出之前至少已刷到那个 pageLSN，因而至少刷到了 $\ell$。于是带前像的那条记录在稳定存储上。(b) 若 $T$ 提交了，它之所以被报告为已提交，正是因为它的全部日志记录——包括每条带后像的更新记录——都已刷出（重做规则）。落在稳定存储上的记录能在崩溃中幸存。
:::

::: example 违反撤销规则 {#ex-wal-violation}
$T$ 把 $X$ 从 $5$ 改为 $6$（日志记录 $\ell = 70$，仍在日志缓冲区里）。缓冲管理器在刷写日志*之前*把 $X$ 的页写到盘上，随后、且早于 $T$ 提交，系统崩溃。重启时会怎样？若是另一种情形——日志已刷出，但 $T$ 的提交在其提交记录落盘之前就被确认了呢？
::: solution
重启时该页上写着 $X = 6$，属于一个从未提交的事务的修改，必须撤销。可是唯一保留前像 $5$ 的记录 $70$ 已随日志缓冲区丢失：恢复甚至说不出 $X$ 被改过，遑论恢复原值。数据库就此悄悄含有一个不原子的事务。撤销规则（写页之前须 $\text{pageLSN} = 70 \le \text{flushedLSN}$）堵住的正是这一漏洞。

第二种情形下，$T$ 的更新记录在稳定存储上，提交记录却不在；恢复把 $T$ 当作失败事务撤销，可用户已被告知它提交了——这是对持久性的违背。重做规则禁止在提交记录落盘之前确认提交。
:::
:::

所以，事务的提交点就是它的提交记录抵达稳定存储的那一刻：之前崩溃，留下的是必须撤销的事务；之后崩溃，留下的是必须重做的事务。一次提交只花一次顺序的日志刷写，而不是许多次随机的页写。**成组提交**让它更便宜：一次刷写就让许多并发事务的提交记录同时持久。若一次刷写耗时 $2$ ms，每次提交各刷一次至多每秒 $500$ 个提交，而把 $32$ 条提交记录合成一组刷写可达每秒 $16\,000$ 个（[[#ex-group-commit]]）。

### 重做与幂等性

恢复本身可能被又一次崩溃打断后再重启，所以它采取的每个动作都必须是可重复的。物理重做——"把页 $P$ 上的数据项 $X$ 置为后像"——是**幂等**的：做两遍与做一遍效果相同。但许多系统记录的是*逻辑*或**物理-逻辑**操作（"把这条记录插入页 $P$"、"给 $X$ 加 $10$"），它们并不幂等：加两次 $10$ 就加了 $20$。pageLSN 解决了这一问题。

::: lemma 带 pageLSN 检验的重做是幂等的 {#lem-pagelsn}
假设每当应用 LSN 为 $\ell$ 的日志记录的修改时，页的 pageLSN 就置为 $\ell$，且对同一页的修改按 LSN 次序应用。若重做仅当 $\text{pageLSN}(P) < \ell$ 时才对页 $P$ 应用 LSN 为 $\ell$ 的记录，那么无论重做重复多少遍，每个已记录日志的修改都恰好被应用到其页上一次。
:::

::: proof
对同一页的修改按 LSN 递增的次序应用，每次应用把 pageLSN 置为该 LSN，所以任一时刻页上恰含 LSN 不超过其 pageLSN 的那些修改——它们已被应用——而不含更晚的。重做考察记录 $\ell$ 时：若 $\text{pageLSN}(P) \ge \ell$，修改已在页上，跳过；否则尚未，于是应用它，pageLSN 变为 $\ell$。再来一遍时会看到 $\text{pageLSN}(P) \ge \ell$ 而跳过。按 LSN 次序对记录归纳，每个修改恰好被应用一次。
:::

### 检查点

若无帮助信息，恢复就得从头读起整个日志。**检查点**记录足够的系统状态，使恢复可以从日志接近末尾处开始。**静止**检查点暂停新事务、等待活跃事务结束、刷出全部脏页——简单，但让系统停摆。ARIES 使用**模糊检查点**：写一条 `begin_checkpoint` 记录，再写一条 `end_checkpoint` 记录，内含当前的**事务表**与**脏页表**（定义见下），强制刷写日志，并把 `begin_checkpoint` 的 LSN 存到稳定存储上一个众所周知的位置——**主记录**。什么也不必等待，任何页也不必刷出；脏页表告诉恢复重做必须从哪里开始。为让这个起点保持新鲜，缓冲管理器在后台源源不断把脏页写到盘上。

::: widget plot

## ARIES

ARIES（Algorithm for Recovery and Isolation Exploiting Semantics，利用语义的恢复与隔离算法）在 steal 与 no-force、细粒度（记录级）锁定和逻辑撤销之下工作，建立在三条原则之上：

1. **预写式日志**，见 [[#def-wal]]。
2. **重做时重复历史**：崩溃之后，先重做*全部*已记录日志的修改——包括那些将要回滚的事务的——把数据库带回崩溃那一刻的状态。
3. **撤销时也记日志**：每个撤销动作本身都记入日志，成为一条**补偿日志记录**（CLR），于是一次撤销永不被再次撤销，恢复在反复崩溃中始终向前推进。

::: definition ARIES 的数据结构 {#def-aries}
- 每条日志记录都有 LSN 和 prevLSN（同一事务的前一条记录）。
- **补偿日志记录**（CLR）描述对某条更新记录 $u$ 的撤销：它包含这次撤销所需的重做信息（把 $u$ 的前像当作新值）和一个 **undoNextLSN**，即 $u$ 的 prevLSN——本事务下一个待撤销的记录的 LSN。CLR 会被重做，但绝不被撤销。
- **事务表**（TT）为每个活跃事务设一项：其状态（运行中/撤销中，或已提交）与 **lastLSN**，即它最近一条日志记录的 LSN。
- **脏页表**（DPT）为缓冲池中每个脏页设一项，带 **recLSN**：自该页上次写到盘上以来、使它变脏的第一条日志记录的 LSN。
:::

正常运行期间，每次更新追加一条记录、设置页的 pageLSN、并更新该事务的 lastLSN；一个页首次变脏时带着它的 recLSN 进入 DPT，被写出时离开。中止的事务写一条 abort 记录，然后完全按下面撤销阶段的方式回滚，写出 CLR，最后写一条 end 记录。提交的事务写一条 commit 记录，强制刷写日志（重做规则），释放它的锁，稍后再写一条 end 记录。

::: example 一次正常的撤销 {#ex-abort}
事务 $T$ 写出更新记录 $200$（$X$：$1 \to 2$）、$210$（$Y$：$3 \to 4$）、$220$（$Z$：$5 \to 6$），各自的 prevLSN 指向前一条，然后应用调用 `ROLLBACK`。ARIES 会写哪些日志记录？内容是什么？
::: solution
先是一条 abort 记录，LSN $230$（prevLSN $220$）。然后 $T$ 的记录按逆序撤销，每次撤销都由一条 CLR 记入日志：

| LSN | 记录 | 修改 | undoNextLSN |
|---|---|---|---|
| 240 | $220$ 的 CLR | $Z \gets 5$ | 210 |
| 250 | $210$ 的 CLR | $Y \gets 3$ | 200 |
| 260 | $200$ 的 CLR | $X \gets 1$ | — |
| 270 | end | | |

每条 CLR 的 undoNextLSN 就是它所补偿的那条记录的 prevLSN。若系统在 $250$ 落到稳定存储之后崩溃，重启会重做 CLR $240$ 与 $250$，把 $T$ 找作 lastLSN 为 $250$ 的失败事务，沿 undoNextLSN 走到 $200$，只再写一条 CLR——$240$ 与 $250$ 的功不会被重复。锁要等 end 记录之后才释放，所以别的事务看不到撤销到一半的状态。
:::
:::

::: algorithm ARIES 的重启 {#alg-aries}
1. **分析。** 读主记录，从最后一条 `begin_checkpoint` 开始；用 `end_checkpoint` 初始化 TT 与 DPT。沿日志向前扫到末尾。对事务 $T$ 的每条记录：若是 end 记录，把 $T$ 从 TT 中删去；否则若 $T$ 不在 TT 中则加入，把它的 lastLSN 置为当前 LSN，若该记录是 commit 记录则把状态置为已提交。对于页 $P$ 上的一条更新记录或 CLR，若 $P$ 不在 DPT 中，则以当前 LSN 作为 recLSN 把 $P$ 加入。扫描结束时，TT 中尚未提交的事务就是**失败事务**（loser）。
2. **重做。** 从 $\mathit{redoLSN}$（DPT 中最小的 recLSN）向前扫。对页 $P$ 上的每条更新记录或 CLR（LSN 为 $\ell$）：若 $P$ 不在 DPT 中、或 $\text{recLSN}(P) > \ell$、或（读出 $P$ 后）$\text{pageLSN}(P) \ge \ell$，则*跳过*；否则重新应用该修改并置 $\text{pageLSN}(P) \gets \ell$。然后为 TT 中已提交的事务写 end 记录并把它们移去。
3. **撤销。** 令 ToUndo 为各失败事务 lastLSN 的集合。反复从中取出最大的 LSN $\ell$：
   - 若记录 $\ell$ 是 CLR，把它的 undoNextLSN 加入 ToUndo（若为空指针，则为该事务写 end 记录）；
   - 若是更新记录，撤销修改，写一条 undoNextLSN 等于该记录 prevLSN 的 CLR，并把那个 prevLSN 加入 ToUndo（若为空指针，写 end 记录）；
   - 若是 abort 记录，加入它的 prevLSN。
:::

重做阶段*重复全部*历史，失败事务也不例外，因为这使撤销阶段变得简单：重做之后数据库与崩溃时刻完全一致，于是撤销可以像正常中止那样把失败事务滚回去，需要时使用逻辑撤销（比如索引中的一个键自那时起可能已挪到别的页上）。跳过条件避免不必要的读页：不在 DPT 中的页、或 recLSN 晚于 $\ell$ 的页，是在记录 $\ell$ 的修改之后写到盘上的，修改自然已经在里面。

::: example 一次完整的 ARIES 重启 {#ex-aries}
最后一次检查点（其 TT 与 DPT 为空）之后的日志如下；数据项 $A, E$ 在页 $P_1$，$B$ 在 $P_2$，$C$ 在 $P_3$，$D$ 在 $P_4$。

| LSN | 事务 | 记录 | prevLSN |
|---|---|---|---|
| 30 | $T_1$ | 更新 $P_1$：$A$ $10 \to 20$ | — |
| 40 | $T_2$ | 更新 $P_2$：$B$ $5 \to 7$ | — |
| 50 | $T_1$ | 更新 $P_3$：$C$ $1 \to 2$ | 30 |
| 60 | $T_2$ | commit | 40 |
| 70 | $T_3$ | 更新 $P_4$：$D$ $8 \to 9$ | — |
| 80 | $T_2$ | end | 60 |
| 90 | $T_1$ | 更新 $P_2$：$B$ $7 \to 70$ | 50 |
| 100 | $T_3$ | 更新 $P_1$：$E$ $3 \to 4$ | 70 |
| 110 | $T_3$ | abort | 100 |
| 120 | $T_3$ | CLR：撤销 100，$E \gets 3$，undoNextLSN $70$ | 110 |

随后系统崩溃。盘上，$P_1$ 最后写出时 pageLSN 为 $100$（含有 $A = 20$、$E = 4$），$P_2$ 的 pageLSN 为 $40$（$B = 7$），$P_3$、$P_4$ 从未写出（$C = 1$、$D = 8$）。执行一次重启。
::: solution
**分析。** 从 LSN $30$ 扫描：$T_1$ 进入 TT，$P_1$ 以 recLSN $30$ 进入 DPT；$T_2$ 与 $P_2$（recLSN $40$）；$P_3$（recLSN $50$）；$T_2$ 在 $60$ 处变为已提交；$T_3$ 与 $P_4$（recLSN $70$）；$T_2$ 在 $80$ 处离开 TT；此后 lastLSN 不断前移。结束时：TT $= \set{T_1\colon \text{lastLSN } 90,\ T_3\colon \text{lastLSN } 120}$，两者都是失败事务；DPT $= \set{P_1\colon 30, P_2\colon 40, P_3\colon 50, P_4\colon 70}$。

**重做**，从 $\mathit{redoLSN} = 30$ 开始：

| LSN | 页 | 盘上的 pageLSN | 动作 |
|---|---|---|---|
| 30 | $P_1$ | 100 | 跳过（$100 \ge 30$） |
| 40 | $P_2$ | 40 | 跳过（$40 \ge 40$） |
| 50 | $P_3$ | 0 | 重做 $C = 2$，pageLSN $50$ |
| 70 | $P_4$ | 0 | 重做 $D = 9$，pageLSN $70$ |
| 90 | $P_2$ | 40 | 重做 $B = 70$，pageLSN $90$ |
| 100 | $P_1$ | 100 | 跳过 |
| 120 | $P_1$ | 100 | 重做 CLR：$E = 3$，pageLSN $120$ |

数据库现在与崩溃时刻一致：$A = 20$、$E = 3$、$B = 70$、$C = 2$、$D = 9$。

**撤销**，ToUndo $= \set{90, 120}$（新记录依次取 LSN $130, 140, \ldots$）：

| 取出 | 记录 | 动作 | 其后的 ToUndo |
|---|---|---|---|
| 120 | $T_3$ 的 CLR | 无可撤销；沿 undoNextLSN 前进 | $\set{90, 70}$ |
| 90 | $T_1$ 更新 $B$ | $B \gets 7$；写出 CLR 130（undoNext 50） | $\set{70, 50}$ |
| 70 | $T_3$ 更新 $D$ | $D \gets 8$；写出 CLR 140（undoNext —）；$T_3$ 的 end 记录在 150 | $\set{50}$ |
| 50 | $T_1$ 更新 $C$ | $C \gets 1$；写出 CLR 160（undoNext 30） | $\set{30}$ |
| 30 | $T_1$ 更新 $A$ | $A \gets 10$；写出 CLR 170（undoNext —）；$T_1$ 的 end 记录在 180 | $\emptyset$ |

最终状态：$A = 10$、$E = 3$、$B = 7$、$C = 1$、$D = 8$。已提交的 $T_2$ 的修改 $B = 7$ 得以保留（它被失败事务 $T_1$ 覆写过，又因撤销 $T_1$ 而复原），失败事务 $T_1$ 与 $T_3$ 的修改则荡然无存。注意 CLR $120$ 使撤销跳过了 $T_3$ 的记录 $110$ 与 $100$：它们的撤销在崩溃之前已经完成并记录在案。[[#alg-aries]] 的一个 Python 模拟（[[#ex-implement]]）打印出的正是这些步骤。
:::
:::

撤销阶段沿日志中的后退链行走：事务内部的 prevLSN 指针，以及从 CLR 出发的 undoNextLSN——它一步跨过那些已经被补偿过的记录。

::: widget graph

caption: [[#ex-aries]] 的撤销阶段所走的后退链：底部是 $T_1$ 的 prevLSN 链 $90 \to 50 \to 30$，顶部是 $T_3$ 的各条记录，其中 CLR $120$ 由它的 undoNextLSN 直指 $70$。从 L120 出发做广度优先搜索只能到达 L70：记录 $110$ 与 $100$ 根本不会被访问，因为它们的撤销在崩溃前已经完成并记入日志。改从 L110 开始搜索，就能看到没有 CLR 时撤销会走的链——那会把 $100$ 再撤销一遍。

### 正确性

::: theorem ARIES 重启的正确性 {#thm-aries}
假定 WAL、严格两阶段锁定，并假定崩溃时稳定存储上的日志是已写日志的一个前缀。则 [[#alg-aries]] 完成后，数据库含有日志中有提交记录的每个事务的全部修改，且不含任何其他事务的任何修改。若在重启期间系统崩溃任意多次并再次重启，结论同样成立。
:::

::: proof
**重做之后，就记了日志的修改而言，数据库等于崩溃时刻的状态。** 考察稳定日志中关于页 $P$ 的任一条更新记录或 CLR $\ell$。若 $\ell$ 早于 $\mathit{redoLSN}$，或 $P$ 不在 DPT 中，或 $\text{recLSN}(P) > \ell$，则由 DPT 的构造方式（来自检查点与分析扫描），$P$ 是在修改 $\ell$ 应用之后写到盘上的，该修改已在盘上。否则，重做当且仅当 $\text{pageLSN}(P) < \ell$ 时应用它，而由 [[#lem-pagelsn]]，每个修改此时都恰好存在一次。不在稳定日志里的修改，按 WAL 的撤销规则，不在盘上任何页中。于是重做之后，每个页恰反映稳定日志的那些修改。

**撤销恰好去掉失败事务的修改。** 获胜事务有提交记录，修改自当保留。对失败事务，撤销阶段从 lastLSN 起沿 prevLSN 和 CLR 的 undoNextLSN 向后走它的记录链。一条 undoNextLSN 为 $u$ 的 CLR 记录了这样的事实：$u$ 之后本事务的每个更新都已被撤销（各由一条 CLR 完成，CLR 本身就在日志里，且已被重做），所以从 $u$ 继续走，每个尚未撤销的更新恰好被撤销一次，且按逆序。严格 2PL 保证失败事务改过的数据项自那以后没有别的任务覆写或读过它，于是恢复前像（或施加逻辑逆操作）得到的正是失败事务染指之前各数据项的值。按全局 LSN 递减处理各失败事务，能把它们正确地穿插起来。

**反复崩溃。** 重做由 [[#lem-pagelsn]] 是幂等的，而分析只读日志。每个撤销步骤都先（按 WAL）记为一条 CLR、之后才可能抵达磁盘，且 CLR 绝不被撤销；在之后的重启中，CLR 被重做，最后一条的 undoNextLSN 告诉撤销该从哪里接着走。所以任何更新都不会被撤销两次，每次重启都有进展。
:::

::: proposition 撤销期间的日志量有界 {#prop-clr-bound}
无论系统在恢复期间崩溃多少次，一个做过 $n$ 次修改的事务的撤销至多写 $n$ 条 CLR。
:::

::: proof
每条 CLR 补偿特定的一条更新记录 $u$，并把下一步撤销引向 $u$ 的 prevLSN。撤销从不把 CLR 当作待撤销对象处理，只沿它的 undoNextLSN 走。崩溃后，撤销从事务的 lastLSN 重新开始，它或是最近的 CLR 或是最近的更新记录，再沿链跨过一切已补偿的东西。于是本事务的每条更新记录至多被补偿一次，CLR 总数至多 $n$ 条。（若没有 CLR，或用"撤销撤销"之类的方案，反复崩溃会使日志无限增长。）
:::

::: quiz
在 ARIES 的重做阶段，一条 LSN 为 $250$ 的记录要更新页 $P$，$P$ 的 DPT 项 recLSN 为 $200$。读出该页后发现它的 pageLSN 是 $260$。重做会怎么做？
- [ ] 重新应用该修改，因为 $250 \ge 200$。
- [x] 跳过，因为页上已经有这个修改。
- [ ] 撤销该修改，因为页比这条日志记录新。
- [ ] 报告损坏，因为 pageLSN 不可能超过记录的 LSN。
::: solution
$\text{pageLSN} = 260 \ge 250$，页已经反映了记录 $250$（以及更晚的 $260$）的修改；重做跳过它。recLSN 只说明该页*可能*从哪儿开始缺修改，拍板的是 pageLSN。pageLSN 大于正在考察的 LSN 是正常现象：该页是在一个更晚的修改之后写到盘上的。
:::
:::

::: warning 日志不是可有可无的，"小"事务也一样
一种诱人的优化是：对小的或"无足轻重"的修改直接写数据页而省掉日志，或在日志刷出之前就确认提交。两者都会破坏保证：一页没带它的日志记录就被写出，其事务若不提交，崩溃后就无法撤销（违反撤销规则）；一个已确认的提交若其记录还在日志缓冲区里，崩溃就把它丢掉（违反重做规则）。一些系统确实把松弛持久性作为显式选项提供——例如 PostgreSQL 的 `synchronous_commit = off`，或 SQLite 在 WAL 模式下的 `PRAGMA synchronous = NORMAL`——它们可能在断电后丢掉最近确认的那几个事务，但绝不会损坏数据库。只有当"丢掉最近一秒的零头工作"可以接受时才用这类设置；除非存储设备在设计上保证兑现刷写请求，否则绝不要想当然。
:::

## 实践

ARIES 或其近似变体是 IBM 的 DB2、Microsoft SQL Server 等系统的基础。建立在 MVCC 之上的系统可以跳过对中止事务的撤销阶段：**PostgreSQL** 把旧行版本留在表里，中止事务写下的新版本根本不可见——因为提交日志中该事务的状态是"aborted"；它的 WAL 因此只需重做，崩溃恢复从最后一个检查点重放日志，并用每次检查点之后的全页镜像修复撕裂页（就版本 17 而言）。

**SQLite** 在一个系统里同时展示两种经典设计。默认的 rollback-journal 模式下，改动数据库文件的页之前，它把页的*原始*内容复制进一个独立的日志文件并同步；提交时先同步数据库文件，再删除（或作废）这个文件。这就是带 force 的撤销日志：崩溃后残留的日志文件意味着一个未完成的事务，把其中的原始页拷回即可。**WAL 模式**反其道而行：改过的页追加到一个预写日志文件，提交是该日志中标了记的一帧，数据库文件稍后由一次**检查点**回写更新——这是带 no-force 的重做日志，它还让读者在写者追加的同时始终读到数据库文件加日志已提交部分构成的一个一致快照（[[databases/transactions]]）。

::: history
为恢复而记日志随着 20 世纪 70 年代第一批事务系统而演化；Jim Gray 的《数据库操作系统笔记》（"Notes on data base operating systems"，1978）与 System R 的恢复管理器（Gray、McJones、Blasgen、Lindsay、Lorie、Price、Putzolu 与 Traiger，"The recovery manager of the System R database manager"，*ACM Computing Surveys*，1981）确立了预写式日志、检查点，以及影子页这一替代方案——System R 也曾采用影子页，后来因其代价而弃用。Theo Härder 与 Andreas Reuter 的综述《面向事务的数据库恢复原理》（"Principles of transaction-oriented database recovery"，*ACM Computing Surveys*，1983）提出了 steal/force 分类与 ACID 缩写。C. Mohan、Don Haderle、Bruce Lindsay、Hamid Pirahesh 与 Peter Schwarz 于 1992 年在 *ACM Transactions on Database Systems* 发表了《ARIES：一种基于预写式日志、支持细粒度锁定与部分回滚的事务恢复方法》（*ARIES: a transaction recovery method supporting fine-granularity locking and partial rollbacks using write-ahead logging*），此前有 1989 年的 IBM 研究报告；连同其管理索引的姊妹篇 ARIES/IM，它成为标准设计。Gray 与 Reuter 的《事务处理：概念与技术》（*Transaction Processing: Concepts and Techniques*，1992）对日志与恢复有深入的论述。
:::

## 后续内容

恢复补全了 [[databases/transactions]] 开启的 ACID 保证。分布式数据库中，跨多台机器的事务必须在所有地方提交或哪都不提交，这需要原子提交协议——两阶段提交，它的各参与者依靠的恰是本章的日志——以及由 Paxos、Raft 这类共识协议保持一致的复制日志（[[distributed-systems]]）。把只增日志当作事实之源的思想远不限于数据库：文件系统用它做日志（[[operating-systems]]），基于日志的消息系统与事件溯源（Kleppmann 的书中有讨论）更在上面搭建起整个架构。

::: summary
- 崩溃恢复在系统崩溃之后提供**原子性**与**持久性**，并为日志假定**稳定存储**。
- **steal** 要求撤销，**no-force** 要求重做（[[#prop-policies]]）；高性能系统用 steal/no-force，前像后像都记日志。
- **预写式日志**：页写出之前先刷它的日志记录，提交确认之前先刷事务的全部记录（含提交记录）（[[#thm-wal]]）；一次提交只花一次顺序日志刷写，**成组提交**让大家共享它。
- **pageLSN** 检验使重做幂等（[[#lem-pagelsn]]）；**模糊检查点**记下事务表与脏页表，使恢复可从日志接近末尾处开始。
- **ARIES** 重启分三趟：**分析**（重建 TT 与 DPT，找出失败事务）、**重做**（自最小 recLSN 起重复全部历史）、**撤销**（按 LSN 递减回滚失败事务，写出 **CLR**）。
- CLR 只被重做、绝不被撤销；其 undoNextLSN 使恢复在反复崩溃下保持正确，并使日志量有界（[[#thm-aries]]、[[#prop-clr-bound]]）。
- PostgreSQL 这类 MVCC 系统只需重做；SQLite 的 rollback journal 是带 force 的撤销日志，其 WAL 模式是带检查点的重做日志。
:::

## 习题

::: exercise 策略与日志 {level=1}
对缓冲策略的每种组合——steal/force、steal/no-force、no-steal/force、no-steal/no-force——说明崩溃恢复必须记录撤销信息、重做信息、两者都要、还是都不必。
::: solution
由 [[#prop-policies]]：steal/force 只需撤销信息；steal/no-force 两者都要；no-steal/force 都不必（假定一个事务的各页是原子地安置到位的）；no-steal/no-force 只需重做信息。在任何未提交修改会被就地施加到缓冲池的策略下，*事务*中止也需要撤销信息——不过在 no-steal 下它们从达不到盘上，内存中的页直接丢弃即可。
:::
:::

::: exercise 应用 WAL 规则 {level=1 check="2"}
flushedLSN 为 $500$。四个脏页的 pageLSN 分别是 $420$、$510$、$499$ 与 $650$。缓冲管理器现在可以把其中几页写到盘上？（输入数目。）
::: solution
按撤销规则，只有 $\text{pageLSN} \le \text{flushedLSN} = 500$ 的页可以写出：pageLSN 为 $420$ 与 $499$ 的两页，即 $2$ 页。其余两页写出之前，日志须至少刷到 $510$ 或 $650$。
:::
:::

::: exercise 数 CLR {level=1 check="4"}
[[#ex-aries]] 的撤销阶段写了几条 CLR？（输入数目。）
::: solution
四条：$130$（撤销 $90$）、$140$（撤销 $70$）、$160$（撤销 $50$）、$170$（撤销 $30$）。CLR $120$ 写在崩溃之前，不会被撤销。总计，$T_1$ 的三次更新得到三条 CLR，$T_3$ 的两次更新得到两条（$120$ 与 $140$），与 [[#prop-clr-bound]] 相符。
:::

::: exercise 从检查点做起的分析 {level=2 check="15"}
`end_checkpoint` 记录列出 TT $= \set{T_4\colon \text{lastLSN } 12}$、DPT $= \set{P_5\colon 15,\ P_6\colon 40}$。其后日志包含：$45$ $T_4$ 更新 $P_7$；$50$ $T_5$ 更新 $P_6$；$55$ $T_4$ commit；$60$ $T_5$ 更新 $P_8$。给出分析结束时的 TT 与 DPT、失败事务、以及重做开始的 LSN。（输入那个 LSN。）
::: solution
$45$：$T_4$ 的 lastLSN 变为 $45$；$P_7$ 以 recLSN $45$ 进入 DPT。$50$：$T_5$ 进入 TT（lastLSN $50$）；$P_6$ 已在 DPT 中，recLSN 保持 $40$。$55$：$T_4$ 已提交（lastLSN $55$）。$60$：$T_5$ 的 lastLSN $60$；$P_8$ 以 recLSN $60$ 进入。结果：TT $= \set{T_4\colon 55\ \text{已提交},\ T_5\colon 60}$，DPT $= \set{P_5\colon 15, P_6\colon 40, P_7\colon 45, P_8\colon 60}$。唯一的失败事务是 $T_5$；$T_4$ 在重做后补一条 end 记录。重做从最小的 recLSN $15$ 开始——在检查点*之前*，因为 $P_5$ 自 LSN $15$ 起就是脏的，可能从未写到过盘上。
:::
:::

::: exercise 哪些记录会被重做？ {level=2 check="1"}
重做阶段，DPT 为 $\set{P_1\colon 20, P_2\colon 50}$，日志中有更新 $20$（$P_1$）、$30$（$P_2$）、$40$（$P_1$）、$50$（$P_2$）、$60$（$P_3$）。盘上 $P_1$ 的 pageLSN 为 $40$，$P_2$ 的为 $30$。实际被重新应用的记录有几条？为哪些记录必须读页？（输入被重新应用的条数。）
::: solution
- $20$（$P_1$）：必须读 $P_1$；pageLSN $40 \ge 20$，跳过。
- $30$（$P_2$）：recLSN $50 > 30$，不读页即跳过——$P_2$ 是在这次修改之后写到盘上的。
- $40$（$P_1$）：pageLSN $40 \ge 40$，跳过。
- $50$（$P_2$）：recLSN $50 \le 50$；读 $P_2$；pageLSN $30 < 50$：**重做**，pageLSN 变为 $50$。
- $60$（$P_3$）：$P_3$ 不在 DPT 中，说明它是在这次修改之后写出的；跳过。

恰好重新应用 $1$ 条记录，而只有 $P_1$ 与 $P_2$ 需要读。$P_2$ 的 recLSN 与它的 pageLSN 是自洽的：该页在修改 $30$ 之后写到盘上，又被修改 $50$ 重新弄脏。
:::
:::

::: exercise 恢复期间的崩溃 {level=2}
设 [[#ex-aries]] 中系统在撤销阶段中途再次崩溃，恰在 CLR $140$ 写到稳定存储之后、end 记录 $150$ 之前。描述第二次重启。
::: solution
分析扫到日志末尾（如今止于 $140$）：TT $= \set{T_1\colon 130,\ T_3\colon 140}$，两者皆为失败事务。重做重复历史，包括 CLR $130$（$B = 7$）与 $140$（$D = 8$），凡已落盘的按 pageLSN 跳过。撤销以 ToUndo $= \set{130, 140}$ 开始。$140$ 是 CLR 且 undoNextLSN 为空：为 $T_3$ 写 end 记录。$130$ 是 CLR，undoNextLSN 为 $50$：加入 $50$。然后 $50$ 与 $30$ 照旧撤销，写出新的 CLR 和 $T_1$ 的 end 记录。更新 $90$ 与 $70$ 不会被再撤销：CLR 把撤销从它们头上引开，正像 [[#prop-clr-bound]] 所保证的那样。最终状态不变。
:::
:::

::: exercise 逻辑重做 {level=2}
某系统对 LSN $70$、页 $P$ 上的一次修改记录的操作是"给 $X$ 加 $10$"（而不是前像后像），$X$ 此前为 $100$。该页在修改之后写到盘上，pageLSN 为 $70$，随后系统崩溃。说明重做若无视 pageLSN 会出什么事，[[#lem-pagelsn]] 又如何修正。为什么这类操作的撤销不需要任何检验就是安全的？
::: solution
盘上 $X = 110$。不带检验的重做会把"加 $10$"再加一遍，得 $120$——错了，因为该操作不幂等。带上检验，$\text{pageLSN} = 70 \ge 70$，记录被跳过，$X$ 保持 $110$。若该页*没有*写出（pageLSN $< 70$，盘上 $X = 100$），检验会让它被应用，得 $110$，与崩溃时刻一致。撤销不需要检验，因为 ARIES 只在重做把每个页带到崩溃时刻状态之后才撤销，彼处每个修改恰好存在一次；撤销随后把"减 $10$"施加一次并记一条 CLR，因而绝不重复。
:::
:::

::: exercise 成组提交 {#ex-group-commit level=2 check="16000"}
一次日志刷写耗时 $2$ ms。若每次提交各自强制刷写，最大提交速率是多少？若提交按 $32$ 个一组刷写呢？（输入以每秒提交数计的第二个速率。）
::: solution
一次提交一次刷写：至多 $1/0.002 = 500$ 个提交每秒。每次刷写含 $32$ 条提交记录：$32 \cdot 500 = 16\,000$ 每秒。代价是时延：事务可能要等凑满一组（或短定时器到期）才轮到刷写。所需带宽并不大——即便每秒 $16\,000$ 个提交、每个占 $1$ KiB 日志，也不过约 $16$ MB/s 的顺序写。
:::
:::

::: exercise 实现 ARIES 重启 {#ex-implement level=3}
为物理修改（前像与后像）写一个 [[#alg-aries]] 的 Python 模拟，并在 [[#ex-aries]] 上运行。
::: solution
日志就是与 [[#ex-aries]] 的表格完全一致的一个元组 `(lsn, txn, kind, page, item, before, after, prev, undo_next)` 列表，`disk` 按崩溃时在盘上的样子保存各页的数据项与 pageLSN。于是重启过程为：

```python
by_lsn = {r[0]: r for r in log}
tt, dpt = {}, {}                                          # 分析
for lsn, t, kind, page, *_ in log:
    if kind == "end":
        tt.pop(t); continue
    tt[t] = {"last": lsn, "status": "C" if kind == "commit" else "U"}
    if kind in ("update", "CLR") and page not in dpt:
        dpt[page] = lsn                                   # recLSN
for lsn, t, kind, page, item, before, after, *_ in log:   # 重做：重复历史
    if kind not in ("update", "CLR") or lsn < min(dpt.values()):
        continue
    if page not in dpt or dpt[page] > lsn or disk[page]["lsn"] >= lsn:
        print("redo skip", lsn); continue
    disk[page][item], disk[page]["lsn"] = after, lsn
    print("redo", lsn, item, "=", after)
next_lsn = 130                                            # 撤销失败事务
todo = {tt[t]["last"] for t in tt if tt[t]["status"] == "U"}
while todo:
    lsn = max(todo); todo.remove(lsn)
    _, t, kind, page, item, before, after, prev, undo_next = by_lsn[lsn]
    nxt = undo_next if kind == "CLR" else prev
    if kind == "update":
        disk[page][item], disk[page]["lsn"] = before, next_lsn
        by_lsn[next_lsn] = (next_lsn, t, "CLR", page, item, None, before, None, prev)
        print("CLR", next_lsn, "undoes", lsn, item, "=", before, "undoNext", prev)
        next_lsn += 10
    if nxt is None:
        print("end", next_lsn, t); next_lsn += 10
    else:
        todo.add(nxt)
print({k: v for p in disk.values() for k, v in p.items() if k != "lsn"})
```
