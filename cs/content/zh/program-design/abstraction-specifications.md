你几乎每天都在调用 `sorted`，却很可能从未读过它的源代码。在 CPython 中它是 Timsort（从 3.11 版起采用改进的 "powersort" 规则来选择归并方式），一种归并排序与插入排序的混合算法，由上千行 C 语言写成：对已经有序的游程有特殊处理，有一个"疾驰"（galloping）模式，还有精细的内存管理。这一切对你都无关紧要。你依赖的是一段简短的描述：*`sorted(xs)` 返回一个新列表，其中包含 `xs` 的各元素，按非递减顺序排列，且相等的元素保持原来的相对顺序。* 如果 CPython 的开发者明天把它换成某种更快但仍兑现这一承诺的实现，你的程序一行都不用改。

这种分离——用一段简短而精确的陈述说明一段代码*做什么*，立在使用它的人与实现它的人之间——是本章的主题，从某种意义上说，也是整个课程的主题。几十行的程序可以通过阅读来理解。几十万行的程序不行：没有人能把它装进脑子。只有当每个部分都能凭借一份远比自身短小的描述来使用、检验和替换时，这样的程序才可能被构建和维护。我们先讲过程抽象与规格说明的构成，然后学会比较规格说明、判定谁负责检查什么，最后学会用霍尔（Hoare）的断言逻辑对照规格说明来推理代码。

## 抽象：略去该略去的细节

在 [[programming-1/functions]] 中你已经见过单个函数的规格说明：调用者必须建立的前置条件，以及函数保证成立的后置条件。这里我们考察这一想法为何如此强大，以及如何有意识地运用它。

::: definition 抽象 {#def-abstraction}
**抽象**是对某物的描述，它刻意略去该物的部分细节，使得许多不同的东西符合同一描述、可以被同等对待。**过程抽象**是一个有名字的计算——一个函数——通过对其效果的描述而非其代码来使用。产生过程抽象的机制有两种：

- **参数化抽象**用参数代替特定的数据，使一个函数描述一整族计算（`hypotenuse(a, b)` 而不是"3–4 直角三角形的斜边"）；
- **规格化抽象**用一份规格说明取代函数体，使得每个满足该规格说明的实现都可以互相替换。
:::

参数化抽象就是你在把重复代码改写为函数时所做的事。规格化抽象更微妙，也更重要：它说的是，从调用者的角度看，函数*就是*它的规格说明。调用者可以假设规格说明所承诺的一切，仅此而已；作为交换，实现者可以改变规格说明没有提到的任何东西。

利斯科夫（Liskov）与古特格（Guttag）——他们的教科书塑造了这部分内容的讲授方式——指出了这种安排的两点好处。

- **局部性。** 程序的一部分可以在不检查其所用部分的代码的情况下被阅读、编写和检验——只依据它们的规格说明。要确信一个使用 `sorted` 的函数是正确的，你需要的是那段描述 `sorted` 的文字，而不是实现它的上千行代码。
- **可修改性。** 一个部分可以被重新实现，而不改变使用它的部分，只要新的实现满足同一份规格说明。

一旦调用者依赖了当前实现恰好具备、而规格说明并未承诺的东西，这两个好处便同时失效。依赖实现碰巧的相等元素返回顺序、碰巧的运行时间、或错误消息的确切措辞的程序，都在悄悄加宽接口；实现的下一次正确改动就会把它弄坏。

::: intuition 规格说明是一堵开了窗的墙
把每个函数想象成墙后的一个箱子。规格说明是墙上的一扇窗：调用者恰好看到它所显示的东西，而实现者在墙后可以自由地重新布置一切。好的设计在很大程度上是选择窗户的艺术——窗要足够大，调用者才能完成工作；又要足够小，实现者才能保住自由。
:::

## 书写规格说明

对只计算并返回值的函数，一个前置条件加一个后置条件就够了。真实的函数还会改变东西——修改实参、写文件、抛出异常——规格说明必须把这一点说清楚。我们采用一种可追溯到利斯科夫与古特格的三段式。

::: definition 规格说明 {#def-spec}
一个函数的**规格说明**包含三个子句。

- **Requires**（前置条件）：允许调用该函数时，实参与程序状态必须满足的条件。省略该子句意为"不要求任何条件"。
- **Modifies**：该函数可能改变的实参和其他对象。凡未列出的都必须保持原样。省略该子句意为函数不改变任何东西。
- **Effects**（后置条件）：返回值、*Modifies* 所列各对象结束时的状态，以及抛出的异常，都用实参*进入时*的值来描述。

一个函数**满足**一份规格说明，当且仅当：每个在满足 Requires 子句的状态下发起的调用都会终止，不改变 Modifies 子句之外的任何东西，并且产生所述的效果。违反 Requires 子句的调用在规格说明之外：无论发生什么，都怪不到函数头上。
:::

在 Python 中，规格说明写在文档字符串里。没有专门的语法；重要的是三个子句都在，并且精确。

::: example 为整数平方根写规格说明 {#ex-isqrt}
为一个返回自然数的整数平方根的函数写出规格说明和实现，并对照规格说明测试该实现。
::: solution
"整数平方根"是含糊的：$10$ 的平方根是 $3$ 还是 $3.16$？$8$ 的平方根向上取整还是向下取整？规格说明通过陈述结果的一个性质而非计算方法来消除含糊。

```python
def isqrt(n):
    """Integer square root.

    Requires: n is an int and n >= 0.
    Effects:  returns the int r with r * r <= n < (r + 1) * (r + 1).
    """
    r = 0
    while (r + 1) * (r + 1) <= n:
        r += 1
    return r

def meets_spec(n, r):
    """True if r is an acceptable result of isqrt(n)."""
    return isinstance(r, int) and r * r <= n < (r + 1) * (r + 1)

print([isqrt(n) for n in range(10)])
print(all(meets_spec(n, isqrt(n)) for n in range(10_000)))
```

```console
$ python3 isqrt.py
[0, 1, 1, 1, 2, 2, 2, 2, 2, 3]
True
```

值得注意的有三点。第一，Effects 子句唯一地确定了答案：对每个 $n \ge 0$，恰有一个自然数 $r$ 满足 $r^2 \le n < (r+1)^2$，即 $\lfloor\sqrt n\rfloor$。第二，规格说明没有规定*如何*求 $r$；这个实现向上计数，约需 $\sqrt n$ 次迭代，而 [[#exr-isqrt-fast]] 会把它换成一个快得多的实现，且不改动任何一个调用者。第三，由于 Effects 子句是一个可检验的性质，它可以被直接改造成测试判断器 `meets_spec`，接受任何正确结果——这就是 [[programming-1/testing-debugging]] 中随机测试的基础。
:::
:::

### 操作式与陈述式规格说明

`isqrt` 的规格说明是**陈述式的**：它陈述输入与输出之间的关系。**操作式的**规格说明则会描述一个过程（"从 $r = 0$ 开始，当……时增大 $r$"）。操作式规格说明很诱人，因为代码一旦存在它就很好写，但它们是糟糕的窗户：它们泄露了实现，并排除了其他一切实现。一般的原则是：规定*做什么*，把*怎么做*写进函数体内部的注释里，那里只有实现者会看。

### 确定与欠确定的规格说明

规格说明不必钉死唯一的结果。考虑在一个可能多次含有某个值的列表中查找该值。

```python
def index_of(xs, x):
    """Requires: x occurs in xs.
    Effects:  returns some i with xs[i] == x."""
    for i in range(len(xs)):
        if xs[i] == x:
            return i

def index_of_from_end(xs, x):
    """Same specification as index_of."""
    for i in range(len(xs) - 1, -1, -1):
        if xs[i] == x:
            return i

xs = [5, 7, 5, 2]
print(index_of(xs, 5), index_of_from_end(xs, 5))
print(index_of(xs, 2), index_of_from_end(xs, 2))
```

```console
$ python3 indexof.py
0 2
3 3
```

这个规格说明是**欠确定的（underdetermined）**：对某些输入它允许多于一个结果。两个函数都满足它，尽管它们在 `[5, 7, 5, 2]` 上意见不一。欠确定不是草率，而是刻意赠予实现者的自由——例如，一个基于哈希的实现可能最快找到的恰好是*某个*出现位置。代价由调用者和测试者支付：调用者必须使用返回的任意下标，而断言 `index_of([5, 7, 5, 2], 5) == 0` 的测试是错的，因为它检验的并非规格说明承诺的性质。正确的测试是 `xs[index_of(xs, 5)] == 5`。

### 说明改变的规格

当函数改变某个实参时，Modifies 子句要写明，而 Effects 子句必须用初始状态来描述最终状态。一个方便的记号——从利斯科夫与古特格处借用——把进入时的值写作 $xs_{\text{pre}}$，把退出时的值写作 $xs_{\text{post}}$。

```python
def remove_all(xs, x):
    """Modifies: xs.
    Effects:  xs_post is xs_pre with every element equal to x removed,
              the other elements kept in their original order."""
    xs[:] = [y for y in xs if y != x]   # 切片赋值：改变 xs 本身

def without(xs, x):
    """Effects: returns a new list: xs with every element equal to x removed."""
    return [y for y in xs if y != x]

a = [1, 2, 1, 3]
b = a                     # b 和 a 引用同一个列表
print(without(a, 1), a)
remove_all(a, 1)
print(a, b)
```

```console
$ python3 removeall.py
[2, 3] [1, 2, 1, 3]
[2, 3] [2, 3]
```

两份规格说明描述同样的过滤，契约却完全不同。`without` 什么都不修改，所以调用者可以依赖之后的 `a` 保持不变；`remove_all` 修改它的实参，所以*每个*绑定到那个列表的名字——这里还有 `b`——都会看到这次改变，正如 [[programming-1/sequences]] 中别名所做的那样。因此 Modifies 子句是调用者最需要看见的那扇窗户的一部分：一个改变调用者以为安全的对象的函数，是最令人困惑的缺陷的最常见来源之一。

::: warning 缺少的子句也是一项承诺
省略 Modifies 子句并非中立：它承诺什么都不改变。一个"作为副作用"原地排序其参数的函数，如果它的文档字符串只描述返回值，就违背了自己的规格说明，即使返回的值是对的。同样，如果一个函数可能抛出调用者应当处理的异常——畸形输入的 `ValueError`、缺失键的 `KeyError`——Effects 子句就必须说明何时抛出。
:::

::: quiz
`def largest(xs)` 的规格说明是"Requires: `xs` 是一个非空数的列表。Effects: 返回 `xs` 的一个不小于 `xs` 每个元素的元素。"以下哪项正确？
- [ ] 对空列表，实现可以返回 `None`，以便调用者检测它。
- [ ] 实现可以原地排序 `xs` 并返回它的最后一个元素。
- [x] `largest([3, 3])` 必须返回 `3`。
- [ ] 测试 `assert largest([2, 9, 4]) is not None` 足以说明实现满足规格说明。
::: solution
规格说明没有 Modifies 子句，因此它承诺 `xs` 不被改变：原地排序违反它，即使返回的值是对的。由于前置条件排除了空列表，规格说明对 `largest([])` 未置一词；那里返回 `None` 是*允许的*，但调用者不可依赖它，因为另一个正确的实现可能改为抛出异常。对 `[3, 3]`，唯一不小于每个元素的元素是 `3`，所以结果被确定。最后一个测试几乎没有检验任何东西：返回 `xs[0]` 的实现也能通过。
:::
:::

## 比较规格说明

一份规格说明何时"好于"另一份？一个规格说明的实现何时可以在另一个规格说明被期待的地方使用？答案是一个精确的序关系，我们在 [[program-design/inheritance-polymorphism]] 讨论子类、在 [[program-design/types-interfaces]] 讨论类型时还会再用到它。

把规格说明 $S$ 看作一对 $(P_S, Q_S)$：关于输入 $x$ 的前置条件 $P_S(x)$，以及联系输入 $x$ 与结果 $y$ 的后置条件 $Q_S(x, y)$（对有副作用的函数，$y$ 包含最终状态）。

::: definition 更强的与更弱的规格说明 {#def-stronger}
规格说明 $S_2$ **强于**（或**精化**）$S_1$，记作 $S_2 \sqsupseteq S_1$，若

1. 它的前置条件不比 $S_1$ 的更强：对每个 $x$，$P_{S_1}(x) \implies P_{S_2}(x)$；并且
2. 在 $S_1$ 允许的输入上，它的后置条件不比 $S_1$ 的更弱：对每个满足 $P_{S_1}(x)$ 的 $x$ 与每个 $y$，$Q_{S_2}(x, y) \implies Q_{S_1}(x, y)$。

换句话说：$S_2$ 对调用者*要求不多*，而向调用者*承诺不少*。
:::

第一个条件的方向常令人意外。更强的规格说明有*更弱的*前置条件，因为接受更多输入是对调用者更强的承诺。

::: theorem 更强的规格说明可以替换 {#thm-substitute}
若 $S_2 \sqsupseteq S_1$，则每个满足 $S_2$ 的实现也满足 $S_1$。因此，针对 $S_1$ 编写的调用者，在被调函数替换为 $S_2$ 的任一实现后仍然正确。
:::

::: proof
设 $f$ 满足 $S_2$，考虑满足 $P_{S_1}(x)$ 的调用 $f(x)$。由条件 1，$P_{S_2}(x)$ 成立，于是——因为 $f$ 满足 $S_2$——该调用终止，得到某个满足 $Q_{S_2}(x, y)$ 的结果 $y$。由条件 2，作用于这个（满足 $P_{S_1}$ 的）$x$ 与这个 $y$，得到 $Q_{S_1}(x, y)$。于是每个满足 $P_{S_1}$ 的调用都终止于一个满足 $Q_{S_1}$ 的结果：$f$ 满足 $S_1$。

至于第二句，针对 $S_1$ 编写的调用者只发起满足 $P_{S_1}$ 的调用，也只依赖事后 $Q_{S_1}$ 成立；我们刚刚证明，$S_2$ 的任何实现都能兑现这一点。
:::

注意条件 2 只对 $S_1$ 允许的输入量化。在这些输入之外，$S_2$ 可以承诺任何东西，因为 $S_1$ 的调用者从不会走到那里。

::: example 查找的四份规格说明 {#ex-compare-specs}
比较 `find(xs, x)` 的这几份规格说明，其中 `xs` 是列表：

- $A$：要求 `x` 出现在 `xs` 中；返回某个满足 `xs[i] == x` 的 `i`。
- $B$：要求 `x` 出现在 `xs` 中；返回满足 `xs[i] == x` 的最小 `i`。
- $C$：不作要求；若 `x` 出现在 `xs` 中则返回某个满足 `xs[i] == x` 的 `i`，否则返回 `-1`。
- $D$：不作要求；若 `x` 出现在 `xs` 中则返回满足 `xs[i] == x` 的最小 `i`，否则返回 `-1`。
::: solution
对每一对检查 [[#def-stronger]] 的两个条件。

- $B \sqsupseteq A$：前置条件相同，而"满足 `xs[i] == x` 的最小下标"特别地是"满足 `xs[i] == x` 的某个下标"。
- $C \sqsupseteq A$：$C$ 不作任何要求，这被任何条件蕴含；在 `x` 出现（即 $A$ 允许）的输入上，$C$ 的后置条件恰为 $A$ 的。
- $D \sqsupseteq B$、$D \sqsupseteq C$ 与 $D \sqsupseteq A$ 由同样的推理成立：$D$ 有最弱的前置条件和最强的后置条件。
- $B$ 与 $C$ 是**不可比的**：$C$ 接受 $B$ 拒绝的输入，故 $B \not\sqsupseteq C$；而 $C$ 可能返回非最小的下标，$B$ 却必须避免，故 $C \not\sqsupseteq B$。

四份规格说明构成一个菱形，$A$ 在底部，$D$ 在顶部：

| | 更弱的前置条件 ↑ | 更强的后置条件 ↑ |
|---|---|---|
| $D$ | 无 | 最小下标或 $-1$ |
| $B$ | `x` 在 `xs` 中 | 最小下标 |
| $C$ | 无 | 任意下标或 $-1$ |
| $A$ | `x` 在 `xs` 中 | 任意下标 |

由 [[#thm-substitute]]，Python 的内建 `xs.index(x)`——它返回最小下标，且在 `x` 缺席时抛出 `ValueError`——同时满足 $A$ 和 $B$，但它不满足 $C$ 或 $D$，因为后两者要求 `-1` 而不是异常。
:::
:::

条件 1 是集合的包含：$S_1$ 允许的输入集必须落在 $S_2$ 允许的输入集之内。

::: widget venn
sets: 2
labels: P; R
expr: P - R
caption: 设 $P$ 为 $S_1$ 的前置条件允许的输入，$R$ 为 $S_2$ 的前置条件允许的输入。阴影区域 $P \setminus R$ 装着 $S_1$ 的调用者可能传入、而 $S_2$ 禁止的输入。仅当该区域为*空*——即 $P \subseteq R$——时，$S_2$ 才能替换 $S_1$。键入 `R - P` 查看 $S_2$ 在 $S_1$ 所需之外还接受的输入：在那里 $S_2$ 可以自由承诺任何东西。
:::

更强的规格说明并不总是更好的。更强的规格说明对调用者更有用，但更难实现、也更难守住：每一条额外的承诺都是对今后所有版本的一个约束。因此设计者追求的是恰好满足其实际拥有的调用者的那份最弱规格说明。例如，Python 的文档承诺 `sorted` 是稳定的——这是一次强化，它排除了许多快速排序算法，之所以采纳，是因为稳定性常常是必要的——但它小心翼翼地不承诺 `set` 的迭代顺序。

## 谁来检查前置条件？

规格说明不作任何要求的函数是**全函数**：它对每个输入都必须做出符合规定的事情。带有非平凡前置条件的是**偏函数**。每个偏函数都带来一个设计问题：前置条件被违反时应该发生什么？

有三种合理的回答，选择是设计的一部分。

1. **强化规格说明**，使函数成为全函数，办法是对每个输入都规定发生的事情——通常是抛出异常。`math.sqrt(-1)` 抛出 `ValueError: math domain error`；这一行为写在文档里，调用者可以依赖它。
2. **检查并快速失败**，不改变规格说明：保留前置条件，但用 `assert` 检验它，一旦失败立即停止。检查是调试的辅助，不是承诺；调用者仍然必须建立前置条件。
3. **信任调用者**：既不检查也不承诺。当检查代价太高时，这是正确的选择。

第三种情形比听起来更常见，因为检查前置条件的代价可能高于干活本身。

::: example 检查的代价 {#ex-check-cost}
二分查找通过反复折半取值可能所在范围，在有序列表中找到一个值。请对照一份明确写出的前置条件编写它，并比较查找的代价与检查前置条件的代价。
::: solution
```python
def search(xs, x):
    """Requires: xs is sorted in non-decreasing order.
    Effects:  returns some i with xs[i] == x, or -1 if x does not occur."""
    lo, hi = 0, len(xs) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if xs[mid] < x:
            lo = mid + 1          # x 若存在，则在 mid 右侧
        elif xs[mid] > x:
            hi = mid - 1          # x 若存在，则在 mid 左侧
        else:
            return mid
    return -1

print(search([1, 3, 4, 7, 9], 7), search([1, 3, 4, 7, 9], 5))
print(search([9, 1, 7, 3], 9))    # 前置条件被违反
```

```console
$ python3 search.py
3 -1
-1
```

对一个含 $n$ 个元素的有序列表，循环至多执行 $\lfloor \log_2 n\rfloor + 1$ 次，如 [[data-structures/asymptotic-analysis]] 所示；当 $n = 2^{20} \approx 10^6$ 时是 $21$ 次迭代。检查有序性，`all(xs[i] <= xs[i + 1] for i in range(len(xs) - 1))`，需要 $n - 1 = 1{,}048{,}575$ 次比较——是查找的五十万倍。一个检查前置条件的二分查找会比根本不需要前置条件的线性扫描更慢。

最后一行显示了信任调用者的代价。在无序列表 `[9, 1, 7, 3]` 上，查找把 $9$ 与 $1$、$7$、$3$ 比较，每次都得出的结论是 $9$ 一定在更右边，于是尽管 $9$ 在下标 $0$ 处，仍报告 `-1`。被违反的前置条件不一定让程序崩溃；它可能悄悄给出一个貌似合理的错误答案，这是最糟糕的失败方式。这就是为什么前置条件必须写在每个调用者都会看到的地方。
:::
:::

把这些决定明确化的纪律——调用者保证前置条件，被调者保证后置条件，双方都不重复检查对方的义务——由梅耶（Meyer）命名为**契约式设计**，他在 1980 年代中期把它做进了 Eiffel 语言，用 `require` 与 `ensure` 子句实现，在测试期间可在运行时检查，在生产环境中可以关闭。Python 没有这样的子句，但 `assert` 扮演着同样的角色（带有同样的开关：`python3 -O` 会移除断言，见 [[programming-1/testing-debugging]]）。

::: warning 防御式编程不能替代规格说明
"到处检查一切"听起来安全，却会在两个方面出错。调用者和被调者里重复的检查会随着代码的修改而彼此漂移，直到一方拒绝另一方接受的东西。而悄悄"修复"坏输入的函数——比如对负数的平方根返回 `0`——会把调用者的缺陷变成离起因很远的错误答案。对每个函数分别决定：某个条件是前置条件（调用者的职责；至多用 `assert` 检验），还是规定行为的一部分（抛出有文档的异常），并把决定写进规格说明。
:::

### 会运行的规格说明

例子是规格说明的极好补充：它们使之具体，并能抓住误读。Python 标准的 `doctest` 模块更进一步：它在文档字符串中找到写成交互式会话的例子，运行它们并比较输出。

```python
def clamp(x, lo, hi):
    """Requires: lo <= hi.
    Effects:  returns the element of [lo, hi] nearest to x.

    >>> clamp(5, 0, 10)
    5
    >>> clamp(-3, 0, 10)
    0
    >>> clamp(12, 0, 10)
    10
    """
    return max(lo, min(x, hi))

if __name__ == "__main__":
    import doctest
    print(doctest.testmod())
```

```console
$ python3 clamp.py
TestResults(failed=0, attempted=3)
```

这些例子不能取代 Effects 子句——三个例子没有说明 `x = 7.5` 时发生什么——但由于它们被自动检查，它们不会悄悄过时。（测试 `if __name__ == "__main__"` 使得只有直接运行文件时才运行这些例子，被导入时不运行；[[program-design/modules-patterns]] 会解释它。）

## 依据契约的推理：霍尔三元组

规格说明让我们在不读被调者的情况下推理调用者。要检验一个函数的*函数体*满足它自己的规格说明，我们需要一种对语句推理的方法。1969 年，霍尔（Hoare）为此提出了一种记号和一小套规则。

::: definition 霍尔三元组 {#def-hoare}
霍尔三元组 $\{P\}\ S\ \{Q\}$，其中 $S$ 是语句，$P$ 与 $Q$ 是关于程序变量的断言，意思是：*如果在满足 $P$ 的状态下执行 $S$，且 $S$ 终止，则终止时的状态满足 $Q$。* $P$ 是三元组的**前置条件**，$Q$ 是**后置条件**。这是**部分正确性**；**完全正确性**再加上要求：只要 $S$ 从满足 $P$ 的状态开始执行，它就必须终止。
:::

一个函数的规格说明就是其函数体的一个三元组。下面的规则让我们能逐块地建立三元组。用 $Q[e/x]$ 表示把断言 $Q$ 中变量 $x$ 的每个自由出现替换为表达式 $e$ 后得到的断言。

::: definition 霍尔逻辑的规则 {#def-hoare-rules}
对一门带有赋值、顺序、`if` 与 `while`（表达式无副作用）的语言：

- **赋值：** $\{Q[e/x]\}\ x = e\ \{Q\}$。
- **顺序：** 由 $\{P\}\ S_1\ \{R\}$ 与 $\{R\}\ S_2\ \{Q\}$ 推出 $\{P\}\ S_1;\,S_2\ \{Q\}$。
- **条件：** 由 $\{P \land b\}\ S_1\ \{Q\}$ 与 $\{P \land \lnot b\}\ S_2\ \{Q\}$ 推出 $\{P\}$ `if b: S1 else: S2` $\{Q\}$。
- **循环：** 由 $\{I \land b\}\ S\ \{I\}$ 推出 $\{I\}$ `while b: S` $\{I \land \lnot b\}$。断言 $I$ 是**循环不变式**。
- **蕴含：** 由 $P' \implies P$、$\{P\}\ S\ \{Q\}$ 与 $Q \implies Q'$ 推出 $\{P'\}\ S\ \{Q'\}$。
:::

赋值规则初看像是倒着来的：要知道 `x = e` *之后*什么为真，你得先对*之前的* `e` 知道同样的事情。它之所以正确，是因为赋值之后，$x$ 恰好具有 $e$ 之前具有的值。例如 $\{y + 1 > 0\}\ x = y + 1\ \{x > 0\}$。这提示我们从后置条件出发反向工作，在每个语句处算出它之前必须成立什么。

蕴含规则就是 [[#def-stronger]] 的再现：加强三元组的前置条件或减弱其后置条件，三元组仍然有效。它的命题逻辑内核是一条你可以自行检验的重言式。

::: widget truthtable
formula: ((r -> p) & (p -> q) & (q -> s)) -> (r -> s)
caption: 蕴含规则背后的逻辑。把 $p$ 与 $q$ 读作一个有效三元组的前置条件与后置条件，$r$ 读作更强的前置条件（$r \to p$），$s$ 读作更弱的后置条件（$q \to s$）。最后一列在全部十六行中为真：只要三个前提成立，$r \to s$ 也成立。把 `(q -> s)` 换成 `(s -> q)`——一个*更强的*后置条件——某些行就变为假：你不能承诺多于语句所保证的东西。
:::

::: example 交换两个变量 {#ex-swap}
证明 $\{x = a \land y = b\}$ `t = x; x = y; y = t` $\{x = b \land y = a\}$，其中 $a$ 与 $b$ 是固定值（程序不会提到的逻辑变量）。
::: solution
从后置条件 $Q \equiv x = b \land y = a$ 出发反向工作，对从最后一条到第一条的每个语句应用赋值规则。

1. 在 `y = t` 之前，我们需要 $Q[t/y] \equiv x = b \land t = a$。
2. 在 `x = y` 之前，我们需要 $(x = b \land t = a)[y/x] \equiv y = b \land t = a$。
3. 在 `t = x` 之前，我们需要 $(y = b \land t = a)[x/t] \equiv y = b \land x = a$。

由顺序规则，$\{y = b \land x = a\}$ `t = x; x = y; y = t` $\{x = b \land y = a\}$，而算出的前置条件恰好就是给定的前置条件（只是合取项次序不同）。Python 的 `x, y = y, x` 一步就完成同样的事：它先对元组 `(y, x)` 求值，然后再对两个名字分别赋值——这正是带同时替换的多重赋值规则 $\{Q[e_1/x, e_2/y]\}$ `x, y = e1, e2` $\{Q\}$ 所刻画的。
:::
:::

::: example 整数平方根是正确的 {#ex-isqrt-proof}
证明 [[#ex-isqrt]] 中 `isqrt` 的函数体满足它的规格说明。
::: solution
函数体是 `r = 0; while (r + 1) * (r + 1) <= n: r += 1; return r`。取循环不变式

$$
I \equiv r \ge 0 \land r^2 \le n.
$$

**初始化。** 由赋值规则，$\{0 \ge 0 \land 0^2 \le n\}$ `r = 0` $\{I\}$，而 $0 \ge 0 \land 0 \le n$ 由前置条件 $n \ge 0$ 推出。由蕴含规则，$\{n \ge 0\}$ `r = 0` $\{I\}$。

**保持。** 我们需要 $\{I \land (r+1)^2 \le n\}$ `r += 1` $\{I\}$。由赋值规则（`r += 1` 就是 `r = r + 1`），最弱前置条件是 $I[r+1/r] \equiv r + 1 \ge 0 \land (r+1)^2 \le n$，而它被 $I \land (r+1)^2 \le n$ 蕴含（因为 $r \ge 0$ 给出 $r + 1 \ge 0$）。于是该三元组由蕴含规则成立。

**退出。** 由循环规则，循环结束后 $I \land \lnot\bigl((r+1)^2 \le n\bigr)$ 成立，即 $r \ge 0 \land r^2 \le n < (r+1)^2$——恰好是 Effects 子句。

**终止。** 如前所述，霍尔逻辑只给出部分正确性，所以我们要用**变体（variant）**另行论证终止：只要不变式成立，量 $n - r^2$ 就是自然数，而每次迭代都使 $r$ 增大，从而严格减小 $n - r^2$。自然数不能永远减小，所以循环会停止，恰好在 $\lfloor\sqrt n\rfloor$ 次迭代之后。这就是 [[programming-1/control-flow]] 中的方法，写成霍尔的记号。
:::
:::

霍尔逻辑很少在日常代码中被完整写出，但它的思想被不断使用：从不变式的角度思考循环、从你需要的东西反向工作、以及认识到更强的前置条件使三元组更容易证明。Dafny、Why3 与 Frama-C 这类工具为真实语言实现了这套逻辑的自动化，这是 [[software-engineering]] 与 [[programming-languages]] 的主题。

::: quiz
哪个前置条件 $P$ 使 $\{P\}$ `x = 2 * x + 1` $\{x > 7\}$ 有效，且尽可能弱？
- [ ] $x > 7$
- [x] $x > 3$
- [ ] $x > 4$
- [ ] $2x + 1 > 7$ 不被允许，因为它两次提到 $x$
::: solution
赋值规则给出最弱前置条件 $(x > 7)[2x+1/x] \equiv 2x + 1 > 7 \equiv x > 3$（对整数与实数同样成立）。前置条件 $x > 7$ 也行——由蕴含规则——但它比必要的更强；$x > 4$ 亦然。两次提到 $x$ 毫无问题。
:::
:::

::: history
程序员从一开始就为例程编写正确性论证：图灵（Turing）的三页笔记《Checking a large routine》（1949）已经用关于程序状态的断言来标注一段程序。弗洛伊德（Floyd）的《Assigning meanings to programs》（1967）把断言附在流程图的边上，而霍尔（Hoare）的《An axiomatic basis for computer programming》（*Communications of the ACM*，1969）把它们化成了这里使用的三元组与规则。前一年，迪杰斯特拉（Dijkstra）的信《Go To Statement Considered Harmful》（*CACM*，1968）论证了不加限制的跳转会使这类推理难以实行，这推动了语言走向霍尔规则所描述的结构化 `if` 与 `while`；迪杰斯特拉的最弱前置条件（1975）把"从后置条件反向工作"变成了一套演算。帕纳斯（Parnas）的《A technique for software module specification with examples》（*CACM*，1972）把规格说明应用到整个模块，利斯科夫与古特格的《Abstraction and Specification in Program Development》（1986）让 requires/modifies/effects 成为教学标准，而梅耶命名了契约式设计，并把它做进了 Eiffel（见他的《Object-Oriented Software Construction》，1988）。
:::

## 后续内容

规格说明是贯穿本课程的那根线。[[program-design/abstract-data-types]] 刻画整个类型而非单个函数，由表示不变式扮演数据的循环不变式的角色。[[program-design/classes-objects]] 把这些类型打包为类，[[program-design/inheritance-polymorphism]] 把 [[#thm-substitute]] 应用于子类（利斯科夫替换原则），而 [[program-design/types-interfaces]] 让类型检查器在程序运行之前校验每份规格说明中最简单的部分——类型。在 [[software-engineering]] 中，规格说明向上扩展为需求与团队之间的接口，形式化验证则把上一节的霍尔逻辑机械化。

::: summary
- **规格化抽象**让调用者仅凭函数的规格说明来使用函数，带来**局部性**（一次检验一部分）与**可修改性**（重新实现而不破坏调用者）（[[#def-abstraction]]）。
- 规格说明有 **Requires**、**Modifies** 与 **Effects** 三个子句；缺省的 Modifies 子句承诺什么都不改变（[[#def-spec]]）。
- 优先采用**陈述式**规格说明（结果的性质）而非操作式的；**欠确定的**规格说明留给实现者自由，测试不得假设多于承诺的东西。
- 若 $S_2$ 要求不多、承诺不少，则它**强于** $S_1$；更强规格说明的实现可以替换更弱规格说明的实现（[[#def-stronger]]、[[#thm-substitute]]）。
- 被违反的前置条件可能给出貌似合理的错误答案；对每个条件分别决定是文档化一个异常、用 `assert` 检验，还是在检查代价太高时信任调用者（二分查找）。
- **霍尔三元组** $\{P\}\,S\,\{Q\}$ 陈述部分正确性；赋值规则通过替换反向工作，循环规则需要一个循环不变式，而终止需要一个单独的变体（[[#def-hoare-rules]]）。
:::

## 习题

::: exercise 写出规格说明 {level=1}
为下列函数写出 Requires、Modifies 与 Effects 子句：(a) 函数 `average(xs)`，返回数列表的算术平均值；(b) 类方法式函数 `push_all(stack, items)`，把 `items` 的每个元素追加到列表 `stack`；(c) 函数 `parse_int(s)`，把十进制数字字符串转换为整数，对其他任何输入抛出 `ValueError`。
::: solution
(a) Requires：`xs` 是一个非空数的列表。Effects：返回 `sum(xs) / len(xs)`。（也可以不作要求，并规定空列表时抛出 `ValueError`——一份更强的全函数规格说明。）

(b) Modifies：`stack`。Effects：$stack_{\text{post}}$ 是 $stack_{\text{pre}}$ 之后依序接上 `items` 的各元素；`items` 不变（它不在 Modifies 子句里，这是蕴含的，但写出来有助于读者）。

(c) Requires：无。Effects：若 `s` 是一个仅由字符 `0`–`9` 组成的非空字符串，返回它按 10 进制表示的整数；否则抛出 `ValueError`。（对每个字符串都规定行为，使函数成为全函数。）
:::
:::

::: exercise 哪些更强？ {level=1 check="2"}
设 $S$ 为：要求 `n > 0`；返回满足 `k >= n` 的整数 `k`。考虑：(i) 要求 `n > 0`，返回 `n`；(ii) 要求 `n > 10`，返回 `n + 1`；(iii) 不作要求，返回 `abs(n) + 1`；(iv) 要求 `n > 0`，返回满足 `k >= n - 1` 的整数 `k`。(i)–(iv) 中有几份强于 $S$？（输入数目。）
::: solution
(i) 前置条件相同；返回 `n` 满足 `k >= n`。更强。
(ii) 它的前置条件 `n > 10` *强于* `n > 0`（它拒绝 `n = 5`，而 $S$ 允许），故条件 1 不成立。不强于。
(iii) 不作要求，这被任何前置条件蕴含；当 `n > 0` 时，`abs(n) + 1 = n + 1 >= n`。更强。
(iv) 前置条件相同，但 `k = n - 1` 被 (iv) 允许而不被 $S$ 允许，故条件 2 不成立。不强于。
共两份：(i) 与 (iii)。
:::
:::

::: exercise 反向工作 {level=1 check="7"}
用赋值规则与顺序规则计算 `x = x + 3; y = 2 * x` 关于后置条件 $y = 20$ 的最弱前置条件。它在 $x$ 取何值时成立？（输入那个值。）
::: solution
在 `y = 2 * x` 之前需要 $(y = 20)[2x/y] \equiv 2x = 20 \equiv x = 10$。在 `x = x + 3` 之前需要 $(x = 10)[x+3/x] \equiv x + 3 = 10 \equiv x = 7$。所以最弱前置条件是 $x = 7$。
:::
:::

::: exercise 不用临时变量的交换 {level=2}
用霍尔的规则证明：对整数，$\{x = a \land y = b\}$ `x = x + y; y = x - y; x = x - y` $\{x = b \land y = a\}$。为什么同样的论证对 Python 浮点数不成立？
::: solution
从 $Q \equiv x = b \land y = a$ 反向工作。
在 `x = x - y` 之前：$x - y = b \land y = a$。
在 `y = x - y` 之前：$x - (x - y) = b \land x - y = a$，即 $y = b \land x - y = a$。
在 `x = x + y` 之前：$y = b \land (x + y) - y = a$，即 $y = b \land x = a$。
这正是给定的前置条件，所以由顺序规则三元组成立。上述代数用了 $(x + y) - y = x$ 与 $x - (x - y) = y$，它们对 Python 的无限精度整数成立。对浮点数，加法要舍入：取 `x = 1e16` 与 `y = 1.0`，`x + y` 仍是 `1e16`，于是程序结束时 `y == 1e16`、`x == 0.0`，并没有交换（见 [[computer-systems/floating-point]]）。霍尔逻辑的规则只与它所推理的数据的代数一样好。
:::
:::

::: exercise 说得太多的测试 {level=2}
针对上面 `index_of` 的欠确定规格说明，一位同事写了测试 `assert index_of([4, 4], 4) == 0` 和 `assert index_of([1, 2, 3], 3) == 2`。哪个测试是正当的？把另一个改写成恰好检验规格说明所承诺的东西，并解释若 `index_of` 被换成 `index_of_from_end`，原来的测试会怎样。
::: solution
第二个测试是正当的：`3` 只出现在下标 `2` 处，规格说明确定了结果。第一个说得过多，因为 `0` 和 `1` 都可接受。一个正确的版本是

```python
i = index_of([4, 4], 4)
assert i in (0, 1)
```

或者更一般地，`xs = [4, 4]; assert xs[index_of(xs, 4)] == 4`。换成 `index_of_from_end` 后，原来的第一个测试会失败，尽管新函数满足规格说明——这是一次误报，它会促使开发者去"修复"一个正确的函数，或者更糟，在没有人决定的情况下强化规格说明。
:::
:::

::: exercise 检查要花多少？ {level=2 check="1048575"}
对 $n = 2^{20}$ 个元素的有序列表做二分查找（如 [[#ex-check-cost]]），外面包着 `assert all(xs[i] <= xs[i + 1] for i in range(len(xs) - 1))`。当列表确实有序时，这个断言做了多少次元素比较？（输入数目。）把这个断言留在测试构建里合理吗？在生产构建里呢？
::: solution
生成器把 $n - 1$ 对相邻元素各比较一次；`all` 只在失败时提前停止，所以对有序列表它做 $n - 1 = 2^{20} - 1 = 1{,}048{,}575$ 次比较，而查找本身至多 $21$ 次。在测试构建里，抓住误用比速度重要，这是可以接受的（有些项目只对部分调用检查昂贵的不变式）。在生产环境中它会毁掉二分查找的意义；用 `python3 -O` 运行以移除它，或者删掉它并把前置条件写进文档。
:::
:::

::: exercise 精化是预序关系 {level=3}
证明 [[#def-stronger]] 的关系 $\sqsupseteq$ 是自反的（$S \sqsupseteq S$）且传递的（若 $S_3 \sqsupseteq S_2$ 且 $S_2 \sqsupseteq S_1$，则 $S_3 \sqsupseteq S_1$）。给出两个不同的规格说明 $S \ne T$，使得 $S \sqsupseteq T$ 且 $T \sqsupseteq S$，说明它不是反对称的。
::: solution
**自反。** 对所有 $x$ 有 $P_S(x) \implies P_S(x)$，对所有 $x$ 与 $y$ 有 $Q_S(x,y) \implies Q_S(x,y)$。

**传递。** 条件 1：$P_{S_1}(x) \implies P_{S_2}(x) \implies P_{S_3}(x)$。条件 2：设 $x$ 满足 $P_{S_1}$，并设 $Q_{S_3}(x, y)$。由 $S_2 \sqsupseteq S_1$ 的条件 1，$x$ 满足 $P_{S_2}$，于是 $S_3 \sqsupseteq S_2$（条件 2）给出 $Q_{S_2}(x, y)$，再由 $S_2 \sqsupseteq S_1$ 给出 $Q_{S_1}(x, y)$。注意第二步需要 $P_{S_2}(x)$ 才能使用：$S_3 \sqsupseteq S_2$ 的条件 2 只谈及 $S_2$ 允许的输入。

**不反对称。** 设 $S$ 为"要求 $n \ge 0$；返回 $n$"，$T$ 为"要求 $n \ge 0$；返回 $n$，且当 $n < 0$ 时返回 $0$"。作为二元组它们不同（负 $n$ 处后置条件相异），但彼此互相精化，因为差别完全落在公共前置条件之外。精化只在实际重要的输入上比较规格说明，所以它是预序（preorder）；当两个规格说明互相精化时，它们是*等价的*。
:::
:::

::: exercise 更快的平方根 {#exr-isqrt-fast level=3}
重新实现 [[#ex-isqrt]] 的 `isqrt`，使迭代次数为 $O(\log n)$：在范围 $[0, n+1)$ 内对 $r$ 做二分查找。写出循环不变式，并用 `meets_spec` 对每个 $n < 10^5$ 以及 $n = 10^{40}$ 检验你的函数。
::: hint
维持 $lo^2 \le n < hi^2$，并把 $hi - lo$ 折半，直到 $hi = lo + 1$。
:::
::: solution
```python
def isqrt(n):
    """Requires: n is an int and n >= 0.
    Effects:  returns the int r with r * r <= n < (r + 1) * (r + 1)."""
    lo, hi = 0, n + 1                  # 不变式：lo*lo <= n < hi*hi
    while hi - lo > 1:
        mid = (lo + hi) // 2           # lo < mid < hi
        if mid * mid <= n:
            lo = mid
        else:
            hi = mid
    return lo

def meets_spec(n, r):
    return isinstance(r, int) and r * r <= n < (r + 1) * (r + 1)

print(all(meets_spec(n, isqrt(n)) for n in range(100_000)))
print(isqrt(10**40), meets_spec(10**40, isqrt(10**40)))
```


**不变式** $I \equiv 0 \le lo < hi \land lo^2 \le n < hi^2$。初始成立，因为 $0 \le n < (n+1)^2$。若 $hi - lo > 1$，则 $lo < mid < hi$；分支把 $mid^2 \le n$ 的检验所允许的那个端点置为 $mid$，从而保持 $I$。退出时 $hi = lo + 1$，于是 $I$ 化为 $lo^2 \le n < (lo + 1)^2$，即 Effects 子句。变体 $hi - lo$ 每次大约减半，所以约有 $\log_2(n+1)$ 次迭代：$n = 10^{40}$ 时为 $133$ 次，而计数版本需要 $10^{20}$ 次。`isqrt` 的调用者除了速度之外分辨不出差别——可修改性在起作用。（Python 标准库把这做成了 `math.isqrt`。）
