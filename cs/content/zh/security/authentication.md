每隔几个月，就有一家公司宣布它的用户账户数据库被窃。接下来发生什么，几乎完全取决于多年之前一个开发者可能只花了十分钟做出的设计决定：口令如何存储。若以明文存储，每个账户当场全部沦陷——而且因为人们复用口令，其他许多网站上的账户也一并沦陷。若用一个快速哈希且不加盐，其中大多数会在几小时内被还原。若用一个慢速、加盐、访存困难的函数，攻击者只能慢慢地还原出最弱的一小部分，用户来得及改口令。同一场盗窃，同一个攻击者，结果却相差几个数量级。

本章讲**认证**：系统如何判定一个请求来自某个特定的人或程序。它是 STRIDE 里的 S（[[security/security-principles]]），也是访问控制的根基，因为权限检查的可靠性不超过它对"谁在请求"的掌握。我们研究口令——它如何被猜出、又该如何存储——并计算 bcrypt、scrypt 与 Argon2 的开销；然后是第二因子，包括 HOTP 与 TOTP 一次性口令算法，按标准测试向量实际计算；挑战–响应与公钥认证，可抵御钓鱼；最后是会话与单点登录。哈希函数、HMAC、签名等密码学工具在 [[cryptography/hash-mac]] 与 [[cryptography/signatures]] 中展开。

## 认证是什么

::: definition 身份标识、认证与授权 {#def-authn}
**身份标识**是对身份的声明（"我是 alice"）。**认证**是对该声明的验证：检查只有所称主体才提供得出的证据。**授权**则是另一个决定——已认证的主体可以做什么（[[security/access-control]]）。证据传统上分为三类**因子**：

1. 你**知道**的东西——口令、PIN 码；
2. 你**拥有**的东西——手机、硬件安全密钥、智能卡、保管着的密钥；
3. 你**是**什么——指纹、面容（生物特征）。

**多因子认证**（MFA）要求来自至少两种不同因子的证据。
:::

有两种不同的东西都叫认证。**实体认证**确立一个主体*当前*在场并参与其中，比如用户登录。**消息**（数据源）**认证**确立消息是谁创建的——无论那是何时；这是 MAC 和签名所提供的。登录协议需要实体认证，也就是需要*新鲜性*：不能录下来日后再重放的证据。本章许多内容讲的正这种新鲜性从何而来。

各因子的失效方式不同。你所知道的秘密能被猜、被钓、跨网站被复用，但它免费且可以更换。你所拥有的东西能被偷、会丢失、要花钱，但若密钥保存在防篡改硬件里，就无法被远程复制。生物特征方便且不会被遗忘，但它们并不秘密（指纹随处可留、面容公之于众），被窃后无法更改，而且匹配是近似的，存在误接受与误拒绝之间的权衡。因此生物特征最适合作为*本地*手段去解锁一台持有密钥的设备，而不适合作为发给服务器的秘密。

## 口令与猜测

口令是人选的，而人的选择可以预料。为推理猜测过程，我们把用户的口令建模为候选口令集上的随机变量 $X$，其概率按递减排列为 $p_1 \ge p_2 \ge \dots$。

::: definition 猜测成功 {#def-guessing}
对一个依概率排好序为 $p_1 \ge p_2 \ge \dots$ 的分布所抽取的口令，可猜 $q$ 次的对手至多以如下概率成功
$$
\lambda_q = \sum_{i=1}^{q} p_i,
$$ {#eq-lambda}
而 $\lambda_q$ 称为该分布的 **$q$-猜测成功率**。
:::

::: proposition 最优猜测 {#prop-optimal-guessing}
在做出 $q$ 个不同猜测的所有策略中，成功概率在按可能性依次猜最可能的 $q$ 个口令时达到最大，最大值为 $\lambda_q$。
:::

::: proof
一个做出 $q$ 个不同猜测的策略（可以自适应地选择，但成功之前唯一的反馈是"不对"，所以序列实际上事先固定）成功当且仅当 $X$ 属于它的猜测集 $G$，概率为 $\sum_{x \in G} \Pr[X = x]$。若 $G$ 不是最可能的 $q$ 个口令之集，则它含有某个 $x$ 而漏掉某个满足 $\Pr[X = y] \ge \Pr[X = x]$ 的 $y$，用 $y$ 替换 $x$ 不会减小总和。如此替换至多 $q$ 次，就把 $G$ 变成最靠前的 $q$ 个口令，其总和 $\lambda_q$ 即为最大值。
:::

若口令在 $N$ 种可能上均匀分布，则 $\lambda_q = q/N$，强度的自然度量便是**熵** $\log_2 N$ 比特。一个随机的 8 字符小写字母串有 $26^8 \approx 2.09 \times 10^{11}$ 种可能，约 $37.6$ 比特；取自全部 $94$ 个可打印 ASCII 字符则 $94^8 \approx 6.1 \times 10^{15}$，约 $52.4$ 比特。从一张 $7776$ 词的表（"骰子选词"表，每个词掷五次骰子）中均匀选取四个词给出 $7776^4 \approx 2^{51.7}$，六个词给出 $2^{77.5}$。

但人选的口令离均匀差得远。在每一个大规模泄露的口令集中，少数口令——`123456`、`password`、人名、键盘模式、词尾加数字——占了账户的很大比例，且频率大致呈幂律衰减。因此从长度与字符类别算出的"熵"几乎说明不了人选口令的强度：`Password1!` 有大小写、数字和符号，却是任何破解工具最先猜的几个之一。真正要紧的是现实 $q$ 下的 $\lambda_q$。

::: example 在线与离线猜测 {#ex-guessing}
用 $N = 10^6$ 个口令上的 Zipf 律建模某网站的口令分布：$p_i = 1/(i H_N)$，其中 $H_N = \sum_{i=1}^N 1/i \approx 14.39$。（真实分布只是近似 Zipf，但这抓住了它肥大的头部。）计算 (a) 每账户每天可试 $10$ 个口令、持续一年的**在线**攻击者，与 (b) 已窃得口令数据库的**离线**攻击者的 $\lambda_q$。
::: solution
由 [[#eq-lambda]]，$\lambda_q = H_q/H_N$。用计算：

```python
H = lambda n: sum(1 / i for i in range(1, n + 1))
HN = H(10**6)
for q in (1, 10, 100, 3650, 10**6):
    print(q, round(H(q) / HN, 3))
```

```console

10 0.204
100 0.36
3650 0.61
1000000 1.0
```

(a) 在线攻击者一年对每个账户猜 $q = 3650$ 次，在本模型中攻破 $61\%$ 的账户——这提醒我们：当用户从肥头分布中选口令时，光有限速并不够；网站还必须拒绝最常见的口令，砍掉攻击者赖以生存的那个头。(b) 离线攻击者只受计算力的限制。若数据库存的是未加盐的快速哈希，按每秒 $10^{10}$ 次猜测计算（这是一个假设，量级上相当于一块现代 GPU 跑快速哈希），整个 $10^6$ 口令表只要 $10^{-4}$ 秒，而 8 个随机小写字母的全部空间（$2.09 \times 10^{11}$）约 $21$ 秒。离线猜测只能靠口令的存储方式来控制，这正是下一节的主题。
:::

### 在线攻击与口令要求

**在线攻击**向真实的登录服务提交猜测。防御是限制速率：随连续失败增长的延迟、临时锁定或额外挑战，并按账户与按来源分别实施。几次失败之后永久锁定是很差的选择，因为它让任何人都能把任何用户锁在门外——一次可用性攻击。NIST 的指南把单个账户上连续失败的尝试限制在至多 $100$ 次以内；再配合常见口令黑名单，在线攻击者的 $\lambda_q$ 便小到可以忽略。

关于应当对用户提什么要求，指南已经发生了剧变。NIST Special Publication 800-63B 第 4 修订版（2025 年定稿，2026 年现行）除其他事项外要求验证器：口令作为唯一因子时至少要求 15 个字符（作为多个因子之一时至少 8 个）；允许至少 64 个字符和任意可打印字符，包括空格；把新口令与常用、易猜或已泄露口令的**黑名单**比对；**不要**强加"至少一个大写字母、一个数字、一个符号"之类的构成规则；**不要**要求定期更换，但在有泄露证据时强制更换；并允许口令管理器执行粘贴。

::: warning 构成规则与强制换期
"至少一个大写、一个数字、一个符号，每 90 天一换"听起来严格，效果却寥寥。用户会按可以预料的方式满足构成规则（`Summer2026!`），而强制更换会产生（`Summer2026!`、`Autumn2026!`）这样的序列，攻击者知道其一便可预测其余。两条规则都把用户推向把口令写下来或复用。真正降低 $\lambda_q$ 的是长度、一份攻击者最先尝试的口令黑名单、限速，以及——最好的——不要只依赖一个记忆口令。
:::

## 口令存储

服务器必须能在无法吐出口令的前提下校验口令。设数据库终将失窃，逐种可能方案考察。

1. **明文**。所有口令全部暴露。绝不可接受。
2. **加密**。密钥就在同一台服务器上，窃得数据库的人通常也窃得密钥；而且加密按设计是可逆的，这一点服务器并不需要。
3. **哈希**：$h = H(\mathit{pw})$，用密码学哈希。被窃的哈希只能靠猜测求逆。但两个用户口令相同时哈希也相同，而攻击者只需对整个词典哈希*一次*就能逐一查找每个用户——还可以利用盗窃之前就建好的预计算表。
4. **加盐哈希**：$h = H(\mathit{salt} \,\|\, \mathit{pw})$，在哈希旁边存一个随机的**盐值**。相同的口令从此哈希不同，预计算失效。
5. **用一个刻意慢速、访存困难的函数作加盐哈希**。攻击者的每次猜测，代价都与服务器完成一次合法登录相当。

::: definition 口令散列方案 {#def-password-hash}
一个**口令散列方案**为每个账户存储形如 $(\mathit{params}, s, h)$ 的记录，其中 $h = F_{\mathit{params}}(s, \mathit{pw})$，$s$ 是为每个账户（以及每次口令变更）独立均匀抽取、至少 $128$ 比特的**盐值**，$F$ 的求值代价可调：时间上的**工作因子**（迭代次数），对访存困难的函数还有内存量。登录尝试 $\mathit{pw}'$ 当 $F_{\mathit{params}}(s, \mathit{pw}') = h$ 时被接受，比较须以常数时间进行。
:::

::: proposition 盐值买到什么 {#prop-salt}
设被窃数据库含 $m$ 个账户，攻击者要把一份含 $D$ 个候选口令的列表测试遍所有账户，其中 $F$ 的一次求值代价为一个单位。无盐时，攻击者把每个候选对每个账户测试需要 $D$ 个单位（外加查找），且这些工作可以在盗窃之前完成。盐值各不相同时，则需 $mD$ 个单位，盗窃前做的任何工作都帮不上忙。
:::

::: proof
无盐时，$h = F(\mathit{pw})$ 只依赖口令本身，于是对每个候选 $c$ 计算一次 $F(c)$，再到存储的 $m$ 个值构成的哈希表中查找，就用 $c$ 测试了所有账户：共 $D$ 次求值。这些计算不依赖数据库中的任何东西，可以事先完成（做成词典表或彩虹表）。有盐时，用 $c$ 测试账户 $j$ 需要 $F(s_j, c)$。由于盐值各不相同，$F(s_j, c)$ 与 $F(s_k, c)$ 是在不同输入上的求值；把 $F$ 建模为随机函数，则知道其一对另一个毫无用处，所以攻击者想测试的每一对 $(j, c)$ 都要各自求值，共 $mD$ 次。盗窃之前盐值未知，且在至少 $2^{128}$ 个值上均匀分布，因此哪怕只想覆盖一个盐值到有意义的比例，就需要约 $2^{128}$ 次求值。
:::

盐值让每个账户成为一个独立的问题；但对单个被盯上的账户它无能为力。那是工作因子的任务。若 $F$ 一次求值耗时 $t$，对一个账户测试 $D$ 个候选就要 $Dt$，所以我们要把 $F$ 选得尽量慢——慢到登录服务承受得起的程度。当前在用的有三类：

- **PBKDF2**（RFC 2898，2000）把 HMAC 迭代 $c$ 次；其代价是纯计算，在 GPU 和定制硬件上很便宜。
- **bcrypt**（普罗沃斯（Provos）和马齐耶尔（Mazières），1999）构建在 Blowfish 密码的密钥调度之上，重复 $2^{\mathit{cost}}$ 次；其存储串记录了代价与盐值。它内存用量不大（4 KiB），对 GPU 有一定抵抗力。它最多处理 72 字节的口令。
- **scrypt**（珀西瓦尔（Percival），2009）与 **Argon2**（2015 年口令散列竞赛的优胜者；RFC 9106，2021）是**访存困难**的：计算需要一大块内存，并以数据相关的顺序填充和读取，所以攻击者无法在不为每个并行猜测同时购买内存的情况下获得廉价的并行加速。混合变体 Argon2id 是通常的推荐。

近年的 OWASP 口令存储速查表建议例如：Argon2id 内存 $19$ MiB、迭代 $2$ 次；scrypt $N = 2^{17}$、$r = 8$、$p = 1$；bcrypt 代价至少 $10$；或在合规要求下使用迭代 $600{,}000$ 次的 PBKDF2-HMAC-SHA256。随着硬件进步这些数字还在上升；原则是取登录服务所能承受的最大代价。

::: example 开销的算术 {#ex-cost}
在这台机器上测量：一次 SHA-256 哈希、迭代 $600{,}000$ 次的 PBKDF2-HMAC-SHA256、$N = 2^{14}$ 与 $2^{17}$ 的 scrypt（$r = 8$、$p = 1$），以及代价 $10$、$11$、$12$ 的 bcrypt。scrypt 用多少内存？对一个账户的离线攻击比单次 SHA-256 慢多少？
::: solution
```python
import hashlib, os, time, bcrypt

pw = b"correct horse battery staple"
salt = os.urandom(16)

def timed(label, f):
    t = time.perf_counter(); f(); print(f"{label:28s} {1000*(time.perf_counter()-t):8.1f} ms")

timed("PBKDF2-SHA256, 600000 it.", lambda: hashlib.pbkdf2_hmac("sha256", pw, salt, 600_000))
timed("scrypt N=2^14 r=8 p=1", lambda: hashlib.scrypt(pw, salt=salt, n=2**14, r=8, p=1))
timed("scrypt N=2^17 r=8 p=1", lambda: hashlib.scrypt(pw, salt=salt, n=2**17, r=8, p=1, maxmem=2**28))
for cost in (10, 11, 12):
    timed(f"bcrypt cost {cost}", lambda: bcrypt.hashpw(pw, bcrypt.gensalt(rounds=cost)))
```

```console
PBKDF2-SHA256, 600000 it.       292.9 ms
scrypt N=2^14 r=8 p=1            50.0 ms
scrypt N=2^17 r=8 p=1           461.0 ms
bcrypt cost 10                   73.9 ms
bcrypt cost 11                  143.3 ms
bcrypt cost 12                  324.1 ms
```

用 `timeit` 在一百万次调用上测得，一次加盐 SHA-256 约 $0.75$ µs。（计时来自 2020 年代一台服务器核心上的一次运行，各台机器有差别。）bcrypt 的代价每加 $1$，时间翻倍，与 $2^{\mathit{cost}}$ 的预言一致。scrypt 的内存约为 $128 \cdot N \cdot r$ 字节：$128 \times 2^{14} \times 8 = 2^{24}$ 字节 $= 16$ MiB（$N = 2^{14}$ 时），$N = 2^{17}$ 时是 $128$ MiB——这就是为什么 Python 默认的 $32$ MiB `maxmem` 必须调高。与 SHA-256 相比，代价 $12$ 的 bcrypt 使每次猜测在本硬件上贵 $0.32/(0.75 \times 10^{-6}) \approx 430{,}000$ 倍。原先在一个账户上不到一秒就能试完 [[#ex-guessing]] 中那张百万词表的攻击者，现在在这样一枚核心上每个账户约需 $3.7$ 天；而访存困难的函数让攻击者的 GPU 与定制芯片的优势远不如对 SHA-256 时那么大。
:::
:::

在应用代码里，用经过检验的库这就是寥寥数行；绝不要自己动手写散列。

```python
import bcrypt

def register(password: str) -> bytes:
    # gensalt 生成全新的随机 16 字节盐值；cost 12 = 2^12 轮密钥调度
    return bcrypt.hashpw(password.encode(), bcrypt.gensalt(rounds=12))

def login(stored: bytes, attempt: str) -> bool:
    # checkpw 从存储串中读回 cost 与盐值，并以安全方式比较
    return bcrypt.checkpw(attempt.encode(), stored)

record = register("plum-anvil-sixty-orbit")
print(record.decode())
print(login(record, "plum-anvil-sixty-orbit"), login(record, "plum-anvil-sixty-orbiT"))
print(register("plum-anvil-sixty-orbit") == record)   # 同一口令，新的盐值
```

True False

记录 `$2b$12$…` 里保存着算法版本、代价、22 个字符的盐值和哈希，所以日后可以调高代价：用户登录成功时，服务器用新代价重散列其口令。这里所用的库（Python 的 bcrypt 5.0）拒绝超过 72 字节的口令，而不像旧版本那样悄悄截断；应用要么限制长度，要么先用带密钥的函数预散列。还有两个常见的改进。**胡椒**（pepper）是一个密钥，保存在数据库之外（硬件安全模块或独立的机密存储中），在散列之前用 HMAC 混入，使仅被窃的数据库根本无法被攻击。此外，$h$ 与计算值之间的比较必须**常数时间**完成、与首个不同字节出现的位置无关（Python 里的 `hmac.compare_digest`），以免响应时间泄露分毫。

::: quiz
某网站存储 `SHA-256(salt || password)`，每用户一个 16 字节随机盐。攻击者窃得数据库。下列说法正确的是？

- [ ] 盐值使哈希不可能被破解，因为攻击者需要 $2^{128}$ 张表。
- [x] 常见口令仍会被较快还原，只不过要一个账户一个账户地来，因为每次猜测只需一次快速哈希。
- [ ] 攻击者可以利用预先为 SHA-256 算好的彩虹表。
- [ ] 攻击者能看出哪些用户共用同一个口令。
::: solution
盐值消灭了预计算，并使相同的口令不再看起来相同（[[#prop-salt]]），所以第三、四项错误。但用快速哈希时，在一个账户上测试一百万个候选大约要一秒，弱口令很快沦陷。出路是慢速、访存困难的函数：Argon2id、scrypt 或 bcrypt。
:::
:::

## 一次性口令与第二因子

口令是静态的秘密：谁见到一次，谁就永远可以用。**一次性口令**增加一个取值不断变化的第二因子，其值由用户设备与服务器共同持有的秘密密钥导出。

::: algorithm HOTP 与 TOTP {#alg-hotp}
设 $K$ 为共享秘密密钥（至少 128 比特），$C$ 为 8 字节计数器。

1. 计算 $M = \mathrm{HMAC\text{-}SHA1}(K, C)$，一个 20 字节的串（[[cryptography/hash-mac#def-hmac]]）。
2. **动态截断**：设 $o$ 为 $M$ 最后一个字节的低 $4$ 位，$0 \le o \le 15$。把 $M[o..o+3]$ 四个字节按大端解释为整数并清掉其最高位，得到一个 31 位数 $S$。
3. 输出 $\mathrm{HOTP}(K, C) = S \bmod 10^d$，写成 $d$ 位数字（通常 $d = 6$）。

**HOTP**（RFC 4226，2005）在每次使用后令 $C$ 加一。**TOTP**（RFC 6238，2011）对当前 Unix 时间 $T$ 取 $C = \lfloor (T - T_0)/X \rfloor$，通常 $T_0 = 0$、时间步长 $X = 30$ s；服务器接受当前步的口令码，并为时钟偏差留余地，往往还接受前后各一步的。
:::

::: example HOTP 的 RFC 测试向量 {#ex-hotp}
RFC 4226 使用 ASCII 密钥 `12345678901234567890`。由 HMAC 值手工计算 $\mathrm{HOTP}(K, 0)$，用程序核对前四个口令码，并核对 RFC 6238 中 $T = 59$ s、$8$ 位的 TOTP 值。
::: solution
```python
import hmac, hashlib, struct

def hotp(key: bytes, counter: int, digits: int = 6, alg=hashlib.sha1) -> str:
    mac = hmac.new(key, struct.pack(">Q", counter), alg).digest()  # 8 字节大端计数器
    offset = mac[-1] & 0x0F                                          # 动态截断
    code = int.from_bytes(mac[offset:offset + 4], "big") & 0x7FFFFFFF
    return str(code % 10**digits).zfill(digits)

def totp(key: bytes, unix_time: int, step: int = 30, digits: int = 6) -> str:
    return hotp(key, unix_time // step, digits)

key = b"12345678901234567890"                      # RFC 4226 测试密钥
print([hotp(key, c) for c in range(4)])
print(totp(key, 59, digits=8), totp(key, 1111111109, digits=8))
mac = hmac.new(key, struct.pack(">Q", 0), hashlib.sha1).digest()
print(mac.hex(), mac[-1] & 15)
```

```console
['755224', '287082', '359152', '969429']
94287082 07081804
cc93cf18508d94934c64b65d8ba7667fb7cde4b0 0
```

以 $C = 0$ 手工计算：$M$ 的最后一个字节是 `b0`，其低 nibble 为 $o = 0$，故取第 $0$–$3$ 字节 `cc93cf18`。清掉最高位得 `4c93cf18` $= 1{,}284{,}755{,}224$，模 $10^6$ 为 $755224$，即 RFC 4226 的第一个测试值。TOTP 在 $T = 59$ 时，$C = \lfloor 59/30 \rfloor = 1$，8 位口令码 $94287082$ 与 RFC 6238 的表一致；$T = 1111111109$ 时的 $07081804$ 亦然。清最高位是为了让有符号与无符号算术在每个平台上给出同一个数。
:::
:::

一次性口令码使单次所见的口令码无从重放，并使猜测不可行（30 秒窗口内 $10^6$ 种可能，且有限速）。但它们挡不住**钓鱼**：假登录页把用户输入的口令和当前口令码实时转发给真网站，即以用户身份登录。弱点在于口令码证明了对 $K$ 的知识，却对用户正在与*哪个网站*交谈不置一词。短信口令码也是如此，而且额外暴露于 SIM 卡劫持诈骗，在 NIST 的指南中作为认证手段在多数用途上已被弃用。

### 挑战–响应与公钥

稳健的解决方案是这样的协议：服务器发送一个新鲜的随机**挑战**，用户设备以一个依赖于挑战、秘密*以及网站身份*的响应作答。

::: definition 挑战–响应认证 {#def-challenge}
验证者 $V$ 认证持有秘密的证明者 $P$：$V$ 发送一个新鲜的、均匀随机的 $n$ 比特挑战 $r$；$P$ 用一个 $V$ 早前注册过其公钥的签名密钥回复 $\sigma = \mathsf{Sign}_{sk}(r \,\|\, \mathit{context})$（或用共享密钥回复 $\sigma = \mathrm{MAC}_K(r \,\|\, \mathit{context})$）；若 $\sigma$ 对 $V$ 所发的 $r$ 和它期望的上下文验证通过，则 $V$ 接受。
:::

::: proposition 抗重放与抗中继 {#prop-challenge}
设签名方案是不可伪造的（[[cryptography/signatures#def-sig]]）。一个已录下对 $q$ 个早前挑战的响应、且无法让 $P$ 在验证者当前的挑战与上下文下产生新签名的攻击者，使 $V$ 接受的概率至多为 $q/2^n + \varepsilon$，其中 $\varepsilon$ 是其伪造优势。若上下文包含验证者的身份并由 $P$ 的设备核对，那么另一个验证者（比如钓鱼网站）获得的响应，$V$ 同样不会接受。
:::

::: proof
$V$ 要接受，攻击者必须对当前挑战 $r$ 与期望上下文 $c$ 的消息 $(r \,\|\, c)$ 给出有效签名。要么这条一模一样的消息就在这 $q$ 条先前已签名的消息之中——这要求 $r$ 等于某个早先的挑战；由于 $r$ 均匀且独立，由联合界其概率至多 $q/2^n$——要么攻击者对一条新消息产生了有效签名，这是一次伪造，至多以概率 $\varepsilon$ 发生。至于第二点，钓鱼网站 $V'$ 只能获得上下文写着 $V'$ 的消息的签名（因为诚实的设备填入的是它实际交谈的网站的身份，而不是用户以为的那个）。这样的消息与 $(r \,\|\, c_V)$ 不同，所以把它中继给 $V$，$V$ 仍没有自己期望消息的有效签名，第一部分适用。
:::

这正是 **FIDO2/WebAuthn** 安全密钥与**通行密钥**（passkey）的工作方式（W3C Web Authentication，自 2019 年起成为推荐标准）。注册时，设备为该网站生成一对新密钥并把公钥交给网站。登录时，网站发来挑战；浏览器构造一个包含挑战和它实际连接到的**源**（origin，例如 `https://bank.example`）的结构，设备在用户触摸它、或用指纹或 PIN 解锁之后，把它连同网站的标识一起签名。一个相似的钓鱼域名得到的签名写的是错误的源，真网站于是拒绝它：协议替网站核对了身份，用户就不必自己核对。由于每个网站各有自己的密钥对、服务器只存公钥，被窃的服务器数据库里没有任何能用来登录的东西，也没有任何东西跨网站复用。指纹从不离开设备；它只解锁本地密钥——生物特征正是按上文推荐的方式使用的。

::: quiz
下列哪种登录方法能抵御一个把用户输入的一切实时转发给真网站的实时钓鱼网站？

- [ ] 一个口令管理器生成、手工键入的长随机口令。
- [ ] 口令外加六位 TOTP 码。
- [ ] 口令外加短信验证码。
- [x] WebAuthn 安全密钥或通行密钥。
::: solution
中继式钓鱼网站会把键入的口令和任何一次性口令码在其有效期内转发过去。只有 WebAuthn 的签名绑定在浏览器实际连接的源上，因此为钓鱼网站生成的响应拿到真网站处毫无用处（[[#prop-challenge]]）。（一个只在域名匹配时才自动填充的口令管理器，实践中也能抗钓鱼，前提是用户不在自动填充失败时手工复制口令。）
:::
:::

## 会话与单点登录

登录之后，服务器需要认出用户随后的请求，而不用每次都要口令。它签发一个**会话令牌**：一个至少 128 比特、来自密码学安全发生器的随机值（Python 中的 `secrets.token_urlsafe(32)`），由客户端保存——通常是 cookie——并随每个请求发送。服务器把令牌映射到会话的状态；或者令牌本身就是经过签名或 MAC 保护的结构，里面写着用户和失效时间。令牌在其存续期间与口令同样有效，所以它必须只经 TLS 传输、不被脚本和其他网站取得（cookie 属性 `Secure`、`HttpOnly`、`SameSite`，见 [[security/web-security]]）、要过期、登录后要更换（防止**会话固定**：攻击者在用户登录前埋下一个自己已知的令牌），并在登出和改口令时作废。

::: example 会话令牌必须多长？ {#ex-token}
某服务任意时刻有 $10^6$ 个活跃会话，每个会话由一个 $b$ 位的均匀随机令牌标识。攻击者每秒能提交 $10^9$ 次猜测（远超任何真实服务的允许量），持续一年。就 $b = 32$ 和 $b = 128$，给出某个猜测命中某个活跃会话的概率的上界。
::: solution
每次猜测命中 $10^6$ 个活跃令牌之一的概率至多为 $10^6/2^b$。一年约 $3.16 \times 10^7$ s，故共有 $3.16 \times 10^{16}$ 次猜测，由联合界，任何成功的概率至多 $3.16 \times 10^{16} \times 10^6 / 2^b = 3.16 \times 10^{22}/2^b$。$b = 32$ 时，这个界超出 $1$ 约 $7 \times 10^{12}$ 倍——第一秒内的一小会儿就必然命中。$b = 128$ 时为 $3.16 \times 10^{22}/3.4 \times 10^{38} \approx 9.3 \times 10^{-17}$。这就是为什么令牌必须来自至少 128 位的密码学安全发生器：计数器、时间戳或用户名的哈希，其可猜空间远小于长度给人的印象。
:::
:::

用户在几十个服务上有账户，而**单点登录**（SSO）让一个**身份提供者**为众多**依赖方**完成认证。各服务不再都存储口令，而是信任由身份提供者签名的断言。

- **Kerberos**（MIT 的 Project Athena，1980 年代；第 5 版见 RFC 4120，2005）建立在 Needham–Schroeder 对称密钥协议之上，是企业网络的标准：用户向密钥分发中心认证一次，得到一张**票据授予票据**，再换取短时的**服务票据**，每张服务票据用中心与该服务共享的密钥加密，并以时间戳保证新鲜性。
- **SAML 2.0**（2005）与 **OpenID Connect**（2014，是 **OAuth 2.0**（RFC 6749，2012）之上的一层）是 web 的协议。OpenID Connect 中，依赖方把浏览器重定向到身份提供者；用户在那里登录（最好用 WebAuthn）；提供者带着一个短时授权码重定向回来，依赖方再经一条直接的 TLS 连接用授权码换取签名的 **ID 令牌**，其中写明用户是谁、给哪个依赖方、有效期至何时。

OAuth 2.0 本身是**委托授权**协议——让应用凭一个受限的**访问令牌**代表你在另一个服务上行事，而不必把口令交给它——不是认证协议；身份这一层由 OpenID Connect 添加。这些流程的安全系于些容易做错的细节：注册的回调地址要精确匹配、每个响应要绑定到发起它的那个请求（`state` 与 `nonce` 参数，以及 PKCE，RFC 7636），并检查令牌的签名、签发者、受众与有效期。请使用维护中的库，并遵循当前的最佳实践文档而不是博客文章。

SSO 在集中便利的同时也集中了风险：身份提供者成为单点故障，也是整个组织中价值最高的目标，所以最强的认证应当安放在它那里。而每个系统都有一条最薄弱的路径：**账户恢复**。如果忘记口令可以靠回答"母亲的娘家姓"、或在电话里说服一个客服人员来重置，那么无论登录页要求什么，那才是系统的真实强度。恢复应依赖与登录至少同样强的因子——第二把已注册的安全密钥、注册时打印出来的恢复码、或带延迟与通知的身份核验。

::: history
费尔南多·科尔巴托（Fernando Corbató）在 MIT 的兼容分时系统于 1960 年代使用口令，1966 年它的口令文件曾被印在"每日消息"的位置上而出名。罗伯特·莫里斯（Robert Morris）与肯·汤普森（Ken Thompson）的《口令安全：一个案例研究》（"Password security: a case history"，《Communications of the ACM》，1979）记述了 Unix 转向加盐、刻意慢速的 `crypt` 散列函数——12 比特盐值与 25 轮修改过的 DES。莱斯利·兰波特（Lamport）1981 年提出哈希链一次性口令；罗杰·尼达姆（Roger Needham）与迈克尔·施罗德（Michael Schroeder）1978 年的协议催生了 Kerberos——后者在 1980 年代由 MIT 的 Project Athena 开发。尼尔斯·普罗沃斯（Niels Provos）与戴维·马齐耶尔（David Mazières）1999 年在 USENIX 提出 bcrypt，科林·珀西瓦尔（Colin Percival）2009 年提出 scrypt，亚历克斯·比留科夫（Alex Biryukov）、丹尼尔·迪努（Daniel Dinu）与德米特里·霍夫拉托维奇（Dmitry Khovratovich）的 Argon2 赢得 2015 年口令散列竞赛。来自业界组织"开放认证倡议"（Initiative for Open Authentication）的 HOTP 与 TOTP 于 2005 年和 2011 年成为 RFC。FIDO 联盟（2013）与 W3C 的 Web Authentication 标准（2019）把公钥登录带进浏览器，主要平台自 2022 年起把这类凭据以"通行密钥"（passkeys）同步。NIST 的 SP 800-63B（2017）放弃了构成规则与强制换期，其第 4 修订版于 2025 年定稿。
:::

## 后续内容

认证确立*是谁*；[[security/access-control]] 决定*他可能做什么*，其模型假定认证已经正确完成。会话令牌活在 cookie 里，防范其他网站属于 [[security/web-security]]；机器之间的认证信道，从 TLS 客户端证书到 VPN，见 [[security/network-security]]。口令数据库是入侵者所能偷到的最有价值的东西之一，这也是 [[security/malware]] 把凭据窃取当作入侵核心环节的原因之一。挑战–响应背后的密码学——签名及其不可伪造性——在 [[cryptography/signatures]]，认证密钥交换在 [[cryptography/protocols]]。

::: summary
- **认证**依据证据验证所声明的身份：你知道的、拥有的、或你自身的什么（[[#def-authn]]）。实体认证需要**新鲜性**，使录下的证据无法重放。
- 人选口令的分布有偏；合适的度量是 $q$-猜测成功率 $\lambda_q$，先猜最可能的口令可使其最大（[[#prop-optimal-guessing]]）。长度、黑名单和限速有用；构成规则和强制换期没有。
- 用**加盐、慢速、访存困难**的函数（Argon2id、scrypt 或 bcrypt），经由经过检验的库来存储口令。盐值让每个账户成为独立的问题并消灭预计算（[[#prop-salt]]）；工作因子让每次猜测都昂贵；胡椒与常数时间比较提供更进一步的保护。
- **HOTP/TOTP** 口令码是截断成几位的 HMAC 值（[[#alg-hotp]]）；它们防重放和猜测，但不防实时钓鱼。
- **把公钥绑定到源的挑战–响应**（WebAuthn、通行密钥）同时抗重放与钓鱼（[[#prop-challenge]]），并且被窃的服务器数据库里不留任何可复用的东西。
- **会话令牌**是持有者凭据：随机、经 TLS 传输、放在受保护的 cookie 中、登录时更换并到期作废。**SSO**（Kerberos、SAML、OpenID Connect）把认证集中于一个身份提供者，它必须是保护得最好的系统。账户恢复往往是最薄弱的环节。
:::

## 习题

::: exercise 随机口令的熵 {level=1 check="8"}
从 $62$ 个字母与数字中均匀随机选取、且至少有 $45$ 比特熵的口令，最小长度 $L$ 是多少？（填 $L$。）
::: solution
每个字符给出 $\log_2 62 \approx 5.954$ 比特。需要 $5.954 L \ge 45$，故 $L \ge 7.56$，于是 $L = 8$（约 $47.6$ 比特）。
:::
:::

::: exercise scrypt 的内存 {level=1 check="64"}
scrypt 约使用 $128 \cdot N \cdot r$ 字节内存。$N = 2^{16}$、$r = 8$ 时使用多少 Mebibyte？（填入 MiB 数。）
::: solution
$128 \times 2^{16} \times 8 = 2^7 \times 2^{16} \times 2^3 = 2^{26}$ 字节 $= 64$ MiB。
:::
:::

::: exercise 提高 bcrypt 的代价 {level=1 check="4"}
某网站把 bcrypt 代价从 $10$ 提高到 $12$。攻击者测试一次口令猜测的时间增大为原来的几倍？（填入倍数。）
::: solution
bcrypt 做 $2^{\mathit{cost}}$ 轮昂贵的密钥调度，故倍数为 $2^{12}/2^{10} = 4$——与 [[#ex-cost]] 实测的 $74$ ms 和 $324$ ms 在计时噪声内吻合。
:::

::: exercise 盐值的账 {level=2 check="1000000"}
被窃数据库有 $10{,}000$ 个账户，攻击者想把最常见的 $100$ 个口令逐一对每个账户测试。若每个账户各有自己的盐值，需要多少次口令散列求值？无盐时呢？（填入有盐时的数目。）
::: solution
由 [[#prop-salt]]，盐值各不相同时，每个（账户，候选）对都要各自求值：$10{,}000 \times 100 = 10^6$。无盐时 $100$ 次求值即可——若攻击者手里有预计算表，一次都省了——随后是 $10^6$ 次廉价查找。设慢哈希每次求值 $0.3$ s，有盐的攻击单核约需 $3.5$ 天，无盐的只要 $30$ 秒。
:::
:::

::: exercise HOTP 截断 {level=2 check="287082"}
对 RFC 4226 的密钥与计数器 $C = 1$，HMAC-SHA1 给出 20 字节的值 `75a48a19d4cbe100644e8ac1397eea747a2d33ab`。手工完成动态截断。（填入六位口令码，不含前导零。）
::: solution
最后一个字节是 `ab`，其低 nibble 为 `b` $= 11$，故 $o = 11$。第 $11$ 至 $14$ 字节（从 $0$ 数起）：字节串为 `75 a4 8a 19 d4 cb e1 00 64 4e 8a c1 39 7e ea 74 …`，故第 $11$–$14$ 字节是 `c1 39 7e ea`。清掉最高位得 `41397eea` $= 1{,}094{,}287{,}082$，模 $10^6$ 为 $287082$，即 RFC 的第二个测试值、[[#ex-hotp]] 打印出的第二个值。
:::
:::

::: exercise TOTP 窗口 {level=2}
某服务器接受当前 30 秒步以及前后各一步的 TOTP 口令码。(a) 攻击者观察到的一个口令码最长还能使用多久？(b) 一个没有密钥的在线攻击者猜 6 位码；每步限 $5$ 次尝试，一天之内成功的概率多大？(c) 服务器应记住什么，以防止口令码被用两次？
::: solution
(a) 第 $C$ 步的码在服务器当前步为 $C - 1$、$C$ 或 $C + 1$ 期间都被接受，前后共 $90$ 秒。用户在第 $C$ 步输入时被看到的码，一直可用到第 $C + 1$ 步结束——最迟 $60$ 秒之后——除非服务器像 (c) 那样拒绝重复使用。(b) 一天有 $2880$ 步，每步至多 $5$ 次猜测，共至多 $14{,}400$ 次，每次成功概率约 $3/10^6$（任意时刻有三个可接受的码）。联合界给出至多 $14{,}400 \times 3 \times 10^{-6} \approx 0.043$——偏高，这正是限制必须跨步生效的原因（例如连续失败几十次后锁定第二因子并通知用户）。(c) 每个账户最近一次成功使用的步号；来自该步或更早步的码一律拒绝，RFC 6238 即如此建议。
:::
:::

::: exercise 设计一个口令存储 {level=3}
用 `hashlib.scrypt` 写出 `hash_password(pw)` 与 `verify(pw, record)`：$N = 2^{14}$、$r = 8$、$p = 1$、来自 `os.urandom` 的 16 字节盐值、32 字节输出、常数时间比较，并把参数与记录一起存储以便日后更改。展示正确口令与错误口令的验证都能工作，并说明如何把已有用户迁移到 $N = 2^{17}$。
::: solution
```python
import hashlib, hmac, os

def hash_password(pw: str, n: int = 2**14, r: int = 8, p: int = 1) -> str:
    salt = os.urandom(16)
    h = hashlib.scrypt(pw.encode(), salt=salt, n=n, r=r, p=p, dklen=32, maxmem=2**28)
    return f"scrypt${n}${r}${p}${salt.hex()}${h.hex()}"

def verify(pw: str, record: str) -> bool:
    _, n, r, p, salt, h = record.split("$")
    cand = hashlib.scrypt(pw.encode(), salt=bytes.fromhex(salt), n=int(n), r=int(r),
                          p=int(p), dklen=32, maxmem=2**28)
    return hmac.compare_digest(cand, bytes.fromhex(h))   # 常数时间比较

rec = hash_password("plum-anvil-sixty-orbit")
print(rec[:40] + "...")
print(verify("plum-anvil-sixty-orbit", rec), verify("plum-anvil-sixty-orbi", rec))
```

```console
scrypt$16384$8$1$d8d48d31142b0a76804dad8...
True False
```

（盐值每次运行都不同。）迁移的做法：继续接受旧记录；用户登录成功时，明文短暂可得，此时用 $N = 2^{17}$ 重算记录并存储。对从不登录的账户，可以用包裹立即加强保护：存储 $\mathrm{scrypt}_{2^{17}}(\text{旧散列})$，验证时先算旧散列、再算新的，使任何存储的值都不弱于新标准。生产环境请使用实现了这种格式及其升级的、维护中的库（例如 Argon2id 的绑定库）。
:::

::: exercise 为什么服务器端生物特征是不好的口令 {level=3}
某公司提议：把客户指纹的扫描上传服务器，与存储的模板比对，以此认证客户。用本章的思想，给出这一设计相比于"用同一根指纹解锁用户手机上的 WebAuthn 密钥"的四个不同弱点，并说明每个弱点威胁哪个安全目标。
::: solution
(1) **重放**：扫描是静态证据；凡能在传输途中、在被攻陷的客户端上、或从服务器里把它录下来的人，都能再次提交。WebAuthn 对一个新鲜挑战签名，录下的响应毫无用处（[[#prop-challenge]])——真实性。(2) **不可撤销**：模板数据库被窃后，暴露的是用户永远无法更改的数据，不像口令或密钥对可以重新注册——机密性，且后果永久。(3) **跨站关联与复用**：同一根指纹会被采用这一方案的每一个服务接受，一处失陷即全部沦陷，模板还能把一个人的各个账户关联起来；WebAuthn 对每个站点使用单独的密钥对——机密性与隐私。(4) **服务器端近似匹配**：服务器必须接受近似匹配，于是一个能在线反复尝试合成或提取指纹的攻击者，每次尝试都有不可忽略的误接受率；WebAuthn 的匹配在设备上完成，设备会限制尝试次数并回退到 PIN——真实性。还可以补一条：扫描根本不是秘密——指纹能从物体表面提取——所以这一设计把"你是"什么当作"你知道的"什么来用，而它并不是。
:::
:::
