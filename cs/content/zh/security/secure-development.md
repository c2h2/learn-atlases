多数漏洞并不离奇。它们是普通的缺陷——少了一次检查、误读了一个输入、一个在测试里成立而在生产环境不成立的假设——只是恰好被别有用心的人够得着。前面几章研究的是特定的缺陷类别与特定的防御；本章问的是：一个组织怎样才能从一开始就造出缺陷更少的软件，在攻击者之前找到剩下的那些，并负责任地处置事后发现的漏洞。答案不是某一件工具，而是一套流程：设计期的安全需求与威胁模型，代码里的安全默认与健壮输入处理，评审与静态分析，面向意外的测试——尤其是**模糊测试**——对组件与构建之供应链的控制，以及一套纪律严明的漏洞报告接收与修复规程。

我们用使每一步变得具体的工具来研究每一步：手工追踪一次污点分析，一个静态分析器的查准率与查全率，一个（由赖斯定理出发的）"任何分析器都不可能完美"的证明，一个变异模糊测试器如何在一千个输入以内在一个玩具解析器里发现随机测试二十万个输入也发现不了的缺陷，解释其间差别的概率算术，以及一次协同披露的时间线。一般的软件工程实践——流程、需求、测试、验证——在 [[software-engineering]]，尤其是 [[software-engineering/testing]] 与 [[software-engineering/verification]]；这里我们专注安全所增添的部分。

## 开发生命周期中的安全

2002 年 1 月，比尔·盖茨（Bill Gates）的《可信赖计算》（"Trustworthy Computing"）备忘录让微软的 Windows 开发大部分停下脚步去做安全培训与评审；其成果**安全开发生命周期**（Security Development Lifecycle，SDL，2004 年起陆续发布）让安全活动在每个阶段都成为强制。NIST 的**安全软件开发框架**（SP 800-218，2022）与 OWASP SAMM 成熟度模型为任何组织描述了同样的思想。

::: definition 安全开发实践 {#def-sdl}
一个**安全开发生命周期**把安全活动附着于开发的每个阶段：

1. **需求**：安全与隐私需求，滥用用例（"作为攻击者，我想……"），项目的风险等级。
2. **设计**：架构的威胁模型（[[security/security-principles#def-threat-model]]），为其威胁选定缓解措施；攻击面评审；安全默认。
3. **实现**：核准的语言、库与配置；禁用危险函数；代码评审；静态分析。
4. **验证**：安全测试、模糊测试、动态分析，以及**由获授权测试人员执行的**渗透测试。
5. **发布与响应**：最终安全评审，签名且可复现的构建，事件响应计划，以及接收并修复漏洞报告的流程。
:::

经济学站在早期工作一边：威胁建模会上发现的设计缺陷花费一次谈话，同一个缺陷若在发布后才发现，就花费一个补丁、一次协同披露、每一位客户的紧急部署，或许还有一起数据泄露。人们常引用的精确倍数缺乏有力支撑，但方向毋庸置疑。

### 设计：让安全的路成为容易走的路

最有效的安全设计决策移除整个缺陷类别，而不是要求每个程序员每次都躲开它们。

- **为新代码选择内存安全的语言**，尤其是解析不受信输入的代码。Google 在 2024 年报告：随着新代码转向内存安全的语言、旧代码并不重写，Android 漏洞中源于内存安全缺陷的份额从 2019 年的 76% 降到 2024 年的 24%。
- **使用构造即安全的接口。**用参数化查询 API 而非字符串拼接，用默认对输出编码的模板引擎，用接收描述符而非路径的文件 API（[[security/access-control#def-toctou]]）。接口代程序员完成的检查，程序员就无从忘记。
- **解析，而非校验。**在边界处把不受信输入一次性转换成带类型的内部表示（一个 `EmailAddress`、一个 `UserId`、一个有界整数），解析不过的就拒绝，让程序其余部分只处理良类型的值。四散的事先校验必然会漏掉某条路径。
- **用允许列表（白名单）而非拒绝列表（黑名单）**，默认拒绝（[[security/security-principles#def-saltzer-schroeder]]）：接受你确知安全的输入形式，而不是试图枚举危险的那些。
- **安全默认。**出厂即开启加密、关闭调试接口、没有默认口令、服务以最小特权运行。多数部署从不改动默认配置。
- **最小化并隔离。**在接触不受信数据的部件里，减少功能、减少解析器、减少特权（[[security/access-control]]）。

::: example 让威胁模型驱动设计 {#ex-design}
一个团队正为某 web 应用添加"上传头像"功能。在写任何代码之前，用 STRIDE 式的问题推出设计决策。
::: solution
**篡改/权限提升**：上传的文件是图像解码器的攻击者可控输入——历来是内存安全缺陷的富矿。决定：在独立的沙箱进程里解码，除其输入与输出外没有任何网络与文件系统访问；如有可能，使用维护中的、内存安全语言的解码库；把每张图片重新编码成规范格式，从此只分发重新编码后的文件。**信息泄露**：照片带着元数据（位置、相机序列号）。决定：重新编码时剥除元数据——数据最小化（[[security/privacy]]）。**假冒/权限提升**：`avatar.html` 这样的文件若从应用自身的源站分发，就能在用户的浏览器里运行脚本。决定：文件以生成的名字存储；从一个单独的域名、以固定的图像内容类型分发，绝不使用用户的文件名。**拒绝服务**：一张小小的压缩图像可以解码出数 GB。决定：限制文件大小、图像尺寸与解码时间。**抵赖**：上传时记录用户与时间。每个决定都为该功能未来的一切改动移除了一类问题，这比为每次改动专门评审一遍更便宜。
:::
:::

## 评审与静态分析

由第二人执行的**代码评审**能抓住许多缺陷，而安全评审会添上特定的问题：不受信数据从哪里进入、流向哪里，每个敏感操作由哪些检查把守，每一条错误路径上会发生什么。评审者擅长设计层面的问题——少了一次授权检查、误用了一个密码学 API——不擅长穷尽式排查，这正是工具帮忙的地方。

**静态分析**不运行代码而检查代码。最简单的分析器给危险函数与危险模式打标（`gets`、用字符串拼格式的 SQL、对输入用 `eval`）；编译器的警告（`-Wall -Wextra -Wformat-security`）也是静态分析。更强的分析器追踪数据在程序中的流动。

::: definition 污点分析 {#def-taint}
**污点分析**把来自不受信**源**（请求参数、文件内容、环境变量）的值标记为**带污点的**，让污点随计算传播（由带污点的值算出的值也带污点），在指定的**净化函数**（sanitiser——与用途相称的校验或编码函数）处将其清除，并报告一切这样的路径：带污点的值未经该汇对应的净化就到达了敏感的**汇**（一条查询、一个 shell 命令、一个文件路径、一个 HTML 页面）。
:::

::: example 追踪污点 {#ex-taint}
在这个（虚构的）请求处理程序片段上追踪污点。源是 `request.args`；汇是 `db.execute`（SQL）与 `render`（HTML）；`int()` 是 SQL 的净化函数（整数带不动 SQL 语法），`html.escape` 之于 HTML。

```python
name  = request.args["name"]                 # 1
uid   = int(request.args["id"])              # 2
greet = "Hello, " + name                     # 3
db.execute("SELECT * FROM t WHERE id = " + str(uid))   # 4
db.execute("SELECT * FROM t WHERE name = '" + name + "'")  # 5
render("<p>" + html.escape(greet) + "</p>")  # 6
render("<p>" + greet + "</p>")               # 7
```
::: solution
| 行 | 效果 | 此后带污点的 |
|---|---|---|
| 1 | `name` 来自源 | `name` |
| 2 | `int()` 对 SQL 起净化作用 | `name`（`uid` 对 SQL 干净） |
| 3 | 拼接传播污点 | `name`、`greet` |
| 4 | `uid` 经净化后到达 SQL 汇 | ——无报告 |
| 5 | `name` 到达 SQL 汇 | **报告：SQL 注入** |
| 6 | `greet` 已对 HTML 转义 | ——无报告 |
| 7 | `greet` 到达 HTML 汇 | **报告：跨站脚本** |

两条发现。第 5 行的修复不是净化函数而是参数化查询，`db.execute("SELECT * FROM t WHERE name = ?", (name,))`，它让数据根本不进入查询的语法；第 7 行应使用转义后的值，或更好的，使用默认转义的模板引擎。注意净化函数是按汇区分的：`html.escape` 并不能让 `name` 在第 5 行安全，分析器必须知道哪个净化函数配哪个汇。
:::
:::

每个分析器都面对一个根本限制。

::: theorem 不存在完美的分析器 {#thm-no-perfect}
设**污点缺陷**指一次带污点的值到达汇的执行。不存在这样一个算法：对任意程序，它总能停机，并正确回答该程序是否存在带污点缺陷的执行。因此，每个能停机的分析器要么漏掉一些缺陷（是**不可靠的**），要么上报一些并无缺陷的程序（是**不完整的**），或两者兼有。
:::

::: proof
把停机问题归约过来（[[theory-of-computation/reductions]]）。给定图灵机 $M$ 与输入 $w$，构造程序 $P_{M,w}$：从源读入一个值 $x$；模拟 $M$ 在 $w$ 上运行；若模拟停机，就把 $x$ 交给汇。$P_{M,w}$ 有污点缺陷当且仅当 $M$ 在 $w$ 上停机，且该构造是可计算的。于是，一个总能停机且永远正确的分析器就能判定停机问题，而这不可能。（这是赖斯定理（Rice）的一个实例：程序行为的任何非平凡性质都是不可判定的。）
:::

因此实用的分析器必须作出取舍。**可靠**（sound）的工具（用于安全攸关的代码，常常配合标注）把一切可能是缺陷的都报出来，接受误报；多数商业与开源缺陷查找器刻意选择不可靠以压低误报，因为开发者会不再去读那些通常出错的警告——[[security/network-security#prop-base-rate]] 的基率问题换了个面目出现。它们的质量像检测器的质量一样度量。

::: example 分析器的查准率与查全率 {#ex-precision}
某代码库里存有 $40$ 个真实的注入缺陷（后来由别的途径查明）。一个分析器产生 $120$ 条警告，其中 $30$ 条是真实缺陷。计算它的查准率与查全率；再计算一项把警告削减到 $40$ 条、其中 $24$ 条为真者的配置变更的效果。
::: solution
**查准率**是警告中真者的比例：$30/120 = 25\%$。**查全率**是真实缺陷中被报告的比例：$30/40 = 75\%$。变更之后，查准率 $24/40 = 60\%$，查全率 $24/40 = 60\%$。孰优孰劣取决于用途：第二种配置浪费的评审时间少得多（假警告 $16$ 条而不是 $90$ 条），在日常开发中更可能被认真对待；第一种找到更多缺陷，或许适合一次性的安全审计。许多团队对每次变更运行高查准率的配置，并周期性地运行高查全率的配置。
:::
:::

## 面向意外的测试：模糊测试

普通测试检查程序在程序员想到的输入上表现正确。攻击者用的是程序员没想到的输入。**模糊测试**自动生成海量的这类输入，并盯着失效的发生。

::: definition 模糊测试 {#def-fuzzing}
**模糊测试器**（fuzzer）反复生成输入、在其上运行程序，并记录那些触发由**判定器**（oracle）检出的失效的输入：一次崩溃、一次失败的断言、一次挂起、一个意外异常，或 AddressSanitizer 之类净化器（sanitiser）的报告。**生成型** fuzzer 从头构造输入（随机的或按语法的）；**变异型** fuzzer 修改来自示例**语料库**的输入；**覆盖引导型** fuzzer（AFL、libFuzzer）对程序插桩，把每个触达新代码的变异输入收进语料库，并对其继续变异。
:::

巴顿·米勒（Barton Miller）1990 年的研究——随机输入让受测 Unix 工具中约四分之一到三分之一崩溃——开创了这一领域。它的现代形态，覆盖引导的模糊测试配合各类净化器，已发现数以万计的缺陷；Google 的 OSS-Fuzz 服务自 2016 年起不间断地对关键开源项目做模糊测试。

引导的威力从概率看得最清楚。缺陷通常躲在随机输入几乎从不能通过的检查后面——一个魔数、一个版本字段、一个校验和。

::: proposition 魔数的代价 {#prop-magic}
设某个缺陷只有前 $k$ 个字节等于某个固定串的输入才能到达，而 fuzzer 生成的输入各字节独立且均匀。则每个输入以概率 $2^{-8k}$ 到达缺陷，首次成功前的期望输入数为 $2^{8k}$。反之，若程序的比较逐字节进行，而 fuzzer 凡通过更多一个字节的输入就保留（当每个字节的比较各是一个分支时，覆盖反馈正是如此），则期望数至多 $k \cdot 2^8$。
:::

::: proof
对独立均匀的字节，每个字节以概率 $2^{-8}$ 匹配，故全部匹配的概率为 $2^{-8k}$；首次成功前的试验次数服从几何分布，均值为 $1/2^{-8k} = 2^{8k}$。有反馈时，考察阶段 $j$：此时语料库里有一个匹配前 $j - 1$ 个字节的输入，fuzzer 把第 $j$ 个字节变异成均匀随机的值；每次尝试以概率 $2^{-8}$ 成功，故阶段 $j$ 期望需要 $2^8$ 次尝试（若 fuzzer 偶尔变异到别的字节则更多，这只改变常数）。对 $k$ 个阶段用期望的线性性，总数为 $k \cdot 2^8$（乘以该常数）。
:::

对一个 4 字节的魔数，这就是 $2^{32} \approx 4.3 \times 10^9$ 次盲打对约 $1000$ 次引导。编译器还把多字节比较拆成单字节分支，进一步帮助引导；现代的 fuzzer 还直接读取运行中程序里比较运算的操作数。

::: widget plot
f: 1 - exp(-x/2^k)
x: 0, 100000
y: 0, 1
sliders: k=16:8:32:1
labels: P(bug found after x random inputs)
caption: 随机 fuzzer 在 $x$ 个输入后通过某个 $k$ 比特检查的概率 $1 - (1 - 2^{-k})^x \approx 1 - e^{-x/2^k}$（[[#prop-magic]]）。$k = 16$（一个两字节魔数）时，十万个输入几乎必定成功；把 $k$ 调到 $24$ 或 $32$，曲线便塌平到横轴上。引导式模糊测试把一个 $k$ 比特的检查拆成小步，把指数 $2^k$ 变成了一串小项之和。
:::

::: example 模糊测试一个玩具解析器 {#ex-fuzz}
一个为杜撰的记录格式写的小解析器，要么返回条目列表，要么抛出 `FormatError`；任何其他行为都是缺陷。比较一个只喂随机字节的 fuzzer 与一个用单个合法输入做种子的变异 fuzzer。
::: solution
```python
import random

class FormatError(Exception):
    """parse() 按文档规定拒绝畸形输入的方式。"""

def parse(data: bytes) -> list[bytes]:
    """玩具格式：b"TR"、版本字节、条目数字节，然后是 count 个条目（长度字节 + 数据）。
    版本 2 在条目之后多出一个字节的校验和。"""
    if len(data) < 4 or data[:2] != b"TR":
        raise FormatError("bad header")
    version, count, pos, items = data[2], data[3], 4, []
    for _ in range(count):
        if pos >= len(data):
            raise FormatError("truncated")
        n = data[pos]
        if pos + 1 + n > len(data):
            raise FormatError("truncated entry")
        items.append(data[pos + 1:pos + 1 + n]); pos += 1 + n
    if version == 2 and sum(map(len, items)) % 256 != data[pos]:   # 缺陷：pos 可能已越过末尾
        raise FormatError("bad checksum")
    return items

def run(gen, trials, rng):
    """把生成的输入喂给 parse()；除正常返回与 FormatError 外，任何情况都是缺陷。"""
    for i in range(1, trials + 1):
        x = gen(rng)
        try:
            parse(x)
        except FormatError:
            pass
        except Exception as e:
            return i, x, type(e).__name__
    return trials, None, None

def random_bytes(rng):
    return bytes(rng.randrange(256) for _ in range(rng.randrange(1, 12)))

SEED = b"TR\x01\x01\x03abc"                                  # 一个合法输入
def mutate(rng):
    x = bytearray(SEED)
    for _ in range(rng.randrange(1, 3)):                     # 改动一到两个字节
        x[rng.randrange(len(x))] = rng.randrange(256)
    return bytes(x)

print("random:  ", run(random_bytes, 200_000, random.Random(1)))
print("mutation:", run(mutate, 200_000, random.Random(1)))
```

```console
random:   (200000, None, None)
mutation: (856, b'TR\x02\x01\x03abc', 'IndexError')
```

随机字节从未通过"两字节头加上版本字节 `2`"这一关——按 [[#prop-magic]]，还没算上那些结构性检查，期望就需要约 $2^{24} \approx 1.7 \times 10^7$ 个输入。变异 fuzzer 从一个合法输入出发，只需把版本字节改成 `2`（单次单字节变异的概率约 $\frac{1}{8} \cdot \frac{1}{256}$），在 $856$ 个输入处就发现了缺陷：一条缺了校验和字节的版本 2 记录使 `data[pos]` 越过末尾读取。修复就是补上缺失的越界检查——`if pos >= len(data): raise FormatError("missing checksum")`——而那个失败输入要进入回归测试套件，让这个缺陷一去不返。在 C 里，同样的错误是一次越界读，只有当 fuzzer 带着净化器运行才可能被发现；Python 的边界检查把它变成了一个异常。
:::
:::

模糊测试补充而非取代其他测试。**基于性质的测试**（[[software-engineering/testing]]）陈述对所有输入都应当成立的性质（解码是编码的逆）；**差分测试**对同一规格运行两个实现，把不一致处标出来；**净化器**把悄无声息的内存与未定义行为缺陷变成响亮的失败。**渗透测试**——获授权的专家像对手那样攻击系统、并受一份关于范围的文字协议约束——检验整个部署，包括配置和人。对你并不拥有、或未获明确许可测试的任何系统做测试，既不道德，在多数国家也违法（[[software-engineering/professional-ethics]]）。

::: quiz
一个 fuzzer 在一个解析器上跑了一周，没有发现崩溃。你能得出什么结论？

- [ ] 该解析器没有内存安全缺陷。
- [x] 只能说明它生成的输入配合其判定器没有暴露失效；躲在它从未通过的检查后面的缺陷、以及判定器看不见的失效，仍可能存在。
- [ ] 若 fuzzer 是覆盖引导的，该解析器就是安全的。
- [ ] 再测更久也不会有新发现。
::: solution
测试只能表明缺陷之所在，永远不能表明缺陷之不存在。覆盖率报告显示 fuzzer 到达了哪些代码；未到达的代码没有被测试，已到达的代码里也可能藏着需要特定值的缺陷，或不带净化器就不崩溃的缺陷。改进种子语料库、添加格式字典、启用净化器、为更深层的函数编写测试脚手架，常常能找到更多。
:::
:::

## 供应链

现代应用主要由别人的代码构成：库、框架、构建工具、容器基础镜像，以及构建和分发它们的服务。每一环都是可信计算基的一部分，而攻击者正日益以链条而非产品为目标。2021 年 12 月的 Log4Shell 漏洞（CVE-2021-44228）蛰伏在一个日志库中，而这个库常常隔着好几层依赖，嵌在数量庞大的 Java 应用里，其所有者甚至不知道自己用了它。2020 年 12 月发现的 SolarWinds 事件中，恶意代码被插入供应商的构建流程，于是签好名的更新把它送到了成千上万的客户手里。2024 年 3 月，安德烈斯·弗罗因德（Andres Freund）在调查 SSH 登录变慢的小问题时，发现压缩库 xz-utils 被一个在项目里花了约两年攒下信任的维护者安了后门（CVE-2024-3094）；此事幸而在到达主流 Linux 发行版的稳定发布之前被查获。

防御针对每一环。

- **知道你发布的是什么。**一份**软件物料清单**（software bill of materials，SBOM，格式如 SPDX 与 CycloneDX）列出每一个组件与版本，于是漏洞公告一出，你能在几分钟内查明自己是否受影响——这正是 Log4Shell 事件中许多机构答不上来的问题。
- **让依赖少、新、并锁定版本。**用锁文件锁定精确版本并配校验和，深思熟虑且及时地更新，优先选择维护良好的项目。自动化工具会把依赖与漏洞数据库相互比对。
- **保护构建。**构建在隔离的、用完即弃的机器上，从经评审的源代码出发进行；产物签名；**溯源**（provenance）记录（如 SLSA 框架所做）写明每个产物由哪份源代码、哪次构建产生。**可复现构建**——同样的源代码在独立机器上产出比特级相同的输出——让任何人都能核查二进制与其源代码是否相符。
- **核验你安装的。**校验软件包与更新的签名，所用密钥一旦被窃须能被发现；透明日志（如 Sigstore，2021）公开记录每一个签名，被窃密钥的滥用因此无所遁形。
- **支持维护者。**大量关键基础设施由少数不领薪的志愿者维护；xz 事件归根结底是一场针对不堪重负的维护者的社会攻击。

::: warning "我们的代码经过评审，所以产品是安全的"
评审自己的代码是必要的，但远远不够。肯·汤普森（Ken Thompson）的图灵奖演讲《对信任之信任的反思》（"Reflections on trusting trust"，1984）描述了一个被改动的编译器：它既往登录程序里安插后门，*又*在每次编译自身的干净副本时把这个改动重新安插进去——于是检查全部源代码也一无所获。他的结论是："你不能信任任何并非完全由你自己创造的代码。"没人能亲手创造一切，所以实际的回答是减少并核验信任：依赖要少、构建可复现、独立重建（大卫·惠勒（David Wheeler）的**多样化双重编译**用一个独立编译器去编译，就能检出汤普森式的编译器）、签名与透明。
:::

## 漏洞披露与响应

无论流程多好，漏洞都会在发布后被发现——被供应商、被用户、被研究者，或被攻击者。接下来发生什么，决定它们造成多大伤害。

::: definition 协同漏洞披露 {#def-cvd}
在**协同漏洞披露**（coordinated vulnerability disclosure）中，发现者把漏洞私下报告给供应商（或经由国家 CERT 之类的协调方），供应商予以确认，开发并发布修复，待用户有过合理的升级机会后公开细节，通常在商定或公示的期限内。漏洞被赋予一个 **CVE 标识符**（一份自 1999 年维护的目录），其严重性常用 $0$ 到 $10$ 的 **CVSS** 分数概括。
:::

每个要素的存在都有理由。私下报告让攻击者占不到先手；一个**期限**（Google Project Zero 自 2014 年起的政策是 $90$ 天，修复指日可待时略有宽限）使供应商不能把报告无限期压在手里；公开让防御者看清风险、研究界从中学习。供应商靠公开的政策与联系渠道（一个 `security.txt` 文件，RFC 9116，2022）、承诺对政策范围内善意研究不诉诸法律、以及常常设有**漏洞赏金**（bug bounty）为有效报告付费，让报告变得容易。国际标准 ISO/IEC 29147（披露）与 30111（处置）描述了供应商一侧的做法。

::: example 一条披露时间线 {#ex-disclosure}
一位研究者在她获准测试的软件中，发现某供应商的应用存在一个让一个客户能读到另一个客户发票的缺陷。在 90 天政策下写出一条合理的日程，并说明每一步供应商应做什么。
::: solution
**第 0 天**：她通过供应商公布的渠道报告，附最简描述与复现步骤，并且只访问演示问题所必需的数据。**第 2 天**：供应商确认收到，分配一个跟踪编号与一个严重性估计（越权访问其他客户的数据：高）。**第 2–10 天**：供应商分诊、复现、定位根因——少了一个逐对象的授权检查（[[security/access-control#def-refmon]]）——在自己代码的其他地方搜同一个模式，并检查日志中过往的被利用迹象。**第 21 天**：修复部署（对托管服务，供应商直接部署；对安装式软件，则发一份更新与一份安全公告）。**第 21 天起**：若日志显示数据曾被访问，供应商的事件响应与数据泄露通知义务随即开始（[[security/privacy]]）。**第 90 天，或经协商更早**：发布联合公告，附 CVE 标识符、对研究者的致谢、受影响版本与修复办法；随后补上回归测试，并复盘当初为什么漏掉了这个检查（一个设计层面的修复，例如一个自动强制实施所有权的访问层）。供应商最重要的两个动作是变体搜索与根因修复，它们能挡掉接下来的十份报告。
:::
:::

披露只是响应的可见部分。在其背后，还有供应商客户一侧的**补丁管理**（多数成功的攻击利用的是早已存在修复的漏洞）、对利用行为的**监视**，以及 [[security/malware]] 的事件响应流程。公告写得清楚、修复发得及时、把升级做成自动的供应商，对其用户的保护远胜于发布更少、更安静的修复的供应商。

::: history
肯·汤普森（Ken Thompson）的《对信任之信任的反思》发表于 1984 年。巴顿·米勒（Barton Miller）的模糊测试研究发表于《ACM 通讯》（*Communications of the ACM*，1990；该实验始于 1988 年的一个课堂项目）。CVE 列表由 MITRE 于 1999 年推出。比尔·盖茨 2002 年 1 月的《可信赖计算》备忘录催生了微软的安全开发生命周期；首版 CVSS 发布于 2005 年，4.0 版发布于 2023 年。污点检查出现在 Perl 的污点模式（1989）中；大规模静态缺陷查找成长自道森·恩格勒（Dawson Engler）的元级编译（2000）与随之而来的 Coverity 工具等工作。康斯坦丁·谢列布里亚内（Konstantin Serebryany）及其同事于 2012 年引入 AddressSanitizer；米哈尔·扎莱夫斯基（Michał Zalewski）2013 年发布覆盖引导的模糊测试器 AFL，libFuzzer 随后于 2015 年问世，Google 的 OSS-Fuzz 于 2016 年。Google Project Zero（2014）让固定的披露期限广为流行。NIST 于 2022 年发布其安全软件开发框架；2024 年的 xz-utils 后门把开源维护的安全问题带到了大众视野。
:::

## 后续内容

本章把课程的思想转化为实践，为课程收束。威胁建模（[[security/security-principles]]）成了一种设计活动；访问控制的错误（[[security/access-control]]）以及注入与内存缺陷（[[security/web-security]]、[[security/memory-safety]]）成了评审、分析与模糊测试的靶子；对漏网之鱼的处置则接入 [[security/malware]]。能够*证明*整类缺陷不存在的验证技术——类型系统、模型检测、演绎验证——在 [[software-engineering/verification]] 与 [[programming-languages/type-systems]]；安全工作的职业责任，包括测试授权与负责任披露，在 [[software-engineering/professional-ethics]]。

::: summary
- 安全融入每个阶段（[[#def-sdl]]）：需求与滥用用例、威胁模型驱动的设计、安全的实现、安全测试，以及带着响应流程的发布。
- 最好的设计决策移除整个缺陷类别：内存安全的语言、构造即安全的接口（参数化查询、默认转义的模板）、解析而非校验、允许列表、安全默认、解析器的隔离。
- **污点分析**（[[#def-taint]]）让不受信数据从源经净化函数到汇一路被追踪；没有分析器能既可靠又完整（[[#thm-no-perfect]]），于是工具们拿**查准率**换**查全率**。
- 配合净化器的**模糊测试**（[[#def-fuzzing]]）能找到意外；覆盖引导把一个 $k$ 字节检查的 $2^{8k}$ 搜索变成约 $k \cdot 2^8$ 步（[[#prop-magic]]）。模糊测试能发现缺陷；不能证明缺陷不存在。
- **供应链**是可信计算基的一部分：了解你的组件（SBOM）、锁定并更新它们、保护并复现构建、核验签名——对信任之信任没有彻底的解法。
- **协同披露**（[[#def-cvd]]）——私下报告、修复、期限、附 CVE 的公告——加上根因修复与变体搜索，能把每一个被发现的漏洞化作将来更少的漏洞。
:::

## 习题

::: exercise 魔数的盲搜 {level=1 check="65536"}
某个缺陷只有前两个字节为 `0xCA 0xFE` 的输入才能到达。期望需要多少个均匀随机的输入才能到达它？（填入数字。）
::: solution
由 [[#prop-magic]]，$k = 2$，$2^{16} = 65{,}536$。
:::
:::

::: exercise 引导搜索 {level=1 check="1024"}
用 [[#prop-magic]] 的逐字节上界，一个覆盖引导的 fuzzer 大约需要多少个输入才能通过一个 4 字节的魔数？（填入上界 $k \cdot 2^8$。）
::: solution
$4 \times 256 = 1024$，而盲打用的随机输入需要 $2^{32} \approx 4.3 \times 10^9$。
:::
:::

::: exercise 查准率与查全率 {level=1 check="0.8"}
某分析器报告 $50$ 条警告，其中 $40$ 条是真实缺陷；代码中共有 $100$ 个真实缺陷。它的查准率是多少？（填入小数。）
::: solution
查准率 $= 40/50 = 0.8$；查全率 $= 40/100 = 0.4$。
:::
:::

::: exercise 用错净化函数的污点 {level=2}
在 [[#ex-taint]] 中，一位开发者用 `db.execute("SELECT * FROM t WHERE name = '" + html.escape(name) + "'")` 把第 5 行"修好"了。污点分析器还该报告它吗？解释之，并给出正确的修复。
::: solution
该报。`html.escape` 把 `<`、`>`、`&` 和引号编码成 HTML 实体，恰好把 `'` 变成 `&#x27;`——但净化函数是按汇区分的，HTML 转义对 SQL 总体而言并不是防线（它对反斜杠和某些 SQL 方言的其他语法原封不动，还会破坏含这些字符的合法数据）。正确的分析器只把 `html.escape` 当作 HTML 汇的净化函数，这条流仍要报告。正确的修复是参数化查询，`db.execute("SELECT * FROM t WHERE name = ?", (name,))`，它绝不让 `name` 被当作 SQL 解释。
:::
:::

::: exercise 修复并回归 {level=2}
修复 [[#ex-fuzz]] 解析器中的缺陷，把变异 fuzzer 以 $200{,}000$ 个输入重跑一遍，并解释为什么即便缺陷已修复，导致崩溃的输入也应加入测试套件。
::: solution
在校验和比较之前加上越界检查：

```python
    if version == 2:
        if pos >= len(data):
            raise FormatError("missing checksum")
        if sum(map(len, items)) % 256 != data[pos]:
            raise FormatError("bad checksum")
```

重跑 `run(mutate, 200_000, random.Random(1))` 现在返回 `(200000, None, None)`：没有任何输入产生过成功或 `FormatError` 之外的结果。导致崩溃的输入 `b'TR\x02\x01\x03abc'` 应当变成一条回归测试，断言 `parse` 抛出 `FormatError`，因为后来的改动（一次重构、格式的第三个版本）都可能把同一个错误带回来，而存下的输入能在每次构建时花几毫秒复查一遍。模糊测试的语料库出于同样的理由被保存下来。
:::
:::

::: exercise 读一份 SBOM {level=2}
某库 `logfmt` 的 $2.14.0$ 到 $2.14.1$ 版被公告存在漏洞。你的应用的 SBOM 把 `logfmt 2.13.3` 列为直接依赖，并经另一个库把 `logfmt 2.14.1` 列为传递依赖。你受影响吗？你该做什么？没有 SBOM 你又该做什么？
::: solution
很可能受影响：传递的那份副本 $2.14.1$ 在受影响区间内，而许多生态里两份副本（或只有较新的那份）最终都会进入构建，所以你必须查明实际加载的是哪一份、有漏洞的代码路径是否可达。把中间那个库升级到依赖修复版 `logfmt` 的版本，或把传递版本覆写成修复版，重新构建、测试、部署；然后在暴露窗口的日志里查找被利用的迹象。没有 SBOM，你还得先发现 `logfmt` 究竟在不在这个产品里——对传递依赖，往往靠扫描每一个构建产物——而这正是许多机构在 Log4Shell 中吃过的延误。
:::
:::

::: exercise 一个可判定片段的分析器 {level=3}
[[#thm-no-perfect]] 说污点缺陷在一般情况下不可判定。现在改看直线程序：一串形如 `x = e` 的赋值，其中 `e` 是一个源、一个常量、一个变量、施加于变量的一个净化函数，或变量与常量的拼接，其后是对变量的汇调用。为这个片段给出一个能停机、可靠且完整的算法，证明其正确，并说明真实程序中的哪些特性会破坏这一论证。
::: solution
按顺序处理语句，维护带污点变量的集合 $T$：`x = source` 把 `x` 加入；`x = constant` 或 `x = sanitiser(y)` 把 `x` 移出；`x = y` 或拼接时，当且仅当表达式中某个变量属于 $T$ 才把 `x` 置为带污点；`sink(x)` 当且仅当 `x` 属于 $T$ 才报告。这在程序规模上是线性时间的。**正确性**，对已执行语句的数目作归纳：不变式是"每条语句之后，$x \in T$ 当且仅当 $x$ 的当前值派生自某个源而未经净化函数"。它最初成立（$T$ 为空，没有任何值被派生）。每条赋值规则都按污点传播的定义为被赋值的变量重建不变式，其余变量不受影响。直线程序恰有一次执行，所以分析器在汇处的报告对那次执行是正确的：可靠（不漏缺陷）且完整（不误报）。这一论证会在**分支与循环**（分析器必须归并各路径的集合，而一条路径是否可行取决于数据——这是通往不可判定性的道路）、**函数调用与别名**（两个名字指向同一个值），以及**隐流**（`if secret: x = 1`）处断裂——后者不经直接赋值而传播信息。
:::
:::

::: exercise 含噪声引导搜索的期望代价 {level=3}
改进 [[#prop-magic]]：每个阶段，fuzzer 从 $L$ 个字节位置中等概率选一个去变异，只有变异到下一个未匹配的位置（且变到正确的值）才算前进。证明通过一个 $k$ 字节检查的期望输入数为 $k \cdot L \cdot 2^8$，并对 $k = 4$、$L = 64$ 求值。
::: solution
每个阶段中，一个输入算前进，当且仅当 fuzzer 选中了正确的位置（概率 $1/L$）且变到了正确的值（概率 $2^{-8}$），二者独立：每个输入成功的概率为 $1/(L \cdot 2^8)$，故阶段长度服从均值 $L \cdot 2^8$ 的几何分布。$k$ 个阶段先后通过，故由期望的线性性，总数为 $k \cdot L \cdot 2^8$。$k = 4$、$L = 64$ 时：$4 \times 64 \times 256 = 65{,}536$ 个输入——仍比盲打所需的 $2^{32}$ 少约 $65{,}000$ 倍，而每秒运行数千个输入的 fuzzer 不到一分钟就能通过它。
:::
:::
