一个团队开发了一款病房应用，供护士记录他们给出的药。需求规格来自与医院药房和 IT 部门的一次会议，应用通过了每一项测试，速度也很快。上线三周之后，一个病房里的护士却在手套背面记下剂量，等换班结束时再统一录入。没有人要她们这样做，也没有人预料到这一点。这款应用需要一双手，还需要在一台共享平板上登录，而平板一分钟就锁屏；病床边的护士既没有空闲的双手，也没有这一分钟——她们正扶着病人的手臂。规格说明里没有任何一条是错的，它只是描述了一份工作，而没有人真正按照会议设想的方式去做它。

**以用户为中心的设计**（user-centred design，UCD）正是为了避免这种结局而来的学问：在设计之*前*和之*同时*就弄清楚谁将使用一个系统、他们想做什么、在什么情况下做，并与这些人——而不是与建造它的人——一起检验设计。[[software-engineering/requirements]] 从开发者的角度讲过需求获取——访谈、观察、工作坊。本章更深入的正是人的这一面：可用性是什么、如何对它作出规定，以人为中心的设计过程，理解用户及其工作的现场方法，如何以已知可靠的信度分析所学到的东西，如何描述用户与任务（人物角色、场景、层次任务分析），以及唐·诺曼（Don Norman）从日常失败中提炼出的设计原则。

## 什么是可用性

"容易使用"不是一条谁都能检验的需求。关于可用性的国际标准给这个词下了一个包含三个可测量成分的定义，而每个成分都是相对于某种特定情形的。

::: definition 可用性 {#def-usability}
**可用性**是指**指定用户**在**指定使用情境**下，以**有效性**、**效率**和**满意度**达成**指定目标**的程度（ISO 9241-11:2018）。其中

- **有效性**指用户达成目标的精确与完备程度（例如任务完成率与错误率）；
- **效率**指所用资源与所达结果之比（时间、精力、成本）；
- **满意度**指用户的生理、认知与情感反应满足其需要和期望的程度（常用 SUS 之类的问卷测量——[[hci/usability-evaluation]]）；
- **使用情境**包括用户、他们的目标与任务、可用的资源，以及技术、物理、社会、文化和组织环境。
:::

这个定义使可用性成为*情境中的系统*的性质，而不是系统孤立地具有的性质。一款应用对坐在桌前的药剂师可能非常好用，对病床边的护士却可能根本没法用。它同时使可用性可测量："一名受训护士应能用单手在 15 秒内记录一次给药，且每 200 次记录中记录错误不超过 1 次"，按 [[software-engineering/requirements#def-verifiable]] 的意义，这就是一条可验证的可用性需求。

**用户体验**（user experience，UX）是一个更宽泛的术语，ISO 9241-210 把它定义为使用或预期使用一个系统所产生的用户的知觉与反应——包括使用之前、之中之后的情感、信念与偏好。可用性只是其中一部分；信任、愉悦、意义以及围绕产品的品牌是其余的部分。

## 以人为中心的设计过程

1985 年，约翰·古尔德（John Gould）与克莱顿·刘易斯（Clayton Lewis）在 *Communications of the ACM* 上发表了 "Designing for usability: key principles and what designers think"。他们提出三条原则——**早期关注用户与任务**、对模拟与原型的**使用情况作实证测量**、以及**迭代设计**——然后调查了 447 名系统设计者，发现大多数人在被问到会如何设计一个系统时，一条也没有提到，或者只提到其中一条。这些原则听起来不言自明；调查表明它们并没有被实践。如今它们已被写入一项国际标准。

::: definition 以人为中心的设计 {#def-hcd}
**以人为中心的设计**（human-centred design，ISO 9241-210:2019）是一种交互式系统开发方法，它通过关注用户及其需要与需求、并运用人因学、可用性知识和技术，使系统可用且有用。其原则是：

1. 设计建立在对用户、任务与环境的明确理解之上；
2. 用户参与设计与开发的全过程；
3. 设计由以用户为中心的评估驱动并加以完善；
4. 过程是迭代的；
5. 设计关注完整的用户体验；
6. 设计团队包含多学科的技能与视角。

它的四项环环相扣的活动反复进行，直到设计满足需求：**理解并规定使用情境**；**规定用户需求**；**产出设计方案**；以及**依据需求评估设计**。
:::

这个循环与敏捷迭代（[[software-engineering/software-process]]）形状相同，也能很好地嵌入其中——只要用户研究与评估是每次迭代的一部分，而不是开头的一个阶段。本章其余部分涵盖前两项活动；[[hci/prototyping]] 涵盖第三项，[[hci/usability-evaluation]] 与 [[hci/experiments]] 涵盖第四项。

::: warning "我也是用户，所以我知道用户要什么"
开发者几乎从不具有代表性。他们知道系统内部如何工作（所以它的概念模型对他们不言自明），通常是熟练的计算机用户，而且对复杂性异乎寻常地宽容。他们还无法为了像新人那样看待界面而*忘掉*自己知道的东西——心理学家称之为**知识的诅咒**。同样的告诫也适用于经理和替别人说话的"高级用户"。要与符合指定特征的人一起测试，在他们的情境中测试，并把自己的反应当作假设。
:::

## 理解用户及其工作

现场方法在能揭示什么上各有不同。一个有用的划分是人们**说的**（访谈、问卷、焦点小组）与人们**做的**（观察、情境查询、日志与分析数据）之别；人们对自己行为的陈述系统性地不完整，因为许多熟练工作是隐含的、例行化的，而且人们报告的是他们自认为*应该*做的事。

| 方法 | 你能了解什么 | 典型规模 | 主要弱点 |
|---|---|---|---|
| 半结构化访谈 | 目标、动机、词汇、问题 | 5–20 人 | 是陈述，不是行为 |
| 情境查询 | 真实的工作实践、变通办法、环境 | 5–15 场 | 耗时、观察者效应 |
| 日记研究 | 数天数周的行为 | 10–30 人 | 参与者负担、中途退出 |
| 问卷调查 | 态度与行为有多普遍 | 数百到数千人 | 只能问出你已经想到要问的事 |
| 分析数据与日志 | 用户在现有系统中实际做什么 | 所有人 | 显示*做了什么*，不显示*为什么* |

### 访谈

**半结构化访谈**依照一份备好的开放问题指南进行，但允许访谈者追问任何显得有意思的话题。好的访谈问题询问**具体的过去事件**，而不是一般化的陈述或假设情形（"跟我讲讲您上次夜里给药的情形"，而不是"您通常怎么记录剂量？"或"您会用语音功能吗？"），是**开放**的而不是是非题，是**中立**的而不带诱导。人们很不擅长预测自己的未来行为，又乐于对假设表示赞成，所以"您会用……吗？"这类问题多半测量的只是客气。

::: example 修改一份访谈指南 {#ex-interview}
一名学生为使用某学校在线缴费系统的家长草拟了下面几个问题。指出每个问题的毛病并改写它。

1. "您不觉得缴费页面让人糊涂吗？"
2. "您多久给学校活动交一次费？"
3. "如果应用提醒您缴费，您会喜欢吗？"
4. "您用网站还是用应用？"
::: solution
1. *诱导*：它暗示了期望的答案并邀请附和。改写："请带我回到您上一次在学校系统里缴费的那次经历，跟我说说发生了什么。"——然后逐步追问（"您当时预期会发生什么？"）。
2. *一般化*：人们对频率的估计很差，答案将是一个猜测。应当询问具体的近期过去（"您最近一次缴费是什么时候？在那之前呢？"），或者从缴费日志中测量频率——日志比任何访谈都更能回答这个问题。
3. *假设且诱导*：对一个免费的功能几乎人人都会说好。改问问题本身："您有没有错过过缴费期限？讲讲那次的情况。"如果错过期限既常见又令人难受，提醒可能有用；访谈发现的是一个需要，而不是验证了一个方案。
4. *封闭*（是非题或二选一），而且单独几乎没有用处。应当问："您上一次缴费时人在哪里、用的是什么设备？"——情境（校门口的手机、公交车上）才是有价值的内容。
:::
:::

### 情境查询

休·拜尔（Hugh Beyer）与卡伦·霍尔茨布拉特（Karen Holtzblatt）的**情境查询**（contextual inquiry，出自其著作 *Contextual Design*，1998）把观察与访谈结合起来。研究者在一个人的真实场所观察他做真实的工作，并随着事情发生随时提问，采取一个**学徒**向**师傅**学艺的关系。四条原则指导着它：**情境**（到工作发生的地方去）、**伙伴**（由参与者主导、研究者跟随）、**解释**（把你的解释告诉参与者，以便他们纠正）与**焦点**（清楚你此行的任务是研究工作的那些方面）。情境查询正是发现"拿手套当便签本"这类事情的方法：护士不会在访谈里提到它，因为它不属于这份工作*被规定*应当如何做的一部分。

### 问卷与样本量

问卷测量某事有多*普遍*——前提是你已经知道该问什么，而这通常来自访谈。问卷的精度取决于回答份数，这由抽样理论的一个标准结果决定（[Maths Atlas：置信区间](/learn/maths/lesson.php?c=statistics&l=confidence-intervals)）。

::: proposition 比例的可误差范围 {#prop-moe}
设 $n$ 名回答者来自一个大总体的简单随机样本，该总体中比例为 $p$ 的人会回答"是"，$\hat p$ 为样本比例。由二项分布的正态近似，$p$ 的近似 95% 置信区间为 $\hat p \pm 1.96\sqrt{\hat p(1-\hat p)/n}$。其半宽（**可误差范围**）至多为 $0.98/\sqrt{n}$；要使无论 $p$ 为何值误差范围都不超过 $m$，只需

$$
n \ge \left(\frac{1.96}{2m}\right)^2.
$$ {#eq-survey-n}
:::

::: proof
"是"的个数服从二项分布，均值为 $np$、方差为 $np(1-p)$，于是 $\hat p$ 的均值为 $p$、标准差为 $\sqrt{p(1-p)/n}$；$n$ 大时它近似正态，且 $\Prob(\lvert \hat p - p\rvert \le 1.96\,\sigma) \approx 0.95$。函数 $p(1-p)$ 的导数为 $1 - 2p$，在 $p = 1/2$ 处为零，此处它达到最大值 $1/4$。故误差范围 $1.96\sqrt{p(1-p)/n} \le 1.96 \sqrt{1/(4n)} = 0.98/\sqrt n$，而它 $\le m$ 当且仅当 $n \ge (0.98/m)^2 = (1.96/2m)^2$。
:::

要使误差范围为 $\pm 5$ 个百分点，$n \ge (1.96/0.1)^2 = 384.16$，即需要 385 份回答；要 $\pm 10$ 个百分点，只需 97 份。误差范围只随 $\sqrt n$ 收缩：要把它减半，回答份数要变成四倍。

::: widget plot

x: 10, 1000
y: 0, 30
sliders: p=0.5:0.01:0.99:0.01
labels: \text{取 } p \text{ 时的误差范围}; \text{最坏情形 } 0.98/\sqrt{n}
caption: 95% 可误差范围（百分点）随回答份数 $n$ 的变化：第一条曲线对应真实比例 $p$，第二条曲线对应最坏情形 $p = 1/2$（[[#prop-moe]]）。把 $p$ 拖向 0 或 1：罕见的回答在绝对数值上测得更准。曲线很快就变平——从 400 份增加到 1,000 份，误差范围只从大约 5 个百分点缩到大约 3 个百分点。
:::

::: warning "我们有 5,000 份回答，所以结果很准"
[[#prop-moe]] 假定的是**随机样本**。挂在产品帮助页面上的问卷触达的是访问帮助页面的人——其中遇到问题的人比例偏高——而自愿回答者又经历了一次自我选择。任何样本量都纠正不了这种偏差：5,000 份自愿回答给出的是一个错误量的极其精确的估计。应当报告回答者如何招募、回答率、回答者与总体的差异，并把可误差范围当作不确定性的下界。
:::

### 需要多少访谈？

定性研究不估计比例，所以误差范围并不适用；但有一个相关的计算能告诉你，你能不能*遇到*某一类用户或问题。

::: proposition 观察到某种模式的概率 {#prop-detect}
设用户总体中有比例 $p$ 的人有某种需要、习惯或问题，你独立随机地研究 $n$ 个用户。至少有一人具有它的概率为

$$
P_n = 1 - (1-p)^n,
$$ {#eq-detect}

而 $P_n \ge c$ 当且仅当 $n \ge \ln(1-c) / \ln(1-p)$。
:::

::: proof
每位参与者不具有该模式的概率为 $1 - p$，且相互独立，所以 $n$ 人都不具有它的概率为 $(1-p)^n$，其补事件为 $1 - (1-p)^n$。不等式 $1 - (1-p)^n \ge c$ 即 $(1-p)^n \le 1-c$；取自然对数得 $n \ln(1-p) \le \ln(1-c)$，除以 $\ln(1-p) < 0$ 时反向。
:::

::: example 为罕见需求做访谈 {#ex-rare}
一家银行约 10% 的客户代他人理财（比如年迈的父母）。要随机访谈多少位客户，才有 90% 的把握至少遇到一位这样的人？这对招募意味着什么？
::: solution
由 [[#prop-detect]]，$n \ge \ln 0.1 / \ln 0.9 = 21.85$，故 $n = 22$：确实 $1 - 0.9^{22} \approx 0.902$、$1 - 0.9^{21} \approx 0.891$。而对一位照护者的单次访谈，几乎不足以理解其需要。所以对重要的少数群体不要依赖随机招募：要**有目的地招募**——刻意纳入几位照护者、几位屏幕阅读器用户、几位读写能力有限的人——因为定性研究的目的是覆盖各种情形的范围，而不是测量它们有多常见。同一个公式将在 [[hci/usability-evaluation]] 中再次出现，即发现可用性问题的尼尔森–兰道尔（Nielsen–Landauer）模型，其假设也将在那里受到检验。
:::
:::

经验上，格雷格·格斯特（Greg Guest）、阿尔文·邦斯（Arwen Bunce）与劳拉·约翰逊（Laura Johnson）（"How many interviews are enough?"，*Field Methods*，2006）对在西非两国女性中进行的 60 次访谈作了编码，发现他们最终使用的编码中的绝大多数在前十几次访谈里就已经出现。她们强调，这只适用于对相当同质的群体提出聚焦的问题；多样的群体与宽泛的问题需要更多访谈。诚实的做法是一直做到新的访谈不再改变你对事情的认识为止（**饱和**），并且对每个不同的用户群体分别做到这一点。

## 整理研究所得

现场研究会产出几个小时的录音和几十页笔记。两种广泛使用的分析方法把它们变成发现。

**亲和图**（affinity diagram，出自川喜田二郎（Kawakita）的 KJ 法）把每条观察写在单独一张卡片上，让团队*自底向上*把卡片分堆、给每堆命名，然后再对各堆进行归类，使主题从数据中浮现，而不是来自事先定好的框架。**主题分析**（thematic analysis；弗吉尼亚·布劳恩（Virginia Braun）与维多利亚·克拉克（Victoria Clarke），2006，发表于 *Qualitative Research in Psychology*）是更正式的形式：熟悉数据，生成初始**编码**（给文本片段的简短标签），在编码之间寻找主题，审查主题，界定并命名它们，最后写成报告。

当多名分析者对同一材料编码，或者编码将被计数时，你需要知道编码是否被一致地施加。原始一致率会高估信度，因为随机编码的分析者有时也会碰巧一致。

::: definition 科恩的 kappa {#def-kappa}
两名编码者各自给同样的 $n$ 个条目指定 $k$ 个类别之一。设 $p_o$ 为他们一致的条目比例，$a_j$ 与 $b_j$ 为第一、第二名编码者放入类别 $j$ 的条目数。**偶然一致率**为 $p_e = \sum_j a_j b_j / n^2$，**科恩 kappa 系数**（Cohen's kappa）为

$$
\kappa = \frac{p_o - p_e}{1 - p_e} \quad (p_e < 1).
$$
:::

::: proposition kappa 的解释 {#prop-kappa}
$\kappa = 1$ 当且仅当编码者在每个条目上都一致。若两名编码者以固定的边际频数独立地指定类别，则期望的观测一致率为 $p_e$，于是 kappa 把超出偶然的一致程度表示为超出偶然的可能的最大一致的分数；$\kappa < 0$ 表示一致程度不如偶然。
:::

::: proof
$\kappa = 1$ 当且仅当 $p_o - p_e = 1 - p_e$，即 $p_o = 1$。若两名编码者独立标注，各以概率 $a_j/n$ 与 $b_j/n$ 选择类别 $j$，则他们对某个给定条目在类别 $j$ 上一致的概率为 $(a_j/n)(b_j/n)$；对 $j$ 求和，期望的一致比例为 $\sum_j a_j b_j / n^2 = p_e$，故期望 $\kappa = 0$。分子 $p_o - p_e$ 是超出偶然而实际达成的一致，分母 $1 - p_e$ 是超出偶然所能达到的最大一致，所以 $\kappa$ 是二者之比；它为负当且仅当 $p_o < p_e$。
:::

::: example 编码者之间的一致性 {#ex-kappa}
两名研究者独立地把护士访谈的 40 个摘录编码为*变通办法*（W）、*对系统的信任*（T）或*时间代价*（C）。列联表（行：编码者 1；列：编码者 2）为

| | W | T | C |
|---|---|---|---|
| **W** | 14 | 2 | 1 |
| **T** | 1 | 9 | 3 |
| **C** | 0 | 2 | 8 |

计算他们的百分一致率与 kappa。
::: solution
对角线给出 $p_o = (14 + 9 + 8)/40 = 31/40 = 0.775$。行合计为 $17, 13, 10$，列合计为 $15, 13, 12$，于是 $p_e = (17 \cdot 15 + 13 \cdot 13 + 10 \cdot 12)/40^2 = 544/1600 = 0.34$，从而

$$
\kappa = \frac{0.775 - 0.34}{1 - 0.34} = \frac{0.435}{0.66} \approx 0.659.
$$

用程序检验：

```python
from collections import Counter

def cohen_kappa(a, b):
    """Cohen's kappa for two coders' labels a[i], b[i] of the same items."""
    n = len(a)
    p_o = sum(x == y for x, y in zip(a, b)) / n          # observed agreement
    ca, cb = Counter(a), Counter(b)
    p_e = sum(ca[k] * cb[k] for k in ca) / n**2          # agreement expected by chance
    return p_o, p_e, (p_o - p_e) / (1 - p_e)

table = {("W", "W"): 14, ("W", "T"): 2, ("W", "C"): 1,
         ("T", "W"): 1,  ("T", "T"): 9, ("T", "C"): 3,
         ("C", "W"): 0,  ("C", "T"): 2, ("C", "C"): 8}
a, b = [], []
for (x, y), k in table.items():
    a += [x] * k
    b += [y] * k
p_o, p_e, kappa = cohen_kappa(a, b)
print(f"n = {len(a)}, observed = {p_o:.3f}, chance = {p_e:.4f}, kappa = {kappa:.3f}")
```

```console
$ python3 kappa.py
n = 40, observed = 0.775, chance = 0.3400, kappa = 0.659
```

Landis 与 Koch（1977）一类的基准把 0.61–0.80 称为"显著的一致"，但这只是没有实证根据的约定；更有用的是看编码者*在哪些类别上*不一致。这里大多数不一致（9 处中的 5 处）发生在 T 与 C 之间："信任"与"时间代价"的两个定义彼此重叠，编码手册需要一条更锐利的规则（例如"抱怨延误属于 C，除非护士怀疑被记录的数据"）。一致率是改进编码的工具，不是合格证。
:::

## 描述用户与任务

研究发现必须变成设计团队每天都能使用的形式。

**人物角色**（personas）由艾伦·库珀（Alan Cooper）在《The Inmates Are Running the Asylum》（1999）中推广，是把原型用户当作具体的人来描述——姓名、照片、目标、挫折、技能与情境——由研究综合而成。人物角色给团队一个"我们在为谁设计？"的共享答案，取代那个随任何人想要的功能而随意变形的"弹性用户"。John Pruitt 与 Jonathan Grudin（"Personas: practice and theory"，2003）报告说，人物角色在微软有用，主要是作为交流的媒介；而且只有植根于数据、并在整个项目中保持活力时才起作用；在会议室里凭空发明的人物角色只是带了名字的刻板印象。它们还可能编码偏见：如果每个人物角色都年轻、视力正常、英语流利，团队就只会为这些人设计。

**场景**（scenarios）是一个人物角色在某种情境中追求目标的故事，在设计存在之前写下（*问题场景*），或描述拟议的设计将如何被使用（*活动场景*）；约翰·卡罗尔（John Carroll）的 *Making Use*（2000）发展了基于场景的设计。**旅程图**把一个用户在一个较长时段——买房、大病初愈——中跨越多个系统的步骤、接触点与感受铺陈出来，显示体验在哪里断裂。

### 层次任务分析

**任务分析**描述用户为达成目标所做的事，细到足以据以设计。使用最广的形式由 John Annett 与 Keith Duncan 于 1967 年提出。

::: definition 层次任务分析 {#def-hta}
**层次任务分析**（hierarchical task analysis，HTA）把一个目标描述成一棵树。每个节点是一个（子）目标；它的子节点是实现它的各子目标，编号 $1, 2, \dots$（目标 1 之下写作 $1.1, 1.2, \dots$，依此类推）；每个非叶节点带有一个**计划**，说明它的子节点按什么次序、在什么条件下被执行（依次、按需、任意次序、重复直到某条件成立）。当某个子目标是一个简单的、其难度或风险不足以进一步细化的动作时，分解就到此为止。
:::

::: example 售票机的层次任务分析 {#ex-hta}
为在车站售票机上购买一张单程票写一个层次任务分析，并据此发现设计问题。
::: solution
```text
0. 购买一张前往某目的地的单程票
   计划 0：依次做 1-2-3-4；若付款失败，重复 3 或放弃。
   1. 选择目的地
      计划 1：做 1.1；若列表中查无该目的地，做 1.2 后回到 1.1。
      1.1 从常用车站列表中选择目的地
      1.2 键入目的地名称进行搜索
   2. 选择车票
      计划 2：依次做 2.1-2.2-2.3。
      2.1 选择单程或往返
      2.2 选择票种（非高峰、随时、预订）
      2.3 如持有铁路卡，添加折扣
   3. 付款
      计划 3：做 3.1 或 3.2。
      3.1 刷卡支付（插卡或挥卡；需要时输入 PIN）
      3.2 现金支付（投入硬币和纸钞；取回找零）
   4. 取票（以及收据；如插了卡，取回卡）
```

逐条走完这棵树会提出一份功能清单不会提出的问题。步骤 2.2 要求旅客选择票价类型，而这需要多数偶尔出行的旅客不具备的票价规则知识——所以售票机应当就*他们的*行程解释选项（"适用于 09:30 之后的列车"），或默认最便宜的可行票价。步骤 2.3 出现在票价选定*之后*，所以铁路卡持有者到最后才看到折扣价，而若他们早知道，也许会选另一种票价。步骤 4 掩盖了经典的**完成后错误**：一旦"买票"这一目标达成，人们就会忘记"拿回我的卡"这个附属步骤——这就是设计良好的机器先退卡、*再*出票的原因。这一结构还提示了可测量的可用性需求：例如，90% 的首次使用者应在 90 秒内完成目标 0。
:::
:::

## 来自日常事物的设计原则

唐·诺曼（Don Norman）的《设计心理学》(*The Design of Everyday Things*，1988 年初版时名为 *The Psychology of Everyday Things*，2013 年修订扩充）解释了人们为什么在门、水龙头、炉子和软件面前同样手足无措，并把解释提炼为几条原则。

::: definition 诺曼的设计原则 {#def-norman}
- **可供性**（affordance）是物体的属性与智能体的能力之间的一种关系，它决定物体可以被如何使用：门上平整的推板暗示推，把手暗示转。这个术语来自吉布森（Gibson）的生态心理学（1977、1979）。
- **指示物**（signifier）是关于在哪里、如何行动的知觉信号：把手的形状、标签、带下划线的链接、按钮上的图标。诺曼在 2013 年版本中引入该词，因为设计师们已经用"可供性"来指他们其实想说"指示物"的地方。
- **映射**（mapping）是控件与其效果之间的关系；**自然映射**利用空间类比或文化惯例，使之无需标签。
- **反馈**即时而信息充分地传达动作的结果。
- **约束**——物理的、文化的、语义的和逻辑的——限制可能的动作，使错误的动作不可能或不太可能发生。
- 通过系统映像传达的好的系统**概念模型**，能让用户预测自己动作的效果。
:::

著名的**诺曼门**（Norman door）——其设计暗示了错误动作的门，典型如需要推的门上装了拉的手柄——是指示物的失败：门可供两种动作，但它的手柄只暗示其一，而且暗示了错的那一个。"推"字标牌是一种症状：当一件简单的东西需要贴标签时，它的设计就失败了。在软件中，2010 年代流行的"扁平化设计"去掉了许多指示物（按钮的边框、链接的下划线），用户只能靠试错来发现哪些元素可以交互。

::: example 炉头与旋钮的映射 {#ex-stove}
一台灶具有 $2 \times 2$ 排列成方阵的四个炉头，和一排沿前沿排列的四个旋钮。把旋钮分配给炉头有多少种方式？你如何让正确的那一种一目了然？
::: solution
旋钮到炉头的任意双射都是可能的，所以有 $4! = 24$ 种映射；而旋钮排成一行、炉头排成方阵，其中没有一种是自然的：用户只能从标签或试错中学习映射——常常以烧坏东西为代价。自然映射能消除歧义：把旋钮摆成与炉头相同的 $2 \times 2$ 图案；或者把炉头从左到右错开排列，使旋钮的次序对应炉头从左到右的次序；或者把每个旋钮放在它的炉头旁边。标签是有代价的退路：每次使用都需要阅读和翻译。
:::
:::

::: quiz
一款文件共享应用在每个文件旁显示一个云图标。一些用户以为点它可以上传文件；另一些用户以为它只是表示文件已经存储在云上。用诺曼的术语说，问题出在哪里？
- [ ] 该图标缺少可供性。
- [x] 该图标是一个含义不明确的指示物：它没有表明自己是一个控件还是一个状态指示器。
- [ ] 应用缺少一个能阻止点击的约束。
- [ ] 点击之后的反馈太慢。
::: solution
屏幕上的图标无论长什么样都可供点击——每个像素都是。用户缺少的是一种清晰的**指示物**，说明这个图标是哪类东西、点击它会做什么。补救办法：在视觉上把状态指示器与控件区分开（控件看起来可按，并带有标签或无障碍名称，例如"上传"）；让图标随状态变化（上传后变成带对勾的云）；并在状态改变时给出**反馈**。
:::
:::

这些原则有助于*诊断*——人们为什么犯难？——但它们不能替代对真实用户的观察：设计师可以满足每一条原则，却仍然造出错误的东西。它们将以尼尔森可用性启发式的形式在 [[hci/usability-evaluation]] 中重现；而诺曼描述用户想做的事与系统允许做的事之间距离的执行与评估两个鸿沟，将在 [[hci/interaction-techniques]] 中讲述。

## 从研究到需求

只有改变做出来的东西，研究才有用。本章的产出直接输入需求工程：人物角色和场景变成用户故事的*角色*与*收益*；层次任务分析变成用例及其扩展；观察到的问题变成可测量的可用性需求（[[#def-usability]]）；关于使用情境的发现——单手、嘈杂、被打断、共享设备——变成约束。在病房应用的例子里，"双手都被占用"和"平板是共享的、会锁屏"这两个观察，导出诸如"扫过病人腕带和药品即可用单手记录一次给药"、"记录一次给药除碰一碰工牌外无需登录"、"录入中途被打断的护士能在 10 分钟内继续而无需重新输入"之类的需求。对着最初的规格说明怎么测试也不会产生它们。

::: history
人因学始于第二次世界大战：阿方斯·沙帕尼斯（Alphonse Chapanis）等人把许多飞机事故追溯到容易混淆的驾驶舱控制器——襟翼与起落架的操纵杆一模一样——并用形状编码解决了它们。亨利·德雷夫斯（Henry Dreyfuss）的 *Designing for People*（1955）把人体测量数据带进工业设计。在计算领域，约翰·古尔德与克莱顿·刘易斯 1985 年的文章确立了早期关注用户、实证测量与迭代设计的原则；唐·诺曼与斯蒂芬·德雷珀（Stephen Draper）主编的 *User Centered System Design*（1986）为这一方法命名；诺曼的 *The Psychology of Everyday Things*（1988）使它家喻户晓。休·拜尔与卡伦·霍尔茨布拉特的 *Contextual Design*（1998）、艾伦·库珀的人物角色（1999）与约翰·卡罗尔的基于场景的设计（2000）为实践者提供了方法。ISO 13407（1999）把以人为中心的设计标准化；它于 2010 年被 ISO 9241-210 取代并于 2019 年修订；ISO 9241-11（1998）的可用性定义在 2018 年修订。
:::

## 后续内容

理解用户是第一步；[[hci/prototyping]] 把这种理解变成便宜到可以丢弃的设计，[[hci/usability-evaluation]] 则与用户一起检验这些设计。对有效性、效率与满意度的精确测量是 [[hci/experiments]] 的主题，而"指定用户"必须包括残障人士这一要求将在 [[hci/accessibility-ethics]] 中展开。同一项工作的软件一侧——把需求写下来、追踪到测试——在 [[software-engineering/requirements]]。

::: summary
- **可用性**（[[#def-usability]]）是指定用户、目标与情境下的有效性、效率与满意度；它可测量、依赖情境。UX 更宽泛。
- **以人为中心的设计**（[[#def-hcd]]）立足于早期关注用户、全程参与、评估驱动的迭代与多学科团队（Gould 与 Lewis 1985；ISO 9241-210:2019）。
- 把显示人们**说的**与**做的**的方法结合使用；问具体的过去事件，不问假设；情境查询能揭示隐性的实践与变通办法。
- 问卷误差范围按 $1/\sqrt n$ 收缩（[[#prop-moe]]），但仅对随机样本成立；$1 - (1-p)^n$（[[#prop-detect]]）说明为什么必须刻意招募罕见的用户群体。
- 用亲和图或主题分析整理定性数据；用**科恩 kappa**（[[#def-kappa]]）检验编码信度，并利用分歧打磨编码。
- 用植根于研究的**人物角色**与**场景**描述用户，并用**层次任务分析**（[[#def-hta]]）发现诸如完成后错误一类的问题。
- 诺曼的原则——可供性、**指示物**、映射、反馈、约束与概念模型（[[#def-norman]]）——诊断日常设计失败。
:::

## 习题

::: exercise 需要多少份回答 {level=1 check="97"}
简单随机样本需要多少份回答，才能保证无论真实比例为何，95% 的可误差范围至多为 10 个百分点？（输入最小整数。）
::: solution
由 [[#eq-survey-n]]，$n \ge (1.96/0.2)^2 = 96.04$，故 $n = 97$。
:::
:::

::: exercise 给度量分类 {level=1}
把下列度量分类为有效性、效率或满意度（[[#def-usability]]）：(a) 成功预约到正确号源的参与者百分比；(b) 预约平均耗时；(c) 问卷得分；(d) 每项任务的错误数；(e) 每次预约的点击数；(f) 说自己会再次使用该系统的参与者比例。
::: solution
(a) 有效性（达成目标的完备与精确）。(b) 效率（单位结果的时间）。(c) 满意度。(d) 有效性（精确性）——能被纠正的错误同样花费时间，所以也影响效率。(e) 效率（单位结果的精力），不过点击是弱指标：三次轻松的点击可能胜过一次艰难的点击。(f) 满意度（一种陈述的态度），而不是实际未来使用的度量。
:::
:::

::: exercise 由计数求 kappa {level=1 check="0.6"}
两名编码者把 100 条评论分类为正面或负面。他们在 80 条上一致。编码者 1 判定 50 条为正面，编码者 2 判定 50 条为正面。科恩 kappa 是多少？（输入数值。）
::: solution
$p_o = 0.8$，$p_e = (50 \cdot 50 + 50 \cdot 50)/100^2 = 0.5$，故 $\kappa = (0.8 - 0.5)/(1 - 0.5) = 0.6$（[[#def-kappa]]）。
:::
:::

::: exercise 发现罕见需求 {level=2 check="14"}
某旅行应用 20% 的用户代团体预订。随机招募多少名参与者，才能以至少 95% 的概率保证至少有一人代团体预订？（输入最小整数。）
::: solution
由 [[#prop-detect]]，$n \ge \ln 0.05 / \ln 0.8 \approx 13.4$，故 $n = 14$；验证：$1 - 0.8^{14} \approx 0.956$、$1 - 0.8^{13} \approx 0.945$。更好的做法是刻意招募若干名团体预订者。
:::
:::

::: exercise 密码重设的层次任务分析 {level=2}
为通过电子邮件重设网站上被遗忘的密码写一个带计划的层次任务分析，并指出用户常出的两处差错。
::: solution
```text
0. 重新获得账户访问权
   计划 0：做 1-2-3-4；若邮件几分钟后仍未到达，做 5。
   1. 发起重设
      1.1 找到"忘记密码？"链接
      1.2 键入电子邮箱地址或用户名
   2. 取回重设邮件
      计划 2：做 2.1；找不到就做 2.2。
      2.1 切换到邮件程序并打开邮件
      2.2 查看垃圾邮件文件夹
   3. 设置新密码
      3.1 跟随链接（在链接过期之前）
      3.2 键入符合规则的新密码（并确认一次）
   4. 用新密码登录
   5. 联系客服
```

常见的失误：在 1.2，有多个邮箱地址的用户不知道账户用的是哪一个，好的设计接受地址或用户名皆可，并且绝不泄露某个账户是否存在（这是一条安全需求）；在 2，切换设备或应用会丢失上下文，而邮件可能落进垃圾邮件夹；在 3.1，链接可能过期，或在一台不同的设备上被打开；在 3.2，规则要等一次输入被拒绝之后才显示——应当提前显示；在 4，一些网站重设后不自动登录，多加了一个不必要的步骤。
:::
:::

::: exercise 指示物还是可供性？ {level=2}
就下列各例，指出问题主要出在可供性、指示物、映射、反馈还是约束上，并给出修改建议：(a) 一个房间六盏灯的开关面板上有六个一模一样的开关；(b) 一个按下后没有任何可见反应的"保存"按钮；(c) 一个接受 "31/02/2026" 的日期输入框；(d) 一个可滚动列表，最后一个可见行恰好截在行的边界上，用户没有意识到它可以滚动。
::: solution
(a) **映射**：排成一行的相同开关丝毫不提示每个开关控制哪盏灯；按房间的平面图排列它们，或者加上标签。(b) **反馈**：显示确认信息（"已保存 10:42"），或改变按钮状态。(c) 缺少**约束**：用日期选择器或校验使不可能的日期根本无法输入，并给出解释。(d) 缺少**指示物**：显示一行被截断的内容、滚动条或边缘渐隐，以示意还有更多内容。
:::
:::

::: exercise 百分一致率为何误导 {level=3}
两名编码者把 100 张工单标为"紧急"或"不紧急"。每人把 90 张标为"不紧急"。(a) 证明：若两人按各自的比率独立标注，其期望的百分一致率为 82%。(b) 他们实际在 84 张上一致。计算 kappa 并评论。(c) 证明：对两个类别、两名编码者第一个类别的边际比例同为 $q$ 的情形，$p_e = q^2 + (1-q)^2 \ge 1/2$，因此偶然情况下总能达到至少 50% 的百分一致率。
::: solution
(a) $p_e = 0.1 \times 0.1 + 0.9 \times 0.9 = 0.01 + 0.81 = 0.82$。(b) $\kappa = (0.84 - 0.82)/(1 - 0.82) = 0.02/0.18 \approx 0.11$。虽然 84% 的一致率听起来很高，但它只比偶然略高：编码者几乎从不在*哪些*工单紧急上达成一致，而这恰恰是唯一要紧的事。(c) $q^2 + (1-q)^2 = 2q^2 - 2q + 1 = 2(q - \tfrac12)^2 + \tfrac12 \ge \tfrac12$，等号成立当且仅当 $q = 1/2$。所以边际相同的两名编码者偶然一致的概率至少为一半，而当某一类别占主导时更高——这恰恰是罕见而重要的类别所处的情形。报告 kappa（或相关的一致性修正指标）和混淆表，而不是原始一致率。
:::

::: exercise 一项现场研究计划 {level=3}
受邀重新设计送货司机用来记录包裹投递的应用。写一份研究计划：用哪些方法、哪些参与者、各多少人，你要寻找什么，你将如何分析数据，你将向设计团队交付什么。用本章内容为每一项选择给出理由。
::: solution
一份好的计划应包括：(1) **情境查询**——随 6–10 名司机跑真实的投递线路（[[#def-hcd]]，原则 1），有目的地选择以覆盖不同线路（城市公寓、乡村独栋）、经验（新手与老司机）、设备，以及任何有相关障碍或英语有限的司机（[[#ex-rare]]）；观察单手持机使用、手套、雨与眩光、时间压力，以及诸如把照片存在私人手机里一类的变通办法。(2) 每个班末就具体事件做**简短访谈**（"讲讲最近一次投递失败的情形"），避免假设性问题（[[#ex-interview]]）。(3) 现有应用的**日志**用于频率——每个屏幕多久被用一次、司机在哪里退出、每次投递耗时——因为这些正是日志擅长测量的。(4) 之后可选地对全体司机做一次**问卷**，测量所发现的问题有多普遍，并附 [[#prop-moe]] 的抽样告诫。分析：团队一起对观察笔记做亲和图归类；然后由两名研究者对一个子集应用编码手册，计算 kappa 并解决分歧（[[#def-kappa]]）。交付物：2–4 个植根于研究的人物角色、问题场景、含例外情形的投递 HTA（[[#def-hta]]）、按频率与严重程度排序的观察问题清单，以及可测量的可用性需求（"戴手套的单手在 10 秒内完成一次投递记录"）。伦理：知情同意、未经许可不录制客户，并保证研究结果不用于给个别司机打分。
:::
