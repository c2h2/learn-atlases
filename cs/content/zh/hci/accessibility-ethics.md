一位失明用户用屏幕阅读器购买火车票。页面读出来的是"按钮"、"按钮"、"按钮"——三个没有文字的图标——然后是"可点击"，那是一个加了样式的 `<div>`，充当*购买*按钮，却无法用键盘到达。页面看上去毫无问题，但购买根本无法完成。下一个站点上，cookie 横幅给出一个很大的"全部接受"按钮；而要拒绝跟踪，得在小号灰色的"管理选项"链接上点击一次，再拨动三个开关，再确认一次——用击键级模型来算，耗时约为前者的五倍。两个页面都出自称职的开发者之手。第一个页面因疏忽把人排斥在外；第二个页面则靠设计把人往既定方向推。

这最后一章讲的，是界面遗漏的人与被界面摆布的人。**无障碍**（accessibility）是让能力范围尽可能广的人都能使用系统的实践，如今在世界许多地方已是法律要求。交互设计中的**伦理**关心设计者对用户的注意、选择与数据所拥有的权力。我们将看到：残障与人们使用的辅助技术；界面如何向这些技术暴露自己的结构；《Web 内容无障碍指南》（Web Content Accessibility Guidelines，WCAG）2.2，连同一道目标尺寸的计算实例；截至 2026 年的法律状况，包括《欧洲无障碍法案》；如何评估无障碍；以及**欺骗性设计模式**、对它的测量与规制。软件伦理总体的职业与法律框架见 [[software-engineering/professional-ethics]]。

## 残障与无障碍

两种看待残障的方式塑造着设计。**医学模式**把残障定位于个人的损伤，要靠治疗或补偿来解决。**社会模式**由 20 世纪 70 年代英国的残障活动家发展而来，并由迈克·奥利弗（Oliver）于 1983 年命名，它把残障定位于人造与设计的世界设置在使用损伤者面前的障碍：轮椅使用者是被楼梯残障的，而不是被自己的双腿。世界卫生组织的 *International Classification of Functioning, Disability and Health*（2001）把两者结合，把残障描述为健康状况与情境因素之间的交互。对设计者而言，社会模式才是有生产力的那种：不可用的界面是设计缺陷，而缺陷是可以修的。

数字是庞大的。世界卫生组织的 *Global Report on Health Equity for Persons with Disabilities*（2022）估计，约 13 亿人——约占世界人口的 16%——经历着显著残障，而且这一比例随年龄上升。损伤可以是**永久性的**（失明、失聪、截肢）、**暂时性的**（骨折、眼科手术后的恢复期）或**情境性的**（强光下的手机屏幕、一只臂弯里的婴儿、嘈杂的车站、使用第二语言）；为第一组人做的往往也帮助后两组。

::: definition 无障碍 {#def-accessibility}
**无障碍**指产品、系统、服务与环境在规定的语境中，能被人群中需求、特征与能力范围最广泛的用户用于实现规定目标的程度（依 ISO 9241-112 与 ISO 9241-171）。它就是"规定的用户"把残障人士也包括进来的可用性（[[hci/user-centred-design#def-usability]]）。
:::

| 损伤 | 障碍举例 | 辅助技术与适配 |
|---|---|---|
| 失明 | 没有文字的图像、无名称的控件、仅鼠标可操作 | 屏幕阅读器（语音或盲文输出）、键盘导航 |
| 低视力 | 文字过小、对比度低、缩放后布局错乱 | 放大、高对比与深色模式、文字缩放 |
| 色觉缺陷 | 颜色作为唯一线索 | 图案、标签与安全调色板（[[hci/visual-design]]） |
| 失聪与重听 | 音频没有字幕、仅电话支持 | 字幕、文字稿、手语翻译、在线文字聊天 |
| 运动功能障碍 | 目标过小、时限、只能拖动或多指手势 | 开关访问、语音控制、眼动追踪、键盘替代 |
| 认知与学习障碍 | 文字密集、导航复杂、依赖记忆的关卡 | 平实的语言、一致的布局、无时间压力、再认而非回忆 |
| 光敏性癫痫 | 闪烁内容 | 一秒内闪烁不超过三次的内容限制 |

## 辅助技术如何"看"界面

屏幕阅读器看不见像素。它读的是平台依据应用代码构建、并通过**无障碍 API** 暴露出来的界面结构化描述。

::: definition 无障碍树 {#def-accessibility-tree}
**无障碍树**是应用程序用户界面对象构成的一棵树，由浏览器或工具包从其文档树或组件树派生，并提供给辅助技术。每个节点有一个**角色**（按钮、链接、复选框、标题、文本字段……）、一个**无障碍名称**（为它读出的文字——来自其内容、`<label>`、`alt` 属性或 `aria-label`）、可选的**状态与属性**（已选中、已展开、已禁用、必填）和一个值；这些发生变化时，平台会派发**事件**。一个控件能被辅助技术操作，仅当它的节点具有正确的角色、有意义的名称、正确的状态，并接受标准的键盘或无障碍动作。
:::

原生 HTML 元素自带正确的角色、名称与键盘行为：`<button>` 可获得焦点，由 Enter 与空格激活，并连同其文字读作"按钮"。一个样式化成按钮的 `<div>` 这些都没有。WAI-ARIA（Accessible Rich Internet Applications，W3C 规范；1.2 版于 2023 年成为 W3C 推荐标准）允许作者给自定义组件添加角色与状态，但它自己的第一条指引就是"ARIA 使用第一法则"：存在具备你所需语义的原生元素时，就使用它。ARIA 只改变辅助技术被*告知*的内容；它不添加键盘行为，所以 `<div role="button">` 仍然需要 `tabindex="0"` 和按键处理器——而与行为不符的 ARIA 角色比没有角色更糟。

::: example 找出机器可检测的失效 {#ex-a11y-check}
编写一个小检查器，标记没有 `alt` 的图像、没有无障碍名称的按钮、没有标签的表单输入框，以及非交互元素上的点击处理器，并在票务页面的一段片段上运行它。
::: solution
```python
from html.parser import HTMLParser

class Checker(HTMLParser):
    """Flags a few machine-detectable failures; most of WCAG needs human judgement."""
    def __init__(self):
        super().__init__()
        self.problems, self.labels, self.inputs = [], set(), []
        self.button = None                         # text collected inside an open <button>
    def handle_starttag(self, tag, attrs):
        a = dict(attrs)
        if tag == "img" and "alt" not in a:
            self.problems.append(f"img {a.get('src')}: no alt attribute (1.1.1)")
        if tag == "label" and "for" in a:
            self.labels.add(a["for"])
        if tag == "input" and a.get("type") not in ("hidden", "submit", "button"):
            self.inputs.append(a)
        if tag == "button":
            self.button = a.get("aria-label", "")
        if "onclick" in a and tag not in ("button", "a", "input"):
            self.problems.append(f"<{tag} onclick>: not keyboard-operable by default (2.1.1)")
    def handle_data(self, data):
        if self.button is not None:
            self.button += data.strip()
    def handle_endtag(self, tag):
        if tag == "button":
            if not self.button:
                self.problems.append("button with no accessible name (4.1.2)")
            self.button = None
    def report(self):
        for a in self.inputs:
            if a.get("id") not in self.labels and "aria-label" not in a:
                self.problems.append(f"input {a.get('name')}: no label (1.3.1, 4.1.2)")
        return self.problems

page = """
<img src="logo.png">
<img src="divider.png" alt="">
<label for="q">Search</label> <input id="q" name="q" type="search">
<input name="email" type="email" placeholder="Email">
<button><svg aria-hidden="true"></svg></button>
<button aria-label="Close dialog"><svg aria-hidden="true"></svg></button>
<div class="btn" onclick="buy()">Buy now</div>
"""
c = Checker()
c.feed(page)
for p in c.report():
    print(p)
```

```console
$ python3 a11y.py
img logo.png: no alt attribute (1.1.1)
button with no accessible name (4.1.2)
<div onclick>: not keyboard-operable by default (2.1.1)
input email: no label (1.3.1, 4.1.2)
```

其中的数字是 WCAG 成功标准的编号。注意*没有*被标记的东西：分隔图上的 `alt=""` 是正确的，它把图像标记为装饰性内容，让屏幕阅读器跳过；带标签的搜索框和有名称的关闭按钮都通过；而占位符不是标签，因为输入时它会消失。修复办法：`<img src="logo.png" alt="Northern Rail home">`、`<label for="email">Email</label>`、`<button aria-label="Open menu">`（或可见文字），以及给 *Buy now* 用一个真正的 `<button>`。检查器无法判断 `alt` 文字是否*有意义*（"image123.png" 也能通过），无法判断阅读顺序是否合理，也无法判断任务能否用键盘完成——这正是自动检查只是无障碍评估的开端的原因。
:::
:::

## WCAG 2.2

**《Web 内容无障碍指南》**由 W3C 的网络无障碍倡议组织（Web Accessibility Initiative）发布。WCAG 2.2 于 2023 年 10 月 5 日成为 W3C 推荐标准（2024 年 12 月发布了更新版），并与 WCAG 2.0（2008）和 2.1（2018）向后兼容：符合 2.2 的内容也符合更早的版本。尽管名字如此，它的适用范围远超网页，欧洲的 EN 301 549 之类的标准把它的标准应用于文档、软件与移动应用。

::: definition WCAG 的结构与符合性 {#def-wcag}
WCAG 2.2 组织在四条**原则**之下——内容必须是**可感知的**、**可操作的**、**可理解的**、**健壮的**（POUR）——其下含 13 条**指南**，其下含 86 条可检验的**成功标准**，每条分为 **A**、**AA** 或 **AAA** **级**。一个网页在如下情形于 AA **级符合**：它对完整的页面与完整的流程，仅使用无障碍支持的技术，在不干扰页面其余部分的前提下，满足每条 A 级与 AA 级成功标准（或提供符合的替代版本）。多数法律与政策引用的级别是 AA。
:::

部分最重要的标准：

| 标准 | 级别 | 要求（意译） |
|---|---|---|
| 1.1.1 非文本内容 | A | 为图像与其他非文本内容提供文字替代 |
| 1.2.2 字幕（录制内容） | A | 同步媒体中的录制音频需要字幕 |
| 1.3.1 信息与关系 | A | 结构（标题、列表、表格、标签）可由程序获取 |
| 1.4.1 颜色的使用 | A | 颜色不得作为传达信息的唯一视觉手段 |
| 1.4.3 对比度（最低） | AA | 文字 4.5:1，大字号文字 3:1（[[hci/visual-design#def-contrast]]） |
| 1.4.10 回流 | AA | 内容在 320 CSS px 宽度下无需二维滚动即可工作 |
| 2.1.1 键盘 | A | 全部功能均可用键盘操作 |
| 2.2.1 时限可调 | A | 用户可以关闭、调整或延长时限 |
| 2.4.7 焦点可见 | AA | 键盘焦点指示器可见 |
| 2.5.8 目标尺寸（最低） | AA | 指针目标至少 24 × 24 CSS px，另有例外 |
| 3.3.1 错误识别 | A | 以文字指明并描述输入错误 |
| 3.3.8 无障碍身份验证（最低） | AA | 登录不得要求认知功能测试（如记忆或转写），除非提供替代方式或辅助（如粘贴或密码管理器） |
| 4.1.2 名称、角色、值 | A | 用户界面组件须暴露名称、角色、状态与值（[[#def-accessibility-tree]]） |

WCAG 2.2 新增了九条成功标准——2.4.11 焦点不被遮挡（最低，AA）、2.4.12 焦点不被遮挡（增强，AAA）、2.4.13 焦点外观（AAA）、2.5.7 拖动动作（AA）、2.5.8 目标尺寸（最低，AA）、3.2.6 一致的求助（A）、3.3.7 冗余输入（A）、3.3.8 与 3.3.9 无障碍身份验证（最低，AA；增强，AAA）——并移除了已无实际作用的 4.1.1 解析。许多新标准帮助的是运动与认知障碍者，早期版本对他们关照较少。

### 一条标准的演算：目标尺寸

成功标准 2.5.8 要求指针目标至少是 24 乘 24 CSS 像素，*例外*是（除其他例外情形外）尺寸不足的目标彼此留距，使得以每个目标的外接框为中心、直径 24 CSS px 的圆不与另一个目标或另一个不足尺寸目标的圆相交。该标准由费茨定律与触摸准确性（[[hci/interaction-techniques]]）导出，其留距例外可以化成一条简单不等式。

::: proposition 一行中小目标的留距 {#prop-target-spacing}
考虑一行相同的正方形目标，边长 $s < 24$ CSS px，相邻目标之间留距 $g$ px，于是中心相距 $s + g$。它们满足 WCAG 2.2 成功标准 2.5.8 的留距例外，当且仅当 $s + g \ge 24$，即 $g \ge 24 - s$。
:::

::: proof
每个目标配一个以其中心为圆心、半径 12 的圆。相邻两个圆不相交，当且仅当两心距离不小于半径之和：$s + g \ge 24$。圆还不得与相邻的*目标*相交：相邻正方形到第一个中心的最近点是它的近侧边缘，水平距离 $(s + g) - s/2 = s/2 + g$，所以条件是 $s/2 + g \ge 12$，即 $s + 2g \ge 24$。由于 $g \ge 0$，有 $s + 2g \ge s + g$，故第二个条件由第一个推出。一行中更远处的目标离得更远。因此例外成立当且仅当 $s + g \ge 24$。（按通常的读法，我们视"相切"的圆为不相交。）
:::

::: example 一排小图标工具栏 {#ex-target-size}
某文本编辑器的工具栏上是 16 × 16 px 的图标按钮，相邻按钮之间隔 4 px。它满足 2.5.8 吗？需要多大的留距？还有什么别的办法？
::: solution
目标尺寸不足（$16 < 24$），因此需要留距例外：由 [[#prop-target-spacing]]，留距至少 $24 - 16 = 8$ px。只有 4 px 时中心相距 20 px，相邻的 24-px 圆相交；工具栏不合格。可选方案：把留距加大到 8 px（图标本身不必变大——圆的检验看的是留距）；用内边距把每个按钮的可点击区域扩大到 24 × 24 px 而保持 16-px 图标（常用修复，且按费茨定律对所有人都有利）；或在别处提供同样满足标准的等效控件，例如把同样的命令放进菜单（"等效"例外）。24 px 只是下限：触摸的平台指南如 [[hci/interaction-techniques]] 所述在 44–48 单位左右，而 WCAG 的 AAA 级标准 2.5.5 要求 44 × 44 CSS px。
:::
:::

sliders: b=0.45:0.15:1:0.05

:::

::: quiz
一个登录页要求用户重新键入短信发送的六位验证码，且验证码输入框禁止粘贴。一位有诵读困难与短期记忆困难的用户无法可靠地转写验证码。最直接相关的是哪条 WCAG 2.2 标准，如何修复？
- [ ] 1.4.3 对比度；提高验证码输入框的对比度。
- [x] 3.3.8 无障碍身份验证（最低）；允许粘贴并自动填入验证码（例如通过平台的一次性验证码自动填充），或提供无需转写的方式。
- [ ] 2.5.8 目标尺寸；把验证码输入框做大。
- [ ] 1.1.1 非文本内容；给输入框添加替代文字。
::: solution
转写验证码在 3.3.8 之下属于认知功能测试，除非给予用户帮助——允许粘贴或自动填充，使验证码根本无需被记住或重新键入——或提供替代方式，如魔法链接或通行密钥。禁止粘贴是常见的失效，它同时削弱安全性，因为它妨碍密码管理器。
:::
:::

::: example 审查一个注册表单 {#ex-audit}
某注册表单的字段只有占位符作标签；必填字段仅以红色边框标示；五分钟后会话过期并清空表单；提交前必须解出图片验证码；错误信息只作为页面顶部的红色横幅出现。它违反了哪些 WCAG 2.2 成功标准，各应如何修复？
::: solution
- **标签只有占位符**：违反 1.3.1 信息与关系与 3.3.2 标签或说明（A），若在计算中得不到无障碍名称，通常还违反 4.1.2；占位符还会在输入时消失，加重记忆负担。修复：可见的 `<label>` 元素。
- **必填仅以颜色标示**：违反 1.4.1 颜色的使用（A）；红色边框若与背景对比低于 3:1，还可能违反 1.4.11 非文本对比度（AA）。修复：在标签中写出"必填"（required）字样（并加上 `required` 属性，辅助技术会朗读它）。
- **五分钟过期并清空表单**：违反 2.2.1 时限可调（A），除非警告用户并允许延长时间（至少为默认时限的十倍，或以简单操作给予 20 秒预告）。修复：过期前给出"延长"按钮，并保留已输入的数据。
- **图片验证码**：验证码需要描述其用途的文字替代以及不同感觉通道的替代形式（1.1.1）；若它是登录的一部分，谜题就是 3.3.8（AA）之下的认知功能测试。修复：改用负担更小的机器人检查（限流、无感风险评分），或提供无障碍的替代方式。
- **错误只在顶部横幅中显示**：3.3.1 错误识别（A）要求指明出错的字段并以文字描述错误；3.3.3 错误建议（AA）要求给出修改建议；4.1.3 状态消息（AA）要求把消息读给屏幕阅读器。修复：把消息放在相应字段旁边并以程序方式与之关联（例如用 `aria-describedby`），在顶部放一个链接到各字段的摘要，并把焦点移到摘要上。

每一项失效同样伤害没有残障的用户——占位符标签与丢失的输入是可用性测试中最常见的抱怨之列（[[hci/usability-evaluation]]）——这是一个反复出现的结论：无障碍的设计通常也是更好的设计。
:::
:::

## 法律状况（截至 2026 年）

无障碍正日益成为法律义务，而不仅是良好实践。细节会变；以下概述 2026 年的状况。

- **联合国。**《残疾人权利公约》（2006）要求缔约国确保获得信息与通信技术（第 9 条）。
- **欧盟。** **《欧洲无障碍法案》**（Directive (EU) 2019/882）自 **2025 年 6 月 28 日**起适用。它覆盖计算机、智能手机、自助服务终端与电子阅读器等产品，以及电子商务、消费银行、电子书、电子通信与旅客运输售票等服务；提供服务的小微企业豁免，已在使用的服务与终端有过渡期。符合协调标准 EN 301 549（其网络要求采纳 AA 级 WCAG）即推定符合。更早的《网络无障碍指令》(EU) 2016/2102 覆盖公共部门的网站与应用。
- **美国。**《美国残疾人法》（1990）通过诉讼被广泛适用于网站。《康复法》第 508 条要求联邦机构的信息与通信技术无障碍，2017 年的更新纳入了 WCAG 2.0 AA。2024 年 4 月，司法部依据 ADA 第二章通过规则，要求州与地方政府的网络内容和移动应用满足 WCAG 2.1 AA；2026 年 4 月的临时最终规则把合规期限推迟到 2027 年 4 月（较大实体）与 2028 年 4 月（较小实体）。
- **英国。**《2010 年平等法》要求作出合理调整；《2018 年公共部门机构无障碍条例》要求公共部门网站满足 WCAG AA 并发布无障碍声明。

法律引用的是特定版本的 WCAG，总是落后于当前版本；按 WCAG 2.2 AA 设计即可满足上述全部法律的技术要求，但没有一部法律能靠一张核对清单得到满足。

## 评估无障碍

无障碍评估结合三种方法，成本与洞见依次递增。

**自动化测试**能发现可从代码检测出的失效：缺失替代文字、缺失标签、低对比度、空的链接与按钮、缺失文档语言。它快速、可重复，应当进入持续集成。它同时也非常不完整：无法判断替代文字是否有意义、焦点顺序是否合理、任务能否完成。即便如此，它也揭示了多数网络离最低要求有多远：WebAIM Million 报告每年对头部一百万个网站的主页运行自动检查器，2026 年 2 月的结果显示 **95.9%** 的主页存在可检测的 WCAG 2 违规，平均每页 56 处，最常见的是低对比文字（83.9% 的页面），其次是缺失替代文字与缺失表单标签。

**人工专家评审**带着键盘走遍页面与任务（一切都能到达并操作吗？焦点始终可见吗？有没有键盘陷阱？），带着屏幕阅读器（名称、角色与状态读得合理吗？阅读顺序对吗？变化会播报吗？），在 200% 与 400% 缩放下，在模拟的色觉缺陷下（[[hci/visual-design#ex-cvd]]），并对照每一条 WCAG 成功标准。

**与残障用户一起测试**——请日常生活使用辅助技术的参与者做可用性测试（[[hci/usability-evaluation#def-usability-test]]）——能发现符合性核查发现不了的：体验究竟是否可用、高效、有尊严。一个页面可以符合 WCAG 却让人用屏幕阅读器用得心力交瘁。要有目的地招募（[[hci/user-centred-design#ex-rare]]），付给参与者公平的报酬，让他们使用自己的设备与设置，并留足时间。

::: warning "装一个无障碍小部件，网站就无障碍了"
第三方的"无障碍叠加层"——加一个工具栏、声称自动修复无障碍问题的脚本——无法可靠修复缺失的语义、键盘陷阱与无意义的标签，可能干扰用户自己的辅助技术，也造不出法律合规。2021 年，数百名无障碍从业者与残障用户联署 *Overlay Fact Sheet*，吁请组织不要依赖它们。无障碍来自正确的标记、设计与测试，最好内建在组件与设计系统里，让每个页面都继承它。同样，"最后再补无障碍"会和迟到的安全一样失败：返工比一开始就建入昂贵得多。
:::

## 伦理：欺骗性设计

本课程的技术——对注意、记忆、默认与省力的了解——既可以用来帮助人们达成目标，也可以用来让他们做本来不会选择的事。后一种用法有名有姓。

::: definition 欺骗性设计模式 {#def-dark-pattern}
**欺骗性设计模式**（"dark pattern"，哈里·布里努尔（Brignull）2010 年提出）是这样一种用户界面设计：通过欺骗、胁迫或操纵用户，使其作出在充分知情且不受阻碍时不会作出的选择，从而以用户为代价使服务受益。科林·格雷（Gray）及其合作者（CHI 2018）把这类模式归为五种策略：**纠缠**（nagging，反复打断）、**阻碍**（obstruction，把任务弄得比必要的更难，如取订阅的迷宫）、**潜行**（sneaking，隐藏或延迟相关信息，如隐藏费用或往购物车里加商品）、**界面干扰**（interface interference，操纵界面使某些动作被偏袒，如预先勾选的框、伪装的广告或"确认羞辱"——"不了，我不喜欢省钱"），以及**强制行动**（forced action，要求先做无关动作才能继续）。
:::

这类模式相当常见。阿鲁内什·马图尔（Mathur）及其合作者（"Dark patterns at scale"，*Proceedings of the ACM on Human–Computer Interaction*，CSCW 2019）爬取了约 11,000 个购物网站，在其中 1,254 个上发现 1,818 处黑暗模式——约 11%——包括虚假的倒计时和编造的"库存紧张""他人正在查看"提示。由于其中许多无法被自动爬取发现，真实流行度可能更高。努力不对称是阻碍的一种形式，可以用 [[hci/interaction-techniques]] 的工具量化。

::: example 测量不对称的 cookie 横幅 {#ex-banner}
某横幅把"全部接受"做成一个大按钮。拒绝则要先进入"管理选项"，再关掉三个预先勾选的类别，再点"确认我的选择"。按手已放在鼠标上的击键级模型估计两条路径。
::: solution
每一步是一个判定、一次指点移动与一次点击，$M\,P\,K$（[[hci/interaction-techniques#def-klm]]）。

```python
# KLM estimate (hand already on the mouse) for two paths through a cookie banner.
T = {"M": 1.35, "P": 1.10, "K": 0.20}
def klm(ops):
    return sum(T[o] for o in ops.split())

accept = "M P K"                                   # "Accept all"
reject = ("M P K "                                 # "Manage options"
          "M P K M P K M P K "                      # switch off three pre-ticked categories
          "M P K")                                  # "Confirm my choices"
print(f"accept: {klm(accept):.2f} s, reject: {klm(reject):.2f} s, ratio {klm(reject) / klm(accept):.1f}")
```

```console
$ python3 banner.py
accept: 2.65 s, reject: 13.25 s, ratio 5.0
```

拒绝的专家执行时间是接受的五倍，而且这个估计对该设计已经够宽容：它没有算阅读选项、找到一个小号灰色链接（比大按钮更小的 $W$、更大的费茨指数），也没有算对每个开关含义的不确定——而每个用户都要在每一个网站上付出这笔代价。按欧盟 GDPR 及欧洲法院在 *Planet49*（2019）案中的解释，预先勾选的开关本身即不构成有效同意。对称的设计会在第一层就把"全部接受"与"全部拒绝"做成同样醒目的按钮。
:::
:::

监管机构已对此类设计采取行动。欧盟《通用数据保护条例》（General Data Protection Regulation，GDPR，2016）要求同意出于自愿、特定、知情且明确，撤回须与给出同样容易（第 7 条）；《数字服务法》（Regulation (EU) 2022/2065）禁止在线平台设计欺骗或操纵用户、或实质性扭曲其自由知情决策能力的界面（第 25 条）；美国联邦贸易委员会 2022 年的工作人员报告 *Bringing Dark Patterns to Light* 记录了其视为不公平或欺骗的做法。法律只抓得住最露骨的情形；其余依靠职业责任。

### 负责任地设计

除避免欺骗之外，还有若干框架帮助设计者思考价值。**价值敏感设计**（value sensitive design；Batya Friedman，1996；弗里德曼与 David Hendry 的专著，2019）识别直接与间接利益相关者及其所涉价值——隐私、自主、公平、信任、无障碍——并在整个设计过程中从概念、经验与技术三方面研究它们。B. J. 福格（Fogg）的 *Persuasive Technology*（2003）描述了计算机如何改变态度与行为，它所命名的领域如今追问：何时说服是在尊重自主（用户自己选择接收的提醒），何时是在利用弱点（为最大化停留时间而设计的变奖励通知）。**隐私内建**（Privacy by design）——收集最少的数据、默认采取保护性选项、让数据流向可见——在 GDPR 之下是法律义务（"经设计的数据保护与默认的数据保护"，第 25 条）。而用机器学习模型对人作决策的系统，其公平、透明与可异议问题见 [LLM 图谱](/learn/llm/)。

任何设计评审都可以问这些务实的问题：这个默认让谁受益？若每个选项都同样容易，用户还会这样选吗？若用户看到这条流程是如何设计、为何设计，我们会坦然吗？这个设计排斥了谁，我们和这些人测过吗？ACM 伦理准则（2018）要求计算专业者"避免伤害"，并设计"公平并主动行动以不歧视"的系统（[[software-engineering/professional-ethics]]）；无障碍与诚实设计，正是这些原则落在界面处的地方。

::: history
美国《康复法》第 508 条于 1998 年强化，覆盖联邦电子与信息技术，其时距 W3C 创立网络无障碍倡议组织（1997）一年；WCAG 1.0 于 1999 年跟进，WCAG 2.0 于 2008 年（2012 年采纳为 ISO/IEC 40500），WCAG 2.1 于 2018 年，WCAG 2.2 于 2023 年。《美国残疾人法》于 1990 年通过，联合国《残疾人权利公约》于 2006 年通过。罗恩·梅斯（Mace）在 20 世纪 80 年代提出"通用设计"。在伦理方面，巴特娅·弗里德曼（Friedman）于 1996 年提出价值敏感设计，B. J. 福格的 *Persuasive Technology* 于 2003 年问世，哈里·布里努尔于 2010 年提出"黑暗模式"，而格雷及其合作者的分类法（2018）与马图尔及其合作者的爬取研究（2019）把它们带进了研究视野。GDPR 于 2018 年生效，《数字服务法》的义务于 2024 年起适用于全部平台，《欧洲无障碍法案》自 2025 年 6 月起适用。
:::

- 残障产生于损伤与障碍的交互（**社会模式**）；约 16% 的人经历显著残障（WHO 2022），而情境性损伤关乎每个人。**无障碍**是面向最广用户范围的可用性（[[#def-accessibility]]）。

- 截至 2026 年，**《欧洲无障碍法案》**自 2025 年 6 月 28 日起适用；美国与英国法律同样要求无障碍，且多数法律引用 WCAG AA。
- 评估要自动化工具（头部一百万主页中 95.9% 连这些基本的都过不了，WebAIM 2026）、键盘与屏幕阅读器的人工测试、以及与残障用户一起测试并用；叠加层不是解决办法。
- **欺骗性设计模式**（[[#def-dark-pattern]]）利用注意、默认与省力；可用 KLM 量化不对称（[[#ex-banner]]）；GDPR 与《数字服务法》禁止最露骨的情形。价值敏感设计与隐私内建帮助负责任地构建。

## 习题

::: exercise 最小留距 {level=1 check="6"}
一行图标按钮为 18 × 18 CSS px。要适用 WCAG 2.2 成功标准 2.5.8 的留距例外，它们之间以 CSS px 计的最小留距是多少？（输入留距。）
::: solution
由 [[#prop-target-spacing]]，$g \ge 24 - 18 = 6$ px。
:::
:::

::: exercise 名称、角色、值 {level=1}
对下列每个元素，说明屏幕阅读器会读出什么，以及如何修复：(a) 用作开关的 `<div class="toggle on" onclick="flip()"></div>`；(b) `<a href="/report.pdf">Click here</a>`；(c) 用来显示季度销售额的 `<img src="chart.png" alt="chart">`；(d) 没有标签元素的 `<input type="checkbox" id="t"> I agree`。
::: solution
(a) 没什么有用的——至多读出"可点击"，没有角色、没有名称、没有状态，而且无法获得焦点。改用 `<button role="switch" aria-checked="true">Notifications</button>`（键盘支持由原生按钮提供），或样式化成开关的原生复选框。(b) 读出"点击这里，链接"——脱离语境毫无意义，而屏幕阅读器用户常常通过链接列表导航。改成"下载 2025 年年度报告（PDF，2 MB）"。(c) 读出"chart，图像"——信息丢失了。给一段概括其要旨的简短替代文字（"销售额逐季上升，从 120 万英镑增至 190 万英镑"），并在附近以表格给出数据。(d) 读作"复选框，未选中"，没有名称。改用 `<input type="checkbox" id="t"> <label for="t">I agree to the terms</label>`，这还能让文字可点击——目标更大了。
:::
:::

::: exercise 为模式归类 {level=1}
把下列欺骗性模式各自归入格雷及其合作者的五种策略（[[#def-dark-pattern]]）：(a) 网上即可开通、却只能在工作时间打电话取消的订阅；(b) 每次打开应用都弹出的"给应用评分！"提示；(c) 被默认加入购物车的旅游保险；(d) 刷新后重新开始计时的"优惠将于 09:59 后结束"倒计时；(e) 阅读一篇公开文章也必须注册账号。
::: solution
(a) 阻碍（"蟑螂汽车旅馆"：进得来，出不去）。(b) 纠缠。(c) 潜行（悄悄加进购物车）；也可辩称为经由预选默认的界面干扰。(d) 界面干扰——虚假紧迫；马图尔及其合作者把假计时器归入紧迫性一类，而且它们在法律意义上也是欺骗。(e) 强制行动。
:::
:::

::: exercise 按钮的对比度 {level=2}
某设计系统的主按钮是 `#0066CC` 上的白色文字，其禁用态是 `#E0E0E0` 上的 `#A0A0A0` 文字。用 [[hci/visual-design#ex-contrast]] 的对比度计算，对照 WCAG 2.2 检查两者并评论。
::: solution
白字在 `#0066CC` 上的对比度约为 5.57:1，对普通文字通过 AA 级 1.4.3。禁用态中，`#A0A0A0` 的 $L \approx 0.3515$，`#E0E0E0` 的 $L \approx 0.7454$，故对比度为 $(0.7454 + 0.05)/(0.3515 + 0.05) \approx 1.98$。这会违反 1.4.3——但 WCAG 把**未激活**用户界面组件中的文字豁免于对比度要求之外。豁免使设计"符合"，却未必是好的：低视力用户可能仍然需要*阅读*一个禁用按钮来了解它本会做什么，所以许多设计系统让禁用文字保持在 3:1 附近，并解释控件为何被禁用。
:::
:::

::: exercise 键盘路径 {level=2 check="9"}
某页面有一个含 6 个链接的页眉、一个搜索框及其提交按钮，然后是需要用户的主内容，其中第一个链接就是用户要去的地方。仅用键盘，从页眉第一个链接之前出发，需要按几次 Tab 才能到达那个链接？一个"跳到主内容"链接（WCAG 2.4.1）会如何改变这一点？（输入没有跳过链接时按 Tab 的次数。）
::: solution
每个可聚焦元素是一个 Tab 停靠点：页眉的 6 个链接（第 1–6 次）、搜索框（第 7 次）与其按钮（第 8 次），因此第一个内容链接在第 **9** 次按下时到达。跳过链接作为第一个可聚焦元素，用 Tab、Enter 与再一次 Tab 把用户带进主内容：每个页面三次按键，而不是九次。对屏幕阅读器用户，标题与地标（`<main>`、`<nav>`）提供类似的捷径。
:::
:::

::: exercise 取消订阅迷宫的代价 {level=2}
某订阅只能通过一个五屏流程取消：每屏要求一个决定与一次点击，每屏提供留下的折扣。用 KLM 估计专家执行时间，并论证该流程在欧盟是否合法、在 ACM 伦理准则下是否可接受。提出一个替代方案。
::: solution

::: exercise 二维留距检查 {level=3}
把 [[#prop-target-spacing]] 推广到网格：边长 $s < 24$ 的正方形目标按行列排布，水平与垂直留距均为 $g$。证明条件 $s + g \ge 24$ 依然充分（包括对角相邻的目标），并写一个函数，对任意以 $(x, y, w, h)$（CSS px）给出的轴对齐矩形目标列表检查留距例外，把每个不足尺寸目标的圆视为以其外接框为中心。在 16-px 图标组成的 $3 \times 3$ 网格上分别以 8-px 与 6-px 留距测试它。
::: solution
在网格中，水平与垂直相邻目标的中心距离为 $s + g$，对角相邻的为 $\sqrt2\,(s + g)$，更大；中心到对角相邻目标最近点的距离为 $\sqrt2\,(s/2 + g)$，也比水平情形的 $s/2 + g$ 大。于是所有条件都化为水平方向的条件，$s + g \ge 24$ 即充分。

```python
from math import hypot

def nearest_distance(cx, cy, rect):
    """Distance from point (cx, cy) to the nearest point of an axis-aligned rectangle."""
    x, y, w, h = rect
    dx = max(x - cx, 0, cx - (x + w))
    dy = max(y - cy, 0, cy - (y + h))
    return hypot(dx, dy)

def spacing_ok(targets, size=24):
    r = size / 2
    small = [t for t in targets if t[2] < size or t[3] < size]
    centre = lambda t: (t[0] + t[2] / 2, t[1] + t[3] / 2)
    for t in small:
        cx, cy = centre(t)
        for u in targets:
            if u is t:
                continue
            if nearest_distance(cx, cy, u) < r:                      # circle hits a target
                return False
            if u in small and hypot(cx - centre(u)[0], cy - centre(u)[1]) < 2 * r:
                return False                                          # two circles intersect
    return True

def grid(s, g, n=3):
    return [(i * (s + g), j * (s + g), s, s) for i in range(n) for j in range(n)]

print(spacing_ok(grid(16, 8)), spacing_ok(grid(16, 6)), spacing_ok(grid(24, 0)))
```

```console
$ python3 spacing.py
True False True
```

留距 8 px 时中心相距 24 px，网格通过；留距 6 px 时中心相距 22 px，不通过；24-px 目标没有尺寸不足，即使零留距也平凡地通过。（恰在距离 24 处相切的圆，在此同证明中的处理一样，计为不相交。）
:::

::: exercise 默认效应与同意 {level=3}
一项研究发现，当器官捐赠、养老金或 cookie 的选择以"同意"为预选时，最终选择"同意"的人远多于以"拒绝"为预选时，尽管两者都只相隔一次点击。用 KLM 与你所知的人类决策知识，解释默认为何如此强大——即便改变它如此轻易；并论证默认何时是正当的设计选择、何时变成欺骗性设计模式。把你的回答与 GDPR 的同意要求联系起来。
::: solution
KLM 表明改变默认的*执行*时间很短（$M\,P\,K$，不到 3 秒），所以这个效应主要不关乎省力：它关乎决策。默认会被读作**推荐**（设计者多半选了明智的选项），它省去了决定的认知劳动——昂贵的算子是 $M$，而对一个不熟悉的问题，它远不止 1.35 秒——而且人们会以现状为锚；埃里克·约翰逊（Johnson）与丹尼尔·戈德斯坦（Goldstein）对欧洲各国器官捐赠登记率的分析（"Do defaults save lives?"，*Science*，2003）是经典演示。默认符合多数用户经思考后会作的选择、符合用户利益、被清楚披露、且改变它与维持它同样容易时，它是正当的；带简便退出机制的职业养老金自动加入是标准例子。当它服务于服务方、与用户的可能偏好相悖，并靠用户的不注意来维系——尤其再配上阻碍（让替代更难）或潜行（不披露）——它就成了欺骗性模式。依 GDPR，同意必须是肯定的作为，因此预先勾选的框根本不能构成同意（*Planet49*，2019）：就个人数据而言，法律上的默认是"不"，直到用户说"是"。
:::
:::
