在本课程的测试机上，`ps` 列出约五千个线程，而处理器有 36 个核心。任一瞬间至多 36 个在运行；其余都在等——大多在等输入、磁盘、定时器或锁，也有一些只是在等轮到自己。每隔几毫秒，以及每当一个运行中的线程阻塞，内核都必须回答一个问题：*这个核心下一个该运行哪个可运行线程？*答案决定文本编辑器是一毫秒还是一秒响应一次按键，一次长计算是今晚还是明天完成，也决定一个不守规矩的程序能否饿死其余的程序。

本章研究这个问题。我们先从内核一侧看进程——表示它的数据结构、它经历的状态，以及把处理器从一个进程移到另一个进程的**上下文切换**（其代价我们将实测）。然后定义什么是好的调度，研究经典策略：先来先服务、最短作业优先及其可抢占形式、时间片轮转、多级反馈队列、按比例共享，以及 Linux 的公平调度器。其间我们会证明最短作业优先对平均周转时间最优，并理解这种最优性为何在实践中用途有限。

[[computer-systems/exceptions-processes]] 从程序员一侧介绍了进程（[[computer-systems/exceptions-processes#def-process]]）以及 `fork`、`execve` 和 `waitpid`；[[operating-systems/os-structure]] 表明定时器中断正是内核能收回处理器的原因。两者我们都要用到。本章中"进程"一词处处都可读作"线程"：Linux 调度的是线程（进程的每个线程都是独立可调度的任务），而策略是相同的。线程本身是 [[operating-systems/threads-locks]] 的主题。

## 内核眼中的进程

对每个进程，内核都保存一份记录，记下使它停下来、之后再让它恢复（仿佛什么都没发生）所需的一切。

::: definition 进程控制块 {#def-pcb}
**进程控制块**（PCB）是内核对进程的档案。它至少包含：进程标识符（PID）及其父进程；进程的**状态**；进程未运行期间保存的**寄存器上下文**（程序计数器、栈指针、通用寄存器、标志）；对它**地址空间**的描述（指向其页表与内存区域的指针）；它的打开文件表；凭据（用户与组 ID）；调度信息（优先级、累计 CPU 时间、所在的队列）；以及记账与信号状态。在 Linux 中，PCB 是 `struct task_struct`，每个线程一个，好几千字节。
:::

进程在为数不多的几个状态之间移动。

::: definition 进程状态 {#def-states}
- **就绪**（可运行）：进程可以运行，正在等待处理器。
- **运行**：它正在处理器上执行。
- **阻塞**（等待、睡眠）：在某个事件发生之前它不能运行——I/O 完成、定时器到期、锁释放、子进程退出。
- **新建**与**终止**（僵尸）：正在创建，或已结束但尚未被父进程回收（[[computer-systems/exceptions-processes]]）。

转移有：*分派*（就绪 → 运行）、*抢占*或*让出*（运行 → 就绪）、*阻塞*（运行 → 阻塞，由一次必须等待的系统调用引起）、*唤醒*（阻塞 → 就绪，事件发生时，通常在中断处理程序里），以及*退出*（运行 → 终止）。
:::

::: widget graph
nodes: new@0,1; ready@1.5,1; running@3,1; blocked@2.25,0; zombie@4.5,1
edges: new>ready; ready>running; running>ready; running>blocked; blocked>ready; running>zombie
algorithm: dfs
start: new
caption: [[#def-states]] 的进程状态图。从 `new` 起逐步执行深度优先搜索，注意两件事。第一，进入 `running` 的唯一途径是 `ready`：被唤醒的阻塞进程不会立刻运行，而是变为就绪，等待被选中。第二，`running → ready` 这条箭头就是调度器的杠杆——**可抢占**调度器用定时器中断强行使用它；**不可抢占**调度器等进程自己阻塞或让出。
:::

Linux 的 `ps` 用单个字母显示这些状态：`R`（运行或就绪——Linux 不在状态字段中区分二者）、`S`（睡眠，可被信号唤醒）、`D`（不可中断睡眠，通常在等磁盘 I/O）、`T`（停止）和 `Z`（僵尸）。内核把就绪任务放在每个核心的**运行队列**里，把阻塞的任务放在**等待队列**里，每个可能被等待的事件一个队列。

### 上下文切换

::: definition 上下文切换 {#def-context-switch}
**上下文切换**是内核把处理器从一个进程（或线程）转移到另一个的动作。它发生在内核内部、旧进程的上下文中：(1) 旧进程进入内核时（经系统调用、故障或中断），它的用户寄存器已经保存在它自己的内核栈上；(2) 调度器挑选下一个进程；(3) 内核把旧进程的*内核*栈指针和被调用者保存寄存器存入它的 PCB，并装载新进程的——于是执行在新进程的内核栈上继续，接着*它*上次调用调度器的地方；(4) 若新进程有不同的地址空间，内核装载它的页表根（x86-64 上的 `%cr3`）；(5) 新进程从内核返回用户态，恢复它的用户寄存器。
:::

第 (3) 步是巧妙之处。每个未运行的进程，在内核看来，都挂起在调度器函数内部、在它自己的某个内核栈上。切换不过就是换栈：对底层切换例程（Linux 的 `switch_to`）的调用由一个进程发出，却在另一个进程里返回。直接代价很小——保存和恢复几十个寄存器。间接代价更大：新进程发现高速缓存和快表里装满了旧进程的数据（[[computer-systems/memory-hierarchy]]），而在没有进程上下文标识符（PCID）的处理器上，`%cr3` 一改，快表就必须冲刷（[[operating-systems/address-spaces-paging]]）。

::: example 测量一次上下文切换 {#ex-pingpong}
两个进程绑定在同一个核心上，通过两条管道来回传递一个字节 200,000 次。每次往返迫使两次上下文切换（每个进程都在 `read` 里阻塞，直到对方写入）。估计一次切换的代价。

```c
#define _GNU_SOURCE                    /* sched_setaffinity、CPU_SET */
#include <sched.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/wait.h>
#include <time.h>
#include <unistd.h>

int main(int argc, char *argv[]) {
    int cpu_b = argc > 1 ? atoi(argv[1]) : 0;   /* 子进程的 CPU；父进程在 CPU 0 */
    enum { N = 200000 };
    int ab[2], ba[2];
    char c = 'x';
    if (pipe(ab) || pipe(ba)) return 1;
    cpu_set_t s;
    CPU_ZERO(&s); CPU_SET(0, &s);
    sched_setaffinity(0, sizeof s, &s);
    if (fork() == 0) {                          /* 子进程：把每个字节原样送回 */
        CPU_ZERO(&s); CPU_SET(cpu_b, &s);
        sched_setaffinity(0, sizeof s, &s);
        for (int i = 0; i < N; i++)
            if (read(ab[0], &c, 1) != 1 || write(ba[1], &c, 1) != 1) _exit(1);
        _exit(0);
    }
    struct timespec t0, t1;
    clock_gettime(CLOCK_MONOTONIC, &t0);
    for (int i = 0; i < N; i++)
        if (write(ab[1], &c, 1) != 1 || read(ba[0], &c, 1) != 1) return 1;
    clock_gettime(CLOCK_MONOTONIC, &t1);
    wait(NULL);
    double ns = ((t1.tv_sec - t0.tv_sec) * 1e9 + (t1.tv_nsec - t0.tv_nsec)) / N;
    printf("round trip %.0f ns (child on CPU %d)\n", ns, cpu_b);
    return 0;
}
```
::: solution
```console
$ gcc -std=c17 -Wall -Wextra -O2 -o pingpong pingpong.c
$ ./pingpong 0
round trip 6176 ns (child on CPU 0)
$ ./pingpong 1
round trip 7651 ns (child on CPU 1)
```
两个进程都在 CPU 0 上时，每次往返由四次系统调用（两次 `write` 和两次 `read`）和两次上下文切换组成。`/usr/bin/time -v` 证实仅父进程就有约 $200{,}000$ 次自愿切换。若这四次系统调用连同管道簿记各花约 $0.5$ µs——即 [[operating-systems/os-structure]] 中对一次最简调用的实测数字——那么两次切换共花约 $6.2 - 2 = 4.2$ µs，在这台机器上约每次 $2$ µs（一项**观测**；它包含唤醒另一个进程和调度器的决策，而在没有 Meltdown 缓解措施的较新硬件上，通常是几百纳秒到一微秒）。进程分处不同核心时，关键路径上没有切换，但每次唤醒都必须向可能空闲休眠的核心发送一次处理器间中断，在这里反而更慢。无论哪种情形，一次切换都要花几千条指令的时间，所以一个每微秒切换一次的调度器会把全部时间花在切换上。
:::
:::

## 什么样的调度算好

要比较策略，我们需要一个模型和若干度量。一个**作业**（或**爆发段**）是进程在下次阻塞之前想要完成的一段计算；它有变成就绪的**到达时刻** $a_j$ 和**长度**（服务时间）$b_j$。一个调度决定每个作业何时运行；作业 $j$ **首次运行**于 $s_j$，**完成**于 $c_j$。

::: definition 调度度量 {#def-metrics}
对作业 $j$：

- **周转时间** $T_j = c_j - a_j$，从到达至完成的时间；
- **等待时间** $W_j = T_j - b_j$，处于就绪却没有运行的时间；
- **响应时间** $R_j = s_j - a_j$，直到首次运行的时间。

对一组作业，评价一个调度器要看这些量的平均值、**吞吐率**（单位时间完成的作业数）、**CPU 利用率**（处理器忙的时间比例）、**公平性**（每个作业是否得到自己的一份），以及最坏情形（任何作业都不应**饥饿**，即永远等待）。
:::

这些目标相互冲突。批量计算关心周转时间和吞吐率；交互程序关心响应时间；共享服务器关心公平性。下面每个策略都是这些取舍上的一个立场。除特别说明外，我们假设单处理器、上下文切换免费，时间以抽象单位度量（可当作毫秒）。

我们用同一组四个作业贯穿全章：

| 作业 | 到达 $a$ | 长度 $b$ |
|---|---|---|
| A | 0 | 6 |
| B | 1 | 3 |
| C | 2 | 8 |
| D | 4 | 2 |

总工作量是 $19$，所以任何从不空转的策略都在时刻 $19$ 完成最后一个作业。本章的数字是用一个简短的 Python 模拟器算出（最后有一道习题请你写一个）并手工核对的。

## 先来先服务与最短作业优先

最简单的策略按到达顺序运行作业，每个跑到完成。

::: algorithm 先来先服务（FCFS） {#alg-fcfs}
把就绪作业放在一个先进先出队列里。处理器空闲时，取走队首的作业，运行到它完成（或阻塞）。新变就绪的作业接到队尾。
:::

在贯穿示例上，FCFS 让 A 运行于 $[0, 6)$、B 于 $[6, 9)$、C 于 $[9, 17)$、D 于 $[17, 19)$。周转时间是 $6, 8, 15, 15$，平均 $11$；等待时间 $0, 5, 7, 13$，平均 $6.25$。渺小的 D 只要 $2$ 个单位，却在长长的 C 后面等了 $13$。

这就是**护航效应**：短作业排在一个长作业后面，像跟在大卡车后面的小汽车。其影响可以很惊人。三个同时到达的作业长度为 $20$、$2$ 和 $2$，按这个顺序平均周转 $(20 + 22 + 24)/3 = 22$，短的先行则是 $(2 + 4 + 24)/3 = 10$。显而易见的补救是先运行短作业。

::: algorithm 最短作业优先（SJF） {#alg-sjf}
处理器空闲时，运行长度 $b_j$ 最小的就绪作业并跑到完成（并列时按到达时刻打破）。
:::

在贯穿示例上：时刻 $0$ 只有 A 就绪，它跑到 $6$。时刻 $6$ 就绪的是 B（$3$）、C（$8$）、D（$2$）：D 运行于 $[6, 8)$，B 于 $[8, 11)$，C 于 $[11, 19)$。周转时间 $6, 10, 17, 4$，平均 $9.25$。

::: theorem SJF 使平均等待时间最小 {#thm-sjf}
设 $n$ 个作业都在时刻 $0$ 到达，长度为 $b_1, \dots, b_n$，调度不空转地让每个作业跑到完成。在一切这样的调度中，按长度不减的顺序运行作业使平均等待时间最小，因而也使平均周转时间最小。
:::

::: proof
不带空闲时间的不可抢占调度就是作业的一个排列 $j_1, j_2, \dots, j_n$。作业 $j_k$ 要等它前面的所有作业，所以它的等待时间是 $W_{j_k} = \sum_{i<k} b_{j_i}$，总等待时间是

$$
\sum_{k=1}^n W_{j_k} = \sum_{k=1}^{n} (n - k)\, b_{j_k},
$$

因为位于第 $k$ 位的作业延迟它后面的 $n - k$ 个作业。设某个排列在位置 $k$ 与 $k+1$ 上有相邻两个作业满足 $b_{j_k} > b_{j_{k+1}}$。交换它们只改变这两项：交换前它们贡献 $(n-k) b_{j_k} + (n-k-1) b_{j_{k+1}}$；交换后是 $(n-k) b_{j_{k+1}} + (n-k-1) b_{j_k}$。两者之差（前减后）是 $b_{j_k} - b_{j_{k+1}} > 0$，所以交换严格减少总和。于是任何未按长度排序的排列都可改进，因此最优排列（存在，因为排列有限）必是排好序的；所有排好序的排列总和相同，因为交换相等的长度不改变任何事。周转时间 $T_j = W_j + b_j$，而 $\sum_j b_j$ 对一切调度都一样，所以同一个排列也使平均周转时间最小。
:::

作业到达时刻不同时，不可抢占 SJF 不再最优：贯穿示例里，C 和 D 被卡在 A 后面，因为 A 在它们到达之前就已经开始。允许**抢占**能解决这个问题。

::: algorithm 最短剩余时间优先（SRTF，又称 STCF） {#alg-srtf}
每当有作业到达或完成，就运行*剩余*工作量最少的就绪作业，必要时抢占正在运行的作业。
:::

在贯穿示例上：A 运行于 $[0, 1)$；时刻 $1$ B 到达，B 的 $3 < 5$（A 的剩余），所以 B 运行于 $[1, 4)$；时刻 $4$ D 到达，剩 $2$，最少，运行于 $[4, 6)$；然后 A 在 $[6, 11)$ 跑完它剩下的 $5$ 个单位，C 运行于 $[11, 19)$。

| 策略 | 调度 | 周转时间 A、B、C、D | 平均周转 | 平均响应 |
|---|---|---|---|---|
| FCFS | A 0–6, B 6–9, C 9–17, D 17–19 | 6, 8, 15, 15 | 11 | 6.25 |
| SJF | A 0–6, D 6–8, B 8–11, C 11–19 | 6, 10, 17, 4 | 9.25 | 4.5 |
| SRTF | A 0–1, B 1–4, D 4–6, A 6–11, C 11–19 | 11, 3, 17, 2 | 8.25 | 2.25 |

即使有任意的到达时刻，SRTF 对单处理器上的平均周转时间仍是最优的（这是 Linus Schrage 1968 年的结果，用一个按工作单位进行、更精细的交换论证证明）。那么为什么没有真实系统使用它？

::: warning 最优，却建立在无人拥有的信息上
SJF 与 SRTF 需要*事先知道每个作业的长度*。操作系统不知道一个进程在下次阻塞之前将计算多久；它只能从过去猜测，比如对测得的爆发段 $t_n$ 取指数平均 $\tau_{n+1} = \alpha t_n + (1-\alpha)\tau_n$。猜测恰在最要命的时候失败（程序改变了阶段），而因短爆发得到奖励的程序可以故意短暂阻塞来撒谎。SRTF 还会使长作业**饥饿**：只要短作业源源不断地到达，一个长作业就永远轮不到。最优性结论仍然宝贵——它们告诉我们偏袒短作业是对的，并给出一把标尺——但真实的调度器必须*学会*哪些作业短，这正是多级反馈队列所做的事。
:::

::: quiz
三个作业在时刻 $0$ 到达，长度为 $5$、$1$ 和 $3$。哪些说法正确？
- [x] SJF 按 $1$、$3$、$5$ 的顺序运行它们，平均周转 $(1 + 4 + 9)/3 = 14/3$。
- [ ] FCFS 按给出的顺序也得到平均周转 $14/3$。
- [x] 在这里，没有不可抢占调度的平均等待时间比 SJF 更小。
- [ ] 在这里，SRTF 的平均周转比 SJF 更小。
::: solution
SJF：在 $1$、$4$、$9$ 完成，平均 $14/3 \approx 4.67$。按 $5, 1, 3$ 顺序的 FCFS：在 $5$、$6$、$9$ 完成，平均 $20/3$。[[#thm-sjf]] 表明所有作业同时到达时 SJF 最优。只有当一个作业在另一个运行期间到达时，SRTF 才与 SJF 不同；这里全部在 $0$ 到达，所以 SRTF 给出同样的调度、同样的平均值。
:::
:::

## 时间片轮转与响应时间

FCFS、SJF 与 SRTF 是为批量作业设计的，它们的响应时间很差：一个作业可能要等很久才轮上运行。交互式系统则让每个就绪作业轮流运行。

::: algorithm 时间片轮转（RR），时间片为 $q$ {#alg-rr}
把就绪作业放在一个先进先出队列里。让队首作业运行至多 $q$ 个时间单位（**时间片**，quantum 或 time slice），由定时器中断强制执行。到那时它既没完成也没阻塞，就抢占它，把它放到队列尾部。（此处采用的约定：与抢占恰好同时到达的作业，排在被抢占作业*之前*入队。）
:::

::: example 贯穿示例上的时间片轮转 {#ex-rr}
对四个作业 A–D 跟踪 $q = 2$ 的时间片轮转，计算周转时间与响应时间。
::: solution
A 运行 $[0, 2)$；其间 B 在 $1$ 到达、C 在 $2$ 到达，于是队列为 B、C、A。B 运行 $[2, 4)$；D 在 $4$ 到达；队列 C、A、D、B。接着 C $[4, 6)$、A $[6, 8)$、D $[8, 10)$（完）、B $[10, 11)$（完）、C $[11, 13)$、A $[13, 15)$（完），最后 C $[15, 19)$。周转时间 $15, 10, 17, 6$，平均 $12$；响应时间 $0, 1, 2, 4$，平均 $1.75$。
:::
:::

| 策略 | 平均周转 | 平均响应 |
|---|---|---|
| RR，$q = 1$ | 11.75 | 0.75 |
| RR，$q = 2$ | 12 | 1.75 |
| RR，$q = 4$ | 11.75 | 3.75 |
| SRTF | 8.25 | 2.25 |

时间片轮转有最好的响应时间，周转时间却也在最差之列：共享处理器的代价是拖慢*每个人*的完成。四个长度 $10$ 的相同作业同时到达，FCFS 在 $10, 20, 30, 40$ 完成它们（平均 $25$），而 $q = 1$ 的 RR 在 $37, 38, 39, 40$ 完成（平均 $38.5$）——每个作业几乎和最晚的那个一样晚结束。

::: proposition 时间片轮转下的响应时间 {#prop-rr-response}
设 $n$ 个作业就绪，没有作业阻塞，每次上下文切换代价 $s$。在时间片为 $q$ 的时间片轮转下，一个作业在相邻两次运行之间至多等 $(n - 1)(q + s)$；只要所有作业都还需要至少一个完整的时间片，处理器时间中用于有效工作的比例至少是 $q/(q + s)$。
:::

::: proof
在一个作业的两次运行之间，其余 $n - 1$ 个作业各至多运行一次、至多 $q$，而每次运行前有一次代价为 $s$ 的切换；由此得证上界。只要每个作业还至少需要 $q$，每次运行都跑满时间片 $q$ 并花一次切换 $s$，所以每 $q + s$ 中有 $q$ 是有效工作。
:::

这就是时间片的权衡。取 $s = 2$ µs（[[#ex-pingpong]] 的实测值）、$q = 10$ ms，开销是 $0.02\%$——可忽略——但若有 $100$ 个就绪作业，一个作业可能为一轮运行等上一秒。$10$ µs 的时间片会带来很快的轮转，却把 $17\%$ 的处理器浪费在切换上，还不算每次切换引起的缓存缺失。真实系统使用大约 1–100 ms 的时间片，而且——更重要的是——很少有很多一直全部就绪的作业，因为交互程序大多在睡觉。

::: widget plot
f: 1 - p^x
x: 1, 20
y: 0, 1
sliders: p=0.8:0.1:0.99:0.01
labels: \text{CPU 利用率 } 1 - p^n
points: 4,0.5904; 11,0.9141
caption: 多道程序为何存在。若 $n$ 个进程每个都把 $p$ 的时间花在阻塞等 I/O 上，且进程彼此独立地阻塞，那么处理器空闲只发生在 $n$ 个进程同时阻塞之时，概率为 $p^n$，于是利用率为 $1 - p^n$。取 $p = 0.8$，一个进程只让处理器忙 $20\%$ 的时间，四个让它忙 $59\%$，十一个超过 $91\%$。把 $p$ 增大到接近 $1$（I/O 密集型负载），看看需要多少个进程——并记住独立性只是一种理想化。

## 多级反馈队列

我们两者都要：短作业有短周转（像 SJF），交互作业有快响应（像 RR），且没有饥饿——而且不知道作业长度。Fernando Corbató 在 1962 年的 CTSS 中给出的答案是，从行为中*学习*：一个用满时间片的作业多半是长作业；一个很快阻塞的作业多半是交互作业。

::: algorithm 多级反馈队列（MLFQ） {#alg-mlfq}
维护 $k$ 个就绪队列 $Q_0, \dots, Q_{k-1}$，$Q_0$ 优先级最高；队列 $Q_i$ 有时间片 $q_i$，通常随 $i$ 增大。

1. 若就绪作业的队列优先级高于正在运行作业的队列，它先运行（必要时抢占）。
2. 同一队列中的作业以时间片轮转运行。
3. 新作业进入 $Q_0$。
4. 每个作业在本级有一份 **配额**（allotment）的 CPU 时间（这里：一个时间片）。一旦用完配额——*无论用几次运行用完，无论中间阻塞过多少次*——它就降一级。
5. 每隔 $S$ 个时间单位，把所有作业移回 $Q_0$（**优先级提升**）。
:::

规则 4 使 MLFQ 近似 SRTF：短作业还在高优先级队列时就已经完成；长作业沉到底部，在那里用长时间片运行（有利于它的缓存），且只在没有更短的作业等待时才运行。短暂运行、很快阻塞的交互作业留在高处，得到快速响应。规则 5 防止饥饿——到底部的长作业会被周期性地提拔上来，即使短作业源源不断——并让一个从计算转为交互的作业爬回高处。

::: example 跟踪一个多级反馈队列 {#ex-mlfq}
三个队列，时间片 $q_0 = 1$、$q_1 = 2$、$q_2 = 4$，不做提升。作业 A（长度 $12$）在 $0$ 到达，B（长度 $2$）在 $3$，C（长度 $1$）在 $5$。跟踪 MLFQ，并把周转时间与 FCFS 比较。
::: solution
| 时刻 | 运行 | 队列层级 | 事件 |
|---|---|---|---|
| 0 | A | 0 | A 用掉 1 的时间片，降到 $Q_1$ |
| 1–2 | A | 1 | A 用掉 2 个单位，降到 $Q_2$ |
| 3 | B | 0 | B 到达于 $Q_0$，压过 A；用 1 个单位，降到 $Q_1$ |
| 4 | B | 1 | B 跑完最后一个单位，在 5 完成 |
| 5 | C | 0 | C 到达，运行 1 个单位，在 6 完成 |
| 6–14 | A | 2 | A 以 4、4、1 的时间片跑完剩下的 9 个单位；在 15 完成 |

周转时间：A $15$，B $5 - 3 = 2$，C $6 - 5 = 1$，平均 $6$。FCFS 会让 A 运行于 $[0, 12)$，B 于 $[12, 14)$，C 于 $[14, 15)$：周转 $12$、$11$、$10$，平均 $11$。MLFQ 不知道长度，却让每个短作业都得到了 SRTF 会给的周转时间，代价是 A 多花了 $3$ 个单位。
:::
:::

没有规则 4 的严格记账，MLFQ 可以被钻空子：一个程序只要在时间片快到期时发起一次无关紧要的 I/O 请求，就能永远留在 $Q_0$，同时把 $99\%$ 的时间花在计算上。有了跨运行累计的配额，它会像其他长作业一样沉下去。选择队列数、时间片、配额和 $S$ 是一门艺术——用 Arpaci-Dusseau 的话说，是一些"巫术常数"（voodoo constants）。MLFQ 的变体曾是 BSD Unix、Solaris 和 Windows NT 的调度器；后者至今仍用 32 个优先级层级，并对完成 I/O 或拥有前台窗口的线程动态提升优先级。

## 按比例共享与 Linux 调度器

另一个目标是**公平性**：每个作业应得到处理器的固定份额，比如与管理员设定的**权重**成比例。**彩票调度**（lottery scheduling，Waldspurger 与 Weihl，1994）按权重给每个作业彩票，每个时间片随机抽取一张彩票；随时间推移，每个作业的份额趋近其比例。**步进调度**（stride scheduling）确定性地做同样的事：每个任务有一个 *pass* 值，每次运行后前进 $1/\text{weight}$，pass 最小的任务下一个运行。Linux 的调度器是步进调度的精化。

::: definition 加权公平共享 {#def-fair-share}
在**加权公平共享**调度器中，每个可运行任务 $i$ 有权重 $w_i > 0$。在任何可运行任务集合 $R$ 保持不变的区间内，任务 $i$ 应得到处理器

$$
\frac{w_i}{\sum_{j \in R} w_j}
$$ {#eq-share}

的份额。每个任务的**虚拟运行时间**是它获得的 CPU 时间除以其权重（缩放使默认权重的任务虚拟时间等于真实时间）；公平的调度器把可运行任务的虚拟运行时间保持在彼此接近的水平。
:::

**完全公平调度器**（CFS），从 2007 年（内核 2.6.23）直到 2023 年的 Linux 默认调度器，直接实现了这一点：它把可运行任务保存在一棵按虚拟运行时间排序的红黑树里，总是运行最左边的——得到加权时间最少的任务。睡眠后醒来的任务被放在当前最小值附近，于是睡眠不会积攒无限的积欠。权重来自任务的 **nice** 值，从 $-20$（最高优先级）到 $19$：nice $0$ 权重 $1024$，每加一级权重乘以约 $1.25$（nice $1$ 是 $820$，nice $5$ 是 $335$，nice $10$ 是 $110$，nice $-5$ 是 $3121$），于是一级 nice 使一个任务相对竞争对手的份额改变约 $10\%$。

::: example 两个 nice 值不同的自旋进程 {#ex-nice}
两个 CPU 密集型程序绑定在同一核心上运行三秒，一个 nice $0$，一个 nice $5$。它们各得到多少份额？与一次测量比较。

```c
#define _POSIX_C_SOURCE 200809L
#include <stdio.h>
#include <time.h>

/* 挂钟时间自旋 3 秒；报告获得的 CPU 时间。 */
int main(int argc, char *argv[]) {
    struct timespec w0, w, c;
    clock_gettime(CLOCK_MONOTONIC, &w0);
    do clock_gettime(CLOCK_MONOTONIC, &w);
    while (w.tv_sec - w0.tv_sec < 3);
    clock_gettime(CLOCK_PROCESS_CPUTIME_ID, &c);
    printf("%s: %.2f s of CPU in 3 s\n", argc > 1 ? argv[1] : "?", c.tv_sec + c.tv_nsec * 1e-9);
    return 0;
}
```
::: solution
由 [[#eq-share]]，nice-0 任务应得到该核心的 $1024/(1024 + 335) \approx 0.753$，nice-5 任务得 $0.247$，比例约 $3$ 比 $1$。

```console
$ gcc -std=c17 -Wall -Wextra -O2 -o spin spin.c
$ taskset -c 33 ./spin nice0 & taskset -c 33 nice -n 5 ./spin nice5 & wait
nice0: 2.25 s of CPU in 3 s
nice5: 0.74 s of CPU in 3 s
```
份额是 $2.25/2.99 = 0.752$ 与 $0.248$——与预言相差不到零点几个百分点。（输出顺序与具体时间每次运行都有变化，核心繁忙时其他任务也会分走时间：另一次运行、另一个核心上，两个进程在 $3$ 秒中分别得到 $1.86$ 与 $0.61$ 秒，比例相同。）`taskset -c 33` 把程序绑定到 33 号核心，让两者真正竞争；不这样做的话，调度器会把它们放到不同的空闲核心上，无论 nice 如何，各自独占一核。
:::
:::

Linux 6.6（2023 年 10 月）把 CFS 的选取规则换成了 **EEVDF**——*最早符合资格的虚拟期限优先*（earliest eligible virtual deadline first）——这是 Ion Stoica 与 Hussein Abdel-Wahab 在 1995 年发表的算法。公平性以每个任务的**滞后**（lag）度量：理想加权共享下它应得的服务，减去它已得的服务。滞后非负（它还欠着时间）的任务是**符合资格的**。每个任务还有一个请求的**片段** $r$；它的**虚拟期限**是它的符合资格时刻加上 $r/w$。EEVDF 运行虚拟期限最早的符合资格任务。公平份额仍是 [[#eq-share]]，与 CFS 相同，但现在时延有了自己的旋钮：片段短的任务得到提前的期限、更早运行，只是每次运行得更短，份额并不更大。截至 2026 年，EEVDF 是 Linux 普通类（`SCHED_OTHER`）的调度器，默认基准片段 $0.75$ ms，随 CPU 个数的对数上调（八核及以上的机器上调到 $3$ ms），并且自 Linux 6.12（2024）起，任务可以用 `sched_setattr` 请求自己的片段。Linux 6.12 还加入了 `sched_ext`，允许把调度策略作为 eBPF 程序装载。

Linux 还有**实时**类：优先级固定为 $1$–$99$ 的 `SCHED_FIFO` 与 `SCHED_RR` 任务永远先于任何普通任务运行（`chrt` 命令设置它们；默认实时任务每秒被限流到 $95\%$，因此失控的实时任务无法让机器死锁——测试机上 `/proc/sys/kernel/sched_rt_runtime_us` 在 $1000000$ µs 的周期内是 $950000$），而 `SCHED_DEADLINE` 以带准入控制的最早期限优先调度任务。

### 多处理器

核心多了，调度器还必须决定任务*在哪里*运行。单一的共享运行队列实现简单、负载均衡完美，但每次调度决策都要给它加锁，而且任务在核心之间迁移会丢掉缓存数据。因此 Linux 每个核心保留一个运行队列，**负载均衡**定期执行、并在核心变空闲时执行，且倾向于把任务留在它先前运行的核心（或至少是同一缓存与内存节点）上——**缓存亲和**。程序可以用 `sched_setaffinity`（如 [[#ex-pingpong]] 所做）或 `taskset` 把自己限制在选定的核心上。让并行程序中相互协作的线程在不同核心上同时运行，即**成组调度**（gang scheduling），是 [[parallel-computing]] 的课题。

::: history
早期批量系统按先来先服务运行作业。科尔巴托（Corbató）、Merwin-Daggett 与 Daley 的 1962 年 CTSS 论文描述了一种多级调度方案：用满时间片的作业被移到时间片更长的低优先级队列——这是第一个多级反馈队列；科尔巴托因这项工作、以及他对分时和 Multics 的贡献获得 1990 年图灵奖。Linus Schrage 于 1968 年证明，单处理器上最短剩余处理时间优先使平均完成时间最小。Leonard Kleinrock 在 1960 年代对分时的排队分析量化了时间片轮转的取舍。Carl Waldspurger 与 William Weihl 于 1994 年提出彩票调度、1995 年提出步进调度；Stoica 与 Abdel-Wahab 于 1995 年发表了 EEVDF。Ingo Molnár 编写了 Linux 的 O(1) 调度器（2002）和后来的 CFS（2007），其灵感来自 Con Kolivas 的公平调度实验；转向 EEVDF 由 Peter Zijlstra 主导，2023 年并入 Linux 6.6。
:::

## 后续内容

进程抽象有两半：本章虚拟化了处理器，[[operating-systems/address-spaces-paging]] 虚拟化内存。多个线程共享一个地址空间时，调度决策可以在任何一条指令处打断它们，这正是 [[operating-systems/threads-locks]] 中竞争条件的来源；优先级调度与锁相互作用会引起*优先级反转*，在 [[operating-systems/synchronisation]] 中讨论。磁盘请求调度面临着同样的吞吐率与公平性的取舍，见 [[operating-systems/storage-io]]；在物理处理器上调度虚拟处理器见 [[operating-systems/virtualisation]]。排队论由到达与服务分布预测平均等待时间，建立在 [Maths Atlas](/learn/maths/) 的概率论之上；跨机器的调度是 [[distributed-systems]] 的一部分。

::: summary
- 内核用一个 **PCB**（[[#def-pcb]]）表示每个进程（在 Linux 中是每个线程），让它在就绪、运行与阻塞之间移动（[[#def-states]]）；**上下文切换**保存旧上下文，靠切换内核栈和地址空间恢复新上下文（[[#def-context-switch]]），直接代价是微秒级，缓存与快表缺失带来更大代价（[[#ex-pingpong]]）。
- 调度以周转、等待和响应时间，吞吐率、利用率与公平性来评判（[[#def-metrics]]）；这些目标相互冲突。
- **FCFS** 有护航效应。**SJF** 在所有作业同时到达时对平均等待时间最优，用交换论证证明（[[#thm-sjf]]）；**SRTF** 在有到达情形时最优。两者都需要作业长度，而操作系统并不知道，且两者都可能使长作业饥饿。
- **时间片轮转**响应时间好、周转时间差；时间片用切换开销 $s/(q+s)$ 换等待时间 $(n-1)(q+s)$（[[#prop-rr-response]]）。
- **MLFQ** 从行为学习作业长度：用完配额的作业降级，交互作业留在高处，周期性提升以防饥饿（[[#alg-mlfq]]）。
- **按比例共享**调度器给任务 $i$ 份额 $w_i/\sum w_j$（[[#eq-share]]）。Linux 用过 CFS（虚拟运行时间，2007–2023），截至 2026 年使用 EEVDF（滞后与虚拟期限，自 6.6 起）；nice 层级使权重改变约 $1.25$ 倍。
:::

## 习题

::: exercise 手工 FCFS {level=1 check="8.25"}
作业 P、Q、R、S 在时刻 $0, 1, 2, 3$ 到达，长度为 $5, 2, 6, 1$。画出 FCFS 调度并计算平均周转时间。（输入平均周转时间。）
::: solution
FCFS 让 P 运行于 $[0, 5)$，Q 于 $[5, 7)$，R 于 $[7, 13)$，S 于 $[13, 14)$。周转时间：P $5 - 0 = 5$，Q $7 - 1 = 6$，R $13 - 2 = 11$，S $14 - 3 = 11$。平均 $33/4 = 8.25$。S 只要一个单位，却等了 $10$。
:::
:::

::: exercise 同一批作业的 SRTF {level=1 check="5.75"}
对上一道习题的作业，画出 SRTF 调度并计算平均周转时间。（输入平均周转时间。）
::: solution
时刻 $0$ 只有 P 就绪：它运行。时刻 $1$ Q 到达，Q 的 $2 < 4$（P 的剩余）：Q 运行于 $[1, 3)$ 并完成。时刻 $2$ R 到达，剩 $6$；时刻 $3$ S 到达，剩 $1$，最少：S 运行于 $[3, 4)$。然后 P（剩余 $4$）运行于 $[4, 8)$，R 于 $[8, 14)$。周转时间：P $8$，Q $2$，R $12$，S $1$；平均 $23/4 = 5.75$。（不可抢占 SJF 给出 $6.75$，FCFS 给出 $8.25$。）
:::
:::

::: exercise nice 层级 {level=1 check="1024/1134"}
加权公平调度器下，两个 CPU 密集型任务共享一个核心，一个 nice $0$（权重 $1024$），一个 nice $10$（权重 $110$）。nice-0 任务得到核心的几分之几？（输入该分数。）
::: solution
由 [[#eq-share]]，$1024/(1024 + 110) = 1024/1134 \approx 0.903$。nice-10 任务得到约 $9.7\%$。十个 nice 层级使权重之比乘以约 $1.25^{10} \approx 9.3$。
:::
:::

::: exercise 时间片轮转恶化周转 {level=2 check="38.5"}
四个长度 $10$ 的作业同时到达。计算时间片为 $1$（且上下文切换免费）时时间片轮转下的平均周转时间，并与 FCFS 比较。然后推导 $n$ 个长度为 $L$ 的作业、时间片为 $1$ 时的公式。（输入四个作业在时间片轮转下的平均值。）
::: solution
作业轮流运行 A、B、C、D、A、B、…；每个需要 10 轮。9 个完整轮次（$36$ 个单位）后各剩 $1$ 个单位，于是在 $37, 38, 39, 40$ 完成：平均 $38.5$。FCFS 在 $10, 20, 30, 40$ 完成：平均 $25$。一般地，$n$ 个长度为 $L$ 的作业，时间片轮转让作业 $k$ 在 $n(L-1) + k$ 完成，平均为 $n(L - 1) + (n+1)/2$；FCFS 是 $L(n+1)/2$。$L$ 很大时，RR 的平均约为 $nL$——几乎是 FCFS 的 $nL/2$ 的两倍。平均分配让所有人都结束得晚；RR 的好处是响应时间，不是周转时间。
:::
:::

::: exercise 要多少道多道程序 {level=2 check="11"}
各进程独立地花 $80\%$ 的时间等 I/O。用利用率 $1 - p^n$，使处理器至少 $90\%$ 繁忙的最少进程数 $n$ 是多少？（输入 $n$。）
::: solution
需要 $0.8^n \le 0.1$，所以 $n \ge \ln 0.1 / \ln 0.8 = 2.3026/0.2231 \approx 10.32$，故 $n = 11$：$1 - 0.8^{10} = 0.893$，$1 - 0.8^{11} = 0.914$。模型假设独立阻塞；进程一起等待同一个磁盘块时，真实利用率会更低。
:::

::: exercise 估计切换代价 {level=2 check="2.05"}
一次类似 [[#ex-pingpong]] 的乒乓测试在单个核心上测得每次往返 $6.1$ µs。每次往返发起四次系统调用，除切换外每次约 $0.5$ µs。估计一次上下文切换的代价。（输入微秒数。）
::: solution
一次往返含四次系统调用（$2$ µs）和两次上下文切换。所以 $2x = 6.1 - 2$，$x = 2.05$ µs。这是粗略估计：会阻塞的管道 `read` 的"系统调用代价"与 `getppid` 并不相同，而且测得的时间还包括唤醒另一个进程。`perf bench sched pipe` 这类工具做的正是这项测量。
:::

::: exercise 欺骗调度器 {level=3}
考虑一个 MLFQ，其中的规则 4 被改成：一个作业只有当它*在一次运行*中用满整个时间片时才降级，且阻塞时计数清零。描述一个 CPU 密集型程序，使它在其他 CPU 密集型程序存在时几乎独占处理器，并确切说明原样陈述的规则 4 如何挫败它。这个攻击能否同样骗过 CFS 式的公平调度器？
::: solution
该程序计算 $q_0 - \epsilon$——比顶层时间片只差一点——然后发起一次无关紧要的阻塞调用（比如从一个总是就绪的管道读 1 个字节，或 `nanosleep` 一微秒）。它从不在一次运行中用满整个时间片，所以永不降级；它留在 $Q_0$，而 $Q_0$ 总先于已沉入较低队列的其他 CPU 密集作业运行。它每次重新就绪都会抢占它们。它得到接近 $1$ 的处理器份额。按原样陈述的规则 4，调度器*跨运行*统计作业在本级使用的 CPU 时间；累计达到 $q_0$（无论分成几段）后它被降级，接着在下一级累计 $q_1$ 后再次降级，依此类推，与诚实的 CPU 密集作业分毫不差。公平共享调度器也不会被骗，因为它根本不给作业分类：它按每个任务实际使用的 CPU 时间收费（其虚拟运行时间按该时间除以其权重增长），且总是偏爱得到时间最少的任务，所以短暂阻塞什么也赚不到，除了一个醒来任务被给予的、有上界的积欠之外。
:::
:::

::: exercise Smith 规则 {level=3}
作业在时刻 $0$ 到达，长度为 $b_j$，重要性权重 $u_j > 0$。证明：在不空转的不可抢占调度中，完成时间的加权和 $\sum_j u_j c_j$ 在按 $b_j/u_j$ 不减的顺序运行作业时最小（Smith 规则，1956）。把 [[#thm-sjf]] 作为特例推出。
::: solution
调度就是作业的一个次序。取两个相邻作业，$x$ 在位置 $k$，$y$ 在位置 $k + 1$，设 $t$ 为它们之前那个作业的完成时刻（$k = 1$ 时 $t = 0$）。交换前，两者贡献 $u_x(t + b_x) + u_y(t + b_x + b_y)$；交换后是 $u_y(t + b_y) + u_x(t + b_y + b_x)$。其他完成时间都不变，因为这两个作业合起来仍占据 $[t, t + b_x + b_y)$。差值（前减后）是

$$
u_y b_x - u_x b_y = u_x u_y\left(\frac{b_x}{u_x} - \frac{b_y}{u_y}\right),
$$

它恰在 $b_x/u_x > b_y/u_y$ 时为正。所以任何含有一对按比值 $b/u$ 乱序的相邻作业的次序都可严格改进；最优次序存在（次序有限）因而没有这样的乱序对，于是它按 $b_j/u_j$ 排好序；只在相等比值内部不同的次序总和相同，因为交换这样一对不改变任何事。当所有 $u_j = 1$ 时，次序即按长度排序，且 $\sum_j c_j = \sum_j (W_j + b_j)$，所以使总完成时间最小就是使总等待时间最小：[[#thm-sjf]]。
:::
:::

::: exercise 一个调度模拟器 {level=3}
写一个 Python 函数 `rr(jobs, q)`，接受字典 `{name: (arrival, length)}` 和一个时间片，用整数时间和 [[#alg-rr]] 的到达约定模拟时间片轮转，返回完成时刻。对照 $q = 2$ 时贯穿示例的跟踪来检查它。
::: solution
```python
from collections import deque

def rr(jobs, q):
    remaining = {j: b for j, (a, b) in jobs.items()}
    pending = sorted(jobs, key=lambda j: jobs[j][0])   # 尚未到达
    ready, done, t = deque(), {}, 0
    def admit(now):                                     # 把到达者移进队列
        while pending and jobs[pending[0]][0] <= now:
            ready.append(pending.pop(0))
    admit(t)
    while len(done) < len(jobs):
        if not ready:                                   # 空转至下一个到达时刻
            t = jobs[pending[0]][0]; admit(t); continue
        j = ready.popleft()
        run = min(q, remaining[j])
        t += run; remaining[j] -= run
        admit(t)                                        # 新到达者排在 j 之前
        if remaining[j] == 0:
            done[j] = t
        else:
            ready.append(j)
    return done

print(rr({'A': (0, 6), 'B': (1, 3), 'C': (2, 8), 'D': (4, 2)}, 2))
```
```console
$ python3 rr.py
{'D': 10, 'B': 11, 'A': 15, 'C': 19}
```
这些正是正文跟踪的完成时刻（周转 $15, 10, 17, 6$）。因为 `admit(t)` 在被抢占作业重新入队*之前*执行，恰好在抢占时刻到达的作业先入队，与约定一致。
:::
