在笔记本电脑上运行一个程序时，其实已经有几十个程序在运行：一个开着四十个标签页的浏览器、一个音乐播放器、一个备份守护进程、窗口系统、一个终端。每个程序都以为自己独享处理器和内存。它们谁也不能读别人的内存，不能通过向磁盘控制器写入而使机器崩溃，也不能进入一个无限循环而永久霸占处理器。然而它们共享同一个处理器（或几个核心）、同一条内存和同一块磁盘。有一个东西在仲裁——而它不能仅仅又是一个程序，因为想要作弊的程序完全可以无视它。

仲裁者就是**操作系统**，而它工作原理的关键在于硬件的一个特性：处理器可以运行在两种模式下，其中只有一种能触碰真正重要的机构。本章解释这一基础。我们先讲操作系统的用途；然后确切地看是哪些硬件机制使保护成为可能，并证明它们每一个都是必不可少的；再看程序请求服务所必须经过的系统调用边界及其代价；比较内核可能的组织方式——单体式、分层式、微内核及其他——以及它们之间的取舍；最后跟着一台机器从加电一直走到第一个用户进程。

[[computer-systems/exceptions-processes]] 已经介绍了异常、异常的四种类型、寄存器层面的系统调用、进程、`fork`、`execve` 和信号。本章直接沿用这些内容，不再重复；若其中有任何名词对你还很陌生，请先读那一章。

本课程的所有程序都在 x86-64 Linux（内核 7.0、glibc 2.43、Intel Xeon E5-2696 v3）上用 GCC 15.2 编译，除特别说明外命令都是 `gcc -std=c17 -Wall -Wextra -O2`。计时是那台机器上的**观测**；进程号与地址每次运行都会变化。

## 操作系统的职能

最好同时在心里保留关于操作系统的三幅图景。

- **裁判。** 若干程序由互不信任的不同人编写，共享一台机器。操作系统决定谁得到什么——哪个程序在哪个核心上运行、每个程序可以用多少内存、谁可以打开哪个文件——并且强制执行这些决定，于是一个有缺陷或有恶意的程序无法伤害其他程序。
- **幻术师。** 每个程序都被交给一台简化过的、理想化的机器：属于它自己的处理器（进程抽象）、一大块私有内存（虚拟内存），以及有名字、持久、可按字节寻址的文件，而不是编号的磁盘扇区。物理资源被**虚拟化**——在时间上复用（处理器）或在空间上复用（内存、磁盘）——使每个用户都看到一份私有副本。
- **粘合剂。** 它提供每个程序都需要的公共服务：文件系统、网络协议、对成千上万种不同设备的统一接口、启动其他程序并与之通信的方法。

这三种角色组织起本课程的其余部分，用的是 Remzi 与 Andrea Arpaci-Dusseau 的教材使之成为标准的三个标题：**虚拟化**（进程、调度、地址空间、分页）、**并发**（线程、锁、条件变量、信号量、死锁）与**持久化**（设备、磁盘、文件系统、崩溃一致性），最后以整台机器的虚拟化收尾。

::: definition 操作系统与内核 {#def-os}
**操作系统**是管理计算机硬件资源、为程序提供公共服务的软件。它的核心是**内核**，即以完全硬件特权运行的那部分：只能经异常（系统调用、中断和故障）进入，而且只有它能执行特权指令、访问全部内存和每一个设备。操作系统的其余部分——C 库、shell、系统守护进程、窗口系统——以普通**用户态**程序运行。
:::

这一区分很重要，因为"操作系统"一词用得很宽松。一个 Linux 发行版包含上千个软件包，但 Linux *内核*只是一个程序，启动时载入，机器运行期间常驻内存。本课程不加限定地说"操作系统做 X"时，指的就是内核。

一个反复出现的设计原则是**机制**与**策略**的分离。机制是*如何做*得到——能让内核把处理器收回来的定时器中断、映射地址的页表。策略是*选择做哪一个*——下一个运行哪个进程、逐出哪个页。好的内核把机制做通用，让策略可替换：例如 Linux 在相同的底层机制之上提供多个调度类和多个 I/O 调度器。我们在每一章都会遇到这种分工。

## 保护：硬件必须提供什么

假设操作系统只是一些有用例程的库，链接进每个程序，就像早期运行 MS-DOS 的个人计算机那样。那么就没有任何东西能阻止一个程序改写这个库、给磁盘控制器重新编程、或者永远不把处理器交还。保护不能只靠软件建立，因为软件所做的任何检查，被检查的程序都可以从旁边跳过去。它需要处理器的帮助。

::: definition 双模式运行 {#def-dual-mode}
若一个处理器具有（至少）两个特权级别——**内核态**与**用户态**——记录在处理器状态的一个模式位中，使得：

1. 一组**特权指令**——改变模式、内存映射、异常表或定时器、执行 I/O 或使处理器停机的指令——只能在内核态执行；在用户态尝试执行会引发一个异常；
2. 从用户态进入内核态的唯一途径是异常（陷入、故障或中断），它把控制转移到内核事先选定地址处的处理程序；
3. 从异常返回（x86-64 上的 `iret`、`sysret`）可以把特权级别重新降回用户态。

就称该处理器支持**双模式运行**。
:::

在 x86-64 上，特权级别是**当前特权级**（CPL），占两个位、四个**环**（0 到 3）；Linux 与 Windows 只用环 0（内核）和环 3（用户）。ARMv8 有异常级别 EL0（用户）到 EL3（安全监控器），RISC-V 有用户态、监管态和机器态。本章的一切两个级别就够用；多出的级别用于虚拟机监控器和固件（[[operating-systems/virtualisation]]）。

下面是一个普通程序尝试执行特权指令时会发生什么。`hlt` 使处理器停机直到下一个中断——对内核的空闲循环无害，但倘若任何程序都能这样做就是灾难。

```c
#include <stdio.h>

int main(void) {
    printf("about to execute hlt in user mode\n");
    fflush(stdout);
    __asm__ volatile ("hlt");     /* 特权指令：只允许在内核态（环 0）执行 */
    printf("never printed\n");
    return 0;
}
```

```console
$ gcc -std=c17 -Wall -Wextra -O2 -o priv priv.c
$ ./priv; echo "exit status $?"
about to execute hlt in user mode
Segmentation fault         ./priv
exit status 139
$ strace -e trace=none ./priv
about to execute hlt in user mode
--- SIGSEGV {si_signo=SIGSEGV, si_code=SI_KERNEL, si_addr=NULL} ---
+++ killed by SIGSEGV +++
```

处理器触发了一个**一般保护性故障**（x86 的异常 13）；内核的处理程序发现是一个用户程序引起的，就向该程序发送 `SIGSEGV`——状态 $139 = 128 + 11$——机器继续运行。`si_code=SI_KERNEL` 记录该信号来自内核的故障处理程序，而不是来自另一个进程。

双模式保护的是特权*指令*。还有两个机制保护程序可能独占的另外两种资源。

- **内存保护。** 在用户态，每个地址都由**内存管理单元**（MMU）通过只有内核能修改的页表来转换（[[operating-systems/address-spaces-paging]]）。用户程序只能指名内核为它映射的页，并且只能以内核选定的权限访问；内核自己的内存映射时不带用户访问权。
- **CPU 保护。** 硬件**定时器**周期性地或在程序设定的期限处发出中断。由于中断进入内核，无论程序循环多久，内核至少每那么久就能重新获得控制。只有内核态才能给定时器重新编程或屏蔽中断（当 I/O 特权级别低于 CPL 时 `cli` 是特权指令，现代内核都这样配置）。

::: proposition 保护的三条要求 {#prop-protection}
考虑一台同时运行不受信任的用户程序与内核的机器。假设下面每一件事都可能由用户程序做到：(a) 经由内核选定的异常入口之外的途径进入内核态；(b) 修改内存映射，或访问自己映射的页以外的内存；(c) 屏蔽定时器中断或给定时器重新编程。那么在每种情形下，用户程序都能使内核无法执行任何策略。反之，若 (a)–(c) 都不可能，且内核的异常处理程序是正确的，则用户程序只能通过内核提供的服务影响其他程序。
:::

::: proof
(a) 若程序能在自己选定的地址进入内核态，它就是以完全特权运行自己的代码：它能执行每条特权指令，于是控制内核所控制的一切。(b) 若程序能修改映射，它就能映射内核代码或异常表，并用它自己的指令覆写它们；下一次异常就会在内核态运行该程序的代码，这就回到情形 (a)。若它能直接读写其他内存，就能在没有内核参与的情况下读取或破坏其他程序的数据。(c) 若程序能屏蔽定时器，那么一旦它运行起来、既不发起系统调用也不引发故障，就永远不会有任何异常发生；而内核只在响应异常时才运行，所以内核再也不会运行，程序就永远霸占处理器。

反过来，注意内核只在响应异常时才执行，而用户程序运行期间只能在自己的映射内存上执行非特权指令（由 (a)、(b) 及特权指令的定义）。每一条这样的指令只影响该程序自己的寄存器和内存。程序只能靠引发一个异常来影响其他任何东西，而异常会运行内核处理程序，所以其他程序只在那些处理程序允许的范围内受到影响。由 (c)，无论程序做什么，定时器中断都会在一个定时器周期内到达，于是内核的调度策略也得到了执行。（直接用内存访问的设备也必须受限，即由 IOMMU 限制，上述论证才能覆盖 DMA；而 Meltdown 这样通过推测执行泄露内核内存的处理器缺陷说明，硬件必须分毫不差地实现这些规则——见 [[security]]。）
:::

::: quiz
为使保护成立，下面哪些 x86-64 指令或动作必须是特权的？
- [x] 装载 `%cr3`，即存放顶层页表物理地址的寄存器。
- [ ] 执行 `syscall`。
- [x] 执行 `cli` 以屏蔽中断。
- [x] 用 `lidt` 装载中断描述符表的地址。
- [ ] 用 `rdtsc` 读时间戳计数器。
::: solution
装载 `%cr3` 改变内存映射（要求 (b)）；`cli` 屏蔽定时器中断（要求 (c)）；`lidt` 决定异常的去向，于是一个无特权的 `lidt` 就能让程序在它自己选定的地址进入内核态（要求 (a)）。`syscall` *必须*是非特权的——它就是用户程序用来进入内核的那条指令，入口地址是内核存在一个模型专用寄存器里的。`rdtsc` 只是读一个计数器；它默认非特权（内核可以让它触发故障，一些沙箱为了让精确计时更难就这么做，但 [[#prop-protection]] 意义上的保护不依赖于它）。
:::
:::

## 系统调用边界

有了保护，用户程序就被限制在自己的内存和非特权指令之内。其余的一切——读文件、发分组、创建进程，甚至多要一些内存——都是对内核的请求，经系统调用发出。[[computer-systems/exceptions-processes]] 展示了寄存器约定：调用号放在 `%rax`，实参放在 `%rdi`、`%rsi`、`%rdx`、`%r10`、`%r8`、`%r9`，然后执行 `syscall` 指令。从操作系统的角度看，系统调用的集合就是内核对世界的全部接口。

::: definition 系统调用接口 {#def-syscall-interface}
内核的**系统调用接口**是它向用户程序提供的服务集合，每个服务由一个号标识，接受至多六个字大小的实参。每次系统调用都是向同一个内核入口的陷入，该入口 (1) 保存用户寄存器，(2) 检查号是否有效并通过**系统调用表**分派，(3) 校验每一个实参——指针指向的必须是调用者可访问的用户内存、描述符必须是打开的、调用者必须有权限——(4) 执行服务，(5) 返回结果，失败时返回负错误码 $-\mathit{errno}$。
:::

C 库的包装函数把这些藏了起来，但没有任何东西规定必须有它们。

::: example 不用库的系统调用 {#ex-raw-syscall}
写一个程序，用 `syscall` 指令直接调用 `write`，一次写到标准输出，一次写到一个未打开的描述符，并预言每次调用返回什么。


```c
#include <stddef.h>

/* 不用 C 库包装函数的 write(fd, buf, len) */
static long raw_write(int fd, const void *buf, size_t len) {
    long ret;
    __asm__ volatile ("syscall"
                      : "=a"(ret)                       /* 结果在 %rax */
                      : "a"(1L), "D"((long)fd), "S"(buf), "d"(len)
                      : "rcx", "r11", "memory");        /* syscall 会破坏 rcx、r11 */
    return ret;
}

int main(void) {
    long n = raw_write(1, "hello from a raw syscall\n", 25);
    long e = raw_write(99, "x", 1);                     /* 非法描述符 */
    return (n == 25 && e == -9) ? 0 : 1;                /* -9 即 -EBADF */
}
```

::: solution
GCC 的内联汇编把实参放进约定的寄存器；程序自己检查两个结果。

```console
$ gcc -std=c17 -Wall -Wextra -O2 -o rawsys rawsys.c && ./rawsys; echo "status $?"
hello from a raw syscall
status 0
$ strace ./rawsys 2>&1 | tail -3
write(99, "x", 1)                       = -1 EBADF (Bad file descriptor)
exit_group(0)                           = ?
+++ exited with 0 +++
```

约束字母 `a`、`D`、`S`、`d` 分别指名 `%rax`、`%rdi`、`%rsi`、`%rdx`。破坏列表很重要：`syscall` 指令把用户的返回地址存进 `%rcx`、把其标志存进 `%r11`，所以编译器绝不能在那里保留任何东西。没有 C 库，就没有东西把 $-9$ 变成 $-1$ 和 `errno`；内核的原始约定清晰可见。
:::
:::

### 为什么内核必须不信任它的实参

[[#def-syscall-interface]] 中的第 (3) 步是内核最常犯错的地方。一个指针实参是一个不受信任的程序选定的地址。如果内核简单地把它解引用，一个程序就可以传入内核内存的地址，让内核代它读取或覆写——从内部破坏 [[#prop-protection]]。因此 Linux 只通过 `copy_from_user`、`copy_to_user` 这类函数在用户内存与内核内存之间复制数据，这些函数检查整个范围位于地址空间的用户部分，并能从容处理中途发生的缺页（返回 `-EFAULT`，即 "Bad address" 错误），而不是让内核崩溃。自 2012 年（SMEP）和 2014 年（SMAP）起，x86 处理器还有 **SMEP** 与 **SMAP**（监管态执行阻止与访问阻止），它们使内核对用户页的任何访问都触发故障，除非内核显式地为访问打开一个窗口，于是一处缺失的检查会变成一次崩溃，而不是一个无声的漏洞。

一个更微妙的缺陷是**双重取数**（double fetch）：内核从用户内存读一个长度，检查它，稍后又再读一次来使用它。同一程序的另一个线程可以在两次读之间改变这个值，于是使用的值不是检查过的值。补救办法是把每个实参恰好复制一次到内核内存，之后只在副本上工作。这是**检查时刻与使用时刻不符**（time-of-check-to-time-of-use，TOCTOU）这一普遍问题的一个实例，我们在文件处还会遇到它（[[operating-systems/file-systems]]），并在 [[security]] 中系统处理。

### 一次系统调用多贵

系统调用远比函数调用昂贵。处理器必须切换特权级和栈；内核要保存寄存器、分派、校验；而在受 Meltdown 影响的处理器上，内核还要在每次进入和退出时切换页表（**内核页表隔离**，即测试机 `/proc/cpuinfo` 里的 `pti` 标志），并冲刷或分区处理器状态以防御推测执行攻击。下面的程序对此作了测量：

```c
#define _GNU_SOURCE                        /* 供 syscall() 使用 */
#include <stdio.h>
#include <sys/syscall.h>
#include <time.h>
#include <unistd.h>

static double now(void) {                 /* 秒，单调时钟 */
    struct timespec t;
    clock_gettime(CLOCK_MONOTONIC, &t);
    return t.tv_sec + t.tv_nsec * 1e-9;
}

__attribute__((noinline)) static long f(long x) { __asm__ volatile(""); return x + 1; }

int main(void) {
    enum { N = 10000000 };
    struct timespec ts;
    long s = 0;
    double t0 = now();
    for (int i = 0; i < N; i++) s += f(i);                      /* 普通函数调用 */
    double t1 = now();
    for (int i = 0; i < N; i++) s += syscall(SYS_getppid);      /* 真正的陷入 */
    double t2 = now();
    for (int i = 0; i < N; i++) { clock_gettime(CLOCK_MONOTONIC, &ts); s += ts.tv_nsec & 1; }
    double t3 = now();
    printf("function call   %6.1f ns\n", (t1 - t0) / N * 1e9);
    printf("getppid syscall %6.1f ns\n", (t2 - t1) / N * 1e9);
    printf("clock_gettime   %6.1f ns\n", (t3 - t2) / N * 1e9);
    return s == 42;                        /* 使用 s，使循环不被删除 */
}
```

```console
$ ./cost
function call      1.8 ns
getppid syscall  478.0 ns
clock_gettime     18.5 ns
```

在这台机器上，一次最简系统调用约相当于 250 次函数调用（一项**观测**：在近年不受 Meltdown 缓解措施影响的处理器上通常是 50–150 ns）。但 `clock_gettime`——手册页里也把它列为系统调用——只要 18 ns。原因是 **vDSO**（虚拟动态共享对象，virtual dynamic shared object）：内核把一个小的只读共享库映射进每个进程（在 `/proc/self/maps` 中显示为 `[vdso]`），连同它随时保持更新的一页数据（`[vvar]`），于是读时钟就成了一次读普通内存的普通函数调用。`strace` 证实读时钟从不进入内核：

```c
#define _POSIX_C_SOURCE 200809L
#include <stdio.h>
#include <time.h>
#include <unistd.h>

int main(void) {
    struct timespec t;
    for (int i = 0; i < 1000; i++) clock_gettime(CLOCK_MONOTONIC, &t);
    printf("pid %d\n", (int)getpid());
    return 0;
}
```

```console
$ strace -c ./vdso 2>&1 | grep -E 'clock|getpid|write|total'
  3.24    0.000018          18         1           write
  0.54    0.000003           3         1           getpid
100.00    0.000556          15        35         1 total
```

一千次 `clock_gettime` 调用，没有一次是系统调用。vDSO 是一般策略"*尽可能少跨界*"的极致。C 库的缓冲 I/O（[[computer-systems/system-io]]）把每字符一次 `write` 变成每 4 KiB 一次；`io_uring`（Linux，2019 年起）让程序把许多 I/O 请求放进一个共享内存环，一次调用全部提交，或者——若有一个内核线程轮询该环——连一次调用都不用。

::: proposition 摊薄边界代价 {#prop-amortise}
设每次系统调用的代价是固定的 $c$ 加每件工作 $d$，程序必须处理 $N$ 件工作。若每次调用处理 $k$ 件，总时间为

$$
T(k) = \left\lceil \frac{N}{k} \right\rceil c + N d ,
$$ {#eq-amortise}

于是每件工作的边界开销至多为 $c/k + c/N$，每次调用合并 $k$ 件工作能把每件工作的开销降低近 $k$ 倍，直到它小到可以和 $d$ 相比。
:::

::: proof
把 $N$ 件工作每 $k$ 件一批来处理需要 $\lceil N/k\rceil$ 次调用，每次付一次 $c$；每件工作恰好付一次 $d$，与 $k$ 无关。除以 $N$ 并用 $\lceil N/k \rceil < N/k + 1$，即得每件工作的开销小于 $c/k + c/N$。
:::

::: widget plot
f: c/x + d
x: 1, 256
y: 0, 500
sliders: c=480:50:1000:10; d=2:0:20:1
labels: \text{每项时间（ns）}
points: 1,482; 16,32; 64,9.5; 256,3.9
caption: 每件工作的时间 $c/k + d$：$k$ 件工作合摊一次固定代价为 $c$ ns 的系统调用（这里取 $480$ ns，即实测的 `getppid` 代价），每件工作还有 $d$ ns 的实际工作。注意曲线平得有多快：到 $k = 64$，边界开销每件工作已不足 $8$ ns，此后只有 $d$ 重要。把 $d$ 调大以模拟昂贵的工作（一次磁盘写入），就会看到此时合并买不来多少东西，因为开销从来不是主要代价。
:::

::: example 数一数一个程序的系统调用 {#ex-strace-count}
一个空的 C 程序 `int main(void) { return 0; }`，分别以常规方式和 `-static` 编译，在 `strace` 下运行。它们各发起多少次系统调用？这些调用从何而来？
::: solution
```console
$ gcc -std=c17 -Wall -Wextra -O2 -o nothing nothing.c
$ gcc -std=c17 -Wall -Wextra -O2 -static -o nothing-static nothing.c
$ strace -c ./nothing 2>&1 | tail -1
100.00    0.000000           0        30         1 total
$ strace ./nothing-static 2>&1 | grep -c '('
15
```
动态链接的程序发起 $30$ 次调用（其中一次 `access("/etc/ld.so.preload")` 以 `ENOENT` 失败，即错误列中的那个 "1"）。十四次是 [[computer-systems/linking-loading]] 的动态链接器在干活：它打开 `/etc/ld.so.cache` 和 `libc.so.6`，读 ELF 头，用 `mmap` 映射库的各段，并用 `mprotect` 把重定位后的数据设为只读。静态程序发起 $15$ 次：`execve`，C 库的启动（用 `brk` 建立堆，`arch_prctl` 设置线程局部存储寄存器 `%fs`，为线程设置的 `set_tid_address`、`set_robust_list` 和 `rseq`，用 `prlimit64` 读栈限制，用 `getrandom` 取栈保护金丝雀和指针扰乱所需的随机数，对 `/proc/self/exe` 的 `readlinkat`），最后一次 `mprotect`，然后 `exit_group`。我们的 `main` 一次都没有。任何程序无论多么简单，在第一行代码运行之前都依赖十来个内核服务。
:::
:::

## 内核的组织方式

Linux 内核源码有超过 3500 万行（截至 2026 年），其中大多是设备驱动程序。如此庞大的一段特权代码应该如何组织？答案不止一个，真实系统往往混用。

::: definition 内核架构 {#def-kernel-arch}
- **单体内核**把全部操作系统服务——调度、内存管理、文件系统、网络协议、设备驱动——都放在内核态的同一个地址空间里，彼此以普通函数调用。例子：Unix、Linux、各 BSD。
- **分层**系统把内核安排成一个层级的层次，每层只使用它下面各层的服务。例子：迪杰斯特拉（Dijkstra）的 THE 系统（1968）。
- **微内核**在内核态只保留必须特权的最小部分——地址空间、线程与调度，以及**进程间通信**（IPC）——把文件系统、驱动和网络协议栈作为用户态**服务器**运行，以消息通信。例子：Mach、L4 与 seL4、QNX、MINIX 3。
- **混合内核**按微内核设计组织，但为了速度把多数服务器放在内核态运行。例子：Windows NT 及其后继者、苹果的 XNU（Mach 加 BSD）。
:::

**单体内核**很快：读一个文件就是一次系统调用、经文件系统到块层再到驱动的几次函数调用、然后返回。它的弱点是每一行代码都拥有完全特权。一个不起眼的 USB 驱动里的缺陷就能破坏调度器的数据，而它的一个安全漏洞会把整台机器交给攻击者。单体不等于无模块化：Linux 在运行时把大多数驱动作为**可装载内核模块**载入（`/proc/modules` 在测试机上列出 138 个），它的内部接口——虚拟文件系统、块层、网络设备接口——是小心分层的。但模块一旦装载就是内核的一部分，毫无隔离可言。

**分层**是最古老的纪律，使系统更容易推理：迪杰斯特拉的小组把 THE 建在六个层上（处理器分配与中断在层 0，内存段在层 1，操作员控制台在层 2，I/O 缓冲在层 3，用户程序在层 4，操作员在层 5），每一层测试彻底之后才在其上建造。不过严格的分层难以维持。真实的依赖不是线性的——内存管理器要做 I/O 以换页，I/O 系统需要内存作缓冲——而且每跨一层都增加开销。

**微内核**下的是反向赌注：把一切不必特权的都搬出内核。文件系统变成一个服务器进程；程序读文件就给它发一条消息；它再给磁盘驱动服务器发一条消息；回答沿原路返回。崩溃的驱动只是一个崩溃的进程，可以被重启（MINIX 3 自动重启它），而特权代码小到足以审查——甚至证明正确：2009 年 seL4 团队发表了一个机器检验过的证明，证明他们约 8700 行 C 实现了其形式化规约。代价是 IPC。每一项原本是函数调用的服务都变成一对消息，每条都要陷入内核、切换地址空间再返回出去。

::: example 消息的代价 {#ex-microkernel}
一个程序读文件的一个块。在单体内核里，这只是一次系统调用，边界开销（进入、退出和分派）$0.5$ µs 加上工作本身。在微内核里，请求从程序到文件系统服务器，从文件系统服务器到磁盘驱动服务器，回答沿原路返回。每条单向 IPC 消息花 $1$ µs（它陷入内核、切换地址空间、再返回到接收者）。两种设计下每次读的边界开销各是多少？若工作本身（在缓存里找到该块并复制 4 KiB）要 $2$ µs，每次读各慢多少倍？
::: solution
微内核需要四条消息：程序 → 文件系统，文件系统 → 驱动，驱动 → 文件系统，文件系统 → 程序。边界开销 $4 \times 1 = 4$ µs，对 $0.5$ µs。每次读的总时间：单体 $2 + 0.5 = 2.5$ µs，微内核 $2 + 4 = 6$ µs，相差 $6 / 2.5 = 2.4$ 倍。若块已经在文件系统服务器内部的缓存里，就不必惊动驱动，两条消息就够，倍数为 $(2 + 2)/2.5 = 1.6$；若这次读必须下到一块要花 $80$ µs 的 SSD，倍数只有 $(80 + 6)/(80 + 2.5) \approx 1.04$。这个教训与 [[#prop-amortise]] 吻合：消息开销的重要性，与它所包裹的工作有多便宜成正比。第一代微内核如 Mach（1986）在当时的硬件上 IPC 代价达几十微秒，文件系统繁重的负载受害严重；Jochen Liedtke 的 L4（1993）表明，围绕 IPC 设计的内核能把它加快二十倍，现代 L4 家族内核发一条短消息只要几百个周期。
:::
:::

还有更激进的设计。**外内核**（exokernel，MIT，1995）安全地复用硬件，却不提供任何抽象，把抽象留给链接进每个应用的库。**unikernel** 把一个应用连同它刚好需要的库操作系统组件编译成单一镜像，在虚拟机里的内核态运行，把隔离交给虚拟机监控器（[[operating-systems/virtualisation]]）。而 Linux 的 **eBPF** 允许用户程序把小程序装载进内核——用于跟踪、分组过滤和安全策略——前提是先由一个**验证器**证明它们会停机、且只访问被允许的内存：这是在不信任扩展的前提下扩展一个单体内核的办法。

::: warning "内核是一个一直在运行的进程"
人们很想把内核想象成一个守在用户进程旁边、监视它们的主管进程。它不是。那个意义上的内核没有自己的控制流：它*在……的上下文中*运行——哪个进程经系统调用或故障陷入内核、或被中断打断，它就在哪个进程的上下文中、在那个进程的内核栈上运行——然后返回用户态（上下文切换之后可能是另一个进程）。没有程序在运行时，核心执行内核的空闲循环，该循环停机直到下一个中断。Linux 确实有**内核线程**（`kworker`、`ksoftirqd`、`kswapd`），它们像进程一样被调度，但它们是内核为推迟的工作创建的帮手，不是内核本身。把这一点弄清楚，就能解释为什么系统调用可以阻塞：*调用进程*睡在内核里，调度器让别人运行。
:::

## 从加电到第一个进程

内核是一个程序，所以必须有别的东西装载它。启动计算机是一条装载程序能力递增的链，每一环刚好足够聪明去找到并启动下一环——**自举**（bootstrapping），这个名字来自"拽着自己的鞋带把自己提起来"这一不可能的事。

::: algorithm 启动一台 PC {#alg-boot}
1. **复位。** 处理器从一个固定的地址开始执行，该地址映射到主板上的闪存；此时它处于最高特权模式，MMU 关闭。
2. **固件**（当代 PC 上的 UEFI，老机器上的 BIOS）初始化内存控制器、枚举设备、执行加电自检，并在启用**安全启动**时检查下一阶段的签名。它在磁盘的 EFI 系统分区（一个 FAT 文件系统）上找到引导装载程序并运行它。
3. **引导装载程序**（GRUB、systemd-boot 或内核自带的 EFI 存根）把内核映像和一个**初始内存文件系统**（initramfs）载入内存，传入内核命令行和一份内存描述，然后跳到内核。
4. **内核**建立自己的页表并开启分页，安装异常表，初始化内存管理、调度器、中断和定时器，启动其他核心，探测驱动程序，并把 initramfs 解开为一个临时根文件系统。
5. 内核运行 initramfs 里的 `/init`，创建第一个用户进程，即 **PID 1**。这个程序装载通往真正根文件系统所需的模块（RAID、加密、网络存储），挂载它，并执行真正的 `init`——多数 Linux 发行版上是 **systemd**——它继续保持 PID 1。
6. `init` 按依赖顺序启动系统服务，最后是登录提示符或图形会话。其他每个进程都是 PID 1 的后代，由 `fork` 和 `execve` 创建。
:::

每一环都相信前一环正确地装载了自己，因此整个系统的安全不可能好于最早的一环：安全启动把一条**信任链**从固件中保存的密钥出发，经过签名的引导装载程序，延伸到签名的内核和（可选的）签名的模块。

第 6 步本身就是一个调度问题。服务声明依赖——网络服务需要设备管理器；web 服务器需要网络和文件系统——`init` 必须等每个服务所依赖的一切就绪之后再启动它。依赖构成一个有向无环图，它的任何一个**拓扑序**都是合法的启动顺序；systemd 并行启动相互独立的服务，这就是它比传统 Unix `init` 严格串行的脚本启动更快的原因。

::: widget graph
nodes: firmware@0,1; loader@1,1; kernel@2,1; init@3,1; udev@4,2; mount@4,0; network@5,2; journal@4,1; sshd@6,2; web@6,1; login@6,0
edges: firmware>loader; loader>kernel; kernel>init; init>udev; init>mount; init>journal; udev>network; mount>network; network>sshd; network>web; journal>web; mount>login; journal>login
algorithm: topo
caption: 简化的启动依赖图：固件、引导装载程序和内核严格按顺序运行，之后 `init`（PID 1）在各服务依赖就绪后启动它们。逐步执行拓扑排序，得到一种合法的启动顺序。注意 `udev`、`mount` 和 `journal` 互不依赖，可以并行启动；拖动顶点可以看到各层。加一条边 `web>mount` 制造一个环，就不存在任何顺序了——systemd 会把这种配置错误报告为 "ordering cycle"，并通过跳过一个单元来解开它。
:::

测试机是虚拟化宿主机上的一个容器，它的 PID 1 确实是 `systemd`：

```console
$ ps -p 1 -o comm=
systemd
```

::: example 跟踪从复位到 shell 提示符 {#ex-boot-trace}
在一台带 UEFI 的 Linux PC 上，按顺序列出从按下电源键到用户经文本控制台登录后 shell 打印第一个提示符之间，引导核心上运行过的每一个特权级别和每一个程序。其中哪些运行在内核态？
::: solution
(1) UEFI 固件，处于处理器的最高特权状态（x86 上是环 0，另有系统管理模式代码，比内核的特权还高）。(2) 引导装载程序，仍在固件上下文中，拥有完全特权。(3) 内核的初始化代码，环 0；它开启分页并安装异常处理程序。(4) 来自 initramfs 的第一个用户态（环 3）程序，即 PID 1。(5) 真正的 `init`，即 systemd——PID 1 用 `execve` 换入的镜像——仍然是 PID 1，环 3。(6) systemd 派生的服务进程，环 3，包括控制台上的 `getty`。(7) `getty` 执行 `login`，后者核验口令，`login` 再执行用户的 shell，shell 打印提示符——全部环 3。第 4–7 步期间，内核只在这些程序发起系统调用、引发故障或被中断时才运行。只有第 1–3 步以内核态作为控制流主线；第 3 步之后不存在"内核进程"，只有经异常进入的内核代码（见上文的那条警告）。
:::
:::

## 实践中

截至 2026 年，广泛使用的通用内核不是单体式就是混合式：Linux（服务器、Android 手机和大多数嵌入式设备）、Windows NT（混合式）、苹果的 XNU（混合式，macOS 与 iOS）。微内核占主导的场合是可靠性与认证比峰值吞吐更重要：QNX 在汽车和工业控制器中，L4 家族在 modem 基带处理器和安全隔离区中，seL4 在高保障系统中。这些思想也在回流：Linux 把一些驱动放在用户空间运行（通过 `vfio` 和 FUSE 文件系统），Windows 与 macOS 都把一类类驱动搬出内核，以限制它们故障的后果。

2018 年以来，由于推测执行漏洞及其缓解措施，跨边界的代价上升了；这也是 `io_uring` 与 vDSO 这类新接口力求少跨界的原因之一。没有唯一最好的架构——只有速度、隔离、以及必须信任的代码量这三者之间取舍的不同立场。

::: history
最早的操作系统是**批量监控程序**（通用汽车与北美航空为 IBM 704 开发的系统，1956），它们从磁带上一个作业接一个作业地装载。曼彻斯特大学的 Atlas 计算机（1962）有一个带"扩展指令"（extracodes）的"监督程序"——系统调用的前身——以及中断。费尔南多·科尔巴托（Fernando Corbató）在 MIT 的小组于 1961 年演示了**兼容分时系统**（CTSS）并于 1962 年发表：多个用户经终端通过时间片共享一台 IBM 709，这是第一个交互式分时系统，它恰好需要 [[#prop-protection]] 所要求的那些保护硬件（一台经过改装的 IBM 7090 提供内存保护和一个时钟）。**Multics**（MIT、贝尔实验室与通用电气，1965 年的一组论文）引入了分层的保护环，1973 年在 Honeywell 6180 上以硬件实现。埃德斯加·迪杰斯特拉（Edsger Dijkstra）1968 年关于 **THE 多道程序系统**的论文引入了分层结构（以及信号量，我们将在 [[operating-systems/synchronisation]] 遇到）；Per Brinch Hansen 的 RC 4000 "核"（1970）是早期的微内核。肯·汤普森（Ken Thompson）与丹尼斯·里奇（Dennis Ritchie）的 **Unix**（1969，1974 年发表于《ACM 通讯》）表明，一个用高级语言写成的小型单体内核可以在不同机器之间移植。Mach（卡内基梅隆大学，1986）使微内核流行起来；Jochen Liedtke 的 L4（1993–95）使它快了起来；Gerwin Klein 等人验证了 seL4（2009）。林纳斯·托瓦兹（Linus Torvalds）在 1991 年公布了 Linux，而他 1992 年在新闻组上与安德鲁·塔能鲍姆（Andrew Tanenbaum）围绕 "Linux is obsolete" 的辩论，至今仍是关于内核架构最有名的一场争论。
:::

## 后续内容

本章之后的每一章都建立在这些机制之上。[[operating-systems/processes-scheduling]] 用定时器中断共享处理器；[[operating-systems/address-spaces-paging]] 用 MMU 给每个进程自己的内存；[[operating-systems/storage-io]] 展示内核如何经中断和 DMA 与设备对话；[[operating-systems/virtualisation]] 在内核之下再加一个特权级别，把整个操作系统当作客户机来运行。保护边界、内核的攻击面与双重取数缺陷会重现于 [[security]]，并行系统中的内核—用户通信在 [[parallel-computing]]。

::: summary
- 操作系统是裁判、幻术师与粘合剂；它的**内核**是特权核心，只能经异常进入（[[#def-os]]）。把**机制**（如何做）与**策略**（选哪个）分开。
- 保护立足于硬件：**双模式运行**与特权指令（[[#def-dual-mode]]）、只有内核控制的 MMU、只有内核能重新编程的定时器。三者缺一不可（[[#prop-protection]]）；用户态执行特权指令会触发故障（`hlt` → `SIGSEGV`）。
- **系统调用接口**是内核的全部 API（[[#def-syscall-interface]]）。内核必须校验每个实参并恰好复制一次（`copy_from_user`；双重取数是 TOCTOU 缺陷）。
- 一次系统调用要几百纳秒（实测约 480 ns，而函数调用 2 ns）；vDSO、缓冲与 `io_uring` 减少跨界，每次调用合并 $k$ 件工作能把开销降低约 $k$ 倍（[[#prop-amortise]]）。
- 内核可以是**单体式**（快，全部代码可信）、**分层式**、**微内核**（可信核心小，服务器在用户态，IPC 开销）或**混合式**；取舍在于速度对隔离、以及对被信任代码的规模（[[#ex-microkernel]]）。
- 启动是一条链：固件 → 引导装载程序 → 内核 → PID 1（`init`），后者按依赖的拓扑序启动服务（[[#alg-boot]]）。
:::

## 习题

::: exercise 特权与否 {level=1}
对每个操作，说明它是否必须特权，以及它属于 [[#prop-protection]] 的哪一条要求（若有）：(a) 写定时器的控制寄存器；(b) 两个寄存器相加；(c) 写存放系统调用入口地址的寄存器（x86-64 上的 `IA32_LSTAR`，用 `wrmsr` 写）；(d) 执行 `int3`，即断点陷入；(e) 用 `in` 读一个连着磁盘控制器的 I/O 端口。
::: solution
(a) 特权——要求 (c)：能给定时器重新编程的程序就能让它停下来。(b) 非特权：只影响程序自己的寄存器。(c) 特权——要求 (a)：谁选定入口地址，谁就选定了 `syscall` 之后在内核态运行什么代码；`wrmsr` 是特权指令。(d) 非特权：与 `syscall` 一样，它是向内核选定的处理程序（调试器接口）的陷入，不能给程序特权。(e) 特权：直接访问设备会让程序读或改写任意磁盘块，绕过文件系统的权限检查——按原文陈述它不在三条要求之列，但论证与 (b) 之于设备相同；x86 使 `in` 与 `out` 成为特权指令，除非内核把特定端口授予某个程序。
:::
:::

::: exercise 百万次系统调用的代价 {level=1 check="0.48"}
一个程序每写一个字节就调用一次 `write`，共写出一百万个字节。取一次系统调用 $480$ ns，忽略写每个字节本身的工作，单是边界开销要花多少秒？（输入秒数。）
::: solution
$10^6 \times 480 \text{ ns} = 4.8 \times 10^8 \text{ ns} = 0.48$ 秒。改用 C 库 4 KiB 的缓冲后，同样的输出需要 $\lceil 10^6 / 4096\rceil = 245$ 次调用，约 $0.12$ ms 的开销——即 [[computer-systems/system-io]] 中见到的那 245 次 `write`。
:::
:::

::: exercise 静态与动态启动 {level=1 check="15"}
利用 [[#ex-strace-count]]：动态链接的空程序比静态的多发起多少次系统调用？说出其中三次额外调用的名字及各自的用途。（输入差值。）
::: solution
$30 - 15 = 15$。多出的调用是动态链接器的：`access("/etc/ld.so.preload")`（查看是否有需要预装载的库；以 `ENOENT` 失败）、对 `/etc/ld.so.cache` 与 `libc.so.6` 的 `openat`（找到并打开库）、`read` 与 `pread64`（读 ELF 头和程序头表）、`fstat`（获知文件大小）、五次 `mmap`（映射库的代码、只读数据和可写数据，以及给未初始化数据清零的内存）、`close`、进一步的 `mprotect`（在重定位之后把重定位过的数据设为只读，即 RELRO），以及对缓存文件的 `munmap`。每次都是一次约半微秒的跨界，所以启动开销以微秒计——对长程序可忽略，对被重复启动百万次的极短程序则很可观。
:::
:::

::: exercise 微内核的盈亏平衡点 {level=2 check="3"}
在 [[#ex-microkernel]] 的设定下，经微内核的一次读需要四条各 $1$ µs 的单向消息，而单体系统的系统调用有 $0.5$ µs 的开销。每次读的工作量 $w$（以 µs 计）为多少时，微内核恰好慢一倍？$w$ 为多少时它慢不到 $10\%$？（第一问输入 $w$，以微秒计。）
::: solution
解 $(w + 4)/(w + 0.5) = 2$：$w + 4 = 2w + 1$，故 $w = 3$ µs。验算：$7/3.5 = 2$。要慢不到 $10\%$：$(w + 4)/(w + 0.5) < 1.1$ 即 $w + 4 < 1.1w + 0.55$，亦即 $0.1w > 3.45$，$w > 34.5$ µs。真正要干几十微秒活的请求——任何下到 SSD 的请求——几乎完全藏起了消息开销；几微秒内由缓存服务的请求则藏不住。
:::
:::

::: exercise 用一条指令打破保护 {level=2}
一位处理器设计师提议把写异常表基址寄存器的指令（x86 上的 `lidt`）设为非特权，"因为程序可能想自己处理自己的除法错误"。证明这样一个用户程序随后就能获得对整台机器的完全控制。有什么安全的替代方案已经提供了设计师想要的东西？
::: solution
程序在自己的内存里构造一张异常表，其中某个异常——比如除法错误，或定时器中断——的表项指向它自己的代码，然后用 `lidt` 装载其地址。接着它除以零（或等下一个定时器滴答）。处理器经由这张新表递送异常，从而*进入内核态*，跳到该程序的代码。这段代码从此拥有完全特权：它可以装载 `%cr3`、屏蔽中断、覆写内核。这违反了 [[#prop-protection]] 的要求 (a)——在内核未选定的地址进入内核态。（实践中，处理器还要能访问程序里存放处理程序的那个页，除非启用 SMEP，默认内核态就能访问它；这救不了这个设计，因为控制了 `lidt` 之后，程序也能把表指向已存在的内核代码片段。）安全的替代方案是**信号**：内核自己处理该异常，并且若程序已用 `sigaction` 提出请求，就向一个在*用户*态运行的处理程序递送 `SIGFPE`（[[computer-systems/exceptions-processes]]）。
:::
:::

::: exercise 自己动手写 getpid {level=2}
以 `raw_write` 为样板，写一个 `long raw_getpid(void)`，直接发起 39 号系统调用（x86-64 的 `getpid`），并验证它与库的 `getpid()` 一致。
::: solution
```c
#define _POSIX_C_SOURCE 200809L
#include <stdio.h>
#include <unistd.h>

static long raw_getpid(void) {
    long ret;
    __asm__ volatile ("syscall"
                      : "=a"(ret)
                      : "a"(39L)                  /* x86-64 上的 __NR_getpid */
                      : "rcx", "r11", "memory");
    return ret;
}

int main(void) {
    long a = raw_getpid(), b = getpid();
    printf("raw %ld, libc %ld\n", a, b);
    return a != b;
}
```
```console
$ gcc -std=c17 -Wall -Wextra -O2 -o rawpid rawpid.c && ./rawpid
raw 3430123, libc 3430123
```
（号码每次运行都不同。）不需要实参，所以只有 `%rax` 是输入；破坏列表与之前相同。系统调用号在不同体系结构之间不同——64 位 ARM 上 `getpid` 是 172 号——这也是真实代码里应当使用库包装函数或 `syscall(SYS_getpid)` 的原因之一。
:::
:::

::: exercise 用 io_uring 合并提交 {level=3 check="16"}
一个服务器处理小请求。每个请求需要一个 I/O 操作，其真正工作花 $d = 30$ ns 的内核时间，而每次系统调用有 $c = 480$ ns 的固定代价。每次操作一次系统调用时，每次操作的代价是 $c + d$。用 [[#eq-amortise]]（忽略上取整），每次调用必须提交多少个操作 $k$，才能使每次操作的时间 $c/k + d$ 等于 $60$ ns？与 $k = 1$ 相比，这把每次操作的时间降为几分之一？（输入 $k$。）
::: solution
需要 $480/k + 30 = 60$，所以 $480/k = 30$，$k = 16$。于是每次操作只花 $60$ ns 而不是 $480 + 30 = 510$ ns，相差 $510/60 = 8.5$ 倍。把 $k$ 再翻倍到 $32$ 只降到 $45$ ns，仅再改善 $25\%$：一旦 $c/k$ 与 $d$ 相当，合并就已基本做完它能做的事，[[#prop-amortise]] 之后的那张图说明了这一点。（真实的 `io_uring` 提交还有每次操作的额外代价，所以这是一个模型，不是预言。）
:::
:::

::: exercise 一个双重取数缺陷 {level=3}
一个玩具内核实现了系统调用 `set_name(struct req *u)`，其中 `struct req { size_t len; char name[]; }` 位于用户内存。处理程序这样做：(1) `if (u->len > 64) return -EINVAL;`；(2) `memcpy(kbuf, u->name, u->len);` 复制到 64 字节的内核缓冲区 `kbuf`，且再次从用户内存读 `u->len`。描述一种与第二个用户线程的交错，使内核溢出 `kbuf`，并正确地改写处理程序。第 (1) 步的检查为什么起不到保护作用？
::: solution
线程 A 以 `len = 10` 调用 `set_name`。内核在第 (1) 步读 `u->len`，看到 $10 \le 64$，通过检查。第 (2) 步之前，在另一个核心上运行、共享同一地址空间的线程 B 写入 `u->len = 4096`。第 (2) 步内核再次读 `u->len`，把 4096 字节复制进 64 字节的缓冲区，覆写紧随其后的内核数据。那次检查之所以不保护，是因为它检验的值与使用的值*不是同一个*：用户内存在两次读之间随时可能改变，所以从用户内存读两次的值是两个值。正确版本：把请求头恰好复制一次到内核内存，检查副本，之后只用副本（一段内核 C，使用 Linux 的 `copy_from_user`，不是独立程序）：

```text
size_t len;
if (copy_from_user(&len, &u->len, sizeof len)) return -EFAULT;  /* 只取一次 */
if (len > sizeof kbuf) return -EINVAL;                          /* 检查副本 */
if (copy_from_user(kbuf, u->name, len)) return -EFAULT;         /* 使用副本 */
```

`copy_from_user` 还检查源范围确实是用户内存，并把故障变成 `-EFAULT`。这是一个检查时刻与使用时刻不符的缺陷；查找同一用户地址两次取数的静态分析器在生产内核中找到过真实的实例。
:::
