本课程用的测试机并不完全是一台机器。问它：

```console
$ systemd-detect-virt
lxc
$ uname -r
7.0.14-8-pve
```

它是一个**容器**——一组被隔离的进程，有自己的文件系统、进程树、网络接口和主机名——跑在一台 Proxmox 宿主上，与宿主共享内核（版本串里的 `pve` 就是 Proxmox 内核的标记）。同一块硬件上还跑着别的容器和完整的**虚拟机**，各自有自己的内核，各自以为独占一台计算机。在云数据中心这是常态：一台物理服务器跑着属于不同客户的几十台虚拟机，每台里面往往又有几十个容器。

本章把整门课程的主题——虚拟化——再往下推进一层。进程为*程序*虚拟化了处理器和内存（[[operating-systems/processes-scheduling]]、[[operating-systems/address-spaces-paging]]）；**虚拟机监控器**（hypervisor）则为一个*操作系统*虚拟化了整台机器。我们要问一台机器必须提供什么才使这一点成为可能——Popek–Goldberg 定理，以及 x86 直到 2005 年为何不满足它——并考察虚拟化处理器（陷入并模拟、二进制翻译、半虚拟化、硬件支持）、内存（影子页表与嵌套页表）和设备所使用的各项技术。然后转向**容器**：它虚拟化的不是机器，而是操作系统的*命名空间*，我们还要亲手搭一个。最后比较每种隔离各自防得住与防不住什么。

## 虚拟机与虚拟机监控器

::: definition 虚拟机与虚拟机监控器 {#def-vm}
**虚拟机**（VM）是一台真实机器的高效、隔离的复制品，由**虚拟机监控器**（hypervisor）或**虚拟机监视器**（VMM）创建。按照 Popek 与 Goldberg（1974）的说法，VMM 必须提供：

1. **等价性**（fidelity）：程序在虚拟机中的行为与在真实机器上一致，时间以及可用资源的数量除外；
2. **资源控制**（safety）：VMM 完全控制真实资源；客户机不能使用或影响任何 VMM 没有分配给它的东西；
3. **效率**：客户机的绝大多数指令直接在真实处理器上执行，无需 VMM 干预。

运行在虚拟机里的操作系统是**客户机**（guest）；运行 VMM 的机器与软件是**宿主**（host）。
:::

**1 型**（裸金属）虚拟机监控器直接运行在硬件上：Xen、VMware ESXi、Microsoft Hyper-V。**2 型**（宿主型）虚拟机监控器作为传统操作系统的一部分或在其之上运行：VirtualBox、VMware Workstation、QEMU。Linux 的 **KVM** 模糊了这条界线——一个内核模块，把 Linux 自己变成虚拟机监控器，每台虚拟机是一个普通进程（通常是 QEMU），它的线程就是虚拟 CPU，由普通的 Linux 调度器调度。

效率排除了显而易见的做法——**仿真**——用软件解释执行每条客户机指令，就像 QEMU 在 x86 宿主上运行 ARM 客户机时所做的那样——它比原生执行慢几十倍。客户机必须直接在处理器上运行。但客户机内核期望在核心态运行，执行特权指令、控制页表，而 VMM 不能答应这一点，否则就失去了资源控制。经典的解法是**陷入并模拟**（trap-and-emulate）：把客户机内核跑在*用户*态（去权），使它执行的每条特权指令都陷入 VMM，VMM 再模拟该指令对*虚拟*机器状态的影响。

::: widget graph
nodes: app@0,3; guestK@1,2; vmx@2,1; kvm@3,0; hw@4,1; qemu@4,2
edges: app>guestK; guestK>vmx; vmx>kvm; kvm>vmx; kvm>qemu; qemu>kvm; kvm>hw
algorithm: bfs
start: app
caption: KVM 虚拟机中的控制权归属。客户机应用（`app`）向客户机内核（`guestK`）发起系统调用，与真实硬件上完全一样，不经过虚拟机监控器；两者都以 VMX 非根模式（`vmx`）直接在处理器上运行。只有配置过的事件才会**VM 退出**到宿主内核里的 KVM，KVM 自己处理大部分再经一次 VM 进入返回；它处理不了的设备访问上行到宿主用户态的 QEMU 进程。从 `app` 起逐步执行广度优先搜索，注意退出路径上客户机与硬件隔着多少步——而常见的路径，从 `app` 到 `guestK`，根本不经过任何虚拟机监控器。
:::

### 陷入并模拟何时可行

要说出何时可行，按指令与机器控制状态（运行模式、内存映射、定时器、I/O 设备）的关系对指令分类。

::: definition 特权指令与敏感指令 {#def-sensitive}
一条指令若在用户态执行时陷入、在核心态执行时不陷入，则称它是**特权**的。若它或是*控制敏感*的——能改变控制状态（处理器运行模式、内存映射、中断状态、设备配置）——或是*行为敏感*的——其效果依赖控制状态，例如依赖当前运行模式或它在物理内存中运行的位置——则称它是**敏感**的。不敏感的指令是**无害**的。
:::

::: theorem Popek–Goldberg 虚拟化定理 {#thm-popek}
对一台具有核心态与用户态、采用基于重定位的内存保护的传统处理器，若敏感指令集是特权指令集的子集，就能造出满足等价性、资源控制与效率的虚拟机监控器。
:::

::: proof
（概要，沿 Popek 与 Goldberg 的论证。）VMM 把客户机——内核代码和用户代码一视同仁——跑在用户态，内存重定位到客户机只见得到自己的区域，并保存一份客户机*虚拟*控制状态的副本（它的虚拟运行模式、虚拟映射寄存器、虚拟中断标志）。无害指令直接在硬件上运行：按定义它们既不改变也不依赖控制状态，所以在用户态带重定位地执行它们，恰与它们在拥有一份客户机虚拟状态的真实机器上的效果一致——这给出效率，以及这些指令的等价性。每条敏感指令按假设都是特权指令，于是在用户态陷入 VMM。VMM 的处理程序（称为*解释器*例程）计算该指令在拥有一份客户机虚拟状态的真实机器上本应产生的效果，把它应用到虚拟状态上（并在 VMM 的分配允许处应用到真实状态——例如，安装一个把客户机的映射与 VMM 自己的映射结合起来的页表基址），然后在该指令之后恢复客户机执行。于是每条指令的行为都与一台带虚拟状态的真实机器上一致（等价性），而每次改变真实控制状态的企图都经过 VMM，客户机只能控制 VMM 授予它的东西（资源控制）。
:::

这个条件不难陈述，却被 1990 年代最重要的处理器违反了。32 位 x86 有十七条敏感但不特权的指令（Robin 与 Irvine 在 2000 年数出来的）。最出名的是 `popf`，它从栈上装载标志寄存器。在核心态它能改变中断允许标志 IF；在用户态同一条指令*悄悄忽略*对 IF 的改动——它是行为敏感的，却不陷入。

::: example 一条不陷入的敏感指令 {#ex-popf}
证明 `popfq` 在用户态不能关中断，而且它也不产生异常。

```c
#include <stdio.h>

static unsigned long get_flags(void) {
    unsigned long f;
    __asm__ volatile ("pushfq; popq %0" : "=r"(f));
    return f;
}

static void set_flags(unsigned long f) {
    __asm__ volatile ("pushq %0; popfq" : : "r"(f) : "cc", "memory");
}

int main(void) {
    const unsigned long IF = 1UL << 9;            /* 中断允许标志 */
    unsigned long before = get_flags();
    set_flags(before & ~IF);                      /* 试图关中断 */
    unsigned long after = get_flags();
    printf("IF before: %lu, after popf with IF cleared: %lu\n",
           (before & IF) >> 9, (after & IF) >> 9);
    return 0;
}
```
::: solution
```console
$ gcc -std=c17 -Wall -Wextra -O2 -o popf popf.c && ./popf
IF before: 1, after popf with IF cleared: 1
$ strace ./popf 2>&1 | tail -2
exit_group(0)                           = ?
+++ exited with 0 +++
```
IF 仍为 $1$：请求被忽略，而 `strace` 没有显示任何信号——处理器没有产生异常。对普通程序这是正确的行为（[[operating-systems/os-structure#prop-protection]] 要求用户代码不能关中断）。对 VMM 却是致命的：一个被去权的客户机内核执行 `popf` 想在临界区周围关中断，自认为做到了，但 VMM 毫不知情，可能把一个虚拟中断投递到临界区的正中间。陷入并模拟在这样的处理器上无法工作，因为有些敏感指令根本到不了 VMM。
:::
:::

### 虚拟化 x86

人们找到了三种答案。

**二进制翻译。** VMware 的第一款产品（1999）直接运行客户机*用户*代码，但在执行客户机*内核*代码之前即时扫描它，以基本块为单位，把它翻译成安全的代码：无害指令原样拷贝，敏感指令替换为对 VMM 的调用，翻译结果缓存起来。内核代码大部分是无害的，所以预热之后开销不大。

**半虚拟化。** Xen（Barham 等，2003）改的是客户机：客户机内核被修改为显式调用虚拟机监控器——**超级调用**（hypercall）——而不是执行敏感指令，并在页表和设备上与其协作。半虚拟化很快，但需要修改过的客户机，这对 Linux 和 BSD 是可行的，对 Windows 在当时则不行。它的设备接口以 **virtio**（Rusty Russell，2008）的形式存活至今，成为 KVM 及其他虚拟机监控器标准的半虚拟网络与磁盘设备。

**硬件支持。** 2005–2006 年，Intel（VT-x）和 AMD（AMD-V）增加了特权的一整维。有了 VT-x，处理器处于 **VMX 根模式**（虚拟机监控器）或 **VMX 非根模式**（客户机），且各有通常的环 $0$–$3$，所以客户机内核未经修改地运行在非根模式的环 $0$。每个虚拟 CPU 一份的**虚拟机控制结构**（VMCS）告诉处理器哪些事件和指令会引起一次 **VM 退出**到虚拟机监控器——`cpuid`、对控制寄存器的访问、I/O 指令、外部中断，还有许多可配置的其它事件——并保存客户机的状态，处理器在每次退出和每次 **VM 进入**时保存并恢复它。实际上，硬件让所有敏感指令都陷入（陷到虚拟机监控器，而不是客户机内核），恢复了 Popek–Goldberg 条件。测试机的处理器在 `/proc/cpuinfo` 中列有 `vmx`（VT-x）、`ept` 和 `vpid`。

VM 退出不是免费的：处理器要保存并装载数百字节的状态，虚拟机监控器还必须解码并处理退出的原因。一个来回在硬件上花大约一千个时钟周期，加上处理——2026 年简单退出约一微秒。

::: proposition 退出的代价 {#prop-exits}
若一台客户机每秒引起 $n$ 次 VM 退出，每次花 $c$ 秒处理器时间来处理和返回，则一个虚拟 CPU 因虚拟化开销损失的份额是 $nc$，客户机以原生速度的 $1 - nc$ 运行（忽略高速缓存和 TLB 污染等间接影响），前提是 $nc < 1$。
:::

::: proof
每一秒内有 $nc$ 秒耗在退出上；其余时间直接执行客户机指令，由效率性质知其以原生速度运行。
:::

::: widget plot
f: 100*x*c/1000000
x: 0, 200000
y: 0, 50
sliders: c=1.5:0.5:10:0.5
labels: \text{开销（占一个 CPU 的百分比）}
points: 100000,15
caption: 以 CPU 百分比计的虚拟化开销 $100\,nc$，横轴是每秒 VM 退出次数 $n$，每次退出处理花 $c$ µs（来自 [[#prop-exits]]）。取 $1.5$ µs 时，每秒 $100{,}000$ 次退出——做小规模仿真 I/O 的客户机轻易就能达到——要损失 CPU 的 $15\%$；很少退出的计算密集客户机几乎什么都不损失。把 $c$ 调到 $10$ µs——必须上行到用户态设备模拟器的退出的典型值——直线就冲出图外：这就是半虚拟设备与直通设备重要的原因。
:::

## 虚拟化内存

客户机内核管理的页表把**客户机虚拟**地址映射到它自以为是物理地址的地方——**客户机物理**地址。这些地址并非真实：虚拟机监控器把客户机物理内存映射到**宿主机物理**内存，随它乐意放在哪里。于是客户的每次内存访问都需要两次转换。

在硬件支持出现之前，虚拟机监控器使用**影子页表**。对每张客户机页表，VMM 维护一张把客户机虚拟地址直接映射到宿主机物理地址的*影子*表，并让真正的 `%cr3` 指向影子表。为使影子表保持最新，VMM 把客户机自己的页表页写保护：客户机内核每次修改它的页表，这次写都陷入 VMM，VMM 把两张表一起更新。这对未经修改的客户机可行，但页表繁忙的负载——`fork`、进程创建、内存映射 I/O——会引发一阵陷入风暴。

2008 年起（AMD 的嵌套页表，随后 Intel 的**扩展页表**，EPT），硬件自己走完两级页表。客户机的 `%cr3` 指向以客户机物理地址解释的客户机页表；虚拟机监控器的 EPT 把客户机物理地址映射到宿主机物理地址。于是 TLB 缺失需要一次**二维遍历**：客户机页表的每个指针本身是客户机物理地址，必须先经 EPT 转换才能被读取。

::: theorem 嵌套遍历的代价 {#thm-nested}
对 $n$ 级客户机页表和 $m$ 级嵌套（EPT）表，且两者都不作缓存，一次客户机虚拟地址的 TLB 缺失需要 $nm + n + m = (n+1)(m+1) - 1$ 次访存才能得到宿主机物理地址。
:::

::: proof
客户机遍历读 $n$ 个表项。这些客户机页表页的地址都是客户机物理地址（第一个来自客户机的 `%cr3`，其余来自上一级表项），所以每次读之前都要做一次 $m$ 级 EPT 遍历来转换它：客户机遍历共 $n(m + 1)$ 次访存。客户机遍历结束时得到数据的客户机物理地址，还需要再一次 $m$ 次访存的 EPT 遍历。总计 $n(m+1) + m = (n+1)(m+1) - 1$。取 $n = m = 4$，这是 $24$，而非虚拟化时是 $4$（[[operating-systems/address-spaces-paging]] 嵌套转换习题的计算）。
:::

所以虚拟机里的 TLB 缺失可能多花六倍的访存，处理器用大 TLB、缓存中间表项、按虚拟机标记的 TLB 表项（Intel 的 **VPID**——测试机的 `vpid` 标志——这样在虚拟机之间切换不必冲刷 TLB）以及两级**大页**来弥补：用 1 GiB 的 EPT 页时，$m$ 实际上是 $2$，遍历的代价降到 $14$。

::: example 虚拟机中的有效访问时间 {#ex-nested-eat}
访存耗时 $100$ ns，TLB 命中率 $99\%$，TLB 缺失由不经缓存的遍历满足。用 [[operating-systems/address-spaces-paging#thm-eat]]（查表时间取 $0$）比较原生（四级页表）与虚拟机（客户机和 EPT 各四级）中的有效访问时间。
::: solution
原生下一次缺失花 $4$ 次访存：$\text{EAT} = 100 + 0.01 \times 4 \times 100 = 104$ ns。虚拟机里一次缺失花 $24$ 次（[[#thm-nested]]）：$\text{EAT} = 100 + 0.01 \times 24 \times 100 = 124$ ns，比原生慢约 $19\%$。客户机用大页时，TLB 的覆盖范围扩大 $512$ 倍，命中率随之上升；用 2 MiB 的 EPT 页时，即便缺失，嵌套遍历也缩短到 $n(m+1) + m = 4 \times 4 + 3 = 19$ 次访存。因此虚拟机里内存密集的负载通常都在宿主机上配置大页。
:::
:::

虚拟机监控器还可以**超额承诺**（overcommit）内存，向各虚拟机承诺的总量超过宿主机实际拥有的。它用**气球驱动程序**从客户机回收内存——一个装在客户机里的驱动程序，应虚拟机监控器的请求分配客户机内存并把页框交还出来，于是由客户机自己的页面置换策略（[[operating-systems/page-replacement]]）决定放弃什么——还能在虚拟机之间共享内容相同的页（VMware 的透明页共享；Linux 的 KSM，*内核页合并*），以写时复制方式映射它们。不同客户的虚拟机之间的页共享后来被发现会通过时序侧信道泄漏信息（对共享页的写很慢，因为它触发一次拷贝），VMware 于 2014 年默认关闭了跨虚拟机页共享。

### 设备

客户机看到的每个设备也是虚拟的。虚拟机监控器可以**仿真**一个真实设备——一块众所周知的网卡或磁盘控制器——靠陷入对其寄存器的每次访问，这对任何客户机都可行，但每次寄存器访问要花一次或多次 VM 退出。**半虚拟**设备（virtio）使用存放请求与完成情况的共享内存环，像 NVMe 的队列（[[operating-systems/storage-io]]），于是整批 I/O 只需一次通知。**设备直通**让虚拟机直接访问真实设备；IOMMU 把设备的 DMA 地址经该虚拟机的客户机物理映射转换，使设备只能到达该虚拟机的内存；**SR-IOV** 让一块物理网卡或 SSD 呈现多个相互独立的"虚拟功能"，一机一个。

关于硬件辅助虚拟化，哪些说法正确？

- [ ] 有了 VT-x，客户机内核执行的每条指令都引起一次 VM 退出。
- [x] 有了嵌套页表，客户机修改自己的页表不必引起 VM 退出。
- [x] 四级页表下，嵌套页表的 TLB 缺失至多花 $24$ 次访存。
::: solution
客户机内核运行在非根模式的环 $0$，几乎全部指令都直接执行；只有 VMCS 中配置的事件和指令才引起退出。嵌套页表让客户机完全拥有自己的页表（它们由 EPT 转换），免除了影子页表所需的陷入，代价是 [[#thm-nested]] 的二维遍历。
:::
:::

## 容器

虚拟机复制一整台计算机，连内核一起，还要引导它。很多时候需要的是更少的东西：在*同一个*内核上运行一个应用，带着它自己的库和配置，与其他应用相互隔离。这就是**容器**。

::: definition 容器 {#def-container}
**容器**是跑在宿主机内核上、由**命名空间**与其他进程隔离开——命名空间给它对所选内核资源的私有视图——并由**控制组**限制资源用量的一组进程；它通常有自己的根文件系统，由联合文件系统把只读镜像层组装而成。
:::

Linux 有八种命名空间（每个进程的命名空间列在 `/proc/self/ns` 里）：

| 命名空间 | 隔离的内容 | Linux 版本 |
|---|---|---|
| mount | 已挂载文件系统的树 | 2.4.19（2002） |
| UTS | 主机名与域名 | 2.6.19（2006） |
| IPC | System V IPC 对象、POSIX 消息队列 | 2.6.19（2006） |
| PID | 进程 ID：第一个进程是 PID 1 | 2.6.24（2008） |
| network | 接口、地址、路由表、端口、防火墙规则 | 2.6.29（2009） |
| user | 用户与组 ID：里面是 root，外面不是 | 3.8（2013） |
| cgroup | 对 cgroup 层次的视图 | 4.6（2016） |
| time | 启动时钟与单调时钟 | 5.6（2020） |

**用户命名空间**正是非特权容器成为可能的原因：一个进程可以创建一个并在其中成为 `root`——对该命名空间拥有的资源有全部特权，在外面则一点也没有。有了它，普通用户就能创建其余的命名空间。

::: example 用命令行使用命名空间 {#ex-unshare}
在测试机上以非特权用户身份，用 `unshare` 命令给一个 shell 它自己的主机名、自己的（空的）网络和自己的进程 ID 空间，并从里面和外面各自检查每一样都是分开的。
::: solution

```console
$ unshare -Ur --uts sh -c 'hostname sandbox; hostname'; hostname
sandbox
f
$ unshare -Urn ip -br link
lo               DOWN           00:00:00:00:00:00 <LOOPBACK>
$ unshare -Ur --pid --fork sh -c 'echo "my PID inside: $$"; readlink /proc/self/ns/pid'
my PID inside: 1
pid:[4026534969]
$ readlink /proc/self/ns/pid
pid:[4026535092]
```

第一条命令在新的 UTS 命名空间里改了主机名；在外面，主机名仍是 `f`。第二条创建了一个网络命名空间，里面只有一个环回接口，而且是关着的：在有人把虚拟接口接上去之前根本没有网络。第三条创建了一个 PID 命名空间，其中 shell 是 $1$ 号进程——它那棵小进程树的 `init`——并且里面和外面的命名空间标识符不同。（`-U -r` 创建一个用户命名空间并把调用者映射为其中的 root。）
:::
:::

**控制组**（cgroups，Linux 4.5 起为 version 2，2016）把进程组织成一棵层次树 `/sys/fs/cgroup`，并对每个组施加**控制器**：`cpu`（像 nice 值一样的权重，外加硬性配额）、`memory`（限额，[[operating-systems/page-replacement]] 的 OOM killer 在组内起作用）、`io`（按设备的带宽与权重）、`pids`（进程数上限，可阻止 fork 炸弹）。在测试机上，systemd 可以为一条命令创建一个组并把它限制在四分之一个 CPU——每 $100$ ms 周期内 $25$ ms 的 CPU 时间配额：

```console
$ systemd-run --user --scope -q -p CPUQuota=25% sh -c \
    'cat /sys/fs/cgroup$(cut -d: -f3 /proc/self/cgroup)/cpu.max; ./spin capped'
25000 100000
capped: 0.69 s of CPU in 3 s
```

`spin` 是 [[operating-systems/processes-scheduling#ex-nice]] 的那个忙循环。不受限时它得到一个完整的核；在组里它 $3$ 秒中得到 $0.69$ 秒，约 $23\%$（另一次运行是 $0.77$ 秒；配额 $50\%$ 时 $1.46$ 秒）。调度器用**限流**强制执行配额：组在一个周期内用掉它的 $25$ ms 之后，其任务就不再被运行，直到下一个周期开始。

剩下的最后一块是文件系统。容器镜像是一叠只读**层**——一个基础发行版，然后是安装的软件包，然后是应用——由 **overlayfs** 合并成一棵树，顶上再加一个可写层存放容器的改动（以整个文件为单位的写时复制）。然后**挂载命名空间**与 `pivot_root` 把这棵树变成容器的 `/`。Docker（2013）把这些机制连同镜像格式和仓库一起打包成工具，使容器无处不在；开放容器倡议（2015）标准化了镜像与运行时格式，Kubernetes 这样的编排系统则在整个集群上调度容器。

::: example 亲手搭一个容器 {#ex-container}
要以上述机制运行一个作为容器的 web 服务器——自己的根文件系统（来自镜像）、自己的进程树和主机名、一个带一个虚拟接口的私有网络、至多两个 CPU 和 1 GiB 内存、在宿主机上没有 root 特权——你会按什么顺序组合哪些机制？
::: solution
(1) 创建把容器 root 映射到某个非特权宿主用户的**用户命名空间**——放在第一步，因为它让其余命名空间无需宿主特权就能创建。(2) 创建**挂载、UTS、IPC、PID 和 network 命名空间**（用 `unshare`，或带相应标志的单次 `clone`）。(3) 用 **overlayfs** 组装根文件系统——镜像层只读，上面加一个空的可写目录——挂载它，为新 PID 命名空间挂载一个新鲜的 `/proc`，再 `pivot_root` 进去，使宿主的文件不再可见。(4) 创建一对 **veth** 接口（两个虚拟接口，像电缆一样连在一起），把一端移进容器的网络命名空间，另一端接到宿主机上的网桥。(5) 创建一个 `cpu.max` 设为 `200000 100000`（每 $100$ ms 周期两个 CPU 的时间）、`memory.max` 设为 `1G` 的 **cgroup**，把容器的第一个进程移进去。(6) 放弃 capabilities 并安装一个限制服务器可以发起哪些系统调用的 **seccomp** 过滤器。(7) `execve` 服务器程序，它在里面成为 PID $1$。`runc`、`crun` 这样的容器运行时就是按配置文件执行这些步骤的。
:::
:::

## 隔离性比较

| | 进程 | 容器 | 虚拟机 |
|---|---|---|---|
| 内核 | 共享 | 共享 | 独立客户机内核 |
| 虚拟化的内容 | CPU、内存 | 加上名字：PID、挂载、网络、用户 | 整台机器 |
| 启动时间 | 毫秒 | 几十到几百 ms | 秒（微型虚拟机约 $100$ ms） |
| 内存开销 | 无 | 小 | 整个客户机操作系统 |
| 隔离边界 | 系统调用、权限 | 系统调用 + 命名空间 + 控制组 | 虚拟机监控器接口（VM 退出） |

决定性的差别是攻击者必须跨越的边界的大小。容器的进程直接向宿主机内核发起系统调用——多达数百种，由几百万行代码实现——所以任何一个可被利用的内核 bug 都能让容器里的代码接管宿主及其所有其他容器。虚拟机的客户机通过窄得多的接口与虚拟机监控器对话：几十种 VM 退出和虚拟设备。虚拟机监控器也有 bug，设备模拟部分尤甚，但攻击面小得多。

::: warning "容器就是轻量级虚拟机"
容器用起来像小型虚拟机——自己的 `/`、自己的 `ps`、自己的 `root`——但它们是共享内核上的进程。在没有用户命名空间的容器里以 root 运行的代码，在很多内核接口看来*就是* root；内核参数、系统时钟和内核模块都是共享的；一个内核漏洞就是宿主机上每个容器共同的漏洞。这就是为什么公共云把每个客户的容器再装进虚拟机里运行，也是 gVisor（用用户态内核拦截容器的系统调用）这样的沙箱和 Firecracker（2018，一个基于 KVM 的极简 VMM，约十分之一秒就能引导一个 Linux 客户机）这样的**微型虚拟机**存在的原因：它们把容器的便利与虚拟机监控器的边界结合在一起。容器用来做打包和资源管理；不要指望单靠它来分隔相互敌对的租户。
:::

::: history
IBM 的 CP-40（1967）和 CP-67，以及 VM/370 操作系统（1972），在一台大型机上运行 IBM 操作系统的多个副本——最早的虚拟机监控器；System/370 体系结构就是按可虚拟化设计的。Gerald Popek 与 Robert Goldberg 在"Formal requirements for virtualizable third generation architectures"（《ACM 通讯》，1974）中把要求形式化了。John Scott Robin 与 Cynthia Irvine 在 2000 年证明 x86 违反了这些要求。Mendel Rosenblum 与斯坦福的同事们（Disco 项目，1997）让虚拟机在现代硬件上复兴，并创办了 VMware，其带二进制翻译的 Workstation 于 1999 年上市。Paul Barham 等人的"Xen and the art of virtualization"（2003）以现代形式引入了半虚拟化。Intel VT-x（2005）和 AMD-V（2006）带来了硬件支持，Avi Kivity 的 KVM 于 2007 年并入 Linux。容器方面，Unix 的 `chroot`（1979）改变一个进程的根目录；FreeBSD jails（2000）和 Solaris Zones（2004）增加了真正的隔离；Linux 从 2002 年起获得命名空间，2008 年获得控制组（来自 Google 的 Paul Menage 与 Rohit Seth），LXC 于 2008 年把它们组合起来，Docker 自 2013 年起让容器普及开来。
:::

## 后续内容

虚拟机与容器是云计算和 [[distributed-systems]] 中大规模系统的基座：集群调度器把它们安放到各台机器上，实时迁移在虚拟机运行的同时拷贝其内存、把它从一台宿主移到另一台，无服务器平台按请求启动微型虚拟机。本章的隔离边界——以及越过边界的侧信道，如共享高速缓存和页共享——是 [[security]] 的中心议题。语言虚拟机（JVM、WebAssembly 运行时）虚拟化的是另一种接口：一套为可移植性而非真实处理器设计的指令集（[[programming-languages]]、[[compilers]]）。

::: summary
- **虚拟机**是一台真实机器的高效、隔离的复制品，由提供等价性、资源控制与效率的**虚拟机监控器**创建（[[#def-vm]]）；1 型直接跑在硬件上，2 型跑在宿主操作系统上，KVM 把 Linux 变成虚拟机监控器。
- 当每条敏感指令都是特权指令时**陷入并模拟**才可行（**Popek–Goldberg**，[[#thm-popek]]）。x86 不合格：`popf` 在用户态悄悄忽略对 IF 的改动，而且不陷入（[[#ex-popf]]）。
- 解决方案：**二进制翻译**（VMware）、**半虚拟化**（Xen、virtio）、**硬件支持**（VT-x/AMD-V：根与非根模式、VMCS、VM 退出）。开销约为（每秒退出次数）×（每次退出代价）（[[#prop-exits]]）。
- 内存需要两次转换；**影子页表**陷入客户机对页表的写，而**嵌套页表**（EPT/NPT）下每次 TLB 缺失至多花 $(n+1)(m+1) - 1 = 24$ 次访存（[[#thm-nested]]），可用 VPID 和大页缓解。气球与页共享实现内存超额承诺。
- **容器**（[[#def-container]]）是由**命名空间**（mount、UTS、IPC、PID、network、user、cgroup、time）隔离、由**控制组**限制（`cpu.max 25000 100000` 把一个自旋进程限制到约 $25\%$）的进程，根文件系统分层组装。
- 容器共享宿主内核，所以其隔离强度不超过内核的系统调用接口；虚拟机的边界窄得多。微型虚拟机与沙箱把两者结合。
:::

## 习题

::: exercise 哪种技术？ {level=1}
为下列情形各说出所用虚拟化技术：(a) 2002 年在 x86 台式机上运行未经修改的 Windows；(b) 调用虚拟机监控器来更新页表的 Linux 客户机；(c) 2026 年在处理器列有 `vmx` 和 `ept` 的服务器上运行未经修改的客户机；(d) 在 x86 笔记本电脑上运行 ARM 程序。
::: solution
(a) 二进制翻译（VMware Workstation）：处理器没有 VT-x，Windows 又无法修改。(b) 半虚拟化（Xen 的半虚拟客户机）：超级调用取代敏感指令。(c) 带嵌套页表的硬件辅助虚拟化（KVM、Hyper-V、ESXi）：CPU 靠 VT-x，内存靠 EPT。(d) 仿真（或跨指令集的动态二进制翻译，如 QEMU 的 TCG 所做），因为那些指令根本不可能原生运行。
:::
:::

::: exercise 敏感还是不敏感 {level=1}
把下列 x86 指令分类为无害、敏感且特权、或敏感但不特权（指 VT-x 之前的 32 位 x86）：(a) `add`；(b) 写 `%cr3` 的 `mov`；(c) `popf`；(d) `hlt`；(e) `sgdt`，它把全局描述符表的地址存入内存，且允许在用户态执行。
::: solution
(a) 无害。(b) 敏感（控制敏感：改变映射）且特权：在用户态陷入。(c) 敏感（它对 IF 的影响取决于运行模式）但不特权：[[#ex-popf]] 的问题。(d) 敏感且特权。(e) 敏感（行为敏感：它暴露一个控制结构的真实位置，与客户机的虚拟位置不同）但不特权——使用了它的客户机内核会看到*宿主机*的表地址。2017 年起一些处理器提供 UMIP（用户态指令防护），让 `sgdt` 及类似指令在用户态陷入。
:::
:::

::: exercise 控制组配额 {level=1 check="2"}
某个控制组的 `cpu.max` 里写着 `200000 100000`。组内进程至多能用多少个 CPU 的时间？（输入数字。）
::: solution
组在每个 $100{,}000$ µs 的周期内可使用 $200{,}000$ µs 的 CPU 时间，即 $200/100 = 2$ 个 CPU 的量——比如两个线程在两个核心上连续运行，或四个线程各运行一半时间。若是 `50000 100000`，就是半个 CPU，即使机器其余部分空闲也照样执行。
:::
:::

::: exercise 退出开销 {level=2 check="0.12"}
某虚拟机的网络驱动每秒引起 $80{,}000$ 次 VM 退出，每次处理花 $1.5$ µs。虚拟 CPU 损失的份额是多少？（输入分数。）若一个半虚拟驱动每次退出批量处理 $32$ 个数据包，份额又是多少？
::: solution
由 [[#prop-exits]]，$nc = 80000 \times 1.5 \times 10^{-6} = 0.12$：一个 CPU 的 $12\%$。每次退出批量 $32$ 个包把 $n$ 降到每秒 $2500$，损失降到 $0.00375$，不到 $0.4\%$——即 [[operating-systems/os-structure#prop-amortise]] 的道理用在 VM 退出上。
:::
:::

::: exercise 大页下的嵌套遍历 {level=2 check="14"}
某客户机用四级页表，虚拟机监控器用 1 GiB 的 EPT 页映射客户机内存，于是每次 EPT 遍历花 $2$ 次访存。一次不经缓存的 TLB 缺失花多少次访存？（输入数字。）若客户机也用 1 GiB 页（客户机遍历两级）呢？
::: solution
按 [[#thm-nested]] 的论证取 $n = 4$、$m = 2$：$(4 + 1)(2 + 1) - 1 = 14$。取 $n = m = 2$：$(3)(3) - 1 = 8$。原生用 1 GiB 页时，一次遍历是 $2$ 次访存。大页对虚拟化的负载有双重好处：每次遍历更短，缺失也更稀少。
:::
:::

::: exercise 影子页表的代价 {level=2}
影子页表之下，一个客户机进程调用 `fork`，客户机内核为写时复制把 $2000$ 个可写 PTE 标成只读。客户机每次写页表页都引起一次到 VMM 的陷入，花 $3$ µs。这部分 `fork` 要多长时间，与原生约 $2$ µs 相比如何？为什么嵌套页表免除了这一代价？它的代价换成了什么？
::: solution
$2000$ 次被陷入的写 $\times\ 3$ µs $= 6$ ms，而原生只有约 $2$ µs 的实际工作（每个 PTE 几纳秒）：慢了三千倍。VMM 会做批量处理和优化（对正被大量修改的页表页可以解除写保护、稍后再同步影子表），但 `fork` 密集的负载——shell 脚本、构建系统——正是影子页表的最坏情形。嵌套页表之下，客户机的页表只是由 EPT 转换的普通客户机内存；客户机全速写它们，没有退出。代价改在 TLB 缺失上支付：至多 $24$ 次访存的二维遍历（[[#thm-nested]]）。
:::
:::

::: exercise popf 与一次虚拟中断 {level=3}
VT-x 之前 x86 上一个被去权的客户机内核在纯陷入并模拟下运行。它执行 `popf` 清 IF，更新一个共享队列，再执行 `popf` 恢复 IF。准确描述出了什么问题，说明它如何违反 [[#def-vm]] 的等价性要求，并解释 VT-x 如何防止它。
::: solution
客户机内核运行在用户态，所以它的第一条 `popf` 悄悄让 IF 保持置位而且不陷入（[[#ex-popf]]）。VMM 保存的客户机虚拟 IF 的副本因此仍写着"允许中断"。若客户机正在更新队列时来了一个给它的时钟中断，VMM 就会递送一个虚拟中断——跳到客户机的中断处理程序——而处理程序可能也去访问那个队列，发现它更新到一半。在真实机器上，清掉的 IF 本会把中断推迟到第二条 `popf` 之后。程序的行为与真实机器不同，违反等价性，因为一条敏感指令在 VMM 不知情的情况下被执行了。（客户机内核还可能用 `pushf` 读标志，看到的将是*真实*的 IF 和真实的运行模式而不是它的虚拟值——又一处行为敏感的泄漏。）有了 VT-x，客户机内核运行在非根模式的环 $0$，`popf` 在那里真的改变 IF——改的是*客户机*处理器状态中的 IF，保存在 VMCS 里并随之恢复——而虚拟机监控器把外部中断配置为无论客户机 IF 如何都引起 VM 退出，只在客户的 IF 允许时才**注入**虚拟中断（用"中断窗口退出"控制来获知何时允许）。客户机对 IF 的视图是精确的，而虚拟机监控器保持控制权。
:::
:::

::: exercise 容器共享了什么 {level=3}
从正文中的 `unshare` 命令出发，列出拥有全部八种命名空间的容器中的一个进程仍与宿主共享的五样内核资源，对每样说出可能出什么事、有什么缓解措施。
::: solution
(1) **内核本身**——同样的代码，同样的漏洞：一次来自容器内部的内核利用就攻陷宿主。缓解措施：及时给内核打补丁，用 seccomp 限制系统调用，把不可信的容器放进虚拟机或 gVisor。(2) **系统时钟**（`CLOCK_REALTIME`）：时间命名空间只虚拟化单调时钟和启动时钟，所以被允许设置时间的容器（`CAP_SYS_TIME`）会替所有人改变它。缓解措施：放弃该 capability（容器运行时的默认做法）。(3) `/proc/sys` 中没有被命名空间隔离的**内核参数**（许多内存与调度设置）：有特权的容器能改变它们。缓解措施：把 `/proc/sys` 挂成只读。(4) **物理资源**——CPU 高速缓存、内存带宽、磁盘：吵闹的邻居会拖慢别人，共享高速缓存还容许时序侧信道。缓解措施：用控制组限制带宽与配额；对付侧信道则分开宿主或核心。(5) **内核内存与页缓存**：容器能填满内核数据结构（目录项、索引节点）或页缓存。缓解措施：memory 控制组把内核内存与页缓存记账到组头上。此外共享的还有：已加载的内核模块、某些配置下的内核钥匙环，以及设备驱动程序。
