一个栈装着 $64$ 个结点。$p$ 个线程各自反复弹出一个结点再把它压回去，重复两百万次。我们用三种方式实现这个栈：每个操作套一把互斥锁；完全不加锁，使用原子的 **compare-and-swap**（比较交换）指令；以及同样的无锁设计、加一个看似无害的简化。运行结束后，一个检查程序遍历栈，确认全部 $64$ 个结点恰好各出现一次。

本章讲许多线程同时使用的共享数据结构。我们首先需要一个针对操作在时间上重叠的对象的正确性定义——**可线性化性**——以及一套描述进展性的词汇：一个实现**无锁**（lock-free）或**无等待**（wait-free）意味着什么。然后我们用精细程度递增的锁构造并发集合与栈，再用 compare-and-swap 做到无锁；认识 ABA 问题及其背后的内存回收问题；概览迈克尔-斯科特队列；并证明赫尔利（Herlihy）的定理：有些原子指令根本上比其他指令更强。假设已具备 [[operating-systems/threads-locks]] 的原子指令与锁，以及 [[parallel-computing/memory-consistency]] 的内存定序。

## 正确性的含义

对顺序的栈，正确性很好陈述：每个操作都按规格说明变换状态。操作在时间上重叠时，连"`pop` 开始时的状态"是什么意思都不清楚。我们用执行的外部可见事件来描述执行。

::: definition 历史 {#def-history}
并发对象的一个**历史**（history）是一列有限的**调用**事件（线程 $T$ 以参数调用操作 $op$）与**响应**事件（操作把结果返回给 $T$）。响应出现的操作是**完成的**，否则是**挂起的**。若 $a$ 的响应出现在 $b$ 的调用之前，则操作 $a$ 在实时间上**先于**操作 $b$，记作 $a \prec b$；互不先于的两个操作**重叠**。若每个调用都紧跟它自己的响应，则历史是**顺序的**。
:::

::: definition 可线性化性（赫尔利与温，1990） {#def-linearisable}
一个历史 $H$ 是**可线性化的**，如果可以删除或以某个响应补全每个挂起的操作，然后把全部完成的操作排成一个顺序历史 $S$，使得

1. $S$ 是**合法的**：它满足对象的顺序规格；
2. $S$ **符合实时间**：若 $a \prec b$ 在 $H$ 中成立，则 $a$ 在 $S$ 中排在 $b$ 之前。

一个对象的实现是可线性化的，如果它能产生的每个历史都可线性化。等价地说，每个操作都像是在调用与响应之间的某个时刻瞬时生效——那一刻就是它的**线性化点**。
:::

可线性化性是并发对象天然的正确性条件：使用者可以像操作一个一个发生、且次序与其所见一致那样推理。重叠的操作怎样排都行；不重叠的操作必须保持实时间次序。较弱的条件是对象的**顺序一致性**，它只要求每个线程自己的操作保持次序。可线性化性有顺序一致性没有的性质：它是**局部的**（赫尔利与温证明：一个历史可线性化当且仅当它限制到每个对象都可线性化），所以由可线性化对象搭建的系统也是可线性化的，而且对象可以逐个验证。

::: example 暴力检查历史 {#ex-check-history}
FIFO 队列的两个历史，时间单位任意：

- $H_1$：A 的 `enq(x)` 在 $[0, 3]$；B 的 `enq(y)` 在 $[1, 4]$；A 的 `deq() → y` 在 $[5, 7]$；B 的 `deq() → x` 在 $[6, 8]$。
- $H_2$：A 的 `enq(x)` 在 $[0, 2]$；B 的 `enq(y)` 在 $[3, 5]$；A 的 `deq() → y` 在 $[6, 8]$。

它们可线性化吗？
::: solution
一个小程序枚举操作的一切次序，保留符合实时时间的，再逐个在顺序队列上重放：

```python
from itertools import permutations

# 一个操作：(名字, 线程, 操作, 参数, 结果, 调用时刻, 响应时刻)
def legal(seq):
    """Is this sequential order legal for a FIFO queue?"""
    q = []
    for _, _, op, arg, res, _, _ in seq:
        if op == "enq":
            q.append(arg)
        elif (q.pop(0) if q else None) != res:      # deq 必须返回最老的元素
            return False
    return True

def linearizable(history):
    """Brute force: some order that respects real time and is legal."""
    for order in permutations(history):
        pos = {op[0]: k for k, op in enumerate(order)}
        respects = all(pos[a[0]] < pos[b[0]]
                       for a in history for b in history if a[6] < b[5])  # a 结束早于 b 开始
        if respects and legal(order):
            return [op[0] for op in order]
    return None

H1 = [("A1", "A", "enq", "x", None, 0, 3), ("B1", "B", "enq", "y", None, 1, 4),
      ("A2", "A", "deq", None, "y", 5, 7), ("B2", "B", "deq", None, "x", 6, 8)]
H2 = [("A1", "A", "enq", "x", None, 0, 2), ("B1", "B", "enq", "y", None, 3, 5),
      ("A2", "A", "deq", None, "y", 6, 8)]
print("H1:", linearizable(H1))
print("H2:", linearizable(H2))
```

```console
$ python3 linearize.py
H1: ['A1', 'B1', 'B2', 'A2']
H2: None
```

$H_1$ 是可线性化的：两次入队重叠，两次出队也重叠，所以次序 `enq(x)`、`enq(y)`、B 的 `deq → x`、A 的 `deq → y` 符合实时间且合法。$H_2$ 不是：`enq(x)` 在 `enq(y)` 开始前就结束了，所以任何符合实时时间的次序都把 $x$ 先入队，于是第一次出队必须返回 $x$。$H_2$ *是*顺序一致的——次序 `enq(y)`、`enq(x)`、`deq → y` 保持了每个线程自己的操作次序——这说明两个条件确实不同。暴力法对 $n$ 个操作要 $n!$ 步；判定可线性化性一般是 NP 完全的（吉本斯（Gibbons）与科拉赫（Korach），1997），但实用的检查器靠剪枝能处理数千个操作的历史。
:::
:::

### 进展性

正确性对操作能否完成一无所说。一个基于锁的对象可以完全正确，却仍可能让所有线程永远等待——只要持锁者被换下 CPU、崩溃，或被一个试图取同一把锁的信号处理程序打断。

::: definition 进展条件 {#def-progress}
并发对象的一个实现是

- **无死锁**（阻塞式）：只要各线程都在执行操作、且持有锁的线程持续得到调度，就必有操作最终完成；**无饥饿**：同一假设下每个操作最终都完成；
- **无阻碍**（obstruction-free）：若从某时刻起某个操作总是单独运行（其他线程全部暂停），它总在有限步自己的执行中完成；
- **无锁**（lock-free）：在每个无限执行中都有无穷多个操作完成——无论线程怎样调度、哪怕有些线程永远暂停，总有某个线程在前进；
- **无等待**（wait-free）：每个操作都在有限步自己的执行中完成，不论其他线程如何。
:::

无等待蕴含无锁，无锁蕴含无阻碍。非阻塞的三个条件对调度器是稳健的：一个在中途被暂停、换出或被杀掉的线程，挡不住其他线程完成它们的操作。无锁允许个别操作饿死——因为别人不断成功，它的 compare-and-swap 永远失败——但系统整体始终在前进。实践中选择无锁结构，与其说为了稳健，不如说为了避免锁在竞争下的护航（convoying）与优先级问题；选择无等待结构则为了实时性保证。

## 加锁设计

最简单的并发对象就是把一个顺序对象包在一把锁里——**粗粒度加锁**。每个操作从头到尾持锁，所以操作是可线性化的（线性化点可取持锁期间的任何时刻），正确性由顺序实现继承而来。但操作被串行化了，竞争之下锁所在的缓存行成为瓶颈，开头那个互斥锁栈已经演示过。

较细的锁能让作用于结构不同部分的操作并行。考虑用一个有序链表表示的整数集合，两端各放一个哨兵结点 $-\infty$ 与 $+\infty$。

::: algorithm 交接加锁（锁耦合） {#alg-hand-over-hand}
每个结点有自己的锁。`add(k)` 或 `remove(k)` 的做法：

1. 锁住头哨兵；令 `pred` 为头结点、`curr` 为它的后继；锁 `curr`。
2. 当 `curr.key` $< k$：解锁 `pred`；令 `pred` $\gets$ `curr`、`curr` $\gets$ `curr.next`；锁 `curr`。
3. 此时 `pred.key` $< k \le$ `curr.key`，且两者都已锁定。对 `add`：若 `curr.key` $= k$ 报告 false；否则在 `pred` 与 `curr` 之间接入一个新结点。对 `remove`：若 `curr.key` $= k$，令 `pred.next` $\gets$ `curr.next` 并报告 true；否则报告 false。
4. 解锁 `curr` 和 `pred`。
:::

线程总是持有它即将离开的结点的锁、直到锁住下一个结点，所以线程沿链表鱼贯而行、永远无法互相超越。两个线程在链表相距很远的部分可以并发工作。每个操作在它锁住最终两个结点中的第二个的那一刻线性化。同时持*两*把锁必不可少：若 `remove` 只持 `curr` 的锁，两个线程并发删除相邻结点 $a$ 与 $b$ 时，各自都可能通过改写前驱的 `next` 摘掉自己的结点，而 $b$ 的删除会被撤销（[[#ex-two-locks]]）。

交接加锁仍使每个操作每经过一个结点就要取一把锁。**乐观**同步先不加锁地遍历，只锁 `pred` 与 `curr`，然后*验证*——重新遍历，检查 `pred` 仍可达且仍指向 `curr`——不成立就重试。**惰性表**（赫勒（Heller）、赫尔利（Herlihy）、卢坎科（Luchangco）、莫尔（Moir）、舍勒（Scherer）与沙维特（Shavit），2005）给每个结点加一个 `marked` 位，在结点被摘除之前置位，于是验证只需检查这两个结点的标记与链接，`contains` 完全不需要锁。集合的读取大多数是 `contains`，所以惰性表在实践中很快。

## 用 compare-and-swap 做无锁编程

无锁编程的基本工具是 **compare-and-swap** 循环：读一个共享字，由它算出新值，只有在此期间字没有变化才安装新值；否则重试。C11 的 `atomic_compare_exchange_weak(&w, &expected, new)` 作为一个原子步骤执行："若 `w` 等于 `expected`，存入 `new` 并返回 true；否则把 `w` 的当前值拷进 `expected` 并返回 false"。（"弱"形式可能虚假失败，在循环里无害。）

::: algorithm 特雷伯（Treiber）无锁栈 {#alg-treiber}
栈是结点的链表；单个共享字 `top` 指向栈顶结点（或为空）。

- `push(n)`：**repeat**：`old` $\gets$ `top`；`n.next` $\gets$ `old` **until** CAS(`top`, `old`, `n`) 成功。
- `pop()`：**repeat**：`old` $\gets$ `top`；**if** `old` 为空 **return** 空栈；`new` $\gets$ `old.next` **until** CAS(`top`, `old`, `new`) 成功；**return** `old`。
:::

::: theorem 特雷伯栈可线性化且无锁 {#thm-treiber}
假设只要任何线程可能还持有指向某结点的指针，该结点就绝不会被复用（释放并重新分配）。则特雷伯栈是可线性化的，每个成功的操作在其成功的 CAS 处线性化（读到空 `top` 的空 `pop` 在其读处线性化），并且它是无锁的。
:::

::: proof
**不变式。** 在成功的两次 CAS 之间，`top` 与其可达结点的 `next` 字段构成一个链表，表示栈的内容、栈顶在前；我们证明每次成功的 CAS 恰好按顺序操作应有的方式改变它。CAS 成功的 `push(n)` 看到 `top` $=$ `old`，且 `n.next` $=$ `old` 是压栈线程在 CAS 之前写的——在结点被发布之前它归该线程私有；所以 CAS 之后链表是 `n` 接旧表——这是一次压栈。CAS 成功的 `pop` 在 CAS 时看到 `top` $=$ `old`，并安装它早先从 `old.next` 读到的值 `new`。在 CAS 那一刻该值仍是 `old.next`：栈内结点的 `next` 字段只由压入该结点的线程在发布它之前写；并由假设，`old` 期间没有被弹出、释放、再次压入（那正是 ABA 情形，已被条件排除）。所以 CAS 之后链表是旧表去掉首结点——一次返回 `old` 的弹栈。失败的 CAS 什么都不改变。空的 `pop` 读到 `top` $=$ null，所以那一瞬间栈是空的。

**可线性化性。** 每个操作的线性化点位于其调用与响应之间，而按时间排序的这些线性化点，由不变式可知恰好重放顺序规格。因此历史都可线性化。

**无锁性。** 对 `top` 的 CAS 失败，只因为 `top` 在该线程读它之后变了；而 `top` 只经成功的 CAS 改变，那次操作随后立即返回。假设某个无限执行只完成了有限个操作。最后一次完成之后，必有一个线程走无穷多步；循环的每次尝试是有限步，所以它执行了无穷多次 CAS，且全部失败。每次失败都要求另一个线程在失败线程读它之后做一次成功的 CAS——也就是最后一次完成之后又有一次完成。这一矛盾说明完成的操作有无穷多个。（栈不是无等待的：一个线程的 CAS 可能永远失败，而其他线程不断成功。）
:::

::: example 两次压栈的竞争 {#ex-push-race}
栈里只有一个结点 $x$。线程 1 与 2 同时调用 `push(a)` 与 `push(b)`，步骤如下穿插：1 读 `top` $= x$；2 读 `top` $= x$；1 令 `a.next` $= x$；2 令 `b.next` $= x$；1 执行 CAS(`top`, $x$, $a$)；2 执行 CAS(`top`, $x$, $b$)；2 重试。追踪状态。
::: solution
| 步骤 | `top` | `a.next` | `b.next` | 说明 |
|---|---|---|---|---|
| 1 读 `top` | $x$ | — | — | 线程 1 的 `old` $= x$ |
| 2 读 `top` | $x$ | — | — | 线程 2 的 `old` $= x$ |
| 1 写 `a.next` | $x$ | $x$ | — | $a$ 仍是线程 1 的私有结点 |
| 2 写 `b.next` | $x$ | $x$ | $x$ | $b$ 仍是线程 2 的私有结点 |
| 1：CAS($x \to a$) | $a$ | $x$ | $x$ | 成功：**push(a) 在此线性化** |
| 2：CAS($x \to b$) | $a$ | $x$ | $x$ | 失败：`top` 是 $a$；C11 把 $a$ 拷入线程 2 的 `old` |
| 2 写 `b.next` | $a$ | $x$ | $a$ | 以 `old` $= a$ 重试 |
| 2：CAS($a \to b$) | $b$ | $x$ | $a$ | 成功：**push(b) 在此线性化** |

最终链表是 $b \to a \to x$，正是顺序历史 `push(a)`、`push(b)` 的结果。线程 2 失败的 CAS 没有造成损害：它什么都没改变，作用只是让线程 2 重做那两个廉价的步骤。若把 CAS 换成普通存储，线程 2 会置 `top` $= b$ 而 `b.next` $= x$，把 $a$ 丢掉。
:::
:::

### ABA 问题

[[#thm-treiber]] 的条件正是开头程序第三个版本出错的地方。那个版本复用结点——每个线程弹出一个结点又把同一个结点压回去——而且只比较结点的下标。

::: example ABA 如何破坏栈 {#ex-aba}
栈为 $A \to B \to C$。线程 1 开始 `pop`：读到 `old` $= A$、`new` $= A.\text{next} = B$，然后在其 CAS 之前被耽搁。线程 2 弹出 $A$、弹出 $B$，再把 $A$ 压回去。追踪栈的变化。
::: solution
线程 2 做完之后：栈是 $A \to C$（$A$ 被压回时它的 `next` 被改写成 $C$），线程 2 手里拿着 $B$。此时线程 1 执行 CAS(`top`, $A$, $B$)：`top` 又是 $A$，于是 CAS *成功*，`top` 变成 $B$——一个不在栈里、在线程 2 手里的结点。栈如今从 $B \to \dots$ 读起（$B$ 那个过时的 `next` 指向哪里算哪里），$C$ 丢失；而线程 2 把 $B$ 压回去时，链表可能成环。CAS 比较的是值 $A$，无从分辨 `top` 曾经从 $A$ 变成别的、又变回 $A$——所以叫 "ABA"。开头实验里检查报了 `nodes 1/64 CORRUPTED`：从 `top` 出发几乎立刻就有结点被走到两次。
:::
:::

标准防御有三种：

- **带标签的指针**（版本计数器）：在被 CAS 的字里把计数器挨着指针存放，每次 CAS 成功就把它加一。这样一个字变了又变回来时 CAS 就会失败，除非计数器在此期间恰好回绕。这就是开头程序的 "CAS+tag" 版本，它把一个 $32$ 位结点下标和一个 $32$ 位标签打包进一个 $64$ 位字；用完整的 $64$ 位指针时就需要双宽 CAS（x86-64 的 `cmpxchg16b`）或指针的富余位。
- **安全内存回收**：指针形式的 ABA 之所以发生，是因为结点被释放、内存被复用，而一个被耽搁的线程还持有指向它的指针。**危险指针**（hazard pointers，马盖德·迈克尔（Maged Michael），2004）让每个线程公布自己即将解引用的指针，结点只有在没有任何危险指针提及它时才被释放。**基于代际（epoch）的回收**只在一个结点被摘除后、每个线程都通过了静止点（quiescent point）才释放它；Linux 内核的**读-复制-更新**（read–copy–update，RCU）机制属于这一类。两者还顺带防止了同一个被耽搁的线程读 `old.next` 时会犯的释放后使用（use-after-free）。
- **垃圾回收**：在 Java、Go 或 C# 中，只要还有线程持有对某结点的引用，该结点就不会被复用，所以指针形式的 ABA 无从发生——无锁结构最早在 Java（`java.util.concurrent`，2004）里普及开来，这是原因之一。

下面是开头实验里带标签的无锁栈。结点是数组的下标，`top` 打包一个下标（低 $32$ 位）和一个标签（高 $32$ 位）；`next[i]` 是原子的，因为执行 `pop` 的线程可能在另一个线程写它时读它，这一竞争由 CAS 事后察觉。

```c
#define NIL 0xFFFFFFFFu
static atomic_uint next[M];                  /* next[i]：结点 i 下面的结点 */
static _Alignas(64) atomic_uint_least64_t top;   /* 低 32 位：下标；高 32 位：标签 */

static uint64_t pack(uint32_t idx, uint32_t tag) { return (uint64_t)tag << 32 | idx; }

static uint32_t pop(void) {
    uint64_t old = atomic_load_explicit(&top, memory_order_acquire), new;
    do {
        uint32_t i = (uint32_t)old;
        if (i == NIL) return NIL;                            /* 空栈 */
        uint32_t below = atomic_load_explicit(&next[i], memory_order_relaxed);
        new = pack(below, (uint32_t)(old >> 32) + 1);        /* 新标签 */
    } while (!atomic_compare_exchange_weak_explicit(&top, &old, new,
                 memory_order_acquire, memory_order_acquire));
    return (uint32_t)old;
}

static void push(uint32_t i) {
    uint64_t old = atomic_load_explicit(&top, memory_order_relaxed), new;
    do {
        atomic_store_explicit(&next[i], (uint32_t)old, memory_order_relaxed);
        new = pack(i, (uint32_t)(old >> 32) + 1);
    } while (!atomic_compare_exchange_weak_explicit(&top, &old, new,
                 memory_order_release, memory_order_relaxed));
}
```

`push` 成功 CAS 的释放定序与 `pop` 各次载入的获取定序，使压栈线程对 `next[i]` 的写（以及它写进结点的一切）对弹出该结点的线程可见（[[parallel-computing/memory-consistency#thm-message-passing]]）。实验的"无标签"版本与此完全相同，只是标签恒为 $0$。完整程序另有互斥锁版本、OpenMP 驱动和完整性检查，共 $76$ 行。

::: quiz
关于特雷伯栈，哪些说法正确？
- [x] 一个线程若在 `push` 中途永远暂停，其他线程仍能完成它们的操作。
- [ ] 每个 `pop` 都在有界的步数内完成。
- [x] 在有垃圾回收的语言里，只要每次 `push` 都分配新结点，无标签版本就是正确的。
- [ ] 把 `top` 声明成 `volatile` 指针而不是原子指针，也能防止 ABA。
::: solution
栈是无锁的：暂停的线程不持锁，它未完成的 CAS 挡不住别人成功。它不是无等待的：竞争之下一个 `pop` 可以无限期地 CAS 失败。有垃圾回收时，被耽搁线程仍引用着的结点不可能被回收复用，所以 `top` 不可能回到同一个结点——除非该结点被弹出又再次压入，而每次 `push` 都新分配就排除了这种可能。`volatile` 既不保证原子性，也防不住 ABA。
:::
:::

::: example 共享栈为何无法扩展 {#ex-stack-throughput}
根据开头的测量，算出 $p = 1, 4, 16$ 时互斥锁栈与无锁栈的总吞吐量，并与移动存放 `top` 的缓存行所加的限制比较——每次转移 $100$–$200$ ns（[[parallel-computing/memory-consistency#ex-pingpong]]）。
::: solution
输出的每一行给出的是每线程每对弹-压的时间，所以总吞吐量是 $p$ 除以该时间：

| $p$ | 互斥锁 | 带标签 CAS |
|---|---|---|
| $1$ | $1/21\text{ ns} = 47.6$ 百万对/秒 | $1/27\text{ ns} = 37.0$ 百万对/秒 |
| $4$ | $4/753\text{ ns} = 5.3$ 百万对/秒 | $4/434\text{ ns} = 9.2$ 百万对/秒 |
| $16$ | $16/4647\text{ ns} = 3.4$ 百万对/秒 | $16/2520\text{ ns} = 6.3$ 百万对/秒 |

单线程时行从不移动，互斥锁（加锁解锁各一条原子指令、全在一条缓存行内）甚至比两重 CAS 循环还略快。多线程时，每次操作都需要把存放 `top` 的行（互斥锁还有存放锁字的行）以 M 状态搬进自己的缓存。相邻两次操作来自不同线程时，一对操作至少要两次转移，所以按每次转移 $100$–$200$ ns，吞吐量至多约 $1/(2 \times 100\text{ ns}) = 5$ 到 $1/(2 \times 200\text{ ns}) = 2.5$ 百万对每秒——除非一个线程在持行期间连做多个操作。测量值正是这个量级。无论线程多少，两种设计都无法超过它；只有线程通常作用于*不同*缓存行的设计才行。
:::
:::

### 队列与帮助

队列比栈难，因为它有两端。**迈克尔-斯科特队列**（Michael–Scott queue，1996）是 Java `ConcurrentLinkedQueue` 的基础，它维护一个带哑结点的链表和两个共享指针 `head`、`tail`。`enqueue` 用一次 CAS 把自己的结点接到最后一个结点之后，再用第二次 CAS 把 `tail` 拨到新结点。两次 CAS 之间，`tail` 落后真正的队尾一个结点。发现 `tail.next` 非空的线程因此知道某个入队只做了一半，于是去**帮助**它：先把 `tail` 推进，再重试自己的操作。帮助是非阻塞设计的关键思想：一个中途被打断的操作，留下的结构状态允许任何线程把它做完，所以谁也不必等待。该队列是可线性化的（入队在接上结点的 CAS 处线性化，出队在推进 `head` 的 CAS 处线性化）且无锁。

## 原子指令的威力

每个并发对象都能无锁实现吗？用哪些指令？莫里斯·赫尔利（Maurice Herlihy）在 1991 年比较各指令能解决的最难问题，从而一并回答了这两个问题。

::: definition 共识 {#def-consensus}
在**共识**问题中，$n$ 个线程各带一个输入值，调用返回某个值的 `decide`，要求

- **一致性**（agreement）：所有线程决定同一个值；
- **有效性**（validity）：所决定的值是某个线程的输入；
- **无等待性**（wait-freedom）：每个线程在自己有限多步内做出决定。

一个对象类型的**共识数**是用该类型对象加读写寄存器能解出 $n$ 线程共识的最大 $n$，若无最大则为 $\infty$。
:::

::: theorem compare-and-swap 的共识数为无穷 {#thm-cas-consensus}
对每个 $n$，$n$ 个线程的共识可以用一个 compare-and-swap 字无等待地解决。
:::

::: proof
让字 $w$ 初始存放一个不是任何线程输入的值 $\bot$。输入为 $v$ 的每个线程执行一次 CAS($w$, $\bot$, $v$)，然后读 $w$ 并决定读到的值。恰有一次 CAS 成功——最先执行的那次，因为其余各次都会发现 $w \ne \bot$——而在那之后 $w$ 永不改变，因为更晚的 CAS 全部失败。于是每个线程读到并决定第一次 CAS 写入的值 $v_1$：一致性。$v_1$ 是执行那次 CAS 的线程的输入：有效性。每个线程走两步：无等待。
:::

相比之下，读写寄存器的共识数是 $1$：只用读写，两个线程不存在无等待的共识协议（卢伊（Loui）与阿布-阿马拉（Abu-Amara），1987；赫尔利（Herlihy），1991）。证明是费希尔（Fischer）、林奇（Lynch）与帕特森（Paterson）关于异步消息传递的不可能性定理（1985，[[distributed-systems]]）风格的**价性论证**：先证明某个可达构型是*临界*的——任一线程的下一步都会决定结局，且决定得不同；再证明不管这两步是什么（读或写、同一个或不同的寄存器），另一个线程都分辨不出它们，矛盾。同样的论证说明 test-and-set、fetch-and-add 与原子交换的共识数恰为 $2$：它们能解两线程共识（[[#ex-tas-consensus]]），三线程就不能。队列与栈的共识数也是 $2$。

赫尔利还证明了反命题：共识是**通用的**。任何有顺序规格说明的对象，都能用 $n$ 线程共识对象加寄存器构造出 $n$ 线程的无等待、可线性化实现（*通用构造*：把所有操作串过一列共识实例，由它们决定操作的次序，并用帮助使其无等待）。两个推论随之而来：三线程以上，队列或 compare-and-swap 的无等待实现不可能用读写和 test-and-set 构造出来，无论多么巧妙；而有了 compare-and-swap（或链接载入/条件存储），什么都能构造。这就是每个现代多处理器指令集都提供二者之一的理由。

::: warning 无锁不等于快
无锁结构避开了锁最恶劣的行为——持有者被换下而别人等待、优先级反转、死锁——但消除不了竞争。特雷伯栈每个成功的操作都写同一个字，所以它的吞吐量受一条缓存行在核心间移动速度的限制，与锁一模一样；开头实验里，$16$ 个线程的总吞吐量还不如一个。CAS 循环还可能浪费劳动：一次失败的尝试已经干了成功尝试的全部工作。无锁设计能扩展，只有当线程通常作用于*不同*的缓存行——桶很多的哈希表、带窃取的每线程队列（[[parallel-computing/shared-memory#alg-work-stealing]]）、按线程分片的计数器。拿不准就测量，并且优先选用久经考验的库实现（Java 的 `java.util.concurrent`、Folly 或 `libcds` 等 C++ 库、Rust 的 `crossbeam`），而不是自己动手。
:::

### 彻底避开竞争

最具扩展性的共享对象，是那些很少被共享的对象。几种常见设计：

- **分片计数器**：每个线程自增自己填充过的计数器，读取时把它们加起来。自增无竞争；读取代价 $O(p)$，读到的值在读取期间的某个时刻是正确值（只有当读很少发生、或你接受稍弱的保证，或采用更讲究的协议，它才是可线性化的）。Linux 的每 CPU 计数器与 Java 的 `LongAdder` 就是这么做的。
- **合并**：发现结构正忙的线程把自己的操作托付给一个线程，由它持锁一次性施加全部操作——**平面合并**（flat combining，亨德勒（Hendler）、因策（Incze）、沙维特（Shavit）与扎夫里尔（Tzafrir），2010）——于是结构的缓存行留在一个缓存里。
- **读多改少的数据**：读者不写任何共享位置就能前进（RCU、序列锁），写者独自承担同步的全部代价。
- **事务内存**：程序员把一个块标记为原子的，系统推测执行它，检测冲突并重试（赫尔利（Herlihy）与莫斯（Moss），1993）。英特尔在 2013 年的 Haswell 处理器上提供了硬件事务内存，但此后在多款处理器上因勘误与安全事件被默认禁用（2026 年）；软件事务内存用于 Haskell 与 Clojure。

::: history
并发数据结构始于操作系统。R·肯特·特雷伯（R. Kent Treiber）1986 年在一份 IBM 研究报告里描述了无锁栈，用的是 System/370 的 compare-and-swap，并同时给出了用版本计数器防御 ABA 的办法。莫里斯·赫尔利（Maurice Herlihy）与珍妮特·温（Jeannette Wing）1990 年定义了可线性化性；赫尔利的《Wait-free synchronization》（1991）引入共识数与通用构造。马盖德·迈克尔（Maged Michael）与迈克尔·斯科特（Michael Scott）1996 年发表他们的非阻塞队列；蒂莫西·哈里斯（Timothy Harris）2001 年用带标记的指针做出无锁链表。马盖德·迈克尔 2004 年提出危险指针，同年道格·利（Doug Lea）建立在诸如此类算法之上的 `java.util.concurrent` 包进入 Java 5。保罗·麦肯尼（Paul McKenney）与约翰·斯林温（John Slingwine）1998 年描述读-复制-更新；2002 年它进入 Linux 内核。莫里斯·赫尔利（Maurice Herlihy）与埃利奥特·莫斯（Eliot Moss）1993 年提出事务内存；赫尔利与尼尔·沙维特（Nir Shavit）的《The Art of Multiprocessor Programming》（《多处理器编程艺术》，2008；与维克托·卢坎科（Victor Luchangco）、迈克尔·斯皮尔（Michael Spear）合作的第二版 2020）成为标准教材。
:::

## 后续内容

[[parallel-computing/shared-memory]] 的工作窃取双端队列就是本章这种无锁结构：一端归主人所有，另一端供人窃取。[[parallel-computing/parallel-algorithms]] 从独立线程共享的数据结构转向在工作-跨度模型中设计的算法，那里的同步隐含在 fork 与 join 之中。用消息通信、可能崩溃的进程之间的共识——[[#thm-cas-consensus]] 中寄存器情形的不可能性在那里就是 FLP 定理，Paxos、Raft 这类协议绕开它——是 [[distributed-systems]] 的核心。数据库在更大的尺度上实现同样的思想：两阶段锁与乐观并发控制就是本章加锁与验证的事务版（[[databases]]）。

::: summary
- 并发对象正确的含义是**可线性化**（[[#def-linearisable]]）：每个历史都能由一个既符合实时间又满足顺序规格的次序解释；每个操作在某个线性化点瞬时生效。可线性化性是局部的，所以可线性化对象可以拼装。小历史可以用暴力检查（[[#ex-check-history]]）。
- 进展条件（[[#def-progress]]）：无死锁与无饥饿（阻塞式）、无阻碍、**无锁**（总有操作在完成）与**无等待**（每个操作在有限步内完成）。
- 基于锁的设计从一把粗锁，到**交接加锁**（[[#alg-hand-over-hand]]）、乐观验证与惰性表。
- **特雷伯栈**（[[#alg-treiber]]）每操作一次 CAS，即可线性化且无锁（[[#thm-treiber]]）——前提是结点在被引用期间不被复用。复用造成 **ABA 问题**（[[#ex-aba]]），它破坏了我们的无标签栈；标签、危险指针、代际或垃圾回收可以防患。
- **帮助**让迈克尔-斯科特队列在操作半途停顿时依然无锁。
- compare-and-swap 能为任意数目的线程解共识（[[#thm-cas-consensus]]）；寄存器一个都解不了，test-and-set 与 fetch-and-add 只能解两线程。有了共识，每个对象都有无等待实现。
- 无锁不等于无竞争：一个共享字限制吞吐量，恰如一把锁；可扩展的设计分片、合并，或者干脆不写共享行。
:::

## 习题

::: exercise 数线性化 {level=1 check="6"}
三个线程各自对一个初始为空的栈调用 `push`，值为 $1$、$2$、$3$，三个操作在时间上两两重叠。没有其他操作。多少个不同的顺序历史是合法的线性化？（填入数目。）
::: solution
三个操作两两重叠，实时间不强加任何次序，栈对三次压栈的任何排列都合法。共 $3! = 6$ 个线性化。后续一串 `pop` 会暴露选中了哪一个，从而排除其余。
:::
:::

::: exercise 给进展条件归类 {level=1}
按 [[#def-progress]] 中最强的满足条件，给共享计数器 `increment` 的几种实现归类：(a) `count++` 套一把互斥锁；(b) 读 `count` 并尝试 CAS(`count`, $v$, $v + 1$)、直到成功的循环；(c) 一条 `atomic_fetch_add`；(d) 每个线程自增数组中自己填充过的一格。
::: solution
(a) 阻塞式：无死锁；若互斥锁公平则也无饥饿；持有者被换下时大家都在等。(b) 无锁：CAS 失败只因为另一次自增成功了，所以总有自增在完成，但特定线程可以一直失败；不是无等待。(c) 无等待，假设硬件在有界时间内执行 `lock xadd`（x86 上如此；在 LL/SC 机器上编译器发出重试循环，那只到无锁）。(d) 自增是无等待且无竞争的；读取必须把所有格子求和，若不加讲究的手段，它对并发自增不是可线性化的。
:::
:::

::: exercise 它可线性化吗 {level=1}
一个栈的历史：A 在 $[0, 2]$ 调用 `push(1)`；B 在 $[1, 3]$ 调用 `push(2)`；A 在 $[4, 5]$ 调用 `pop() → 1`；B 在 $[6, 7]$ 调用 `pop() → 1`。它可线性化吗？若 B 的第二个操作返回的是 $2$ 呢？
::: solution
不可线性化：两次弹栈在实时间上都晚于两次压栈，且 A 的弹栈先于 B 的弹栈，所以任何线性化中，栈在第一次弹栈前持有 $\{1, 2\}$，第一次弹栈去掉一个元素，第二次弹栈必须返回另一个。两次弹栈不可能都返回 $1$，因为 $1$ 只压入过一次。若 B 的弹栈返回 $2$，次序 `push(2)`、`push(1)`、`pop → 1`、`pop → 2` 合法且符合实时间（两次压栈重叠），所以历史可线性化。
:::
:::

::: exercise 标签回绕造成的 ABA {level=2 check="2^32/10^8"}
在带标签的栈里，标签有 $32$ 位，每次 CAS 成功就加一。设栈以每秒 $10^8$ 次成功操作的速率运转。一个被耽搁的线程仍可能遭遇 ABA，如果它暂停期间标签恰好前进了 $2^{32}$ 的整数倍、且同一个下标又回到栈顶。最短的暂停时长是多少秒？（填入秒数。）
::: solution
标签要 $2^{32}$ 次自增才回到同一个值，需要 $2^{32}/10^8 \approx 42.9$ 秒。一个在 `pop` 中途暂停 $43$ 秒的线程——大量换页、或进程被信号停下时都有可能——可能看到一个毫无二致的字。用 $64$ 位指针加 $64$ 位标签（双宽 CAS）后，这个间隔变成几千年。标签让 ABA 只是不太可能，而非不可能；危险指针和代际才使它不可能。
:::
:::

::: exercise 为什么是两把锁？ {#ex-two-locks level=2}
有序链表 $\text{head} \to a \to b \to c$ 上，线程 1 与 2 并发删除 $a$ 和 $b$。证明：若每次删除只锁要删的结点（其前驱的更新不加锁），两个删除都报告成功之后 $b$ 仍可能留在表里。然后解释为什么交接加锁（[[#alg-hand-over-hand]]）能防止这一点。
::: solution
线程 1 锁 $a$，找到前驱 `head`，将要置 `head.next` $\gets$ `a.next`。线程 2 锁 $b$，找到前驱 $a$，将要置 `a.next` $\gets$ `b.next` $= c$。穿插：线程 1 读 `a.next` $= b$；线程 2 置 `a.next` $\gets c$（删掉了 $b$）；线程 1 置 `head.next` $\gets b$。现在链表是 $\text{head} \to b \to c$：删除已成功的 $b$ 回来了，$a$ 没了。交接加锁下，删除 $a$ 需要同时持 `head` 与 $a$ 的锁，删除 $b$ 需要 $a$ 与 $b$ 的锁；两者都要 $a$ 的锁，所以两次删除无法重叠。后到的那个会在自己的锁下重读最新的 `next` 字段。
:::
:::

::: exercise test-and-set 解两线程共识 {#ex-tas-consensus level=2}
用一个 test-and-set 位（初始为 $0$，`TAS` 把它置 $1$ 并返回旧值）和两个寄存器，给出两线程的无等待共识协议并证明其正确。为什么同样的协议对三个线程不行？
::: solution
输入为 $v_i$ 的线程 $i \in \{0, 1\}$：把 $v_i$ 写进寄存器 `prefer[i]`；然后若 `TAS(bit)` 返回 $0$，决定 $v_i$；否则决定 `prefer[1 - i]`。

恰有一个线程的 TAS 返回 $0$，即最先执行者；称它为赢家。赢家决定自己的输入。输家的 TAS 晚于赢家的，赢家的又晚于其写 `prefer[winner]` 的，所以输家读到赢家的输入并决定它：一致性与有效性。每个线程走三步：无等待。三个线程时，输家知道自己输了，却不知道另外两者中*谁*赢了，读两个 `prefer` 寄存器也说不清——那个位只记录有人置过它。赫尔利证明：用 test-and-set 和寄存器根本不存在能解三线程共识的协议：它的共识数是 $2$。
:::
:::

::: exercise 分片计数器 {level=3}
用 C11 为至多 $64$ 个线程写一个分片计数器：`inc(t)` 对第 $t$ 格（每格填充到 $64$ 字节）做宽松的原子加，`read()` 用宽松载入把所有格子求和。把每格的访问建模为瞬时发生的原子事件（一致性硬件正是这样提供的），设 $C(\tau)$ 为到瞬时 $\tau$ 为止已执行的自增次数。证明从瞬时 $s$ 运行到瞬时 $e$ 的 `read` 返回的值是 $C$ 在 $[s, e]$ 内某瞬时取过的值——于是 `read` 是可线性化的——并解释计数器若还支持 `dec`，该论证为何失效。
::: solution
```c
#include <stdatomic.h>

typedef struct { _Alignas(64) atomic_long n; } slot;
static slot count[64];

void inc(int t) { atomic_fetch_add_explicit(&count[t].n, 1, memory_order_relaxed); }

long read(void) {
    long sum = 0;
    for (int t = 0; t < 64; t++) sum += atomic_load_explicit(&count[t].n, memory_order_relaxed);
    return sum;
}
```

设 $c_t(\tau)$ 为第 $t$ 格在瞬时 $\tau$ 的值，于是 $C(\tau) = \sum_t c_t(\tau)$，并设读取在瞬时 $\tau_t \in [s, e]$ 载入第 $t$ 格。它返回 $v = \sum_t c_t(\tau_t)$。每个 $c_t$ 从不减小，所以 $c_t(s) \le c_t(\tau_t) \le c_t(e)$，求和得 $C(s) \le v \le C(e)$。而 $C$ 是非降的整值函数、每次自增恰好变化 $1$，所以从 $C(s)$ 走到 $C(e)$ 途中，它在 $[s, e]$ 的某些瞬时取过中间的每一个整数值；特别地，它在某瞬时 $\tau^* \in [s, e]$ 取值 $v$。把读取在 $\tau^*$ 处线性化：顺序规格（"读取返回在它之前的自增次数"）得到满足，且 $\tau^*$ 落在读取的区间内。自增在它们的原子加处线性化。因此计数器是可线性化的。

有了 `dec`，格子的值不再单调，夹界失效。设两格皆 $0$ 开始。线程 $0$ 把格 $0$ 自增到 $1$（$C = 1$）；读取者载入格 $0$ 得 $1$；线程 $0$ 把格 $0$ 自减到 $0$（$C = 0$）；线程 $1$ 把格 $1$ 自增到 $1$（$C = 1$）；读取者载入格 $1$ 得 $1$。读取返回 $2$，而 $C$ 只取过 $0, 1, 0, 1$。这就是 Java 的 `LongAdder` 只承诺在无并发更新时 `sum()` 精确的原因。
:::

::: exercise 无锁不是无等待 {level=3}
构造一个两线程执行特雷伯 `push` 的调度，使一个线程的 `push` 永不完成，而另一个线程完成无穷多次操作。然后描述一个无等待栈如何借助帮助（helping）的思想、以多做功为代价保证每个操作完成。
::: solution
线程 A 开始 `push(a)`：读 `top` $= x$，置 `a.next` $= x$。A 的 CAS 之前，线程 B 完成一次 `push`（`top` 变了）。A 的 CAS 失败；A 重读 `top` 并重设 `a.next`。A 的 CAS 之前，B 完成一次 `pop` 或又一次 `push`。永远重复：每当 A 即将 CAS，B 刚巧改过 `top`，于是 A 的 CAS 永远失败，而 B 每一轮都完成一个操作。这个调度对 A 不公平但合法，而无锁只承诺*某个*线程在前进。

**用帮助做无等待设计。** 给每个线程一个**公告数组**里的格子，用于公布自己想做操作及其序号。一个线程执行自己的操作之前，先扫描数组（或按轮流挑一格），替公告者完成任何更早公告的操作，把结果记在公告者的格子里，全部用 CAS 完成，从而每个公告的操作恰好被施加一次。于是操作已经公告了一段时间的线程，必能在任意线程的 $O(p)$ 次操作之内被他人代为完成，自己的步数因此有界。这就是赫尔利通用构造的思想，也是科根（Kogan）与佩特兰克（Petrank）队列（2011）等实用无等待队列的思想；代价是每个操作都要替别人做工，所以无等待结构平均起来通常比无锁结构慢，换来的是最坏情况的界。
:::
