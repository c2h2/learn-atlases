一个程序读取长度未知的文件、构建规模未知的树，或维护一个伸缩不定的缓存，它在编译时无法知道自己需要多少内存。全局变量大小固定，局部变量在其函数返回时就消亡。除这些之外的一切，C 程序都调用 `malloc` 从**堆区**取得内存，再调用 `free` 归还，如 [[computer-systems/c-programming]] 所述。这两个函数看起来无足轻重。它们不是：`malloc` 必须在一百万个大小不一的已分配与空闲片段之中，至多用几微秒找到一块合适的空闲内存，还不能浪费太多空间；而 `free` 只拿到一个指针，却要算出这个块有多大、能否与左右邻块合并。又因为 C 对程序员全然信任，使用这两个函数的失误——忘记释放、释放两次、释放后仍在使用——属于系统软件中最常见、也最危险的缺陷之列。

本章要打开这个黑箱。我们先说明一个分配器必须做到什么、它的优劣如何度量；然后逐行搭建一个完整可用的分配器（带边界标记的隐式空闲链表、首次适配放置、拆分与合并）；接着概览实践中更好的设计——显式与分类空闲链表、伙伴系统，以及 glibc 的分配器；最后转到程序员这一侧：内存错误一览、发现它们的工具，以及垃圾回收——它让程序员根本不必再调用 `free`。

程序都在 x86-64 Linux 和 glibc 2.43 上用 GCC 15.2 以 `gcc -std=c17 -Wall -Wextra` 编译，并用 `-fsanitize=address,undefined` 作了测试。glibc 分配器的细节以 2026 年为准，版本之间会有变化。

## 分配器的任务

C 标准库提供四个函数，声明在 `<stdlib.h>` 中：

- `void *malloc(size_t n)` 返回指向至少 `n` 个未初始化字节的指针，其对齐方式适合任何类型；失败时返回 `NULL`；
- `void *calloc(size_t k, size_t size)` 对由 `k` 个 `size` 字节元素组成的数组做同样的事，检查 `k * size` 是否溢出，并把内存清零；
- `void *realloc(void *p, size_t n)` 改变 `p` 处块的大小，必要时移动该块（并复制内容）；
- `void free(void *p)` 归还 `p` 处的块；该块必须出自上面三个函数之一且尚未被释放过；`free(NULL)` 什么都不做。

在 x86-64 Linux 上，"适合任何类型的对齐"指起始地址是 16 字节的倍数。分配器管理堆区——进程虚拟地址空间（[[computer-systems/c-programming#sec-regions]]）中由它向内核索取的一个区域：传统上是用 `brk`/`sbrk` 系统调用移动数据段的末端，即**程序断点**（program break），大块则用 `mmap` 映射新的页。在这次运行中，100 字节的请求由 `brk` 堆区满足，1 MiB 的请求由它自己的 `mmap` 满足，释放时用 `munmap` 归还：

```console
$ strace -e trace=brk,mmap,munmap ./big
...
brk(0x626c6b9d3000)                     = 0x626c6b9d3000
mmap(NULL, 1052672, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS, -1, 0) = 0x71946f30f000
munmap(0x71946f30f000, 1052672)         = 0
```

::: definition 分配器的要求 {#def-allocator}
一个**显式分配器**必须：

1. 以任意次序处理任意一串分配与释放请求，其中每次释放都针对一个当前已分配的块；
2. 立即响应，不重排也不缓冲请求；
3. 把自身的数据结构保存在堆区之内（它自己不能调用 `malloc`）；
4. 返回按任何类型对齐的块；
5. 从不移走或改动已分配的块（程序持有指向块内部的指针）。
:::

第 5 条正是问题困难所在：块一旦分配就永远待在原处，分配器只能在每个请求发生的当下做出好的决策。

在这些约束之内，有两个互相竞争的目标。**吞吐量**是单位时间内处理的请求数。**内存利用率**衡量堆区中实际装着程序数据的比例。设一个块的**有效载荷**是程序索要的那些字节，$P_k$ 是前 $k$ 个请求之后所有已分配块的有效载荷之和，$H_k$ 是当时堆区的大小（在这个模型里堆区不会收缩）。$k$ 个请求之后的**峰值利用率**是

$$
U_k = \frac{\max_{i \le k} P_i}{H_k} .
$$ {#eq-util}

一个从不复用内存的分配器会非常快，但利用率却差得可怜；一个为找最完美的一块而搜索整个堆区的分配器内存用得好，但会很慢。

### 碎片

利用率不佳有两个成因。**内部碎片**指已分配的块比它的有效载荷大：因为头部、对齐，或"宁可略大也不拆分"的策略。**外部碎片**指空闲内存总量足以满足一次请求，却没有单独一块空闲块够大。内部碎片容易量化——它只取决于过去。外部碎片还取决于将来的请求，这就是分配器必须依赖启发式规则的原因。

::: example 外部碎片 {#ex-external}
一个 64 字节的堆区不带头部、以 8 字节为单位管理。程序分配八个 8 字节的块 $b_1, \ldots, b_8$，填满堆区，然后释放 $b_1, b_3, b_5, b_7$。它现在能分配 16 个字节吗？
::: solution
不能。空闲的有 $32$ 个字节，但它们分成四个孤立的 8 字节空洞，每个都夹在两个已分配块之间，而已分配的块不能被移走（第 5 条规则）。16 字节的请求只能扩大堆区，尽管堆区有一半是空闲的。释放之前峰值利用率是 $64/64 = 1$；这个请求靠把堆区扩到 $80$ 字节来满足之后，到此为止的最大有效载荷仍是 $64$，所以 $U = 64/80 = 0.8$，$32$ 个字节空闲着，却对这个请求毫无用处。一般说来任何分配器都躲不开这一点：J. M. Robson 在 20 世纪 70 年代初证明，存在某些请求序列，使得任何分配器所需的堆区都比最大存活有效载荷 $M$ 大出一个按 $\log_2 n$ 量级增长的因子，其中 $n$ 是最大与最小块大小之比。
:::
:::

::: quiz
在 glibc 下（32 字节的块）程序调用 `malloc(1)` 一百万次且从不释放任何东西。哪些说法是正确的？
- [x] 堆区需要约 32 MB，所以峰值利用率约为 $1/32$。
- [x] 浪费几乎全部来自内部碎片。
- [ ] 浪费几乎全部来自外部碎片。
- [ ] 合并能够收回浪费掉的大部分空间。
::: solution
每 1 字节的有效载荷占据一个 32 字节的块，所以 $10^6$ 字节的有效载荷需要 $3.2 \times 10^7$ 字节的堆区：$U \approx 1/32$。浪费在已分配块*内部*（头部、对齐、最小尺寸）：这是内部碎片。这里根本没有任何空闲块，所以既没有外部碎片，也没有任何东西可合并。补救的办法是换一种设计——把这些字节作为一个数组来分配，或对微小对象使用池分配器。
:::
:::

## 隐式空闲链表分配器

任何实用的分配器都必须回答四个问题。`free(p)` 怎么知道 `p` 处块的大小？怎样找到空闲块？为一个请求挑选哪个空闲块（**放置**）？过大的块分配出去后剩下的零头怎么办（**拆分**），一个块被释放时相邻的空闲块又怎么办（**合并**）？我们用最简单的完整设计回答这些问题，并用大约 70 行 C 语言实现它。它只是一个管理固定 4 KiB 数组的教学分配器，不是 `malloc` 的替代品。

::: definition 带边界标记的块格式 {#def-block}
堆区是一串连续的**块**。每个块以一个 8 字节的**头部**开始，以一个一模一样的 8 字节**尾部**结束（头尾即**边界标记**），中间装着有效载荷。标记把块的总大小——16 的倍数，所以其低四位为零——与一个放在第 0 位的**已分配位**打包在一起。指向一个块的指针（`bp`）指向它的有效载荷：位于头部之后 8 个字节，是 16 的倍数。由于每个头部都记录了块的大小，这些块构成一条**隐式空闲链表**：从任一块出发，`bp + size` 就是下一个块；经由前一块的尾部——恰在我们头部之前——也能找到前一个块。
:::

两个特殊的块免除了边界情形：最前面一个 16 字节的已分配**首部块**（prologue，只有头部和尾部），最后面一个大小为 0 的已分配**尾部块**（epilogue）头部。最小的真正块是 32 字节：头部、尾部，外加 16 字节有效载荷，以保持有效载荷的对齐。

```c
/* 一个玩具分配器：隐式空闲链表、边界标记、首次适配（仅供教学）。 */
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>

#define HEAP_SIZE 4096
#define ALIGN 16
#define WSIZE 8                               /* 头部和尾部的大小 */
static _Alignas(16) unsigned char heap[HEAP_SIZE];

/* 标记打包了块大小（16 的倍数）和一个已分配位。 */
static uint64_t *hdr(unsigned char *bp) { return (uint64_t *) (bp - WSIZE); }
static size_t size_of(unsigned char *bp) { return *hdr(bp) & ~(uint64_t) 0xf; }
static int alloc_of(unsigned char *bp) { return (int) (*hdr(bp) & 1); }
static uint64_t *ftr(unsigned char *bp) { return (uint64_t *) (bp + size_of(bp) - 2 * WSIZE); }
static unsigned char *next_bp(unsigned char *bp) { return bp + size_of(bp); }
static unsigned char *prev_bp(unsigned char *bp) {
    return bp - (*(uint64_t *) (bp - 2 * WSIZE) & ~(uint64_t) 0xf);
}
static void set(unsigned char *bp, size_t size, int alloc) {
    *hdr(bp) = size | (uint64_t) alloc;
    *ftr(bp) = size | (uint64_t) alloc;
}

static unsigned char *first;                  /* 第一个真正的块 */

void toy_init(void) {
    /* 布局：pad(8) | 首部块 hdr,ftr（16，已分配）| 空闲块 | 尾部块 hdr（0，已分配） */
    unsigned char *pro = heap + 2 * WSIZE;    /* 首部块的有效载荷地址 */
    set(pro, 16, 1);
    first = pro + 16;
    set(first, HEAP_SIZE - 32, 0);            /* 一个大空闲块 */
    *hdr(next_bp(first)) = 0 | 1;             /* 尾部块：大小 0，已分配 */
}
```

这些辅助函数就是全部的数据结构：`hdr` 与 `ftr` 定位标记，`size_of` 与 `alloc_of` 解码它们，`next_bp` 与 `prev_bp` 沿链表移动。`toy_init` 之后，堆区里有：8 字节对齐填充、首部块、一个 $4096 - 32 = 4064$ 字节的空闲块，以及最后 8 个字节里的尾部块头部。（这里通过 `uint64_t *` 指针访问该数组是可以接受的，因为 `heap` 对齐合适且别无他用；生产级的分配器对 C 的别名规则必须更加小心。）

### 放置、拆分与合并

::: algorithm 带拆分的首次适配分配 {#alg-firstfit}
要分配 $n$ 个字节：

1. 若 $n = 0$，返回 `NULL`。计算所需的块大小 $s = \lceil (n + 16)/16 \rceil \cdot 16$：有效载荷加上头部和尾部，向上取到对齐的倍数。
2. 从第一个块开始向尾部块遍历各个块。首次遇到满足 $\text{size}(b) \ge s$ 的空闲块 $b$ 时：
   1. 若余下的 $r = \text{size}(b) - s$ 不小于最小块大小（32），就**拆分**：把 $b$ 的前 $s$ 个字节标为已分配块，剩下的 $r$ 个字节标为空闲块。
   2. 否则把整个 $b$ 分配出去（多出的部分成为内部碎片）。
   3. 返回 $b$ 的有效载荷指针。
3. 若没有块装得下，宣告失败（真正的分配器会用 `sbrk` 或 `mmap` 扩大堆区再试）。
:::

**首次适配**取第一个够大的块。**下次适配**每次搜索从上一次结束的地方开始，更快，但往往碎片更多；**最佳适配**查看每一个空闲块，取够大的里面最小的那个，内存利用得好，却必须搜索整个链表。对真实程序的研究（尤其是 Wilson、Johnstone、Neely 和 Boles 在 1995 年的工作）发现，只要实现得好，首次适配与最佳适配的碎片程度相当，且都不高。

一个块被释放时，应与它的空闲邻块合并成一个更大的空闲块；否则堆区很快会由许多小空闲块组成——它们加起来能满足一个大请求，单个却都不能（**虚假碎片**）。边界标记让这种合并非常廉价。

::: theorem 常数时间的合并 {#thm-coalesce}
只要每个块两端都有边界标记（并且首部块与尾部块就位），释放一个块并与任何空闲邻块合并只需 $O(1)$ 时间，与块的数目无关。
:::

::: proof
设 $b$ 为被释放的块。它的后继始于 $b + \text{size}(b)$，其后继的头部给出后继的大小与状态；前驱的尾部位于 $b$ 的头部之前紧邻的 8 个字节里，给出前驱的大小与状态，由此前驱始于 $b - \text{size}$。多亏首部块与尾部块，两个邻块总是存在，且在堆区两端都被标为已分配。共有四种情形，每种都只用常数次标记的读写即可处理：

1. 两邻块均已分配：把 $b$ 标为空闲（写它的头部和尾部）。
2. 后继空闲：合并后的块始于 $b$，大小为 $\text{size}(b) + \text{size}(\text{succ})$；在 $b$ 处写头部，在后继末尾写尾部。
3. 前驱空闲：合并后的块始于前驱，大小为 $\text{size}(\text{pred}) + \text{size}(b)$；写前驱的头部和 $b$ 的尾部。
4. 两者皆空闲：合并后的块从前驱的头部延伸到后继的尾部，大小为三个块之和。

每种情形的结果都是一个合法块，头部与尾部一致；并且只要合并之前不存在相邻的空闲块，合并之后也不会有：于是对操作序列归纳即知，堆区中永远不会出现两个相邻的空闲块。
:::

下面的代码依照证明实现（在 `coalesce` 中，情形 2–4 由两条 `if` 语句处理，因为大小的计算方式相同）：

```c
static unsigned char *coalesce(unsigned char *bp) {
    int prev_alloc = alloc_of(prev_bp(bp)), next_alloc = alloc_of(next_bp(bp));
    size_t size = size_of(bp);
    if (!next_alloc) size += size_of(next_bp(bp));               /* 与后继合并 */
    if (!prev_alloc) { bp = prev_bp(bp); size += size_of(bp); }  /* 与前驱合并 */
    set(bp, size, 0);
    return bp;
}

void *toy_malloc(size_t n) {
    if (n == 0 || n > HEAP_SIZE) return NULL;
    size_t need = (n + 2 * WSIZE + ALIGN - 1) & ~(size_t) (ALIGN - 1);  /* + 头部、尾部 */
    for (unsigned char *bp = first; size_of(bp) > 0; bp = next_bp(bp)) {
        if (!alloc_of(bp) && size_of(bp) >= need) {               /* 首次适配 */
            size_t rest = size_of(bp) - need;
            if (rest >= 32) {                                      /* 拆分 */
                set(bp, need, 1);
                set(next_bp(bp), rest, 0);
            } else {
                set(bp, size_of(bp), 1);
            }
            return bp;
        }
    }
    return NULL;                                                   /* 内存耗尽 */
}

void toy_free(void *p) {
    if (p == NULL) return;
    unsigned char *bp = p;
    set(bp, size_of(bp), 0);
    coalesce(bp);
}
```

（`set` 先写头部，然后用*新的*大小去找尾部该写在哪里，这就是 `coalesce` 里 `set(bp, size, 0)` 能把尾部正确写到合并后块末端的原因。）

::: example 追踪玩具分配器 {#ex-toy}
一个测试驱动程序在每次操作之后把堆区打印成 `[size, a/f]` 块的列表：

```c
static void show(const char *label) {
    printf("%-12s", label);
    for (unsigned char *bp = first; size_of(bp) > 0; bp = next_bp(bp))
        printf(" [%zu%s]", size_of(bp), alloc_of(bp) ? "a" : "f");
    printf("\n");
}

int main(void) {
    toy_init();                          show("init");
    char *a = toy_malloc(10);            show("a = 10");
    char *b = toy_malloc(100);           show("b = 100");
    char *c = toy_malloc(30);            show("c = 30");
    printf("a %% 16 = %zu\n", (size_t) ((uintptr_t) a % 16));
    toy_free(b);                         show("free b");
    toy_free(a);                         show("free a");
    char *d = toy_malloc(120);           show("d = 120");
    printf("d == a: %d\n", d == a);
    toy_free(c); toy_free(d);            show("free c, d");
    return 0;
}
```

解释它输出的每一行。

```console
$ gcc -std=c17 -Wall -Wextra -fsanitize=address,undefined -o toy toy.c && ./toy

a = 10       [32a] [4032f]
b = 100      [32a] [128a] [3904f]
c = 30       [32a] [128a] [48a] [3856f]
a % 16 = 0
free b       [32a] [128f] [48a] [3856f]
free a       [160f] [48a] [3856f]

```
::: solution
块的大小遵循 [[#alg-firstfit]] 的第 1 步：$10 + 16 = 26 \to 32$，$100 + 16 = 116 \to 128$，$30 + 16 = 46 \to 48$。每个请求都从那个大空闲块的前端切出，块每次都被拆分。`a` 的有效载荷按 16 字节对齐，符合要求。

释放 `b` 是 [[#thm-coalesce]] 的情形 1（两邻块均已分配）：它只是变成一个 128 字节的空闲块。释放 `a` 是情形 2：它的后继 `b` 是空闲的，于是两者合并成一个 160 字节的空闲块。`d = 120` 需要的大小是 $120 + 16 = 136 \to 144$。首次适配先遇到 160 字节的块；余下的 $16$ 个字节低于最小块大小，所以整个块被分配出去，`d` 恰好拿到 `a` 用过的地址，附带 16 字节的内部碎片。最后，释放 `c` 使它和末端的大块合并（情形 2），释放 `d` 又与之合并（又是情形 2），恢复了最初那个 4064 字节的单一空闲块。AddressSanitizer 没有报告任何错误。
:::
:::

## 实际中的分配器

隐式链表使 `malloc` 的时间与*所有*块（已分配的和空闲的）数目成正比：对有几百万个块的堆区来说实在太慢。真正的分配器把空闲块组织得更好。

**显式空闲链表。** 空闲块的有效载荷反正没人用，可以拿来存放指针：只把空闲块串成一条双向链表，`next` 和 `prev` 存在有效载荷里。这样分配的时间与*空闲*块的数目成正比。释放的块可以插在链表头部（**LIFO** 次序，常数时间），也可以按地址次序插入（这使首次适配的碎片更少，代价是释放时要搜索一遍）。

**分类空闲链表。** 维护一个空闲链表数组，每个**大小类别**一条（例如 32、48、64、…、512 字节，再往后是 2 的幂）。$n$ 字节的请求只搜索自己所属类别的链表，找不到再搜更大的类别。对小尺寸使用精确的类别，分配一个小块就是从链表头部弹出，只需常数时间。几乎所有快速分配器都按这种方式构建；在类别内部做最佳适配，接近于整体的最佳适配。

::: example 为什么隐式链表太慢 {#ex-cost}
一个长期运行的程序有 $10^6$ 个已分配的块，另有 $1000$ 个大小各异、散布在整个堆区中的空闲块。最坏情况下，隐式链表、显式空闲链表、以及有 100 个大小类别的分类链表分别大约要 `malloc` 检查多少个块？
::: solution
隐式链表要遍历*所有*块，无论已分配还是空闲，直到找到合适的：多达 $10^6 + 1000 \approx 10^6$ 个块，每一步都是一次很可能缓存缺失的内存访问（[[computer-systems/memory-hierarchy]]）——按每次缺失约 100 ns 算，最坏情况一次调用约需一百毫秒。显式链表只访问空闲块：至多 $1000$ 个。分类链表中，请求先看自己大小类别的那条链表；若 1000 个空闲块分散在 100 个类别里且类别正好吻合，链表第一个块就合适，搜索是常数时间的弹出。（若该类别为空，分配器接着找下一个更大的非空类别；用一个非空类别位图，几条指令就能找到。）$10^6$、$10^3$、$1$ 这几个数量级的差别，正是所有产品级分配器都采用分类的原因。
:::
:::

**伙伴系统。** 一切块大小都是 2 的幂。一个大小 $2^k$ 的空闲块被分成两个大小 $2^{k-1}$ 的"伙伴"；一个块被释放时，若它的伙伴空闲就与之合并。一个块的伙伴只要翻转它地址中的一位就能找到（$2^k$ 字节块的地址是 $2^k$ 的倍数，其伙伴的地址恰在第 $k$ 位上不同），所以拆分与合并都很快；代价是内部碎片最多可达每个块的近一半。例如，在 16 KiB 的伙伴堆区中，一个 3000 字节的请求把 16 KiB 块分成两个 8 KiB 伙伴，再把其中一个分成两个 4 KiB 伙伴，分配一个 4 KiB 的块——$4096 - 3000 = 1096$ 个字节成了内部碎片。若该块位于偏移 `0x3000`，它的伙伴就在 `0x3000` XOR `0x1000` $=$ `0x2000`；两者都空闲时合并成 `0x2000` 处的 8 KiB 块，而这个块的伙伴 `0x2000` XOR `0x2000` $= 0$，正是原堆区的另一半。Linux 用伙伴分配器管理物理页。

::: application glibc 的 malloc
GNU C 库的分配器（ptmalloc，源自 Doug Lea 的 dlmalloc）管理这样的**块**（chunk）：8 字节的大小字段位于有效载荷之前；记录前一个块大小的那个字段与前一块有效载荷的末尾重叠，只在前一块空闲时才使用。所以一个已分配块的开销只有 8 个字节，最小块是 32 个字节，大小都是 16 的倍数——上面的图显示了这一点，下面这个程序也予以证实：

```c
#define _GNU_SOURCE                  /* 为了 malloc_usable_size */
#include <malloc.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>

int main(void) {
    size_t sizes[] = {1, 24, 25, 40, 100};
    char *p[5];
    for (int i = 0; i < 5; i++)      /* 先全部完成分配：printf 也会分配 */
        if ((p[i] = malloc(sizes[i])) == NULL) return 1;
    for (int i = 0; i < 5; i++) {
        printf("malloc(%3zu): usable %3zu, address mod 16 = %zu",
               sizes[i], malloc_usable_size(p[i]), (size_t) ((uintptr_t) p[i] % 16));
        if (i > 0) printf(", %3td bytes after previous", p[i] - p[i - 1]);
        printf("\n");
    }
    for (int i = 0; i < 5; i++) free(p[i]);
    return 0;
}
```

```console
$ ./usable
malloc(  1): usable  24, address mod 16 = 0
malloc( 24): usable  24, address mod 16 = 0,  32 bytes after previous
malloc( 25): usable  40, address mod 16 = 0,  32 bytes after previous
malloc( 40): usable  40, address mod 16 = 0,  48 bytes after previous
malloc(100): usable 104, address mod 16 = 0,  48 bytes after previous
```

空闲的块存放在分类**箱**（bins）中；自 glibc 2.26（2017）起，每个线程还为每个大小保有一个存放最近释放块的小型缓存（**tcache**），于是大多数小分配无须加锁。超过某个阈值（默认 128 KiB，动态调整）的请求直接由 `mmap` 服务。其他广泛使用的分配器——jemalloc、tcmalloc、mimalloc——也建立在同样的思想之上，只是更加强调多线程可扩展性。
:::

## 内存错误

分配器的接口很简单，误用它的方式却都是已知的。它们全都是**未定义行为**（[[computer-systems/c-programming#def-ub]]），而且许多悄无声息，直到远离出错地点的地方酿成祸端。

| 错误 | 例子 | 典型后果 |
|---|---|---|
| **内存泄漏** | 已分配的块未经 `free` 就变为不可达 | 内存占用不断增长，直到程序被杀死 |
| **释放后使用** | `free(p)` 之后仍读写 `*p` | 读到陈旧或已被复用的数据；写入会破坏别的对象或分配器的链表 |
| **重复释放** | `free(p); free(p);` | 破坏空闲链表；glibc 通常能检测到并中止程序 |
| **非法释放** | `free(p + 1)`，或释放栈对象、全局对象 | 破坏分配器的数据甚至使其崩溃 |
| **堆缓冲区溢出** | 向块末尾之外写入 | 覆盖下一个块的头部或数据 |
| **读取未初始化内存** | `malloc` 之后未写入就先读 | 值不确定（需要零时用 `calloc`） |
| **大小不匹配** | 写成 `malloc(n)` 而非 `malloc(n * sizeof *p)` | 缓冲区溢出 |

GCC 15 能在编译期抓住最简单的情形（`-Wuse-after-free`），glibc 也能在运行期发现一些——下面这次的重复释放就是被它的 tcache 检查抓住的：

```console
$ ./df
free(): double free detected in tcache 2
Aborted
$ echo $?
134
```

（退出状态 $134 = 128 + 6$ 表示进程死于 `SIGABRT`；见 [[computer-systems/exceptions-processes]]。）但分配器的检测只是安全网，不是保证。**AddressSanitizer** 能发现多得多的错误：它在每个块周围划出"红区"，推迟已释放内存的复用，并检查每一次读写。对于释放后使用：

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

int main(void) {
    char *name = malloc(16);
    if (name == NULL) return 1;
    strcpy(name, "Ada");
    free(name);
    printf("%s\n", name);          /* 错误：释放后使用 */
    return 0;
}
```

```console
$ gcc -std=c17 -Wall -Wextra -g -fsanitize=address -o uaf uaf.c
uaf.c: In function 'main':
uaf.c:10:5: warning: pointer 'name' used after 'free' [-Wuse-after-free]
$ ./uaf
==3343680==ERROR: AddressSanitizer: heap-use-after-free on address 0x7807eade0010 ...
READ of size 2 at 0x7807eade0010 thread T0
    #0 ... in puts
    #1 ... in main uaf.c:10
freed by thread T0 here:
    #0 ... in free
    #1 ... in main uaf.c:9
previously allocated by thread T0 here:
...
```

（输出有删节。）报告会给出这次非法访问，以及该块在哪里被释放、在哪里被分配。它的泄漏检查器（LeakSanitizer；在 Linux 上随 AddressSanitizer 启用）会报告程序退出时仍不可达的块：对一个分配一个字符串的三份 10 字节副本却从不释放的循环，它报告 `Direct leak of 30 byte(s) in 3 object(s)`。Valgrind 的 Memcheck 无须重新编译就能发现同样几类错误，只是拖慢得更多。

::: warning `free` 不会改变指针
`free(p)` 之后，变量 `p` 里仍是同一个地址——一个**悬空指针**。之后任何使用都是释放后使用，而且这个缺陷常常测不出来，因为被释放的内存在被别人复用之前还留着旧数据。当指针还在作用域里时就应在释放后把它置为 `NULL`（`free(p); p = NULL;`），这样以后误用会立刻崩溃，而不是悄悄破坏内存；并且要给每个堆对象明确指定一个**所有者**，由它负责恰好释放一次。注意：若别处还存有这个指针的其他副本，只把这一个置 `NULL` 并无帮助。
:::

::: application 堆错误与安全性
释放后使用和堆溢出是浏览器与操作系统中被利用得最频繁的漏洞类别之列。从概念上讲，危险在于已释放的内存会被*复用*：如果程序释放了一个对象却仍拿着指向它的旧指针，而分配器随后把同一块内存交给内容受攻击者影响的另一个新对象，这个旧指针读写的就是攻击者选定的数据——比如一个函数指针。防御在若干层面展开：所有权清晰的设计与语言（或有垃圾回收、或编译期所有权检查，[[programming-languages]]）；开发期的消毒器与模糊测试；以及**加固过的分配器**——它校验自己的元数据、随机化放置位置、在复用前隔离已释放的内存，并且自 glibc 2.32（2020）起还会搅乱存放在已释放块中的空闲链表指针（"safe-linking"），使其更难以被破坏。一如既往：缓解措施只是抬高利用的成本；只有修好缺陷才真正消除危险。
:::

## 垃圾回收

`free` 的替代方案是不去调用它。**垃圾回收器**是一种分配器：当程序再也用不到某些块时，它自动把这些块收回。Python、Java、Go、JavaScript 以及大多数其他现代语言都使用垃圾回收。

::: definition 可达性 {#def-reachable}
把内存看成一个有向的**可达性图**：它的顶点是各个已分配的块，外加一组**根**——堆区之外可能存放指向堆区内指针的位置（寄存器、栈槽、全局变量）；当 $u$ 的某个字里存有指向块 $v$ 的指针时，就有一条从 $u$ 到 $v$ 的边。若存在一条从某个根到这个块的路径，这个块就是**可达的**，否则它就是**垃圾**。
:::

一个垃圾块永远不可能再被用到，因为程序没有办法得到指向它的指针；因此回收器可以释放它。**标记-清除**回收器做的正是这件事：**标记**阶段从根出发做一次图搜索（深度优先或广度优先，如 [[data-structures]] 所述），给到达的每个块置上标记位；**清除**阶段遍历堆区——用隐式链表就够了——释放每一个已分配但未标记的块。

::: widget graph
nodes: roots@0,2; A@2,3; B@2,1; C@4,3; D@4,1; E@6,2; F@6,0
edges: roots>A; roots>B; A>C; B>C; C>E; F>D; D>F
algorithm: bfs
start: roots
caption: 一个可达性图：顶点 `roots` 代表寄存器、栈和全局变量，箭头 $u \to v$ 表示块 $u$ 里存有指向块 $v$ 的指针。请执行这次广度优先搜索——它正是标记-清除回收器的标记阶段。它会标记 $A$、$B$、$C$ 和 $E$。块 $D$ 与 $F$ 互相指向对方，但没有任何可达的东西指向它们：它们是垃圾，清除阶段会把它们释放。只依赖**引用计数**的回收器则永远不会释放它们，因为每个的计数仍为 1——这正是 CPython 在引用计数之外还要加上循环检测回收器的经典弱点。
:::

::: example 引用计数与标记的比较 {#ex-refcount}
对图中的每个块，给出它的**引用计数**（指向它的指针条数）。然后程序把根中指向 $A$ 与指向 $B$ 的指针覆写掉。引用计数回收器会释放哪些块？标记-清除又会释放哪些？
::: solution
数入边：$A$：1（来自根），$B$：1，$C$：2（来自 $A$ 和 $B$），$D$：1（来自 $F$），$E$：1（来自 $C$），$F$：1（来自 $D$）。引用计数回收器在一个块的计数降为 $0$ 时释放它，然后把被释放块所指向的各块的计数逐一减一。

根中指向 $A$ 和 $B$ 的指针被覆写后，两者的计数降为 $0$，于是双双被释放；释放它们使 $C$ 的计数从 $2$ 减到 $0$，于是 $C$ 被释放，这又使 $E$ 的计数减为 $0$，$E$ 随之被释放。$D$ 与 $F$ 的计数却仍是 $1$——它们互相维持着对方"活着"——永远不会被释放：这就泄漏了。标记-清除则什么都标记不到（根现在不指向任何块），清除阶段把六个块全部释放。引用计数及时、增量地回收内存，因而被采用（CPython、Swift、C++ 的 `shared_ptr`），但对带环的结构，它需要一个后备的循环回收器或程序员的自律（弱引用）。
:::
:::

为 C 程序做回收要困难得多，因为 C 并不指明哪些字是指针：一个恰好形如地址的整数无法与指针区分开。针对 C 的**保守式**回收器（Boehm–Demers–Weiser 回收器，1988）把每一个可能是指向堆内指针的字都当作指针对待；它们可能让一些垃圾继续存活，但绝不会释放一个可达的块。为垃圾回收而设计的语言能给回收器精确的类型信息；现代回收器则是*分代的*（大多数对象朝生夕死，所以年轻对象被频繁回收）和*并发的*（与程序同时运行，把停顿压得很短）。它们的设计属于 [[programming-languages]] 与 [[compilers]] 的内容。

::: history
动态存储分配的历史可以追溯到最早的列表处理语言。麦卡锡（McCarthy）的 LISP（1960 年发表）引入了垃圾回收，用的正是标记-清除；George Collins 在同一年描述了引用计数。高德纳（Knuth）的《计算机程序设计艺术》（*The Art of Computer Programming*）第 1 卷（1968）分析了首次适配与最佳适配，提出了实现常数时间合并的**边界标记**法，并描述了伙伴系统（由 Harry Markowitz 发明、Kenneth Knowlton 于 1965 年发表）。Doug Lea 的 dlmalloc（1987）——glibc 的 ptmalloc 的基础——使分类箱广为流传。Paul Wilson、Mark Johnstone、Michael Neely 和 David Boles 的综述《Dynamic Storage Allocation: A Survey and Critical Review》（1995）则利用真实程序的执行踪迹，重新评估了几十年来的分配器研究。
:::

## 后续内容

分配器与计算机科学其余部分的许多地方相连。空闲链表结构就是 [[data-structures]] 里的链表和树；可增长数组的摊还分析（[[algorithms]]）解释了为什么 `realloc` 按常数因子增长是高效的。[[operating-systems]] 会讲内核自己的分配器（管理物理页的伙伴分配器和管理内核对象的 slab 分配器），以及 `brk` 和 `mmap` 如何操纵虚拟内存。[[programming-languages]] 深入研究垃圾回收，以及让 Rust 这类语言在编译期杜绝释放后使用的所有权类型；[[security]] 则讲堆的利用及其缓解措施。

::: summary
- `malloc`、`calloc`、`realloc` 和 `free` 管理堆区；堆区由 `brk` 和 `mmap` 从内核获得；在 x86-64 上块按 16 字节对齐，一经分配永不移位。
- 分配器在**吞吐量**与**峰值利用率** $U_k = \max_{i\le k} P_i / H_k$ 之间权衡；利用率不佳来自**内部**碎片（开销、向上取整）与**外部**碎片（空闲内存被分割得每块都不够用）。
- 带**边界标记**（大小与已分配位记录在头部和尾部中）的**隐式空闲链表**支持首次/下次/最佳适配的放置、拆分，以及常数时间内合并相邻空闲块（[[#thm-coalesce]]）。
- 实际分配器使用**显式**与**分类**空闲链表（大小类别）或**伙伴**系统；glibc 的块开销 8 字节、最小块 32 字节，使用分类箱、每线程缓存，大块交给 `mmap`。
- 内存错误——泄漏、释放后使用、重复与非法释放、堆溢出、读未初始化——都是未定义行为；用 `-Wall -Wextra`、AddressSanitizer、LeakSanitizer 和 Valgrind 找出它们，用明确的所有权防止它们。
- **垃圾回收**自动释放不可达的块：从根标记，清除其余；单靠引用计数无法回收带环结构；保守式回收器对 C 也管用。
:::

## 习题

::: exercise 玩具分配器的块大小 {level=1 check="80"}
本章的玩具分配器为 `toy_malloc(50)` 使用多大的块？这个块中有多少字节是开销或填充？（输入块大小。）
::: solution
由 [[#alg-firstfit]] 的第 1 步，$50 + 16 = 66$，向上取到 16 的倍数：$80$。其中 $16$ 个字节是头部和尾部，$80 - 16 - 50 = 14$ 个字节是填充，内部碎片合计 $30$ 个字节。
:::
:::

::: exercise glibc 的可用大小 {level=1 check="72"}
按图中所示的规则（8 字节的大小字段加上请求量，向上取到 16 的倍数，最小 32），在 x86-64 的 glibc 下 `malloc_usable_size(malloc(60))` 返回什么？（输入字节数。）
::: solution
$60 + 8 = 68$，向上取到 16 的倍数是 $80$——即块的大小。可用大小是块大小减去 8 字节的大小字段：$72$。（*下一个*块的前块大小字段的 8 个字节在本块分配期间是可用的，所以可用大小并不是 $80 - 16$。）在测试系统上运行 `malloc_usable_size(malloc(60))` 打印 $72$。
:::
:::

::: exercise 峰值利用率 {level=1 check="0.625"}
一个 256 字节的堆区（永不增长）依次服务以下请求：分配 64，分配 96，释放那 64，分配 32。只计有效载荷，计算峰值利用率 $U_4$。（以小数形式输入。）
::: solution
各次请求之后的有效载荷：$P_1 = 64$，$P_2 = 160$，$P_3 = 96$，$P_4 = 128$。最大值为 $160$，且 $H_4 = 256$，由 [[#eq-util]] 得 $U_4 = 160/256 = 0.625$。峰值利用率用的是到此为止的*最大*有效载荷，而不是当前的载荷（$128/256 = 0.5$），因为堆区必须大到足以应付那个峰值。
:::

::: exercise 首次适配与最佳适配 {level=2 check="3"}
一个空闲链表按地址次序含有大小为 40、96、64、128 和 48 字节的空闲块（块大小已含全部开销）。依次到达对 48、32、112 字节块的请求；只要余下的部分不小于 16 就允许拆分。首次适配和最佳适配各用哪个块满足每个请求？最佳适配之后还剩下几个空闲块？（输入那个数字。）
::: solution
**首次适配。** 48：第一个 $\ge 48$ 的块是 96，拆成 48（分配出去）和 48 空闲。链表：40、48、64、128、48。32：第一个 $\ge 32$ 的块是 40，余下 8 小于 16，于是 40 个字节全部用来分配。链表：48、64、128、48。112：128 那个块，余下 16，拆分。链表：48、64、16、48——四个空闲块。

**最佳适配。** 48：$\ge 48$ 的最小块是末尾那个 48，正好用完。链表：40、96、64、128。32：$\ge 32$ 的最小块是 40，余下 8，整块分配。链表：96、64、128。112：只有 128 装得下，拆成 112 和 16。链表：96、64、16——**三个**空闲块，而 96 和 64 字节的大块为将来的请求原封不动地留了下来。
:::

::: exercise 是哪一种合并情形？ {level=2}
在 [[#ex-toy]] 的追踪中，假如程序不是先释放 `b` 再释放 `a`，而是先释放 `a`，再释放 `c`，最后释放 `b`。给出每次 `free` 之后的堆区，并说明每次用到 [[#thm-coalesce]] 的哪一种情形。
::: solution
初始：`[32a] [128a] [48a] [3856f]`。释放 `a`：前驱是首部块（已分配），后继 `b` 已分配，所以是情形 1：`[32f] [128a] [48a] [3856f]`。释放 `c`：前驱 `b` 已分配，后继是那个 3856 字节的空闲块，所以是情形 2：`[32f] [128a] [3904f]`。释放 `b`：两侧邻块都空闲，情形 4：合成一个 $32 + 128 + 3904 = 4064$ 字节的块，`[4064f]`。
:::

::: exercise 找出错误 {level=2}
指出这个函数中的每一个内存错误，并改正它。

```c
char *join(const char *a, const char *b) {
    char *r = malloc(strlen(a) + strlen(b));
    strcpy(r, a);
    strcat(r, b);
    free(r);
    return r;
}
```
::: solution
(1) 分配少了一个字节：结果需要 `strlen(a) + strlen(b) + 1` 个字节来容纳终止符 `'\0'`，所以 `strcat` 会向块末尾之外多写一个字节——堆缓冲区溢出。(2) `malloc` 的结果没有检查是否为 `NULL`。(3) 块被释放之后又当作返回值交出去：调用方拿到的是悬空指针，任何使用都是释放后使用。(4) 若长度受攻击者控制且非常大，这个加法可能溢出。改正如下：

```c
#include <stdlib.h>
#include <string.h>

char *join(const char *a, const char *b) {     /* 调用方必须释放结果 */
    size_t la = strlen(a), lb = strlen(b);
    if (la > SIZE_MAX - lb - 1) return NULL;   /* 大小会溢出 */
    char *r = malloc(la + lb + 1);
    if (r == NULL) return NULL;
    memcpy(r, a, la);
    memcpy(r + la, b, lb + 1);                 /* 连同 b 的终止符一起 */
    return r;
}
```
:::

::: exercise 一个玩具 realloc {level=3}
为玩具分配器实现 `void *toy_realloc(void *p, size_t n)`，语义与 `realloc` 一致：`p` 为 `NULL` 时相当于 `toy_malloc`；$n = 0$ 时释放并返回 `NULL`；块本来已经够大时原样返回；否则分配一个新块，复制旧内容，再释放旧块；失败时必须让旧块原封不动。再对它进行测试。
::: solution
```c
#include <string.h>

void *toy_realloc(void *p, size_t n) {
    if (p == NULL) return toy_malloc(n);
    if (n == 0) { toy_free(p); return NULL; }
    size_t have = size_of(p) - 2 * WSIZE;          /* 当前有效载荷容量 */
    if (n <= have) return p;                       /* 缩小：保留原块 */
    void *q = toy_malloc(n);
    if (q == NULL) return NULL;                    /* 旧块原封不动 */
    memcpy(q, p, have);
    toy_free(p);
    return q;
}
```

测试如下：分配 `s = toy_malloc(10)` 存入 `"systems"`，再分配 `x = toy_malloc(10)`（使 `s` 不能原地增长），然后 `s = toy_realloc(s, 200)`；程序打印 `systems`，堆区为 `[32f] [32a] [224a] [3776f]`：旧的 32 字节块已空闲，`x` 未受影响，新块装着 $200 + 16 = 216 \to 224$ 个字节。把两者都释放之后，堆区恢复为 `[4064f]`；AddressSanitizer 没有报告任何错误。一种改进是：当一个块的后继空闲且足够大时就原地扩张这个块，免去复制；glibc 会这样做，对由 `mmap` 服务的块，它甚至能用 `mremap` 无复制地扩张。
:::

::: exercise 去掉尾部 {level=3}
尾部使每个块多付出 8 个字节。证明：若每个头部在又一个低位比特中保存*前一个*块是否已分配，则已分配的块不需要尾部。说明玩具分配器的每个操作必须如何改变，以及新的最小块大小是多少。
::: solution
读尾部的只有 `prev_bp`，且发生在合并期间，目的是找到*前一个*块的起点——而合并只在前一块空闲时才需要它。所以只有空闲块需要尾部，只要我们仅凭当前块就能判断前一块是否空闲。把这一点存在每个头部的第 1 位（"prev-alloc" 位；大小是 16 的倍数，所以第 1–3 位空着可用）。

改动如下：`set` 对已分配的块只写头部，并保留 prev-alloc 位；对空闲块则写头部和尾部。每当某个块的分配状态改变，分配器还必须更新*下一个*块头部中的 prev-alloc 位。`coalesce` 读被释放块头部的 prev-alloc 位：若它表明前一块已分配，就根本不碰前驱；若空闲，则前驱必有尾部，合并照旧进行。后继的状态仍从后继自己的头部读取。

已分配的块如今只需要一个 8 字节的头部，它的有效载荷可以一直延伸到块的末尾：最小块仍是 32 字节，因为一个*空闲*块至少要装下头部、尾部和（在显式链表分配器中）两个链表指针——$8 + 8 + 16 = 32$；但已分配块的开销从 16 个字节降到了 8 个字节。这正是 glibc 采用的方案：它的块"size"字段里有一个 `PREV_INUSE` 位，而前块大小字段只在前一块空闲时才有效。
