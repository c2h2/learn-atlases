"Put the red blocks in a row in front of the blue bowl, five centimetres apart." A skill planner of the kind in [[llm-robot-control/grounded-task-planning]] could handle this only if someone had written a `make_row` skill. A person programming the robot would write four lines: find the bowl, find the red blocks, compute a target for each block, loop over them calling pick and place. Language models write such lines fluently, and that observation is the basis of **code as policies**: instead of choosing from a menu of skills, the model writes a short program against a robot API, and the program — with loops, arithmetic and conditionals — is the policy. This chapter shows how to design the API so that generated code is short and checkable, how to prompt for it, what generated code looks like, and above all how to run code written by a model without trusting it: static checks, a restricted namespace, process isolation and timeouts, a dry run that records intended actions, and limit checks on every motion before it reaches the arm. The general techniques of code-writing agents are covered in the LLM Atlas chapter [Code generation and execution](/learn/llm/lesson.php?c=agents&l=code-agents); here we specialise them to a machine that moves.

## Why code? {#sec-why-code}

Three kinds of instruction are awkward as skill sequences and natural as programs.

- **Arithmetic and spatial patterns.** "A row five centimetres apart", "a 4 × 3 grid with 30 mm pitch", "halfway between the two fixtures", "rotate it 90 degrees". The numbers must be computed from perceived poses, and a program computes them exactly.
- **Iteration over what is perceived.** "Every red block", "all screws that are not yet tightened", "until the tray is full". The number of steps is not known when the plan is written.
- **Conditionals.** "If the part is upside down, flip it first", "skip any that are scratched".

The original **Code as Policies** work (Liang et al., 2022) showed that a language model prompted with a few examples of instructions and the code that carries them out could generate new programs for tabletop manipulation, drawing and mobile robots, including spatial-geometric reasoning ("a bit to the left", "the corner closest to the bowl") that the model expressed through calls to numerical libraries.

::: definition Code-as-policy {#def-cap}
A **code-as-policy** (in the original paper, a *language model program*) is a program $P$, generated by a language model from an instruction and a prompt, that calls a fixed robot API $\mathcal A$ of perception and action functions. Executing $P$ maps observations, obtained through perception calls, to actions, issued through action calls; the program is therefore a policy. The model never issues actions directly; every effect on the world passes through a function of $\mathcal A$.
:::

The last sentence of the definition is what makes the approach safe enough to use: the API is the narrow waist through which all effects pass, so all checks can be placed there.

## Designing the robot API {#sec-api}

The quality of generated code depends more on the API than on the model. An API designed for a person — dozens of functions, configuration objects, implicit units — produces long programs with many places to go wrong. An API designed for generation is small, explicit and forgiving in the right places.

::: definition Robot API for code generation {#def-api}
A **robot API for code generation** is a set of functions with
- **perception queries** that return plain data: object lists with identifiers, poses and confidence (`detect`, `get_pose`);
- **actions** at the level of validated skills (`move_to`, `grasp`, `place`, `release`), never joint torques or raw trajectories;
- **conventions stated once**: units (metres, radians), the reference frame (the robot base frame, $z$ up), the meaning of a pose;
- **failure by exception**: an action that cannot be performed raises an error with a readable message instead of returning a status that the code may ignore;
- **built-in checks**: every action validates its arguments against the robot's limits before doing anything (see [[#sec-limits]]).
:::

Here is a complete small API for a tabletop arm with a parallel gripper and a calibrated RGB-D camera. The docstrings are the documentation the model will see.

```python
"""Robot API. All positions are in metres in the robot base frame:
x forward, y left, z up, origin at the base on the table surface.
Orientations: yaw in radians about z (gripper always points down)."""

from dataclasses import dataclass

@dataclass(frozen=True)
class Obj:
    id: str        # unique identifier, e.g. "red_block_2"
    name: str      # class name from the detector, e.g. "red block"
    x: float       # centre position, m
    y: float
    z: float
    yaw: float     # rad
    size: tuple    # (length, width, height), m
    score: float   # detector confidence 0..1

def detect(query: str) -> list[Obj]:
    """Objects matching a short description ("red block", "bowl"),
    sorted by confidence. Returns [] if none is found."""

def get_pose(query: str) -> Obj:
    """The single most confident object matching query.
    Raises NotFound if there is none."""

def move_to(x: float, y: float, z: float, yaw: float = 0.0, speed: float = 0.1):
    """Move the tool point in a straight line to (x, y, z), gripper down.
    speed in m/s, at most 0.25. Raises LimitError if outside the workspace."""

def grasp(obj_id: str):
    """Pick the object: approach from above, close the gripper, lift 10 cm.
    Raises GraspFailed if nothing is held afterwards."""

def place(x: float, y: float, z: float, yaw: float = 0.0):
    """Lower the held object until its base is at height z (m),
    centred at (x, y), open the gripper and retreat 10 cm."""

def release():
    """Open the gripper where it is."""

def say(text: str):
    """Report to the operator."""
```

Several choices here are deliberate. `grasp` takes an object identifier, not a pose: the model cannot invent coordinates for a grasp, only refer to something the detector found. `place` takes the *base height* of the object rather than the tool height, so the model does not have to know the object's height or the gripper length. Speeds have a hard maximum stated in the docstring and enforced in the implementation. There is no `set_joint_positions`, no `set_force_limit`, no `disable_collision_checking`: what is not in the API cannot be called.

::: warning Units and frames are the commonest bug
The most frequent error in generated robot code is not logic but **units and frames**: millimetres passed where metres are expected, a position in the camera frame used as if it were in the base frame, degrees used as radians. A model that has seen both conventions in its training data will mix them. State the convention once at the top of the API, use one convention everywhere, make functions reject implausible values (a position of $350\,\mathrm m$ is a units error, not a far-away target), and never expose two functions that take the same quantity in different units.
:::

## Prompting for code {#sec-prompt}

The prompt has four parts, in a fixed order so that the stable part can be cached (see [[llm-robot-control/language-and-robots#sec-latency]]):

1. **Role and rules**: "You write Python that controls a robot arm through the API below. Use only the API functions and built-in arithmetic. Do not import modules. Output only code."
2. **The API** with its docstrings, exactly as above.
3. **Examples**: three to ten pairs of an instruction (as a comment) and the program that carries it out, chosen to show the patterns you want — iterating over detections, computing offsets, handling "not found", reporting with `say`.
4. **The instruction**, as a comment, followed by nothing: the model continues with code.

A good example teaches more than any rule. One example:

```python
# Instruction: put the screw in the cup.
screw = get_pose("screw")
cup = get_pose("cup")
grasp(screw.id)
place(cup.x, cup.y, cup.z + 0.01)
say("The screw is in the cup.")

# Instruction: stack all the green blocks on the yellow block.
base = get_pose("yellow block")
top = base.z + base.size[2]
for b in detect("green block"):
    grasp(b.id)
    place(base.x, base.y, top)
    top = top + b.size[2]
say("Stacked the green blocks.")
```

Examples should include the failure case you want handled — what to do when `detect` returns an empty list — because the model will imitate whatever the examples do.

::: example Generated code for a row {#ex-row}
Instruction: "Put three red blocks in a row in front of the blue bowl, five centimetres apart." The detector reports the blue bowl at $(0.45, 0.10, 0.00)\,\mathrm m$ (base of the bowl on the table) and four red blocks of size $0.04\times0.04\times0.04\,\mathrm m$. "In front of" means closer to the robot, i.e. smaller $x$. A typical generated program is
```python
bowl = get_pose("blue bowl")
blocks = detect("red block")
if len(blocks) < 3:
    say(f"I can only see {len(blocks)} red blocks.")
else:
    for i, b in enumerate(blocks[:3]):
        grasp(b.id)
        place(bowl.x - 0.10, bowl.y - 0.05 + 0.05 * i, 0.0)
    say("Placed three red blocks in a row in front of the bowl.")
```
Where do the blocks go, and is the program right?
::: solution
The targets are $x = 0.45 - 0.10 = 0.35\,\mathrm m$ and $y = 0.10 - 0.05 + 0.05i$ for $i = 0, 1, 2$, i.e. $y = 0.05$, $0.10$, $0.15\,\mathrm m$, with the block bases on the table ($z = 0$). The row is centred on the bowl's $y$, $10\,\mathrm{cm}$ in front of it, with centres $5\,\mathrm{cm}$ apart. Since the blocks are $4\,\mathrm{cm}$ wide, the gaps between them are $1\,\mathrm{cm}$ — tight for a parallel gripper whose fingers are perhaps $1\,\mathrm{cm}$ thick, so the third placement may hit the second block. The program is logically correct and physically marginal; "five centimetres apart" was interpreted as centre spacing, which is the usual reading, but a geometric check (fingers of the open gripper against neighbouring blocks) is what discovers the problem. The model chose $10\,\mathrm{cm}$ as "in front of" without being told — a reasonable default that the operator might want to change. Sanity check on the arithmetic: $0.05 + 2\times0.05 = 0.15$ ✓.
:::
:::

Two refinements from the Code as Policies work are worth knowing. **Hierarchical generation**: if the generated code calls a function that does not exist yet (say `make_grid(objects, rows, cols, pitch)`), a second model call is asked to write that function, recursively, so complex behaviour is built from short pieces. **Third-party libraries**: the original system allowed `numpy` for geometry; in a production system each such library widens what the code can do and must be considered when designing the sandbox — exposing a few vetted helper functions (`midpoint`, `offset`, `grid_positions`) is usually safer than exposing a whole numerical library.

## Running untrusted code {#sec-sandbox}

Generated code must be treated exactly like code from an anonymous stranger: it may be wrong, and if the prompt or the scene contains hostile text (see [[llm-robot-control/llm-guardrails]]), it may be deliberately harmful. Python's flexibility makes this serious — a single line can import `os`, delete files, open network connections or reach into the API's internals to bypass its checks.

::: definition Sandbox {#def-sandbox}
A **sandbox** for generated robot code is a set of mechanisms that together ensure the program (i) can call only the functions of the robot API and a small set of pure built-ins, (ii) cannot access files, the network, other processes or the API's internals, (iii) terminates within a time limit and a limit on the number of API calls, and (iv) cannot affect the robot except through API calls whose arguments are checked. No single mechanism achieves all four; they are layered.
:::

The layers, from cheapest to strongest:

1. **Static checks on the syntax tree.** Parse the code with Python's `ast` module before running it, and reject anything outside a small allow-list of node types: no `import`, no function or class definitions, no `while` loops (only `for` over finite sequences), no attribute access except to plain data fields, no names beginning with an underscore, calls only to API functions.
2. **A restricted namespace.** Execute with `exec(code, {"__builtins__": SAFE_BUILTINS, **API_FUNCTIONS})`, where `SAFE_BUILTINS` contains only `range`, `len`, `min`, `max`, `abs`, `round`, `enumerate`, `sorted`.
3. **Process isolation.** Run the interpreter in a separate operating-system process (or container) with no file-system write access, no network, a memory limit and a CPU-time limit; the robot API is reached through a narrow message channel (a pipe or socket) to the robot process, which performs all checks itself.
4. **Runtime budgets.** A wall-clock timeout for the whole program and a maximum number of action calls (for a "three blocks" instruction, perhaps 20); exceeding either stops the program and the arm.

A static checker for the first layer is short:

```python
import ast

ALLOWED_NODES = (
    ast.Module, ast.Expr, ast.Assign, ast.AugAssign, ast.Name, ast.Load, ast.Store,
    ast.Constant, ast.Call, ast.keyword, ast.Attribute, ast.Subscript, ast.Slice,
    ast.Tuple, ast.List, ast.Dict, ast.BinOp, ast.UnaryOp, ast.BoolOp, ast.Compare,
    ast.If, ast.For, ast.Break, ast.Continue, ast.IfExp, ast.JoinedStr,
    ast.FormattedValue, ast.comprehension, ast.ListComp,
    ast.Add, ast.Sub, ast.Mult, ast.Div, ast.FloorDiv, ast.Mod, ast.USub, ast.UAdd,
    ast.And, ast.Or, ast.Not, ast.Eq, ast.NotEq, ast.Lt, ast.LtE, ast.Gt, ast.GtE,
    ast.In, ast.NotIn,
)
API = {"detect", "get_pose", "move_to", "grasp", "release", "place", "say",
       "range", "len", "min", "max", "abs", "round", "enumerate", "sorted"}
DATA_FIELDS = {"id", "name", "x", "y", "z", "yaw", "size", "score"}

def check_program(src: str, max_loops: int = 3) -> list[str]:
    """Return a list of problems; an empty list means the program may run."""
    try:
        tree = ast.parse(src, mode="exec")
    except SyntaxError as e:
        return [f"syntax error: {e.msg} (line {e.lineno})"]
    problems, loops = [], 0
    for node in ast.walk(tree):
        line = getattr(node, "lineno", "?")
        if isinstance(node, (ast.For, ast.comprehension)):
            loops += 1
        if not isinstance(node, ALLOWED_NODES):
            problems.append(f"line {line}: {type(node).__name__} is not allowed")
        elif isinstance(node, ast.Attribute) and node.attr not in DATA_FIELDS:
            problems.append(f"line {line}: attribute .{node.attr} is not allowed")
        elif isinstance(node, ast.Name) and node.id.startswith("_"):
            problems.append(f"line {line}: name {node.id} is not allowed")
        elif isinstance(node, ast.Name) and isinstance(node.ctx, ast.Store) \
                and node.id in API:
            problems.append(f"line {line}: cannot rebind {node.id}")
        elif isinstance(node, ast.Call):
            if not (isinstance(node.func, ast.Name) and node.func.id in API):
                problems.append(f"line {line}: only API functions may be called")
    if loops > max_loops:
        problems.append(f"{loops} loops (limit {max_loops})")
    return problems
```

On the program of [[#ex-row]] it returns an empty list. On a program containing `import os`, `while True:` or `(1).__class__.__bases__`, it returns one message per violation, which can be sent back to the model for a corrected version.

::: warning Restricting Python's namespace is not a security boundary
It is tempting to stop after layers 1 and 2. Do not. Python has a long history of escapes from "restricted" execution through introspection (`__class__`, `__subclasses__`, frame objects), and new ones are found regularly; the Python documentation itself says that `exec` with restricted globals is not a sandbox. Static checks and namespaces are excellent for catching *mistakes* and producing good error messages. Protection against *malicious* code needs operating-system isolation (layer 3), and protection of people and machines needs the limits enforced in the robot process and in the safety controller, which no Python code can reach at all.
:::

::: quiz
Which of these generated lines does the static checker above reject?
- [ ] `top = base.z + base.size[2]`
- [x] `import math`
- [x] `while not done: grasp(b.id)`
- [x] `move_to.__defaults__ = (0.0, 2.0)`
- [ ] `for b in sorted(blocks, key=None): grasp(b.id)`
::: solution
`import` is not an allowed node; `while` is not allowed (only bounded `for` loops); `__defaults__` is an attribute outside the data fields (and an attempt to change the default speed of `move_to` behind the API's back — exactly the kind of manipulation the checker exists to stop). The first line uses only data fields, indexing and arithmetic. The last uses `sorted` with a keyword argument; `keyword` nodes are allowed and `None` is a constant, so it passes — harmlessly.
:::
:::

## Limit checks before motion {#sec-limits}

The sandbox controls *what code can call*. Limit checks control *what the calls can do*. They live in the implementation of each API action, in the robot process, and they run on every call regardless of where it came from.

The simplest and most important check is a **workspace box**: an axis-aligned box in the base frame inside which the tool point must stay, chosen to exclude the operator's side of the bench, the fixture's clamping area and anything above a safe height.

::: proposition Straight-line moves stay in a convex workspace {#prop-convex}
Let the allowed workspace $W\subset\R^3$ be convex — for example the box $W = [x_{\min}, x_{\max}]\times[y_{\min}, y_{\max}]\times[z_{\min}, z_{\max}]$. If the start point $\mathbf p_0$ and target $\mathbf p_1$ of a straight-line Cartesian move both lie in $W$, then every point of the path $\mathbf p(s) = (1 - s)\mathbf p_0 + s\mathbf p_1$, $s\in[0, 1]$, lies in $W$. For a box it therefore suffices to check the target of each straight-line move, given that the current position is inside.
:::

::: proof
A set is convex if and only if it contains the segment between any two of its points; this is the definition, so it remains to check that a box is convex. If $\mathbf p_0, \mathbf p_1\in W$, then for each coordinate, say $x$, $x_{\min}\le x_0, x_1\le x_{\max}$, and $(1 - s)x_0 + sx_1$ is a weighted average of $x_0$ and $x_1$ with non-negative weights summing to 1, hence lies between them and so in $[x_{\min}, x_{\max}]$. The same holds for $y$ and $z$, so $\mathbf p(s)\in W$. The assumption that matters is that the controller actually follows the straight line: a move interpolated in *joint* space produces a curved tool path that can leave a convex box even when both endpoints are inside it, and must be checked by sampling the path with forward kinematics.
:::

The proposition is why the API's `move_to` is a *linear* move: its safety check is a single comparison per coordinate. A complete set of per-call checks is:

::: algorithm Executing a generated program {#alg-execute}
1. **Static check** the program ([[#sec-sandbox]]). On failure, return the problems to the model for repair (at most two or three attempts), then give up and tell the operator.
2. **Dry run.** Execute the program in the sandbox against a *recording* implementation of the API: perception calls return the current scene snapshot; action calls check their arguments (step 3) and append the intended action to a log instead of moving. Abort on any exception.
3. **Per-action checks** (in the dry run and again at execution): every target inside the workspace box; speed at most the configured maximum; the object of `grasp` exists in the current detection list with a confidence above a threshold; the arm's payload not exceeded by the object's estimated mass; an inverse-kinematics solution and a collision-free path exist.
4. **Plan-level checks on the action log**: number of actions within budget; total motion time within budget; no action in a zone that requires confirmation (else ask the operator, showing the planned actions).
5. **Execute** the program for real, in the sandbox with the timeout, against the real API — whose actions repeat the checks of step 3 with fresh perception, because the scene may have changed since the dry run.
6. **Report** the outcome, with the action log, to the operator and to the log store.
:::

::: example Checking a move against the workspace {#ex-workspace}
The workspace box is $x\in[0.20, 0.70]$, $y\in[-0.40, 0.40]$, $z\in[0.00, 0.50]\,\mathrm m$ and the speed limit is $0.25\,\mathrm m/\mathrm s$. A generated program calls `move_to(0.62, -0.31, 0.20, speed=0.4)` from the current position $(0.35, 0.05, 0.25)\,\mathrm m$, and later `move_to(0.72, 0.10, 0.10)`. What do the checks report, and what is the shortest time for the first move at the permitted speed?
::: solution
First move: the target satisfies $0.20\le0.62\le0.70$, $-0.40\le-0.31\le0.40$, $0\le0.20\le0.50$, so it is in the box, and by [[#prop-convex]] so is the whole straight path. The requested speed $0.4\,\mathrm m/\mathrm s$ exceeds the limit. The API should *raise* rather than silently clamp, so that the model and the log see the problem: `LimitError: speed 0.40 m/s exceeds 0.25 m/s`. (Clamping is defensible for speed, which only affects time, but must then be logged.) At $0.25\,\mathrm m/\mathrm s$, the distance $\sqrt{0.27^2 + 0.36^2 + 0.05^2} = 0.453\,\mathrm m$ takes at least $0.453/0.25 = 1.81\,\mathrm s$ plus acceleration phases. Second move: $x = 0.72 > 0.70$, outside the box, so `LimitError: x = 0.72 m outside [0.20, 0.70]` — in the dry run, before anything has moved. Sanity check: a two-centimetre violation is typical of a model adding an offset to a pose near the edge; the right behaviour is to stop and report, not to move to the nearest allowed point, which would place the object somewhere the operator did not ask for.
:::
:::

::: example A dry run of a grid program {#ex-dryrun}
Instruction: "Arrange the twelve washers in a grid, three across and four deep, 30 mm apart, starting at $(0.40, -0.045)$." The generated program loops over rows $r = 0..3$ and columns $c = 0..2$, calling `grasp(w.id)` and `place(0.40 + 0.03*c, -0.045 + 0.03*r, 0.0)` for each washer. The cell's default action budget is 20 actions and its rule is that any program with more than $60\,\mathrm s$ of estimated motion is shown to the operator for confirmation. One pick-and-place cycle takes about $5\,\mathrm s$. What does the dry run report?
::: solution
The action log has $12$ `grasp` and $12$ `place` calls, $24$ actions in all, so with the default budget the dry run stops at the 21st action with `BudgetExceeded: 20 actions`. The budget is too low for this instruction, not the program too long: a better rule derives the budget from the request, for example $2\times(\text{objects named}) + 4 = 28$. With that budget the log passes. Targets: $x\in\{0.40, 0.43, 0.46\}\,\mathrm m$ and $y\in\{-0.045, -0.015, 0.015, 0.045\}\,\mathrm m$; the extreme corners $(0.40, -0.045)$ and $(0.46, 0.045)$ are inside the workspace box of [[#ex-workspace]], so by convexity all targets are. Estimated motion time $12\times5 = 60\,\mathrm s$, at the confirmation threshold, so the operator is shown the twelve planned positions (a small plot of the grid is ideal) and confirms. Sanity check: a 30 mm pitch with washers of, say, 24 mm outside diameter leaves 6 mm gaps, enough for a suction cup but not for parallel-gripper fingers — another case for a geometric check of neighbours.
:::
:::

::: remark Why a dry run is not enough
The dry run executes the program against a snapshot. If the program's behaviour depends on perception results that change during execution — a block is knocked over, a `detect` call returns a different list — the real run can take a branch the dry run never took. That is why step 5 repeats every check, and why programs that interleave perception and action extensively are better handled by the tool-calling loop of [[llm-robot-control/robot-tool-calling]], where each action is checked at the moment it is requested.
:::

## Sampling several programs {#sec-sampling}

A model asked twice for the same program, with sampling temperature above zero, writes different programs. Some fail the static check or the dry run, others pass. Because the checks are cheap compared with robot time, it can pay to generate several candidates and keep the first that passes.

::: proposition Best-of-$k$ with a validator {#prop-best-of-k}
Suppose each generated program independently passes all checks with probability $q$. Among $k$ programs generated in parallel, the probability that at least one passes is
$$
1 - (1 - q)^k ,
$$ {#eq-best-of-k}
and when programs are generated one at a time until one passes, the expected number of generations is $1/q$. The number of parallel samples needed to reach a pass probability $P$ is $k = \lceil\ln(1 - P)/\ln(1 - q)\rceil$.
:::

::: proof
The probability that all $k$ independent programs fail is $(1 - q)^k$; the complement is at least one pass. Generating sequentially, the index of the first passing program is geometrically distributed with success probability $q$, whose mean is $\sum_{j\ge1} j\,q(1 - q)^{j-1} = 1/q$. Solving $1 - (1 - q)^k\ge P$ for $k$ gives $k\ge\ln(1 - P)/\ln(1 - q)$ (both logarithms are negative, so the inequality direction is preserved on division).
:::

Independence is optimistic: samples from one prompt share the model's misunderstandings, so if the model misreads the instruction, all samples misread it the same way. Passing the checks also does not mean doing what the operator wanted — the checks catch unsafe or impossible programs, not wrong ones. Best-of-$k$ is therefore a tool against *syntax and limit* failures, not against misinterpretation, which needs confirmation (show the operator the planned placements) or feedback.

::: widget plot
f: 1 - (1 - q)^x
x: 0, 10
y: 0, 1
sliders: q=0.6:0.05:0.95:0.01
hlines: 0.95; 0.99
labels: P(\text{at least one of } k \text{ passes})
caption: Probability that at least one of $k$ independently generated programs passes the static check and dry run (horizontal axis $k$), for single-program pass rate $q$. At $q = 0.6$, three samples give 94% and five give 99%. Lower $q$ to 0.2, as for a hard instruction with a poor prompt, and note how many samples are needed: improving the prompt and the API raises $q$, which is worth far more than extra samples.
:::

::: example Parallel samples and latency {#ex-samples}
Programs pass the checks with $q = 0.6$. Each generation takes $5.8\,\mathrm s$ (from [[llm-robot-control/language-and-robots#ex-latency]]) and the checks $0.3\,\mathrm s$. Compare generating three in parallel with generating one at a time until success.
::: solution
In parallel, three generations take about $5.8\,\mathrm s$ of wall-clock time (the provider serves them concurrently) plus $0.3\,\mathrm s$ to check them, and succeed with probability $1 - 0.4^3 = 0.936$. Sequentially, the expected number of generations is $1/0.6 = 1.67$, i.e. an expected $1.67\times(5.8 + 0.3) = 10.2\,\mathrm s$, with a long tail (a 16% chance of needing three or more). Parallel sampling triples the token cost but cuts the latency and its variance; for interactive use it is usually the better trade.
:::
:::

::: history
Programming robots in a textual language is as old as industrial robots: Unimation's VAL (1979) and IBM's AML (1982) let integrators write motion programs, and every robot manufacturer has a language of its own. Natural-language programming of robots was studied from the 1970s with hand-written grammars, and statistical semantic parsers translated instructions into short programs in the 2010s. Large language models trained on code changed the economics: OpenAI's Codex (2021) showed that models can write working Python from docstrings. In 2022, Code as Policies (Jacky Liang, Andy Zeng and colleagues at Google) prompted such a model with a perception and control API and a few examples, generating policies for tabletop manipulation, whiteboard drawing and a mobile manipulator, with hierarchical generation of undefined functions; ProgPrompt (Singh et al., 2022) used program-like prompts for household task plans. Later work combined code generation with vision-language models for 3-D spatial reasoning (VoxPoser, 2023) and with self-correction from execution errors, while industrial deployments moved the generated code behind sandboxes and typed tool interfaces.
:::

::: summary
- A **code-as-policy** ([[#def-cap]]) is a program, written by the model, that calls a fixed robot API; loops, arithmetic and conditionals make spatial patterns and perception-dependent tasks natural.
- Design the API for generation ([[#def-api]]): few functions, plain data, skill-level actions, one stated unit and frame convention, failure by exception, checks inside every action.
- Prompt with rules, the API, worked examples (including failure handling) and the instruction, in that order.
- Run generated code in **layers** ([[#def-sandbox]]): AST allow-list, restricted namespace, OS-level process isolation, timeouts and call budgets; Python namespace restrictions alone are not a security boundary.
- Check every action against workspace, speed, payload, detection and collision limits; for a convex workspace, straight-line moves need only their targets checked ([[#prop-convex]]).
- Dry-run the program against a recording API, check the action log, then execute with all checks repeated ([[#alg-execute]]).
- Best-of-$k$ sampling raises the probability of a valid program to $1 - (1 - q)^k$ ([[#prop-best-of-k]]) but does not fix misinterpretation.
:::

## Exercises

::: exercise Row positions {level=1 check="0.22"}
Generalise the program of [[#ex-row]] to $n$ blocks so that the row stays centred on the bowl: block $i$ ($i = 0, \dots, n - 1$) goes to $y = y_{\text{bowl}} - 0.05(n - 1)/2 + 0.05i$. With five blocks and the bowl at $(0.50, 0.12, 0.00)\,\mathrm m$, what is the $y$ coordinate of the last block placed? (Enter $y$ in m.)
::: solution
The centring offset is $-0.05\times4/2 = -0.10\,\mathrm m$, and the last block has $i = 4$: $y = 0.12 - 0.10 + 0.20 = 0.22\,\mathrm m$. The row spans $y = 0.02$ to $0.22\,\mathrm m$, symmetric about $0.12$ ✓. Note that the original program hard-coded the offset $-0.05$, which is right only for $n = 3$ — the kind of silent assumption that makes "small changes" to generated code dangerous.
:::

Each program passes the checks with probability $q = 0.45$. What is the probability that at least one of four parallel samples passes? (Enter the probability to four decimal places.)
::: solution

::: exercise Samples for 95% {level=2 check="6"}
With $q = 0.45$, how many parallel samples are needed for at least a 95% chance that one passes? (Enter the integer $k$.)
::: solution
$k\ge\ln(0.05)/\ln(0.55) = (-2.996)/(-0.598) = 5.01$, so $k = 6$. Five samples give $1 - 0.55^5 = 0.9497$, just short of 95%; six give $0.9723$.
:::

::: exercise Minimum move time {level=2 check="1.811"}
At the speed limit of $0.25\,\mathrm m/\mathrm s$, what is the minimum time, ignoring acceleration, for a straight move from $(0.35, 0.05, 0.25)$ to $(0.62, -0.31, 0.20)\,\mathrm m$? (Enter the time in s to three decimal places.)
::: solution
Distance $\sqrt{0.27^2 + 0.36^2 + 0.05^2} = \sqrt{0.0729 + 0.1296 + 0.0025} = \sqrt{0.205} = 0.4528\,\mathrm m$; time $0.4528/0.25 = 1.811\,\mathrm s$.

::: exercise A units bug {level=2}
A generated program for "move the cup 5 cm to the right" reads `cup = get_pose("cup"); grasp(cup.id); place(cup.x, cup.y - 5, cup.z)`. Explain what goes wrong, which check catches it, and how the API or the prompt could make the bug less likely.
::: solution
"Right" from the robot's point of view is $-y$ in the stated frame (x forward, y left), so the direction is correct, but `5` is in centimetres where metres are expected: the target is $5\,\mathrm m$ to the right. The workspace check rejects it ($y < -0.40\,\mathrm m$) in the dry run, before anything moves. Mitigations: state the units in the docstring of every function, include an example in the prompt that uses a small offset in metres (`cup.y - 0.05`), and make `place` reject any coordinate whose magnitude exceeds the arm's reach with an explicit message ("y = −4.88 m is outside the reach of the arm; positions are in metres"), which tells the model exactly how to fix the program.
:::
:::

::: exercise Joint-space paths {level=3}
Show by a simple planar example that a move interpolated linearly in joint space can leave a convex workspace even though its endpoints are inside, and explain how the check of [[#prop-convex]] must change for such moves.
::: solution
Take a planar 2R arm with $L_1 = L_2 = 0.4\,\mathrm m$ and the workspace the box $x\in[0.2, 0.75]$, $y\in[-0.3, 0.3]$. Configuration A: $\theta_1 = -60^\circ$, $\theta_2 = 90^\circ$ gives the tool at $(0.4\cos(-60^\circ) + 0.4\cos 30^\circ,\ 0.4\sin(-60^\circ) + 0.4\sin 30^\circ) = (0.546, -0.146)$. Configuration B: $\theta_1 = 60^\circ$, $\theta_2 = -90^\circ$ gives $(0.546, 0.146)$. Both are in the box. Halfway in joint space, $\theta_1 = 0$, $\theta_2 = 0$: the arm is straight and the tool is at $(0.8, 0)$, outside the box by $5\,\mathrm{cm}$. The tool path in joint interpolation is a curve, and convexity of $W$ says nothing about it. For joint-space moves the check must sample the path (or bound it) with forward kinematics at a resolution fine enough for the tool speed, or the motion must be planned and checked by the motion planner against the workspace constraint.
:::
:::

::: exercise Escaping the checker {level=3}
The static checker allows attribute access only to `DATA_FIELDS`. Explain why an attacker who controls the instruction could still cause harm without breaking the sandbox, and what defences remain.
::: solution
The checker restricts *how* the program acts, not *what it intends*. A program that uses only allowed constructs can still, for example, grasp the operator's phone (if the detector finds it) and place it in the scrap bin, or move repeatedly at maximum allowed speed near the edge of the workspace. Defences beyond the sandbox: per-object policies in the API (`grasp` refuses objects of classes not on an allow-list for this cell); zones that require operator confirmation; action budgets; the operator's view of the planned action log before execution for unusual commands; and the safety controller's speed, force and separation monitoring, which bound harm to people regardless of what the program does. The general point, developed in [[llm-robot-control/llm-guardrails]], is that code checks catch malformed programs, while the limits that protect people sit below all code.
:::
:::

::: exercise Design an API for palletising {level=3}
Design a code-generation API (five to eight functions with signatures and one-line docstrings) for an arm that palletises boxes of several sizes onto a pallet, accepting instructions such as "build a two-layer interlocked pattern with the 400 × 300 boxes". State the conventions, which checks each action performs, and one example for the prompt.
::: solution
A possible design. Conventions: metres, pallet frame with origin at the pallet's near-left corner, $x$ along the pallet length, $y$ along its width, $z$ up from the pallet deck; yaw in radians, $0$ or $\pi/2$ only. Functions: `pallet() -> Pallet` (length, width, max_height, max_mass); `box_types() -> list[BoxType]` (id, length, width, height, mass); `next_box(type_id) -> Box` (waits for a box of that type on the infeed); `place_box(box, x, y, layer, yaw)` (places the box with its near-left corner at $(x, y)$ on the given layer; checks: footprint inside the pallet, no overlap with boxes already placed in that layer, support from the layer below over at least 70% of the footprint, total height and mass within limits); `layer_height(layer) -> float`; `say(text)`. Example for the prompt: a single layer of $0.4\times0.3$ boxes on a $1.2\times0.8$ pallet as a $3\times2$ grid, with a loop computing $x = 0.4i$, $y = 0.3j$ and a comment noting that $3\times0.4 = 1.2$ and $2\times0.3 = 0.6 \le 0.8$. Keeping the overlap and support checks inside `place_box` means a wrong interlock pattern from the model raises a precise error ("box overlaps box 4 in layer 2") rather than producing an unstable pallet.
:::
