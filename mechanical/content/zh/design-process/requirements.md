设计任务书通常只是一句话：“我们需要一把更便宜的无绳电钻”“医院想要一张一名护士就能推动的病床”“这台泵必须能熬过雨季”。这样的一句话里没有任何东西可以计算、绘图或试验。一个项目中第一项真正的工程工作，就是把它变成一份**设计要求表**（specification）：一系列陈述，每一条都指明产品的一项可度量的性能、它必须达到的值，以及检查这个值的方法。此后的每一个决策——开发哪个概念（[[design-process/concept-generation]]、[[design-process/concept-selection]]）、轴要做多粗（[[design-process/embodiment-design]]）、要试验多少台样机——都要对照这份清单来评判。含糊的设计要求表无法平息争论；错误的设计要求表则会让一个能干的团队高效地朝错误的方向前进。

本讲沿着从需要到设计要求表的路径展开。它从弄清用户真正需要什么开始，区分需要、要求和设计要求，说明一项需要如何变成带有目标值的指标，并介绍验证要求的四种方法。接着用两种经典工具来组织信息：卡诺模型（Kano model），它按需要对满意度的影响对其进行分类；以及质量功能展开（QFD），它把加权的客户需要转化为工程指标之间的优先次序。本讲最后讨论可追溯性和更改控制，并定量地考察通过试验进行的验证——要多少台产品通过试验，才能声称满足了某项可靠性要求。本讲所处的整个设计过程见[[design-process/design-process-overview]]。

## 从需要到设计要求 {#sec-needs}

### 弄清需要什么

用户很少以工程师可用的形式陈述他们的需要，也很少把需要全部说出来。因此，有经验的团队用几种互为补充的方式收集需要：

- **访谈**：在用户自己的环境中逐一访谈用户，用开放式问题（“请带我回顾一下你上一次……的过程”），而不是让人们去设计产品。一次只访谈一个人，可以避免焦点小组中的从众现象。
- **观察使用过程**（有时称为情境调查）：观看机修工更换泵的密封件，或护士推动病床，可以发现种种变通做法、临时凑合的工具和困难，这些东西因为已经习以为常，没人会想到提起。
- **领先用户**——比整个市场更早或更强烈地感受到某种需要的人，例如对电动工具而言的专业技工——往往已经改装过现有产品，并能描述大众市场以后才会感受到的需要。
- **文件和数据**：现有产品的投诉和保修记录、现场故障报告、事故统计，以及产品必须满足的法规和标准。
- **所有利益相关者**，而不只是购买者：用户，以及安装、维护、运输、销售、回收或监管该产品的人。一张病床由采购部门购买，由病人使用，由护工推动，由保洁人员清洁，由技术人员维修；每一个群体都有自己的需要。

原始的结果是一长串用客户自己的话写成的陈述。下一步是把每一条改写成需要陈述。

::: definition 客户需要、要求与设计要求 {#def-need}
**客户需要**是从某一利益相关者的角度，对产品应具有的一项属性所作的、不依赖于任何特定解决方案的陈述（“电钻不充电能用一整个工作日”）。**要求**是由设计团队重新表述的需要，用工程语言写成产品*应*具有的性能，并给出限定条件（“电钻充一次电应能把至少 100 颗规格为$5\times 50\,\mathrm{mm}$的螺钉拧入软木”）。**设计要求表**（或目标设计要求）是要求的集合，其中每项要求都通过一个**指标**（带单位的可度量的量）、一个**目标值**（或范围）和一种**验证方法**而变得精确。限制解决方案而不与其他要求进行权衡的要求——法律、标准、接口尺寸——称为**约束**；应当做得尽可能好的要求称为**目标**。
:::

按照乌尔里希（Ulrich）与埃平格（Eppinger）的说法，写需要陈述的准则是：表达产品必须做*什么*而不是*怎么做*（“手柄保持凉爽”，而不是“手柄用尼龙制成”）；保持原始数据的具体程度；使用肯定的措辞；描述产品的属性而不是用户的义务。写不含解决方案的需要，目的是让概念空间保持开放：如果需要被记录为“尼龙手柄”，以后就没有人会去考虑隔热的空气间隙了。

### 指标、目标值及其范围

一项需要只有与一个能在样机上测量的**指标**联系起来，才对工程师有用。指标通常是间接的：“握在手里感觉轻”变成以千克计的质量，*以及*质心到握把的距离；“能用一整天”变成规定工作循环下以瓦时计的储能。好的指标应当

- **取决于**产品本身，而不取决于试验做得好不好；
- **切实可行**——能用现有设备以合理的成本测量；
- 与其他指标合在一起是**完备的**，使得满足全部指标确实就满足了需要。

在项目早期，目标值很少是单个数值。一种常见的做法是记录一个**临界值**（刚好使产品在商业上可行的值）和一个**理想值**（所能期望的最好值），并且只在概念选定、其能力已知之后才缩小这个范围。对标（benchmarking）——用同样的指标测量竞争对手的产品——使这两个值都有现实依据。

::: example 从“能用一整天”到电池设计要求 {#ex-battery}
对安装橱柜的木工的访谈得出需要“电钻不充电能用一整个工作日”。观察表明，繁忙的一天大约要把 100 颗$5\times 50\,\mathrm{mm}$的螺钉拧入软木，螺纹咬合后每颗约需转 8 圈，平均转矩为$5\,\mathrm{N\,m}$。设从电池到钻夹头的总效率（电动机、电子器件和齿轮箱）为$60\,\%$，并且为保护电芯寿命，只能使用额定电池能量的$80\,\%$。导出电池能量的目标值，以及在标称电压$18\,\mathrm V$下相应的容量。
::: solution
每颗螺钉的机械功：$W = T\theta = 5\,\mathrm{N\,m}\times(8\times2\pi\,\mathrm{rad}) = 251.3\,\mathrm J$。
效率为$60\,\%$时每颗螺钉的电池能量：$251.3/0.60 = 418.9\,\mathrm J$。
100 颗螺钉：$41\,890\,\mathrm J = 41.89\times10^{3}/3600\,\mathrm{Wh} = 11.64\,\mathrm{Wh}$。
可用$80\,\%$时的额定能量：$11.64/0.80 = 14.54\,\mathrm{Wh}$。
$18\,\mathrm V$下的容量：$14.54\,\mathrm{Wh}/18\,\mathrm V = 0.808\,\mathrm{Ah}$。
因此一条合理的设计要求是：*指标*为电池包额定能量；*临界值*$15\,\mathrm{Wh}$；*理想值*$30\,\mathrm{Wh}$（为更硬的木材、钻孔和电芯老化留出余量）；*验证*方法为试验——在标准夹具上拧螺钉，直到电池包断电。合理性检查：市售$18\,\mathrm V$电池包的规格大致为$1.5$到$5\,\mathrm{Ah}$（约 27 到 90 Wh），远高于我们的临界值；这与以下事实相符：实际用户还要钻孔，而钻孔所需的能量远多于拧螺钉。估算给出下限，对标给出理想值。
:::
:::

### 写出可以检查的要求

一项要求写成一个含有“应”的句子，每句只讲一项性能，带有适用条件和带单位的值：“在床垫平台中央放置$300\,\mathrm{kg}$载荷时，病床*应*能在平整地面上以不超过$200\,\mathrm N$的水平手推力推动。”需求工程标准 ISO/IEC/IEEE 29148 列出了一项结构良好的要求应具备的特性；对机械产品而言，最重要的是每项要求都是**必要的**（可追溯到某项需要或约束）、**无歧义的**（只有一种解读）、**单一的**（只讲一项性能）、**可行的**和**可验证的**。诸如*足够*、*容易*、*坚固*、*用户友好*、*尽可能*和*等等*之类的词会使要求无法验证，应当换成数字或删去。

::: warning 把解决方案写进要求里
“外壳应为压铸铝件”不是要求，而是一项设计决策；一开始就把它写进设计要求表，会在注塑聚合物、钣金和其他一切方案被考虑之前就把它们排除掉。要问这句话*为什么*会被提出：如果答案是“因为它必须散发$40\,\mathrm W$的热量，且表面温度低于$60\,^\circ\mathrm C$”或“因为它必须经受从$1\,\mathrm m$高处跌落到混凝土上”，那就把*这个*写下来。真正的解决方案约束确实存在——产品必须适配现有的螺栓孔分布，或者工厂只有一种压力机——但要把它们连同理由一起记为约束，以便理由消失时可以对其提出质疑。
:::

### 验证与确认 {#sec-verification}

每项要求都带有表明它已被满足的方法。系统工程中有四种标准方法：

::: definition 验证方法 {#def-verification}
- **检查**（inspection）：凭感官或简单测量对产品或其文件进行检验（标签存在，某个尺寸在公差范围内，图样上规定了正确的材料）。
- **分析**（analysis）：根据经过验证的模型进行计算或仿真（应力分析给出安全因数；热模型预测表面温度）——用于试验不可能、危险或代价过高的场合，或在硬件出现之前作为证据。
- **演示**（demonstration）：操作产品以表明某项功能有效，不作详细测量（病床能被推过一扇标准门）。
- **试验**（test）：在受控条件下操作产品，进行测量并记录数据，通常按照标准程序进行（跌落试验、疲劳试验、噪声级测量）。
:::

**验证**问的是“我们把产品造对了吗？”——产品满足其设计要求吗？**确认**问的是“我们造的是对的产品吗？”——它在实际使用中满足用户的需要吗？如果设计要求本身是错的，一件产品可能通过每一项验证试验，却仍然无法通过确认；这就是为什么要尽早把样机交到真实用户手中，也是为什么从每项要求回溯到某项需要的链条（[[#sec-traceability]]）如此重要。

::: example 选择验证方法 {#ex-verification}
为一张手动推行的病床的下列各项要求指定验证方法：
(a) 病床应带有适用的医疗器械法规所要求的标签。
(b) 脚轮制动器应能使满载病床在$6^\circ$的坡道上保持不动。
(c) 床架应能承受$2\times10^5$次床垫平台载荷循环而不开裂。
(d) 侧护栏应能由一个人单手升起和放下。
(e) 床头段的铰接销对屈服的安全因数应不小于 3。
::: solution
(a) 检查——查看标签并核对其内容。
(b) 试验——把满载病床放在规定角度的坡道上，测量任何移动。（对制动器摩擦的计算可以作为辅助，但这项要求试验起来既便宜又重要。）
(c) 试验，辅以分析——在试验台上对一个或多个床架进行疲劳试验；在试验台建成之前，用疲劳分析（[[machine-design]]）预测结果并确定试验条件。
(d) 演示——由几位身材不同的人操作护栏；没有单一的数值可供记录。（如果操作力很重要，就应当把这项要求改写为带有力的限值，然后进行*试验*。）
(e) 分析——对销轴进行应力计算；破坏性试验只能表明某一根销轴的安全因数大于 3，而不能表明大多少。
检查：每项要求都恰好有一种主要方法，而且方法与陈述所要求的证据类型相符——一项含有数字却“通过演示”验证的要求，说明要求或方法有一个是错的。
:::
:::

## 需要并不都一样：卡诺模型 {#sec-kano}

客户对不同的属性有不同的反应。汽车的制动器必须有效；没有人因为它有效而欣喜，但如果它失效，每个人都会愤怒。燃油经济性带来的满意程度与它的好坏成正比。一项没人预料到的功能——比如一种能提示螺钉已完全拧到位的工具——即使做得一般也能令人惊喜，而没有它也不会让任何人失望。狩野纪昭（Noriaki Kano）及其同事于1984年把这些观察形式化了。

::: definition 卡诺类别 {#def-kano}
对于实现程度为$x$（从不具备到完全具备）的产品属性和客户满意度$s$：
- **必备**（基本型）属性在不具备时引起强烈的不满，而具备时至多只是不偏不倚；
- **一维**（期望型、性能型）属性使满意度大致与其实现程度成正比地提高；
- **魅力**（兴奋型）属性不具备时不引起不满，具备时满意度不断提高；
- **无差异**属性无论有无对满意度影响都很小；
- **反向**属性是有些客户主动反感其存在的属性。
:::

卡诺问卷就一项属性向每位受访者提两个问题——一个*正向*问题（“如果电钻*带有* LED 工作灯，你感觉如何？”）和一个*反向*问题（“如果它*没有*，你感觉如何？”）——每个问题用以下答案之一回答：我喜欢、理应如此、无所谓、能忍受、我不喜欢。这对答案按一张标准表格分类：喜欢/不喜欢为一维；喜欢/无所谓（或喜欢/能忍受、喜欢/理应如此）为魅力；理应如此/不喜欢、无所谓/不喜欢或能忍受/不喜欢为必备；两个问题都答中间选项为无差异；具备时不喜欢而不具备时喜欢为反向。每项属性归入大多数受访者所属的类别。

::: widget plot
f: -exp(-3*x); x - 0.5; exp(3*(x - 1)); 0*x
x: 0, 1
y: -1.1, 1.1
labels: \text{必备}; \text{一维}; \text{魅力}; \text{无差异}
caption: 示意性的卡诺曲线：客户满意度（纵轴，从不满意$-1$到惊喜$+1$）与属性具备程度（横轴，从不具备$0$到完全具备$1$）的关系。这些曲线是对各类别的示意，而不是拟合的数据。注意必备曲线从不升到零以上——基本属性再多也不会令人惊喜——而魅力曲线从不降到零以下。随着时间推移，属性在各类别中逐级下移：昨天的魅力属性（电钻上的工作灯）成了今天理所当然的功能。
:::

其工程上的结论是：应按类别以不同方式设定目标值。必备属性需要一个必然能达到的阈值——它们通常就是约束和安全要求。一维属性在设计要求表中与成本进行权衡；对标和下一节的 QFD 在这里最为重要。魅力属性是产品能以低成本形成差异的地方，但随着竞争对手的模仿，它们会变成必备功能。

::: example 根据调查答案对属性分类 {#ex-kano}
二十位专业用户就一把无绳电钻的三项属性回答了卡诺问题。最常见的答案对（正向/反向）为：
(a) 电量指示——“理应如此”/“我不喜欢”（20 人中 14 人）；
(b) 每次充电的运行时间——“我喜欢”/“我不喜欢”（20 人中 12 人）；
(c) 与手机应用的蓝牙连接——“无所谓”/“无所谓”（20 人中 11 人），另有 6 人回答“我喜欢”/“无所谓”。
对每项属性分类，并说明它对设计要求意味着什么。
::: solution
(a) 理应如此/不喜欢属于*必备*：电量指示必须具备，但更精致的版本不会提高满意度。把它规定为约束（通过检查验证），在它上面的花费不要超过必要的程度。
(b) 喜欢/不喜欢属于*一维*：运行时间越长，满意度稳步提高。它应作为目标列入设计要求表，带有临界值和理想值（[[#ex-battery]]），并与质量和成本进行权衡。
(c) 多数答案为*无差异*，少数（20 人中 6 人，30 %）认为它是*魅力*属性。对这一用户群体而言，该功能在基本型产品中抵不上它的成本和复杂性；可以考虑在某个变型产品中，面向认为它有魅力的细分市场提供。
检查：类别是说得通的——(a) 中 20 人有 14 人选必备，是明显的多数；(c) 的决定遵从多数，但记录了少数意见，这正是一个细心的团队会报告的内容。
:::
:::

## 质量功能展开 {#sec-qfd}

需要一旦加了权、指标一旦选定，团队就必须决定哪些指标最重要：对哪些指标要仔细对标，把开发力量花在哪里，指标之间的冲突要在哪里解决。**质量功能展开**（quality function deployment，QFD）是在20世纪60年代末和70年代的日本工业界发展起来的，并经豪泽（Hauser）与克劳辛（Clausing）1988年的文章《质量屋》（“The House of Quality”）在西方普及；它是用矩阵完成这项工作的一种结构化方法。

::: definition 质量屋 {#def-hoq}
**质量屋**是这样一张图表：其各行是客户需要$i = 1,\dots,m$，带有重要度权重$w_i$；各列是工程指标$j = 1,\dots,n$。每个单元格填写一个**关系强度**$r_{ij}$，表示指标$j$对需要$i$的影响有多强，按惯例取$9$（强）、$3$（中）、$1$（弱）或$0$（无）。在这个中心矩阵周围，“屋子”还加上：*屋顶*——一个三角矩阵，表示各对指标之间是相互支持还是相互冲突；*右墙*——客户针对每项需要对现有产品和竞争对手产品的评分；以及*地下室*——每个指标的单位、竞争对手的实测值、技术难度和目标值。
:::

::: algorithm QFD 中的技术重要度 {#alg-qfd}
1. 为每项需要指定重要度$w_i$（例如根据客户调查取 1–5；也可以乘以右墙中的改进比或卖点因子）。
2. 对每项需要和每个指标，经团队讨论指定$r_{ij} \in \{0, 1, 3, 9\}$；大多数单元格应为零，而每项需要至少应有一个强关系（否则说明缺少某个指标）。
3. 计算每个指标的**技术重要度**
$$
t_j = \sum_{i=1}^{m} w_i\,r_{ij}
$$ {#eq-qfd}
及其**相对重要度**$t_j \big/ \sum_k t_k$，通常用百分数表示。
4. 用排序来分配注意力：为重要度高的指标设定有挑战性的目标值，并检查屋顶中它们之间的冲突。
:::

9-3-1 标度有意把分数拉开，使强关系占主导。这些数字是判断，因此结果是一种结构化的意见，而不是测量：它最有用的地方在于揭示团队尚未讨论过的东西（空行、没有强关系的列），以及把分歧明确地摆出来。

::: example 无绳电钻的质量屋 {#ex-qfd}
五项需要（权重 1–5）与五个指标的关系如下：

| 需要（$w_i$） | M1 电池包能量（Wh） | M2 质量（kg） | M3 最大转矩（N m） | M4 反冲断电 | M5 单件成本（£） |
|---|---|---|---|---|---|
| 能用一整天（5） | 9 | 3 | 0 | 0 | 3 |
| 握在手里轻（4） | 3 | 9 | 3 | 0 | 0 |
| 能拧大螺钉（4） | 1 | 0 | 9 | 3 | 1 |
| 钻头卡住时安全（3） | 0 | 1 | 3 | 9 | 0 |
| 价格可承受（3） | 3 | 0 | 3 | 1 | 9 |

计算每个指标的技术重要度和相对重要度。
::: solution
由[[#eq-qfd]]，逐列计算：
M1：$5\cdot9 + 4\cdot3 + 4\cdot1 + 3\cdot0 + 3\cdot3 = 45 + 12 + 4 + 0 + 9 = 70$。
M2：$5\cdot3 + 4\cdot9 + 0 + 3\cdot1 + 0 = 15 + 36 + 3 = 54$。
M3：$0 + 4\cdot3 + 4\cdot9 + 3\cdot3 + 3\cdot3 = 12 + 36 + 9 + 9 = 66$。
M4：$0 + 0 + 4\cdot3 + 3\cdot9 + 3\cdot1 = 12 + 27 + 3 = 42$。
M5：$5\cdot3 + 0 + 4\cdot1 + 0 + 3\cdot9 = 15 + 4 + 27 = 46$。
总和$278$；相对重要度依次为$25.2\,\%$、$19.4\,\%$、$23.7\,\%$、$15.1\,\%$、$16.5\,\%$。
电池包能量和转矩排在前面。屋顶会表明电池包能量与质量（电池包越大越重）以及与成本相冲突，因此团队预先就知道，设计要求中最难的权衡是能量与质量和成本之间的权衡——而这恰恰是电池供应商的产品系列所围绕的权衡。检查：相对重要度之和为$100\,\%$，且最重要的需要（权重 5）与排名第一的指标之间有强（9）关系，这与预期相符。
:::
:::

::: remark 质量屋的逐级展开
QFD 可以继续向下游展开：第一个质量屋的指标成为第二个质量屋的“需要”，其各列是零件特性；然后是关于工艺参数的第三个质量屋，以及关于生产控制的第四个质量屋。实践中大多数团队只用第一个质量屋，但逐级展开表达了一个重要思想——每一项机加工公差最终都应能追溯到客户关心的某件事。
:::

## 要求的优先排序、追溯与控制 {#sec-traceability}

一件复杂产品的设计要求表包含成百上千项要求，而且它们会随着项目认识的加深而变化。有三种做法可以使它们处于受控状态。

**优先排序。** 并非每一项要求都能在每一个版本中得到满足。项目管理中广泛使用的一种简单方案是 **MoSCoW**：每项要求被标记为*必须有*（must have）、*应该有*（should have）、*可以有*（could have）或*（这次）不会有*（won't have）。必须有的要求大致对应于卡诺的必备属性以及法律和安全约束；一个漏掉其中任何一项的产品版本根本不予发布。

**可追溯性。** 每项要求都记录它从何而来（它所服务的需要、法规或接口），以及后来由哪些设计要素满足它、由哪项验证活动来关闭它。**可追溯性矩阵**把这些联系列成表。它回答每个项目中都会出现的三个问题：*这项要求为什么在这里？*（向后追溯到需要——孤立的要求应当删除或说明理由）；*每项需要都被覆盖了吗？*（向前追溯——没有对应要求的需要不会被纳入设计）；以及*一项更改会影响什么？*（影响分析）。

**更改控制。** 设计要求表一经同意，就被置于配置控制之下：更改要先提出，评估其对成本、进度和其他要求的影响，予以批准或否决，并以新的修订版本记录下来。后期更改代价高昂（原因见[[design-process/design-process-overview]]），但压制必要的更改更糟：一个发现设计要求有错却不加以更改的团队，交付的产品会通过验证而无法通过确认。

::: quiz
一项要求写道：“泵应便于维护。”改进它的最好办法是什么？
- [ ] 加上“且可靠”，使它同时涵盖维护和失效。
- [ ] 规定泵应有螺栓连接的泵壳。
- [x] 用可度量的陈述代替它，例如“经过培训的技术人员仅用标准工具包中的工具，应能在 30 min 内更换机械密封”，并说明如何验证。
- [ ] 保持原样；可维护性是主观的，无法规定。
::: solution
“便于”是无法验证的。第三个选项给出了指标（时间）、条件（经过培训的技术人员、标准工具）和目标值，并且可以通过演示或试验来验证。第二个选项把解决方案写进了要求，第一个选项则在同一个句子里又加了一项含糊的性能。
:::
:::

## 通过试验验证要求：需要多少台？ {#sec-success-run}

有些要求涉及概率：“锁扣应能承受$10^4$次操作，可靠度至少为$0.95$。”试验永远不能确定地证明这样的陈述，但能在规定的**置信度**下支持它。最简单的方案是对$n$台产品按要求的工况进行试验，若无一失效则接受该设计。

::: proposition 零失效（成功运行）试验 {#prop-success-run}
设对$n$台产品进行试验，它们的失效相互独立，且每台以同一概率$R$经受住试验工况，结果无一失效。若方案规定只有在这种情况下才接受该设计，则要以置信度$C$证明可靠度至少为$R_0$，需要
$$
n \ge \frac{\ln(1 - C)}{\ln R_0}.
$$ {#eq-success-run}
:::

::: proof
如果真实可靠度只有$R \le R_0$，那么$n$台独立产品全部经受住试验的概率为$R^n \le R_0^n$。以置信度$C$进行证明，意味着可靠度低至$R_0$的设计通过试验的概率至多为$1 - C$：$R_0^n \le 1 - C$。取对数，并注意除以$\ln R_0 < 0$时不等号反向，得$n \ge \ln(1 - C)/\ln R_0$。所作的假设是：试验工况代表现场工况，试验件代表批量产品，且失效相互独立。
:::

::: example 锁扣的样本量 {#ex-success-run}
要以$C = 90\,\%$的置信度证明$R_0 = 0.95$，必须有多少个锁扣无失效地完成$10^4$次循环？$R_0 = 0.99$时又如何？
::: solution
由[[#eq-success-run]]：$n \ge \ln(0.10)/\ln(0.95) = (-2.3026)/(-0.05129) = 44.9$，所以需要$n = 45$个锁扣。对于$R_0 = 0.99$：$n \ge -2.3026/(-0.01005) = 229.1$，所以需要$230$个锁扣。
所证明的可靠度每多一个“9”，试验件数量就要增加到约十倍，因为当$R_0$接近 1 时，$\ln R_0 \approx -(1 - R_0)$，$n \approx \ln\!\big(1/(1-C)\big)/(1 - R_0)$；当$C = 0.9$时，它等于$2.30/(1 - R_0)$，给出$46$和$230$——与精确值一致。这就是为什么高可靠度要通过对加速试验和现场数据的分析来证明，而不是通过成功运行试验（[[design-process/reliability-risk]]），也是为什么要求中“9”的个数不应超出需要所能证明其合理的程度。
:::
:::

::: widget plot

x: 0.8, 0.99

sliders: C=0.9:0.5:0.99:0.01

:::

::: application 编写设计要求表
本讲的最终产物是一张表格——每项要求占一行，包括编号、要求文本、它所追溯到的需要或约束、指标和单位、临界值和理想值（对约束则为单一限值）、优先级以及验证方法。这样一张表，经项目评审并签署后，就是[[design-process/concept-generation]]的出发点，也是以后每次设计评审所对照检查的依据。由于它是受控文件，表头上的修订字母与其内容同样重要。
:::

::: history
系统化的要求表在德国设计方法学中有悠久的历史：*Anforderungsliste*（要求表）是格哈德·帕尔（Gerhard Pahl）与沃尔夫冈·拜茨（Wolfgang Beitz）在《设计学》（*Konstruktionslehre*，1977年）中阐述的方法的第一项交付物。质量功能展开源于日本的质量管理实践：20世纪60年代中期普利司通轮胎公司使用的一种工序保证表，以及约1972年三菱重工神户造船厂制定的“质量表”，经赤尾洋二（Yoji Akao）和水野滋（Shigeru Mizuno）系统化；约翰·豪泽（John Hauser）与唐·克劳辛（Don Clausing）1988年发表在《哈佛商业评论》（*Harvard Business Review*）上的文章《质量屋》使这一方法广为西方读者所知。狩野纪昭（Noriaki Kano）、濑乐信彦（Nobuhiko Seraku）、高桥文夫（Fumio Takahashi）和辻新一（Shinichi Tsuji）于1984年在日本质量管理学会会刊上发表了《魅力质量与必备质量》。阿比·格里芬（Abbie Griffin）与约翰·豪泽1993年的论文《客户之声》（“The Voice of the Customer”）研究了如何最好地收集、组织需要并确定其优先次序；卡尔·乌尔里希（Karl Ulrich）与史蒂文·埃平格（Steven Eppinger）的教科书《产品设计与开发》（*Product Design and Development*，第1版1995年）使本讲所用的需要—指标—目标值序列成为工程课程中的标准内容。
:::

::: summary
- 需要是来自利益相关者的、不含解决方案的陈述；要求把它们重新表述为“应”的陈述；设计要求表为每项要求附上指标、目标值（或临界值和理想值）以及验证方法。
- 通过访谈、观察使用过程、领先用户、各种记录以及所有利益相关者（而不只是购买者）来收集需要。
- 好的要求是必要的、无歧义的、单一的、可行的和可验证的；摒弃*容易*、*足够*之类的词，不要在不记录理由的情况下把解决方案写进要求。
- 验证方法：检查、分析、演示、试验。验证对照设计要求检查产品；确认对照用户的需要检查产品。
- 卡诺模型区分必备、一维、魅力、无差异和反向属性；为必备属性设定阈值，把一维属性与成本进行权衡。
- QFD 技术重要度$t_j = \sum_i w_i r_{ij}$（$r_{ij}\in\{0,1,3,9\}$）对指标进行排序；屋顶揭示指标之间的冲突。
- 对$n \ge \ln(1-C)/\ln R_0$台产品进行零失效试验，可以以置信度$C$证明可靠度$R_0$；每多一个 9，所需台数约增加到十倍。
- 对要求进行优先排序（MoSCoW），把每项要求追溯到需要及其验证，并控制更改。
:::

## 习题

::: exercise 改写需要 {#exr-rewrite level=1}
一位园林粉碎机的用户说：“它需要更强劲的电动机，因为碰到粗树枝老是卡住。”写出一条不含解决方案的需要陈述，以及一项带有指标、目标值和验证方法的要求。
::: solution
用户提出的是一个解决方案（更强劲的电动机）。其背后的需要大致是“粉碎机能处理修剪花园时通常产生的树枝而不卡住”。一项要求：“粉碎机应能以不低于$0.5\,\mathrm{m/min}$的进给速度处理直径不超过$40\,\mathrm{mm}$的新剪硬木树枝$30\,\mathrm{min}$，而不发生堵转或卡住”，通过对一批规定的树枝进行试验来验证。解决办法可能是更强劲的电动机，但同样可能是不同的刀具几何形状、转矩更大而切削速度更低的方案，或者自动反转——需要陈述让所有这些方案都保持开放。
:::
:::

::: exercise QFD 的一列 {#exr-qfd-column level=1 check="54"}
三项需要的权重分别为 5、3 和 2，它们与某指标的关系分别为 9、1 和 3。该指标的技术重要度是多少？（输入$t_j$。）
::: solution
$t_j = 5\times9 + 3\times1 + 2\times3 = 45 + 3 + 6 = 54$。
:::
:::

::: exercise 零失效试验的台数 {#exr-success-run level=1 check="22"}
要以$90\,\%$的置信度证明可靠度为$0.90$，必须有多少台产品通过零失效试验？（输入台数的整数。）
::: solution
$n \ge \ln(0.10)/\ln(0.90) = -2.3026/(-0.10536) = 21.85$，所以$n = 22$。
:::
:::

::: exercise 相对重要度 {#exr-relative level=2 check="45"}
一个质量屋有三个指标，其技术重要度分别为$54$、$36$和$30$。第一个指标的相对重要度是多少？（以百分数输入。）
::: solution
总和$54 + 36 + 30 = 120$；$54/120 = 0.45 = 45\,\%$。
:::

::: exercise 运行时间要求 {#exr-runtime level=2 check="150"}
一台无绳角磨机充一次电必须以$1.2\,\mathrm{kW}$的平均轴功率切割$6\,\mathrm{min}$。从电池到轴的效率为$80\,\%$，在本估算中额定能量可以全部使用。电池包的最小额定能量是多少？一个$18\,\mathrm V$、$5\,\mathrm{Ah}$的电池包能满足这项要求吗？（以 Wh 输入能量。）
::: solution
轴上能量$1.2\,\mathrm{kW}\times 0.1\,\mathrm h = 0.12\,\mathrm{kWh} = 120\,\mathrm{Wh}$；电池能量$120/0.8 = 150\,\mathrm{Wh}$。一个$18\,\mathrm V$、$5\,\mathrm{Ah}$的电池包标称储能$18\times5 = 90\,\mathrm{Wh}$，只有所需的$60\,\%$——实际上还更少，因为电池包在角磨机所需的大电流（约$1.5\,\mathrm{kW}/18\,\mathrm V \approx 83\,\mathrm A$）下放出的能量低于其额定值。要么重新商定这项要求（连续切割$6\,\mathrm{min}$是真实的需要，还是在一项有间歇的作业中累计$6\,\mathrm{min}$？），要么产品需要两个电池包或更高电压的电池包。
:::
:::

::: exercise 验证方法的分类 {#exr-methods level=2}
对于一只家用压力锅，给出你会对下列每项要求采用的验证方法并说明理由：(a) 内部表压超过$5\,\mathrm{kPa}$时锅盖应无法打开；(b) 锅体应能经受住其工作压力的规定倍数的液压试验；(c) 锅底的平面度应在$0.3\,\mathrm{mm}$以内；(d) 应以销售国的语言提供说明书；(e) 工作压力下的壁面应力不应超过适用标准的许用应力。
::: solution
(a) 试验：给压力锅加压，并在一系列压力下尝试打开它，记录联锁装置释放时的压力；这是安全关键项，不作测量的演示是不够的。(b) 按定义就是试验——液压耐压试验（用水进行，使失效时释放的储能很少，并且只能由经过培训的人员在防护设施后进行）。(c) 检查：用直尺和塞尺或三坐标测量机测量平面度。(d) 对文件进行检查。(e) 分析，按标准规定的方法（薄壁压力容器公式，见[[mechanics-of-materials]]），并以 (b) 中的试验作为支持。注意压力设备是按照适用的标准和法规设计和认证的；本题只是说明如何指定验证方法。
:::
:::

::: exercise 允许一次失效 {#exr-one-failure level=3 check="38"}
零失效方案很严苛：一次不走运的失效就会否定整个设计。把[[#prop-success-run]]推广到这样的方案：若$n$台产品中至多一台失效，则接受该设计。证明$n$必须满足$R_0^n + nR_0^{n-1}(1 - R_0) \le 1 - C$，并求$R_0 = 0.90$、$C = 0.90$时的最小$n$。（输入台数的整数。）
::: solution
对于可靠度为$R$的独立产品，失效台数服从参数为$n$和$1 - R$的二项分布。当失效台数为$0$或$1$时方案接受设计，概率为$P_{\text{acc}}(R) = R^n + nR^{n-1}(1 - R)$。它随$R$递增（越可靠的设计越常通过），所以在$R \le R_0$中最坏的情况是$R = R_0$，置信度要求为$P_{\text{acc}}(R_0) \le 1 - C$。试算：$n = 37$：$0.9^{37} + 37\times0.9^{36}\times0.1 = 0.0203 + 0.0834 = 0.1037 > 0.1$；$n = 38$：$0.0183 + 0.0770 = 0.0953 \le 0.1$。所以$n = 38$——而零失效方案为$22$。多出的 16 台换来了对一次失效的容忍；这一方案也给了好设计更大的通过机会（真实$R = 0.97$时，38 台中允许一次失效的通过概率为$0.68$，而 22 台零失效为$0.51$；$R = 0.98$时为$0.82$对$0.64$）。
:::
:::

::: exercise 爬楼手推车的设计要求表 {#exr-design level=3}
一家慈善机构需要一种手推车，让一名志愿者能把$40\,\mathrm{kg}$的食品包裹沿楼梯送上没有电梯的公寓楼。(a) 列出来自至少三类不同利益相关者的至少八项需要。(b) 把其中四项变成带有指标、临界值和理想值以及验证方法的要求，其中至少包括一项必备的安全要求。(c) 指出一对可能相互冲突的指标，并说明你将如何决定其权衡。
::: solution
一种可能的答案。(a) 志愿者：不必抬起载荷就能爬楼；稳定——不会顺着楼梯溜下去；轻到可以搬进汽车后备箱；能折叠放进小汽车；适合不同身高和力气的人使用。住户：不损坏楼梯踏步前缘或地毯；夜间在走廊里安静。慈善机构：价格可承受；当地修理铺能修。物业管理者：适用于标准楼梯和楼梯平台。
(b) *手推力*：载$40\,\mathrm{kg}$爬标准楼梯时，把手处的峰值力不应超过$150\,\mathrm N$（临界值）/$80\,\mathrm N$（理想值）；在试验楼梯上用装在把手中的测力传感器进行试验。*防溜车*（必备）：在任何把手角度下，除非操作者操作某个控制件，满载手推车都不应下降一级台阶；进行试验，包括操作者失手的情况。*质量*：临界值$\le 15\,\mathrm{kg}$，理想值$\le 9\,\mathrm{kg}$；称重检查。*楼梯适应性*：能爬踏步高度$150$到$220\,\mathrm{mm}$、踏步宽度$220$到$300\,\mathrm{mm}$的楼梯；在可调试验楼梯上演示，并测量任何打滑。
(c) 手推力小需要某种机构（三星轮组、履带或动力爬楼器），这会增加质量，与质量目标相冲突。决定的办法是：根据对志愿者的访谈对需要加权，为两三个概念快速制作样机并测量这两个指标（[[design-process/concept-selection]]）；防溜车要求是一项约束，无论如何权衡，每个概念都必须满足。

## 延伸阅读

乌尔里希、埃平格与杨（Yang）的《产品设计与开发》（*Product Design and Development*，第7版，2020年）中关于识别客户需要和用临界值与理想值建立目标设计要求的章节写得很清楚。帕尔、拜茨、费尔德胡森（Feldhusen）与格罗特（Grote）的《工程设计：系统化方法》（*Engineering Design: A Systematic Approach*，英文第3版，2007年）把要求表作为系统化设计的基础。豪泽与克劳辛的《质量屋》（*Harvard Business Review*，1988年）仍是最易读的 QFD 入门；迪特（Dieter）与施密特（Schmidt）的《工程设计》（*Engineering Design*，第6版，2021年）把 QFD、卡诺模型和设计要求表放在一起讨论。
